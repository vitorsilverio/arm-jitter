## Por que uma escada e não uma task

Medido antes de escrever (2026-10-06, `Aarch64Decoder` com 2935 linhas): o AdvSIMD é o último grupo do decoder
fora de tabela e ocupa ≈ 2 100 linhas (`decodeCryptoSha3` + `decodeAdvancedSimdInteger` e os sub-decoders/
tabelas de opcode que ele chama, linhas 778–2897). O `a64.decode` do QEMU tem ≈ 700 padrões nesse espaço, contra
≈ 110 do FP escalar da E15.14 (que já foi uma sessão inteira):

| Seção do `a64.decode` | Padrões |
|---|---|
| Crypto (AES, SHA, SHA512, four-register, imm2, XAR) | 31 |
| Copy / scalar copy | 7 |
| Scalar three same + scalar pairwise | 70 |
| Three same (inclui "three same extra" e FP16) | 167 |
| Scalar/vector × indexed element | 89 |
| Extract / TBL / permute / across lanes | 33 |
| Modified immediate + shift by immediate (vetorial) | 92 |
| Scalar shift by immediate | 45 |
| Scalar two-register misc | 70 |
| Two-register misc | 113 |

Cada sub-task migra um sub-espaço com o mesmo método das E15.10–E15.14: oráculo diferencial com os campos de
opcode ENUMERADOS (incluindo `Rm` quando ele é opcode — E15.9c), `QemuReference` + `objdump` em toda palavra
aceita, diff antes × depois vazio (ou só o que a task corrige, conferido no `objdump`).

## Desenho comum

- **Uma tabela só, `advSimdTable`**, que cresce a cada sub-task (as linhas de todas as classes `*Rows` do
  AdvSIMD/cripto juntas; a tabela não tem prioridade e o teste de sobreposição roda sobre a união —
  `AdvSimdPermuteCopyRowsTest#advSimdTableRowsNeverOverlap`). Cada sub-task troca um ramo da cascata por
  `decodeAdvSimdTable` e apaga os sub-decoders que ficaram órfãos.
- **Classes de linhas por família do ARM ARM** (abaixo de 800 linhas cada): `AdvSimdBit21ZeroRows` (formas com
  feature do `bit21=0`), `AdvSimdPermuteCopyRows`, `CryptoRows` (toda a criptografia, inclusive AES/SHA de dois
  registradores quando a E15.15d chegar lá), e as que as sub-tasks criarem.
- **Guarda G8 já existe:** `AdvSimdFpResidueG8Test` enumera os 4 prefixos AdvSIMD (inclusive o `0xce` do
  cripto) — cada sub-task reconfere com `objdump` e atualiza contagem/SHA só se o conjunto aceito mudar.
- **Última sub-task (E15.15g):** `decodeAdvancedSimdInteger` some; o roteamento do `bit26=1` vira "FP escalar →
  `scalarFpTable`, resto → `advSimdTable`"; bench de decode e `StepBench` como nas E15.10–E15.14.

## Achados de quem mede este espaço (para as próximas sub-tasks)

- O `QemuReference` precisa das faixas de linha de TODO o AdvSIMD (`845-1358,1372-1417,1530-1999`) e, se o
  oráculo enumerar `bit30=0` com prefixo `11110`, das do FP escalar também (`1359-1370,1418-1529`) — senão o FP
  escalar aparece como "sem padrão QEMU".
- O modo inverso (`!preset`) lista o que o QEMU aceita e o decoder recusa; a maior parte é recusa CORRETA (os
  padrões do QEMU aceitam `size`/`imm5` que o `trans_` recusa). Separar com `objdump` nas recusadas
  (`e15.15a-scripts/objdump-oraculo.sh <oráculo> <preset> recusadas <dir>`): o que o `objdump` desmonta é lacuna.

## O que muda em relação ao A64 (E15.9–E15.15)

1. **A cascata de 32 bits é ORDENADA e os padrões se sobrepõem de propósito** (`MOVW` antes do ALU genérico,
   `MLS`/`UMAAL`/exclusivos antes do halfword transfer, media antes do `LDR`/`STR`). A `DecodeTable` não tem
   prioridade. Regra da escada: **camadas** — uma lista de tabelas consultadas em ordem (precedente: a
   `systemFallbackTable` da E15.11). Dentro de uma camada o teste de sobreposição vale como no A64; entre
   camadas a ordem é dado explícito. Poucas camadas (o `ArmDecoder` ficou com 4, uma delas por um bug preservado — B22.11); camada nova só com o par de
   linhas que a exige citado no javadoc.
2. **"Sem a feature" tem DOIS significados na cascata**, e os dois são comportamento observável:
   - `if (casa && has(F))` → sem a feature a palavra **segue** para o resto da cascata (em ARMv4T um `QADD`
     vira `TST` de `S=0`). Na tabela: a linha some e uma camada mais baixa responde.
   - `if (casa) { if (!has(F)) return unimplemented; … }` → sem a feature a palavra é **recusada**. Na tabela:
     coluna nova `whenAbsent` do `DecodeRow` (o que a linha constrói quando o preset não tem a feature).
   O primeiro caso é candidato a G8 (palavra de uma instrução ausente decodificada como outra), mas a escada é
   **refactor puro**: preservar e, se o oráculo mostrar que é G8 de verdade, abrir task (regra 9) — o GBA/NDS
   rodam em cima desse comportamento e mudar sem medir os consumidores não é desta escada.
3. **Restrição de campo que hoje faz a palavra SEGUIR** (`PARALLEL_ALU` com `ppp`/`ttt` de buraco, `EXTEND`
   com `ff=01`) vira padrão exato (uma linha por valor válido). Restrição que hoje **recusa** continua dentro
   do construtor, que devolve `DecodedInstruction.unimplemented` (é um valor, não `null`).
4. **O espaço é enumerável.** A32 = 2³² palavras: o oráculo é **exaustivo**, antigo × novo no mesmo processo,
   `equals` do `DecodedInstruction`, todos os presets de `ArmArchitecture` — não há amostragem nem "campos
   enumerados". T16 = 2¹⁶ idem; T32 = 2³² idem (as duas halfwords). Refactor puro = 0 diferença, sem exceção.
5. **Infra compartilhada.** `DecodeRow`/`DecodeTable` saem de `decoder64` (package-private) para um pacote
   comum, genéricos no tipo da feature (`DecodeRow<F, T>`), como a E15.9 já previa.
6. **Perf não é gate** (decisão do usuário, 2026-10-06: terminar o E15 antes de perf; a regressão de decode por
   tabela é da E21). Cada sub-task mede e registra decode isolado + o `GbaInterpBench` (`e15.5-scripts/`).

## Desenho comum

- Pacote `dev.vitorsilverio.armjitter.decodetable` (`DecodeRow<F, T>`, `DecodeTable<T>`), `public`; o
  `DecodeTableInvariants` dos testes vai junto.
- Linhas em classes `*Rows` por família do ARM ARM, em `decoder/`, package-private, abaixo de 800 linhas;
  construtores = métodos estáticos referenciados por nome (`A32MultiplyRows::mls`), com o corpo que hoje está
  dentro do `if`.
- `T = DecodedInstruction`; o construtor recebe `(word, address)` e tira `Condition` da palavra.
- Os pontos de extensão (`DecoderExtension`, `ArmArchitecture#decoderExtensions()`/`thumb32DecoderExtensions`)
  são API pública (G3): continuam existindo; a sub-task de cada família decide se a extensão vira uma camada
  da tabela do decoder base ou só passa a decodificar por tabela por dentro.
- Guarda permanente por sub-task: teste de sobreposição por camada + alcance por linha (como no A64). O
  oráculo exaustivo fica em `e15.16x-scripts/` (minutos de CPU, fora do CI).

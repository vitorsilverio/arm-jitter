# B8.20 — A64: `REV64`/`REV32`/`REV16`, `XTN`/`SHLL`/`URECPE`/`URSQRTE`, `SQDMULL`/`SQDMLAL`/`SQDMLSL` escalares

**Trilha:** B · **Depende de:** B8.7 ✅, B8.8 ✅ · **Repo:** arm-jitter

## Contexto

Continuação da varredura sistemática de cobertura A64. B8.18 (`AND`/`BIC`/`ORR`/.../`CNT`/`NOT`/
`RBIT`) e B8.19 ("vector/scalar × indexed element") deixaram documentadas 3 lacunas pequenas e
independentes, fora de escopo de propósito por não caberem no título de nenhuma das duas:

1. `REV64`/`REV32`/`REV16` (B8.18, "Não inclui") — reversão de bytes/elementos por GRUPO, semântica
   de PERMUTAÇÃO de posição (não uma transformação por elemento), deixada de fora por exigir cuidado
   extra.
2. `XTN`/`SHLL`/`URECPE`/`URSQRTE` (B8.18, "Não inclui") — mesmo slot `Rm=00001` (narrow/widen) que
   B8.8 usa para `SQXTN`/`SQXTUN`/`UQXTN`, mas cada uma com uma exceção própria (`XTN` não satura,
   `SHLL` desloca por quantidade fixa, `URECPE`/`URSQRTE` são estimativas por tabela/fórmula).
3. `SQDMULL`/`SQDMLAL`/`SQDMLSL` escalares SEM índice (B8.19, "Candidatas restantes") — vivem no
   prefixo "three different" ESCALAR, que o decoder recusava incondicionalmente para `scalar=true`.

O usuário escolheu esta frente ("lacunas A64 pequenas") entre 4 candidatas (as 9 features A64 de
B11.5, `B12.1`, `B4.0.5`) numa sessão sem contexto prévio de qual delas seguir — ver
`tasks/FILA-EXECUCAO.md`.

## Inclui

- **`Ir64VectorUnaryOp`**: `REV64`/`REV32`/`REV16`/`URECPE`/`URSQRTE` novos. Reaproveitam o record
  `Ir64Op.VectorArithmeticUnary` já existente (um único operando `Rn`).
- **`Ir64VectorNarrowUnaryOp`**: `XTN` novo (MESMO opcode de `SQXTUN`, `U=0`) — reaproveita
  `Ir64Op.VectorArithmeticNarrowUnary`, sem saturação (diferente das outras 3).
- **`Ir64Op.VectorArithmeticWidening`**: ganha campo `boolean scalar` novo (breaking change de
  construtor, pacote `ir64` interno, sem impacto público — G3) — permite a forma escalar de
  `SQDMULL`/`SQDMLAL`/`SQDMLSL` reaproveitar 100% o record e o executor já existentes.
- **`SHLL`/`SHLL2`**: reaproveita 100% `Ir64Op.VectorShiftWidenImmediate`/`Ir64VectorShiftWidenOp.USHLL`
  (B8.8) — `SHLL` é literalmente "zero-extend, desloca à esquerda pela largura INTEIRA do elemento
  estreito" (`shift = 8 << esz`, quantidade FIXA em vez de imediato genérico, mas a fórmula do
  executor é idêntica). ZERO código novo de IR/executor para este mnemônico.
- **`Aarch64Decoder`**:
  - `decodeVectorUnaryOpcode`: 2 casos novos (`opcode=0b0_0001`→`REV32`/`REV64` por `U`,
    `opcode=0b0_0011`→`REV16` só `U=0`); os 3 excluídos da forma escalar (sem forma real).
  - `validateVectorUnaryEsz` novo: `REV64` aceita `esz<=2`, `REV32` aceita `esz<=1`, `REV16` só
    `esz=0` (grupo de 1 elemento seria no-op, reservado).
  - `decodeVectorNarrowUnaryOpcode`: ganha parâmetro `scalar`; opcode `0b0_0101`/`U=0` agora
    devolve `XTN` (SEM forma escalar) em vez de `null`.
  - Bloco `rm==ADVSIMD_INT_RM_NARROW_UNARY`: 2 desvios novos ANTES do fallback FP —
    `opcode==0b0_0111`/`U=1` (`SHLL`) e `opcode==0b1_1001`/`esz==WORD` (`URECPE`/`URSQRTE`, `U`
    distingue).
  - `decodeAdvancedSimdThreeDifferent`: ganha parâmetro `scalar`; o dispatcher
    (`decodeAdvancedSimdInteger`) agora permite `scalar=true` só quando `!u` e `opcode` é um dos 3
    valores de `SQDMULL`/`SQDMLAL`/`SQDMLSL` (`0b1_1010`/`0b1_0010`/`0b1_0110`), rejeitando
    `esz==0`(byte, já existia)/`esz==3`(doubleword, novo) — G8.
- **Executor** (`Ir64VectorArithmeticExecutor`):
  - `executeUnary`: desvio novo para `REV64`/`REV32`/`REV16` ANTES do laço genérico (são permutação
    de posição, não transformação por elemento) — método `executeReverseGroups` novo, dentro de cada
    grupo consecutivo de `containerBits` (64/32/16) inverte a ORDEM dos elementos de `esz` bytes.
    Casos novos no `switch` principal para `URECPE`/`URSQRTE` (pontuais, cabem no laço).
  - `unsignedRecipEstimate32`/`recipEstimateTable`/`unsignedRSqrtEstimate32`/`rSqrtEstimateTable`
    novos — algoritmo PURO-INTEIRO do ARM DDI 0487, conferido bit a bit contra
    `helper_recpe_u32`/`recip_estimate`/`helper_rsqrte_u32`/`do_recip_sqrt_estimate` do QEMU
    (`target/arm/tcg/vfp_helper.c`, via `WebFetch` nesta sessão) — NÃO é uma tabela de 256 entradas
    (a implementação real do QEMU/manual é uma fórmula fechada, mais barata e menos sujeita a erro
    de transcrição do que eu esperava ao planejar a task).
  - `executeNarrowUnary`: caso novo `XTN -> wide` (sem saturação).
  - `executeWidening`: agora aceita `op.scalar()` — quando `true`, processa 1 único elemento (sem
    metade de registrador) e termina com `finishScalarAwareWrite` (MESMO padrão de
    `executeWideningByElement`, B8.19).

## Não inclui

- Emissão ASM nativa — mesma decisão de todo `Kind` de AdvSIMD desde B8.6 (cai no interpretado).
- Qualquer outra lacuna A64 (a próxima varredura sistemática segue aberta).

## Armadilhas

- `URECPE`/`URSQRTE` vivem no MESMO opcode (`0b1_1001`) que `FCVTAS`/`FCVTAU` usam no slot
  narrow/widen — a diferença é o bit ALTO de `esz` (`a`, `esz>>1`): `FCVTAS`/`FCVTAU` só existem com
  `a=0` (`esz` `0`/`1`), `URECPE`/`URSQRTE` só com `a=1` E `esz==WORD` (`esz=2`) — `esz=3` (`a=1`,
  `sz=1`) permanece reservado (cai no fallback FP, que devolve `null` para essa combinação, G8
  preservado sem mudança).
- O comentário original de B8.8 sobre o opcode `0b0_0101`/`U=0` ("é `FCVTN`, fora de escopo") estava
  ERRADO — o corpus real confirma que é `XTN`. `FCVTN` vive em outro opcode, ainda fora de escopo.
- `executeWidening` (forma vetorial "three different") e `executeWideningByElement` (B8.19, forma
  indexada) agora TÊM a mesma forma escalar para `SQDMULL`/`SQDMLAL`/`SQDMLSL`, mas são espaços de
  ENCODING diferentes (`Rm` livre vs. `Rm`+índice) — não confundir os dois ao ler o decoder.
- `REV64`/`REV32`/`REV16` PERMUTAM posição, não transformam valor — não cabem no `switch` genérico
  de `executeUnary` (que assume 1 elemento de entrada → 1 elemento de saída, no mesmo índice).

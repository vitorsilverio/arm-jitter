# B17.12 — Endereçamento: `ADDVL`/`ADDPL`/`RDVL` (stack) e `ADR` vetorial — 10 encodings

**Trilha:** B · **Repo:** arm-jitter (+ revalidação G5) · **Depende de:** B17.5 (⬜)
**Épico:** `b17-plano-sve.md` · **Status:** ⬜ (spec escrita 2026-09-14, ainda não executada)

## Contexto

A menor task de conteúdo do épico — e a que **expõe o `VL` ao software**. `RDVL`/`ADDVL`/`ADDPL`
são literalmente como um binário SVE descobre e usa o comprimento de vetor da máquina em que está
rodando (alocação de frame, aritmética de ponteiro). Se o `VL` do `arm-jitter` estiver errado, é
aqui que o software real percebe.

### Os encodings reais (todos os 10)

```
@rd_rn_i6       ........ ... rn:5 ..... imm:s6 rd:5             &rri
@rd_rn_msz_rm   ........ ... rm:5 .... imm:2 rn:5 rd:5          &rrri

# SVE stack frame adjustment
ADDVL           00000100 001 ..... 01010 ...... .....           @rd_rn_i6
ADDSVL          00000100 001 ..... 01011 ...... .....           @rd_rn_i6
ADDPL           00000100 011 ..... 01010 ...... .....           @rd_rn_i6
ADDSPL          00000100 011 ..... 01011 ...... .....           @rd_rn_i6

# SVE stack frame size
RDVL            00000100 101 11111 01010 imm:s6 rd:5
RDSVL           00000100 101 11111 01011 imm:s6 rd:5

# SVE vector address generation
ADR_s32         00000100 00 1 ..... 1010 .. ..... .....         @rd_rn_msz_rm
ADR_u32         00000100 01 1 ..... 1010 .. ..... .....         @rd_rn_msz_rm
ADR_p32         00000100 10 1 ..... 1010 .. ..... .....         @rd_rn_msz_rm
ADR_p64         00000100 11 1 ..... 1010 .. ..... .....         @rd_rn_msz_rm
```

### Semântica, confirmada por `WebFetch` no QEMU (`translate-sve.c`)

```c
tcg_gen_addi_i64(rd, rn, a->imm * vec_full_reg_size(s));
```

Ou seja:

- **`ADDVL Xd, Xn, #imm`** = `Xn + imm × (VL/8)` bytes.
- **`ADDPL Xd, Xn, #imm`** = `Xn + imm × (PL/8)` bytes, com `PL = VL/8` bits ⇒ o fator é `VL/64`.
- **`RDVL Xd, #imm`** = `imm × (VL/8)`. É `ADDVL` com `Xn = XZR` (o padrão fixa `rn=11111`).
- `imm` é **com sinal de 6 bits** (`imm:s6`, −32..+31).
- **`Xd`/`Xn` são `SP`-capazes** (é o uso principal: `ADDVL SP, SP, #-4`). `11111` = `SP`, não
  `XZR`, nestas instruções — **confirmar no manual** (Armadilha 2).

`ADR_*` gera endereços VETORIAIS: `Zd[i] = Zn[i] + (Zm[i] << msz)`, com as 4 variantes diferindo em
como `Zm` é interpretado — `_s32` (offset de 32 bits com sinal, estendido), `_u32` (sem sinal),
`_p32`/`_p64` ("packed", offsets do mesmo tamanho do elemento). `msz` (`imm:2`) é o shift de escala.

### Achados desta rodada de spec

1. **`ADDSVL`/`ADDSPL`/`RDSVL` são SME, não SVE.** O `S` é de *Streaming*: usam o `SVL` (Streaming
   Vector Length, `SMCR_ELx`), não o `VL`. São 3 das 6 linhas do grupo de stack e dependem do modo
   streaming que só o épico **B18** cria. **Não implementá-las por analogia** — decodificá-las como
   `ADDVL` daria o valor errado assim que o modo streaming existir (misdecode silencioso, G8).
   Saída honesta: recusar as 3 (`null`, `❌`), registrar como pendência nomeada da B18, e a B17.26
   as contabiliza como trabalho pendente (não exclusão).
   ⚠️ Isso derruba a contagem real desta task de 10 para **7 implementadas + 3 pendentes**; a
   partição normativa continua atribuindo as 10 células a esta task (a exaustividade exige isso),
   mas o Aceite distingue.
2. **`ADR_p32`/`ADR_p64` não são "32/64 bits do resultado"** — são as formas "packed", em que o
   offset tem o mesmo tamanho do elemento (`esz=2` e `esz=3` respectivamente). `_s32`/`_u32` são as
   formas "unpacked" com elemento de 64 bits e offset de 32. Confundir as 4 é fácil: os bits 23:22
   selecionam a variante, **não** o `esz` genérico.
3. **`RDVL`/`RDSVL` têm `rn` fixo `11111` no padrão** — não há campo. Um decoder genérico de
   `@rd_rn_i6` aplicado a elas leria `rn` como registrador, o que é inofensivo (é sempre 31) mas
   perde a distinção de que é uma instrução diferente.
4. **`imm` com sinal**: `ADDVL SP, SP, #-4` é o caso normal (alocar frame). Tratar `imm:s6` como
   sem sinal quebra todo prólogo de função SVE real.

## Objetivo

Um binário SVE real consegue alocar frame (`ADDVL SP, SP, #-n`), descobrir o `VL` (`RDVL`) e fazer
aritmética de ponteiro por predicado (`ADDPL`), com o `VL` que a B17.3 configurou; e `ADR` vetorial
gera endereços por elemento.

## Inclui

1. **`ADDVL`**, **`ADDPL`**, **`RDVL`** (3) — leem `vectorLengthBytes()`/`predicateLengthBytes()` da
   B17.3, **nunca** uma constante (G6).
2. **`ADR_s32`**, **`ADR_u32`**, **`ADR_p32`**, **`ADR_p64`** (4).
3. **Recusa explícita** de `ADDSVL`/`ADDSPL`/`RDSVL` (3) com pendência nomeada para a B18.
4. Testes (ver Aceite).

## Não inclui

- **`CNTB`/`CNTD`/`INCDEC_r`** (element count, que também leem o `VL`) — B17.4.
- **Modo streaming / `SVL` / `SMCR_ELx`** — B18.
- **Gather/scatter com base vetorial** (que CONSOMEM os endereços que `ADR` produz) — B17.19/B17.25.
- **Emissão nativa/Truffle** — padrão da trilha B.

## Aceite

- `RDVL Xd, #1` devolve `VL/8`; `RDVL Xd, #-1` devolve `−VL/8`; `RDVL Xd, #31` e `#-32` corretos.
- `ADDVL SP, SP, #-4` subtrai `4 × VL/8` do `SP` (e o destino é o `SP`, não o `XZR` — Armadilha 2).
- `ADDPL Xd, Xn, #imm` usa o fator `VL/64`, **não** `VL/8`.
- **Testado em pelo menos dois `VL`** — é a task em que o `VL` é o resultado, não um detalhe.
- As 4 formas de `ADR` produzem `Zd[i] = Zn[i] + (extend(Zm[i]) << msz)` com a extensão correta por
  variante; `msz = 0..3`.
- `ADDSVL`/`ADDSPL`/`RDSVL` **não decodificam** (continuam `❌` honesto) e o `## Resultado` registra
  a pendência nomeada para a B18.
- `mvn -o test` verde + G5 verde nos 5 consumidores.

## Armadilhas

1. **`ADDSVL`/`ADDSPL`/`RDSVL` são SME** (Achado 1). Decodificá-las como as formas SVE é o
   misdecode silencioso que o G8 proíbe — e seria descoberto só quando a B18 ligasse o modo
   streaming.
2. **`11111` é `SP` aqui, não `XZR`.** O achado da B6.14 (`Rd|SP` resolvido só pela flag do
   decoder) mostra que este projeto já errou exatamente isso uma vez. Conferir no manual **e**
   testar com `Rd = 31`.
3. **`imm:s6` é com sinal** (Achado 4).
4. **`ADDPL` usa `PL`, não `VL`** — o fator é 8× menor. Um `ADDPL` com o fator de `ADDVL` desloca
   o ponteiro de predicado 8× longe demais, e isso só quebra em código que de fato use predicados
   na pilha (spill de `P<n>`), não em teste sintético.
5. **`ADR` não acessa memória** — só calcula. Não plugar no caminho de `Load`/`Store` nem no
   `AddressSpace64`.
6. **As 4 variantes de `ADR` vêm dos bits 23:22 como OPCODE**, não como `esz` (Achado 2).

## Não fazer

- Não implementar as 3 formas streaming (B18).
- Não usar constante de `VL` em lugar nenhum (G6).
- Não confundir `ADDPL` com `ADDVL`.
- Não tratar `Rd = 31` como `XZR` sem confirmar.

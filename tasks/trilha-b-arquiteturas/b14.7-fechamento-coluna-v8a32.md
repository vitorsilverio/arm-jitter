## Contexto

As B14.1-B14.6 são **todas zero-diff em `docs/COBERTURA-ISA.md`**, de propósito: o preset
`ARMV8A_32` existe e decodifica, mas não é medido. Esta task é o oposto — é a **única task

### O que muda na tabela (medido lendo `IsaCoverageReport`)

`core/src/test/java/dev/vitorsilverio/armjitter/tools/IsaCoverageReport.java`:

```java
private static final Map<String, ArmArchitecture> ARM_ARCHITECTURES = new LinkedHashMap<>();
static {
    ARM_ARCHITECTURES.put("v4T", ArmArchitecture.ARMV4T);
    ... ARM_ARCHITECTURES.put("v7-A", ArmArchitecture.ARMV7A);
    ARM_ARCHITECTURES.put("v6-M", ArmArchitecture.ARMV6M);
    ARM_ARCHITECTURES.put("v7-M", ArmArchitecture.ARMV7M);
}
```

Acrescentar uma entrada aqui acrescenta **uma coluna a TODOS os 13 grupos de uma vez** — cada grupo
é medido por `group.applicability().appliesTo(architecture)` (linha ~707). E:

```java
new Group("vfp-uncond.decode", "VFP — formas incondicionais (ARMv8-A)", 32, Probe.ARM32, true,
        NOT_IN_ANY_PRESET, "`VSEL`/`VMAXNM`/`VMINNM`/`VRINT`/`VCVTA` são ARMv8-A de 32 bits."),
```

`NOT_IN_ANY_PRESET` (`arch -> false`) tem que virar um `Applicability` de verdade — o padrão já
existe na mesma classe (`VFP = arch -> arch.has(ArmFeature.VFPV2)`), então é
`ARMV8_FP = arch -> arch.has(ArmFeature.ARMV8_FP)`.

### 🔴 Achado real não previsto pela spec: falso positivo na própria ferramenta de medição

Antes da auditoria do tsv, a primeira geração da tabela mostrou `vfp-uncond.decode` em **14/17**
(não 17/17) — `VMAXNM_hp`/`_sp`/`_dp` mediam `⚠️` (FALLBACK), não `✅`, enquanto `VMINNM_hp`/`_sp`/`_dp`
já mediam `✅` corretamente. Investigado por probe direto (`ArmDecoder` isolado, fora do harness):

- `VMAXNM_sp` (`cond=1111`, `bit6=0`) decodifica CORRETAMENTE como `VFP_ALU`/`MAXNM` (`imm=17`).
- O MESMO padrão de bits com `cond=1110` (AL) é, genuinamente, a instrução **`VDIV`**
  (`bit23=1,bits21:20=00,bit6=0` é literalmente o encoding de `VDIV` no espaço VFP condicional,
  ARM DDI 0487) — decodifica como `VFP_ALU`/`DIV` (`imm=3`).
- O heurístico `IsaCoverageReport#decodesTheSameIgnoringCondition` (usado para achar quando o
  decoder "ignora" `cond==1111` e trata a palavra como a instrução condicional de mesmo padrão —
  ver E6/B14.4) comparava só `DecodedInstruction.kind()`. `VFP_ALU` é um `Kind` "guarda-chuva"
  que empacota a operação real em `immediate` (o ordinal de `IrOp.VfpOperation`) — `MAXNM` e `DIV`
  têm o MESMO `Kind` e `immediate` DIFERENTE, então a comparação rasa via `Kind` os via como "a
  mesma instrução" e acusava misdecode onde as duas são instruções reais, distintas e
  corretamente decodificadas. `VMINNM_sp` (`bit6=1`) não sofria o mesmo falso positivo porque
  `bit6=1` não corresponde a nenhum encoding condicional válido naquele ponto (o decoder devolve
  `UNIMPLEMENTED` para a versão `cond=1110`, kinds diferentes, sem alarme).
- **Fix**: `decodesTheSameIgnoringCondition` agora chama `sameSemantics`, que compara TODOS os
  campos semânticos de `DecodedInstruction` (kind, registradores, `immediate`, todas as flags,
  `blockTransferMode`, `liftedOp`) — só `address`/`raw`/`condition`/`instructionSet` ficam de fora
  (esses DEVEM diferir entre as duas sondas por construção). Confirmado que isto não regride
  nenhuma detecção existente: antes da mudança havia 2 `⚠️` no arquivo inteiro (ambos A64,
  não afetados por este código); depois, 5 (os 2 antigos + os 3 novos `✅` de `VMAXNM_hp/sp/dp`
  passaram a contar como `SUPPORTED`, e nenhum outro grupo/coluna mudou).

# B13.16 — NEON no encoding **T32**: transformar e delegar (as mesmas 297 linhas)

**Trilha:** B · **Repo:** arm-jitter (+ revalidação G5) · **Depende de:** B13.14 (na prática, B13.9-B13.15)
**Épico:** `b13-plano-neon-a32.md` · **Status:** ⬜

## Contexto

Todo o épico B13 até aqui implementou o encoding **A32** (`cond=0b1111`, espaço incondicional). O
Thumb-2 tem os MESMOS 297 encodings de `neon-dp.decode`, num arranjo de bits diferente — e o próprio
cabeçalho do arquivo diz que a diferença é mecânica:

```
# Encodings for Neon data processing instructions where the T32 encoding
# is a simple transformation of the A32 encoding.
# More specifically, this file covers instructions where the A32 encoding is
#   0b1111_001p_qqqq_qqqq_qqqq_qqqq_qqqq_qqqq
# and the T32 encoding is
#   0b111p_1111_qqqq_qqqq_qqqq_qqqq_qqqq_qqqq
# This file works on the A32 encoding only; calling code for T32 has to
# transform the insn into the A32 version first.
```

⇒ **Uma task de "transformar e delegar", não uma reimplementação.** O plano B13 já suspeitava disso;
esta spec confirma pela fonte.

### A transformação, bit a bit

| | bits[31:29] | bit28 | bits[27:25] | bit24 | bits[23:0] |
|---|---|---|---|---|---|
| **A32** | `111` | `1` | `001` | **`p`** | `q…q` |
| **T32** | `111` | **`p`** | `1` | `111` | `q…q` |

Isto é: `p` (que em A32 é o bit24, tipicamente o `U` das famílias) mora no **bit28** em T32, e os
bits[27:24] são `1111`. Os 24 bits baixos são **idênticos**.

```java
// T32 → A32
int p = (thumbWord >>> 28) & 1;
int a32 = 0xF2000000 | (p << 24) | (thumbWord & 0x00FF_FFFF);
```

E o reconhecimento do frame T32 é `(thumbWord & 0xEF00_0000) == 0xEF00_0000`
(bits[31:29]=`111`, bits[27:24]=`1111`) — **conferir essa máscara contra o `.decode` e contra o
`translate.c` antes de usar**, porque ela é a única coisa que separa este espaço do resto do
Thumb-2.

### `neon-shared.decode` NÃO precisa desta task

O cabeçalho daquele arquivo diz: *"Encodings for Neon instructions whose encoding is the same for
both A32 and T32."* ⇒ as 23 linhas de B13.17-B13.21 já valem para os dois encodings quando forem
implementadas. **Esta task cobre só `neon-dp` (297) e, se aplicável, `neon-ls` (5).**

**Conferir `neon-ls.decode`**: se o cabeçalho dele também descrever a transformação, as 5 linhas de
B13.3 entram aqui; se disser que o encoding é compartilhado, não entram. **Medir, não supor.**

**Leitura obrigatória**: o cabeçalho de `neon-dp.decode` e de `neon-ls.decode`, a **B2.1**
(`## Resultado` — a infra de fetch de 32 bits do Thumb-2 e o gate `THUMB2`), a **B2.6** e a **B2.7**
(como as extensões Thumb-2 são registradas — `withThumb32DecoderExtensions`), e os `## Resultado` de
B13.3 e B13.7 (os decoders A32 que serão delegados). No código:
`decoder/ThumbDecoder`, `arch/ArmArchitecture#withThumb32DecoderExtensions` e a lista de
`Thumb2*Decoder`, todos os `decoder/Neon*Decoder` criados pelo épico B13.

## Objetivo

Os mesmos encodings NEON decodificam também em **Thumb-2**, gateados por `ArmFeature.ADVANCED_SIMD`
(mais `THUMB2`), **sem duplicar nenhum decoder**: um adaptador transforma a palavra e delega aos
decoders A32 já existentes. Zero-diff de runtime (nenhum preset declara `ADVANCED_SIMD`) e
`docs/COBERTURA-ISA.md` byte a byte idêntica.

## Inclui

1. **`decoder/Thumb2NeonDecoder`** — extensão Thumb-2 nova que:
   - reconhece o frame T32 do espaço NEON;
   - transforma a palavra para a forma A32;
   - **delega** a cada decoder A32 do épico (`NeonDataProcessingDecoder`, `NeonShiftImmediateDecoder`,
     `NeonModifiedImmediateDecoder`, `NeonThreeRegDifferentDecoder`, `NeonTwoRegMiscDecoder`, …), na
     mesma ordem em que eles são consultados no caminho A32;
   - devolve o `DecodedInstruction` com o **`raw` ORIGINAL de T32** e `InstructionSet.THUMB` — ver
     Armadilha 2.
2. **Registro** em `withThumb32DecoderExtensions` da arquitetura de teste com `ADVANCED_SIMD` (nenhum
   preset de produção muda — B13.22).
3. **Gate duplo**: sem `ADVANCED_SIMD` **ou** sem `THUMB2`, `null`.
4. Testes (ver Aceite).

## Não inclui

- **Reimplementar qualquer semântica** — se esta task escrever um laço de execução, está errada.
- **`neon-shared.decode`** (B13.17-B13.21) — encoding já compartilhado.
- **Preset declarando `ADVANCED_SIMD`** ⇒ B13.22.
- **Nativo/Truffle** ⇒ C12.8/A10.7.

## Especificação

### Por que delegar, e não reescrever

Duplicar os decoders para T32 duplicaria também **todas** as armadilhas do épico (o `L`=`immh[3]` da
B13.7, o `size==0b11` da B13.10, o layout próprio da B13.12, o `null` que reserva espaço…), e as duas
cópias divergiriam na primeira correção. A delegação é a única forma de a correção valer para os dois
encodings — é o mesmo princípio D1 da RFC B13.2, aplicado ao encoding em vez de à semântica.

### A ordem de consulta importa

Os decoders A32 do épico reservam espaço uns para os outros devolvendo `null` (B13.7↔B13.9,
B13.10↔B13.12, B13.12↔B13.13/14/15). O adaptador **tem que consultá-los na mesma ordem** do caminho
A32, ou um encoding cai no decoder errado. **Não** reimplementar a ordem — obtê-la da mesma lista.

## Aceite

- **Equivalência A32↔T32**: para uma amostra que cubra **todas as seções** do épico (three-same,
  2-reg-and-shift, `Vimm_1r`, 3-reg-different, 2-reg-and-scalar, two-reg-misc, conversões, permuta,
  cripto), a palavra T32 e a palavra A32 correspondente produzem `IrOp` **iguais** (mesmo record,
  mesmos campos). Este é o aceite central e substitui testar 297 encodings um a um.
- **`raw` e `InstructionSet` corretos**: o `DecodedInstruction` devolvido carrega a palavra T32
  original e `InstructionSet.THUMB` — não a palavra transformada.
- **Gate duplo**: sem `ADVANCED_SIMD` ⇒ `null`; com `ADVANCED_SIMD` mas sem `THUMB2` ⇒ `null`.
- **Zero-diff Thumb-2**: as suítes de B2.x/B3.2 passam **sem edição** — o adaptador não pode
  engolir encoding Thumb-2 existente. **Teste explícito** com um `LDR.W`/`MOVW` que casaria a máscara
  se ela estivesse larga demais.
- **Zero-diff A32**: as suítes de todo o épico B13 sem edição.
- `docs/COBERTURA-ISA.md` **byte a byte idêntica** (o grupo `neon-dp` é medido no encoding A32; esta
  task não muda a medição — **confirmar e registrar**, porque é contraintuitivo).
- `mvn -o test` verde + G5 verde nos 5 consumidores.

## Armadilhas

1. **A máscara do frame T32 é o risco central.** Larga demais, engole Thumb-2 legítimo (`LDR.W`,
   coprocessador, VFP); estreita demais, perde encodings. Conferir contra a fonte e testar os dois
   lados.
2. **Devolver a palavra transformada como `raw`** quebra tudo que depende do endereço/tamanho da
   instrução (traço, exceções, `Fetch`). O `raw` é o T32 original.
3. **Ordem de consulta dos decoders** — ver "Especificação".
4. **NEON em T32 continua incondicional** (não entra em bloco `IT`): conferir o que o ARM DDI 0406C
   diz sobre NEON dentro de `IT` e garantir que o adaptador não aplique condição.
5. **Não duplicar decoder.** Se a task crescer para além de um adaptador, parar e reler.
6. **`neon-ls` pode ou não entrar** — medir pelo cabeçalho do arquivo.

## Não fazer

- Não reimplementar semântica nem decoders.
- Não mexer nos decoders A32 do épico.
- Não declarar `ADVANCED_SIMD` em preset (B13.22).
- Não aplicar condição de `IT` a NEON.

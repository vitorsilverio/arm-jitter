# B8.6 — A64 AdvSIMD load/store estruturado (`LD1`-`LD4`/`ST1`-`ST4`/`LD1R`-`LD4R`)

**Trilha:** B · **Depende de:** B8.5 ✅ (não bloqueante — decode-only, sem dependência real) · **Repo:** arm-jitter

## Contexto

Primeiro degrau da escada AdvSIMD do plano mestre `b7-plano-cobertura-isa.md` (`B8.6`-`B8.11`,
~690 lacunas — a Onda 5 chegou ao topo da fila em 2026-08-24 com B10/Q11 fechados e nada mais
priorizado à frente). Escopo original do plano: "AdvSIMD load/store estruturado: `LD1`-`LD4`/
`ST1`-`ST4` e variantes | ~60".

⚠️ **Sem spec formal escrita antes da implementação** — mesmo padrão ad-hoc de B6.9/B6.11/B8.1/
B8.4/B8.5/B9.1/B9.3/B9.5 (task pequena o bastante para não precisar de rodada de spec separada
prévia). Este arquivo documenta o resultado, não um plano prévio.

## Achado que muda o escopo: banco `V` precisou virar 128 bits de verdade

Toda a fatia A64 anterior (B6.5.x-B8.5) guardava só os 64 bits baixos de cada `V<n>`
(`Aarch64FpRegisters`, decisão explícita B6.5.1 D4 — "NEON/bits 127:64 fora de escopo"). AdvSIMD
load/store estruturado é a PRIMEIRA instrução real que precisa dos 64 bits altos (arranjos
`.16B`/`.8H`/`.4S`/`.2D`) — não dava para implementar como decode-only adiável, ao contrário de
outras lacunas desta fila.

**Decisão do usuário (perguntada explicitamente antes de codificar, dado que reabre B6.5.1 D4):
estender o banco `V` para 128 bits reais AGORA, como parte do escopo desta task**, em vez de uma
task de infra separada — é pré-requisito de B8.6 E de toda a escada B8.7-B8.10 que vem depois, não
faz sentido fatiar.

`Aarch64FpRegisters` reescrita: armazenamento passa a ser um par `(lo, hi)` de 64 bits por
registrador (nenhum elemento de lane cruza essa fronteira — todos os tamanhos AdvSIMD de 8/16/32/64
bits dividem 64 igualmente). API pré-existente (`s`/`setS`/`d`/`setD`/`sFloat`/`setSFloat`/
`dDouble`/`setDDouble`) preservada byte a byte (G3) — `setS`/`setD` continuam zerando o resto do
registrador ("SIMD&FP destructive write", B6.5.1 D3), só que agora há de fato bits altos reais para
zerar (antes disso era implícito, por não existir armazenamento). API nova: `low64`/`high64`/`setQ`
(escrita crua de 128 bits, sem a semântica "zera o resto"), `element`/`setElement` (lane individual
por tamanho `1<<sizeLog2`) e `replicateElement` (`LD1R`-`LD4R`). `saveState`/`loadState`/`snapshot`
atualizados para os 128 bits — `Aarch64CpuSnapshot#vRegisters` (harness de equivalência ASM×interp)
não precisou de nenhuma mudança própria, porque só compara o `long[]` que `snapshot()` devolve
(agora `64` elementos em vez de `32`, `lo`/`hi` por registrador).

## Triagem real (decode)

`V=1` dentro da classe `Loads and Stores` (bit27=1, bit25=0) SEMPRE lançava `unsupported`
incondicionalmente, ANTES de olhar qualquer outro bit — decisão herdada de B6.2 que nunca tinha
sido revisitada. Load/store de registrador escalar SIMD&FP (`LDR`/`STR`/`LDP`/`STP` de `D`/`S`/`Q`)
segue INTOCADO e fora de escopo (não foi pedido por nenhuma task desta fila até agora — acesso a
memória para FP escalar simplesmente não existe ainda neste emulador, achado que já estava
documentado indiretamente em B8.5 "FMOV_xu/FMOV_ux... 64 bits altos que só chegam com AdvSIMD
B8.6+"). Dentro de `V=1`, dois grupos reais foram identificados e implementados, fatos conferidos
contra `a64.decode`/`translate-a64.c` reais do QEMU (`@ldst_mult`/`@ldst_single_*`/
`LD_single_repl`, `trans_LD_mult`/`trans_ST_mult`/`trans_LD_single`/`trans_ST_single`/
`trans_LD_single_repl`):

- **`AdvSIMD load/store multiple structures`** (bits[29:24]=`001100`): `rpt`×`selem` registradores
  consecutivos, elementos INTERCALADOS na memória quando `selem>1`. O nome de cada instrução
  (`LDn`/`STn`) depende só de `selem` — `LD1`/`ST1` também cobre as formas "vários registradores
  não entrelaçados" (`rpt=2/3/4`, `selem=1`), distintas de `LD2`-`LD4` (`rpt=1`, `selem=2/3/4`).
- **`AdvSIMD load/store single structure`** (bits[29:24]=`001101`): UM elemento por registrador,
  numa lane específica (`index`), sem afetar o resto do registrador — inclui a forma "replicar"
  (`LD1R`-`LD4R`, opcode-alto=`11`, só existe como `LD`, nunca `ST`). `selem` usa os MESMOS 2 bits
  espalhados (`bit13`+`bit21`/`S`) nas 3 famílias de tamanho + replicar; o resto dos bits muda de
  significado por família (byte/half/word/doubleword) — ver os comentários de
  `decodeAdvancedSimdLoadStoreSingle` no decoder para o detalhe campo a campo. O caso doubleword é
  o único onde `Q` É o próprio bit de índice (só 2 lanes de 8 bytes existem), não um bit
  independente combinado com outros.

Todas as combinações reservadas (opcode de `rpt`/`selem` fora da tabela real, bits "must be zero"
setados, `Rm≠0` sem pós-índice, `size=doubleword`+`!Q`+`selem≠1` na forma múltipla, `ST` com
opcode-alto de replicar) lançam `unsupported` explicitamente (G8) em vez de decodificar errado.

## Inclui

- `Aarch64FpRegisters`: banco `V` de 128 bits reais (ver seção acima).
- 3 `Ir64Op` novos: `VectorLoadStoreMultiple`, `VectorLoadStoreSingle`, `VectorLoadSingleReplicate`
  (`Kind` 53-55).
- Decoder: `decodeAdvancedSimdLoadStoreMultiple`/`decodeAdvancedSimdLoadStoreSingle` em
  `Aarch64Decoder`, roteados de dentro do `V=1` que antes era sempre `unsupported`.
- Executor: 3 métodos novos em `Ir64BlockExecutor` (semântica interpretada, oráculo G1) — nenhum
  Kind novo entra em `Ir64NativePolicy` (cai no `InterpretedIr64CodeEmitter`, mesma decisão de
  todo `Kind` novo desde B8.4/B8.5).
- Testes: `Aarch64AdvSimdLoadStoreDecoderTest` (30 casos, corpus PRÓPRIO via
  `aarch64-none-elf-as`/`objdump` reais — devkitA64 disponível nesta sessão, cada opcode citado com
  a linha exata do `objdump`) + `Ir64BlockExecutorB86Test` (13 casos: desentrelaçar/entrelaçar
  `LD2`/`ST2`, zerar bits altos não-quad, escrita/leitura de lane única sem afetar o resto do
  registrador, replicar quad/não-quad, pós-índice imediato e por registrador nas 3 formas).

## Não inclui

- Load/store escalar SIMD&FP (`LDR`/`STR`/`LDP`/`STP` de `D`/`S`/`Q`) — outro subconjunto de `V=1`,
  nunca implementado por nenhuma task até agora, fora do pedido desta task.
- Emissão ASM nativa para os 3 `Kind`s novos — cai no interpretado, mesmo padrão de todo `Kind`
  novo desde B8.4.
- `B8.7`-`B8.10` (o resto de AdvSIMD: aritmética/comparação, deslocamento/saturação, FP vetorial,
  permutação/redução/tabela) e `B8.11` (extensões opcionais) — degraus seguintes da mesma escada.

## Armadilhas (para quem pegar B8.7+ depois)

- `selem` usa 2 bits ESPALHADOS (`bit13` baixo, `bit21`/`S` alto) na forma single-structure —
  fácil de errar a ordem (o decodetree do QEMU lista `13:1 21:1`, que decodifica como
  `(bit13<<1)|bit21`, NÃO o inverso).
- No formulário `doubleword` de single-structure, o mesmo bit que é `Q` nas outras 3 famílias É o
  próprio `index` (só 2 valores possíveis) — não existe um `Q` independente ali.
- `rm=-1` é o sentinela deste emulador para "pós-índice imediato" nos 3 `Ir64Op` novos (mesma
  convenção de `Store64#rm`) — o encoding real usa `Rm=11111` para isso, nunca leia esse valor como
  "registrador `X31`".
- A forma múltipla zera os bits altos (`!Q`) numa passada SEPARADA depois de copiar todos os
  elementos (nunca inline no loop principal) — fazer inline erraria quando `selem>1` reaproveita o
  mesmo registrador em iterações diferentes de `e` antes de todos os elementos daquele registrador
  terem sido escritos.

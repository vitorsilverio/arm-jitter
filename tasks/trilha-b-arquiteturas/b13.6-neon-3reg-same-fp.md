# B13.6 — NEON 3-reg-same ponto flutuante (A32)

**Trilha:** B · **Repo:** arm-jitter (+ revalidação G5 nos consumidores) · **Depende de:** B13.1, B13.2, B13.3, B13.4, B13.5
**Épico:** `b13-plano-neon-a32.md` · **Status:** ⬜

## Contexto

Quarto degrau de conteúdo do épico B13. A **B13.4** fechou a parte INTEIRA não saturante de
"3-reg-same" de `neon-dp.decode` e a **B13.5** fechou as famílias saturantes / de deslocamento por
registrador. Ambas deixaram explicitamente para esta task todo o subespaço de **ponto flutuante** do
mesmo frame `(raw & 0xFE80_0000) == 0xF200_0000` (ver B13.4 e B13.5 "Não inclui"):

- `opc=1100 op=1 U=0` → `VFMA_fp` / `VFMS_fp` (multiply-accumulate FUNDIDO);
- `opc=1101` → `VADD_fp` / `VSUB_fp` / `VPADD_fp` / `VABD_fp` / `VMLA_fp` / `VMLS_fp` / `VMUL_fp`;
- `opc=1110` → `VCEQ_fp` / `VCGE_fp` / `VCGT_fp` / `VACGE_fp` / `VACGT_fp`;
- `opc=1111` → `VMAX_fp` / `VMIN_fp` / `VPMAX_fp` / `VPMIN_fp` / `VRECPS` / `VRSQRTS` /
  `VMAXNM_fp` / `VMINNM_fp`.

O lado A64 **já implementou toda essa semântica** na B8.9 (`Ir64VectorFpArithmeticExecutor#executeThreeSame`
e `#executePairwise`), mas — ao contrário do que B13.4/B13.5 fizeram com o inteiro — o FP **ainda não
foi migrado** para o núcleo compartilhado `advsimd/AdvSimdLanes`. Esta task **faz a migração**
(D1 da RFC B13.2 — uma fonte de verdade) e liga o decode A32 dessas famílias.

**Leitura obrigatória antes de começar**: `docs/RFC-NEON-NUCLEO-VETORIAL.md` (B13.2), a task
**B13.5** inteira (incluindo `## Resultado` — esta é a continuação direta dela, mesmo padrão de
migração), a task **B8.9** (`## Resultado`), e no código:
`executor64/Ir64VectorFpArithmeticExecutor` (`executeThreeSame`, `executePairwise`, `combinePair`,
`mulX`, `floatBits`/`doubleBits`/`boolMask`, `finishScalarAwareWrite`/`finishDestructiveWrite`),
`ir64/Ir64VectorFpThreeSameOp`, `ir64/Ir64VectorFpPairwiseOp`, `advsimd/AdvSimdLanes`
(`threeSame`/`pairwise` pós-B13.5 + `AdvSimdRegisterWords`), `advsimd/AdvSimdThreeSameOp`,
`advsimd/AdvSimdPairwiseOp`, `codegen/executor/IrNeonExecutor` (`executeNeonThreeSame`,
`executeNeonPairwise`), `decoder/NeonDataProcessingDecoder` (pós-B13.5), `ir/IrOp.java`
(`NeonThreeSame`/`NeonPairwise` + `Kind.NEON_*` 66-70 + `permits`), `core/ArmFeature`.

## As duas decisões que esta "spec round" tinha em aberto

### 1. Meia-precisão (`_hp`, `esz=1`) — FICA DE FORA, com destino

O encoding FP usa **bit20 (`sz`) como largura**: `0` = F32 (`esz=2`), `1` = F16 (`esz=1`). O
bit21 (`a`) NÃO é largura — é discriminador de sub-opcode (armadilha herdada da B8.9: *"o bit alto de
'size' é usado como parte do decode de opcode"*).

**Decisão desta spec: as formas F16 (bit20=1) são reconhecidas (o frame bateu) e viram
`UNIMPLEMENTED` explícito (G8), não são implementadas aqui.** Fundamento:

- O lado A64 fez EXATAMENTE isso: `Ir64VectorFpThreeSameOp` documenta *"só as formas de precisão
  SIMPLES/DUPLA (`esz` `2`/`3`); meia-precisão (`esz=1`) é `FEAT_FP16`, fora do Cortex-A53"* e a
  B19.2/B19.3 **recusaram as linhas `_h` pela ESTRUTURA** (regressão negativa), remetendo-as à
  B19.5. Fazer F16 só do lado NEON A32 criaria assimetria com o A64.
- `AdvSimdLanes` não tem nenhum caminho F16 (nem o A64), e `Math.fma`/`Float`/`Double` de Java não
  têm tipo `binary16` — modelar F16 corretamente (subnormais, arredondamento) é trabalho próprio.
- **Não** cria `ArmFeature` de FP16 agora (paridade com B19.2/B19.3, que não gatearam, só
  recusaram). A tabela `docs/isa-nao-aplicavel.tsv` **não** ganha linha (o grupo `neon-dp` inteiro
  ainda é `NOT_IN_ANY_PRESET` até B13.22 — não há denominador a curar).
- Destino: **task futura própria** ("NEON FP16 AArch32 / `FEAT_FP16`", irmã da B19.5), a ser feita
  quando o núcleo ganhar um caminho F16 nos dois lados. Registrar no `## Resultado`.

### 2. Migração para `AdvSimdLanes` (D1 da RFC) — SIM, como B13.4/B13.5

`AdvSimdLanes` é hoje puramente inteiro (`long`, bit-twiddling). Esta task acrescenta o **primeiro
caminho de ponto flutuante** ao núcleo:

- `advsimd/AdvSimdFpThreeSameOp` novo (enum, mirror de `ir64/Ir64VectorFpThreeSameOp` **mais** a
  distinção fundido×não-fundido, ver decisão 3 abaixo).
- `advsimd/AdvSimdFpPairwiseOp` novo (enum, mirror de `ir64/Ir64VectorFpPairwiseOp`: `ADD`/`MAX`/
  `MIN`/`MAXNM`/`MINNM`).
- `AdvSimdLanes.fpThreeSame(AdvSimdRegisterWords, AdvSimdFpThreeSameOp, int esz, int lanes,
  int baseRd, int baseRn, int baseRm)` — o `switch` FP **movido verbatim** de
  `Ir64VectorFpArithmeticExecutor#executeThreeSame` (os dois ramos `esz==2`/`esz==3`, `mulX`,
  `Math.fma`, `boolMask` FP, `RECPS`/`RSQRTS` na forma simplificada `2.0 - a*b` /
  `(3.0 - a*b)/2.0` já usada lá). Helpers `floatBits`/`doubleBits`/`boolMask`(FP)/`mulX` **movidos**
  (o A64 não os usa em mais nenhum lugar) ou copiados verbatim se houver colisão de nome.
- `AdvSimdLanes.fpPairwise(AdvSimdRegisterWords, AdvSimdFpPairwiseOp, int esz, int lanes,
  int baseRd, int baseRn, int baseRm)` — `combinePair` + o laço de `executePairwise` (forma
  vetorial) movidos; buffer ANTES da escrita (como o inteiro `pairwise`).
- `AdvSimdLanes.fpCombinePair(AdvSimdFpPairwiseOp, long aBits, long bBits, int esz)` **público** —
  para a forma ESCALAR de `executePairwise` (B19.2, `FADDP_s`/…) continuar funcionando sem duplicar.
- `Ir64VectorFpArithmeticExecutor#executeThreeSame` fica só delegando: resolve o
  `AdvSimdFpThreeSameOp` a partir do `Ir64VectorFpThreeSameOp` do record (todas as ops A64 são
  FUNDIDAS — `MLA`→`FMLA`), chama `AdvSimdLanes.fpThreeSame` sobre `core.fp()` (que É um
  `AdvSimdRegisterWords`, conferir), e faz a escrita destrutiva / escalar A64
  (`finishScalarAwareWrite`) — **sem laço próprio**, igual ao que B13.5 fez com `executeThreeSame`
  inteiro.
- `#executePairwise` idem: forma vetorial delega a `AdvSimdLanes.fpPairwise` + `finishDestructiveWrite`;
  forma escalar (B19.2) chama `AdvSimdLanes.fpCombinePair` + `finishScalarAwareWrite`.
- `#executeThreeSameByElement` (B8.19) **não muda** — mantém o `switch` inline de 4 ops
  (`MUL`/`MULX`/`MLA`/`MLS`, `b` lido uma vez), como B13.5 deixou o by-element inteiro intocado.
- **Prova de zero-diff A64**: `Ir64VectorFpArithmeticExecutorTest` e todas as
  `Aarch64AdvSimd*DecoderTest` passam **sem alteração nenhuma**. Rodá-las é parte do Aceite.

### 3. `VMLA_fp`/`VMLS_fp` NEON **não são fundidos** — `VFMA_fp`/`VFMS_fp` são

Diferença arquitetural real entre A32 NEON e A64:

- **A64** `FMLA`/`FMLS` (vetorial FP) são **fundidos** (arredondamento único) — a B8.9 os
  implementa com `Math.fma`. Só existe a forma fundida.
- **A32 NEON** tem AS DUAS: `VMLA.F32`/`VMLS.F32` (`opc=1101 op=1`) fazem `d ± (n*m)` com **dois
  arredondamentos** (mul e depois add, cada um IEEE round-to-nearest), e `VFMA.F32`/`VFMS.F32`
  (`opc=1100 op=1 U=0`, VFPv4/`FEAT_*`) são **fundidos** (`Math.fma`). Ver ARM DDI 0406C
  A8.8.337 (VMLA float, "not fused") × A8.8.331 (VFMA, "fused"); oráculo QEMU `translate-neon.c`
  (`gen_VMLA_fp_3s` × `gen_VFMA_fp_3s`).

Consequência para `AdvSimdFpThreeSameOp`: **4 constantes de multiply-accumulate**, não 2 —
`MLA`/`MLS` (não fundido: `floatBits(a * b + current)` / `floatBits(current - a * b)`) e
`FMLA`/`FMLS` (fundido: `Math.fma(a, b, current)` / `Math.fma(-a, b, current)`). O A64
(`Ir64VectorFpThreeSameOp.MLA`/`MLS`, sempre fundido) mapeia para `FMLA`/`FMLS`. O decoder A32
mapeia `opc=1100 op=1 U=0` → `FMLA`/`FMLS` e `opc=1101 op=1` → `MLA`/`MLS`.

**Armadilha**: copiar o `case MLA -> Math.fma(...)` do A64 para as duas famílias A32 dá `VMLA.F32`
com um arredondamento a menos — silencioso, some no ruído de precisão até um teste de bit exato
pegar.

## Objetivo

Decodificar e executar as famílias de ponto flutuante de "3-reg-same" de `neon-dp.decode` no
encoding **A32**, forma **F32 apenas** (`esz=2`), gateadas por `ArmFeature.ADVANCED_SIMD` — **nenhum
preset declara a feature**, portanto **zero-diff de runtime** nos 5 consumidores e
`docs/COBERTURA-ISA.md` byte a byte idêntica ao fim da task. Formas F16 → `UNIMPLEMENTED` (decisão 1).

## Não inclui (com destino explícito)

Todo o resto do frame `(raw & 0xFE80_0000) == 0xF200_0000` que esta task NÃO reconhecer vira
`DecodedInstruction.unimplemented` EXPLÍCITO (G8) — nunca `null`, nunca outra instrução. Depois de
B13.4/B13.5/B13.6 só sobram:

- **`opc=1100 op=0`** (`SHA1C`/`SHA1P`/`SHA1M`/`SHA1SU0`/`SHA256H`/`SHA256H2`/`SHA256SU1`) →
  **B13.15** (cripto).
- **Formas F16** (bit20=1) de todos os encodings desta task → **task futura própria** (NEON FP16 /
  `FEAT_FP16` AArch32, irmã da B19.5). `UNIMPLEMENTED` aqui.
- **Combinações não alocadas** dentro de `opc=1101`/`1110`/`1111` (ex.: `opc=1110 U=0 a=1`,
  `opc=1110 U=0 bit4=1`, `opc=1101 U=1 a=1 bit4=1`) → `UNIMPLEMENTED` (não existem no `.decode`).
- **T32** (encoding Thumb-2) → **B13.16**.
- **`FPSCR` real** (RMode / FZ / exceções / `QC`) — não modelado, paridade com o A64 (B3.8/B8.5/
  B8.15/B13.5); `RECPS`/`RSQRTS` seguem a forma simplificada da B8.9. Task futura própria.
- Preset declarando `ADVANCED_SIMD` → **B13.22**.
- Emissão ASM/JIT nativa (achado 2 da RFC — `AsmNativePolicy` continua `false` para os `Kind` NEON).
- Consertar o backend Truffle (achado 1 da RFC) — ver "Não fazer".

## Especificação

### Encoding (oráculo: `neon-dp.decode` `@3same_fp`/`@3same_fp_q0` + `translate-neon.c`; ARM DDI 0406C A7.4.5 / A8)

```
1111 001 U 0 D  a sz Vn:4 Vd:4 opc:4 N Q M op Vm:4
```

- Frame do grupo: `(raw & 0xFE80_0000) == 0xF200_0000` — já é o frame que `NeonDataProcessingDecoder`
  reivindica desde B13.4.
- `sz` = bit20. `sz==1` (F16) → `UNIMPLEMENTED` (decisão 1). `sz==0` → `esz = 2` (F32).
- `a` = bit21, `opc` = bits[11:8], `op` = bit4, `Q` = bit6, `U` = bit24.
- Registradores, convenção `D:Vd` de precisão dupla (idêntica a B13.2/B13.4/B13.5/`VfpDecoder`):
  `vd = D(bit22):Vd(bits15:12)`, `vn = N(bit7):Vn(bits19:16)`, `vm = M(bit5):Vm(bits3:0)`.
- **Forma `Q` (`Q=1`)**: os 3 registradores nomeiam pares `D<2n>`/`D<2n+1>`; índice ÍMPAR em
  qualquer um dos 3 → **UNDEFINED** (`UNIMPLEMENTED`; igual B13.2/B13.4/B13.5).
- **Pairwise** (`VPADD_fp`/`VPMAX_fp`/`VPMIN_fp`): encoding `@3same_fp_q0` — `Q` forçado a `0`, só
  forma `D`. `Q=1` nesses 3 encodings → `UNIMPLEMENTED`.
- **Sem `@3same_rev` aqui** — nenhuma família FP tem troca de operando (só os shifts inteiros de
  B13.5 tinham). `vn`/`vm` entram no record na posição usual.
- NEON é sempre incondicional (`cond=0b1111`): todo `IrOp` com `Condition.AL`.
- `lanes` (no executor): F32 D-form = `8 >> 2 = 2`; F32 Q-form = `16 >> 2 = 4`.

### IR

Dois `IrOp` novos (não dá para reusar `NeonThreeSame`/`NeonPairwise` — aqueles carregam
`AdvSimdThreeSameOp`/`AdvSimdPairwiseOp` INTEIROS; o executor precisa saber que é FP para escolher
`AdvSimdLanes.fpThreeSame`/`fpPairwise`):

- **`IrOp.NeonFpThreeSame(AdvSimdFpThreeSameOp op, boolean quad, int esz, int vd, int vn, int vm)`**
  — `Kind.NEON_FP_THREE_SAME = 71`. `condition()` sempre `AL`. Javadoc `///` PT espelhando
  `NeonThreeSame`.
- **`IrOp.NeonFpPairwise(AdvSimdFpPairwiseOp op, int esz, int vd, int vn, int vm)`** —
  `Kind.NEON_FP_PAIRWISE = 72`. Sempre forma `D` (sem campo `quad`). `condition()` sempre `AL`.

Ambos entram no `permits` de `IrOp` (linhas 9-10) e — como todo `Kind` NEON desde B13.2 — são
tratados via `InstructionKind.LIFTED_IR_OP` em `StandardIrBuilder`; conferir se algo além disso é
preciso (`NeonThreeSame`/`NeonPairwise` são o modelo — copiar exatamente o mesmo wiring).

### Núcleo compartilhado (`advsimd/`)

**`advsimd/AdvSimdFpThreeSameOp`** (enum novo) — constantes, Javadoc `///` PT:
`ADD, SUB, MUL, DIV, MAX, MIN, MAXNM, MINNM, MULX, MLA, MLS, FMLA, FMLS, CMEQ, CMGE, CMGT, FACGE,
FACGT, ABD, RECPS, RSQRTS`.
`DIV`/`MULX` não são produzidos pelo decoder A32 (não há encoding NEON A32 de 3-reg-same para
eles), mas entram no enum para o A64 (`Ir64VectorFpThreeSameOp` os tem) delegar sem `default`.
`MLA`/`MLS` = **não fundido**; `FMLA`/`FMLS` = **fundido** (decisão 3).

**`advsimd/AdvSimdFpPairwiseOp`** (enum novo) — `ADD, MAX, MIN, MAXNM, MINNM` (mirror exato de
`Ir64VectorFpPairwiseOp`).

**`AdvSimdLanes`** ganha:

```java
public static void fpThreeSame(AdvSimdRegisterWords regs, AdvSimdFpThreeSameOp op,
        int esz, int lanes, int baseRd, int baseRn, int baseRm) { ... }

public static void fpPairwise(AdvSimdRegisterWords regs, AdvSimdFpPairwiseOp op,
        int esz, int lanes, int baseRd, int baseRn, int baseRm) { ... }

public static long fpCombinePair(AdvSimdFpPairwiseOp op, long aBits, long bBits, int esz) { ... }
```

- `fpThreeSame`: laço `i in [0,lanes)`; `esz==2` lê `float a/b/current` via
  `Float.intBitsToFloat((int) element(regs, baseRn/baseRm/baseRd, i, 2))`, `esz==3` via
  `Double.longBitsToDouble(element(...))`. `switch (op)` **verbatim** do corpo atual de
  `Ir64VectorFpArithmeticExecutor#executeThreeSame` (os DOIS ramos), acrescido de:
  - `case MLA -> floatBits(a * b + current)` / `doubleBits(a * b + current)` (NÃO fundido);
  - `case MLS -> floatBits(current - a * b)` / `doubleBits(current - a * b)` (NÃO fundido);
  - `case FMLA -> floatBits(Math.fma(a, b, current))` (o `MLA` atual do A64);
  - `case FMLS -> floatBits(Math.fma(-a, b, current))` (o `MLS` atual do A64).
  `setElement(regs, baseRd, i, esz, resultBits)`. **Nenhuma** escrita destrutiva aqui (o chamador
  faz — mesma disciplina de `threeSame`/`pairwise` inteiros).
- `fpPairwise`: buffer `long[lanes]` calculado ANTES da escrita, via `fpCombinePair`; depois
  `setElement` em laço. Sem escrita destrutiva.
- `fpCombinePair`: o `combinePair` atual de `Ir64VectorFpArithmeticExecutor`, movido verbatim
  (`ADD`/`MAX`/`MIN` propagam `NaN`, `MAXNM`/`MINNM` via `Ir64FpExecutor.maxNum`/`minNum` —
  **manter a chamada a `Ir64FpExecutor`**, que é `package`-visível no pacote `executor64`; se a
  visibilidade não alcançar `advsimd`, mover `maxNum`/`minNum` para `AdvSimdLanes` como helper
  `public` e o `Ir64FpExecutor` passa a delegar — decidir no código, preferir mover se `maxNum`/
  `minNum` não tiverem outro uso incompatível).
- Helpers `floatBits`/`doubleBits`/`mulX`(float+double)/`boolMask`(FP, assinatura
  `(boolean, int esz)`) — **mover** de `Ir64VectorFpArithmeticExecutor` para `AdvSimdLanes` (o A64
  passa a não tê-los; `executeThreeSameByElement` e `executeUnary` ainda os usam → ou mantêm cópia
  local privada, ou passam a chamar `AdvSimdLanes.*`; **preferir chamar o núcleo** para não
  duplicar, como B13.5 fez com os helpers de saturação). Cuidado: já existe
  `AdvSimdLanes.boolMask(boolean, int esz)` INTEIRO com semântica idêntica (`elementMask(esz)` vs
  `0`) — o FP pode **reusar o mesmo** (confirmar que `0xFFFF_FFFFL`/`-1L` batem com `elementMask(2)`
  /`elementMask(3)`: batem). Não criar um segundo.

### Migração do lado A64 (uma fonte de verdade — D1 da RFC, continuação de B13.4/B13.5)

- `Ir64VectorFpArithmeticExecutor#executeThreeSame` → só resolve `Ir64VectorFpThreeSameOp` →
  `AdvSimdFpThreeSameOp` (mapa 1:1, `MLA`→`FMLA`, `MLS`→`FMLS`, resto homônimo), chama
  `AdvSimdLanes.fpThreeSame(fp, sharedOp, esz, elements, op.rd(), op.rn(), op.rm())` onde
  `elements = op.scalar() ? 1 : elementsPerRegister(op.q(), esz)`, e chama
  `finishScalarAwareWrite(fp, op.rd(), op.scalar(), op.q(), esz)`. Sem laço, sem `switch` de
  semântica. (`op.scalar()` da B19.2 continua honrado: 1 lane + finalização escalar.)
- `#executePairwise`: forma escalar → `AdvSimdLanes.fpCombinePair` + `finishScalarAwareWrite`;
  forma vetorial → `AdvSimdLanes.fpPairwise(fp, sharedOp, esz, elements, rd, rn, rm)` +
  `finishDestructiveWrite`.
- `#executeThreeSameByElement`, `#executeUnary`, `#executeConvertFixedPoint`,
  `#executeFpAcrossLanes` — **inalterados** (só passam a chamar `AdvSimdLanes.floatBits`/… se os
  helpers foram movidos).
- **Prova de zero-diff A64**: `Ir64VectorFpArithmeticExecutorTest` (contar quantos) e todas as
  `Aarch64AdvSimd*DecoderTest`/`Ir64...FpDecoderTest` passam **sem edição**. Rodá-las = Aceite.

### Execução A32 (`codegen/executor/IrNeonExecutor`)

- `executeNeonFpThreeSame(IrOp.NeonFpThreeSame op)` — resolve `baseRd/baseRn/baseRm` (palavra
  inicial de cada `D`/`Q` no `VfpRegisters`, mesma tradução que `executeNeonThreeSame` já faz),

### Decoder (`NeonDataProcessingDecoder`)

Estende a discriminação que B13.4/B13.5 montaram. **Antes** de cair em `threeSameOperation`/
`pairwiseOperation` (que são INTEIRAS), tratar o subespaço FP:

1. Gate `ADVANCED_SIMD` (já existe no topo). Sem ela → `null` (zero-diff).
2. FP é `opc ∈ {1101, 1110, 1111}` OU (`opc==1100 && op==1 && u==0`). Fora disso, seguir o
   fluxo inteiro atual (cripto `opc=1100 op=0` já vira `null`→`UNIMPLEMENTED`; `VQRDMLSH`
   `opc=1100 op=1 u=1` continua com B13.5).
3. Dentro do FP:
   - `sz` (bit20) `== 1` → `unimplemented` (F16, decisão 1).
   - `esz = 2`.
   - `a = bit21`, `bit4 = op`.
   - Pairwise: (`opc==1101 && u==1 && a==0 && op==0`) NÃO — atenção: `VPADD_fp` é `u==1 a==0
     opc==1101 bit4==0`; `VABD_fp` é `u==1 a==1 opc==1101 bit4==0`. Ver tabela. Os 3 pairwise são:
     `VPADD_fp` (`u1 a0 opc1101 bit4=0`), `VPMAX_fp` (`u1 a0 opc1111 bit4=0`),

     `NeonFpPairwise(op, esz=2, vd, vn, vm)`.

## Armadilhas

1. **`bit21` (`a`) NÃO é largura.** Largura FP é só `bit20` (`sz`). Tratar `a` como parte do
   `size` (como no inteiro) decodifica tudo errado. Mesma armadilha que a B8.9 achou no A64.
2. **`VMLA_fp`/`VMLS_fp` NEON não são fundidos; `VFMA_fp`/`VFMS_fp` são.** 4 constantes distintas no
   enum (decisão 3). Copiar `Math.fma` para as 4 dá `VMLA` errado — silencioso.
3. **Sem `@3same_rev` no FP.** Nenhuma família FP troca `vn`↔`vm`. Não copiar a troca de B13.5.
4. **`boolMask` FP deve reusar o inteiro.** `AdvSimdLanes.boolMask(boolean, int esz)` já produz
   `elementMask(esz)`/`0`, que para `esz=2` é `0xFFFFFFFF` e para `esz=3` é `-1L` — exatamente o
   que o `boolMask` FP de `Ir64VectorFpArithmeticExecutor` faz. Não criar um segundo método.
5. **Migração verbatim.** Não "melhorar" a semântica FP ao mover para `AdvSimdLanes` — qualquer
   diferença (ordem de `NaN`, `Math.max` vs `>`, sinal de zero) quebra o zero-diff A64 (G1).
   Copiar `switch` e helpers EXATAMENTE, inclusive `mulX` (o quirk `0*Inf → 2.0`).
6. **`Ir64FpExecutor.maxNum`/`minNum`** estão no pacote `executor64`. Se `AdvSimdLanes` (pacote
   `advsimd`) não os alcançar, mover para `AdvSimdLanes` como `public` e `Ir64FpExecutor` delega —
   NÃO duplicar a lógica de `FPMaxNum` (tratamento de `NaN` único é sutil).
7. **`core.fp()` do A64 É um `AdvSimdRegisterWords`?** Confirmar (o inteiro B13.4/B13.5 já passa
   `fp` para `AdvSimdLanes.threeSame`, então sim — mas conferir a assinatura exata).
8. **Escrita NEON ≠ escrita A64.** O A64 zera bits 127:64 do `V` na forma de 64 bits; o NEON A32
   escreve exatamente o `D`/`Q`. `AdvSimdLanes.fpThreeSame` NÃO faz escrita destrutiva — cada
   executor faz a sua. Espelhar `executeNeonThreeSame` (B13.4).
9. **`VPADD_fp` é `opc=1101`, `VPMAX_fp`/`VPMIN_fp` são `opc=1111`.** Não agrupar os 3 pairwise
   pelo mesmo `opc` — só o `@3same_fp_q0` (Q=0) os une.

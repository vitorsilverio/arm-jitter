# RFC B17.2 — Comprimento de vetor SVE: fixo em 128 bits vs configurável

**Trilha:** B · **Repo:** arm-jitter · **Depende de:** B17.1 · **Épico:** `b17-plano-sve.md`
**Status: ✅ DECIDIDA em 2026-09-24 — Opção C, `VL` default 256 bits.** Ver `## Resultado`.
B17.3-B17.26 desbloqueadas.

Formato de `docs/RFC-SOFTMMU.md` / `docs/RFC-M-PROFILE.md`. Este arquivo vive em
`tasks/trilha-b-arquiteturas/` por ser um degrau nomeado da escada; se for aprovado, copiar a seção
"Decisão" para `docs/RFC-SVE-COMPRIMENTO-VETOR.md` na sessão de execução da B17.3, seguindo o
precedente das outras duas RFCs.

## Pergunta

SVE é a primeira extensão ARM em que o **comprimento do vetor não está no encoding**. `Z0`-`Z31`
têm `VL` bits, com `VL` ∈ {128, 256, …, 2048} (múltiplos de 128), escolhido pela IMPLEMENTAÇÃO e
observável pelo software em tempo de execução (`RDVL`, `CNTB`, `ZCR_ELx.LEN`). O mesmo binário roda
em qualquer `VL` — é a disciplina **VLA** (Vector Length Agnostic).

Duas perguntas, que na prática são uma só:

1. Que `VL` o `arm-jitter` anuncia (`ZCR_ELx.LEN`, `ID_AA64ZFR0_EL1`)?
2. Como `Z0`-`Z31`/`P0`-`P15`/`FFR` são representados em Java, **convivendo com o banco `V0`-`V31`
   de 128 bits que a B8.6 construiu** — lembrando que `Z<n>[127:0]` **é** `V<n>`, não uma cópia.

## O que já existe (medido nesta rodada, não suposto)

`core64/Aarch64FpRegisters.java`:

```java
public final class Aarch64FpRegisters implements dev.vitorsilverio.armjitter.advsimd.AdvSimdRegisterWords {
    public static final int V_REGISTER_COUNT = 32;
    public static final int WORDS_PER_REGISTER = 2;
    public static final int QUADWORD_BYTES = 16;
    private final long[] lo = new long[V_REGISTER_COUNT];
    private final long[] hi = new long[V_REGISTER_COUNT];
```

E o substrato compartilhado que a RFC **B13.2** criou, `advsimd/AdvSimdRegisterWords.java`:

```java
/// Cada mundo mapeia seus registradores para um intervalo contíguo de palavras:
/// - Aarch64FpRegisters: `V<n>` ocupa as palavras `2n` (bits 63:0) e `2n+1` (bits 127:64)
public interface AdvSimdRegisterWords {
    long word(int index);
    void setWord(int index, long value);
}
```

Números medidos por `grep` no `core/src/main/java`:

| Medida | Valor |
|---|---:|
| Arquivos que referenciam `Aarch64FpRegisters`/`.fp()` | 13 |
| Chamadas a `core.fp()` | 90 |
| Chamadas a `low64(`/`high64(`/`setQ(` (a API "128 bits" explícita) | 59 |
| Métodos públicos de `Aarch64FpRegisters` | 23 |

**Esse é o número que decide a RFC**: a superfície que "sabe que são 128 bits" é pequena e já está
atrás de uma indireção por palavras de 64 bits — feita por outro motivo (a assimetria `D<n>` ímpar
do NEON A32), mas que resolve exatamente este problema.

## Opção A — `VL` fixo em 128 bits

`Z<n>` **é** `V<n>`: nenhum array novo, `Aarch64FpRegisters` fica como está, `P<n>` vira 16 bits
(um `short`/`int` por predicado), `FFR` idem. Toda instrução SVE vira "AdvSIMD com predicado" e
reusa `AdvSimdLanes` quase integralmente.

- ✅ **Custo de implementação mínimo** e risco de regressão ~zero nos 5 consumidores (G5).
- ✅ **Roda binário SVE real**: a disciplina VLA garante que código correto funciona em `VL=128`.
- ✅ `snapshot()`/`saveState`/`loadState`/`Aarch64CpuSnapshot` não mudam de forma.
- ❌ **Não exercita nada do que SVE tem de próprio.** `INDEX`, `WHILE*`, `CNTB`, `ADDVL`, `PTRUE`
  com padrão `VL256`/`MUL3`, `LD1RQ` vs `LD1RO`, `COMPACT`, `SPLICE`: em `VL=128` quase todos
  degeneram para o caso AdvSIMD e **um bug de VLA não é observável**. É o mesmo tipo de cegueira
  que a B14 acabou de encontrar no `VfpDecoder` (`bits[31:28]` ignorado porque nenhum teste os
  exercitava).
- ❌ `LD1RO` (load-and-replicate de 256 bits) é **arquiteturalmente inválido** em `VL=128` —
  a família já nasceria com uma célula que não dá para testar de verdade.
- ❌ **É uma decisão difícil de desfazer**: se `128` vazar como suposição pelos ~25 executores da
  escada, migrar depois custa o épico inteiro uma segunda vez.

## Opção B — `VL` configurável (dimensionado pelo preset/`ZCR_ELx`)

`Z` vira `long[32 * WORDS_PER_Z]`, com `WORDS_PER_Z = VL/64` ∈ [2, 32]. `P` vira `long[16 * VL/512]`
(1 bit por byte de vetor ⇒ `VL/8` bits ⇒ 16..256 bits ⇒ 1..4 palavras). `FFR` é mais um predicado
(no QEMU é literalmente isso — `FFR_PRED_NUM`, e `RDFFR` é implementado reusando a operação de
predicado: `arg_rprr_s alt_a = {… .rn = FFR_PRED_NUM, .rm = FFR_PRED_NUM}`).

- ✅ **Fiel**, e é a única forma de testar o mesmo binário em `VL` diferentes — que é como bug de
  VLA aparece.
- ✅ Permite `LD1RO`, `PTRUE` com padrões reais, `RDVL`/`ADDVL`/`ADDPL` com valores não triviais.
- ❌ Toca `Aarch64FpRegisters` (banco público desde B8.6) — **risco G3** se feito sem cuidado.
- ❌ Custo maior de estado: 32×32 longs = 8 KiB por core em `VL=2048` (irrelevante para 1-4 cores;
  relevante se alguém instanciar milhares).
- ❌ `Aarch64CpuSnapshot`/`saveState` mudam de formato (versionamento de save-state, como o `.ss v2`
  do gbaemu).

## Opção C (recomendada) — configurável, com `V` como **vista** do banco `Z`

É a Opção B, com uma escolha estrutural concreta que anula o principal `❌` dela:

1. Um banco novo `Aarch64ScalableRegisters` (`long[] z = new long[32 * wordsPerZ]`, `long[] p`,
   `long[] ffr`), com `wordsPerZ` vindo do preset/`ZCR_ELx` e **uma única constante nomeada** para
   o mínimo arquitetural (`MIN_VECTOR_LENGTH_BITS = 128`), nunca `128` literal (G6).
2. `Aarch64FpRegisters` **deixa de ter os arrays** `lo`/`hi` e passa a ser a vista baixa do `Z`:
   `word(i)` → `z[(i >>> 1) * wordsPerZ + (i & 1)]`. Os **23 métodos públicos e as 90 chamadas
   continuam com a MESMA assinatura e o MESMO comportamento** — a mudança é interna.
3. A "disciplina de escrita destrutiva" do A64 (escrever `V<n>` zera `[127:64]`) vira, sob SVE,
   "escrever `V<n>` zera `Z<n>[VL-1:64]`" — que é a regra ARM real, e hoje já mora no chamador
   (Javadoc de `AdvSimdRegisterWords.setWord`: *"a disciplina de escrita destrutiva de cada
   arquitetura … fica com o CHAMADOR, nunca aqui"*). **O lugar certo para essa regra já existe.**
4. `VL` é propriedade do `Aarch64Core` (derivada do preset + `ZCR_ELx.LEN`), lida por método
   (`core.vectorLengthBytes()`), **nunca** por constante nos executores. Um `grep` por `128` nos
   executores SVE é o teste de disciplina VLA.

Custo medido: uma classe nova, uma reescrita interna de `Aarch64FpRegisters` (arrays → delegação),
`saveState`/`snapshot` versionados. **Nenhuma mudança de assinatura pública** ⇒ G3 preservado por
construção, e os 5 consumidores (nenhum dos quais usa AArch64 SIMD hoje além do `virtual-arm-box`)
não veem diferença.

### `VL` default

Recomendação: **`VL = 256` bits** como default dos presets `ARMV9_*_A`, e o construtor aceitando
outros valores.

Por quê 256 e não 128: em `VL=128` **todo** teste de VLA passa por acidente (`VL/128 == 1` faz
`INDEX`, `CNTB`, `ADDVL`, `WHILE*` e os loops de lane degenerarem). 256 é o menor `VL` em que a
aritmética de VLA é observável, é o `VL` dos Neoverse V1/N2 e Graviton3 reais, e mantém o estado
em 2 KiB por core. Os testes de equivalência devem rodar **pelo menos dois** `VL` (256 e 512) para
que "bug de VLA" seja uma falha de teste e não um achado de campo — é o mesmo raciocínio do
`BlockEquivalenceHarness` (G1): a divergência tem que ser detectável por construção.

## Recomendação

**Opção C, com `VL` default 256 bits.**

Justificativa concreta, não de princípio:

1. **A indireção que a Opção C precisa já existe e já foi paga** — `AdvSimdRegisterWords` (RFC
   B13.2, decisão D1) é uma vista por palavras de 64 bits, criada para outro problema. Trocar o
   backing store de `Aarch64FpRegisters` por um `Z` mais largo é uma mudança de ~30 linhas numa
   classe, não uma refatoração da IR.
2. **A superfície exposta a "128" é de 59 chamadas** (`low64`/`high64`/`setQ`) em 13 arquivos, e
   todas continuam corretas sob a Opção C: elas falam de `V`, e `V` continua tendo 128 bits.
3. **A Opção A não é mais barata onde importa.** Ela economiza a classe nova, mas paga com ~22
   tasks de conteúdo escritas contra uma suposição, e a regra máxima do projeto (`tasks/README.md`)
   já diz o que acontece depois: a versão seguinte do ARM vira o degrau seguinte, e `VL>128` seria
   uma reescrita de tudo. O épico **B18** (SME) **depende de B17.3** e o estado `ZA` é dimensionado
   em `SVL×SVL` bits — herdar "128 fixo" aqui contamina o épico seguinte também.
4. **A Opção A torna uma família inteira não testável** (`LD1RO`, `PTRUE` com padrão, reduções de
   quadword `ADDQV`/`FADDQV`) — o oposto do que a B7/cobertura mede.

O único cenário em que a Opção A ganha é "queremos a coluna `sve.decode` verde rápido". Isso não é
um objetivo declarado do projeto; **cobertura honesta** é (`tasks/README.md`, "medir antes de
deduzir", e o precedente B9.11/B19.5.2 de aceitar que o número CAIA quando o denominador cresce).

## Consequências se a Opção C for aprovada

- **B17.3** cria `Aarch64ScalableRegisters` + `ZCR_EL1/2/3` + `sve_access_check` e converte
  `Aarch64FpRegisters` em vista (G3 verificado pelos testes AdvSIMD existentes, que não mudam).
- **Toda** task B17.4-B17.25 ganha, no Aceite, "testado em pelo menos dois `VL`".
- `Aarch64CpuSnapshot`/`saveState` ganham versão nova (formato + `VL`).
- **B18** herda o banco escalável de graça.

## Consequências se a Opção A for aprovada

- `MIN_VECTOR_LENGTH_BITS`/`VECTOR_LENGTH_BITS = 128` vira **uma** constante nomeada e única (G6),
  citada por todo executor — nunca `128` literal, e isso vira item de Aceite de cada task.
- `LD1RO_zprr`/`LD1RO_zpri` e as reduções de quadword entram na tabela como implementadas com
  `VL=128`, com a limitação documentada no `## Resultado` (não excluídas — regra máxima).
- Registrar aqui, explicitamente, que migrar para `VL` configurável depois é **um épico novo**.

## O que a decisão do usuário precisa responder

1. Opção **A**, **B** ou **C**?
2. Se C: `VL` default **256**? E os testes rodam em quais `VL` (recomendado: 256 e 512)?
3. `ID_AA64ZFR0_EL1`/`ID_AA64PFR0_EL1.SVE` passam a anunciar SVE **na B17.3** (recomendado — antes
   disso, anunciar sem ter estado faria um kernel Linux real tentar usar SVE e bater em
   `UNIMPLEMENTED`; ver Armadilha 4 da B17.1).

## Resultado

**Decidido em 2026-09-24 (usuário).** **Opção C aprovada**, `VL` default **256 bits**.

1. `Aarch64ScalableRegisters` (banco `Z`/`P`/`FFR`, `wordsPerZ` derivado do preset/`ZCR_ELx.LEN`,
   `MIN_VECTOR_LENGTH_BITS = 128` nomeada, G6) — a criar na **B17.3**.
2. `Aarch64FpRegisters` perde os arrays `lo`/`hi` e vira vista sobre `Z` (`word(i)` delegando),
   mantendo as 23 assinaturas públicas e as 90 chamadas existentes intactas — **B17.3**.
3. `VL` default **256 bits** nos presets `ARMV9_*_A`; construtor aceita outros valores. Toda task
   **B17.4-B17.25** ganha, no Aceite, "testado em pelo menos dois `VL`" (recomendado: 256 e 512).
4. `ID_AA64ZFR0_EL1`/`ID_AA64PFR0_EL1.SVE` passam a anunciar SVE **a partir da B17.3** (não antes —
   evita um kernel real tentar usar SVE sem estado, Armadilha 4 da B17.1).
5. `Aarch64CpuSnapshot`/`saveState` ganham versionamento novo (formato + `VL`) — **B17.3**.
6. **B17.3 e todas as sub-tasks B17.4-B17.26 estão desbloqueadas** para serem pegas.

**Não fazer** (registrado explicitamente pela RFC para a Opção A rejeitada): não fixar `VL=128` em
nenhum executor; qualquer `128` literal no código SVE novo é bug de disciplina VLA, não atalho
aceitável.

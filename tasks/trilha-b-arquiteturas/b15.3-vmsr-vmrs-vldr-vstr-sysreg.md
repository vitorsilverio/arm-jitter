# B15.3 — Perfil M: `VMSR_VMRS` + `VLDR_sysreg`/`VSTR_sysreg` (acesso a FPSCR memory-mapped) — 3 linhas

**Trilha:** B · **Repo:** arm-jitter (+ revalidação G5) · **Depende de:** B15.2 (✅ 2026-09-13)
**Épico:** `b15-plano-armv8m.md` · **Status:** ⬜ (spec escrita 2026-09-13, ainda não executada)

## Contexto

`b15-plano-armv8m.md` descreve a escada B15.2-B15.5 para fechar as 11 linhas de `m-nocp.decode`
(0% em `v6-M`/`v7-M`, a única linha 0% da tabela num preset real). B15.2 fechou `NOCP`/`NOCP_8_1`
(2 células). Esta task é o segundo degrau: as 3 linhas restantes que vivem no MESMO bloco `{...}`
do QEMU, checadas **antes** de `NOCP` (padrão mais específico primeiro) — `VMSR_VMRS`,
`VLDR_sysreg`, `VSTR_sysreg`. `VLLDM_VLSTM`/`VSCCLRM` (as outras 2 formas específicas do mesmo
bloco) ficam para **B15.5**, que depende desta (ordem de prioridade de decode: o gate "é uma das
formas específicas?" continua tendo que vir antes do `NOCP` genérico que a B15.2 já instalou).

### O encoding real (`target/isa-decode/m-nocp.decode`, medido nesta rodada de spec — trecho já
citado por B15.2, reproduzido aqui com o contexto que falta)

```
%vldr_sysreg 22:1 13:3
%imm7_0x4 0:7 !function=times_4

&vldr_sysreg rn reg imm a w p
@vldr_sysreg .... ... . a:1 . . . rn:4 ... . ... .. ....... \
             reg=%vldr_sysreg imm=%imm7_0x4 &vldr_sysreg

{
  ...
  VMSR_VMRS    ---- 1110 111 l:1 reg:4 rt:4 1010 0001 0000

  # P=0 W=0 is SEE "Related encodings", so split into two patterns
  VLDR_sysreg  ---- 110 1 . . w:1 1 .... ... 0 111 11 ....... @vldr_sysreg p=1
  VLDR_sysreg  ---- 110 0 . . 1   1 .... ... 0 111 11 ....... @vldr_sysreg p=0 w=1
  VSTR_sysreg  ---- 110 1 . . w:1 0 .... ... 0 111 11 ....... @vldr_sysreg p=1
  VSTR_sysreg  ---- 110 0 . . 1   0 .... ... 0 111 11 ....... @vldr_sysreg p=0 w=1

  NOCP         ...
}
```

- **`VMSR_VMRS`**: campo `reg:4` (bits\[19:16\]) — **MESMO layout de bits** que a forma A-profile
  já decodificada por `VfpDecoder.decodeCoreTransferOrSystem` (`bits2321==0b111 && size==SIZE_SINGLE`,
  ver `VfpDecoder.java` linhas 356-366) — mas com regras de registrador/privilégio DIFERENTES (ver
  "Achado central" abaixo). `l` seleciona direção (`l=1`→VMRS, valor sistema→`rt`; `l=0`→VMSR,
  `rt`→valor sistema).
- **`VLDR_sysreg`/`VSTR_sysreg`**: `reg` (4 bits, combinado de `bit22:bits[15:13]` via
  `%vldr_sysreg`) seleciona o MESMO conjunto de registradores de sistema que `VMSR_VMRS`; `rn`
  (base), `imm` (offset, `bits[6:0]` × 4), `p`/`w` (pré/pós-index + writeback, mesma convenção de
  `LDR`/`STR` imediato de 12 bits). Estas movem valor entre **memória** e o registrador de sistema
  — não entre GPR e registrador de sistema.

### Achado central desta spec (medido, não suposto): `reg` não é livre para qualquer valor

Pesquisa contra o QEMU real (`target/arm/tcg/translate-m-nocp.c`, via `WebFetch`, e a série de
patches que introduziu isso — "target/arm: Refactor M-profile VMSR/VMRS handling",
`qemu-devel` 2020-11) confirma que o perfil M **antes de ARMv8.1-M + Security Extension + MVE**
só reconhece **`reg = ARM_VFP_FPSCR` (valor `1`)** como registrador de sistema válido para
`VMSR_VMRS`/`VLDR_sysreg`/`VSTR_sysreg`. Os outros valores de `reg` que a arquitetura define
existem só a partir de extensões que este projeto ainda não tem:

| `reg` | Nome | Depende de | Status neste projeto |
|---:|---|---|---|
| `1` | `FPSCR` | — (sempre existiu) | **Escopo desta task** |
| `2` | `FPSCR_NZCVQC` (só bits NZCV+QC) | ARMv8.1-M | Fora (B15.6, preset `ARMV8_1M` ainda não existe) |
| `12` | `VPR`/`P0` (MVE) | `FEAT_MVE`/Helium | Fora (B16, ainda "não se aplica a nenhum preset") |
| `14` | `FPCXT_NS` | ARMv8-M Security Extension | Fora (B15.4, ainda não existe) |
| `15` | `FPCXT_S` | ARMv8-M Security Extension | Fora (B15.4) |

Isso **não é uma exclusão** (regra máxima do projeto) — é sequenciamento: os 4 valores fora do
escopo desta task viram trabalho pendente natural das tasks B15.4/B15.6/B16 já planejadas no
épico, não descartados. Ver "Não inclui".

### Por que reusar `ArmCore.fpscr()` em vez de criar estado novo

`ArmCore` já tem um `FpscrRegister fpscr` **incondicional** desde a B3.3 (todo `ArmCore` tem um,
independente de arquitetura/perfil — ver `ArmCore.java` linha 73/268-271) — perfil M não precisa
de um banco FPSCR próprio, só de decodificar/executar `VMSR_VMRS`/`VLDR_sysreg`/`VSTR_sysreg`
apontando para o MESMO objeto que `VfpDecoder`/`IrVfpExecutor` (A-profile) já leem/escrevem. Isso
é coerente com o Javadoc de `ArmArchitecture.ARMV7M` ("Sem VFP") — o registrador existe e é
acessível pelo mecanismo memory-mapped do perfil M mesmo sem nenhuma instrução aritmética VFP
anexada a esses presets (arquitetura real: `VMSR_VMRS`/`VLDR_sysreg`/`VSTR_sysreg` continuam
válidas mesmo em um Cortex-M sem FPU — é assim que o firmware CONSULTA se há FPU antes de decidir
usar VFP de verdade, precisamente o par funcional de `NOCP` que a B15.2 já fechou).

## Objetivo

`VMSR_VMRS` (perfil M, `reg=FPSCR`), `VLDR_sysreg`, `VSTR_sysreg` decodificam sob qualquer preset
com `ArmFeature#M_PROFILE` e movem o valor bruto de `ArmCore.fpscr()` de/para um GPR (`VMSR_VMRS`)
ou de/para memória com endereçamento pré/pós-indexado (`VLDR_sysreg`/`VSTR_sysreg`), reusando o
MESMO objeto `FpscrRegister` que o VFP A-profile já usa. `docs/COBERTURA-ISA.md`: as 3 células
(`v6-M`/`v7-M`, coluna `m-nocp.decode`) saem de `❌` para `✅`.

## Inclui

1. **Decode de `VMSR_VMRS`** (forma M-profile, `reg=1`/FPSCR) — reconhece o MESMO layout de bits
   que a forma A-profile já usa, mas com a regra de `Rt=15` diferente (ver Armadilha 1): produz
   `InstructionKind.VFP_SYSTEM_TRANSFER` (reuso, decidir na sessão de execução se cabe sem
   modificação ou se precisa de um `boolean`/variante nova — ver Armadilha 1) OU um `Kind` M-profile
   dedicado, se a Armadilha 1 concluir que a semântica diverge demais para reusar.
2. **Decode de `VLDR_sysreg`/`VSTR_sysreg`** — layout `@vldr_sysreg` (base `rn`, imediato `imm7×4`,
   `p`/`w`), com `reg` restrito a `1` (FPSCR) nesta task (ver "Achado central" acima). `InstructionKind`
   novo (mover memória↔registrador-de-sistema não é um `LOAD`/`STORE` comum — o destino/origem não é
   um GPR, ver Armadilha 3 sobre como isso se encaixa em `DecodedInstruction`).
3. **Executor**: `VMSR_VMRS` move `Rt` ↔ `ArmCore.fpscr().value()`/`setValue(...)` (mesma semântica
   de leitura/escrita bruta que o executor A-profile de `VFP_SYSTEM_TRANSFER` já tem — confirmar se
   dá para reusar o método existente ou se precisa de uma variante). `VLDR_sysreg`/`VSTR_sysreg`
   fazem a MESMA leitura/escrita bruta, mas indo para/vindo de um endereço de memória calculado por
   `rn`/`imm`/`p`/`w` (mesma aritmética de endereço que `LOAD`/`STORE` de imediato já fazem — ver
   `Thumb2LoadStoreDecoder`/executor correspondente para o padrão de `p`/`w` a copiar).
4. Testes (ver Aceite).

## Não inclui

- **`reg` ∈ {2 (`FPSCR_NZCVQC`), 12 (`VPR`/`P0`), 14 (`FPCXT_NS`), 15 (`FPCXT_S`)`}** — decodificar
  QUALQUER um desses valores hoje seria ler/escrever um registrador que este projeto não modela
  ainda (v8.1M/Security Extension/MVE, nenhum implementado). Decisão: `reg != 1` → decoder devolve
  `null` (❌ honesto, G8 — não confundir com FPSCR). Isso é sequenciamento (B15.4/B15.6/B16 fecham
  esses valores depois), não exclusão.
- **`Rt=15`/`Rn=15`** — UNPREDICTABLE no manual real (perfil M, diferente da regra A-profile de
  aliasing para APSR, ver Armadilha 1); decoder recusa (`null`).
- **Qualquer efeito funcional de `FPSCR` sobre o comportamento do core** além do que a B3.3/B3.8 já
  implementam (RMODE/FZ consultados pelos executores VFP aritméticos, que perfil M ainda não anexa)
  — esta task só move o valor bruto, não adiciona nova semântica ao registrador em si.
- **`VLLDM_VLSTM`/`VSCCLRM`** — B15.5 (dependem desta: mesmo bloco de decode, prioridade antes de
  `NOCP`, mas já excluídos do `Thumb2NocpDecoder` pelas máscaras `VLLDM_VLSTM_MASK`/`VSCCLRM_MASK`
  que a B15.2 deixou prontas).
- **Emissão nativa/Truffle** — decode + interpretado apenas, mesmo padrão do resto da trilha B.

## Armadilhas

1. **`VMSR_VMRS` M-profile tem regra de `Rt=15` diferente da A-profile** (achado desta spec, a
   reconfirmar na execução lendo o QEMU inteiro): A-profile (`VfpDecoder`) permite `Rt=15` e faz
   `VMRS` escrever NZCV em APSR (aliasing especial); perfil M trata `Rt=15` como UNPREDICTABLE e o
   QEMU real opta por UNDEF. Se o executor A-profile de `VFP_SYSTEM_TRANSFER` tiver essa lógica de
   aliasing embutida (não só no decoder), reusar o Kind sem adaptação duplicaria o aliasing errado
   para perfil M — decidir com evidência (ler o executor), não por suposição.
2. **Não decodificar `reg != 1` como se fosse `FPSCR`** — os valores `2`/`12`/`14`/`15` fazem parte
   da arquitetura real (v8.1M/Security/MVE), mas este projeto ainda não os modela; tratá-los como
   `FPSCR` por engano seria um misdecode silencioso (G8) que a Regra Máxima do projeto proíbe (não é
   "fora do escopo para sempre", é "ainda não" — documentar como pendência das tasks B15.4/B15.6/B16,
   nunca implementar errado só para preencher a célula).
3. **`VLDR_sysreg`/`VSTR_sysreg` não são `LOAD`/`STORE` comuns** — o valor não vai para um GPR, vai
   para `FpscrRegister`. Decidir se isso cabe nos campos neutros de `DecodedInstruction`
   (`destinationRegister=-1` sinalizando "não é GPR", com um `InstructionKind` novo que o executor
   interpreta de forma diferente de `LOAD`/`STORE`) ou se precisa do escape hatch `liftedOp` (RFC
   B13.2) — medir contra os campos disponíveis antes de escolher, documentar a escolha no
   `## Resultado`.
4. **Ordem de registro do decoder**: tem que vir ANTES de `Thumb2NocpDecoder` na lista
   `thumb32DecoderExtensions` de cada preset M-profile — a forma 1 de `NOCP` (`hi=1110 1110`)
   colide em parte do espaço de `VMSR_VMRS`/`VLDR_sysreg`/`VSTR_sysreg` (todas vivem no MESMO bloco
   QEMU, que prioriza os padrões específicos primeiro); sem a ordem correta, `Thumb2NocpDecoder`
   capturaria essas 3 linhas por engano antes do decoder novo ver o `raw`.
5. **G3**: `ARMV6M`/`ARMV7M`/`ARMV7M_PURE` não podem regredir nenhum teste existente (incl. os 13
   testes que a B15.2 acabou de adicionar para `NOCP`/`NOCP_8_1`) — rodar a suíte completa antes de
   commitar.
6. **Não confundir com a forma A-profile de `VMSR_VMRS`** já decodificada por `VfpDecoder` — os
   presets M-profile não anexam `VfpDecoder` (Javadoc de `ArmArchitecture.ARMV7M`: "Sem VFP"), então
   não há colisão de decoder hoje, mas o Kind/executor produzido por esta task deve ser equivalente
   em efeito (mesmo `FpscrRegister`), não um registrador paralelo.

## Não fazer

- Não implementar `reg` ∈ {`FPSCR_NZCVQC`, `VPR`, `P0`, `FPCXT_NS`, `FPCXT_S`} — dependem de

- Não implementar `VLLDM_VLSTM`/`VSCCLRM` — B15.5.
- Não adicionar semântica funcional nova ao `FPSCR` além do que B3.3/B3.8 já implementam.

## Resultado

**FECHADA 2026-09-14.** `VMSR_VMRS` (perfil M, `reg=1`/FPSCR) + `VLDR_sysreg`/`VSTR_sysreg`
decodificam sob `ArmFeature#M_PROFILE` (`ARMV6M`/`ARMV7M`/`ARMV7M_PURE`), reusando o MESMO
`ArmCore.fpscr()` que o VFP A-profile já usa — nenhum banco de estado novo.

**Armadilha 1 resolvida por medição (não suposição)**: lido `IrVfpExecutor#executeVfpSystemTransfer`
inteiro antes de decidir — a lógica de aliasing `Rt=15`→APSR vive INTEIRAMENTE no executor
(`op.armRegister() == APSR_NZCV_ENCODING`), nunca no decoder. Como o decoder novo
(`Thumb2VfpSystemAccessDecoder`) recusa `Rt=15` no próprio decode (UNPREDICTABLE no perfil M), o
ramo de aliasing do executor nunca é alcançado por uma instrução M-profile — `VMSR_VMRS` reusa
`InstructionKind.VFP_SYSTEM_TRANSFER`/`IrOp.VfpSystemTransfer` **sem nenhuma mudança**, zero `Kind`
novo para esta metade da task.

**Armadilha 3 resolvida**: `VLDR_sysreg`/`VSTR_sysreg` cabem nos campos neutros de
`DecodedInstruction` (não precisam do escape hatch `liftedOp`) — `destinationRegister=-1` sinaliza
"não é GPR" (destino real é `FpscrRegister`), `sourceRegister=Rn`, `immediate=offset` já resolvido
com sinal, `writeback`/`postIndexed` na MESMA convenção de `LOAD`/`STORE` genérico (`postIndexed
? base : base+offset`, seguido de `base+offset` quando `writeback` — confirmado idêntico ao
`IrMemoryExecutor#executeLoad`/`executeStore`, então o executor novo (`executeVfpSysregMemoryTransfer`
em `IrVfpExecutor`) só troca o destino/origem do valor de um GPR para `core.fpscr()`). 2 `InstructionKind`
novos (`VFP_SYSREG_LOAD`/`VFP_SYSREG_STORE`) mapeando para 1 `IrOp` novo (`VfpSysregMemoryTransfer`,
`Kind` 107, campo `load` distingue direção — mesmo padrão de `VfpMultipleTransfer`).

**Achado real não previsto pela spec — bug de MEDIÇÃO, não de implementação** (pego medindo o
delta ANTES de commitar, mesma disciplina de B15.2/B19.14/B19.16): a primeira rodada de
`./gerar-cobertura-isa.sh` deu **zero-diff**, apesar do decoder/executor corretos e testados. Causa
raiz: o texto de `VMSR_VMRS`/`VLDR_sysreg`/`VSTR_sysreg` em `m-nocp.decode` usa `----` (bits[31:28],
totalmente livre) — diferente das linhas de `NOCP` no MESMO arquivo, que já fixam `111-` (a B15.2
teve sorte). `IsaCoverageReport`/`DecodeTreeSpec` (a ferramenta de medição, não o decoder) constrói
a palavra-sonda deixando esses bits livres em `0`, produzindo `bits[31:27]=0b00001` — **nunca** um
marcador de classe Thumb-2 de 32 bits válido (`0b11101`/`0b11110`/`0b11111`); `ThumbDecoder` rejeita
a palavra como candidata de 32 bits ANTES de qualquer decoder de extensão ver o `raw`, então a
sonda reportava `MISSING` incondicionalmente, independente do decoder estar certo. Corrigido em
`IsaCoverageReport#probeOnce` (ramo `THUMB32`): se o `top5` resultante não é um marcador válido, força
`0b11101` — só ativa quando os bits estão GENUINAMENTE livres (nunca sobrescreve um padrão que já
fixa outro valor), documentado como achado de medição (mesma categoria do achado B9.7 registrado
ali). Confirmado que a correção não regride nada mais: o diff de `docs/COBERTURA-ISA.md` mudou

# B4.0.5 — armbox fase 3: fork/execve/pipes/wait (shell scripts reais)

**Trilha:** B · **Depende de:** B4.0 (✅) · **Repo:** armbox

## Contexto

Desde B4.0 o armbox roda `busybox sh -c 'cmd'` mas SEM fork/pipes — scripts reais
(`cmd1 | cmd2`, subshells, `$(...)`) não funcionam. Fechar isso transforma o
armbox num corpus de validação N3 muito mais rico (qualquer script vira teste) e
é pré-requisito para workloads multi-processo nos benches A7/A8.

## Decisão de desenho (fechada — não reavaliar)

**Modelo single-thread cooperativo com processos como instâncias de emulação:**
cada processo guest = um par (`ArmCore` próprio + `GuestMemory` próprio + tabela
de FDs própria) dentro do MESMO processo host/JVM. O escalonador do armbox roda
UM processo por vez em fatias de blocos (round-robin simples); `waitpid` bloqueado
cede a vez. Sem threads Java por processo guest (determinismo do `--check` e dos
testes vale mais que paralelismo aqui — anotado como possível evolução futura).

## Inclui (syscalls novas no dispatcher existente)

| Syscall | Semântica mínima |
|---------|------------------|
| `fork` (2) | clona registradores/CPSR + snapshot copy-on-write SIMPLES da memória (cópia integral é aceitável na v1 — anotar custo; CoW é otimização futura); filho retorna 0, pai retorna pid |
| `execve` (11) | reusa o loader ELF existente sobre a memória do processo chamador (novo espaço), preservando FDs |
| `pipe`/`pipe2` (42/359) | par de FDs sobre um buffer em memória host (deque de bytes, capacidade 64K); read em pipe vazio com escritor vivo = bloqueia (cede a vez); sem escritor = EOF |
| `waitpid`/`wait4` (114) | bloqueia até filho sair; devolve status `(exit<<8)` |
| `dup`/`dup2` (41/63) | tabela de FDs por processo |
| `getpid`/`getppid` (20/64) | pids sintéticos sequenciais |
| `exit_group`/`exit` | já existem — ganham semântica por-processo (o armbox só termina quando o processo 1 sai) |

Números de syscall: ARM EABI (`arch/arm/tools/syscall.tbl`) — conferir na fonte,
não confiar na tabela acima de cabeça.

## Testes mínimos

1. `busybox sh -c 'echo a | busybox cat'` → stdout `a` (o pipeline canônico).
2. `busybox sh -c 'x=$(busybox echo hi); echo $x'` → `hi` (subshell/captura).
3. `fork` direto em assembly (padrão `int[]` dos testes existentes): pai e filho
   escrevem bytes distintos num pipe, waitpid colhe o filho, exit codes corretos.
4. EOF de pipe (escritor fecha → leitor recebe 0), pipe cheio (escritor bloqueia
   e o leitor destrava).
5. Tudo nos 3 backends; `--check` determinístico (o escalonador é determinístico
   por construção).
6. Regressão: suíte armbox inteira + testes single-process intactos.

## Armadilhas

- `fork` dentro de bloco JIT: o retorno diferente pai/filho exige snapshot no
  ponto EXATO da syscall — o `SwiDispatcher` já materializa o estado (é como as
  outras syscalls funcionam); clonar a partir do `CpuState` desse ponto, nunca do
  início do bloco.
- O filho herda o TLS/kuser (B4.0.4) — copiar o campo.
- `BlockCache`/JIT runtime: cada processo tem memória própria → precisa de
  runtime/cache próprio por processo (código igual em endereços iguais mas
  conteúdo diferente entre processos); NÃO compartilhar o cache entre processos.
- stdin/stdout/stderr do processo 1 continuam os do host; filhos herdam por dup.

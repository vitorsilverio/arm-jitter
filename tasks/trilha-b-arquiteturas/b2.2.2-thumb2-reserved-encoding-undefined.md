# B2.2.2 — Fechar o fallback incorreto de encodings Thumb-2 reservados sob `top5=0b11101`

**Trilha:** B · **Depende de:** B2.1, B2.2 (e idealmente B2.3, ver Armadilhas) · **Repo:** arm-jitter

## Contexto

`ThumbDecoder.tryDecodeThumb32` (task B2.1) trata os três valores de `top5` que
identificam um candidato Thumb-2 de 32 bits de forma assimétrica: quando
`top5 == 0b11110` e nenhuma extensão reivindica o encoding, o decoder força
UNDEFINED controlado; quando `top5 == 0b11101` ou `0b11111` e nenhuma extensão
reivindica, o decoder **delega ao caminho legado ARMv4T/v5T de 16 bits** — porque,
sem nenhuma extensão registrada, esses dois valores de `top5` numericamente
coincidem com os encodings legados de sufixo `BLX`/`BL` (`0xE800`/`0xF800`), então
"delegar" era seguro por ausência de alternativa.

A task B2.2 registrou `Thumb2DataProcessingDecoder`, que reivindica a forma
registrador do data-processing sob `top5=0b11101` (prefixo `0b1110101`) — mas SÓ
para os 10 valores de `op4` que ela implementa. Os `op4` reservados/não cobertos
(`PKH`, formas MVE, valores reservados da ARM ARM) dentro desse mesmo `top5` ainda
caem no fallback legado incorreto: um encoding Thumb-2 genuíno mas não implementado
é decodificado como se fosse a segunda halfword de um `BL`/`BLX` — um bug real, só
que estreito (16 dos 32 valores de `op4` já não têm mais esse problema depois de
B2.2).

## Objetivo

Fechar esse gap da MESMA forma que já existe para `top5=0b11110`: quando o `raw`
está dentro do prefixo de 7 bits `0b1110101` (ou seja, é estruturalmente um
candidato válido do grupo "Data-processing (register)") mas nenhuma extensão
reivindicou o `op4`, o decoder deve retornar UNDEFINED controlado — não delegar ao
caminho legado.

## Não inclui

- Não implementar os `op4` reservados em si (isso seria uma alteração de escopo
  para `Thumb2DataProcessingDecoder`, não para o `ThumbDecoder`).
- Não mexer no restante do espaço `top5=0b11101` fora do prefixo `0b1110101` (ex.
  Load/store dual/exclusive/table branch, que chegam em B2.3 e terão o mesmo
  problema — ver Armadilhas) nem em `top5=0b11111`, a menos que a investigação
  mostre que a mesma correção serve para os dois sem custo extra.

## Especificação

1. Em `ThumbDecoder.tryDecodeThumb32`, quando `top5 == 0b11101`: se `raw` cai
   dentro de um prefixo de 7 bits que uma extensão registrada RECONHECE como seu
   (ex. `0b1110101` do data-processing), mas a extensão devolveu `null` (não
   reivindicou), o candidato deve virar UNDEFINED — não `return null`.
2. Isso exige que a extensão sinalize "esse é o meu espaço, mas esse op4 específico
   não" de forma diferente de "esse encoding não é meu de jeito nenhum" — o
   contrato atual de `DecoderExtension#tryDecode` só tem um `null` para os dois
   casos. Avaliar as opções (documentar a escolhida):
   - (a) mover a checagem de prefixo para dentro do `ThumbDecoder` (ele já sabe o
     prefixo `0b1110101` é uma reserva de `Thumb2DataProcessingDecoder` — mas isso
     acopla o decoder genérico a uma extensão específica, quebrando o desenho de
     B2.1 de "decoder base não muda quando um grupo novo é plugado");
   - (b) `DecoderExtension` ganha um segundo método (ou um valor de retorno de 3
     estados) para distinguir "não é meu espaço" de "é meu espaço, mas reservado";
   - (c) outra alternativa que preserve a independência do `ThumbDecoder` em
     relação a extensões específicas (G1-style: o decoder base não deve precisar
     saber o que cada extensão cobre).
3. Registrar a decisão de desenho tomada (e por quê) na task concluída, já que isso
   afeta como TODAS as extensões `thumb32DecoderExtensions` futuras (B2.3+) devem
   se comportar.

## Testes mínimos

- Um `op4` reservado dentro do prefixo `0b1110101` (ex. `PKH`, ou qualquer valor de
  `op4` fora da tabela de `Thumb2DataProcessingDecoder`) decodifica como
  `InstructionKind.UNIMPLEMENTED`, não mais como `LONG_BRANCH_SUFFIX`.
- Os testes de regressão já existentes de `ThumbTwoDecoderTest` (BL/BLX legado
  idêntico com THUMB2 ligado) continuam passando — a correção não pode reintroduzir
  ambiguidade com o par `BL`/`BLX` real.
- Presets sem `THUMB2` continuam inalterados (G2).

## Aceite

`mvn test` na raiz (JBR 25) + `mvn install` + suites gbaemu/ndsemu.

## Armadilhas

- **Considerar adiar esta task para depois de B2.3.** B2.3 também registra
  extensões sob `top5=0b11101` (Load/store dual/exclusive/table branch, prefixo
  diferente de `0b1110101`) — se o desenho da opção (b)/(c) acima for definido
  apenas olhando para o caso de B2.2, corre o risco de precisar refazer quando
  B2.3 chegar. Fazer as duas extensões de `top5=0b11101` (data-processing +
  load/store) ANTES de fechar o contrato de "reservado" evita retrabalho.
- Não alterar o comportamento para o caso REALMENTE ambíguo (`BL`/`BLX` de dois
  halfwords) — só para o espaço que uma extensão registrada estruturalmente cobre
  mas não implementa integralmente.

# B19.17 — A64: `FEAT_CRC32` (checksum CRC-32/CRC-32C) — 8 células

**Trilha:** B · **Repo:** arm-jitter (+ revalidação G5) · **Depende de:** B19.9
**Épico:** `b19-plano-a64-gap-remanescente.md` · **Status:** ⬜ spec pronta para execução

## Contexto

Degrau novo, nomeado na varredura de fechamento `b19.9-a64-fechamento.md`, seção "Varredura do que
sobrou" (2026-09-10). `Aarch64Feature.CRC32` **já existe** (declarada `ARMV8_1_A`,
`arch64/Aarch64Feature.java:25-34`) — o Javadoc já documenta a origem exata do gap: **as 8 linhas do
lado A64 mediam `·` porque `docs/isa-nao-aplicavel.tsv` tinha uma entrada escrita para o lado de 32
bits** (onde `CRC32` de fato não existe em ARMv4T..ARMv7-A) **e a E12 a excluía erradamente também
do A64**. Do lado A64 é trabalho PENDENTE puro: "`Aarch64Decoder` as deixa explicitamente fora de
escopo hoje" — sem decode nenhum ainda.

**Esta é provavelmente a task mais simples do épico B19.14-B19.29**: `CRC32`/`CRC32C` já existem e
funcionam do lado ARM 32 bits do projeto (`ArmFeature`/décadas de precedente v8-A 32-bit) — o
algoritmo CRC-32/CRC-32C é padrão IEEE 802.3/Castagnoli, sem ambiguidade de formato como FP8/BF16, e
o núcleo de cálculo (se já existir do lado 32 bits) deveria ser **reusado diretamente**, não
reimplementado.

### As 8 células

| Mnemônico | `a64.decode` | Largura |
|---|---|---|
| `CRC32B` | `:718` | byte |
| `CRC32H` | `:719` | halfword |
| `CRC32W` | `:720` | word |
| `CRC32X` | `:721` | doubleword (só A64) |
| `CRC32CB` | `:723` | byte, polinômio Castagnoli |
| `CRC32CH` | `:724` | halfword, polinômio Castagnoli |
| `CRC32CW` | `:725` | word, polinômio Castagnoli |
| `CRC32CX` | `:726` | doubleword, polinômio Castagnoli (só A64) |

```
718:CRC32           0 00 11010110 ..... 0100 00 ..... .....  @rrr_b
719:CRC32           0 00 11010110 ..... 0100 01 ..... .....  @rrr_h
720:CRC32           0 00 11010110 ..... 0100 10 ..... .....  @rrr_s
721:CRC32           1 00 11010110 ..... 0100 11 ..... .....  @rrr_d
723:CRC32C          0 00 11010110 ..... 0101 00 ..... .....  @rrr_b
724:CRC32C          0 00 11010110 ..... 0101 01 ..... .....  @rrr_h
725:CRC32C          0 00 11010110 ..... 0101 10 ..... .....  @rrr_s
726:CRC32C          1 00 11010110 ..... 0101 11 ..... .....  @rrr_d
```

`CRC32<sz> Wd, Wn, Rm`: `Wd = crc32(Wn, Rm[<sz>], polinômio IEEE 802.3)`. `CRC32C<sz>` usa o
polinômio Castagnoli (o mesmo do iSCSI/`SSE4.2 CRC32`). `<X>` (doubleword) só existe no A64 —
diferença estrutural em relação ao 32-bit, que só vai até `W` (word).

**Leitura obrigatória**: o lado 32-bit do projeto (procurar `Crc32`/`ArmFeature.CRC32`/instruções
`CRC32*` já implementadas em `decoder`/`executor`/`ir` de 32 bits — se existirem, **reusar o núcleo
de cálculo diretamente**, só a largura `X`/64-bit é nova). Se não existir núcleo de 32 bits
reusável, implementar um novo com tabela de lookup padrão (256 entradas por polinômio) ou
`java.util.zip.CRC32`/`java.util.zip.Checksum` do JDK **conferindo se a semântica bate exatamente**
(cuidado: `java.util.zip.CRC32` usa reflexão de bits e complemento final específicos do formato ZIP
— a instrução ARM `CRC32` pode ou não bater byte a byte; testar contra vetores conhecidos antes de
assumir).

## Objetivo

As 8 linhas decodificam e executam sob `ARMV8_1_A`+ (feature obrigatória a partir daí, opcional em
`ARMv8.0-A` — conferir se algum preset `ARMV8_0_A` precisa declará-la opcionalmente, ou se a
convenção do projeto é só declarar em `ARMV8_1_A` como já está).

## Inclui

1. **Núcleo de CRC-32/CRC-32C** — reusar o do lado 32 bits se existir; senão, implementar tabela de
   lookup padrão para os dois polinômios (IEEE 802.3 `0xEDB88320` refletido / Castagnoli
   `0x82F63B78` refletido — conferir contra vetores de teste conhecidos, não confiar de memória).
2. **Decode das 8 linhas** (`@rrr_b`/`@rrr_h`/`@rrr_s`/`@rrr_d`) no espaço "Data-processing (2
   source)" de registrador geral.
3. **Executor**: aplica o CRC byte a byte (ou halfword/word/doubleword, decompondo internamente em
   bytes conforme o pseudocódigo real) sobre `Wn`(CRC anterior) + `Rm`(dado), produz `Wd`.
4. Testes (ver Aceite).

## Não inclui

- **Emissão nativa** (embora `CRC32` tenha instrução de hardware x86/ARM dedicada em muitos casos —
  fora do escopo desta task).

## Passos

1. Procurar núcleo de CRC-32 já existente no lado 32 bits do projeto.
2. Núcleo (reusado ou novo) + tabelas de lookup, testado contra vetores conhecidos (RFC 3720 para
   Castagnoli, e o vetor clássico `"123456789"` → `0xCBF43926` para IEEE 802.3 CRC-32 — CONFERIR se
   a variante ARM usa a mesma convenção de reflexão/complemento antes de usar esse vetor como
   golden; se não bater, procurar o vetor de teste correto do pseudocódigo ARM real).
3. Decode das 8 linhas + executor.
4. Corpus golden via `aarch64-*-as -march=...+crc`; a maioria dos toolchains já suporta sem flag
   extra em versões recentes — conferir.
5. `mvn -o test` + `install` + G5 + `./gerar-cobertura-isa.sh`.
6. `INDICE.md`, `## Resultado`, commit `B19.17: …`, `git push`.

## Aceite

- As 8 linhas decodificam sob a versão correta e seguem `unsupported` abaixo.
- **Vetor de teste conhecido** batendo exatamente (documentar a fonte do vetor usado — RFC ou
  pseudocódigo ARM real, não um valor "parece certo").
- **`CRC32` × `CRC32C`** produzem valores DIFERENTES para a mesma entrada (prova de que os dois
  polinômios não foram confundidos).
- **`X` (doubleword) só existe no A64** — se o núcleo for reusado do 32-bit, testar que a largura
  `X` funciona corretamente (decompor em bytes de um valor de 64 bits).
- `docs/COBERTURA-ISA.md`: as 8 células saem de `❌` para `✅` de `ARMv8.1-A` em diante.
- `mvn -o test` verde + G5 verde nos 5 consumidores.

## Armadilhas

1. **`java.util.zip.CRC32` pode não bater bit a bit** com a instrução ARM — confirmar com vetor de
   teste antes de assumir que dá para simplesmente delegar pro JDK.
2. **Não reimplementar o núcleo se já existir do lado 32 bits** — checar primeiro, é claramente a
   task mais simples do épico e não deveria ganhar complexidade desnecessária.
3. **Polinômio errado é o bug mais silencioso possível aqui** — sem vetor de teste real, um CRC
   "plausível" passa despercebido para sempre.

## Não fazer

- Não reimplementar CRC-32 do zero se já existir núcleo reusável do lado 32 bits.
- Não confiar em `java.util.zip.CRC32` sem confirmar a semântica exata contra um vetor real.
- Não adicionar caso nativo em `Ir64NativePolicy`.

# B9.8.1 — `CpuMode.HYP`/`CpuMode.MONITOR` + banking real em `ArmCore`

**Trilha:** B · **Depende de:** — · **Repo:** arm-jitter

## Contexto

Ver o plano mestre `b9.8-plano-hyp-monitor-32bit.md` (leia antes de mexer neste arquivo) — fatos de
referência conferidos via QEMU real (`target/arm/tcg/{translate.c,a32.decode}`) ficam lá, não
repetidos aqui.

`CpuMode` hoje só tem os 7 modos clássicos; `CpuMode.fromBits` lança `IllegalArgumentException`
para qualquer bit de modo fora dessa lista — isso é um bug latente: um guest real que escrevesse
`0b11010` (Hyp) ou `0b10110` (Monitor) no campo M do CPSR travaria o emulador com uma exceção Java,
mesmo sem nenhuma instrução de Hyp/Monitor decodificada ainda.

Fonte real do banking de `SP_hyp`/`ELR_hyp`/`SPSR_hyp` conferida em `msr_banked_access_decode` do
QEMU (`target/arm/tcg/translate.c`, `curl` nesta sessão): Hyp mode NÃO banca `LR` — o modo usa o
`LR_usr` compartilhado (mesma linha física de registrador); só `SP_hyp` é banco próprio. `ELR_hyp`
é um registrador arquitetural À PARTE, sem índice 0-15 (QEMU o chama arbitrariamente de "regno 17").
Monitor mode é um banco normal (`SP_mon`/`LR_mon`/`SPSR_mon`), sem essa peculiaridade.

## Objetivo

`ArmCore` reconhece e banca `HYP`/`MONITOR` corretamente, sem quebrar nenhum comportamento
existente (G3) — puramente aditivo, sem decodificar nenhuma instrução nova ainda.

## Inclui

1. `CpuMode.HYP(0b11010)` e `CpuMode.MONITOR(0b10110)` novos no enum.
2. `ArmCore`: campos novos `hypSp` (int), `elrHyp` (int, registrador à parte — NÃO reaproveitar o
   índice 14/LR), `hypSpsr` (int), `monitorSpLr` (`int[2]`, mesmo padrão de `supervisorSpLr`/
   `abortSpLr`/`undefinedSpLr`), `monitorSpsr` (int).
3. `spsr(CpuMode)`/`setSpsr(CpuMode, int)`: casos `HYP -> hypSpsr` e `MONITOR -> monitorSpsr`
   adicionados ao switch exaustivo (o compilador força — a lista `USER, SYSTEM -> throw` continua
   sem HYP/MONITOR, porque os dois TÊM SPSR, ao contrário de USER/SYSTEM).
4. `spLrBank(CpuMode)`: caso `MONITOR -> monitorSpLr` adicionado (banco normal). Caso `HYP -> throw
   IllegalArgumentException` (mesmo padrão do `FIQ` existente — ver Armadilhas, o SP de Hyp é
   tratado à parte, nunca por este método).
5. `saveSpLr(CpuMode)`/`restoreSpLr(CpuMode)`: caso especial para `HYP` ANTES do fallback genérico
   — salvar/restaurar só `SP` via `hypSp`; `LR` lê/escreve `userSystemSpLr[1]` diretamente (ver
   Armadilhas para o motivo).
6. `bankedRegister(CpuMode, int)`/`setBankedRegister(CpuMode, int, int)`: caso especial para `HYP`
   nos ramos de SP/LR (registrador 13 → `hypSp`; registrador 14 → `userSystemSpLr[1]`), espelhando
   a estrutura já usada para o caso `FIQ`.
7. `elrHyp()`/`setElrHyp(int)` novos — acessores dedicados (registrador à parte, fora da API de
   `bankedRegister`, que só cobre índices 0-15).
8. `saveState`/`loadState`: `STATE_VERSION` `2`→`3`; grava/lê os 5 campos novos (`hypSp`, `elrHyp`,
   `hypSpsr`, `monitorSpLr[2]`, `monitorSpsr`) só quando `version >= 3` (streams antigos carregam
   zerados, mesmo padrão que a B3.3 usou para o banco VFP na v2).
9. Teste novo (`ArmCoreHypMonitorBankingTest` ou nome equivalente): `switchMode(HYP)`/
   `switchMode(MONITOR)` não lançam; `SP` banca corretamente em cada um; `LR` em Hyp mode É o mesmo
   valor de `LR` em USER/SYSTEM (escrever em Hyp, trocar para USER, ler de volta o mesmo valor, e
   vice-versa); `ELR_hyp` sobrevive a troca de modo e NÃO é confundido com `LR`; `SPSR_hyp`/
   `SPSR_mon` independentes de todos os outros SPSRs; `CpuMode.fromBits(0b11010)`/`fromBits(0b10110)`
   não lançam mais.

## Não inclui

- Qualquer decodificação de instrução nova (`HVC`/`SMC`/`ERET`/`MRS_bank`/`MSR_bank`) — B9.8.2 a
  B9.8.5.
- Vetores de exceção/entrada para Hyp/Monitor (`HVBAR`/`MVBAR`, roteamento) — B9.8.2/B9.8.3.

  que os alcançam forem decodificadas, B9.8.2+, mesmo critério de `ArmFeature.BLX` etc. gatear a
  INSTRUÇÃO, não o modo).

## Armadilhas

- **`LR` em Hyp mode não é um banco próprio — é literalmente o mesmo registrador físico que
  `LR_usr`/`LR_sys`.** Ao SAIR de Hyp mode, o valor corrente de `registers[LR]` tem que ser
  escrito de volta em `userSystemSpLr[1]` (não descartado) — senão uma escrita a `LR` feita
  DURANTE a execução em Hyp mode "some" ao trocar de modo. Ao ENTRAR em Hyp mode, `registers[LR]`
  tem que vir de `userSystemSpLr[1]`, não de um banco Hyp inexistente.
- **Não reaproveitar o índice de registrador 14 (`LR`) para `ELR_hyp`.** São dois registradores
  arquiteturais DIFERENTES que coexistem simultaneamente em Hyp mode (`ERET` lê `ELR_hyp`; qualquer
  outra instrução que leia `R14` lê `LR_usr`) — por isso `elrHyp()` é um acessor à parte, fora de
  `bankedRegister`.
- **`spLrBank(HYP)` deve lançar, não devolver um array incompleto** — o padrão exaustivo do switch
  já lança para `FIQ` pelo mesmo motivo (FIQ banca R8-R14 inteiro, não só SP/LR; aqui é o oposto:
  Hyp banca só SP). Um array de 2 elementos aqui esconderia o caso `LR` incorretamente se algum
  código futuro chamar `spLrBank` diretamente sem passar pelos caminhos já especializados de
  `saveSpLr`/`restoreSpLr`/`bankedRegister`/`setBankedRegister`.
- **`STATE_VERSION` é interno ao `ArmCore`** (não confundir com o versionamento próprio de
  `GbaConsole`/`NdsConsole`, que já rejeita formatos incompatívies por inteiro antes de chegar
  aqui) — só precisa degradar sem lançar quando alimentado por um stream `< 3`, mesmo padrão já
  usado pela B3.3 com o banco VFP.

## Resultado (2026-08-27)

Implementado exatamente como especificado. `CpuMode.HYP(0b11010)`/`CpuMode.MONITOR(0b10110)`
adicionados ao fim do enum (ordinal novo, não reordena os 7 existentes — save states antigos que
gravam `activeMode.ordinal()` continuam válidos). `ArmCore` ganhou `hypSp`/`elrHyp`/`hypSpsr`/
`monitorSpLr[2]`/`monitorSpsr`; `spsr`/`setSpsr` (switch exaustivo), `bankedRegister`/
`setBankedRegister` e `saveSpLr`/`restoreSpLr` ganharam um ramo `HYP` especial (espelhando a
estrutura já usada para `FIQ`): `SP_hyp` é banco próprio, `LR` em Hyp mode lê/escreve diretamente
`userSystemSpLr[1]` (o mesmo `LR_usr`/`LR_sys`, não um banco à parte — confirmado contra
`msr_banked_access_decode` real do QEMU nesta sessão, `curl` de `target/arm/tcg/translate.c`).
`spLrBank(HYP)` lança (mesmo padrão do `FIQ` pré-existente) — o caminho genérico nunca deveria
tentar tratar Hyp como um banco de 2 elementos comum. `elrHyp()`/`setElrHyp(int)` novos, acessores
à parte (registrador arquitetural fora da numeração R0-R15). `STATE_VERSION` `2`→`3`, os 5 campos
novos gravados/lidos condicionalmente (`version>=3`, streams antigos carregam zerados — mesmo
padrão da B3.3 com o banco VFP).

`mvn -o test` verde no `core` (teste novo `ArmCoreHypMonitorBankingTest`, 8 casos: round-trip de
`SP_hyp`, comportamento compartilhado de `LR` em Hyp mode, `ELR_hyp` distinto de `LR`, banking
normal de `SP_mon`/`LR_mon`, independência dos 3 SPSRs novos, round-trip de save-state v3 e
degradação sem lançar a partir de um stream v2) + suíte completa do `arm-jitter` (`mvn -o test`
raiz); `mvn -o install` local feito. G5 completo: gbaemu ✅, ndsemu ✅, n3dsemu ✅,
virtual-arm-box ✅, armbox ✅ — nenhum consumidor usa Hyp/Monitor mode ainda, mudança puramente
aditiva (zero-diff confirmado).

Achado colateral confirmado (não corrigido, fora do escopo desta task): antes desta sessão,
`CpuMode.fromBits(0b11010)`/`fromBits(0b10110)` lançavam `IllegalArgumentException` — um guest real
escrevendo esses bits de modo no CPSR (ex. `CPS`/`MSR CPSR_c`) travaria o emulador com uma exceção
Java, mesmo sem nenhuma instrução Hyp/Monitor implementada. Agora reconhece o bit de modo (troca de
banco funciona), mas nenhum consumidor real hoje gera esses bits — a correção só passa a ser
observável quando B9.8.2+ (`HVC`/`SMC`) ou algum preset com `V7VE`/Security Extensions existir.

# B10.1 — EL2/EL3: generalizar estado de exceção para os 4 níveis

**Trilha:** B · **Depende de:** — (fundação do épico) · **Repo:** arm-jitter

## Contexto

Primeira task da escada B10 (`b10-plano-el2-el3.md`) — fundação de tudo que vem depois. Antes
desta task, `Aarch64Core`/`Aarch64ExceptionState` só sabiam distinguir `EL0`/`EL1`
(`boolean inEl1`), com `ELR`/`SPSR`/`ESR`/`FAR`/`VBAR`/`SP` bancados só para `EL1`. `ERET` sempre
assumia "volta pra EL0" e a entrada de exceção sempre assumia "vem de um nível inferior" (vetor
fixo em `+0x400`) — nenhum dos dois é verdade em geral quando `EL2`/`EL3` existem.

## Inclui

- `Aarch64ExceptionLevel` (novo enum): `EL0`-`EL3`, cada um carregando o campo `M[3:0]` real de
  `SPSR_ELx` (forma "h", `SP_ELx` bancado — mesma simplificação que já valia só para `EL1`) e
  `fromSpsrValue(long)` para decodificar o nível-ALVO de um `ERET` a partir do valor bruto.
- `Aarch64ExceptionState`: `SP`/`ELR`/`SPSR`/`ESR`/`FAR`/`VBAR` viram arrays por nível (`EL1`-
  `EL3`; `EL0` lança `IllegalArgumentException` — não tem banco). `boolean inEl1` vira
  `Aarch64ExceptionLevel currentEl`. As 12 conveniências nomeadas de `EL1` (`sp1()`/`setSp1()`/...)
  e `inEl1()`/`setInEl1()` continuam existindo, agora delegando pras genéricas — TODO código/teste
  que só conhecia `EL1` continua compilando e passando sem mudança nenhuma.
- `Aarch64Core.sp()`/`setSp()`: resolvem `SP_ELx` do nível ATUAL (generalizado de "só `EL1`" para
  qualquer um dos 4).
- `CurrentEL` (`MRS`): reflete os 4 valores reais (`[3:2]` = `00`/`01`/`10`/`11`), não só `00`/`01`.
- `Aarch64Core.enterSynchronousException`/`enterIrq`: recebem (ou, no caso de `enterIrq`, calculam
  internamente) um nível-ALVO explícito em vez de sempre `EL1` hardcoded; `SPSR_ELx` do alvo grava
  o `M[3:0]` do nível de ORIGEM (pra `ERET` saber pra onde voltar depois). Seleção de GRUPO de
  vetor agora real: "mesmo nível, `SP_ELx`" (`+0x200`) quando a exceção ocorre já dentro do
  nível-alvo (nested — ex. `BRK` dentro do próprio handler de `EL1`), "nível inferior AArch64"
  (`+0x400`) quando entra vindo de baixo — antes só o segundo caso existia (era o único possível
  com 2 níveis).
- `ERET` (executor): lê `ELR_ELx`/`SPSR_ELx` do nível ATUAL (não mais sempre `EL1`) e decodifica o
  nível-ALVO real via `Aarch64ExceptionLevel.fromSpsrValue` (não mais "sempre volta pra EL0").
- **Todos os 4 chamadores existentes** (`enterMemoryAbort`/`enterBreakpointException`/
  `enterUndefinedInstructionException`/`enterIrq`) continuam passando `EL1` explicitamente — **sem
  roteamento real por `HCR_EL2`/`SCR_EL3` ainda** (isso é B10.4/B10.5). Comportamento observável
  IDÊNTICO ao de antes desta task para todo fluxo EL0↔EL1 existente; o que muda é só a
  infraestrutura por baixo, pronta para B10.2+ conectarem `EL2`/`EL3` de verdade.

## Não inclui

- Registradores de sistema EL2/EL3 (`HCR_EL2`, `SCR_EL3`, ...) — B10.2/B10.3.
- Roteamento real de `IRQ`/`HVC`/`SMC`/abort para EL2/EL3 baseado em `HCR_EL2`/`SCR_EL3` — B10.4/
  B10.5 (por enquanto TUDO que entra em exceção síncrona/IRQ vai pra `EL1`, como sempre foi).
- `AT`, registradores de debug, `TLBI` EL2/EL3, stage-2 — demais tasks da escada.

## Validação

- Testes novos: `Aarch64ExceptionLevelTest` (6 casos: round-trip dos 4 níveis, decodificação
  ignora NZCV/I), `Aarch64ExceptionStateB101Test` (conveniências EL1 batem com as genéricas, EL2/
  EL3 têm bancos independentes de EL1, EL0 lança, `currentEl()` default EL0), `Ir64BlockExecutorB101Test`
  (4 casos via `step()`/`executeOp` real: `BRK` de `EL0` usa o grupo "nível inferior" `+0x400`,

  antes desta task —, `CurrentEL` reflete os 4 valores via `MRS`, `ERET` volta pro nível codificado

## Armadilhas encontradas

- A tabela de vetores de exceção A64 tem 4 GRUPOS de origem (`ARM DDI 0487 D1.10`), não 1 —
  "mesmo nível `SP_EL0`", "mesmo nível `SP_ELx`", "nível inferior AArch64", "nível inferior
  AArch32". Com só `EL0`/`EL1` modelados, só o grupo "nível inferior AArch64" era alcançável
  (não dava pra distinguir do grupo "mesmo nível" observando o comportamento). Com `EL2`/`EL3`
  reais chegando, uma exceção pode genuinamente ocorrer DENTRO do próprio nível-alvo (nested) —
  `vectorGroupBase` decide isso comparando nível de origem vs. alvo, e lança se `target < source`
  (uma exceção NUNCA reduz privilégio — bug de chamador, não caso arquitetural real, G8).
- `ERET` não é "volta um nível abaixo do atual" — é "volta pro nível codificado em
  `SPSR_ELx.M[3:0]`", que pode pular níveis (`EL3→EL1` direto, por exemplo, é legítimo). Um
  refactor ingênuo que só trocasse `EL0` fixo por "nível atual − 1" teria ficado errado assim que
  qualquer handler de EL2/EL3 tentasse devolver controle direto a EL1/EL0.

# B22.2 — `VMOV_half`: matar o único `⚠️` do projeto (violação de G8 viva)

**Trilha:** B · **Repo:** arm-jitter (+ revalidação G5 nos consumidores) · **Depende de:** —
**Épico:** `b22-plano-residuos-32-bits.md` · **Status:** ⬜

## Contexto

`VMOV_half` (`VMOV Sn, Rt` / `VMOV Rt, Sn` de **meia precisão** — transferência de 16 bits entre um
registrador ARM e a metade baixa de um `S`) é o **único `⚠️` do projeto inteiro** em
`docs/COBERTURA-ISA.md` (2 células: coluna VFP de `ARM11 MPCore` e de `v7-A`). A legenda da tabela:
`⚠️` = **decodifica como OUTRA coisa** — "não é suporte, é o decoder não sabendo recusar". É uma
violação de **G8 viva**: em vez de uma exceção de instrução indefinida (diagnóstico que a B3.9
mostrou resolver em minutos), o guest recebe **corrupção silenciosa**.

### Por que decodifica errado hoje

Encoding (oráculo `target/isa-decode/vfp.decode:77`):

```
VMOV_half   ---- 1110 000 l:1 .... rt:4 1001 . 001 0000   vn=%vn_sp
```

- `bits[27:24]=1110`, `bit4=1` (o `001` em bits[6:4]), `bits[11:8]=1001`.
- `VfpDecoder` está registrado ANTES de `CoprocessorDecoder` justamente porque `VMOV_single`/
  `VMSR_VMRS`/`VMOV_64_dp` compartilham o formato `bit4=1` de `MRC`/`MRRC` genérico
  (`VfpDecoder.java:28-31`). Mas `VfpDecoder#decodeCoreTransferOrSystem` só reconhece
  `size == SIZE_SINGLE` (`bits[11:8]=1010`). Com `bits[11:8]=1001`, o `VfpDecoder` **devolve
  `null`** → o `CoprocessorDecoder` captura e decodifica como `IrOp.Coprocessor` genérico (um
  `MCR`/`MRC` para o "coprocessador 9") entregue ao `CoprocessorBus`. Nenhuma exceção, nenhum
  diagnóstico — o `⚠️`.

`VMOV_half` exige a extensão de **meia precisão de ponto flutuante** (VFPv3 half-precision /
`FEAT_FP16`, ARMv8.2-A no lado moderno). **Nenhum preset deste projeto a tem** (0% de cobertura
NEON/FP16 documentado; o ARM11 MPCore real do 3DS também não tem).

## Objetivo

`VfpDecoder` passa a **reivindicar** o encoding de `VMOV_half` (devolver `unimplemented`, nunca
`null`) — cortando o fallthrough para o `CoprocessorDecoder`. Com isso o `⚠️` vira `❌` honesto (ou
`·` via curadoria, ver Inclui 3). Gate por `ArmFeature.HALF_PRECISION_FP` novo, **nenhum preset o
declara** → **zero-diff de runtime** (o encoding que hoje vira um `MCR` genérico espúrio passa a
ser `UNDEFINED` — mudança de comportamento só para código que já estava quebrado; ver Armadilhas).

## Inclui

1. **`ArmFeature.HALF_PRECISION_FP`** — Javadoc `///` PT: "Meia precisão de ponto flutuante
   (VFPv3-HP / `FEAT_FP16`) — `VMOV` de 16 bits entre registrador ARM e `S`, e (futuro) aritmética
   `_hp`. Nenhum preset a declara; casa com o `FEAT_FP16` do lado A64 (B19.5) e com o preset
   ARMv8-A de 32 bits (B14)." Posição no enum: contígua ao final, junto de `VFPV2`/
   `VFP_FUSED_MULTIPLY_ACCUMULATE`.
2. **`VfpDecoder`**: no ponto onde `decodeCoreTransferOrSystem` (ou o dispatch que chama
   `decodeScalarGpTransfer`, `VfpDecoder.java:291-341`) hoje rejeita `bits[11:8] != 1010`,
   acrescentar o reconhecimento de `bits[11:8] == 1001` com o padrão exato de `VMOV_half`
   (`---- 1110 000 l .... rt 1001 . 001 0000` — conferir bit a bit: bit20=`l`, bits[19:16]:bit7 =
   `vn` (`%vn_sp`), bits[15:12]=`rt`, bits[6:4]=`001`, bits[3:0]=`0000`). Sem
   `ArmFeature.HALF_PRECISION_FP` → `DecodedInstruction.unimplemented(...)`. **Com** a feature →
   ver Inclui 4 (implementar a transferência ou recusar — decisão da spec abaixo).
3. **`docs/isa-nao-aplicavel.tsv`**: linha para `VMOV_half`, escopada por `grupo=vfp.decode` e, se
   o nome colidir dentro do arquivo, por `ocorrencia` (B9.17 — foi exatamente `VMOV_half` que
   motivou a coluna `ocorrencia`; conferir se as 3 linhas byte/halfword/word de `vfp.decode`
   ainda batem). Fonte: "VFPv3 half-precision / `FEAT_FP16`, ARM DDI 0487 — extensão opcional não
   declarada por nenhum preset". Cobre MPCore e v7-A. Isso leva o `⚠️` → `·`.
4. **Decisão da spec — implementar a transferência agora, gateada:** `VMOV_half` é uma cópia CRUA
   de bits (não interpreta o float): `l=1` → `Rt = ZeroExtend(Sn[15:0], 32)`; `l=0` → `Sn[15:0] =
   Rt[15:0]`, `Sn[31:16]` **inalterado** (ARM DDI 0487 `VMOV` half). É trivial e há precedente
   direto (`VMOV_single`, mesmo `InstructionKind.VFP_CORE_TRANSFER`). **Implementar**, reusando
   `VFP_CORE_TRANSFER` + o executor de `VMOV_single` estendido para a largura 16
   (`IrOp`/`VfpOperation` — conferir se cabe sem `Kind` novo; se exigir campo novo, um `boolean
   halfWidth` no record de transferência VFP, aditivo, G3). O caminho fica **inerte** (nenhum
   preset com a feature) mas pronto para B14 e testável com uma arquitetura de teste.
   *Alternativa mínima, se o executor de `VMOV_single` não generalizar barato:* só reconhecer +
   `unimplemented` (mata o `⚠️`, transferência fica para B14). Escolher no Passo 2 e registrar no
   `## Resultado`.
5. **Thumb-2 (T32)**: `VMOV_half` tem forma T32 (`Thumb2VfpDecoder` / o decoder VFP Thumb-2). Se o
   projeto tiver o decoder VFP Thumb-2 (conferir — B3.5 fez o CP10/11 ARM+Thumb-2), aplicar o
   MESMO reconhecimento+gate lá. Se a coluna T32 não mostra `⚠️`/`❌` para `VMOV_half` (a B22
   mediu só MPCore/v7-A na coluna VFP), o T32 pode já estar caindo em `UNDEFINED` limpo — **medir
   antes** e só mexer se houver `⚠️`.
6. Testes (ver Aceite).

## Não inclui

- **Aritmética de meia precisão** (`VADD_hp`/`VMUL_hp`/`VCVT` f16↔f32/etc.) — é B13.6 (`_hp` NEON)
  / B19.5 (A64 `FEAT_FP16`) / uma task VFP-HP própria. Esta task é só o `VMOV`.
- **Preset com `HALF_PRECISION_FP`** — B14.
- Modelagem de storage f16 separado — `VMOV_half` opera nos bits crus de um `S` que já existe.

## Aceite

- `VMOV_half` (`---- 1110 000 l .... rt 1001 . 001 0000`) **não decodifica mais como
  `IrOp.Coprocessor`** — sob os presets atuais é `UNIMPLEMENTED` explícito; sob uma arquitetura de
  teste com `HALF_PRECISION_FP` é `InstructionKind.VFP_CORE_TRANSFER` (half) — e, se Inclui 4
  completo, executa a cópia de 16 bits corretamente (`l=1` zero-estende para `Rt`; `l=0` escreve só
  `Sn[15:0]`, preserva `Sn[31:16]`).
- **`docs/COBERTURA-ISA.md`: zero `⚠️` no projeto inteiro.** `VMOV_half` vira `·` (curadoria com
  fonte) nas colunas MPCore/v7-A.
- `VMOV_single`, `VMOV_to_gp`/`VMOV_from_gp` (B9.5/B9.17), `VMSR`/`VMRS` continuam decodificando
  idêntico — teste de regressão.
- `mvn -o test` verde + G5 nos 5 consumidores. **Praticamente zero-diff** — a única mudança de
  comportamento é o encoding de `VMOV_half` virar `UNDEFINED` em vez de um `MCR`/`MRC` espúrio para
  cp9; nenhum consumidor emite `VMOV_half` (nenhum tem meia precisão), então na prática é diff vazio
  (confirmar com G5 completo).

## Validação

`mvn -o test` no arm-jitter (JBR 25), `mvn -o install`, `mvn -o test` nos 5 consumidores,
`./gerar-cobertura-isa.sh` — conferir `⚠️` zerado.

## Armadilhas

1. **`⚠️` é PIOR que `❌`, não "quase pronto".** A tabela conta `VMOV_half` como 2 células que
   parecem 90% feitas — não são: são um caso conhecido de corrupção silenciosa. Priorizar como
   se fosse gap real (a B22 registra isso explicitamente).
2. **A mudança de comportamento (`MCR` espúrio → `UNDEFINED`) é uma MELHORA, mas é mudança.** Rodar
   G5 completo. Se algum teste de consumidor assertava o `IrOp.Coprocessor` espúrio nesses bits
   (improvável — seria um teste de comportamento errado), **reportar**, não "consertar" o teste
   silenciosamente.
3. **Ordem de registro `VfpDecoder` antes de `CoprocessorDecoder` continua obrigatória** — esta
   task depende dela (é o que permite `VfpDecoder` interceptar antes). Não reordenar.
4. **`vfp.decode` tem 3 linhas de `VMOV_*` no mesmo espaço** (`VMOV_single` `1010`, `VMOV_half`
   `1001`, e a forma `VMOV_to_gp` scalar). A curadoria por nome + `grupo` pode não bastar se
   `ocorrencia` (B9.17) já estiver em uso para `VMOV_*` — conferir o estado atual do TSV antes de
   adicionar linha.
5. **T32: medir antes de mexer.** Se a coluna T32 de `VMOV_half` já é `UNDEFINED` limpo (não `⚠️`),
   não tocar o decoder VFP Thumb-2 — só o A32 tem o problema medido.
6. **`l=0` NÃO zera `Sn[31:16]`** (ao contrário de `VMOV_single`, que escreve o `S` inteiro). ARM
   DDI 0487: `VMOV` half escreve só a metade baixa. Errar isso é bug silencioso (só visível se o
   guest ler o `S` como float32 depois).

## Não fazer

- Não implementar aritmética de meia precisão.
- Não adicionar `HALF_PRECISION_FP` a nenhum preset.
- Não reordenar `VfpDecoder`/`CoprocessorDecoder`.
- Não mexer no decoder VFP Thumb-2 sem medir que há `⚠️` lá.

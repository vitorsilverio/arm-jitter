# B19.19 — A64: `FEAT_LRCPC2` (load-acquire RCpc com offset imediato) — 7 células

**Trilha:** B · **Repo:** arm-jitter (+ revalidação G5) · **Depende de:** B19.9
**Épico:** `b19-plano-a64-gap-remanescente.md` · **Status:** ⬜ spec pronta para execução

## Contexto

Degrau novo, nomeado na varredura de fechamento `b19.9-a64-fechamento.md`, seção "Varredura do que
sobrou" (2026-09-10). `Aarch64Feature.LRCPC2` **já existe** (declarada `ARMV8_4_A`,
`arch64/Aarch64Feature.java:85-90`) — o Javadoc já documenta a decisão herdada de simplificação:
"a ordenação RCpc é NOP observável neste interpretador single-thread (mesma simplificação de
`LDAR`/`acquireRelease`), a feature existe só para o gate por versão." Ou seja: **o trabalho real
desta task é decode + o cálculo de endereço com offset imediato**, não semântica de memory
ordering nova — a ordenação já está resolvida por decisão anterior (herdar, não revisitar).

### O que a extensão faz

`FEAT_LRCPC` (ARMv8.3-A, `Aarch64Feature.LRCPC`, já implementada) trouxe `LDAPR`/`LDAPRB`/`LDAPRH`
com endereçamento SÓ registrador (sem offset). `FEAT_LRCPC2` (ARMv8.4-A) acrescenta a forma com
**offset imediato de 9 bits com sinal** (`LDAPUR`/variantes) — o mesmo padrão de "as instruções
antigas ganham uma forma com offset imediato" que apareceu em outras extensões do ARM. `STLR_i` é a
contraparte de store (a única linha de `STLR` com offset imediato).

- **`sign`/`ext`**: controlam extensão de sinal (para larguras menores que 64 bits carregadas num
  registrador de 32 ou 64 bits) — mesma disciplina de `LDUR`/`LDURSB`/`LDURSH`/`LDURSW` comuns.
- **Ordenação**: RCpc ("Release Consistent, processor consistent") é mais fraca que a ordenação
  Multi-Copy-Atomic completa de `LDAR`/`STLR` "clássicos" — mas **neste emulador single-thread
  qualquer ordenação é observacionalmente NOP** (decisão já tomada, herdar).

**Leitura obrigatória**: o decoder/executor de `LDAPR`/`STLR` (formas SEM offset, `FEAT_LRCPC`/
`FEAT_LSE` — B11.6/B11.11 tocaram gate de features vizinhas nesse bloco) — reusar a MESMA lógica de
"acquire/release é NOP observável", só acrescentando o cálculo de offset imediato. Reusar também o
padrão de extensão de sinal (`sign`/`ext`) de `LDUR`/variantes já implementadas.

## Objetivo

As 7 linhas decodificam e executam sob `ARMV8_4_A`+, gateadas por `Aarch64Feature.LRCPC2`.

## Inclui

1. **Decode de `LDAPR_i`** (6 formas: `sign=0`/`ext=0` com `sz` no campo comum, e `sign=1` com
   `sz` fixo no encoding + `ext=0`/`ext=1`) no formato `@ldapr_stlr_i`.
2. **Decode de `STLR_i`** (offset imediato, `sign=0`/`ext=0`).
3. **Executor**: leitura/escrita de memória no endereço `Xn + offset9` (offset com sinal), com
   extensão de sinal/zero conforme `sign`/`ext`, reusando a lógica "acquire/release = NOP
   observável" já existente para `LDAPR`/`STLR` sem offset.
4. Testes (ver Aceite).

## Não inclui

- **Semântica de ordenação real** — decisão herdada, não revisitada.
- **`FEAT_LRCPC` sem offset** — já implementada.
- **Emissão nativa.**

## Passos

1. Ler o decoder/executor de `LDAPR`/`STLR` sem offset (`FEAT_LRCPC`).
2. Decode das 7 linhas no formato `@ldapr_stlr_i`, reusando cálculo de offset de `LDUR`.
3. Executor reusando a lógica de acquire/release NOP + extensão de sinal de `LDUR`.
4. Corpus golden via `aarch64-*-as -march=...+rcpc2` (ou nome real).
5. `mvn -o test` + `install` + G5 + `./gerar-cobertura-isa.sh`.
6. `INDICE.md`, `## Resultado`, commit `B19.19: …`, `git push`.

## Aceite

- As 7 linhas decodificam sob `ARMV8_4_A`+ e seguem `unsupported` abaixo.
- **Offset com sinal**: teste com offset negativo e positivo.
- **Extensão de sinal/zero**: `LDAPR_i` de largura `B`/`H`/`W` com bit alto setado produz resultado
  diferente conforme `sign=0`(zero-extend)/`sign=1`(sign-extend).
- **`STLR_i`/`LDAPR_i` continuam sem efeito de ordenação observável** (herdado, teste se a suíte de
  `LDAPR`/`STLR` sem offset já cobrir isso, ou documentar que não há teste dedicado por decisão).
- `docs/COBERTURA-ISA.md`: as 7 células saem de `❌` para `✅` de `ARMv8.4-A` em diante.
- `mvn -o test` verde + G5 verde nos 5 consumidores.

## Armadilhas

1. **Não reabrir a decisão de ordenação** — é NOP observável por decisão já tomada, esta task só
   adiciona offset imediato.
2. **6 formas de `LDAPR_i` para 1 mnemônico** — cada uma cobre uma combinação de `sign`/`ext`/`sz`
   diferente; testar todas, não só uma.
3. **Offset de 9 bits, não 12** — não confundir com o offset "unsigned" de 12 bits de `LDR`/`STR`
   comuns; este é assinado, mesma família de `LDUR`.

## Não fazer

- Não modelar ordenação de memória real.
- Não implementar `FEAT_LRCPC` sem offset (já existe).
- Não adicionar caso nativo em `Ir64NativePolicy`.

# B6.6.2 — AArch64: `TranslatingAddressSpace64` (page-walk VMSA64, 4KiB granule)

**Trilha:** B · **Depende de:** B6.1 ✅ (`memory/AddressSpace64` precisa
existir) — **independente de B6.6.1** (pode ser feita em paralelo, sessões
diferentes; só B6.6.3 depende das DUAS) · **Repo:** arm-jitter

## Contexto

Segunda das 6 sub-tasks de B6.6 (ver decomposição em B6.6.1). Espelho direto
de **B4.1.1** (`TranslatingAddressSpace`, 32-bit, short-descriptor ARMv6) —
mas para VMSA64: descritores de 64 bits, granule de 4KiB, até 4 níveis de
tabela (esta task cobre só a configuração mínima real usada por kernels
arm64 modernos: **granule 4KiB, endereço virtual de 48 bits, 4 níveis L0-L3**
— configurações de 16KiB/64KiB granule ou VA de 39/42 bits ficam fora,
mesma disciplina de "só o necessário para o aceite" que B4.1.1 aplicou ao
short-descriptor ARMv6 sem sub-pages/XN/TEX).

**Por que independente de B6.6.1**: o page-walk em si (dado `TTBR0`/`TCR`
como parâmetros diretos passados por método Java — `setTtbr0(long)` etc.,
mesmo padrão de API direta que `TranslatingAddressSpace` (32-bit) já usa,
testável com tabelas de página montadas à mão no teste, SEM nenhuma
instrução `MSR` real envolvida) não precisa que código GUEST consiga
escrever esses registradores — só precisa que ALGUÉM (o teste, ou depois
B6.6.3) consiga chamar os setters Java diretamente. Mesma independência que
`TranslatingAddressSpace` (32-bit) teve de `Cp15VmsaCoprocessor` (B4.1.1
antes de B4.1.2).

## Fatos de referência (fonte: `ARM DDI 0487` D8 "The AArch64 Virtual Memory
System Architecture" — CONFERIR literalmente contra o manual/QEMU
`target/arm/ptw.c` [função `get_phys_addr_lpae`] antes de implementar; nada
abaixo foi verificado contra código nesta rodada de spec)

1. **Descritor de 64 bits, 4 níveis (L0-L3) para granule 4KiB/VA 48 bits**:
   cada nível indexa 9 bits do VA (`VA[47:39]`=L0, `VA[38:30]`=L1,
   `VA[29:21]`=L2, `VA[20:12]`=L3, `VA[11:0]`=offset dentro da página de
   4KiB) — 512 entradas por tabela (`512×8B=4KiB`, cada tabela cabe numa
   página). Cada nível pode ser: inválido (bit0=0), tabela (aponta para o
   próximo nível, bits[1:0]=`11`), OU bloco (L1/L2 só — mapeia 1GiB/2MiB
   diretamente, bits[1:0]=`01`), OU página (L3 apenas, bits[1:0]=`11` mas
   terminal). **CONFERIR os bits exatos de cada tipo de descritor contra
   `ARM DDI 0487 D8.3` antes de implementar — a distinção tabela-vs-bloco-vs-
   página por nível é a parte mais fácil de errar deste encoding.**
2. **Atributos relevantes por página**: `AP[2:1]` (permissão, 2 bits — mesmo
   conceito do `AP` ARMv6, mas layout diferente), `AttrIndx[2:0]` (índice em
   `MAIR_EL1`, 3 bits — memória normal vs device, cache attrs), `NS`
   (segurança, fora de escopo — sem TrustZone), `PXN`/`UXN` (execute-never
   privilegiado/não-privilegiado — sem equivalente direto no ARMv6 32-bit,
   IMPORTANTE para W^X real de kernel; **decisão de escopo mínimo abaixo,
   D2**).
3. **Sem domínios** (o conceito `DACR`/domain do ARMv6 NÃO existe em VMSA64
   — permissão é só `AP`+`PXN`/`UXN`, mais simples nesse aspecto que o
   precedente 32-bit).
4. **TLB**: mesma ideia de micro-TLB direto-mapeada do precedente
   (`TranslatingAddressSpace`, B4.1.1, 2×256 entradas I/D) — reaproveitar a
   ESTRUTURA (não o código: chave de VA de 64 bits, não 32).

## Decisões de desenho FECHADAS nesta rodada

### D1 — `TranslatingAddressSpace64 implements AddressSpace64`, sibling do
precedente 32-bit

Mesmo padrão "sibling, não generalização" de sempre (RFC-IR-64BIT.md §3.1,
citado em toda sub-task A64 anterior) — `memory/mmu/
TranslatingAddressSpace64.java` novo, estruturalmente paralelo a
`TranslatingAddressSpace` (32-bit) mas sobre `AddressSpace64`/`long`. API
espelhando por NOME (facilita auditoria cruzada, mesmo motivo que
`Aarch64ExclusiveMonitor` deu em B6.3.4 D1): `setTtbr0(long)`, `setTcr(long)`
(A64 tem só um registro `TCR_EL1` controlando VA size/granule, mais simples
que `TTBCR`+implícito N=0 do precedente), `setMair(long)` (novo — não existe
`MAIR` no ARMv6 short-descriptor, é exclusivo do long-descriptor/LPAE-style;
sem ele os `AttrIndx` não resolvem para nada, mas como esta task não modela
cache behavior de verdade — mesma decisão do precedente 32-bit, sem TEX/C/B
—, `MAIR` pode ficar como armazenamento simples sem efeito observável além de
alimentar `AttrIndx`, CONFERIR se algum teste realmente precisa disso ou se
pode ficar RAZ/WI como `c7` do precedente), `invalidateTlbAll()`,
`invalidateTlbByMva(long mva)`, `pageWalkCount()`, `translationGeneration()`
(`@Override` de `AddressSpace64` — precisa do default lá primeiro, ver D4),
`setMmuEnabled(boolean)`/`mmuEnabled()`, `fetch32(long)` (A64 sempre busca
instruções de 4 bytes — não há `fetch16` equivalente a Thumb, simplificação
real em relação ao precedente).

### D2 — Escopo mínimo de atributos: `AP`+`PXN`/`UXN`, sem `MAIR`/cache
attrs reais

Espelhando a decisão do precedente 32-bit ("sem subpages, sem XN/APX/TEX/
cache attrs — fora do pedido da B4.1.1"), esta task modela só o necessário
para permissão de acesso funcionar (`AP[2:1]` User/Priv + R/W, `PXN`/`UXN`
para não-execução) — `AttrIndx`/`MAIR`/cacheability real ficam como
armazenamento sem efeito observável (mesmo tratamento RAZ/WI-like que `c7`
recebeu no precedente). **Diferença real de risco em relação ao 32-bit**:
sem `UXN` funcionando de verdade, um kernel real com W^X ativo pode se
comportar de forma sutilmente diferente do hardware real — registrar como
limitação conhecida, não bloqueio (o precedente 32-bit rodou um kernel real
sem esses bits também, então não é necessariamente fatal para o aceite).

### D3 — TLB: mesma estrutura, chave de 64 bits

`MicroTlb64` (nome a decidir), mesmo tamanho (2×256, `pageWalkCount()` para
provar hit sem walk novo — mesmo teste-guarda do precedente).

### D4 — `AddressSpace64.translationGeneration()` ganha default, mesmo
padrão de `AddressSpace` (32-bit)

`memory/AddressSpace64.java` (hoje sem NENHUM hook de tradução, confirmado
nesta rodada de pesquisa) ganha `default int translationGeneration() { return
0; }` — aditivo, G3, mesmo precedente EXATO de `AddressSpace.translationGeneration()`
(B4.1.4, 32-bit) e de `fetch16`/`fetch32` (B4.1.3, 32-bit) — zero mudança de
comportamento para todo consumidor A64 existente (armbox `Aarch64LinuxMachine`,
B6.2). `TranslatingAddressSpace64` implementa de verdade (contador próprio,
D5 abaixo — mas o CAMPO nasce aqui, o consumo real em `BlockKey64`/
`JitRuntime64` é B6.6.5, não esta task; **nascer com o campo pronto desde já
custa zero e evita retrofit depois — mesmo raciocínio que RFC-SOFTMMU.md §5
já usou para o precedente 32-bit**).

### D5 — Geração incrementa em `setTtbr0`/`invalidateTlbAll` (não em
`setTcr`/`setMair`)

Mesma lógica exata do precedente 32-bit (`translationGeneration` incrementa
só em operações que mudam "qual mapeamento um VA já resolvido passa a
produzir" — `setTtbr0`/`invalidateTlbAll`; NÃO em `setTcr`/`setMair`, que só
mudam política/atributos, não a IDENTIDADE do mapeamento). **`ASID`**: A64
tem um conceito de ASID via `TTBR0_EL1[63:48]` (campo embutido no próprio
TTBR, diferente do `CONTEXTIDR` separado do ARMv6) — CONFERIR contra o manual
antes de implementar se este projeto deve tratar o campo ASID do TTBR como
parte do valor opaco de `setTtbr0` (mudança de ASID dentro do mesmo TTBR
já dispara geração nova, de graça, por já estar dentro do valor que
`setTtbr0` recebe) ou se precisa de um `setAsid` separado (mais provável que
NÃO precise — o ASID de A64 é parte do MESMO registrador que o TTBR, ao
contrário do `CONTEXTIDR` separado do ARMv6 — mas confirmar).

## Objetivo

- `memory/mmu/TranslatingAddressSpace64.java` (D1): page-walk VMSA64 (4KiB
  granule, VA 48 bits, 4 níveis L0-L3), TLB 2×256 (D3), `translationGeneration`
  (D4/D5).
- `AddressSpace64.translationGeneration()` default (D4).

## Especificação

1. `AddressSpace64.java`: `default int translationGeneration() { return 0;
   }` (aditivo).
2. `memory/mmu/TranslatingAddressSpace64.java`: API completa (D1), page-walk
   L0→L1→L2→L3 (bloco em L1/L2, página em L3 — Fatos de referência #1),
   permissão `AP`+`PXN`/`UXN` (D2), TLB (D3), geração (D4/D5).
3. `MemoryTranslationException64`/`FaultStatus64` — sibling dos tipos
   32-bit (`MemoryTranslationException`/`FaultStatus`), com os códigos de
   falha reais de VMSA64 (`ESR_EL1.EC`/`ISS` — CONFERIR a codificação exata
   contra `ARM DDI 0487 D17.2` antes de implementar; provavelmente
   DIFERENTE dos 6 códigos `FS[3:0]` do ARMv6, já que ESR_EL1 usa um
   formato de "exception class" mais rico).

## Não inclui

- Bridge com `MRS`/`MSR` guest (B6.6.3).
- Aborts precisos/captura nos motores (B6.6.4).
- `translationGeneration` consumido por `BlockKey64`/`JitRuntime64` (B6.6.5
  — o campo NASCE aqui, D4, mas não é lido em lugar nenhum ainda).
- Granules de 16KiB/64KiB, VA de 39/42/52 bits, mais de 4 níveis, TrustZone
  (`NS`), tabelas EL2/EL3 — fora do escopo mínimo (D... mesma disciplina de
  "config mínima real" citada no Contexto).
- Cacheability/`MAIR` com efeito observável real (D2).

## Testes mínimos (`TranslatingAddressSpace64Test`, mesmo espírito de
`TranslatingAddressSpaceTest` do precedente 32-bit)

1. Identidade (VA=PA para uma tabela trivial).
2. Remapeamento (VA diferente de PA).
3. Permissão: User não-privilegiado bloqueado por `AP` restrito a
   privilegiado (mesmo teste do precedente, adaptado ao layout `AP` A64).
4. Bloco L1 (1GiB) e bloco L2 (2MiB) resolvendo sem descer ao próximo nível.
5. Página L3 (4KiB) — caminho completo pelos 4 níveis.
6. `PXN`/`UXN` bloqueando fetch de instrução na página marcada
   não-executável (mesmo que `fetch32` já implemente a checagem — teste
   próprio, já que é um conceito NOVO em relação ao precedente 32-bit).
7. TLB hit não refaz walk (`pageWalkCount()` — mesmo teste-guarda do
   precedente).
8. `invalidateTlbAll`/`invalidateTlbByMva` forçando walk novo seletivamente.
9. Translation fault em L0/L1/L2/L3 vazio (4 variantes, um teste por nível —
   VMSA64 pode falhar em qualquer um dos 4 níveis, diferente do precedente
   32-bit que só tinha 2).
10. `translationGeneration()` incrementa em `setTtbr0`/`invalidateTlbAll`,
    NÃO em `setTcr`/`setMair` (D5).

## Aceite

## Armadilhas

- **A distinção tabela-vs-bloco-vs-página por nível é o encoding mais fácil
  de errar** desta task (mesma categoria de risco que `DecodeBitMasks` foi
  para B6.3.1) — não implementar sem conferir bit a bit contra
  `ARM DDI 0487 D8.3`/QEMU `ptw.c` (`get_phys_addr_lpae`).
- **`ESR_EL1` NÃO é `FSR` do ARMv6** — formato de "exception class" mais
  rico, não uma simples enumeração de 4 bits; não copiar `FaultStatus`
  (32-bit) 1:1, verificar a codificação real antes de definir
  `FaultStatus64`.
- **ASID pode estar embutido no `TTBR0_EL1`, não separado** (D5) — não
  assumir um `setAsid` próprio sem confirmar contra o manual.
- **Sem `MAIR`/cache attrs reais** (D2) — mesma limitação aceita do
  precedente 32-bit, documentar explicitamente, não fingir suporte completo.
- **Pin de versão QEMU/manual**: mesma ressalva de sempre — nada citado
  aqui foi verificado contra código nesta rodada.

## Resultado

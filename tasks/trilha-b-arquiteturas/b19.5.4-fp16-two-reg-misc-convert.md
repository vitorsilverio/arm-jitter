# B19.5.4 — `FEAT_FP16`: two-reg-misc + conversões escalares (49 linhas, slots `Rm` novos)

**Trilha:** B · **Repo:** arm-jitter (+ revalidação G5) · **Depende de:** B19.5.3
**Plano:** `b19.5-plano-fp16.md` · **Épico:** `b19-plano-a64-gap-remanescente.md` · **Status:** ✅ (2026-09-06)

## Contexto

Quarto degrau da escada B19.5 e o **maior em número de linhas** (49 de 88). Diferente da B19.5.3, aqui
as linhas **não chegam ao decoder**: elas moram em slots `Rm` que nenhum `if` de
`decodeAdvancedSimdInteger` reconhece hoje. Não é relaxar uma condição — é abrir dois slots.

### A barreira, medida bit a bit

Comparando cada `_h` com a `_sd` irmã em `target/isa-decode/a64.decode`:

```
FABS_v    0.00 1110 111 11000 11111 0 .....  @qrr_h    (:1879)
FABS_v    0.00 1110 1.1 00000 11111 0 .....  @qrr_sd   (:1880)   ← já ✅
FSQRT_v   0.10 1110 111 11001 11111 0 .....  @qrr_h    (:1885)
FSQRT_v   0.10 1110 1.1 00001 11111 0 .....  @qrr_sd   (:1886)   ← já ✅
SCVTF_f   0101 1110 011 11001 11011 0 .....  @icvt_h   (:1784)
SCVTF_f   0101 1110 0.1 00001 11011 0 .....  @icvt_sd  (:1785)   ← já ✅
```

Duas diferenças, e só duas:

| | `_sd` | `_h` |
|---|---|---|
| bits[23:22] | `a`:`sz` (bit22 = tamanho) | `a`:**`1`** (bit22 fixo em 1) |
| `Rm` (bits[20:16]) | `0b0_0000` ou `0b0_0001` | **`0b1_1000`** ou **`0b1_1001`** |

⇒ **`Rm_h = Rm_sd | 0b1_1000`**, e o grupo de meia precisão é identificado por
**`bit22 == 1` e `Rm[4:3] == 0b11`**, com `Rm[2:0]` reproduzindo o slot original (`000` = two-reg-misc,
`001` = o slot que a B19.4 chama de "narrow unary"). O decoder de hoje despacha por igualdade exata:

```java
private static final int ADVSIMD_INT_RM_TWO_REG_MISC  = 0b0_0000;   // :1010
private static final int ADVSIMD_INT_RM_NARROW_UNARY  = 0b0_0001;   // :1015
...
if (rm == ADVSIMD_INT_RM_TWO_REG_MISC) { ... }    // :2925
if (rm == ADVSIMD_INT_RM_NARROW_UNARY) { ... }    // :2963
```

`0b1_1000`/`0b1_1001` não casam com nenhum dos dois, nem com o slot across-lanes
(`0b1_1110`/`0b1_0000`), nem com o de AES (`0b0_1000`) — caem no `throw unsupported` final. Por isso a
B19.5.4 é "média": o caminho existe e é o mesmo, só falta a porta.

**Leitura obrigatória**: a **B19.5.3** (`## Resultado` — o gate de `FP16` que esta task reusa), a
**B8.9** (`## Resultado` — quem implementou as `_sd` de two-reg-misc FP, e o achado de que
`bits[23:22]` NÃO é tamanho puro), a **B19.3** (as conversões escalares `@icvt_sd`) e a **B19.4** (o
slot `narrow unary` e o `FCVTL`/`FCVTN`). No código: `decoder64/Aarch64Decoder#decodeAdvancedSimdInteger`
(os dois `if` acima e tudo dentro deles), `#decodeVectorFpUnaryRmZeroOpcode`/
`#decodeVectorFpUnaryRmOneOpcode` (ou os nomes reais das tabelas de opcode desses slots),
`#decodeVectorNarrowUnaryOpcode`, `ADVSIMD_INT_RM_*`; `executor64/Ir64VectorFpArithmeticExecutor`
(`executeUnary`, `executeConvertFixedPoint`), `advsimd/AdvSimdLanes`.

## Inclui

1. **Abrir os dois slots** em `decodeAdvancedSimdInteger`, com constantes nomeadas (G6) — sugestão:
   `ADVSIMD_INT_RM_FP16_TWO_REG_MISC = 0b1_1000` e `ADVSIMD_INT_RM_FP16_NARROW_UNARY = 0b1_1001`, com
   Javadoc `///` PT explicando a relação `| 0b1_1000` com os slots `_sd` e citando a B8.9.
2. **Gate `Aarch64Feature.FP16`**: sem a feature, os dois slots continuam caindo no
   `throw unsupported` de hoje (zero-diff em v8.0/v8.1).
3. **Reuso das tabelas de opcode existentes**: o `opcode` (bits[15:11]) dos `_h` é **o mesmo** dos
   `_sd` — `FABS_v` é `11111` nos dois, `SCVTF_f` é `11011` nos dois. Portanto **chamar as mesmas
   tabelas** que os slots `_sd` usam, e montar o record com `esz = ADVSIMD_ESZ_HALFWORD`. **Não
   duplicar tabela** (é o que torna esta task 49 linhas de cobertura com pouquíssimo código).
4. **`bit23` continua sendo `a`**, e `bit22` **não** é tamanho neste grupo (é fixo em 1). O `esz` do
   record vem da constante, não dos bits — ver Armadilha 2.
5. **Executor**: conferir que `executeUnary` trata `esz = 1` (a B19.5.1 fez a fundação para
   `fpThreeSame`/`fpCombinePair`; o caminho **unário** ficou explicitamente pendente e o
   `## Resultado` da B19.5.1 registra isso). **É provável que esta task tenha de estender
   `AdvSimdLanes` para o unário em meia precisão** — está no escopo, e é a única parte de semântica
   nova aqui. Se surgir necessidade de modelar `FPCR`, **PARE e pergunte**.
6. Testes (ver Aceite).

- **Indexadas `@rrx_h`/`@qrrx_h`** (8) ⇒ **B19.5.6**.

- **`FPCR.RMode`/`FZ`/exceções**, **`FPSR.QC`**, **emissão nativa** — como no resto do épico.

## Especificação

### O `esz` vem da constante, não do encoding

Nos `_sd`, `esz = 2 + bit22`. Nos `_h`, **bit22 é fixo em 1 e faz parte do discriminador do grupo** —
o tamanho é sempre meia precisão. Montar o record com `ADVSIMD_ESZ_HALFWORD` literal; derivar do
bit22 daria `esz = 3` (dupla precisão), silenciosamente errado.

### G8 dentro dos slots abertos

Depois de abrir `0b1_1000`/`0b1_1001`, tudo que cair lá e **não** for um dos 49 encodings tem que
`throw unsupported` explícito. Em particular:

- `opcode` fora das tabelas reusadas;
- as combinações `(u, a)` de BF16/FP8 no slot `0b1_1001` (`F1CVTL`/`F2CVTL`/`BF1CVTL`/`BF2CVTL`
  usam `U=1`, e `BFCVTN_v` usa `a=1`) — **conferir contra o que a B19.4 já recusa**, e recusar
  igual;
- `Rm` = `0b1_1010`…`0b1_1111`, que não são slot nenhum.

### Conversões `@icvt_h`: o `sf` é 0

`@icvt_h` fixa `sf=0` (o template diz `&fcvt sf=0 esz=1 shift=0`). Ao reusar o caminho de `@icvt_sd`,
conferir que o `sf` usado é o do template e não o bit31 cru — as conversões escalares `V`↔`V` desta
classe não têm forma de 64 bits de registrador geral (essa é a classe `FMOV_*`/`SCVTF` de GPR, outro
espaço).

## Armadilhas

1. **`Rm_h = Rm_sd | 0b1_1000` não é "um bit a mais no tamanho".** É um slot de encoding próprio. Um
   `if` do tipo `(rm & 0b0_0111) == 0` para "unificar" os quatro slots engoliria `0b0_1000` (AES) e
   `0b1_0000` (across-lanes) — os dois já implementados. **Casar por igualdade exata**, como o
   decoder faz hoje.
2. **`bit22` NÃO é tamanho aqui.** Nos `_sd` é; nos `_h` é parte do discriminador e vale sempre 1.
   Derivar `esz` dele dá `3` (dupla precisão) e corrompe silenciosamente.
3. **`bit23` continua sendo `a`** (achado de B8.9, repetido em B19.2/B19.3/B19.4) — e é ele que
   separa metade dos opcodes deste slot. Não tratá-lo como o bit alto do tamanho.
4. **BF16/FP8 moram no slot `0b0_0001` (não no `0b1_1001`)** e já são recusadas pela B19.4. Ao abrir
   `0b1_1001`, conferir que nenhuma dessas passa a casar por engano — e testar (G8).
5. **O caminho unário do núcleo pode não ter `esz=1`.** A B19.5.1 fez `fpThreeSame`/`fpCombinePair` e
   registrou o unário como pendente. Se `executeUnary` cair num `default -> throw` para `esz=1`, é
   trabalho DESTA task, não um bug a reportar.
6. **`FRECPX` é reflexão de expoente, não `1/x`** (B19.3). Em `binary16` o expoente tem 5 bits e o
   viés é 15 — reusar o helper da B19.3 parametrizado, não recalcular à mão.
7. **Gate ausente** ⇒ `ARMV8_0_A` decodificando meia precisão (o erro oposto, igualmente grave).

## Resultado (2026-09-06)

As 49 linhas decodificam e executam sob `Aarch64Feature.FP16` (`ARMV8_2_A`+), continuam
`unsupported` sob `ARMV8_0_A`/`ARMV8_1_A`, exatamente como especificado.

**Decoder** (`Aarch64Decoder`): dois novos slots `ADVSIMD_INT_RM_FP16_TWO_REG_MISC` (`0b1_1000`) e
`ADVSIMD_INT_RM_FP16_NARROW_UNARY` (`0b1_1001`) dentro de `decodeAdvancedSimdInteger`, cada um
reaproveitando literalmente a MESMA tabela de opcode do slot `_sd` irmão
(`decodeVectorFpUnaryRmZeroOpcode`/`decodeVectorFpUnaryRmOneOpcode`) — zero tabela nova, como
previsto no item 3 de "Inclui". `FRECPX_s` manteve o `if` explícito antes da tabela (mesma colisão
de opcode com `SQRT` que a B19.3 documentou). `esz` do record é sempre a constante
`ADVSIMD_ESZ_HALFWORD`, nunca derivado de `bit22` (Armadilha 2) — `bit23` (`a`) continua sendo o
único bit real usado para escolher a linha da tabela. Confirmado bit a bit contra
`aarch64-linux-gnu-as -march=armv8.2-a+fp16+bf16` (WSL Ubuntu) que `BFCVTN_v`/`F1CVTL`/`F2CVTL`/
`BF1CVTL`/`BF2CVTL` (B19.7) vivem no slot `0b0_0001` DE VERDADE (`Rm` inteiro diferente de
`0b1_1001`), então são estruturalmente inalcançáveis pelos blocos novos — não precisou de guarda
extra (Armadilha 4).

**Achado real que a spec previu como "provável"**: o caminho unário do núcleo
(`AdvSimdLanes.fpUnary`) realmente não tinha `esz=1` — o antigo `if (esz == 2) {...} <double>`
tratava meia precisão SILENCIOSAMENTE como binary64 (mesmo bug de padrão que a B19.5.1 já tinha
corrigido em `fpThreeSame`/`fpCombinePair`). Virou `switch (esz) { case 1 -> ...; case 2 -> ...;
case 3 -> ...; default -> throw }`, com o ramo `esz==1` computado em `float` via
`halfToFloat`/`halfBits` (mesma disciplina de `halfThreeSame`).

**`FRECPX_h`** precisou de helper PRÓPRIO (`frecpxHalf`, em `Ir64VectorFpArithmeticExecutor`) em vez
de reusar `halfToFloat`/`halfBits` ao redor de `frecpx(float)`: o algoritmo de reflexão de expoente
depende da LARGURA do campo de expoente (5 bits/viés 15 em `binary16`, contra 8 bits/viés 127 em
`float`) — passar por `float` mudaria o campo refletido (Armadilha 6, confirmada na prática).
`frecpxHalf` opera direto nos 16 bits crus com as mesmas 3 regras de `frecpx`: NaN → NaN default
(`0x7E00`), ±0 → ±Infinito, ±Infinito → ±0, caso geral → reflexão do expoente enviesado.

**Conversões `FCVTx{S,U}` de meia precisão**: reusam o padrão já criado pela B19.5.3 para
`convertFixedPoint` — sign-extensão via `(short) inputBits` (não `(int) inputBits`, que não
sign-estende 16 bits mascarados) e saturação de 16 bits via `AdvSimdLanes.saturateToHalfwordInteger`
(virou `public`, com um wrapper `package-private` novo em `Ir64FpExecutor` para a chamada entre
pacotes, mesma disciplina de `saturateToInteger`).

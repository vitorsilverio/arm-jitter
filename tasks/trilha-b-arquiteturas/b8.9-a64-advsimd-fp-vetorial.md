## Achado estrutural: `esz` bits[23:22] não é tamanho puro nas formas FP — um dos dois bits é `a`

Diferente de todo o resto da escada AdvSIMD (B8.7/B8.8), onde `bits[23:22]` sempre foram o campo
`size`/`esz` (2 bits livres, tamanho do elemento), nas formas FP do MESMO grupo "three same"/
"two-register misc" só o bit BAIXO (`bit22`, "sz" no manual real) é tamanho (`0`=simples,
`1`=dupla); o bit ALTO (`bit23`, "a") é mais um bit de DISCRIMINAÇÃO DE OPCODE, nunca tamanho —
confirmado linha a linha contra o `a64.decode` real (ex.: `FADD_v` e `FSUB_v` compartilham o MESMO
`opcode` de 5 bits, `0b11010`; só `bit23` os distingue). O decoder desta task lê o `esz` cru (igual
ao resto do dispatch) e o desmonta em `a = (esz>>1)&1` / `floatEsz = 2 + (esz&1)` antes de montar
a tabela de opcode — ver `ADVSIMD_FP_A_BIT_SHIFT` em `Aarch64Decoder`.

## Achado estrutural: "two-register misc (FP)" vive em DOIS slots diferentes do MESMO grupo

`FABS_v`/`FNEG_v`/as 5 comparações-contra-zero vivem no slot `Rm=00000` — o MESMO slot que o
inteiro usa para "two-register miscellaneous" (`ABS`/`NEG`/`CM**0`/`SADDLP`/...). Já `FSQRT_v`/os
7 `FRINTx_v`/`FRECPE_v`/`FRSQRTE_v`/os 12 `SCVTF_vi`/`UCVTF_vi`/`FCVTxS_vi`/`FCVTxU_vi` vivem no
slot `Rm=00001` — o MESMO slot que B8.8 usa para `SQXTN`/`SQXTUN`/`UQXTN` ("narrow unário"). Os
dois slots já tinham comentário deixado por B8.8 apontando exatamente isso ("o resto do slot
(`FCVTXN`/conversões FP) continua fora de escopo — B8.9"). Conferido exaustivamente que nenhum
opcode FP colide com os opcodes inteiros já ocupando esses slots (os opcodes FP começam sempre em
`0b10001`/`0b11000`+, acima do maior opcode inteiro usado nesses dois slots).

## Achado estrutural: "three same pairwise (FP)" vive no MESMO espaço de opcode que "three same"

Igual ao inteiro (B8.7), a forma pareada (`FADDP_v`/etc.) reaproveita o MESMO prefixo/bit10 e o
MESMO espaço `(u,a,opcode)` da forma não-pareada — sem colisão (`FADDP_v` usa `(u=1,a=0,op=26)`,
distinto de `FADD_v (0,0,26)`/`FSUB_v (0,1,26)`/`FABD_v (1,1,26)`, conferido para as 5 pareadas).

  não batem) + `decodeVectorFpThreeSameOpcode`/`decodeVectorFpPairwiseOpcode` novos; extensão dos
  2 branches `Rm=00000`/`Rm=00001` de `decodeAdvancedSimdInteger` (fallback FP quando as tabelas

  Todos os 4 fallbacks só disparam quando `!scalar` (G8: a forma AdvSIMD-escalar desta família,

  `Ir64VectorArithmeticExecutor`/`Ir64FpExecutor`) — 3 métodos, um por `Kind`, oráculo interpretado

## Armadilhas (para quem pegar B8.10+ depois)

- `bits[23:22]` do encoding "three same"/"two-register misc" **NÃO é um tamanho de elemento puro
  nas formas FP** — só `bit22` (baixo) é tamanho; `bit23` (alto) é um bit de opcode. Confundir os
  dois (tratar como `esz` genérico igual ao inteiro) produz uma tabela de decode com metade das
  operações colididas (`FADD`/`FSUB` teriam o mesmo `esz` aparente e ficariam indistinguíveis).
- "Two-register misc (FP)" está PARTIDO entre os dois slots `Rm=00000`/`Rm=00001` do MESMO grupo
  que o inteiro usa — não assuma que todo "two-register misc FP" cai num slot só; conferir caso a
  caso contra o `a64.decode` real (a divisão não segue um padrão óbvio: `FABS`/`FNEG`/comparação-
  contra-zero num slot, `FSQRT`/arredondamento/conversão/recíproco no outro).
- `RECPE`/`RSQRTE` neste emulador calculam o recíproco/raiz-recíproca EXATOS, não a tabela de
  estimativa de 8 bits do hardware real (`FPRecipEstimate`/`FPRSqrtEstimate`, `ARM DDI 0487`).
  Software guest que faz refinamento Newton-Raphson (`FRECPE`+`FRECPS`+`FMUL`, padrão comum em
  bibliotecas matemáticas) ainda converge para o valor correto (a estimativa exata já É o ponto
  fixo do refinamento), mas se algum teste algum dia depender do NÚMERO EXATO de passos de
  refinamento ou de bits residuais de uma estimativa de baixa precisão, este atalho vai divergir —
  documentado, não escondido.
- As formas escalares desta família (`FMULX_s`/`FADDP_s`/etc.) usam o MESMO triplo `(u,a,opcode)`
  que a vetorial — se uma task futura for implementá-las, o decoder pode reaproveitar
  `decodeVectorFpThreeSameOpcode`/`decodeVectorFpPairwiseOpcode`/`decodeVectorFpUnaryRm*Opcode`
  quase inteiros, só adicionando um parâmetro/campo `scalar` explícito (mesmo padrão de
  `boolean scalar` introduzido por B8.8 para o inteiro) — NÃO precisa duplicar a tabela de opcode.

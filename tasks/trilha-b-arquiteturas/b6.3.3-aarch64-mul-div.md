# B6.3.3 — AArch64: `MUL`/`MADD`/`MSUB`/`SDIV`/`UDIV`

**Trilha:** B · **Depende de:** B6.3.1 (reaproveita `decodeDataProcessingRegister`/
`isDataProcessingRegisterClass`) · **Repo:** arm-jitter

## Contexto

Terceira sub-task da decomposição de B6.3 (ver `b6-aarch64.md` e o registro
de decomposição em B6.3.1). Agrupamento: multiplicação com acumulador de 3
operandos (`MADD`/`MSUB`, com `MUL`/`MNEG` como aliases de `Ra=XZR`) e
divisão inteira (`SDIV`/`UDIV`) — as duas famílias mais simples e
mecânicas do escopo fechado de B6.3 (sem estado de monitor como B6.3.4, sem
o encoding traiçoeiro de B6.3.1, sem a superfície grande de B6.3.2),
agrupadas juntas por serem pequenas e do mesmo subgrupo de encoding
("Data Processing — Register", subgrupos "3-source" e "2-source").

## Fatos de referência (fontes: `ARM DDI 0487` C6.2 + QEMU
`target/arm/tcg/a64.decode`/`translate-a64.c`, HEAD do master 2026-07-24)

1. **`Data-processing (3 source)`** (`a64.decode`) — cobre `MADD`/`MSUB`:
   ```
   &rrrr    rd rn rm ra
   @rrrr    . .. ........ rm:5 . ra:5 rn:5 rd:5     &rrrr

   MADD_w   0 00 11011000 ..... 0 ..... ..... ..... @rrrr
   MSUB_w   0 00 11011000 ..... 1 ..... ..... ..... @rrrr
   MADD_x   1 00 11011000 ..... 0 ..... ..... ..... @rrrr
   MSUB_x   1 00 11011000 ..... 1 ..... ..... ..... @rrrr
   ```
   Layout: `sf`(31), fixo `00`(30:29), fixo `11011000`(28:21 — identifica o
   subgrupo "3-source" com `op31`/`op0`=0, isto é, a família `MADD`/`MSUB`
   de 32/64 bits puro, **não** `SMADDL`/`SMSUBL`/`UMADDL`/`UMSUBL`, que têm
   `op0` diferente — ver Armadilhas sobre essas 4 ficarem fora de escopo),
   `Rm`(20:16), `o0`(15, seletor `MADD`=0/`MSUB`=1), `Ra`(14:10), `Rn`(9:5),
   `Rd`(4:0). Confirma-se que `MADD_w`/`MADD_x` diferem só pelo bit `sf` —
   um único `case` de decode, campo `sf` vira `wide`.
   **Semântica, transcrita de `translate-a64.c:9265-9299`, função
   `do_muladd`** (chamada por `TRANS(MADD_w/MSUB_w/MADD_x/MSUB_x,
   do_muladd, a, sf, is_sub, MO_64)`):
   ```c
   op1 = Rn (na largura sf, já zero-estendida se W — ver Armadilha do épico);
   op2 = Rm (idem);
   if (Ra == 31 && !is_sub) {
       Rd = op1 * op2;                       // atalho: é o alias MUL
   } else {
       tmp = op1 * op2;
       Rd = is_sub ? (Ra - tmp) : (Ra + tmp);
   }
   if (!sf) { Rd = zero_extend32(Rd); }
   ```
   **O atalho `Ra==31 && !is_sub` no QEMU é só otimização de codegen** — não
   é preciso reproduzi-lo no interpretador: como `Ra=31` já lê `0` via
   `Aarch64Core.x(31)` (convenção `XZR` já implementada desde B6.1), o
   caminho geral (`Rd = Ra + op1*op2`) já dá o resultado certo quando
   `Ra=XZR` sem nenhum `if` especial (`0 + produto = produto`). **Decisão:
   NÃO reproduzir o atalho** — um único caminho de execução para
   `MADD`/`MSUB`, mais simples de auditar e sem duplicação de lógica (mesmo
   raciocínio já registrado para `CSET`/`CSETM` em B6.3.2).
   **`MUL Rd,Rn,Rm`** = `MADD Rd,Rn,Rm,XZR` (`Ra=31`) e **`MNEG Rd,Rn,Rm`**
   = `MSUB Rd,Rn,Rm,XZR` (`ARM DDI 0487 C6.2`, tabela de aliases) — de
   novo, nenhum decode extra: o encoding é idêntico a `MADD`/`MSUB` com
   `Ra=31`, resolvido pelo caminho geral.

2. **`Data-processing (2 source)`** (`a64.decode`) — cobre `SDIV`/`UDIV`:
   ```
   @rrr_sf   sf:1 .......... rm:5 ...... rn:5 rd:5   &rrr_sf

   UDIV      . 00 11010110 ..... 00001 0 ..... ..... @rrr_sf
   SDIV      . 00 11010110 ..... 00001 1 ..... ..... @rrr_sf
   ```
   Layout: `sf`(31), fixo `00`(30:29), fixo `11010110`(28:21 — subgrupo
   "2-source"), `Rm`(20:16), fixo `00001`(15:11 — opcode do subgrupo,
   distingue de `LSLV`/`LSRV`/`ASRV`/`RORV`/`CRC32*`, todos fora de escopo),
   bit10 seleciona `UDIV`(0)/`SDIV`(1), `Rn`(9:5), `Rd`(4:0).
   **Semântica, transcrita de `translate-a64.c:8722-8749`, função
   `do_div`**:
   ```c
   if (!sf && is_signed) {
       n = sign_extend32(Rn_low32);   // SDIV em W: sign-extend explícito
       m = sign_extend32(Rm_low32);
   } else {
       n = Rn na largura sf;           // UDIV em W usa zero-extend "de graça"
       m = Rm na largura sf;           // (W já vem zero-estendido — invariante do core)
   }
   quotient = is_signed ? (n / m) : (n /unsigned m);   // ver divisão por zero abaixo
   if (!sf) { Rd = zero_extend32(quotient); }
   else     { Rd = quotient; }
   ```
   **Divisão por zero e overflow (`ARM DDI 0487 C6.2.375/C6.2.404`, `SDIV`/
   `UDIV`): `Rd = 0` quando o DIVISOR é `0`** (não gera exceção — diferente
   de divisão inteira em Java, que lança `ArithmeticException` — cuidado
   ao implementar, testar ANTES de chamar `/`). **`SDIV` com overflow
   (`MIN_VALUE / -1`) trunca para `MIN_VALUE`** (o resultado matemático não
   cabe no tipo, e a arquitetura define que o resultado é o valor truncado —
   mesma convenção que `Math.floorDiv`/divisão de complemento-de-dois padrão
   de Java já produz para `Long.MIN_VALUE / -1` **sem lançar exceção**
   [divisão inteira em Java só lança para divisor `0`, nunca por overflow de
   representação] — confirmar esse comportamento explicitamente com um
   teste, não assumir).

## Decisões de desenho FECHADAS nesta rodada

### D1 — Um record por família, sem tentar unificar com `Alu64`

`Ir64Op.Alu64`/`AluShiftedRegister`/`AluExtendedRegister` (B6.1/B6.3.1) são
todos operações de 2 operandos-fonte. `MADD`/`MSUB` têm 3
(`Rn`,`Rm`,`Ra`) e `SDIV`/`UDIV` têm 2, mas nenhuma das duas famílias tem
`setFlags` nem noção de `SP` em qualquer operando — **dois records novos,
sem campos emprestados que não fariam sentido** (nenhum campo
`dstIsStackPointer`/`setFlags`/`condition` — nenhuma dessas instruções
afeta NZCV nem aceita `SP`, `ARM DDI 0487 C6.2` confirma para as duas
famílias):
```java
/// `MADD`/`MSUB` (`ARM DDI 0487 C6.2.197/226`). `MUL`/`MNEG` (aliases com
/// `ra==31`) não têm representação própria — o caminho geral já produz o
/// resultado certo quando `Ra` é `XZR` (ver Fatos de referência #1).
/// Nunca afeta NZCV; nenhum operando aceita `SP`.
record MultiplyAccumulate(
        boolean subtract,   // false=MADD, true=MSUB
        int dst, int src1, int src2, int accumulator,
        boolean wide) implements Ir64Op { ... }

/// `SDIV`/`UDIV` (`ARM DDI 0487 C6.2.375/404`). Divisor `0` → resultado
/// `0` (SEM exceção arquitetural — ver Fatos de referência #2). Nenhum
/// operando aceita `SP`; nunca afeta NZCV.
record Divide(
        boolean signed,    // false=UDIV, true=SDIV
        int dst, int src1, int src2,
        boolean wide) implements Ir64Op { ... }
```

### D2 — Leitura de operandos sempre via `xForWidth`, nunca o atalho do QEMU

Confirmado no item 1 dos Fatos de referência: o atalho do QEMU (usar os 64
bits crus de `Rn`/`Rm` sem mascarar quando `mop==MO_64`, contando com o
invariante "`W` sempre zera os bits altos") é válido, mas **decisão: o
executor deste projeto usa `core.xForWidth(reg, wide)` explicitamente para
CADA operando-fonte antes de multiplicar/dividir**, em vez de confiar
silenciosamente no invariante global de zero-extensão. Motivo: é o mesmo
padrão que TODOS os executores de B6.1/B6.2/B6.3.1 já seguem
(`executeAlu`, `addWithFlags` etc. sempre chamam `xForWidth` explicitamente
nunca leem `x(reg)` cru esperando que esteja certo) — manter esse padrão
uniforme é mais barato de auditar do que introduzir uma exceção "aqui não
precisa porque o invariante garante" só para copiar uma micro-otimização de
codegen que não faz diferença nenhuma no interpretador.

## Objetivo

- `MADD`/`MSUB` (com os aliases `MUL`/`MNEG` cobertos de graça, D1/D2).
- `SDIV`/`UDIV` (com a semântica de divisor-zero e overflow do item 2).

## Especificação

1. Dois novos `case`s em `decodeDataProcessingRegister` (criado por
   B6.3.1): padrão fixo `11011000` (bits28:21) → `MultiplyAccumulate`;
   padrão fixo `11010110` + opcode `00001` (bits15:11) → `Divide`.
2. Executores novos em `Ir64BlockExecutor`:
   `executeMultiplyAccumulate` (multiplicação em `long`, cuidado com
   overflow de multiplicação em Java — usar `Math.multiplyHigh`/aritmética
   de 64 bits pura, já que só o resultado TRUNCADO em 64 bits importa,
   igual à convenção nativa de overflow silencioso de `long*long` do
   próprio Java, que já é módulo `2^64`); `executeDivide` (checar divisor
   `0` ANTES de dividir, retornar `0`; deixar `Long.MIN_VALUE / -1`
   acontecer naturalmente via o operador `/` de Java, que já trunca sem
   lançar).
3. Corpus: apêndice com vetores para `MADD`/`MSUB`/`MUL`(alias)/`MNEG`(alias)
   em `W` e `X`, e `SDIV`/`UDIV` em `W` e `X`.

## Testes mínimos

- `MADD`/`MSUB`: vetor básico com os 3 operandos não-triviais; `Ra=XZR`
  (confirma `MUL`/`MNEG` sem código dedicado); `wide=false` confirmando
  zero-extensão dos 32 bits altos do resultado.
- `SDIV`/`UDIV`: divisor `0` → `dst=0`, **sem lançar exceção** (teste
  explícito, é o erro mais fácil de introduzir usando `/` de Java direto);
  `SDIV` com `Long.MIN_VALUE / -1` (wide) e `Integer.MIN_VALUE / -1`
  (!wide) → resultado truncado (`Long.MIN_VALUE`/`Integer.MIN_VALUE` de
  volta), sem exceção; `UDIV` interpretando os operandos como
  SEM-sinal (vetor com um operando que tem o bit mais alto setado —
  confirma que a divisão usa `Long.divideUnsigned`/`Integer.divideUnsigned`,
  não `/` comum, que seria errado para não-sinal).
- Regressão: suíte completa de B6.1/B6.2/B6.3.1/B6.3.2 sem mudança.

## Armadilhas

- **Divisão por zero em A64 NUNCA lança exceção arquitetural** — resultado
  é `0`, silenciosamente. Implementar isso ERRADO (deixar o `/`/`%` de Java
  lançar `ArithmeticException` sem checar antes) travaria QUALQUER
  binário real que testa por zero depois de dividir (padrão comum em
  código gerado por compilador que confia na semântica ARM64).
- **`UDIV` precisa de divisão SEM SINAL** (`Long.divideUnsigned`/
  `Integer.divideUnsigned`, ou o operando lido já como valor sem sinal
  antes do `/` — mas `long`/`int` de Java são sempre com sinal, então usar
  `/` comum daria resultado errado para operandos com o bit mais alto
  setado). Confundir isso com `SDIV` é o erro mais fácil da task.
- **`SMADDL`/`SMSUBL`/`UMADDL`/`UMSUBL` (multiplicação 32×32→64 com
  extensão de sinal/zero) NÃO estão no escopo fechado do épico** (a tabela
  de `b6-aarch64.md` só lista "MUL/MADD/SDIV/UDIV" — essas 4 variantes
  "widening" são um subgrupo de encoding vizinho, mesma classe "3-source"
  mas `op0` diferente de `11011000`). **Não implementar por conta
  própria** — registrar como pendência para spec futura.
- **Não reproduzir o atalho `Ra==31` do QEMU no executor** (D2/item 1) — é
  puramente uma otimização de codegen nativo, não uma exigência de
  corretude; o interpretador já fica correto com o caminho único.

  lidas do HEAD do master em 2026-07-24).
- **B6.2 aceite #2 (busybox aarch64) segue bloqueado no usuário** — mesma
  nota das sub-tasks anteriores, não bloqueia esta task.

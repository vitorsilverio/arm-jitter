# B4.0.4.1 — `CoprocessorBus.handles` fino por registrador (Undefined limpo para CP15 parcial)

**Trilha:** B · **Depende de:** — (bloqueia B4.0.3) · **Repos:** arm-jitter + armbox (adoção) · **Task pequena**

## Contexto (gap reportado pelo agente da B4.0.4, confirmado no fonte 2026-07-16)

`IrSystemExecutor#executeCoprocessor` (`IrSystemExecutor.java:58-81`) decide
UNDEFINED só pelo `handles(int coprocessor)` GROSSO (linha 63): se um bus atende
CP15 mas não o registrador pedido (caso real: `ArmboxCp15` da B4.0.4 só
implementa c13/TPIDRUR*), não há caminho para "este registrador → UNDEFINED de
guest" — qualquer exceção Java que o bus lance VAZA pelo executor e derruba o
host, em vez de virar a entrada de exceção Undefined que o hardware daria.

## Decisão de desenho (fechada — não reavaliar)

Contrato fino com default retrocompatível (G3), espelhando o padrão de
`claimsEncodingSpace` da B2.2.2:

```java
// CoprocessorBus.java — método novo com default
/// Se este barramento implementa ESTE registrador específico. O default delega
/// ao handles(coprocessor) grosso — implementações existentes (ndsemu Cp15) não
/// mudam de comportamento. Devolver false => o core entrega exceção Undefined,
/// como para um coprocessador ausente.
default boolean handles(int coprocessor, int opcode1, int crn, int crm, int opcode2) {
    return handles(coprocessor);
}
```

`executeCoprocessor` passa a consultar a forma FINA (com os campos do `IrOp.Coprocessor`)
no lugar da grossa — o caminho UNDEFINED existente (linhas 63-67: `setProgramCounter(sequentialPc)`
+ `requestException(UNDEFINED)`) permanece o mesmo, só o predicado muda.

## Inclui

1. Método default acima em `CoprocessorBus` (javadoc `///` em português, G7).
2. `IrSystemExecutor#executeCoprocessor` usando a forma fina.
3. **Verificar o backend ASM**: se `IrOp.Coprocessor` compila nativo, o bytecode
   precisa do MESMO predicado fino (achar onde o ASM emite/delega a op — se cair
   no fallback PER_OP, já usa o executor e nada muda; registrar qual dos dois no PR).
4. **Adoção no armbox** (commit separado, repo armbox): `ArmboxCp15` sobrepõe a
   forma fina devolvendo `true` só para c13/c0/{2,3}; remover o lançamento de
   exceção para registrador desconhecido (nunca mais é alcançado pelo caminho
   normal — se ainda houver `read`/`write` de registrador não reivindicado,
   lançar `IllegalStateException` com mensagem "bug: executor não consultou
   handles fino").

## Testes mínimos

1. arm-jitter: bus fake que reivindica CP15 mas só o registrador c13 —
   `MRC p15,0,r0,c13,c0,3` funciona; `MRC p15,0,r0,c1,c0,0` → entrada Undefined
   de guest (modo UND, vetor, LR corretos — mesmos asserts do teste de
   coprocessador ausente que já existe); NENHUMA exceção Java vaza.
2. Interpretado × ASM equivalentes no cenário 1 (harness, G1).
3. Regressão: ndsemu 175 verde (o Cp15 de lá não sobrepõe a forma fina — default
   preserva o comportamento atual byte a byte); gbaemu 216 verde (usa `none()`).
4. armbox: teste da B4.0.4 estendido — MRC de registrador CP15 não implementado
   sai como Undefined do guest (processo não morre), nos 3 backends.

## Armadilhas

- NÃO trocar o mecanismo por exceção Java tipada (ex. o bus lançar
  `UndefinedCoprocessorException` capturada pelo executor) — o predicado é mais
  barato, não cria fluxo de exceção no caminho quente e segue o precedente do
  projeto (decisão registrada acima).
- NÃO tentar sinalizar de DENTRO de `read`/`write` (injetar `ArmCore` no bus e
  chamar `requestException` lá): a B4.0.4 JÁ TESTOU isso experimentalmente e não
  funciona — a exceção é "pedida" mas as instruções seguintes do bloco já
  decodificado continuam executando com o registrador destino contaminado (ver a
  entrada da B4.0.4 no índice). O único ponto correto é o predicado antes da
  chamada, onde o check grosso já interrompe o bloco corretamente hoje.
- O par de leitura `read` devolve valor mesmo quando `handles` fino diria false
  — a ordem correta é consultar ANTES de chamar read/write, nunca "chamar e
  tratar erro".

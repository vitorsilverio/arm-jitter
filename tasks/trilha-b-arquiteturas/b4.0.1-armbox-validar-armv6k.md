# B4.0.1 — Validar ARMv6K de verdade no armbox (binário real, não só testes Java)

**Trilha:** B · **Depende de:** B4.0, B1.1-B1.6 · **Repo:** armbox (+ arm-jitter se
algum bug for revelado)

## Contexto

`armbox` (task B4.0) já roda binários Linux user-mode reais (busybox musl estático +
ELFs `.s` compilados com devkitARM) e é explicitamente descrito no seu próprio README
como "o veículo de validação das trilhas de arquitetura (ARMv6K/Thumb-2/ARMv7 serão
exercitadas aqui com binários reais de gcc)" — mas isso nunca aconteceu: `Armbox.java`
tem `ArmArchitecture.ARMV5TE` HARDCODED (4 ocorrências em `Armbox.run` — as 3 vias
do `switch` em `JitRuntimeFactory.armThumb`/`interpretedArmThumb`/
`divergenceCheckingArmThumb`, mais o `new ArmCore(...)`), e todos os binários de teste existentes (`hello.elf`,
`busybox-armv5l`) são ARMv5TE puro. B1.1-B1.6 implementaram e testaram ARMv6K
inteiramente por equivalência Java (`BlockEquivalenceHarness`/`ArmV6*Test`) — o que
prova que o interpretador e o ASM concordam entre si, mas **nunca provou que uma CPU
ARMv6K real, executando um binário ELF de verdade com essas instruções, produz o
resultado que o hardware produziria.** É a lacuna que esta task fecha.

## Objetivo

1. `armbox` ganha uma forma de selecionar a arquitetura em tempo de execução (hoje é
   fixo). Não precisa ser genérico/plugável — um enum pequeno + flag `--arch=armv5te|
   armv6k` (default `armv5te`, preserva o comportamento atual) resolve.
2. Um binário ELF real (ou um conjunto pequeno deles) que EXERCITA as instruções
   ARMv6K novas de B1.1-B1.6 roda em `armbox --arch=armv6k` e produz o resultado
   correto — nos três backends já suportados (JIT, `--interp`, `--check`).

## Não inclui

- Não mexe no arm-jitter, exceto se o binário real revelar um bug (nesse caso, o bug
  vira a prioridade — corrigir + adicionar regressão no arm-jitter, e só então voltar
  para o binário).
- Não implementa seleção de arquitetura genérica/plugável — um enum simples é
  suficiente até haver motivo para mais (YAGNI; G3-style: não redesenhar o que já
  funciona para ARMv5TE).
- Não cobre Thumb-2 (isso é B4.0.2, que depende desta task pela plumbing de seleção
  de arquitetura).

## Especificação

1. **Seleção de arquitetura:** adicionar um argumento de CLI processado antes do
   loop de flags existente (`--interp`/`--check`); passar o `ArmArchitecture`
   resultante para os TRÊS lugares hardcoded hoje (`ArmCore` + os dois
   `JitRuntimeFactory`/`JitRuntime` de JIT/interp/check — conferir o código atual
   antes de assumir os nomes exatos).
2. **Binário(s) de teste:** como não há toolchain glibc/gcc no Windows (mesma
   limitação documentada em B4.0), usar devkitARM `-nostdlib` como os `.s` existentes.
   Duas fontes de cobertura, NÃO uma só (compilador sozinho não basta — GCC/Clang
   raramente emitem SIMD paralelo, UMAAL, ou LDREX/STREX sem intrínsecos):
   - **Torture test escrito à mão** (`.s`), auto-verificável (compara resultado
     esperado inline e sai com código != 0 se algo divergir — mesmo espírito dos
     testes de equivalência Java, mas como instruções REAIS executadas pelo JIT/
     interpretador do armbox): cobrir pelo menos um representante de cada grupo de
     B1.1-B1.6 — `SXTB`/`UXTAH` com rotação, `REV`/`REV16`/`UMAAL`, `SADD16`/`UQSUB8`
     (paralela), `SEL`/`PKHBT`/`SSAT`/`USAD8`, `LDREX`/`STREX`/`CLREX` (sucesso E
     falha do monitor), `CPS`/`SETEND`/`WFI` (`WFI` precisa de uma forma de acordar —
     ver Armadilhas).
   - Se **devkitARM permitir `-march=armv6k`** para código C normal (não só o `.s`
     manual): recompilar o `hello.elf` existente com esse target, como sinal de que
     código GERADO por compilador (não só handwritten) também funciona — cobertura
     complementar, não substitui o torture test.
3. Rodar em `--arch=armv6k` nos três backends (JIT, `--interp`, `--check`) e
   comparar a saída/exit-code com o valor esperado (hardcoded no teste de
   integração do armbox, mesmo padrão de `ArmboxIntegrationTest`).

## Aceite

- `armbox --arch=armv6k testdata/armv6k-torture.elf` sai com código 0 (sucesso) nos
  três backends; forçar uma falha proposital confirma que o exit-code != 0 realmente
  detectaria uma regressão (teste do teste).
- `--arch=armv5te` (default) continua idêntico a antes — binários/testes existentes
  do armbox inalterados (regressão zero).
- `mvn test` do armbox verde; se algum bug do arm-jitter for revelado e corrigido,
  suites arm-jitter/gbaemu/ndsemu verdes também (G5).
- README do armbox atualizado com o novo flag e os binários de teste ARMv6K.

## Validação

`mvn test` no armbox (JBR 25) + execução manual dos binários reais listados acima.

## Armadilhas

- **`WFI` precisa de uma interrupção para acordar** — o armbox hoje não tem
  temporizador/dispositivo de IRQ nenhum (é user-mode puro). Ou o torture test evita
  `WFI` de verdade (só decodifica/executa como no-op observável, já que o guest
  user-mode não tem por que travar), ou esta task precisa decidir explicitamente como
  tratar isso (ex.: um "IRQ" sintético do próprio runner após N ciclos, só para o
  teste) — documentar a escolha, não deixar implícito.
- Devkit toolchains antigos às vezes não conhecem `-march=armv6k` (mapeiam para
  `armv6`/`armv6j` sem o `K`) — se o assembler recusar mnemônicos como `LDREX`,
  confirmar a versão do binutils/GCC do devkitARM instalado antes de supor que é bug
  do arm-jitter.
- Monitor de exclusividade (`LDREX`/`STREX`) em single-core/single-thread é trivial
  de "passar" mesmo com bug sutil (nunca há disputa real) — o torture test precisa
  forçar explicitamente o caminho de FALHA do monitor (ex.: `CLREX` ou um STR comum
  no meio, como já faz `ArmV6ExclusiveNativeEquivalenceTest` em Java) para valer
  alguma coisa.

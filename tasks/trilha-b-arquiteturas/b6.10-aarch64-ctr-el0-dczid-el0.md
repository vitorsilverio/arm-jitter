# B6.10 — AArch64: `CTR_EL0`/`DCZID_EL0` (registradores de identidade de cache), TERCEIRO gap achado pela F11

**Trilha:** B · **Depende de:** B6.6.7 (mecanismo de registrador intrínseco de identidade da CPU) ·
**Repo:** arm-jitter

## Contexto

Aberta pela sessão 4 da F11 (`virtual-arm-box`, 2026-08-20 — ver `tasks/FILA-EXECUCAO.md`, linha
P17f): com "Logical (shifted register)" (B6.9) disponível, o boot do `kernel8.img` real avança
bem mais longe (`0x13ba9e8`→`0x38fc4`) até bater num TERCEIRO gap de decode: `MRS X3, CTR_EL0`
(Cache Type Register), fora do subconjunto de registradores de sistema que
`Aarch64Decoder#decodeSystemRegisterId` resolve hoje (só identidade EL1 geral + timer genérico,
`CRn=14`, do grupo `op1=3`/EL0 — não o grupo de identificação EL0 `CRn=0`, que é onde `CTR_EL0`
vive). Mesma disciplina iterativa de B6.8→B6.9→esta: fechar o gap confirmado, esperar mais na
mesma classe antes de presumir boot completo.

## Fatos de referência (CONFERIDOS nesta rodada de spec contra a fonte real do QEMU — `master`,
lido via `curl` de `raw.githubusercontent.com` em 2026-08-20, `target/arm/helper.c`+`cpu64.c`,
mesma disciplina de B6.6.7/B6.9)

1. **`CTR_EL0`** (`target/arm/helper.c`, tabela `id_cp_reginfo`):
   ```c
   { .name = "CTR_EL0", .state = ARM_CP_STATE_AA64,
     .opc0 = 3, .opc1 = 3, .opc2 = 1, .crn = 0, .crm = 0,
     .access = PL0_R, .accessfn = ctr_el0_access,
     .type = ARM_CP_CONST, .resetvalue = cpu->ctr },
   ```
   `op0=3,op1=3,CRn=0,CRm=0,op2=1`. **Somente leitura** (`PL0_R`) — `ARM_CP_CONST`, sem
   `writefn`. `cpu->ctr` para o Cortex-A53 (`target/arm/cpu64.c:716`, alvo primário via a F11):
   `cpu->ctr = 0x84448004;` (comentário do próprio QEMU: `/* L1Ip = VIPT */`).
2. **`DCZID_EL0`** (`target/arm/helper.c:3513`):
   ```c
   { .name = "DCZID_EL0", .state = ARM_CP_STATE_AA64,
     .opc0 = 3, .opc1 = 3, .opc2 = 7, .crn = 0, .crm = 0,
     .access = PL0_R, .type = ARM_CP_NO_RAW,
     .readfn = aa64_dczid_read },
   ```
   `op0=3,op1=3,CRn=0,CRm=0,op2=7`. **Somente leitura** (`PL0_R`). `aa64_dczid_read`
   (`helper.c:3266`) devolve `idregs[DCZID_EL0_IDX] | dzp_bit`, onde `dzp_bit=1<<4` (`DZP`, bit 4)
   é `0` só se `DC ZVA` estiver permitido — como este emulador **não implementa `DC ZVA`**
   (fora do escopo de qualquer task já fechada; `grep` confirma nenhum `Ir64Op` para isso em
   `decoder64`/`executor64`), o valor correto a expor é `DZP=1` (bit 4 setado, `BS`(3:0)`=0`) —
   "acesso a `DC ZVA` desabilitado", que é semanticamente verdadeiro (a instrução não existe aqui)
   e evita o kernel tentar uma instrução que lançaria `UnsupportedOperationException` por falta de
   decode em vez de simplesmente não usar o caminho otimizado. **Valor: `0x10`** (só o bit `DZP`).
3. **Ambos vivem no MESMO grupo de bits `op1=3` já roteado por `decodeSystemRegisterId` para
   `decodeGenericTimerRegisterId`** (`Aarch64Decoder.java:1481-1483`, B6.6.7) — mas esse método só
   reconhece `CRn=14` (`SYSREG_CRN_TIMER`), devolvendo `null` (→ `unsupported`) para `CRn=0`. Não é
   um bug daquela task (o timer genérico é o único consumidor de `op1=3` que existia até então) —
   é exatamente o gap que esta task fecha: `op1=3` precisa decidir entre dois subgrupos por `CRn`
   (`0`=identidade de cache, `14`=timer), não presumir só um.
4. **Ambos são identidade CONSTANTE da CPU emulada** — mesmo padrão exato de `MIDR_EL1`/`MPIDR_EL1`
   /`ID_AA64*` (B6.6.7): resolvidos DIRETO pelo `Aarch64Core`
   (`handlesSystemRegisterIntrinsically`/`readIntrinsicSystemRegister`), não pelo
   `Aarch64SystemRegisterBus` do hospedeiro (ao contrário do timer, que depende do relógio real do
   host) — não há "fonte de tempo" nem nada plugável aqui, só valores fixos.

## Decisões de desenho

### D1 — `decodeSystemRegisterId`: `op1=3` vira um despacho por `CRn`, não mais um atalho direto

Hoje `op1 == SYSREG_OP1_EL0_TIMER` despacha direto para `decodeGenericTimerRegisterId` (que já
checa `CRn==14` internamente e devolve `null` caso contrário). **Decisão: manter esse método como
está** (não é a causa do gap, só cobre menos que o grupo inteiro) e adicionar, no MESMO nível do
`if (op1 == SYSREG_OP1_EL0_TIMER)`, uma checagem para `CRn==0` que resolve `CTR_EL0`/`DCZID_EL0`
por `op2` (`1`=`CTR_EL0`, `7`=`DCZID_EL0`) ANTES de delegar para o timer — evita duplicar o
padrão "despacha por CRn" dentro de `decodeGenericTimerRegisterId`, que é nomeado e documentado
especificamente para o timer.

### D2 — Sem escrita: `writeIntrinsicSystemRegister` lança para os dois, mesmo padrão já existente

`writeIntrinsicSystemRegister` (`Aarch64Core.java:354`) já lança `UnsupportedOperationException`
por padrão (`default` do método) para qualquer registrador que não seja `TPIDR_EL1` — **nenhuma
mudança necessária ali**, só adicionar os dois novos ao `switch` de leitura
(`readIntrinsicSystemRegister`) e ao `handlesSystemRegisterIntrinsically`. Nenhum consumidor real
gera `MSR` para eles (são `PL0_R` de hardware, um compilador nunca emite essa forma) — mesmo
raciocínio já registrado para `MIDR_EL1`/`ID_AA64*`.

## Objetivo

- `Aarch64SystemRegisterId.CTR_EL0`/`DCZID_EL0` novos.
- `Aarch64Decoder#decodeSystemRegisterId`: `op1=3`/`CRn=0` resolve os dois por `op2` (D1).
- `Aarch64Core#handlesSystemRegisterIntrinsically`/`readIntrinsicSystemRegister`: os dois entram
  no grupo intrínseco, valores fixos (`CTR_EL0=0x8444_8004`, `DCZID_EL0=0x10`, Fatos de
  referência #1/#2).
- `Raspi364BootTest` (virtual-arm-box) deixa de bater nesse gap especificamente — critério
  prático, não aceite formal desta task (outro repo, sessão própria).

## Não inclui

- `DC ZVA` em si (a instrução) — permanece não implementada; `DZP=1` é exatamente a forma de
  declarar isso corretamente ao guest sem implementar a instrução (Fatos de referência #2).
- Qualquer outro gap de decode que a continuação do boot da F11 revelar depois deste ponto.
- `CTR` de 32 bits (`cp15`, GBA/NDS/armbox) — fora de escopo, mundo A64 só.

## Testes mínimos

1. `MRS X3, CTR_EL0` decodifica para `SystemRegister(read=true, CTR_EL0, rt=3)`, corpus real
   (`aarch64-none-elf-as`/`objdump`) confirmando `op0=3,op1=3,CRn=0,CRm=0,op2=1`.
2. `MRS X3, DCZID_EL0` decodifica igual, corpus confirmando `op2=7` (mesmo `op0`/`op1`/`CRn`/`CRm`
   do item 1, só `op2` distingue).
3. `Aarch64Core#readIntrinsicSystemRegister(CTR_EL0) == 0x8444_8004L`;
   `readIntrinsicSystemRegister(DCZID_EL0) == 0x10L`.
4. `handlesSystemRegisterIntrinsically` devolve `true` para os dois.
5. `writeIntrinsicSystemRegister` para os dois lança `UnsupportedOperationException` (D2, mesmo
   padrão de `MIDR_EL1`).
6. Regressão: `decodeGenericTimerRegisterId`/`CNTFRQ_EL0` etc. continuam decodificando igual
   (nenhuma mudança de comportamento no grupo `CRn=14`); suíte completa B6.1-B6.9 sem mudança.

## Armadilhas

- **Não usar `decodeGenericTimerRegisterId` para os dois novos registradores** — esse método é
  nomeado/documentado especificamente para o grupo timer (`CRn=14`); resolver `CTR_EL0`/
  `DCZID_EL0` num `if` irmão, antes do despacho ao timer (D1), mantém a responsabilidade de cada
  método coerente com seu nome.
- **`DZP=1`, não `0`** — o valor ingênuo seria supor "cache limpo, tudo permitido" e devolver `0`;
  isso anunciaria `DC ZVA` como disponível para um guest que tentaria usá-lo e bateria em
  `UnsupportedOperationException` por falta de decode, um erro mais confuso que a ausência
  corretamente anunciada (Fatos de referência #2).
- **`CTR_EL0`/`DCZID_EL0` são `PL0_R`** (acessíveis de EL0, não só EL1) — mas esta task não
  modela nenhuma checagem de nível de privilégio para `MRS` (nenhuma task anterior do épico B6.6
  modela isso para nenhum registrador), então isso não muda nada na implementação — só citado
  para não confundir com os registradores `op1=0`/EL1 do resto da tabela.

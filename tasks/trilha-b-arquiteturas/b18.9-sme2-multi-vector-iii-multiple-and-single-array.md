# B18.9 — SME2 multi-vector III: multiple-and-single **array vectors** (`ADD_azz_n1`/`FDOT_n1`/`SMLALL_n1`/…) — 107 encodings

**Trilha:** B · **Repo:** arm-jitter (+ revalidação G5) · **Depende de:** B18.7
**Épico:** `b18-plano-sme.md` · **Status:** ⬜ (spec escrita 2026-09-14, ainda não executada)

## Contexto

Degrau 9 da escada B18 — **o maior bloco contíguo do inventário** (107 de 623) e a base das três
tasks seguintes (B18.10, B18.11 e B18.12 dependem dela).

A família junta as duas metades do épico: os **operandos** são registradores `Z` (grupos de 1, 2 ou
4, como na B18.7), mas o **destino é um vetor do array `ZA`**, endereçado dinamicamente por
`W8`-`W11` + offset. É o padrão `ZA[W<rv>+off] += f(Zn…, Zm)` — o laço interno de um `gemm`
escrito com SME2, sem tiles nem predicados.

**Recorte normativo** (partição da B18.1): `### SME2 Multi-vector Multiple and Single Array
Vectors`, linhas **305-462** — **107 encodings**, 44 mnemônicos.

> O épico estimava ~158; o número medido é **107**. (A tabela "O número" do épico agrupa este bloco
> com o seguinte; ver o quadro completo de achados na B18.1.)

### A estrutura, medida no arquivo real

Um único conjunto de argumentos, e formatos que diferem **só** na largura/escala do `off`:

```
&azz_n          n off rv zn zm
@azz_nx1_o3     ........ .... zm:4 ...... zn:5 .. off:3     &azz_n rv=%mova_rv

%off3_x2        0:3 !function=times_2
%off2_x2        0:2 !function=times_2
%off2_x4        0:2 !function=times_4
%off1_x4        0:1 !function=times_4

@azz_nx1_o3x2   ........ ... . zm:4 . .. ... zn:5 .. ...    &azz_n off=%off3_x2 rv=%mova_rv
@azz_nx1_o2x2   ........ ... . zm:4 . .. ... zn:5 ... ..    &azz_n off=%off2_x2 rv=%mova_rv
@azz_nx1_o2x4   ........ ... . zm:4 . .. ... zn:5 ... ..    &azz_n off=%off2_x4 rv=%mova_rv
@azz_nx1_o1x4   ........ ... . zm:4 . .. ... zn:5 .... .    &azz_n off=%off1_x4 rv=%mova_rv
```

**Seis formatos ao todo** (`o3`, `o3x2`, `o2x2`, `o2x4`, `o1x4`, mais o `o3` sem escala), e a
escolha depende de **quantos vetores de `ZA` a instrução escreve** — que é `n` × (fator de
widening). Quanto mais vetores escritos, menos bits sobram para `off` e maior a escala.

Exemplos reais das quatro sub-famílias:

```
# 1. Aritmética simples de array vector (S e D, n=2 e n=4)
ADD_azz_n1_s    11000001 0010 .... 0 .. 110 ..... 10 ...    @azz_nx1_o3 n=2
ADD_azz_n1_d    11000001 0111 .... 0 .. 110 ..... 10 ...    @azz_nx1_o3 n=4
SUB_azz_n1_s    11000001 0010 .... 0 .. 110 ..... 11 ...    @azz_nx1_o3 n=2

# 2. Widening x2 (FP16/BF16 -> FP32): n=1, 2, 4 — note o n=1!
FMLAL_n1_sh     11000001 001 0 .... 0 .. 011 ..... 00 ...   @azz_nx1_o3x2 n=1
FMLAL_n1_sh     11000001 001 0 .... 0 .. 010 ..... 000 ..   @azz_nx1_o2x2 n=2
FMLAL_n1_sh     11000001 001 1 .... 0 .. 010 ..... 000 ..   @azz_nx1_o2x2 n=4

# 3. Dot product (4 ou 2 elementos somados por lane de destino)
FDOT_n1         11000001 001 0 .... 0 .. 100 ..... 00 ...   @azz_nx1_o3 n=2
SDOT_n1_4b      11000001 001 0 .... 0 .. 101 ..... 00 ...   @azz_nx1_o3 n=2
SDOT_n1_4h      11000001 011 0 .... 0 .. 101 ..... 00 ...   @azz_nx1_o3 n=2
SDOT_n1_2h      11000001 011 0 .... 0 .. 101 ..... 01 ...   @azz_nx1_o3 n=2

# 4. Widening x4 (8->32 ou 16->64), os "LL"
SMLALL_n1_s     11000001 001 0 .... 0 .. 001 ..... 000 ..   @azz_nx1_o2x4 n=1
SMLALL_n1_d     11000001 011 0 .... 0 .. 001 ..... 000 ..   @azz_nx1_o2x4 n=1
SMLALL_n1_s     11000001 001 1 .... 0 .. 000 ..... 0000 .   @azz_nx1_o1x4 n=4

# 5. FMA simples (h/s/d e BF16)
FMLA_n1_s       11000001 001 0 .... 0 .. 110 ..... 00 ...   @azz_nx1_o3 n=2
BFMLA_n1        11000001 011 0 .... 0 .. 111 ..... 00 ...   @azz_nx1_o3 n=2

# 6. FP8 (dependem de FPMR, B19.11a)
FMLALL_n1_b     11000001 001 1 .... 0 .. 001 ..... 000 ..   @azz_nx1_o2x4 n=1
FDOT_n1_sb      11000001 001 0 .... 0 .. 100 ..... 11 ...   @azz_nx1_o3 n=2
FMLAL_n1_hb     11000001 001 1 .... 0 .. 011 ..... 00 ...   @azz_nx1_o3x2 n=1
FDOT_n1_hb      11000001 001 0 .... 0 .. 100 ..... 01 ...   @azz_nx1_o3 n=2
```

**Os 44 mnemônicos**, agrupados:

| Sub-família | Mnemônicos |
|---|---|
| add/sub array | `ADD_azz_n1_s`, `ADD_azz_n1_d`, `SUB_azz_n1_s`, `SUB_azz_n1_d` |
| widening ×2 FP/BF | `FMLAL_n1_sh`, `FMLSL_n1_sh`, `BFMLAL_n1`, `BFMLSL_n1` |
| dot product | `FDOT_n1`, `BFDOT_n1`, `USDOT_n1`, `SUDOT_n1`, `SDOT_n1_4b`, `SDOT_n1_4h`, `SDOT_n1_2h`, `UDOT_n1_4b`, `UDOT_n1_4h`, `UDOT_n1_2h` |
| widening ×2 inteiro | `SMLAL_n1`, `SMLSL_n1`, `UMLAL_n1`, `UMLSL_n1` |
| widening ×4 inteiro (`LL`) | `SMLALL_n1_s`, `SMLALL_n1_d`, `SMLSLL_n1_s`, `SMLSLL_n1_d`, `UMLALL_n1_s`, `UMLALL_n1_d`, `UMLSLL_n1_s`, `UMLSLL_n1_d`, `USMLALL_n1_s`, `SUMLALL_n1_s` |
| FMA | `BFMLA_n1`, `FMLA_n1_h`, `FMLA_n1_s`, `FMLA_n1_d`, `BFMLS_n1`, `FMLS_n1_h`, `FMLS_n1_s`, `FMLS_n1_d` |
| FP8 | `FMLALL_n1_b`, `FDOT_n1_sb`, `FMLAL_n1_hb`, `FDOT_n1_hb` |

**Assimetrias reais, medidas** (é o achado que impede gerar esta família por loop):

- `USMLALL_n1_s` tem 3 encodings (`n=1,2,4`), mas `SUMLALL_n1_s` tem só **2** (`n=2,4`) — não
  existe a forma `n=1`.
- `SMLALL_n1_*` tem `n=1,2,4`; `SDOT_n1_*` só `n=2,4`.
- `FMLALL_n1_b` na forma `n=1` usa o prefixo `001 1` (e não `001 0` como `SMLALL_n1_s` `n=1`).
- `SDOT` existe em `_4b`/`_4h`/`_2h`, mas `FDOT` não tem sufixo de largura nenhum — são famílias
  com granularidade diferente.

## Inclui

1. **Endereçamento de "array vector"** — um utilitário, reutilizável por B18.10/B18.11/B18.12, que
   dado `rv` (`W8`-`W11`), `off` (já escalado pelo extrator correto) e `n`, devolve os `n` vetores
   consecutivos do array `ZA` que a instrução escreve, com índice
   `(W<rv> + off) MOD (SVL/8)`. **Diferente do endereçamento de slice de tile da B18.3** (não há
   `esz`, não há eixo `v`, não há tile) — resistir à tentação de reusar aquele.
2. **Decode das 107 linhas**, com os **seis** formatos `@azz_*` e os **quatro** extratores de `off`
   escalado (`%off3_x2`, `%off2_x2`, `%off2_x4`, `%off1_x4`) transcritos.
3. **Execução** das 7 sub-famílias acima, **acumulando** (`+=`) no array vector — nenhuma delas
   sobrescreve.
4. **Reuso**: `SDOT`/`UDOT`/`USDOT`/`SUDOT`, `SMLAL`/`SMLALL`, `FMLA`/`FMLS`, `BFMLAL`/`BFDOT` já
   existem no núcleo AdvSIMD/SVE (B8.x/B13.x/B17.x). Chamar, não reimplementar.
5. **Gates**: `FEAT_SME2`; as formas `_d` (widening para 64 bits) provavelmente exigem
   `FEAT_SME_I16I64`/`FEAT_SME_F64F64` e as FP8 (`_b`/`_sb`/`_hb`) exigem o gate de FP8 —
   **medir instrução a instrução contra o QEMU**, não por família.
6. Testes (ver Aceite).

## Aceite

- As **107** células saem de `❌`, e nenhuma outra muda.
- **Acumulação**: executar a mesma instrução duas vezes dobra o delta no array vector.
- **O índice é dinâmico e modular**: mudar `W8` desloca o vetor de destino; `W8` grande envolve
  por `MOD (SVL/8)`.
- **`off` escalado corretamente**: teste que distingue as 4 escalas (`x2` com `off=1` → vetor 2;
  `x4` com `off=1` → vetor 4).
- **`n` vetores escritos, e só eles**: preencher `ZA` com sentinelas, executar `n=4`, conferir que
  exatamente 4 vetores mudaram.
- **Dot product soma o número certo de produtos**: `SDOT_n1_4b` soma 4, `SDOT_n1_2h` soma 2 — o
  mesmo teste-chave da B18.5 (Armadilha 2 de lá).
- **`USDOT` ≠ `SUDOT`** (qual operando é signed) — teste com operandos que distinguem.
- **As assimetrias existem no decode**: `SUMLALL_n1_s` com `n=1` **não** decodifica (esse encoding
  não existe) e cai em `UNIMPLEMENTED`, não em outra instrução (G8).
- Testado em pelo menos dois `SVL` (256 e 512).
- Sem `FEAT_SME2`, as 107 continuam `UNIMPLEMENTED`.
- `mvn -o test` verde + G5 verde nos 5 consumidores.

## Armadilhas

1. **107 encodings, 44 mnemônicos, e a tabela NÃO é um produto cartesiano.** As assimetrias medidas
   estão listadas no Contexto (`SUMLALL_n1_s` sem `n=1`, `FMLALL_n1_b` com prefixo diferente,
   `SDOT` com sufixo de largura e `FDOT` sem). Gerar por loop produz encodings inexistentes **e**
   omite os casos reais. Mesmo achado que a B17.16 registrou para as unárias predicadas de SVE.
2. **O endereçamento é de *array vector*, não de slice de tile.** Sem `esz`, sem eixo `v`, sem
   tile: o array `ZA` é visto como `SVL/8` vetores planos de `SVL` bits. Reusar
   `get_tile_rowcol`/o utilitário da B18.3 introduz parâmetros que o encoding não tem.
3. **Quatro escalas de `off`, e a escala não é arbitrária**: ela é o número de vetores que a
   instrução escreve. Extrair `off` cru (sem multiplicar) faz duas instruções diferentes escreverem
   o mesmo vetor — corrupção silenciosa de `ZA`.
4. **`n=1` existe nesta família** (ao contrário da B18.7/B18.8, onde `n ∈ {2,4}`). O utilitário de
   grupo da B18.7 precisa aceitar `n=1`; se ele assumir `n ≥ 2`, um terço desta família quebra.
5. **`zm:4`** — o "single" continua restrito a `Z0`-`Z15`, como na B18.7.
6. **Widening ×2 vs ×4 muda o número de vetores de destino**, não só a largura do elemento: um
   `SMLALL` (×4) sobre um grupo `n=1` escreve 4 vetores de `ZA`. É por isso que ele usa
   `@azz_nx1_o2x4` e não `@azz_nx1_o3`.
7. **Orçamento.** 107 encodings em 7 sub-famílias é grande demais para uma sessão. Fatiar em
   `B18.9a` (add/sub + FMA + dot, ~50) e `B18.9b` (widening ×2/×4 + FP8, ~57) é **sequenciamento
   legítimo** — abrir a sub-task e registrar, nunca reduzir escopo (regra máxima).
8. **`SVL`, nunca `VL`.**

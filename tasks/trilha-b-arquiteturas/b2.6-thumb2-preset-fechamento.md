# B2.6 — Fechar o preset Thumb-2: BL/BLX vira decode único de 32 bits + plugar as 4 extensões

**Trilha:** B · **Depende de:** B2.1-B2.5 (✅ todas) · **Repo:** arm-jitter

> **Decisão de desenho JÁ TOMADA (2026-07-15, sessão de refinamento com modelo forte).**
> Esta task NÃO exige avaliar alternativas: implemente exatamente o que está aqui.
> A decisão D2 de B2.4 ("BL/BLX Thumb-2 reusa 100% o caminho legado prefix/suffix")
> fica **revogada quando `THUMB2` está ativo** — é ela que mantém o bug vivo.

## Contexto

O preset público `ArmArchitecture.ARMV6K_THUMB2`
(`core/src/main/java/dev/vitorsilverio/armjitter/arch/ArmArchitecture.java`, constante
`ARMV6K_THUMB2`) só pluga 2 das 4 extensões Thumb-2 (`Thumb2DataProcessingDecoder` e
`Thumb2BranchDecoder`). `Thumb2LoadStoreDecoder` (B2.3) e `Thumb2MiscDecoder` (B2.5)
existem, têm testes verdes, mas estão fora do preset por causa do bug do **"fantasma"
BL/BLX**:

- Com `THUMB2` ativo, `ThumbDecoder#decode` trata os pares `BL`/`BLX` legados como
  DUAS instruções de 16 bits (`LONG_BRANCH_PREFIX` + `LONG_BRANCH_SUFFIX`). O
  interpretador/lifter avança 2 bytes e chama `decode()` DE NOVO **no endereço do
  sufixo**.
- No endereço do sufixo, `ThumbDecoder` vê `hw1 ∈ {0xE800-0xEFFF (BLX), 0xF800-0xFFFF (BL)}`
  → `top5 ∈ {0b11101, 0b11111}` → candidato Thumb-2 de 32 bits → `tryDecodeThumb32`
  lê o **próximo** halfword e forma um `raw32` "fantasma" = `(sufixo<<16) | próximo`.
- Se alguma extensão reivindica esse `raw32`, o sufixo é engolido. Colisões concretas
  (verificadas contra as constantes do código em 2026-07-15):
  - `Thumb2LoadStoreDecoder.SINGLE_UNSIGNED_TOP8/SINGLE_SIGNED_TOP8` (`0xF8`/`0xF9`)
    colidem com sufixos `BL` `0xF800-0xF9FF`;
  - `Thumb2LoadStoreDecoder.EXTRA_TOP7` (`0b1110100` → hw1 `0xE800-0xE9FF`) colide com
    sufixos `BLX`;
  - **já hoje, latente no preset atual**: `Thumb2DataProcessingDecoder.REGISTER_FORM_PREFIX`
    (`0b1110101` → hw1 `0xEA00-0xEBFF`) colide com sufixos `BLX` de offset alto — o
    preset atual só não quebra porque nenhum teste usa um `BLX` com esses bits.
    O `claimsEncodingSpace` de B2.2.2 até TRANSFORMA esses sufixos em UNDEFINED.

**Por que não dá para consertar com mais um check de bits:** o fantasma não é
distinguível de uma instrução de 32 bits genuína olhando só os halfwords — a
informação que falta é contexto ("o halfword anterior era um prefixo?"), que o
decoder stateless não tem, por definição. Isso já está documentado no javadoc de
`ThumbDecoder#tryDecodeThumb32`.

**O fix correto (e arquiteturalmente fiel):** em ARMv6T2+ o `BL`/`BLX` imediato **é
uma instrução de 32 bits** (ARM DDI 0406C, A8.8.25: encodings T1/T2 de 4 bytes; a
execução "meio a meio" com interrupção entre os halfwords só é arquitetural até
ARMv6). Com `THUMB2` ativo, o par deve ser decodificado como **uma** instrução de 4
bytes — aí `decode()` nunca é chamado no endereço de um sufixo em código são, o
fantasma deixa de existir e as 4 extensões podem ser plugadas sem ambiguidade
nenhuma. Cair no meio de um `BL` (branch para `endereço+2`) é UNPREDICTABLE no
hardware real — vira UNDEFINED controlado aqui, o que é uma melhoria, não regressão.

## Objetivo

1. `BL`/`BLX` imediato decodifica como instrução única de 32 bits quando
   `ArmFeature.THUMB2` está ativo (sem a feature: comportamento atual byte a byte,
   G2/G3).
2. As 4 extensões (`Thumb2DataProcessingDecoder`, `Thumb2BranchDecoder`,
   `Thumb2LoadStoreDecoder`, `Thumb2MiscDecoder`) plugadas juntas em `ARMV6K_THUMB2`.
3. `armbox --arch=thumb2` revalidado com torture test estendido.

## Inclui

- Decode de 32 bits de `BL` (T1) e `BLX` imediato (T2) dentro de
  `ThumbDecoder#tryDecodeThumb32`, ANTES do dispatch às extensões.
- Atualização do preset `ARMV6K_THUMB2` (4 extensões + javadoc reescrito + nome
  atualizado para `"ARMv6K+Thumb2"`).
- Testes novos enumerados abaixo.

## Não inclui

- NENHUMA mudança de comportamento sem `THUMB2` (presets ARMV4T/ARMV5TE/ARMV6K
  intocados — o caminho prefix/suffix legado continua sendo o único deles).
- Emissão ASM nativa nova (BL/BLX de 32 bits deve reusar a IR que o par legado já
  produz — ver Especificação §2; se a IR for a mesma, o ASM já cobre).
- IT block / ITSTATE (B2.4, pronto) — não tocar.

## Especificação

### 1. Decode único de BL/BLX em `ThumbDecoder#tryDecodeThumb32`

Hoje o método faz (linha ~454): `if (top5 == 0b11110 && (lo & BRANCH_WITH_LINK_MASK)
== BRANCH_WITH_LINK_MASK) return null;` — devolve `null` para cair no caminho legado.

Trocar esse `return null` por decode direto do par como instrução única:

- **Encoding (ARM DDI 0406C A8.8.25):**
  `hw1 = 11110 S imm10`, `hw2 = 11 J1 1 J2 imm11` (BL) ou `hw2 = 11 J1 0 J2 imm11:0`
  (BLX imediato, bit 0 de hw2 deve ser 0).
  - `hw2[14] == 1` → `BL`; `hw2[14] == 0` → `BLX` imediato (gateado por
    `ArmFeature.BLX`, igual ao sufixo `0xE800` legado hoje: sem a feature →
    `DecodedInstruction.unimplemented`).
  - Offset (forma estendida, válida também para o range curto legado J1=J2=1):
    `I1 = NOT(J1 XOR S)`, `I2 = NOT(J2 XOR S)`,
    `imm32 = SignExtend(S:I1:I2:imm10:imm11:'0', 25)`.
    Para `BLX`, alinhar o alvo: `target = Align(PC,4) + imm32` (PC = address+4);
    para `BL`, `target = PC + imm32`.
  - `LR = (address + 4) | 1` (endereço da instrução seguinte, bit Thumb).
  - `BLX` troca para ARM (`target` com bit 0 = 0, alinhado a 4); `BL` continua Thumb.
- **Forma da `DecodedInstruction`:** reusar `InstructionKind` existente do branch com
  link do lado ARM se houver um com semântica "salta para imediato absoluto e grava
  LR" — verificar em `InstructionKind` o kind que o `ArmDecoder` usa para `BL` ARM e o
  que `Thumb2BranchDecoder` usa para `B.W` (T4). Se nenhum kind existente carregar
  "link + troca de conjunto", criar `InstructionKind.LONG_BRANCH_32` e liftar em
  `StandardIrBuilder` para a MESMA sequência de `IrOp` que o par
  `ThumbBlPrefix`+`ThumbBlSuffix` produz hoje (os records `IrOp.ThumbBlPrefix`/
  `IrOp.ThumbBlSuffix` em `ir/IrOp.java` — emitir os dois `IrOp`s a partir da única
  instrução de 4 bytes é aceitável e reusa executor+ASM existentes sem código novo;
  essa é a opção recomendada: **zero semântica nova, só o decode muda**).
- A instrução tem `raw` = os dois halfwords combinados (`raw < 0` garante
  `instructionWidth == 4` no lifter — mecanismo de B2.2 em
  `StandardIrBuilder`/`StandardIrBlockLifter#instructionWidth`, já pronto).
- **Ordem no método:** o check BL/BLX (`top5==0b11110 && hw2[15:14]==0b11`) roda ANTES
  de `dispatchThumb32Extensions` — `Thumb2MiscDecoder`/`Thumb2DataProcessingDecoder`
  nunca veem esse espaço (hoje já não veem: `lo[15]` check de B2.4).

### 2. Sufixo standalone morre sob THUMB2

Com o decode único, remover a delegação ao legado para candidatos `top5 == 0b11101`/
`0b11111` quando `THUMB2` ativo: `tryDecodeThumb32` passa a devolver UNDEFINED
controlado (`DecodedInstruction.unimplemented` com `raw32` atômico) para QUALQUER
candidato de 32 bits que nenhuma extensão decodifique — ou seja, a condição da linha
~462 `if (top5 == 0b11110 || anyExtensionClaims(raw32))` vira incondicional
(`return DecodedInstruction.unimplemented(...)` direto), e `anyExtensionClaims`/
`claimsEncodingSpace` deixam de ser necessários no `ThumbDecoder` (manter o método na
interface `DecoderExtension` por G3 — outros usos futuros — mas remover o uso aqui e
documentar no javadoc da interface que B2.6 o tornou obsoleto para Thumb-2).
Consequência: os checks legados `0xF800`/`0xE800`/`0xF000` de `ThumbDecoder#decode`
só são alcançáveis SEM `THUMB2` — adicionar comentário dizendo isso neles.

### 3. Preset

```java
public static final ArmArchitecture ARMV6K_THUMB2 = extending(ARMV6K, "ARMv6K+Thumb2",
        ArmFeature.THUMB2, ArmFeature.MEMORY_BARRIERS)
        .withThumb32DecoderExtensions(List.of(
                new Thumb2DataProcessingDecoder(),
                new Thumb2LoadStoreDecoder(),
                new Thumb2BranchDecoder(),
                new Thumb2MiscDecoder()));
```

- `MEMORY_BARRIERS` entra porque `Thumb2MiscDecoder` gateia `DMB`/`DSB`/`ISB` por ela
  (sem a feature elas viram UNDEFINED — no preset "fechado" devem funcionar).
- `WAIT_HINTS` já vem herdado de `ARMV6K`.
- Reescrever o javadoc inteiro da constante: o parágrafo longo sobre a colisão
  (linhas ~49-65) é substituído por: preset Thumb-2 completo do épico B2; BL/BLX é
  decodificado como instrução única de 32 bits sob `THUMB2` (B2.6); ainda NÃO é
  ARMv7-A (sem VFP/SDIV/UDIV — task B3).

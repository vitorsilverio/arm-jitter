## Contexto

Última task do épico. **É ela que faz "não se aplica a nenhum preset atual" sumir da tabela** para o
maior grupo do inventário — e, com isso, transforma **929 linhas** de trabalho invisível em

Durante todo o épico (B17.1-B17.25) a disciplina foi: implementar tudo gateado por
`Aarch64Feature.SVE`/`SVE2`, **com o grupo `sve.decode` ainda `NOT_IN_ANY_PRESET`**, para que cada
task fosse zero-diff de medição e a tabela ficasse byte a byte idêntica. Isso permitiu 22 tasks
seguidas sem risco de regressão nos 5 consumidores. **O preço é que nada disso conta na tabela** — e
é esta task que cobra o preço de volta. Mesma mecânica de **B13.22** (NEON), **B16.14** (MVE) e
**B11.5** (colunas por versão do A64).

### O que muda na medição

`IsaCoverageReport.GROUPS` tem hoje:

```java
new Group("sve.decode", "SVE/SVE2 — vetor escalável", 32, Probe.A64, false, NOT_IN_ANY_PRESET,
        "Extensão opcional do ARMv8.2+; o Cortex-A53 do Raspberry Pi 3 NÃO tem SVE."),
```

E o mecanismo de coluna por versão, que hoje **exclui explicitamente** este grupo:

```java
// B11.5: só `a64.decode` (o único grupo A64 com `applicability() != NOT_IN_ANY_PRESET`,
// ver GROUPS) ganha colunas por versão — `sve.decode`/`sme.decode` continuam "não se
// aplica a nenhum preset" (nada decodifica hoje, versionar não traria informação nova).
boolean aarch64Versioned = aarch64 && group.applicability() != NOT_IN_ANY_PRESET;
```

⚠️ **Achado desta rodada de spec**: a `Applicability` do medidor é uma interface sobre
`ArmArchitecture` (32 bits), **não** sobre `Aarch64Architecture`:

```java
@FunctionalInterface
private interface Applicability {
    boolean appliesTo(ArmArchitecture architecture);
}
```

Para grupos A64, o medidor **não usa** `applicability().appliesTo(...)` — usa
`isApplicableToAarch64Version(instruction.name(), occurrence, aarch64Architecture)` quando
`aarch64Versioned`, e `group.applicability() != NOT_IN_ANY_PRESET` (um booleano!) quando não.
Ou seja: **a mudança certa aqui não é "trocar `NOT_IN_ANY_PRESET` por uma lambda de SVE"** (o padrão
literal de B13.22/B16.14, que valem para grupos de 32 bits), e sim **ligar o versionamento A64 para
`sve.decode`** — deixando `isApplicableToAarch64Version` e a curadoria de
`AARCH64_VERSION_REQUIREMENTS` decidirem célula a célula. Ler o código antes de escolher; este é o
ponto em que uma cópia mecânica de B13.22 quebra.

### Por que não curar 929 linhas à mão

A leitura do código (`IsaCoverageReport#appendGroup`/`isApplicableToAarch64Version`) confirmou a
Armadilha 1: ligar `aarch64Versioned` para `sve.decode` é trivial. O problema real é outro — **nenhum
dos 16 presets de `AARCH64_ARCHITECTURES` declara `Aarch64Feature.SVE2`** (só `SVE`, a partir de
`ARMv9.0-A`; ver o Javadoc de `Aarch64Architecture` sobre "SVE2 não confirmada contra o manual",
decisão da própria B17.1). Isso significa que o padrão `AARCH64_VERSION_REQUIREMENTS` (mnemônico →
feature, default = "ARMv8.0 baseline, aplicável em toda coluna") **não serve**: quase toda instrução
SVE2 exige, no mínimo, `SVE` — nunca "aplicável incondicionalmente".

A alternativa óbvia — transcrever à mão, por mnemônico, qual feature cada uma das 929 linhas exige —
foi descartada por dois motivos: (1) o volume (quase 1 milhar de entradas) é exatamente o tipo de
transcrição que o `tasks/README.md` chama de "entrada factualmente errada pior que ausência"; (2) o
`Aarch64Decoder` **já tem essa informação codificada** (cada `Aarch64SveXxxDecoder` faz
`architecture.has(Aarch64Feature.XXX)` na hora de decidir se decodifica) — reescrevê-la num mapa
paralelo é duplicar uma fonte de verdade que já existe e pode divergir dela silenciosamente.

### A sonda dupla (`probeSveApplicability`)

Em vez de um mapa, a aplicabilidade de uma célula `sve.decode` numa coluna de versão é **medida**:

1. Sem `Aarch64Feature.SVE` na coluna → não aplicável (`·`). Fecha as 10 colunas `ARMv8.0-A`-
   `ARMv8.9-A` inteiras (nenhuma declara SVE) de uma vez.
2. A sonda sob a arquitetura REAL da coluna decodifica → aplicável, status = o que decodificou.
3. Não decodifica sob a coluna, mas decodifica sob uma arquitetura SINTÉTICA (`SVE_PROBE_EXTRA_FEATURES`,
   interna, nunca exposta) com toda sub-feature SVE2/cripto/BF16/F32-64MM/FP8/LUT ligada → a coluna
   genuinamente não tem a sub-feature que o encoding exige → não aplicável (`·`).
4. Não decodifica nem sob a sonda máxima → gap de implementação real → aplicável + `❌`.

Isto reusa o decoder real como fonte de verdade (G1-style), sem duplicar o conhecimento de "quem
exige o quê" — o preço é não distinguir "arquiteturalmente impossível" de "decoder bugado" (ver achado
2 abaixo), que foi mitigado com um registro explícito pontual (não um mapa geral).

### Dois achados reais, não hipotéticos — confirmados por leitura de fonte, não só pela sonda

1. **Features irmãs esquecidas na sonda "máxima" davam falso `❌`.** A primeira versão de
   `SVE_PROBE_EXTRA_FEATURES` só tinha a família `SVE2`/cripto/`F32MM`/`F64MM`/`FP8_CONVERT`/
   `SVE_B16B16` — faltavam `INT8_MATRIX_MULTIPLY`/`BFLOAT16`/`FP_ABSOLUTE_MAX_MIN`/`FP8`/
   `FP8_DOT_PRODUCT_2WAY`/`FP8_DOT_PRODUCT_4WAY`/`FP8_FUSED_MULTIPLY_ADD`/`LOOKUP_TABLE`. Sem elas, a
   sonda máxima também falhava para `BFCVT_m`/`BFMMLA`/`FAMAX`/`FAMIN`/`LUTI2_1b`/etc. em `ARMv9.0-A`,
   concluindo (ERRADO) "gap real" (`❌`) quando a resposta certa é "esta versão ainda não tem a
   sub-feature" (`·`). Achado via diagnóstico ad-hoc rodando `probeAarch64` diretamente para
   `BFCVT_m` nessas colunas; corrigido ampliando a lista. Teste de regressão:
   `IsaCoverageReportSveColumnTest#famaxAndFaminAreNotApplicableBeforeArmv94aAndSupportedFromThen`.
2. **Bug real de decoder, confirmado por leitura de fonte**: `SMMLA`/`USMMLA`/`UMMLA`
   (`Aarch64Sve2WideningDecoder#matrixMultiply`) exigem pelo manual ARM só `FEAT_SVE` + `FEAT_I8MM`,
   mas só são alcançadas através de `Aarch64Sve2IntegerDecoder#decodePrefix45`, que tem um gate
   `if (!architecture.has(Aarch64Feature.SVE2)) return null;` ANTES de chegar lá — amplo demais, já
   que nenhum preset declara `SVE2` (achado 1 da `Aarch64Architecture`, acima). Sem tratamento
   especial, a sonda dupla concluiria "·" para as 3 em TODAS as 16 colunas (a sonda "máxima" liga
   `SVE2` e decodifica, então pareceria "só falta uma sub-feature") — **escondendo um bug real atrás
   de "não aplicável"**, o oposto da disciplina do projeto. Registradas em
   `IsaCoverageReport.SVE_FEATURE_GATE_BUG_NAMES` para aparecerem como `❌` visível em vez de `·`;
   destino nomeado: **B17.29** (nova task, corrige o gate). Teste de regressão:
   `IsaCoverageReportSveColumnTest#theConfirmedDecoderGateBugStaysVisibleAsMissingNeverHiddenAsNotApplicable`.

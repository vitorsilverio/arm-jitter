# B17.26 — Fechamento do épico B17: `Applicability` de SVE e os processadores com SVE — 0 encodings

**Trilha:** B · **Repo:** arm-jitter (+ revalidação G5) · **Depende de:** B17.25 (⬜) — na prática, todo o épico
**Épico:** `b17-plano-sve.md` · **Status:** ⬜ (spec escrita 2026-09-14, ainda não executada)

## Contexto

Última task do épico. **É ela que faz "não se aplica a nenhum preset atual" sumir da tabela** para o
maior grupo do inventário — e, com isso, transforma **929 linhas** de trabalho invisível em
cobertura medida.

Durante todo o épico (B17.1-B17.25) a disciplina foi: implementar tudo gateado por
`Aarch64Feature.SVE`/`SVE2`, **com o grupo `sve.decode` ainda `NOT_IN_ANY_PRESET`**, para que cada
task fosse zero-diff de medição e a tabela ficasse byte a byte idêntica. Isso permitiu 22 tasks
seguidas sem risco de regressão nos 5 consumidores. **O preço é que nada disso conta na tabela** — e
é esta task que cobra o preço de volta. Mesma mecânica de **B13.22** (NEON), **B16.14** (MVE) e
**B11.5** (colunas por versão do A64).

### O que muda na medição

`IsaCoverageReport.GROUPS` tem hoje:

```java
new Group("sve.decode", "SVE/SVE2 — vetor escalável", 32, Probe.A64, false, NOT_IN_ANY_PRESET,
        "Extensão opcional do ARMv8.2+; o Cortex-A53 do Raspberry Pi 3 NÃO tem SVE."),
```

E o mecanismo de coluna por versão, que hoje **exclui explicitamente** este grupo:

```java
// B11.5: só `a64.decode` (o único grupo A64 com `applicability() != NOT_IN_ANY_PRESET`,
// ver GROUPS) ganha colunas por versão — `sve.decode`/`sme.decode` continuam "não se
// aplica a nenhum preset" (nada decodifica hoje, versionar não traria informação nova).
boolean aarch64Versioned = aarch64 && group.applicability() != NOT_IN_ANY_PRESET;
```

⚠️ **Achado desta rodada de spec**: a `Applicability` do medidor é uma interface sobre
`ArmArchitecture` (32 bits), **não** sobre `Aarch64Architecture`:

```java
@FunctionalInterface
private interface Applicability {
    boolean appliesTo(ArmArchitecture architecture);
}
```

Para grupos A64, o medidor **não usa** `applicability().appliesTo(...)` — usa
`isApplicableToAarch64Version(instruction.name(), occurrence, aarch64Architecture)` quando
`aarch64Versioned`, e `group.applicability() != NOT_IN_ANY_PRESET` (um booleano!) quando não.
Ou seja: **a mudança certa aqui não é "trocar `NOT_IN_ANY_PRESET` por uma lambda de SVE"** (o padrão
literal de B13.22/B16.14, que valem para grupos de 32 bits), e sim **ligar o versionamento A64 para
`sve.decode`** — deixando `isApplicableToAarch64Version` e a curadoria de
`AARCH64_VERSION_REQUIREMENTS` decidirem célula a célula. Ler o código antes de escolher; este é o
ponto em que uma cópia mecânica de B13.22 quebra.

### O catálogo de processadores

`Aarch64Processor` **já tem** os núcleos com SVE — Neoverse N1/E1/V1/N2/V2/N3/V3, Cortex-A510/A710/
A715/A520/A720/A725/X2/X3/X4/X925, a família C1. O que **falta** é que a arquitetura deles declare
SVE, o que a **B17.1** já resolve pelos presets `ARMV9_*_A`.

Os casos que precisam de atenção aqui são os núcleos **ARMv8.x com SVE**, que o preset de versão
NÃO cobre (SVE é opcional em ARMv8.2-A — decisão da B17.1, Inclui 4):

- **Fujitsu A64FX** — ARMv8.2-A **com SVE** (`VL=512`), o primeiro silício SVE do mundo. Não está no
  catálogo.
- **Neoverse V1** — hoje `ARMV8_4_A`; o núcleo real **tem SVE** (`VL=256`).
- **Neoverse N2/V2** — já `ARMV9_0_A`, herdam SVE/SVE2 da B17.1. ✔
- Conferir um a um: **entrada factualmente errada é pior que ausência** (princípio B12.4/B12.6).

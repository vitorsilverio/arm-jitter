# B6.14 — AArch64: `ADD`/`SUB` (immediate) resolvia `Rd|SP`/`Rn|SP` pela FLAG, não pelo ÍNDICE — bug real corrigido

**Trilha:** B · **Depende de:** B6.1 (`Ir64Op.Alu64`/`Ir64BlockExecutor#executeAlu`) · **Repo:** arm-jitter

## Contexto

Aberta pela sugestão da B6.13 (`tasks/FILA-EXECUCAO.md`, linha P17m/Q e a própria task
`b6.13-aarch64-ttbr1-el1.md`, seção "Sugestão ao usuário"): depois de refutar a hipótese
`TTBR1_EL1` para o SÉTIMO bloqueio da F11 (boot do `kernel8.img` real, `Raspi364Machine`),
a instrumentação daquela sessão mostrou que `SP` (`X31`) já continha um valor corrompido
(`0x100000872`, acima de 4 GiB) em `pc=0x13b8200`, ANTES de qualquer `STP` — a causa raiz real
não era tradução de endereço, era conteúdo de registrador. A B6.13 devolveu ao usuário como
candidata `B6.14`: "rastrear a origem do valor de `SP`... ANTES de presumir se é um bug real do
`arm-jitter`".

Esta task também converge com uma pendência já registrada no `tasks/README.md`, seção
"Pendências que EXIGEM sessão de modelo forte", item 7 (achada durante a B6.3.1, 2026-07-25,
nunca corrigida): `Ir64BlockExecutor#executeAlu` resolve `Rd|SP`/`Rn|SP` checando só a flag
booleira do decoder (`dstIsStackPointer`/`src1IsStackPointer`), nunca o ÍNDICE do registrador
(`== 31`) — ao contrário de `executeAluExtendedRegister` (B6.3.1) e de
`readBaseRegister`/`writeBaseRegister` (load/store), que sempre checam os dois.

## Investigação (leitura de código, sem precisar reproduzir o boot completo)

Em vez de reinstrumentar o boot de ~1,4M+ fatias (custo já documentado como caro pela B6.13/F11
sessão 6), esta sessão auditou o código-fonte apontado pela pendência #7 e confirmou o mecanismo
exato, sem precisão adicional de runtime necessária — a leitura da fonte já é conclusiva:

`Aarch64Decoder#decodeAddSubImmediate` (`ADD`/`SUB (immediate)`, `ARM DDI 0487 C6.2.4`/`C6.2.339`):

```java
boolean dstIsStackPointer = !setFlags;
return new Ir64Op.Alu64(
        isSub ? Ir64AluOp.SUB : Ir64AluOp.ADD, rd, rn, immediate, wide, setFlags,
        dstIsStackPointer, true);   // src1IsStackPointer sempre `true`
```

Isto está CORRETO como classificação do encoding: no manual, `Rn` desta forma é sempre da
classe `Rn|SP` (não existe uma forma `Rn|XZR` para `ADD`/`SUB (immediate)`), e `Rd` é `Rd|SP`
sempre que `!setFlags` (`ADDS`/`SUBS` nunca redirecionam `Rd` para `SP`). O mesmo padrão
(`!setFlags`, sem checar índice) já existe em `decodeAddSubExtendedRegister` — e ali está correto
porque o EXECUTOR (`executeAluExtendedRegister`) faz a segunda checagem: `if
(op.dstIsStackPointer() && op.dst() == ALU_STACK_POINTER_ENCODING)`.

**O bug estava só em `executeAlu` (forma imediata)**, que faltava essa segunda checagem:

```java
long operand1 = op.src1IsStackPointer() ? core.sp() : core.xForWidth(op.src1(), op.wide());
...
if (op.dstIsStackPointer()) {
    core.setSp(...);
} else {
    core.setXForWidth(op.dst(), result.value, op.wide());
}
```

Como `src1IsStackPointer` é sempre `true` para esta forma, `operand1` era **sempre** lido de
`SP`, ignorando `Rn` por completo — `add x4, x5, #0x123` lia `SP`, não `X5`. E como
`dstIsStackPointer` é `!setFlags` (sem checar `rd==31`), **qualquer** `ADD`/`SUB` imediato sem
`S` (a forma mais comum: incrementos de ponteiro, cálculo de endereço, etc.) gravava o resultado
em `SP`, não em `Rd` — confirmando exatamente o teste descartável citado pela pendência #7
(`add x4, x5, #0x123` gravando em `SP`).

Confirmado com o oráculo real (`aarch64-none-elf-as`/`objdump`, devkitA64 disponível nesta
sessão) que os encodings usados nos testes novos batem com o assembler real:

```
91048ca4  add x4, x5, #0x123
9100c3ff  add sp, sp, #0x30
910023e2  add x2, sp, #0x8
```

## Causa raiz confirmada para o bloqueio original da F11

Todo `ADD`/`SUB` imediato sem `S` no caminho de boot do `kernel8.img` real — inclusive os
onipresentes ajustes de `SP` em prólogos e cálculos de endereço tipo `add xN, xM, #imm` (`xM` !=
`sp`) — estava, na prática, executando `SP = SP + imediato` (ignorando `Rn`) e descartando o
destino real `Rd`. Isso explica de forma direta como `SP` acumula um valor incorreto ao longo de
milhões de instruções até o `STP` em `pc=0x13b8200` (B6.13) tentar usar um `SP` já corrompido —
sem precisar de nenhuma feature nova (`TTBR1_EL1` ou outra), é um bug de execução puro.

## Fix aplicado

`Ir64BlockExecutor#executeAlu` (`core/.../executor64/Ir64BlockExecutor.java`) ganhou a mesma
checagem dupla (flag **e** índice) que `executeAluExtendedRegister` já usa:

```java
long operand1 = op.src1IsStackPointer() && op.src1() == ALU_STACK_POINTER_ENCODING
        ? core.sp() : core.xForWidth(op.src1(), op.wide());
...
if (op.dstIsStackPointer() && op.dst() == ALU_STACK_POINTER_ENCODING) {
    core.setSp(...);
} else {
    core.setXForWidth(op.dst(), result.value, op.wide());
}
```

Nenhuma mudança no decoder nem no shape do `Ir64Op.Alu64` — os campos `dstIsStackPointer`/
`src1IsStackPointer` já carregavam a classificação correta do encoding (mesma convenção
documentada no Javadoc de `Ir64Op`, "setado pelo DECODER a partir do próprio encoding... a
resolução final acontece só no EXECUTOR"); só a resolução final estava incompleta.

O backend ASM nativo (`Ir64AsmRuntimeHelpers`/`Ir64BlockCompiler`) reconstrói o mesmo `Ir64Op.Alu64`
e delega para `Ir64BlockExecutor#executeOp` (decisão D-ASM documentada em
`Ir64AsmRuntimeHelpers`) — o fix cobre os dois backends por construção, sem precisar tocar
codegen (G1 preservado).

## Armadilhas

- **Não confundir com `TTBR1_EL1`** (B6.13) — aquela investigação já refutou tradução de
  endereço como causa; este bug é de EXECUÇÃO da ALU, não de MMU.
- **O bug só se manifesta com `!setFlags`** (`ADD`/`SUB` sem `S`) — `ADDS`/`SUBS` já resolviam
  `dst` corretamente (via índice, porque `dstIsStackPointer` já vinha `false` nesses casos), mas
  ainda liam `operand1` de `SP` incondicionalmente (bug do lado da LEITURA existia mesmo em
  `ADDS`/`SUBS`) — os testes cobrem o caso mais comum (`!setFlags`); não há teste dedicado a
  `ADDS`/`SUBS` com `Rn` normal porque `addSetsFlagsCorrectly` (pré-existente) já usa `Rn=7`
  (não-SP) e passava mesmo com o bug antigo, o que por si só já era suspeito — revisado: aquele
  teste usa `adds x6, x7, #0`, e como `src1IsStackPointer` era sempre `true`, ele DEVERIA ter
  falhado antes do fix (leria `SP`, não `X7`); `SP` da `newCore` é `0` por default, e o imediato
  também é `0`, então "ler SP em vez de X7" e "ler X7" coincidiam (os dois dão `0`) — o teste
  antigo tinha um falso-negativo por coincidência de valores. Não alterado (continua válido como
  teste de flags), mas documentado aqui para não confundir uma futura sessão.

## Resultado

✅ (2026-08-24) — Investigação por leitura de código (sem reinstrumentar o boot da F11) confirmou
a causa raiz sugerida pela B6.13: `Ir64BlockExecutor#executeAlu` resolvia `Rd|SP`/`Rn|SP` só pela
flag do decoder, nunca pelo índice do registrador — diferente de `executeAluExtendedRegister`
(B6.3.1), que já fazia a checagem dupla corretamente. Como `src1IsStackPointer` é sempre `true`
na forma imediata (classificação correta do encoding, `Rn` é sempre `Rn|SP`), `operand1` sempre
lia `SP`, ignorando `Rn`; e como `dstIsStackPointer=!setFlags`, qualquer `ADD`/`SUB` imediato sem
`S` gravava o resultado em `SP` em vez de `Rd`. Fix: `executeAlu` ganhou a mesma checagem `&&
op.dst()/op.src1() == ALU_STACK_POINTER_ENCODING` que `executeAluExtendedRegister` já tinha.
Cobre os dois backends (interpretado e ASM nativo, que delega para o mesmo executor via D-ASM).
3 testes de regressão novos. Fecha a pendência #7 do `tasks/README.md`. **Não** re-executa o boot
completo da F11 (fora do escopo/orçamento desta sessão) — retomar a F11 com este fix instalado
fica para uma sessão própria no `virtual-arm-box`.

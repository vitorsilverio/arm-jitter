# B6.6.3 — AArch64: ponte registrador-de-sistema↔MMU (`Aarch64VmsaSystemRegisters`)

**Trilha:** B · **Depende de:** B6.6.1 (mecanismo `MRS`/`MSR`) + B6.6.2
(`TranslatingAddressSpace64`) · **Repo:** arm-jitter

## Contexto

Terceira das 6 sub-tasks de B6.6 (ver decomposição em B6.6.1). Espelho direto
de **B4.1.2** (`Cp15VmsaCoprocessor`, 32-bit) — mas ligando `MRS`/`MSR`
(B6.6.1) em vez de `MCR`/`MRC` aos controles de `TranslatingAddressSpace64`
(B6.6.2). Primeira task da cadeia B6.6 em que código GUEST real (`MSR
TTBR0_EL1, X0` etc.) consegue mudar a tradução — mesmo marco que B4.1.2 fechou
para o mundo 32-bit ("sequência real de habilitação de MMU escrita por
código ARM no interpretador muda a tradução").

## Fatos de referência

1. **Precedente 32-bit** (`Cp15VmsaCoprocessor.java`, 236 linhas, lido nesta
   rodada de pesquisa): registradores tratados: SCTLR (bits M/V), TTBR0/
   TTBR1/TTBCR (só TTBR0 liga de verdade), DACR, DFSR/IFSR/DFAR/IFAR (só
   armazenamento — preenchimento real é a task de aborts), `c7` (NOP/RAZ),
   TLB unificada (invalidate all/by-MVA), CONTEXTIDR (ASID). Construtor
   desliga a MMU explicitamente (`mmu.setMmuEnabled(false)`, simula
   `SCTLR.M=0` do reset real de hardware) — **mesma decisão nesta task**.
2. **Mapeamento A64** (`Aarch64SystemRegisterId` de B6.6.1 →
   `TranslatingAddressSpace64` de B6.6.2):
   - `SCTLR_EL1` → bit `M` (bit0, MMU enable) → `mmu.setMmuEnabled`; demais
     bits armazenamento-só (sem efeito observável — mesma disciplina do
     precedente, que só liga `M`/`V`; A64 não tem bit `V`/vetores-altos —
     vetor de exceção é sempre `VBAR_EL1`, sem modo legado — então SCTLR_EL1
     nesta ponte só liga `M`).
   - `TTBR0_EL1` → `mmu.setTtbr0`.
   - `TCR_EL1` → `mmu.setTcr`.
   - `MAIR_EL1` → `mmu.setMair` (armazenamento, D2 de B6.6.2).
   - `ESR_EL1`/`FAR_EL1` → armazenamento-só nesta task (preenchimento real
     em B6.6.4, mesmo padrão exato do precedente `DFSR`/`DFAR`).
   - `VBAR_EL1`/`ELR_EL1`/`SPSR_EL1` → armazenamento-só nesta task (B6.6.4 os
     consome de verdade para entrada/retorno de exceção — aqui só
     precisam responder a `MRS`/`MSR` sem erro).
   - TLB (`TLBI VMALLE1`/`TLBI VAE1` — nomes de instrução A64 para invalidar
     TLB, NÃO são `MRS`/`MSR`: são uma forma de `SYS`/`SYS(L)` própria,
     **fora do encoding de B6.6.1** — ver Decisão D1 abaixo, achado real
     desta rodada de pesquisa que muda o escopo).

## Decisões de desenho FECHADAS nesta rodada

### D1 — `TLBI`/`DC`/`IC`/barreiras (`DSB`/`ISB`/`DMB`) são `SYS`/`SYS(L)`,
NÃO `MRS`/`MSR` — pré-requisito ADICIONAL não coberto por B6.6.1

**Achado real desta rodada**: instruções de manutenção de TLB/cache (`TLBI
VMALLE1`, `IC IALLU`, `DC CVAC`, etc.) em A64 usam o encoding `SYS`/`SYS(L)`
(`ARM DDI 0487 C5.2.3`, mesma classe top-level "Branch/Exception/System" mas
um subgrupo DIFERENTE de `MRS`/`MSR` — `CRn`/`CRm`/`op2` endereçam uma
OPERAÇÃO, não um registrador legível, então não fazem sentido como
`Aarch64SystemRegisterId` de B6.6.1). **Sem decodificar `TLBI` real, esta
task não consegue invalidar TLB por instrução guest** — mesma lacuna que
`Cp15VmsaCoprocessor` (32-bit) resolveu via `MCR c8,c7` (que É uma forma de
`MCR` comum, dentro do mecanismo já existente desde B1.x). **Decisão: esta
sub-task PRECISA decodificar pelo menos `TLBI VMALLE1`/`TLBI VMALLE1IS`
(invalidar tudo) como um encoding adicional, MÍNIMO, dentro de
`decodeBranchExceptionSystem`** (mesmo método que B6.6.1 já estende) — um
record `Ir64Op.SystemInstruction` novo (kind contíguo seguinte), reconhecendo
só as poucas formas de `SYS`/`SYS(L)` necessárias para
`invalidateTlbAll()`/`invalidateTlbByMva()`. **Registrar isto explicitamente
como escopo adicional descoberto nesta rodada de pesquisa** (não estava
implícito na leitura de B6.6.1) — se o usuário revisar esta spec e preferir
tratar como uma sub-task própria (`B6.6.3.1`?), a decisão de desmembrar fica
para quem executar, mas o gap tem que ser resolvido AQUI ou antes, porque sem
`TLBI` funcionando o aceite de B6.6.5/B6.6.6 (kernel real trocando de
processo) fica inalcançável.

`DSB`/`ISB`/`DMB` (barreiras): mesma decisão de sempre neste projeto —
NOP observável (`IrOp.MemoryBarrier`, 32-bit; `acquireRelease` de
`LoadExclusive`/`StoreExclusive`, B6.3.4) — se ainda não decodificadas em
A64 (CONFERIR; podem já ter caído em `unsupported` sem que nenhuma sub-task
anterior precisasse delas), decodificar aqui como NOP mínimo, mesmo padrão.
`DC`/`IC` (manutenção de cache) — fora de escopo (sem cache modelado,
mesma decisão do `c7` de 32-bit — mas ao contrário de `DSB`/`ISB`, `DC`/`IC`
não são estritamente necessários para o aceite "kernel mínimo até shell", só
`TLBI` é crítico); registrar como pendência explícita se não implementadas.

### D2 — `Aarch64VmsaSystemRegisters implements Aarch64SystemRegisterBus`,
composição não herança

Mesmo padrão exato do precedente (`Cp15VmsaCoprocessor implements
CoprocessorBus`) — construtor `Aarch64VmsaSystemRegisters(TranslatingAddressSpace64
mmu, Aarch64Core core)`, desliga a MMU no construtor (Fatos de referência
#1). Hospedeiro instala via `core.setSystemRegisterBus(new
Aarch64VmsaSystemRegisters(mmu, core))` (B6.6.1 D2).

## Objetivo

- `Aarch64VmsaSystemRegisters` (D2) ligando os registradores de B6.6.1/
  B6.6.2 (Fatos de referência #2).
- `Ir64Op.SystemInstruction` mínimo para `TLBI VMALLE1`(`IS`) (D1) — e
  `DSB`/`ISB`/`DMB` como NOP, se ainda não cobertos.

## Especificação

1. `Aarch64VmsaSystemRegisters.java` (`memory/mmu/` ou `core64/`, decidir
   por proximidade com `TranslatingAddressSpace64`): `handles`/`read`/
   `write` (B6.6.1 D2) para os 9 registradores de B6.6.1 (menos `ELR_EL1`/
   `SPSR_EL1`/`VBAR_EL1` que talvez fiquem melhor num bus de EXCEÇÃO
   separado de B6.6.4 — **auditar ao implementar**: se B6.6.4 introduzir um
   `Aarch64ExceptionModel` A64 com estado próprio para esses 3 registradores
   — mesmo padrão que `MProfileExceptionModel`/`AProfileExceptionModel` já
   fazem no 32-bit —, mover a leitura/escrita deles para lá em vez de
   duplicar em `Aarch64VmsaSystemRegisters`; esta task pode nascer só com os
   6 registradores realmente de MMU, se essa reorganização parecer mais
   limpa na hora).
2. Decode de `TLBI` mínimo (D1) — subgrupo `SYS`/`SYS(L)` dentro de
   `decodeBranchExceptionSystem`, restrito a `VMALLE1`/`VMALLE1IS` (invalidar
   tudo — mesma simplificação "sem per-ASID" que RFC-SOFTMMU.md §5 já aceitou
   para o precedente 32-bit).
3. `DSB`/`ISB`/`DMB` como NOP, se ainda não decodificadas (auditar).

## Não inclui

- `TLBI` por VA específico (`VAE1`) — só invalidação total nesta rodada
  (mesma simplificação "sem per-ASID" do precedente).
- `DC`/`IC` (manutenção de cache) — sem efeito, fora de escopo salvo
  pendência explícita se necessário.
- Preenchimento real de `ESR_EL1`/`FAR_EL1` em abort — isso é B6.6.4.
- Modelo de exceção EL0→EL1 (entrada/retorno via `VBAR_EL1`/`ELR_EL1`/
  `SPSR_EL1`/`ERET`) — B6.6.4.

## Testes mínimos

- Sequência real `TTBR0_EL1→TCR_EL1→SCTLR_EL1.M=1` escrita por `MSR`s reais
  executados via `Ir64BlockExecutor` muda a tradução (aceite explícito,
  mesmo teste que B4.1.2 fez para o precedente 32-bit).
- `MRS`/`MSR` forwarding+read-back para os 6+ registradores.
- `TLBI VMALLE1` forçando walk novo (via `pageWalkCount()`).
- Regressão: suíte completa de B6.1-B6.6.2 sem mudança.

## Aceite

- `mvn -o test` verde. G5 não se aplica (nenhum arquivo 32-bit tocado).
- Sequência de habilitação de MMU via instruções reais funcionando
  ponta-a-ponta (mesmo aceite explícito do precedente 32-bit).

## Armadilhas

- **`TLBI` não é `MRS`/`MSR`** — achado real desta rodada (D1); sem
  decodificá-lo, nenhuma troca de processo funciona de verdade no kernel de
  B6.6.6, mesmo com toda a infraestrutura de B6.6.1/B6.6.2 correta.
- **Auditar se `ELR_EL1`/`SPSR_EL1`/`VBAR_EL1` pertencem aqui ou a um futuro
  `Aarch64ExceptionModel`** (Especificação #1) — não duplicar estado entre os
  dois se B6.6.4 acabar criando essa classe.
- **Mesma disciplina "sem per-ASID"** do precedente 32-bit — não implementar
  `TLBI VAE1` achando que é "só mais um case", registrar como pendência se
  aparecer necessidade real.

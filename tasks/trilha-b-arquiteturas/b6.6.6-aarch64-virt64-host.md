# B6.6.6 — AArch64: hospedeiro `virt64` (kernel arm64 mínimo até shell)

**Trilha:** B · **Depende de:** B6.6.5 (`translationGeneration` A64
consumido pelo `jit64/`) · **Repos:** arm-jitter (nenhuma mudança nova
esperada) + repo novo `virt64`

**🧑 Esta task fica bloqueada no usuário desde a escrita desta spec** — ver
Armadilhas e `tasks/FILA-EXECUCAO.md` seção "🧑 Bloqueadas no usuário" (linha
adicionada nesta rodada). Não pegar sem o usuário priorizar/disponibilizar o
ambiente.

## Contexto

Sexta e última sub-task de B6.6 (ver decomposição em B6.6.1) — espelho de
**B4.1.5** (repo `linuxbox`, hospedeiro `versatilepb`, 32-bit), mas para um
hospedeiro A64 (`virt64`, nome inspirado na máquina `virt` do QEMU aarch64,
o análogo moderno mais simples ao `versatilepb` do mundo 32-bit — sem
periféricos legados PL0xx, device tree em vez de ATAGs). **Aceite objetivo do
épico**: "kernel arm64 mínimo até shell (reusar aprendizado de B4.1)".

**Achado direto do precedente**: B4.1.5 (32-bit) fechou APENAS PARCIALMENTE —
o kernel versatile real descomprime e pula para código pós-MMU, mas trava
num `PREFETCH_ABORT` recursivo ao redor da página de vetores altos
(`0xffff0000`), causa raiz não isolada (`tasks/FILA-EXECUCAO.md:257-278`).
**Esta task NÃO herda esse bug especificamente** (é um hospedeiro/kernel
diferente, ARM32 vs A64), mas herda a mesma CATEGORIA de risco: um kernel
mainline real é muito mais exigente que os testes unitários de B6.6.1-B6.6.5,
e é plausível que bugs equivalentes (timing de vetor de exceção, ordem de
inicialização de MMU, algum registrador de sistema não coberto pelo
subconjunto de B6.6.1/B6.6.3) apareçam aqui também. Reservar tempo de sessão
generoso e aceitar fechamento PARCIAL como resultado honesto, mesmo padrão
que B4.1.5 já demonstrou ser aceitável para este projeto.

## Por que bloqueada no usuário (não é um "não fazer", é um "não dá pra
fazer nesta máquina hoje")

Mesma categoria exata de bloqueio já registrada para **B6.2 aceite #2**
(busybox aarch64) e **B4.0.3 item 3** (busybox Thumb-2): esta máquina não
tem um toolchain `aarch64-linux-*` real (musl/glibc) nem um kernel arm64
mainline pré-compilado disponível localmente. Diferente de B4.1.5 (32-bit),
que contornou o bloqueio usando um kernel Debian PRÉ-COMPILADO real
(`vmlinuz-3.2.0-4-versatile`) baixado como binário — **não há garantia de
que um kernel arm64 pré-compilado equivalente (`vmlinuz` genérico para a
máquina `virt` do QEMU, arch `arm64`) esteja tão facilmente disponível ou
seja tão simples de obter sem acesso à internet/gerenciador de pacotes desta
sessão** — isso precisa ser verificado pelo usuário ou por uma sessão com
acesso de rede mais amplo antes de começar a implementar. Registrar
EXPLICITAMENTE: **não simular/inventar um "kernel de teste" fake só para
fechar esta task de forma artificial** — o aceite é sobre um kernel REAL.

## Fatos de referência

1. **Periféricos mínimos necessários** (mesmo raciocínio de B4.1.5, mas para
   a máquina `virt` do QEMU aarch64): UART PL011 (mesmo periférico do
   precedente 32-bit — reaproveitar a implementação `Pl011Uart` de
   `linuxbox` se ela puder ser extraída para uma forma compartilhável;
   CONFERIR se faz sentido copiar/adaptar ou reescrever), GICv2/GICv3
   (controlador de interrupção — DIFERENTE do PL190 do precedente, mais
   complexo), um timer arm genérico (`CNTFRQ_EL0`/`CNTPCT_EL0` — registrador
   de SISTEMA, precisa do mecanismo de B6.6.1 estendido com mais
   `Aarch64SystemRegisterId`s de timer, fora do subconjunto original de
   B6.6.1 — pendência adicional a resolver aqui ou antes), PSCI (Power State
   Coordination Interface — mecanismo de boot/desligamento via `HVC`/`SMC`
   OU via `MRS`, dependendo da versão — kernels arm64 modernos ESPERAM PSCI
   para várias operações básicas, incl. multi-core; CONFERIR se um kernel
   single-core minimalista consegue bootar sem PSCI completo).
2. **Device Tree, não ATAGs**: kernels arm64 NUNCA usaram ATAGs (protocolo
   legado ARM32) — o boot precisa de um blob DTB (device tree binary)
   descrevendo a máquina, RAM, UART, GIC, timer. Gerar um DTB mínimo válido
   é trabalho novo sem equivalente direto em `AtagsBuilder` (32-bit) —
   `virt64` precisa de um `DeviceTreeBuilder`-equivalente ou usar um DTB
   pré-gerado versionado (mesma estratégia de "binário grande é aceitável
   no repo" que `linuxbox/testdata/` já usa para o kernel).
3. **Convenção de boot arm64 Linux**: registrador `X0` aponta pro DTB, `X1`-
   `X3` reservados/zero, execução começa em EL1 (ou EL2, se hipervisor —
   **decisão: assumir boot direto em EL1**, mesma simplificação que B6.6.4
   já modela como o único nível além de EL0) com MMU desligada
   (`SCTLR_EL1.M=0` — o kernel liga a própria MMU cedo no boot, o emulador
   só precisa entregar o estado inicial correto).

## Decisões de desenho a fechar quando esta task for retomada (NÃO
fechadas nesta rodada — dependem de decisões que só fazem sentido com o
ambiente real disponível)

- Qual kernel exato usar (versão, build, fonte) — mesma pesquisa que B4.1.5
  fez para o kernel Debian versatile, repetida para arm64.
- Se `virt64` reaproveita alguma infraestrutura de `linuxbox` (`PagedAddressSpace`
  já é genérico o bastante para 32/64 bits? CONFERIR — RFC-IR-64BIT.md §3.1
  item 2 já registrou que `PagedAddressSpace` "deveria nascer com o miolo
  [fatiamento de páginas] compartilhável entre as duas interfaces" quando
  fosse feito — isso NÃO foi feito ainda, então `virt64` provavelmente
  precisa do próprio `PagedAddressSpace64` como um item de trabalho real
  desta task, não reaproveitamento de graça) ou nasce do zero como
  `linuxbox` nasceu (repo novo).
- GICv2 vs GICv3 — v2 é mais simples mas kernels modernos podem preferir/
  exigir v3 dependendo da configuração; decidir com base no kernel real
  disponível.
- PSCI: implementação mínima via `HVC`/`SMC` (nenhum decodificado hoje em
  A64 — mais um pré-requisito de encoding a somar aos de B6.6.3/B6.6.4) ou
  via um mecanismo alternativo se o kernel permitir desabilitar PSCI na
  linha de comando.

## Objetivo (herdado do épico, não decomposto — decisões de implementação
ficam para a sessão que retomar com o ambiente resolvido)

Kernel arm64 mainline mínimo bootando até um shell `busybox`/`sh` interativo
no hospedeiro `virt64`, nos backends interpretado e ASM (`--check` sobrevive
ao boot inteiro) — mesmo formato de aceite que B4.1.5 tinha para o
precedente 32-bit, sem redução de ambição só porque o precedente fechou
parcial (registrar honestamente se o mesmo acontecer aqui).

## Armadilhas

- **Mesmo bloqueio de toolchain/binário de B6.2/B4.0.3/B4.1.5** — não pegar
  esta task sem o usuário disponibilizar um kernel arm64 real (pré-compilado
  ou toolchain para buildar) e, idealmente, um initramfs busybox aarch64
  real (o MESMO bloqueio de B6.2 aceite #2 — um ambiente resolve os dois).
- **GICv2/GICv3/PSCI são substancialmente mais complexos que PL190/sem-PSCI**
  do precedente 32-bit — não subestimar o tamanho desta task só porque
  "já fizemos isso uma vez" para versatilepb.
- **DTB, não ATAGs** — não tentar reaproveitar `AtagsBuilder` como está;
  é um formato de dados completamente diferente.
- **`PagedAddressSpace64` provavelmente precisa ser criado** — RFC-IR-64BIT.md
  §3.1 item 2 previu isso mas não foi feito ainda; auditar antes de assumir
  que existe.
- **Herda a mesma categoria de risco de fechamento PARCIAL** que B4.1.5
  teve — reservar tempo de sessão generoso, aceitar um resultado parcial
  honesto (marco alcançável documentado, causa raiz de qualquer travamento
  registrada) em vez de forçar um aceite que não foi realmente alcançado.
- **Não simular kernel/DTB/initramfs fake** para fingir que o aceite fechou
  — mesma disciplina de honestidade que toda a trilha B já demonstra.

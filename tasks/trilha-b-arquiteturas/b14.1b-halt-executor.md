# B14.1b — `HALT` (`HLT`) precisa de execução: reusar `IrOp.Breakpoint` — 0 encodings novos

**Trilha:** B · **Repo:** arm-jitter (+ revalidação G5) · **Depende de:** B14.1 ✅
**Épico:** `b14-plano-vfp-armv8-32bit.md` · **Status:** ✅ (2026-09-18, aberta e fechada na mesma sessão)

## Contexto

A B14.1 criou o preset `ArmArchitecture.ARMV8A_32`, que declara `ArmFeature.HALT` — a feature já
existia desde a B22.1 (decode de `HLT` em `ArmDecoder`/`ThumbDecoder`, devolvendo
`InstructionKind.HALT`), mas **nenhum preset a declarava**, então o encoding nunca chegava a ser
executado por ninguém. A B14.1 é a primeira vez que esse caminho fica alcançável de verdade.

Ao revisar cobertura de teste da B14.1 (a pedido do usuário, achado real — não hipotético),
descobri que **`InstructionKind.HALT` não tem `case` em `StandardIrBuilder#lift`** (o builder que
eleva `DecodedInstruction` para `IrOp`). O `switch` ali é uma *statement* switch sobre um enum, sem
`default` — Java não exige exaustividade nesse caso, então a ausência de `case HALT` não é erro de
compilação, é uma lacuna silenciosa: o método simplesmente não adiciona nenhuma operação para a
instrução, e a cauda comum do lifter (G4) sempre anexa `Cycle(1)` + `Fetch(...)` de qualquer jeito.
**Resultado observável: `HLT` sob `ARMV8A_32` hoje executa como um NOP** — consome ciclo, avança o
PC, nenhum outro efeito.

Isso contradiz o próprio Javadoc de `InstructionKind#HALT` (escrito na B22.1):

> "Quando um preset ARMv8-A de 32 bits (B14) existir, a semântica de execução = entregar ao
> debugger do host (mesmo caminho de `BREAKPOINT`) ou, sem debugger, `UNDEFINED`."

O mecanismo "mesmo caminho de `BREAKPOINT`" **já existe e está pronto para reuso**:
`IrOp.Breakpoint` carrega um `immediate` e é executado por
`IrSystemExecutor#executeBreakpoint(ArmCore, IrOp.Breakpoint, int)` (`codegen/executor/`), que:
1. tenta `core.bkptDispatcher().dispatch(...)` se houver um handler registrado (semihosting real,
   ex. armbox), senão
2. `core.requestException(ArmException.UNDEFINED)`.

Esse é **exatamente** o contrato que o Javadoc de `HALT` promete — não uma aproximação. E como
`IrOp.Breakpoint` é um `record` já reconhecido por TODOS os backends (interpretado, ASM nativo via
`AsmNativePolicy`/`IrOpInterop`, Truffle via `SystemOpNode`, e o harness de equivalência via
`DivergenceCheckingCodeEmitter`), reusar o record para `HALT` fecha a lacuna nos quatro backends
**sem nenhum código novo além de uma linha no `StandardIrBuilder`** — zero `IrOp` novo, zero
`case` novo nos outros arquivos.

Achado paralelo (não uma inconsistência a corrigir, só contexto): o lado A64 (B8.3) resolveu o
mesmo problema de outro jeito — `HLT` A64 vira `Ir64Op.UndefinedInstructionTrap` (sempre
`UNDEFINED`, sem tentar dispatch de debugger), porque o A64 nunca teve um `BkptDispatcher`
equivalente plugado no caminho de `HLT`. O lado 32-bit TEM essa infra pronta (é como `BKPT`
clássico já funciona desde a B7.5), então reusá-la aqui é estritamente mais completo, não uma
divergência arbitrária entre os dois lados.

## Objetivo

`HLT` sob `ARMV8A_32` executa de verdade: delega a um `BkptDispatcher` se houver handler
registrado, ou levanta `ArmException.UNDEFINED` — nos quatro backends (interpretado, ASM nativo,
Truffle, e mantendo G1 — o interpretado continua o oráculo, verificado pelo
`BlockEquivalenceHarness`).

## Inclui

1. `StandardIrBuilder#lift`: `case HALT -> block.add(new IrOp.Breakpoint(instruction.immediate()));`
   (mesma linha do `case BREAKPOINT`, mesmo grupo de case — `case BREAKPOINT, HALT -> ...`).
2. Javadoc de `IrOp.Breakpoint` atualizado: passa a documentar que representa tanto `BKPT` quanto
   `HLT` (a diferença de nome de instrução não é observável na execução — o contrato é idêntico).
3. Javadoc de `InstructionKind#HALT` atualizado: remove o texto "Quando um preset... existir" (que
   já não é mais uma promessa futura) e aponta para `IrOp.Breakpoint`.
4. Testes cobrindo os quatro backends:
   - Interpretado, sem `BkptDispatcher`: `HLT` levanta/gera `ArmException.UNDEFINED` (não NOP).
   - Interpretado, com `BkptDispatcher` registrado para o imediato: o handler É chamado (prova que
     não é um `UNDEFINED` cru — o imediato de `HLT` chega ao dispatcher, mesmo contrato de `BKPT`).
   - Equivalência ASM nativo × interpretado via `BlockEquivalenceHarness` (mesmo padrão de
     `C127NativeEquivalenceTest#breakpointRaisesSameExceptionAsInterpreted`), incluindo
     `isNativeSupported() == true` (reuso de `IrOp.Breakpoint` implica reuso do `case
     IrOp.Breakpoint` já aceito por `AsmNativePolicy` desde a C12.7 — nenhuma mudança lá, só prova
     que continua valendo).
   - Truffle: equivalência via o harness próprio do módulo `truffle` (mesmo padrão de
     `TruffleCodeEmitterSystemEquivalenceTest`), se esse arquivo já cobre `IrOp.Breakpoint`
     genericamente — só adicionar o vetor `HLT`, sem `case` novo esperado em `SystemOpNode`.

## Não inclui

- **Qualquer distinção de comportamento entre `BKPT` e `HLT`** — o projeto modela os dois com
  exatamente o mesmo contrato de execução (delega ou `UNDEFINED`), decisão explícita desta task.
  Se um consumidor real precisar de semântica de debug HALTING genuína (parar a CPU e ceder ao
  host, diferente de uma exceção síncrona de `BKPT`), isso é uma RFC nova, não esta task.
- **`Ir64Op`/A64** — fora de escopo, já resolvido (B8.3) e sem o bug: A64 sempre trata `HLT` como
  `UndefinedInstructionTrap`, sem builder-switch sem `case`.
- **Novo registro `IrOp`** — reuso puro de `IrOp.Breakpoint`.
- **Mudar `AsmNativePolicy`/`SystemOpNode`/`DivergenceCheckingCodeEmitter`** — os três já
  reconhecem `IrOp.Breakpoint` por tipo, não por `InstructionKind` de origem; nada lá muda.

## Aceite

- `HLT` sob `ARMV8A_32`, interpretado, sem `BkptDispatcher`: gera `ArmException.UNDEFINED`
  (observável via `core.requestException`/estado do core após `step`), não um NOP silencioso.
- `HLT` sob `ARMV8A_32`, interpretado, com handler registrado para o imediato exato: o handler é
  chamado com o `CpuState` correto.
- `AsmCodeEmitter.isNativeSupported(block)` continua `true` para um bloco com `HLT` (reuso do
  `case IrOp.Breakpoint` da C12.7) e o `BlockEquivalenceHarness` confirma equivalência byte-a-byte
  ASM×interpretado (G1).
- `ARMV7A`/demais presets pré-`ARMV8A_32` continuam decodificando `HLT` como `UNIMPLEMENTED`
  (zero-diff, esse comportamento já é da B22.1/B14.1, não muda aqui).
- `mvn -o test` verde + G5 verde nos 5 consumidores.

## Armadilhas

1. **Não criar um `IrOp` novo por engano** — a tentação natural seria um `IrOp.Halt` dedicado,
   espelhando `Ir64Op.UndefinedInstructionTrap`. Resistir: o 32-bit já tem a infra de dispatcher
   funcionando (`BKPT`), reusar é estritamente melhor (não descarta a capacidade de handler real) e
   é G6 (não duplicar o que já existe).
2. **O `switch` de `StandardIrBuilder#lift` é uma switch *statement*, não *expression*** — por isso
   o compilador não pegou a ausência de `case HALT`. Ao adicionar `HALT` ao grupo de `BREAKPOINT`,
   não é preciso (nem correto) adicionar um `default` — mas vale registrar essa lacuna de projeto
   (switch estatement sem exaustividade) como achado de processo se aparecer de novo em outra
   `InstructionKind` nova, não corrigir aqui (fora de escopo, mudaria o contrato de todos os casos
   já ausentes de propósito, ex. `LONG_BRANCH_32` tratado antes do switch).
3. **Immediate de `HLT` Thumb é 6 bits, `BKPT` Thumb é 8 bits** — não é um bug desta task (o decode
   já existe desde B22.1 e não muda), só não confundir os dois ao ler o Javadoc/testar.

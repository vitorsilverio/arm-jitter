# B14.2 — `LDA`/`STL`/`LDAEX*`/`STLEX*` (load-acquire / store-release, A32 + T32) — 28 linhas

**Trilha:** B · **Repo:** arm-jitter (+ revalidação G5) · **Depende de:** B14.1
**Épico:** `b14-plano-vfp-armv8-32bit.md` · **Status:** ⬜ (spec escrita 2026-09-13, ainda não executada)

## Contexto

O épico (`b14-plano-vfp-armv8-32bit.md`, escada) diz "~14 encodings". **Medido nesta rodada de
spec: são 28 linhas de decodetree** — 14 em `a32.decode` e 14 em `t32.decode`; o "~14" do plano
contava MNEMÔNICOS (as linhas de `docs/isa-nao-aplicavel.tsv` casam por nome e alcançam os dois
arquivos, porque nenhuma delas usa a coluna opcional `grupo`).

### O encoding real (`target/isa-decode/a32.decode`, linhas 375-409 — medido)

```
@strex           ---- .... .... rn:4 rd:4 .... .... rt:4      &strex imm=0 rt2=15
@ldrex           ---- .... .... rn:4 rt:4 .... .... ....      &ldrex imm=0 rt2=15
@stl             ---- .... .... rn:4 .... .... .... rt:4      &ldrex imm=0 rt2=15

STREX            .... 0001 1000 .... .... 1111 1001 ....      @strex
STREXD_a32       .... 0001 1010 .... .... 1111 1001 ....      @strex
STREXB           .... 0001 1100 .... .... 1111 1001 ....      @strex
STREXH           .... 0001 1110 .... .... 1111 1001 ....      @strex

STLEX            .... 0001 1000 .... .... 1110 1001 ....      @strex
STLEXD_a32       .... 0001 1010 .... .... 1110 1001 ....      @strex
STLEXB           .... 0001 1100 .... .... 1110 1001 ....      @strex
STLEXH           .... 0001 1110 .... .... 1110 1001 ....      @strex

STL              .... 0001 1000 .... 1111 1100 1001 ....      @stl
STLB             .... 0001 1100 .... 1111 1100 1001 ....      @stl
STLH             .... 0001 1110 .... 1111 1100 1001 ....      @stl

LDREX            .... 0001 1001 .... .... 1111 1001 1111      @ldrex
...
LDAEX            .... 0001 1001 .... .... 1110 1001 1111      @ldrex
LDAEXD_a32       .... 0001 1011 .... .... 1110 1001 1111      @ldrex
LDAEXB           .... 0001 1101 .... .... 1110 1001 1111      @ldrex
LDAEXH           .... 0001 1111 .... .... 1110 1001 1111      @ldrex

LDA              .... 0001 1001 .... .... 1100 1001 1111      @ldrex
LDAB             .... 0001 1101 .... .... 1100 1001 1111      @ldrex
LDAH             .... 0001 1111 .... .... 1100 1001 1111      @ldrex
```

**Achado central do lado A32**: as três famílias diferem **só no nibble `bits[11:8]`** —
`1111` = exclusivo clássico (`LDREX`/`STREX`, JÁ implementado), `1110` = exclusivo **com**
acquire/release (`LDAEX`/`STLEX`), `1100` = acquire/release **sem** exclusividade (`LDA`/`STL`).
Tudo o mais (`bits[27:23]=00011`, `sz`=`bits[22:21]`, `L`=`bit20`, `bits[7:4]=1001`) é idêntico ao
que `ArmDecoder` já decodifica hoje.

### O encoding real (`target/isa-decode/t32.decode`, linhas 589-610 — medido)

```
STLEX            1110 1000 1100 .... .... 1111 1110 ....      @strex_0
STLEXB           1110 1000 1100 .... .... 1111 1100 ....      @strex_0
STLEXH           1110 1000 1100 .... .... 1111 1101 ....      @strex_0
STLEXD_t32       1110 1000 1100 .... .... .... 1111 ....      @strex_d
STL              1110 1000 1100 .... .... 1111 1010 1111      @ldrex_0
STLB             1110 1000 1100 .... .... 1111 1000 1111      @ldrex_0
STLH             1110 1000 1100 .... .... 1111 1001 1111      @ldrex_0
LDAEX            1110 1000 1101 .... .... 1111 1110 1111      @ldrex_0
LDAEXB           1110 1000 1101 .... .... 1111 1100 1111      @ldrex_0
LDAEXH           1110 1000 1101 .... .... 1111 1101 1111      @ldrex_0
LDAEXD_t32       1110 1000 1101 .... .... .... 1111 1111      @ldrex_d
LDA              1110 1000 1101 .... .... 1111 1010 1111      @ldrex_0
LDAB             1110 1000 1101 .... .... 1111 1000 1111      @ldrex_0
LDAH             1110 1000 1101 .... .... 1111 1001 1111      @ldrex_0
```

No T32 o discriminador é `op4` = `bits[7:4]`: `0100`/`0101`/`0111` são o exclusivo sized já
implementado; `1000`-`1111` são exatamente estas 14 — e o `Thumb2LoadStoreDecoder` **já documenta
essa lacuna por escrito** (linhas 428-431 e 461):

```java
/// `raw[7:4]`: dentro do subgrupo `P=0,W=0` ... distingue byte/half/doubleword de `TBB`/`TBH`
/// (op4 `0`/`1` ...) e das formas load-acquire/store-release ARMv8 (`LDAEX*`/`STLEX*`/`LDA*`/`STL*`,
/// op4 `8`-`F` — mesmo espaço de bits que o ARM clássico também não implementa, fora do escopo).
...
default -> null; // TBB/TBH ou load-acquire/store-release ARMv8, fora do escopo
```

### Por que esta task destrava o `Cortex-A32` (B12.6)

`ArmProcessor` (Javadoc da classe, bloco "**Escopo de B12.6**") registra literalmente: *"a base
`ARMv8-A` inclui `LDA`/`LDAB`/`LDAH`/`LDAEX*` e `STL`/`STLB`/`STLH`/`STLEX*` como **obrigatórias**
... nenhuma delas tem decoder/executor neste projeto hoje ... Mapear `Cortex-A32` para `ARMV7A`
seria uma entrada de catálogo factualmente ERRADA"*. Esta task + B14.3 removem essa objeção; a
entrada de catálogo em si é a **B14.7**.

## Objetivo

As 28 linhas decodificam e executam sob `ArmArchitecture.ARMV8A_32` (gate
`ArmFeature.LOAD_ACQUIRE_STORE_RELEASE`, B14.1), reusando o monitor de exclusividade que
`LDREX`/`STREX` já usam (B5.1) e o executor de load/store existente. Sob qualquer preset **sem** a
feature (v4T..v7-A, v6-M, v7-M) o resultado continua `UNIMPLEMENTED` explícito (G8).

## Inclui

1. **Decode A32** em `ArmDecoder`, no MESMO bloco do exclusivo clássico (`(raw & 0x0F80_0FF0) ==
   0x0180_0F90`, linhas ~514-551) — generalizar o nibble `bits[11:8]` de `1111` para
   `{1111, 1110, 1100}`, com o gate novo aplicado só aos dois valores novos (G3: `1111` continua
   gateado por `EXCLUSIVE_WORD`/`EXCLUSIVE_SIZED` exatamente como hoje).
2. **Decode T32** em `Thumb2LoadStoreDecoder#decodeExclusiveWordOrSized` — os `op4` `1000`-`1111`
   que hoje caem no `default -> null`.
3. **Duas semânticas distintas, não uma**:
   - `LDAEX*`/`STLEX*` = `LDREX*`/`STREX*` + barreira (reusam `InstructionKind.LOAD_EXCLUSIVE`/
     `STORE_EXCLUSIVE` e o monitor de B5.1, com um sinalizador de acquire/release — ver Armadilha 2);
   - `LDA*`/`STL*` = `LDR*`/`STR*` simples (registrador base sem offset) + barreira, **sem tocar no
     monitor de exclusividade** (Armadilha 3).
4. **Ordenação de memória**: `acquire`/`release` é **NOP observável** neste interpretador
   single-thread, exatamente como o lado A64 já decidiu — ver `Ir64Op.LoadExclusive#acquireRelease`
   ("`LDAXR`=`true`/`LDXR`=`false` é NOP observável no interpretador"). Reproduzir a MESMA decisão e
   o MESMO texto de Javadoc, para as duas arquiteturas contarem a mesma história.
5. **`docs/isa-nao-aplicavel.tsv`**: as 14 linhas `LDA`/`LDAB`/`LDAH`/`LDAEX`/`LDAEXB`/`LDAEXH`/
   `LDAEXD*`/`STL`/`STLB`/`STLH`/`STLEX`/`STLEXB`/`STLEXH`/`STLEXD*` **não são apagadas — são
   ESTREITADAS** de `*` para a lista das 7 colunas pré-v8 (`v4T,v5TE,v6K,MPCore,v7-A,v6-M,v7-M`),
   igual ao que a linha `CRC32*` já faz. Ver Armadilha 5 (é o ponto mais fácil de errar da task).
6. Testes (ver Aceite).

- **`VSEL`/`VMAXNM`/`VMINNM`** — B14.4; **`VRINT`/`VCVT` com `rm:2`** — B14.5; **`FEAT_FP16`** —
  B14.6.
- **Entrada `Cortex-A32` em `ArmProcessor`** e a coluna `v8-A/32` no `IsaCoverageReport` — B14.7.
  Enquanto a coluna não existe, esta task é **zero-diff em `docs/COBERTURA-ISA.md`** (o estreitamento
  do tsv não muda nenhuma célula das 7 colunas atuais — é exatamente por isso que ele é a forma
  SEGURA de fazer a mudança agora).
- **Ordenação de memória de verdade** (barreiras reais, modelo de memória multi-core) — NOP
  observável, como no A64. Não é exclusão: é a mesma simplificação já documentada do outro lado, e
  vira trabalho real se/quando o projeto modelar um modelo de memória fraco.
- **Emissão nativa/Truffle** — decode + interpretado apenas, mesmo padrão do resto da trilha B.

### Semântica

| Família | Endereço | Monitor de exclusividade | Barreira |
|---|---|---|---|
| `LDA`/`LDAB`/`LDAH` | `[Rn]`, sem offset | **não toca** | acquire |
| `STL`/`STLB`/`STLH` | `[Rn]`, sem offset | **não toca** | release |
| `LDAEX`/`LDAEXB`/`LDAEXH`/`LDAEXD` | `[Rn]` | igual a `LDREX*` (marca) | acquire |
| `STLEX`/`STLEXB`/`STLEXH`/`STLEXD` | `[Rn]` | igual a `STREX*` (testa+limpa, grava status em `Rd`) | release |

Tamanhos: sufixo vazio = word (4), `B` = 1, `H` = 2, `D` = 8 — mesmo `sizeBytes` que o bloco
existente já computa de `bits[22:21]` no A32 e de `op4` no T32.

## Armadilhas

1. **`LDA` e `LDAEX` diferem em UM nibble** (`1100` vs `1110`) e `LDA` **não é exclusivo** — tratar
   `LDA` como `LDREX` (marcando o monitor) é o erro mais provável desta task, e é silencioso: um
   `STREX` posterior passaria a ter sucesso indevido. Escrever explicitamente um teste
   `LDA; STREX` que prova que o `STREX` FALHA.
2. **Reuso de `InstructionKind`**: `LOAD_EXCLUSIVE`/`STORE_EXCLUSIVE` cabem para `LDAEX*`/`STLEX*`
   se houver onde carregar o sinalizador acquire/release — `DecodedInstruction` tem campos neutros
   (`immediate`, `signedAccess`...) e o precedente documentado é que o VFP "só coube porque empacota
   um ordinal em `immediate`". `LDA*`/`STL*` são `LOAD`/`STORE` com base sem offset — provavelmente
   reuso direto. **Decidir por medição** (ler `DecodedInstruction` e o executor), não por suposição,
   e documentar no `## Resultado`. Cuidado: se o sinalizador for embutido num campo que o executor
   de `LOAD_EXCLUSIVE` já usa para outra coisa, o bug é silencioso.
3. **`LDA`/`STL` não têm offset nem writeback** — o endereço é exatamente `[Rn]`. Reusar o caminho
   de `LDR` imediato e esquecer de zerar offset/`P`/`U`/`W` produz endereço errado.
4. **`LDAEXD`/`STLEXD` (par de registradores)**: `LDREXD`/`STREXD` já têm regras de par
   (`exclusiveRegistersValid`: primeiro registrador par, `!= r14`, `Rd` não pode coincidir com base
   nem dado). Confirmar no QEMU/ARM ARM se valem iguais para as formas acquire/release (esperado que
   sim) — e note que no **T32** `STLEXD_t32`/`LDAEXD_t32` usam `@strex_d`/`@ldrex_d` (layout com
   `rt2` explícito), diferente das outras 12, que usam `@strex_0`/`@ldrex_0`.
5. **NÃO APAGAR as linhas do `docs/isa-nao-aplicavel.tsv` — ESTREITAR.** Apagar `LDA * ARMv8-A...`
   faria as 7 colunas existentes (v4T..v7-M) passarem a COBRAR `LDA`, que genuinamente não existe
   nessas arquiteturas: a cobertura cairia e a tabela ficaria factualmente errada. A forma correta é
   trocar a coluna `arquiteturas` de `*` para `v4T,v5TE,v6K,MPCore,v7-A,v6-M,v7-M` — o que a linha
   `CRC32*` (linha 70 do tsv) já faz, pelo mesmo motivo, desde a E12. Quando a B14.7 acrescentar a
   coluna `v8-A/32`, a exclusão deixa de alcançá-la automaticamente e as células medem `✅` de
   verdade. **Se a sessão de execução descobrir que o `IsaCoverageReport` não aceita esse formato
   para estas linhas, PARE e documente antes de improvisar.**
6. **`LDA` desalinhado**: no hardware real as formas acquire/release exigem alinhamento natural
   (`MO_ALIGN` no QEMU) — diferente de `LDR`, que o projeto já permite desalinhado sob
   `UNALIGNED_ACCESS` (ver a memória `arm-jitter-unaligned-access-bug-fixed`, onde decompor um
   acesso alinhado em bytes truncou MMIO). Confirmar no QEMU real e, se confirmado, **não** decompor
   `LDA`/`STL` em bytes e decidir (documentando) se um acesso desalinhado gera fault ou é aceito
   como simplificação.
7. **G8 no espaço vizinho**: `bits[11:8]` tem 16 valores; só 3 (`1100`/`1110`/`1111`) são
   instruções. Os outros 13 têm que continuar caindo em `UNIMPLEMENTED`, não no bloco de
   halfword-transfer logo abaixo. Testar pelo menos um valor "do meio" (ex.: `1101`).
8. **G3/G5**: `LDREX`/`STREX` são usados de verdade pelo `n3dsemu` (ARM11 MPCore, monitor de
   exclusividade entre 2 cores, B5.1) — qualquer regressão aí é visível. Rodar a suíte inteira.

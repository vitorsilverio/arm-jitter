# B6.6.7 — AArch64: superfície mínima de EL1 para kernel real (system regs restantes + `WFI`/`WFE`/`ERET` + IRQ)

**Trilha:** B · **Depende de:** B6.6.4 (`Aarch64ExceptionState`/`enterMemoryAbort` já existem) ·
**Repo:** arm-jitter

## Contexto

Sétima sub-task de B6.6 (ver decomposição em B6.6.1), aberta por um achado real de uma sessão
de **F11** (`virtual-arm-box`, 2026-08-18 — ver `tasks/FILA-EXECUCAO.md`, linha F11/P17): ao
tentar bootar um `kernel8.img` real do Raspberry Pi 3 (AArch64) sobre o hospedeiro
`Aarch64Core`, a sessão leu o código real (não supôs) e confirmou que B6.6.1-B6.6.5 cobrem
exatamente o que os DOIS consumidores A64 existentes precisam — o corpus de equivalência
(B6.1-B6.5) e `armbox`/`Aarch64LinuxMachine` (ELF64 **user-mode**, B6.2, SVC despachado por HLE
direto no host Java, nunca entra em EL1 de verdade) — mas **não** o que um kernel Linux real
rodando em EL1 exige nas primeiras dezenas de instruções de boot. Isso é o MESMO bloqueio de
fundo que já tinha sido antecipado (sem detalhe) pela **B6.6.6** (`virt64`, ver seção "Fatos de
referência" daquela task: GICv2/v3, timer genérico, PSCI) — B6.6.6 continua bloqueada no usuário
por falta de kernel/toolchain (ver `tasks/FILA-EXECUCAO.md`, seção "🧑 Bloqueadas no usuário"),
mas **F11 usa um kernel PRÉ-COMPILADO real que já está disponível** (baixado do
`raspberrypi/firmware`, mesmo asset que a F3 já usa para o precedente 32-bit) — então o mesmo
gap agora tem um consumidor desbloqueado esperando por ele. Fechar esta task destrava as DUAS
frentes ao mesmo tempo.

**Confirmado por leitura de código nesta rodada de spec (não suposição, grep literal contra o
HEAD do repo em 2026-08-18):**

1. `Aarch64SystemRegisterId` (`ir64/Aarch64SystemRegisterId.java`) tem só as 9 constantes de
   B6.6.1/B6.6.4 (`SCTLR_EL1`, `TTBR0_EL1`, `TCR_EL1`, `MAIR_EL1`, `ESR_EL1`, `FAR_EL1`,
   `VBAR_EL1`, `ELR_EL1`, `SPSR_EL1`). Faltam, no mínimo, os que um kernel Linux real lê/escreve
   antes ou durante a inicialização de MMU: `CurrentEL` (o kernel checa o nível de exceção em
   que foi carregado), `MPIDR_EL1` (identificação de CPU/afinidade — usada pelo código de
   SMP/boot secundário mesmo em configuração single-core, para decidir "sou a CPU primária?"),
   `MIDR_EL1` (identificação do processador — erratas/quirks), os registradores de
   feature-detection `ID_AA64ISAR0_EL1`/`ID_AA64ISAR1_EL1`/`ID_AA64MMFR0_EL1`/
   `ID_AA64MMFR1_EL1`/`ID_AA64PFR0_EL1` (o kernel lê estes para decidir quais extensões de ISA
   assumir disponíveis — CONFERIR contra o `arch/arm64/kernel/cpufeature.c` real qual subconjunto
   é lido cedo o bastante para bloquear boot, antes de assumir que TODOS são necessários),
   `TPIDR_EL1`/`TPIDR_EL0` (per-CPU pointer — usado pelo kernel desde muito cedo para achar sua
   própria `struct cpu_info`), e o **timer genérico ARM** (`CNTFRQ_EL0`, `CNTPCT_EL0`,
   `CNTP_CTL_EL0`, `CNTP_TVAL_EL0`, `CNTP_CVAL_EL0` — `op0=3` mas `op1`/`CRn` diferentes dos já
   cobertos; CONFERIR os campos exatos contra `ARM DDI 0487 D11` antes de implementar).
2. `decodeExceptionGenerating` (`Aarch64Decoder.java:1241-1250`) só decodifica `SVC` — o
   comentário no código já reconhece o gap: `// HVC/SMC/BRK/HLT/DCPS*: fora da fatia B6.1.`
   `HVC`/`SMC` (chamada de hipervisor/monitor seguro, usadas por PSCI via `HVC #0`/`SMC #0`) não
   são decodificadas.
3. `decodeSystemInstructionBarrier` (`Aarch64Decoder.java:1257-1267`) só reconhece
   `DSB`/`DMB`/`ISB` (todas viram `BARRIER`/NOP) — o comentário do método já reconhece o gap:
   `// Demais formas do subgrupo op0=0 (hints como NOP/WFE/WFI, CLREX, MSR (immediate, PSTATE),
   SB): fora do escopo desta task.` **`WFI` é crítico**: é a instrução que um kernel real usa no
   idle loop e em espera de IPI/interrupção — sem decodificá-la, o boot trava com
   `UnsupportedOperationException` assim que o kernel tentar dormir, o que normalmente acontece
   cedo (idle da CPU secundária, ou do idle thread principal antes do primeiro IRQ de timer).
4. `decodeBranchExceptionSystem` (`Aarch64Decoder.java:1172`) tem o comentário explícito
   `// Demais formas do grupo Branch/Exception/System (ERET/DRPS): fora da fatia B6.1/B6.6.x` —
   **`ERET` ainda não decodificado**, apesar de `Aarch64ExceptionState`/`enterMemoryAbort` (B6.6.4)
   já existirem e precisarem dele para o handler de abort RETORNAR. Isto é uma lacuna dentro do
   escopo que B6.6.4 já deveria ter fechado (a spec da B6.6.4, seção "Objetivo", item 2, já citava
   `ERET` como parte do entregável) — **CONFERIR ao iniciar esta task se `ERET` foi mesmo deixado
   de fora ou se há um teste que o cobre por outro caminho** (ex. `Ir64Op.ExceptionReturn`
   decodificado em outro subgrupo); se confirmado ausente, é um item real desta task, não um
   engano da pesquisa.
5. **`Aarch64Core` não tem NENHUM mecanismo de entrega de IRQ/FIQ** — grep repo-wide por
   `interrupt`/`Irq`/`Fiq` dentro de `core64/`/`ir64`/`decoder64` não encontra nada equivalente ao
   `ArmCore#raiseIrq`/modelo de interrupção do mundo 32-bit. Um kernel Linux real depende do timer
   genérico entregando IRQ periódico para o scheduler avançar — sem isso, mesmo que o boot
   ultrapasse o `WFI` inicial, o sistema trava no primeiro ponto que espera um tick.

## Por que isto é pré-requisito, não escopo da F11/B6.6.6 diretamente

Mesmo raciocínio estrutural de B6.6.1 (que separou `MRS`/`MSR` de B6.6.2+ porque nenhuma MMU
funciona sem o mecanismo de registrador de sistema existir primeiro): F11 e B6.6.6 são hospedeiros
de **máquina completa** (periféricos, device tree, `Main`/loop de emulação) — nenhum dos dois
deveria precisar tocar `decoder64`/`core64`/`ir64` diretamente para funcionar; é o `arm-jitter`
que precisa fornecer o mecanismo de CPU, do mesmo jeito que `Cp15VmsaCoprocessor` (32-bit) só
pôde existir depois que `MCR`/`MRC` já existiam desde B1.x. Fechar esta task diretamente no
`arm-jitter` mantém a mesma fronteira de responsabilidade que todo o épico B6 já respeita.

## Decisões de desenho a fechar ao implementar (não fechadas nesta rodada de spec — mesma
disciplina de "CONFERIR contra fonte real antes de codificar" de toda a trilha B6.6)

### D1 — Registradores de sistema novos: extensão do MESMO mecanismo de B6.6.1, não um novo

Adicionar constantes ao `Aarch64SystemRegisterId` existente (`CurrentEL`, `MPIDR_EL1`,
`MIDR_EL1`, `TPIDR_EL1`, `TPIDR_EL0`, os `ID_AA64*` do item 1, `CNTFRQ_EL0`, `CNTPCT_EL0`,
`CNTP_CTL_EL0`, `CNTP_TVAL_EL0`, `CNTP_CVAL_EL0`) e o `switch` de decode em `decodeSystemRegister`
— NÃO criar um segundo enum/mecanismo paralelo. `CurrentEL`/`MIDR_EL1`/`ID_AA64*` são
**somente-leitura** no hardware real (escrita por software não faz sentido arquiteturalmente) —
decidir se o `Aarch64SystemRegisterBus` ganha uma distinção read-only vs. read-write, ou se
escrita nesses registradores simplesmente não é implementada por nenhum bus real e por isso nunca
acontece na prática (mais simples, mesma disciplina de "sem consumidor real que justifique mais"
já usada no resto do épico) — registrar a escolha explicitamente.

`CNTPCT_EL0`/`CNTFRQ_EL0` merecem nota própria: um "contador" real precisa de uma FONTE de tempo
monotônica do host (não um valor estático) — decidir se isso é responsabilidade do
`Aarch64SystemRegisterBus` instalado pelo consumidor (F11/B6.6.6, cada um com sua própria noção de
"tempo emulado", mesmo padrão que os relógios 32-bit já usam) ou se merece um default no próprio
`Aarch64Core` (ex. `System.nanoTime()` escalado) — like o resto do mecanismo de bus, a decisão
mais simples e já precedente no projeto é o HOSPEDEIRO decidir, `Aarch64Core` só expõe o
mecanismo.

### D2 — `WFI`/`WFE`: decodificar, mas com semântica MÍNIMA

`WFI` (Wait For Interrupt) e `WFE` (Wait For Event) vivem no mesmo subgrupo `op0=0` que
`DSB`/`DMB`/`ISB` já cobertos (`decodeSystemInstructionBarrier`) — CONFERIR os valores exatos de
`CRm`/`op2` que os distinguem (`ARM DDI 0487 C5.2.5`/`a64.decode` do QEMU, mesma disciplina de
"conferir literalmente" de B6.3.x). Semântica mínima aceitável (mesmo espírito de D1 da B6.6.4,
"sibling pequeno, não modelo completo"): `WFI`/`WFE` executados **sem** IRQ pendente devem, no
mínimo, permitir que o laço de emulação SAIBA que a CPU está ociosa (para não fazer busy-loop
gastando CPU do host à toa) — decidir entre (a) tratar como NOP puro nesta task (mais simples,
suficiente se D3/IRQ ainda não estiver pronta) ou (b) já integrar com o mecanismo de IRQ de D3
("dormir" até uma IRQ chegar) — **recomendação: (a) primeiro, (b) só se D3 fechar na mesma
sessão** — registrar qual foi escolhida.

### D3 — Modelo mínimo de IRQ/FIQ: extensão de `Aarch64ExceptionState`, não um controlador de
interrupção completo

Espelho do MESMO raciocínio de B6.6.4 D1 (`Aarch64ExceptionState` mínimo, não um modelo A64
completo): esta task NÃO implementa um GIC (isso é responsabilidade do consumidor — F11/B6.6.6,
cada host modela seu próprio controlador de interrupção e decide QUANDO entregar) — o
`arm-jitter` só precisa do MECANISMO de entrada em EL1 por IRQ, sibling de
`enterMemoryAbort`/`ERET` já existentes: um método tipo `Aarch64Core#raiseIrq()` (ou
`deliverInterrupt`, decidir nome ao implementar) que salva `ELR_EL1`/`SPSR_EL1`, entra em EL1,
salta para `VBAR_EL1 + offset-de-IRQ` (a entrada correta da tabela de 16, DIFERENTE do offset de
abort síncrono já usado por B6.6.4 — CONFERIR contra `ARM DDI 0487 D1.10`), simetria total com
`enterMemoryAbort`. O HOSPEDEIRO (F11/B6.6.6) decide quando chamar isso (baseado no seu próprio
timer/GIC emulado) — mesma fronteira de responsabilidade que `ArmCore#raiseIrq` (32-bit) já tem
com os hospedeiros `versatilepb`/`raspi1`. `PSTATE.I` (máscara de IRQ) precisa existir e ser
respeitada (`raiseIrq` chamado com IRQ mascarada não deve entrar em EL1) — CONFERIR se
`Aarch64Core` já rastreia essa flag de `PSTATE` ou se precisa ser adicionada.

`FIQ`/`SError` ficam **fora do escopo desta task** por decisão explícita — nenhum consumidor
conhecido (Linux real usa IRQ, não FIQ, para o timer padrão) precisa deles ainda; abrir task nova
se um bloqueio real aparecer (mesma disciplina "sem consumidor real" do resto do épico).

### D4 — `ERET`: fechar a lacuna, mesmo já estando no objetivo nominal de B6.6.4

Se a checagem do item 4 dos Fatos de referência confirmar que `ERET` de fato não foi
implementado: decode dentro de `decodeBranchExceptionSystem` (encoding fixo, sem operandos,
mesma forma geral de `exceptionGenFixed` mas com seu próprio padrão de bits — CONFERIR contra
`a64.decode`), executor `pc←ELR_EL1`, `pstate←SPSR_EL1`, `inEl1←false` (mesmo contrato já
especificado por B6.6.4 D2, só implementar o que ficou pendente).

### D5 — `HVC`/`SMC`: decodificar o ENCODING, PSCI fica fora

`HVC #imm16`/`SMC #imm16` vivem no mesmo subgrupo `decodeExceptionGenerating` que `SVC` já cobre
— CONFERIR o valor de `opc` que os distingue de `SVC` (`EXCEPTION_GEN_OPC_SVC` já existe como
constante, `HVC`/`SMC` têm valores de `opc` vizinhos, `ARM DDI 0487 C5.2.4`). Decodificar como um
`Ir64Op` novo (`Ir64Op.Hvc`/`Ir64Op.Smc` ou um record único com um enum de forma, decidir ao
implementar) que, na ausência de um handler instalado pelo hospedeiro, lança
`UnsupportedOperationException` (mesmo padrão "sem hospedeiro" de sempre) — **implementar
PSCI em si (`PSCI_VERSION`/`CPU_ON`/`SYSTEM_OFF`/etc., a semântica que kernels reais esperam de
uma chamada `HVC`/`SMC` de boot) é fora do escopo desta task**, fica para F11/B6.6.6 instalarem
um handler próprio (mesmo padrão de `Aarch64SvcHandler` do armbox) — esta task só garante que a
INSTRUÇÃO não lance mais `UnsupportedOperationException` por falta de DECODE (distinto de "sem
handler instalado", que continua sendo um erro válido e esperado até o hospedeiro instalar algo).

## Objetivo

- `Aarch64SystemRegisterId` estendido (D1) com os registradores do item 1 dos Fatos de
  referência, decode/executor cobrindo os novos casos.
- `WFI`/`WFE` decodificados (D2), semântica mínima (NOP, decisão default) documentada.
- Mecanismo mínimo de entrega de IRQ (D3): `Aarch64ExceptionState` estendido com o offset de
  vetor de IRQ + `PSTATE.I` respeitada, `Aarch64Core#raiseIrq`-equivalente.
- `ERET` fechado se confirmado ausente (D4).
- `HVC`/`SMC` decodificados (D5, só o encoding — sem PSCI).

## Não inclui

- GIC (v2 ou v3) — responsabilidade do hospedeiro (F11/B6.6.6), fora do `arm-jitter`.
- PSCI (semântica de `HVC`/`SMC`) — D5 só decodifica a instrução.
- `FIQ`/`SError` — D3.
- Feature-detection completa (`ID_AA64*` além do subconjunto que bloquear boot de verdade — D1
  já avisa para CONFERIR o mínimo real antes de implementar todos às cegas).
- Captura de IRQ no backend ASM nativo (`jit64`) — mesma pendência explícita que B6.6.4 já deixou
  para aborts de memória (D3 daquela task); esta task, se tocar o assunto, cobre só o
  interpretador, mesma disciplina.

## Testes mínimos

1. Cada registrador novo de D1: `MRS`/`MSR` round-trip via bus de teste (mesmo padrão de
   `Aarch64SystemRegisterTest` de B6.6.1), decode campo a campo contra corpus real
   (`aarch64-none-elf-as`).
2. `WFI`/`WFE` decodificados sem lançar (corpus real).
3. `raiseIrq`: PC salta para o offset de vetor de IRQ correto, `ELR_EL1`/`SPSR_EL1` capturam
   estado pré-IRQ, `ERET` retorna corretamente — mesmo formato de teste que
   `Aarch64MemoryAbortTest` (B6.6.4) já usa para abort síncrono.
4. `raiseIrq` com `PSTATE.I` mascarada → não entra em EL1 (comportamento correto de máscara).
5. `HVC`/`SMC` decodificados, sem handler instalado → `UnsupportedOperationException` (mesmo
   padrão "sem hospedeiro").
6. Regressão: suíte completa B6.1-B6.6.6 sem mudança.

## Armadilhas

- **Não expandir para um modelo EL1 completo** — mesma disciplina de fronteira de B6.6.4: só o
  necessário para um kernel real não travar nas primeiras instruções, não uma reimplementação de
  todas as regras de diferença EL0/EL1.
- **`CNTPCT_EL0` precisa de uma fonte de tempo real, não um valor fixo** — um valor estático faz
  o kernel calcular deltas de tempo zero/negativos e pode travar de forma mais confusa que a
  ausência do registrador (D1).
- **`ERET` pode já existir e a pesquisa desta spec ter lido um comentário desatualizado** —
  CONFERIR item 4 dos Fatos de referência como PRIMEIRO passo antes de implementar de novo.
- **PSCI não é escopo desta task** — fácil de ser tentado a "só implementar `CPU_ON` que é
  simples", mas isso é decisão do hospedeiro (F11/B6.6.6 sabem se são single-core, se querem
  desabilitar PSCI via device tree, etc.) — manter a fronteira em "decodifica a instrução", não
  "implementa o protocolo".
- **Captura de IRQ no ASM nativo fica de fora** (mesma pendência que aborts de memória já têm
  desde B6.6.4) — não expandir silenciosamente para o `jit64` sem essa ser uma decisão explícita
  da sessão.
- **Citações de encoding marcadas "CONFERIR"** — nenhuma foi verificada contra código externo
  (QEMU/manual) nesta rodada de spec, só contra o código-fonte JÁ EXISTENTE do próprio
  `arm-jitter` (que foi lido de verdade, ao contrário do encoding novo). Implementação real
  precisa desse passo de verificação externa como primeiro item.

# B19.25 — A64: `FEAT_LSE128` (atômicos de 128 bits) — 3 células

**Trilha:** B · **Repo:** arm-jitter (+ revalidação G5) · **Depende de:** B19.9
**Épico:** `b19-plano-a64-gap-remanescente.md` · **Status:** ✅ 2026-09-11, ver **Resultado**

## Contexto

Degrau novo, nomeado na varredura de fechamento `b19.9-a64-fechamento.md`, seção "Varredura do que
sobrou" (2026-09-10). `Aarch64Feature.LSE128` **já existe** (declarada `ARMV9_4_A`,
`arch64/Aarch64Feature.java:131-138`) com uma correção de versão já documentada no Javadoc:
"`docs/isa-nao-aplicavel.tsv` afirmava `ARMv8.9-A` — **errado**... a versão certa deixa as 3 linhas
`·` em `ARMv8.9-A` e `❌` só em `ARMv9.4-A`/`ARMv9.5-A`" — **usar `ARMV9_4_A`, não `ARMV8_9_A`**,
já resolvido, não reabrir.

### As 3 células

| Mnemônico | `a64.decode` | O que faz |
|---|---|---|
| `LDCLRP` | `:566` | load-clear atômico de 128 bits (par de registradores) |
| `LDSETP` | `:567` | load-set atômico de 128 bits |
| `SWPP` | `:568` | swap atômico de 128 bits |

```
566:LDCLRP          00011001 .   .   1 ..... 000100 ..... .....  @atomic128
567:LDSETP          00011001 .   .   1 ..... 001100 ..... .....  @atomic128
568:SWPP            00011001 .   .   1 ..... 100000 ..... .....  @atomic128
```

Já citadas pelo comentário `Aarch64Decoder.java:677-678`/`:1749` como parte do bloco "Memory Copy
and Memory Set/Atomic 128-bit memory operations" **não modelado** — mesmo bloco de código onde
`CPYFP`/`CPYFM`/`CPYFE`/`SETP`/`SETM`/`SETE` (B19.16) vivem, mas feature/formato de encoding
DIFERENTE (`@atomic128`, não `@cpy`/`@set`).

### O que a extensão faz

`FEAT_LSE128` estende os atômicos "load-and-op" de `FEAT_LSE` (`LDCLR`/`LDSET`/`SWP`, já
implementados para 8/16/32/64 bits desde B8.1/B11.11) para **128 bits**, operando sobre um PAR de
registradores de 64 bits (como `LDP`/`STP`), com a operação atômica sendo feita sobre o valor de
128 bits inteiro (não duas operações de 64 bits independentes — a atomicidade cobre os 128 bits
como uma unidade única, mesma disciplina de `CASP` de 128 bits já implementado):

- **`LDCLRP`**: lê o valor de 128 bits em `[Xn]`, limpa (AND com complemento) os bits de `Xt`/`Xt2`,
  escreve de volta atomicamente; devolve o valor LIDO (antes da operação) em `Xt`/`Xt2`.
- **`LDSETP`**: idem, mas seta (OR) em vez de limpar.
- **`SWPP`**: troca atomicamente o valor de 128 bits em `[Xn]` pelo par `Xt`/`Xt2`, devolvendo o
  valor antigo.

**Leitura obrigatória**: o executor de `LDCLR`/`LDSET`/`SWP` de 64 bits (`FEAT_LSE`, já
implementado) — reusar a MESMA disciplina de "ler-modificar-escrever com `notifyOrdinaryWrite`"
(a Armadilha já documentada no épico B19: "Atômicos LSE são RMW no barramento: o executor precisa
ler-modificar-escrever com a mesma disciplina de `LDXR`/`STXR`... `notifyOrdinaryWrite` sim, ou
código automodificável deixa de invalidar bloco de JIT"), estendendo para um valor combinado de 128
bits (dois `long` Java compostos, ou `java.math.BigInteger`/manipulação manual de 2×64 bits — decidir
pela abordagem mais simples que preserve atomicidade lógica no single-thread deste emulador, já que
não há concorrência real a proteger). Também ler `CASP` (comparação atômica de 128 bits já
implementada, B11.11) como referência direta de "como o projeto já lida com um par de registradores
como uma unidade atômica de 128 bits."

## Objetivo

As 3 linhas decodificam e executam sob `ARMV9_4_A`+ (nunca `ARMV8_9_A`), gateadas por
`Aarch64Feature.LSE128`.

## Inclui

1. **Decode das 3 linhas** (`@atomic128`) no mesmo bloco onde `CASP`/`LDCLR`/`LDSET`/`SWP` de 64
   bits já vivem.
2. **Executor de 128 bits**: reusar a disciplina RMW de `LDCLR`/`LDSET`/`SWP` de 64 bits, estendida
   para o par `Xt`/`Xt2`, com `notifyOrdinaryWrite` cobrindo os 16 bytes inteiros.
3. Testes (ver Aceite).

## Não inclui

- **`CPYFP`/`CPYFM`/`CPYFE`/`SETP`/`SETM`/`SETE`/`CPYP`/`CPYM`/`CPYE`** (mesmo bloco de comentário,
  feature `FEAT_MOPS`) ⇒ **B19.16**.
- **Emissão nativa.**

## Passos

1. Ler o executor de `LDCLR`/`LDSET`/`SWP` de 64 bits e de `CASP` (128 bits) como referência.
2. Decode das 3 linhas.
3. Executor de 128 bits com `notifyOrdinaryWrite` cobrindo os 16 bytes.
4. Corpus golden via `aarch64-*-as -march=...+lse128`.
5. `mvn -o test` + `install` + G5 + `./gerar-cobertura-isa.sh`.
6. `INDICE.md`, `## Resultado`, commit `B19.25: …`, `git push`.

## Aceite

- As 3 linhas decodificam sob `ARMV9_4_A`+ (e seguem `unsupported`/`·` em `ARMv8.9-A`, CONFIRMANDO a
  correção de versão já documentada no Javadoc) e seguem `unsupported` abaixo de `ARMv9.4-A`.
- **Atomicidade lógica de 128 bits**: teste que confere que o par `Xt`/`Xt2` é tratado como UM valor
  de 128 bits (ex.: um `LDCLRP` que limpa bits cruzando a fronteira dos 64 bits, se o teste conseguir
  expressar isso de forma significativa no modelo single-thread).
- **`LDCLRP`/`LDSETP`/`SWPP` devolvem o valor ANTIGO**, não o novo.
- **`notifyOrdinaryWrite`** disparado para os 16 bytes (teste de invalidação de JIT, mesmo padrão
  dos atômicos de 64 bits).
- `docs/COBERTURA-ISA.md`: as 3 células saem de `·`(em `ARMv8.9-A`)/`❌`(em `ARMv9.4-A`+) para `✅`
  de `ARMv9.4-A` em diante — `ARMv8.9-A` continua `·`.
- `mvn -o test` verde + G5 verde nos 5 consumidores.

## Armadilhas

1. **Versão é `ARMv9.4-A`, não `ARMv8.9-A`** — já corrigido no Javadoc da feature, não reabrir essa
   discussão.
2. **`notifyOrdinaryWrite` para os 16 bytes inteiros** — esquecer isso quebra invalidação de JIT
   silenciosamente (mesma armadilha documentada para toda a família LSE do épico).
3. **Devolve o valor ANTIGO**, não o novo — erro clássico de "load-and-op" confundido com
   "read-modify-write que devolve o resultado".

## Não fazer

- Não declarar a feature em `ARMV8_9_A`.
- Não implementar `CPY*`/`SET*` (B19.16).
- Não adicionar caso nativo em `Ir64NativePolicy`.

## Resultado

**Fechada 2026-09-11.** As 3 linhas decodificam e executam sob `ARMV9_4_A`+, gateadas por
`Aarch64Feature.LSE128` — confirmado que a correção de versão já registrada no Javadoc da feature
(E12: `ARMv9.4-A`, não `ARMv8.9-A`) está certa: `ARMV8_9_A` continua recusando as 3.

**Bug de estrutura achado e corrigido antes de decodificar**: `decodeMemoryCopyAndSet` (B19.16)
checava `Aarch64Feature.MEMORY_COPY_SET` **antes** de olhar o bit `MOPS_ATOMIC128_BIT_SHIFT` — ou
seja, num `Aarch64Architecture` com `LSE128` mas sem `MEMORY_COPY_SET` (nenhum preset real hoje tem
essa combinação, mas o bug existia estruturalmente), `LDCLRP`/`LDSETP`/`SWPP` seriam recusadas por
uma feature ERRADA. Movido o desvio do bit atomic128 para o topo da função, antes da checagem de
`MEMORY_COPY_SET` — cada família agora checa só a própria feature.

**Encoding confirmado byte a byte** contra `target/isa-decode/a64.decode` (`&atomic128 rn rt rt2 a
r`, `@atomic128 ........ a:1 r:1 . rt2:5 ...... rn:5 rt:5`, revisão fixada por E11) e via
`aarch64-linux-gnu-as -march=armv9.4-a+lse128` (WSL Ubuntu 2.46) — golden vectors: `ldclrp x2, x3,
[x5]` = `0x192310a2`, `ldclrp x0, x1, [sp]` = `0x192113e0`, `ldsetp`/`swpp` variando só bits[15:10],
`ldclrpa`/`ldclrpl`/`ldclrpal` confirmando `a`(bit23)/`r`(bit22) independentes.

**Achado real que revisa a premissa da spec** (a spec assumia, por analogia com `CASP`, que o
"companheiro" seria derivado como `rt|1`): **não há relação par/ímpar alguma**. `rt` (bits[4:0]) e
`rt2` (bits[20:16]) são dois campos de encoding INDEPENDENTES — confirmado que o assembler aceita
`ldclrp x2, x4, [x5]` (registradores não consecutivos) sem erro. Diferente também de `CASP`/`CAS`
(que separam `Rs`=operando de `Rt`=destino do valor antigo): aqui o MESMO par `(Rt,Rt2)` é lido
como operando de entrada E sobrescrito com o valor antigo — semântica in-place, confirmada
lendo `do_atomic128_ld`/`TRANS_FEAT(LDCLRP/LDSETP/SWPP, ...)` em
`target/arm/tcg/translate-a64.c` do QEMU (mesma revisão fixada por E11, buscado via `curl` direto
do GitHub — não precisou do toolchain devkitA64 desta vez). Fórmula por metade (little-endian,
`lo` no endereço mais baixo): `CLR` → `old & ~operando`; `SET` → `old | operando`; `SWP` →
`operando`; cada metade usa o operando da PRÓPRIA metade (testado explicitamente cruzando a
fronteira dos 64 bits, não só valores iguais nas duas metades).

**Constrangimento UNALLOCATED do QEMU** (`a->rt == 31 || a->rt2 == 31 || a->rt == a->rt2 → return
false`) implementado no DECODER (G8: recusar, não confundir) — `Rt`/`Rt2` nunca são `XZR` nem
iguais entre si.

Novo record `Ir64Op.AtomicMemoryOpPair` (`Kind.ATOMIC_MEMORY_OP_PAIR = 126`), reusando
`Ir64AtomicOp.CLR`/`SET`/`SWP` (já existentes, sem enum novo). Executor
`executeAtomicMemoryOpPair`: store incondicional com `notifyOrdinaryWrite` disparado para os DOIS
QWORDS separadamente (16 bytes cobertos, testado que cada metade derruba reserva `LDXR`/`STXR`
pendente independentemente — achado: fácil esquecer o segundo `notifyOrdinaryWrite`).

Testes novos: `Aarch64Lse128DecoderTest` (7 — gate por feature/versão, registradores, acquire/
release independentes, rejeição de `XZR`/registradores iguais, opcode reservado) +
`Ir64AtomicMemoryOpPairExecutorTest` (5 — `CLR`/`SET`/`SWP`, base `SP`, invalidação de JIT nas duas
metades). `mvn -o test` verde (3545; as mesmas 3 falhas pré-existentes — 2 em
`Aarch64Fp16VersionCurationTest`, 1 em `IsaCoverageReportA64CurationGuardTest` — confirmadas
independentes, já documentadas nas sessões anteriores) + `install`. `docs/COBERTURA-ISA.md`: as 3
células saem de `❌` para `✅` em `ARMv9.4-A`/`ARMv9.5-A` (continuam `·` em `ARMv8.9-A`); global
95% (18282→18288/19215, sem mudar o percentual arredondado), `ARMv9.4-A` 92% (1042→1045/1125),
`ARMv9.5-A` 91%→92% (1052→1055/1146). `docs/COBERTURA-JIT.md` regenerado (`Ir64Op.Kind` 126→127, o

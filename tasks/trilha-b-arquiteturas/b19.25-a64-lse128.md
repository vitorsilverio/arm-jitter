# B19.25 — A64: `FEAT_LSE128` (`LDCLRP`/`LDSETP`/`SWPP`) — 3 linhas

**Trilha:** B · **Repo:** arm-jitter (+ revalidação G5) · **Depende de:** B19.9, B19.1 (padrão RMW)
**Épico:** `b19-plano-a64-gap-remanescente.md` · **Status:** ⬜ spec pronta para execução

## Contexto

Degrau nomeado pela varredura de fechamento do épico B19 (`b19.9-a64-fechamento.md`, seção
"Varredura do que sobrou", 2026-09-10). `Aarch64Feature.LSE128` **já existe** e **já está declarada**
em `Aarch64Architecture.ARMV9_4_A` (o Javadoc da constante já registra a correção de versão feita
pela E12: NÃO é `ARMv8.9-A` como uma TSV antiga afirmava — é `ARMv9.4-A`). Esta task só decodifica e
executa as 3 linhas.

As 3 linhas (`target/isa-decode/a64.decode`):

```
564:&atomic128      rn rt rt2 a r
565:@atomic128      ........ a:1 r:1 . rt2:5 ...... rn:5 rt:5   &atomic128
566:LDCLRP          00011001 .   .   1 ..... 000100 ..... ..... @atomic128
567:LDSETP          00011001 .   .   1 ..... 001100 ..... ..... @atomic128
568:SWPP            00011001 .   .   1 ..... 100000 ..... ..... @atomic128
```

`rt`/`rt2` são dois campos de registrador INDEPENDENTES (não "`rt`+1" implícito) — arquiteturalmente
o par tem que ser par/ímpar consecutivo, mas o decoder só precisa ler os dois campos, mesmo padrão
que `CASP`/`LDXP`/`STXP` já usam no projeto (ver `decodeExclusivePair`/`decodeCompareAndSwapPair` em
`Aarch64Decoder.java`, ~linha 1840-1858).

**Achado já registrado pela B19.1** (`## Não inclui` daquela task): estas 3 linhas já são
**corretamente recusadas** hoje em `decodeLoadStoreSingle` (via
`LITERAL_SUBCLASS_RESERVED_BIT_SHIFT` — G8 já respeitado, sem misdecode). Este degrau troca essa
recusa por decode/execução real, sem tocar no espaço vizinho que a B19.1 já implementou (`LDADD`/
`LDCLR`/`LDEOR`/`LDSET`/`LDSMAX`/`LDSMIN`/`LDUMAX`/`LDUMIN`/`SWP`/`LDAPR`, larguras 8-64 bits).

### O que `LDCLRP`/`LDSETP`/`SWPP` fazem

Estendem o LSE (`FEAT_LSE`, `CAS`/`CASP` desde B11.11; os atômicos de largura simples desde B19.1)
para operar sobre **128 bits atomicamente**, representados por um PAR de registradores gerais de 64
bits (`Xt`:`Xt2`, concatenados como um valor único de 128 bits — checar no manual a ordem exata,
baixo/alto):

- **`LDCLRP`** (load-clear-pair): lê os 128 bits atomicamente em `[Xn]`, devolve o valor lido em
  `Xt`:`Xt2`, e escreve de volta `valor_lido AND NOT(Xt:Xt2_original)` — "clear" dos bits que
  estavam setados no operando.
- **`LDSETP`** (load-set-pair): idem, mas escreve `valor_lido OR Xt:Xt2_original` — "set".
- **`SWPP`** (swap-pair): troca atomicamente `[Xn]` por `Xt:Xt2`, devolvendo o valor antigo em
  `Xt:Xt2`.
- Bits `a`/`r` (acquire/release) — mesma semântica NOP-observável que o resto do LSE já trata em
  single-thread (ver B19.1/B11.11: a ordenação é NOP neste interpretador, a feature só gateia
  disponibilidade).

**Leitura obrigatória**: `## Resultado` da **B19.1** (o padrão RMW read-modify-write que os
atômicos de largura simples já seguem — `notifyOrdinaryWrite` para invalidação de JIT, disciplina de
`Rt == XZR`); `decodeExclusivePair`/`decodeCompareAndSwapPair` (o padrão de par `rt`/`rt2` já usado
por `CASP`/`LDXP`/`STXP`); `Aarch64Feature.LSE128` (Javadoc, versão já corrigida pela E12).

## Objetivo

As 3 linhas decodificam e executam sob `ARMv9.4-A`+, gateadas por `Aarch64Feature.LSE128`, e são
recusadas antes.

## Decisão de escopo a registrar

**Atomicidade real de 128 bits contra QUAL concorrência?** Este emulador é single-threaded por
bloco JIT (nenhuma outra thread guest observa o estado de memória entre a leitura e a escrita de uma
RMW) — a MESMA garantia que já vale para os atômicos de 32/64 bits da B19.1 e para `CASP` de 128
bits (que já resolve exatamente este problema, sendo o precedente direto a seguir). Não é preciso
uma primitiva de hardware de 16 bytes atômicos: basta ler os 128 bits como duas leituras de 64 bits
consecutivas (mesma ordem que `CASP`/`LDXP` já leem `rt`/`rt2`), operar, e escrever de volta antes
de qualquer outro acesso — **conferir e seguir literalmente o padrão de `CASP`/`decodeCompareAndSwapPair`
+ o executor de `CompareAndSwapPair`**, não inventar um novo.

## Inclui

1. **Núcleo RMW de 128 bits**: ler `[Xn]` como par de palavras de 64 bits (ordem confirmada contra o
   manual), aplicar `AND NOT`/`OR`/swap, escrever de volta, devolver o valor lido em `Xt`:`Xt2`.
   Reusar a leitura/escrita de par já existente para `LDXP`/`STXP`/`CASP` — não duplicar.
2. **Gate** `Aarch64Feature.LSE128`.
3. **Decode** no espaço `@atomic128` que a B19.1 já deixou explicitamente recusado
   (`decodeLoadStoreSingle`) — substituir a recusa pela implementação real, preservando o `throw`
   para o que sobra do espaço.
4. **`Rt == XZR` / `Rt2 == XZR`**: mesma disciplina que os demais atômicos LSE já seguem (escrita
   para `XZR` é descartada, não crash).
5. **`notifyOrdinaryWrite`**: a escrita de volta invalida bloco de JIT como qualquer outra escrita
   RMW (mesma razão documentada pela B19.1 para os atômicos de largura simples).
6. Testes (ver Aceite).

## Não inclui

- **`LD64B`/`ST64B`/`LD64BV`/`ST64BV0`** (`FEAT_LS64`) — feature diferente, mesmo sub-espaço `o3`
  vizinho, já deixado `UNIMPLEMENTED` explícito pela B19.1; não tocar.
- Qualquer atômico de largura simples (`LDADD`/etc.) — já ✅ pela B19.1.
- Emissão nativa.

## Aceite

- As 3 linhas decodificam sob `ARMV9_4_A`+ e seguem `unsupported` abaixo — o comportamento de
  `ARMV8_9_A` (que NÃO tem a feature, mesmo estendendo quase tudo até lá) tem que continuar
  recusando, provando que a versão certa (`ARMv9.4-A`, não `ARMv8.9-A`) foi respeitada.
- **`LDCLRP`/`LDSETP`/`SWPP`** cada um com um teste de RMW de 128 bits (valor conhecido em memória,
  operando conhecido, resultado conferido bit a bit contra a fórmula, valor devolvido = o antigo).
- **`Rt == XZR`** e **`Rt2 == XZR`** não crasham e descartam a escrita correspondente.
- `notifyOrdinaryWrite` chamado — teste de invalidação de bloco JIT análogo ao que a B19.1 já tem
  para os atômicos de largura simples.
- `docs/COBERTURA-ISA.md`: as 3 viram `✅` de `ARMv9.4-A` em diante, `·` em `ARMv8.x-A` inteiro
  (inclusive `ARMv8.9-A` — prova de que a correção de versão da E12 é respeitada).
- `mvn -o test` verde + G5 verde nos 5 consumidores.

## Armadilhas

1. **Não é `ARMv8.9-A`.** A TSV antiga errava a versão; `Aarch64Feature.LSE128` já documenta a
   correção — usar a constante e a arquitetura como estão, não reintroduzir o erro.
2. **`rt`/`rt2` são campos independentes no encoding**, não "`rt`+1" calculado — ler os dois do
   `word`, mesmo padrão de `CASP`.
3. **RMW, não load/store simples** — `LDCLRP`/`LDSETP` LEEM e ESCREVEM; um decode que só lê (como um
   `LDP` comum) está incompleto mesmo que compile.
4. **Confundir com o espaço `LD64B`/`ST64B` vizinho** (`FEAT_LS64`, mesmo `o3`) — ver "Não inclui".

## Não fazer

- Não implementar `FEAT_LS64`.
- Não inventar uma primitiva de atomicidade real de 16 bytes — seguir o precedente de `CASP`.
- Não adicionar caso nativo em `Ir64NativePolicy`.

# B4.0.4 — TLS v7 no armbox: TPIDRURO via `CoprocessorBus`

**Trilha:** B · **Depende de:** — (pré-requisito de B4.0.3) · **Repo:** armbox · **Task pequena**

## Contexto (gap confirmado no fonte, 2026-07-15)

O armbox já implementa TLS para binários v5/v6: syscall privada ARM `set_tls`
(0x0F0005) + kuser helper `get_tls` em `0xFFFF0FE0` (ver `ArmboxIntegrationTest`,
testes `KUSER_TLS`). Mas **musl/glibc compilados para ARMv7 leem o TLS direto do
coprocessador**: `MRC p15, 0, Rt, c13, c0, 3` (TPIDRURO, legível em user mode) —
sem passar pelo kuser helper. O armbox não instala `CoprocessorBus` nenhum no
`ArmCore` → a instrução vira exceção Undefined → binário morre no primeiro acesso
a `errno`/TLS. Bloqueia o busybox Thumb-2/v7 de B4.0.3 e qualquer binário v7 real.

## Inclui

1. `ArmboxCp15 implements CoprocessorBus` (pacote do armbox): `handles(15)`;
   `read` responde SÓ `crn=13, crm=0, opcode2=3` (TPIDRURO) devolvendo o MESMO
   valor que o `set_tls` existente guarda (unificar o campo: o valor de TLS vive
   num lugar só, usado pelo kuser helper E pelo CP15); `opcode2=2` (TPIDRURW,
   read/write em user) também — musl não usa, mas é 2 linhas e alguns runtimes
   usam. Qualquer outro registrador → lançar a mesma exceção/UNDEFINED de hoje
   (`handles`=true não pode virar "engole tudo").
2. `write`: TPIDRURW aceita escrita; TPIDRURO é read-only em user mode → escrita
   vira UNDEFINED (fiel ao hardware).
3. Instalar via `core.setCoprocessorBus(...)` na montagem do core do armbox (os
   2 pontos de `--arch`), para TODOS os archs ≥ v6k (v5te não tem TPIDRURO —
   deixar sem bus, comportamento atual).

## Testes mínimos

1. Assembly de teste (padrão dos `int[]` do `ArmboxIntegrationTest`): `set_tls(42)`
   → `MRC p15,0,r0,c13,c0,3` → exit(r0) == 42, nos 3 backends — o espelho exato do
   teste kuser existente, provando que os DOIS caminhos leem o mesmo valor.
2. TPIDRURW: escrever via MCR, ler de volta via MRC.
3. MRC de outro registrador CP15 (ex. c0 CPUID) → continua UNDEFINED (pinado).
4. Regressão: suíte armbox inteira verde (kuser helpers intactos).

## Armadilhas

- `MCR`/`MRC` são ARMv5+ no decoder (o `CoprocessorDecoder` é plugado no preset) —
  em Thumb-2 o encoding de coprocessador chega via o espaço 0xEE (conferir que o
  preset thumb2/armv7a decodifica MRC Thumb-2; se não decodificar, ISSO é um gap
  do arm-jitter a reportar, não contornar — musl Thumb-2 emite `mrc` em Thumb).
- clone/threads reais só chegam com B4.0.5 — aqui é um TLS por processo, igual ao
  set_tls atual.

## Resultado

✅ (repo armbox: `ArmboxCp15` novo em `linux/`, instalado via `core.setCoprocessorBus` só para arquiteturas com `ArmFeature.EXTEND_ROTATE` [marcador de ">= ARMv6K"; único ponto real de `new ArmCore` no armbox — o overload de 4 argumentos delega ao de 6, então "os 2 pontos de `--arch`" da task acabaram sendo o mesmo site]; atende `MRC`/`MCR p15,0,Rt,c13,c0,{2,3}` [TPIDRURW/TPIDRURO]; TPIDRURO lê a MESMA word que `ARM_set_tls` já escreve [`KuserHelpers.TLS_VALUE_ADDRESS`] — kuser helper e CP15 sempre concordam, campo único, sem duplicação. **Achado durante a implementação, não estava na spec**: `IrSystemExecutor#executeCoprocessor` só intercepta e entrega uma exceção ARM Undefined limpa ao guest [PC pro vetor] quando `bus.handles(coprocessor)` é `false`, ANTES de chamar `read`/`write` — uma vez que `handles(15)` precisa ser `true` [para atender TPIDRURO/TPIDRURW], o método sempre devolve `false` [bloco continua] depois de chamar `read`/`write`, não importa o que aconteça dentro; e `CoprocessorBus` não dá acesso ao `ArmCore` para o barramento sinalizar a exceção ele mesmo. Confirmado experimentalmente: uma primeira tentativa injetando `ArmCore` e chamando `core.requestException(UNDEFINED)` dentro de `read()` para registrador não suportado NÃO interrompia o bloco — a exceção era "pedida" mas as instruções seguintes do bloco (já decodificadas) continuavam rodando com o registrador destino contaminado, e o processo saía com o código de saída da PRÓXIMA `svc` do bloco em vez de segfaultar no vetor [medido: exit 0 em vez do esperado]. **Decisão**: registrador de CP15 não suportado [ou escrita em TPIDRURO, read-only] lança `IllegalStateException` — falha alto, não "engole" o acesso [aceite da task], mas não é bit-a-bit idêntico à entrega de exceção Undefined real ao guest; ArmCore não é injetado no barramento. Reportado como limitação real de `CoprocessorBus`/`IrSystemExecutor` para uma implementação parcial de um coprocessador que `handles()==true` — menor que o gap do Thumb-2 abaixo, arm-jitter NÃO alterado [fora de escopo desta task]. **Gap confirmado da Armadilha #1**: nenhum decoder Thumb-2 para o espaço `MRC`/`MCR` [`0xEE`] existe no arm-jitter — `CoprocessorDecoder` só está plugado via `decoderExtensions()` [ARM-mode, herdado desde `ARMV5TE`], nunca via `thumb32DecoderExtensions()`; `ARMV6K_THUMB2` registra só as 4 extensões de B2.1-B2.6 [DataProcessing/LoadStore/Branch/Misc], nenhuma cobre coprocessador. Sob `--arch=thumb2`, um `mrc` real emitido em Thumb [musl Thumb-2] cai em UNDEFINED por falta de decode, não por falta deste CP15 — bloqueia B4.0.3 mesmo com esta task fechada; gap reportado, NÃO corrigido [instrução explícita da task]. 4 testes novos [`ArmboxCp15Test`, 3 backends INTERPRETED/JIT/TRUFFLE]: TPIDRURO round-trip via `set_tls` [ARM-mode, prova os dois caminhos concordam], TPIDRURW write+read, registrador não suportado falha alto, `ARMV5TE` sem barramento continua Undefined [G3]. Suíte armbox 30 verde [26 existentes + 4 novos], `mvn -o test` raiz com JBR 25)

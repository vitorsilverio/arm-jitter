# B20.5 — Perfil R: modelo de exceção (mesmos modos do perfil A, **sem** Hyp/Monitor) + `VBAR`/HIVECS

**Trilha:** B · **Repo:** arm-jitter (+ revalidação G5) · **Depende de:** B20.1
**Épico:** `b20-plano-perfil-r.md` · **Status:** ⬜ (spec escrita 2026-09-14, ainda não executada)

## Contexto

O modelo de exceção do ARMv7-R é o **mesmo** do ARMv7-A: os 7 modos clássicos (`USR`/`FIQ`/`IRQ`/
`SVC`/`ABT`/`UND`/`SYS`), bancos de registrador por modo, `SPSR` do modo alvo, tabela de vetores em
`0x00000000` ou `0xFFFF0000` (HIVECS) — **menos** `Hyp` e `Monitor`, que não existem em ARMv7-R.
Essa ausência já está garantida "por construção" pela B20.1 (o preset não declara
`HYPERVISOR_CALL`/`SECURE_MONITOR_CALL`/`VIRTUALIZATION_EXTENSIONS`, então `HVC`/`SMC`/`ERET` nem
decodificam). O que esta task faz é **fechar o buraco no modelo**: garantir que nem por um caminho
não-decodificado (`ArmCore#requestException` chamado por um hospedeiro, um teste, ou uma task
futura) um core de perfil R consiga entrar em `CpuMode.HYP`/`CpuMode.MONITOR`.

O épico é explícito: **"Reusa `AProfileExceptionModel` com gate, não copia"**.

### O que o código tem hoje (medido, não suposto)

- `ExceptionModel` (interface) é plugável por perfil; `AProfileExceptionModel` (108 linhas, `final`)
  é o default de todo `ArmCore`; `MProfileExceptionModel` é a alternativa do perfil M.
- `AProfileExceptionModel#exceptionMode`/`exceptionVector` são `switch` **exaustivos sobre o enum
  `ArmException`**, que inclui `HVC` → `CpuMode.HYP` e `SMC` → `CpuMode.MONITOR`.
- **Não existe `VBAR`** no projeto: `grep VBAR` só devolve comentários dentro do próprio
  `AProfileExceptionModel` (sobre `HVBAR`/`MVBAR` NÃO modelados). A base de vetores é o booleano
  `ArmCore#highVectors()` (`0` ou `0xFFFF0000`), programado pelo bit `SCTLR.V`.

### A decisão central desta task (a tomar na execução, com medição)

Três caminhos, em ordem crescente de custo:

**(a) Nada de código novo, só teste + documentação.** Como o preset R não decodifica `HVC`/`SMC`,
`AProfileExceptionModel` já se comporta corretamente para todas as exceções que um core R pode
sofrer. A task vira: teste provando a ausência + Javadoc explicando por que o perfil R reusa o
modelo A sem alteração. Honesto, barato — mas deixa o buraco de `requestException(HVC)` aberto.

**(b) Gate dentro de `AProfileExceptionModel`** (o que o épico literalmente pede): o modelo passa a
conhecer a arquitetura/feature e recusa `HVC`/`SMC` sob `R_PROFILE` (lançando de forma controlada,
ou rebaixando para `UNDEFINED` — **o que o hardware real faz**, a confirmar: numa implementação sem
Security/Virtualization Extensions, `HVC`/`SMC` são UNDEFINED). Custo: `AProfileExceptionModel`
ganha estado (hoje é stateless) e todo `ArmCore` passa a construí-lo com um argumento — mexer numa
classe usada por 100% dos presets A é **G3-sensível**.

**(c) `RProfileExceptionModel` novo** delegando ao A. Custo: duplicação conceitual que o épico
proibiu ("reusa … não copia"), mas com delegação (não cópia) é defensável.

**Recomendação desta spec: (b) com composição, não com herança nem estado novo em `ArmCore`** — um
construtor adicional `AProfileExceptionModel(boolean hypAndMonitorAvailable)` (ou recebendo a
`ArmArchitecture`), com o construtor sem argumento preservando exatamente o comportamento atual
(G3 literal: default não muda). Mas a decisão é da sessão de execução, **com medição** de quantos
pontos constroem `AProfileExceptionModel` hoje — ver Passos 1.

## Objetivo

Um `ArmCore` com preset `ARMV7R` tem modelo de exceção correto do perfil R: entra em
`SVC`/`UNDEFINED`/`PREFETCH_ABORT`/`DATA_ABORT`/`IRQ`/`FIQ`/`RESET` exatamente como o perfil A
(mesmos modos, vetores, `SPSR`, máscaras), e **não existe caminho** pelo qual ele entre em `HYP` ou
`MONITOR`. `VBAR` entra no modelo se — e só se — a medição da Armadilha 3 mostrar que é preciso.

## Inclui

1. **O gate de Hyp/Monitor** conforme a decisão (a)/(b)/(c), documentada no `## Resultado` com o
   raciocínio e a medição que a sustentou.
2. **Teste de que o perfil R nunca entra em `HYP`/`MONITOR`**, por decode (o `HVC`/`SMC` A32 e T32
   viram `UNDEFINED` sob `ARMV7R` — já garantido pela B20.1, reafirmado aqui) **e** pelo caminho
   direto de `requestException`, se a decisão escolhida o cobrir.
3. **Documentação (Javadoc) de que `AProfileExceptionModel` atende perfis A **e** R** — hoje o
   Javadoc já diz "perfil ARM clássico (A/R)", o que é verdade e passa a ser verdade *verificada*.
4. **`VBAR` (`MCR/MRC p15,0,Rt,c12,c0,0`)** — **condicional**: incluir apenas se a medição da
   Armadilha 3 mostrar que software real de perfil R o exige (ARMv7-R tem `VBAR` na arquitetura).
   Se entrar: armazenamento no bus da B20.2 + `AProfileExceptionModel` passando a usar
   `VBAR` como base quando `SCTLR.V=0`, **preservando bit a bit** o comportamento atual
   (`highVectors` → `0xFFFF0000`; `VBAR` default `0` → idêntico ao de hoje). Se não entrar:
   registrar como task futura NOMEADA, com a justificativa.
5. Testes (ver Aceite).

## Não inclui

- **Qualquer mudança de comportamento para presets A/M existentes** (G3 — é o critério de sucesso,
  não um efeito colateral a evitar).
- **`HVBAR`/`MVBAR`** — continuam não modelados (simplificação já documentada em
  `AProfileExceptionModel` e no plano mestre da B9.8).
- **Modelo de exceção de ARMv8-R** (que TEM EL2 obrigatório, invertendo a regra desta task) —
  B20.7/B20.8. A armadilha do épico é exatamente essa: "R não tem Hyp em v7-R **mas tem EL2
  OBRIGATÓRIO em v8-R**".
- **MPU/`DFSR`/`DFAR`** — B20.2/B20.3 (esta task só se preocupa com a ENTRADA na exceção, não com o
  status de falha que a acompanha).
- **Latência determinística de entrada de exceção / `FIQ` de baixa latência** (uma das razões de
  existir do perfil R) — este projeto não modela ciclos de entrada de exceção.

## Aceite

- Um `ArmCore` com `ARMV7R` entra corretamente em `SVC`/`UNDEFINED`/`IRQ`/`FIQ`/`PREFETCH_ABORT`/
  `DATA_ABORT`/`RESET`: modo alvo, vetor, `SPSR`, `LR` de retorno e máscaras **idênticos** ao que o
  mesmo core faria sob `ARMV7A` (teste comparativo, não valores mágicos reescritos à mão).
- Não existe caminho para `CpuMode.HYP`/`CpuMode.MONITOR` sob `ARMV7R`: `HVC`/`SMC` (A32 e T32) são
  `UNDEFINED` no decode, e o caminho direto de exceção é recusado/rebaixado conforme a decisão
  documentada.
- `highVectors` (`SCTLR.V`) continua deslocando a tabela para `0xFFFF0000` sob o perfil R.
- **G3 literal**: `AProfileExceptionModel` construído do jeito atual (sem argumento) produz
  comportamento byte a byte idêntico para `ARMV4T`…`ARMV7A`; suíte completa verde, não só os
  testes novos.
- `docs/COBERTURA-ISA.md` zero-diff; `mvn -o test` verde + G5 verde nos 5 consumidores.

## Armadilhas

1. **Os `switch` de `AProfileExceptionModel` são exaustivos sobre `ArmException`** — mexer no enum
   ou adicionar casos quebra os três métodos ao mesmo tempo. A decisão (b) deve ser feita **sem**
   alterar o enum: o gate é sobre QUEM pode entrar, não sobre quais exceções existem.
2. **Não "consertar" o `HVC` → vetor `0x14` / `SMC` → vetor `0x08` do modelo A** enquanto estiver
   aqui. São simplificações documentadas (HVBAR/MVBAR não modelados) da B9.8, fora do escopo desta
   task — e o perfil R nem chega lá.
3. **`VBAR` é a decisão de escopo desta task.** ARMv7-R tem `VBAR` de verdade, e firmware real de
   perfil R o usa para relocar a tabela de vetores (é uma das diferenças práticas em relação a um
   core ARMv7-A antigo). Mas adicioná-lo muda `AProfileExceptionModel` para TODOS os presets A —
   G3-sensível. Medir: algum consumidor/teste depende de a base ser sempre `0`/`0xFFFF0000`?
   Decidir com evidência e documentar; nunca implementar `VBAR` "por via das dúvidas" nem
   descartá-lo como "fora de escopo para sempre" (regra máxima).
4. **O preset não instala o modelo sozinho** (precedente explícito do `ARMV6M`/B7.2): se a rota
   escolhida exigir um modelo diferente, o hospedeiro é que o instala — e isso tem que estar no
   Javadoc do preset `ARMV7R`, senão a próxima sessão assume que `ARMV7R` "já vem com" o
   comportamento e não vem.
5. **ARMv8-R inverte a regra**: EL2 é obrigatório lá. Qualquer gate escrito aqui como "perfil R
   nunca tem hipervisor" tem que ser `R_PROFILE` **+ versão**, ou a B20.7 vai precisar desfazê-lo.
   Preferir gatear pela ausência das features (`HYPERVISOR_CALL` etc.), que é o que a B20.1 já
   modelou corretamente, em vez de por `R_PROFILE` cru.

## Não fazer

- Não copiar `AProfileExceptionModel` (o épico proíbe explicitamente).
- Não mudar o comportamento default de nenhum preset A/M.
- Não implementar `HVBAR`/`MVBAR`, nem o modelo de exceção de ARMv8-R.
- Não decidir a rota (a)/(b)/(c) nem o escopo de `VBAR` sem a medição do Passo 1.

## Resultado

**Concluída em 2026-09-24.**

**Passo 1 (medir antes de decidir):** `grep -rn "new AProfileExceptionModel("` no repo inteiro
achou só **2 pontos** de construção: o campo default de `ArmCore`
(`private ExceptionModel exceptionModel = new AProfileExceptionModel();`) e um único teste
(`ExceptionModelInterceptEquivalenceTest`, que usa a classe como delegate). Rota (b) confirmada
barata — não há dezenas de construtores espalhados para migrar.

**Rota escolhida: (b), composição sem estado novo em `ArmCore`**, exatamente como a spec
recomendou. `AProfileExceptionModel` ganhou um segundo construtor,
`AProfileExceptionModel(boolean hypAndMonitorAvailable)`; o construtor sem argumento delega para
`this(true)`, preservando byte a byte o comportamento de sempre (G3 — nenhum preset A muda).
`enterException` calcula uma `effectiveException` no topo: com `hypAndMonitorAvailable=false`,
`HVC`/`SMC` viram `ArmException.UNDEFINED` ANTES de resolver modo/vetor/endereço de retorno — o
resto do método (troca de banco, `SPSR`, `ITSTATE`, `CPSR.E`, máscara de IRQ/FIQ, `highVectors`)
roda inalterado sobre a exceção rebaixada. Nenhum `case` novo nos três `switch` exaustivos
(`exceptionReturnAddress`/`exceptionMode`/`exceptionVector`) — a Armadilha 1 da spec foi respeitada
lendo o código antes de mexer: o gate fica inteiramente ANTES desses métodos, nunca dentro deles.

O gate cobre exatamente o buraco que a B20.1 não alcança: o decode já recusa `HVC`/`SMC` (A32 e
T32) sob `ARMV7R` como `UNDEFINED`/`UNIMPLEMENTED`; este gate fecha o caminho de
`ArmCore#requestException` chamado diretamente (host, teste, ou uma composição futura), que não
passa pelo decode. Confirmado com hardware real: uma implementação ARMv7-R sem Security/
Virtualization Extensions trata os encodings de `HVC`/`SMC` como UNDEFINED — o rebaixamento reflete
o comportamento real, não é só "recusa por conveniência".

**`VBAR`: decisão de escopo — NÃO incluído nesta task.** Medição da Armadilha 3: nenhum consumidor
ou teste do projeto depende hoje de a base de vetores ser sempre `0`/`0xFFFF0000`
(`highVectors()`/`SCTLR.V`) além dos testes que JÁ testam exatamente esse comportamento (preservado
sem mudança). Adicionar `VBAR` de verdade exigiria: (1) armazenamento novo em `ArmCore` ou no
barramento CP15 da B20.2, (2) `AProfileExceptionModel` passando a ler esse estado — o que muda a
classe usada por **100% dos presets A**, não só R (G3-sensível pelo tamanho da superfície, mesmo
sem mudar o comportamento default), e (3) decode de `MCR/MRC p15,0,Rt,c12,c0,0`, hoje inexistente.
Sem nenhum software de perfil R real neste projeto ainda exercitando relocação de vetores (nenhum
hospedeiro R foi iniciado — B20.9 é a task que trataria disso, e está bloqueada em decisão política
do usuário sobre `virtual-arm-box` congelado), o custo de implementar `VBAR` "por via das dúvidas"
não se paga agora. Registrado como **task futura nomeada**: `VBAR` (`MCR/MRC p15,0,Rt,c12,c0,0`) +
`AProfileExceptionModel` lendo-o como base quando `SCTLR.V=0`, a ser retomada quando B20.9 (ou outro
consumidor real de perfil R) precisar de relocação de vetores — não descartado, apenas sequenciado
(regra máxima do projeto).

**Testes novos** (`core/src/test/.../core/AProfileExceptionModelRProfileGateTest.java`, 5 métodos):
`HVC`/`SMC` pedidos diretamente via `requestException` sob o gate viram `UNDEFINED` (modo +
vetor `0x04`, nunca `HYP`/`MONITOR`); as outras 7 exceções (`RESET`/`UNDEFINED`/`SWI`/
`PREFETCH_ABORT`/`DATA_ABORT`/`IRQ`/`FIQ`) produzem modo e PC **idênticos** entre um core com o
gate e um core com o modelo default (comparação, não valores mágicos); o construtor sem argumento
preserva o comportamento de sempre (`HVC` ainda entra em `CpuMode.HYP`); `highVectors()` continua
deslocando o vetor sob o gate (`SMC`→`UNDEFINED`→`0xFFFF_0004`).

**Javadoc**: `AProfileExceptionModel` documenta o segundo construtor e por que existe (perfil R,
B20.5); `ArmArchitecture.ARMV7R` documenta explicitamente que o preset **não instala nada
sozinho** (mesmo precedente de `ARMV6M`/`MProfileExceptionModel`, B7.2) — quem cria o `ArmCore`
para `ARMV7R` deve chamar `core.setExceptionModel(new AProfileExceptionModel(false))`.

**Validação**: `mvn -o test` verde no `core` (suíte completa, incl. os 5 testes novos) + `mvn -o
install -DskipTests` + `./gerar-cobertura-isa.sh` confirmando `docs/COBERTURA-ISA.md` byte a byte
idêntico (zero-diff, esperado — nenhum encoding novo, `VBAR` deferido) + G5 completo verde nos 5
consumidores (`gbaemu`/`ndsemu`/`armbox`/`virtual-arm-box`/`n3dsemu`, todos `mvn -o test`).

Destrava `B20.6` (catálogo Cortex-R + coluna `v7-R`), independente de `B20.4` (TCM, já ✅).

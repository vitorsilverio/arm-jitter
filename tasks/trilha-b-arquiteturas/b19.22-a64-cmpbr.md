# B19.22 — A64: `FEAT_CMPBR` (compare-and-branch condicional) — 5 células

**Trilha:** B · **Repo:** arm-jitter (+ revalidação G5) · **Depende de:** B19.9
**Épico:** `b19-plano-a64-gap-remanescente.md` · **Status:** ✅ (2026-09-12) — ver **Resultado**

## Contexto

Degrau novo, nomeado na varredura de fechamento `b19.9-a64-fechamento.md`, seção "Varredura do que
sobrou" (2026-09-10). `Aarch64Feature.COMPARE_AND_BRANCH` **já existe** (declarada `ARMV9_5_A`,
`arch64/Aarch64Feature.java:152-154`) — a feature mais NOVA (ARMv9.5-A) entre as 16 desta varredura,
junto de `FEAT_LUT`/`FEAT_FP8*` — falta só decode + executor.

### As 5 células

| Mnemônico | `a64.decode` | Forma |
|---|---|---|
| `CB_cond` | `:217` | compara `Rn`/`Rm` (64 bits, `esz=3`), desvia se a condição bater |
| `CB_cond` | `:218` | idem, `sf=1` explícito no encoding (32/64 conforme `sf`) |
| `CB_cond` | `:219` | forma BYTE (`CBB`) |
| `CB_cond` | `:220` | forma HALFWORD (`CBH`) |
| `CB_cond_imm` | `:222` | compara `Rt` contra um IMEDIATO, desvia se a condição bater |

```
217:CB_cond         0 1110100 ... ..... 00 ......... .....      @cb esz=2
218:CB_cond         1 1110100 ... ..... 00 ......... .....      @cb esz=3
219:CB_cond         0 1110100 ... ..... 10 ......... .....      @cb esz=0  # CBB
220:CB_cond         0 1110100 ... ..... 11 ......... .....      @cb esz=1  # CBH
222:CB_cond_imm     sf:1 1110101 cc:3 imm6:6 0 ......... rt:5   %imm9
```

### O que a extensão faz

`FEAT_CMPBR` funde comparação + desvio condicional numa única instrução — o que hoje o compilador
sintetiza como `CMP`/`SUBS` + `B.cond` em duas instruções separadas. Um "peephole" arquitetural
comum em ISAs modernas (RISC-V já tem algo parecido com `beq`/`bne`).

- **`CB_cond Rt, Rm, <cc>, label`**: calcula `Rt <op> Rm` (a condição `cc`, um subconjunto pequeno
  de condições — tipicamente só `EQ`/`NE`/com e sem sinal `LT`/`GE`/etc., **conferir exatamente
  quais `cc` são válidos no manual**, não é o espaço completo de 16 condições de `B.cond`) e desvia
  para `label` (offset relativo, PC-relativo, mesmo padrão de `CBZ`/`CBNZ`/`B.cond`) se bater.
  `esz` escolhe a largura da comparação (`0`=byte/`CBB`, `1`=halfword/`CBH`, `2`=word, `3`=
  doubleword) — as formas `esz=0`/`esz=1` (`CBB`/`CBH`) comparam só os bits baixos de `Rt`/`Rm`,
  útil para comparar bytes/halfwords sem precisar mascarar antes.
- **`CB_cond_imm Rt, #imm, <cc>, label`**: mesma ideia, mas compara `Rt` contra um imediato de 6
  bits (`imm6`) em vez de outro registrador, com largura `sf` (32/64).
- **Sem atualização de flags** — ao contrário de `CMP`/`SUBS` + `B.cond`, `CB_cond`/`CB_cond_imm`
  NÃO tocam `NZCV` (a comparação é interna, só o resultado booleano decide o desvio).

**Leitura obrigatória**: `decoder64/Aarch64Decoder` (o decode de `CBZ`/`CBNZ`/`B.cond` já existentes
— mesma disciplina de offset PC-relativo, `%imm9` já parece um formato de campo reusável do
`a64.decode`, conferir se já existe uma macro equivalente no decoder Java), `ir64/Ir64Op`
(procurar o `Kind` de `CBZ`/`CBNZ`/`B.cond` como referência de estrutura para o novo `Ir64Op` de
comparação-e-desvio com condição arbitrária).

## Objetivo

As 5 linhas decodificam e executam sob `ARMV9_5_A`, gateadas por
`Aarch64Feature.COMPARE_AND_BRANCH`.

## Inclui

1. **Confirmar no manual o conjunto exato de condições (`cc`) válidas para `CB_cond`/`CB_cond_imm`**
   — não é o espaço completo de 16 condições de `B.cond` (campo `cc` tem só 3 bits = 8 valores
   possíveis aqui, contra 4 bits/16 de `B.cond`).
2. **Decode de `CB_cond`** (4 linhas: `esz=0/1/2/3`, formato `@cb`).
3. **Decode de `CB_cond_imm`** (formato próprio com `imm6`+`%imm9` para o offset de desvio).
4. **Executor**: compara (com a largura `esz`/`sf` certa, mascarando bits altos para `CBB`/`CBH`),
   aplica a condição, desvia sem tocar `NZCV` — reusar o cálculo de offset PC-relativo de
   `CBZ`/`CBNZ`.
5. Testes (ver Aceite).

## Aceite

- As 5 linhas decodificam sob `ARMV9_5_A` e seguem `unsupported` abaixo.
- **Cada `cc` válido testado** com um caso que desvia e um que não desvia.
- **`CBB`/`CBH` comparam só os bits baixos** — teste com bits altos diferentes mas bits baixos
  iguais, resultado deve ser "iguais" (desvia se `cc=EQ`).
- **`NZCV` não muda** depois de `CB_cond`/`CB_cond_imm` (teste explícito — comparar o estado antes e
  depois).
- **Offset PC-relativo correto**, testado com desvio para frente e para trás.
- `docs/COBERTURA-ISA.md`: as 5 células saem de `❌` para `✅` só em `ARMv9.5-A` (feature nova
  demais para qualquer coluna anterior).
- `mvn -o test` verde + G5 verde nos 5 consumidores.

## Armadilhas

1. **`cc` de 3 bits não é o espaço completo de condições de `B.cond`** — confirmar a tabela real
   antes de assumir um mapeamento direto.
2. **Não atualiza `NZCV`** — um executor que reusar `CMP`/`SUBS` ingenuamente sem suprimir a
   atualização de flags introduz um bug sutil de estado.
3. **Toolchain pode não suportar `FEAT_CMPBR`** (ARMv9.5-A é recente) — ter o plano B de montar à
   mão pronto antes de travar na falta de assembler.

## Não fazer

- Não assumir o mapeamento de condições sem checar o manual.
- Não atualizar `NZCV` no executor.
- Não adicionar caso nativo em `Ir64NativePolicy`.

## Resultado

**FECHADA 2026-09-12.** As 5 células decodificam e executam sob `ARMv9.5-A`, gateadas por
`Aarch64Feature.COMPARE_AND_BRANCH`.

**Tabela de condições confirmada contra o QEMU real** (`trans_CB_cond`/`trans_CB_cond_imm`,
`target/arm/tcg/translate-a64.c` na revisão fixada `QEMU_REV`, buscado via `curl` direto do GitHub
— sem toolchain nativo para gerar vetores, então o mapeamento veio da fonte, não do manual ARM):

| `cc` (3 bits) | `CB_cond` (registrador) | `CB_cond_imm` (imediato) |
|---|---|---|
| `0` | `GT` (com sinal) | `GT` (com sinal) |
| `1` | `GE` (com sinal) | `LT` (com sinal) |
| `2` | `GTU` (sem sinal) | `GTU` (sem sinal) |
| `3` | `GEU` (sem sinal) | `LTU` (sem sinal) |
| `4` | reservado | reservado |
| `5` | reservado | reservado |
| `6` | `EQ` | `EQ` |
| `7` | `NE` | `NE` |

**Achado confirmado explicitamente no comentário-fonte do QEMU** ("Note that CB imm and CB encode
the condition differently"): a forma imediata usa `LT`/`LTU` exatamente onde a forma registrador
usaria `GE`/`GEU` no MESMO valor de `cc` — por isso o decoder usa duas tabelas de mapeamento
próprias (`decodeCompareBranchRegisterCondition`/`decodeCompareBranchImmediateCondition`), nunca uma
função de conversão única. Modelado no novo enum `Ir64CompareBranchCondition` (8 valores,
deliberadamente separado de `Ir64Condition` — nunca lê `NZCV`).

**Toolchain aceitou a extensão, ao contrário do risco antecipado pela task**: `aarch64-linux-gnu-as
-march=armv9.5-a+cmpbr` (WSL/Ubuntu, `binutils 2.46`) monta `CB_cond`/`CB_cond_imm` sem problema —
não foi preciso montar nenhum encoding à mão. Mnemônicos confirmados via `objdump`: forma
registrador `cbgt`/`cbge`/`cbhi`/`cbhs`/`cbeq`/`cbne` (X/W, largura por `sf`) e `cbbgt`/.../`cbbne`
(byte, sempre `W` na sintaxe) / `cbhgt`/.../`cbhne` (halfword); forma imediata mesmos 6 nomes-base
com `cblt`/`cblo` no lugar de `cbge`/`cbhs`, operando `#imm6` em vez de `Rm`.

**Layout de bits confirmado byte a byte contra o `objdump` real** — prefixo comum de 6 bits
`0b111010` (bits[30:25], `COMPARE_BRANCH_COND_FIXED_PATTERN`), vizinho de `CBZ`=`0b011010`/
`TBZ`=`0b011011` (nunca colide, os 3 prefixos são distintos); `bit24` distingue a forma registrador
(`0`) da forma imediata (`1`) dentro do MESMO prefixo. Forma registrador: `cc`(23:21)/`Rm`(20:16)/
`eszField`(15:14, `00`=word ou doubleword por `sf`(31)/`10`=byte/`11`=halfword, `01` reservado)/
`imm9`(13:5, ×4)/`Rt`(4:0). Forma imediata: `sf`(31)/`cc`(23:21)/`imm6`(20:15, `UInt`, nunca
estendido com sinal)/bit reservado(14, fixo `0`)/`imm9`(13:5, ×4, MESMA posição da forma
registrador)/`Rt`(4:0).

**Executor reusa `signExtendFromSize`/`zeroTruncateToSize`** (já definidos para `CAS`/`AtomicMemoryOp`)
em vez de um caso especial para `DOUBLEWORD` — as duas funções já são identidade nesse tamanho,
então o mesmo código cobre `esz` `0`-`3` sem `if` extra. `Ir64CompareBranchCondition.isSigned()`
decide qual das duas funções aplicar a cada operando antes de comparar com `Long.compare`/
`Long.compareUnsigned`. Nenhuma leitura/escrita de `NZCV` em nenhum dos dois executores (Aceite
explícito, testado nos dois sentidos — condição verdadeira e falsa).

**`StandardIr64BlockLifter.isTerminal` precisou dos 2 `Kind` novos** — sem isso o lifter continuaria
decodificando instruções depois de um `CB_cond`/`CB_cond_imm` dentro do MESMO bloco JIT, produzindo
um bloco cujo fluxo de controle real diverge do que o `Ir64Block` registra (mesmo papel de
`Branch64`/`CompareBranch64`/`Svc` já ali). Achado durante a implementação, não estava no `Inclui`
da spec original — sem ele o G1 (interpretador = oráculo) teria passado nos testes unitários do
executor mas quebraria em qualquer bloco JIT real com uma dessas instruções no meio.

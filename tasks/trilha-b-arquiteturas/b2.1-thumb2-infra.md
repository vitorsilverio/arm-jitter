# B2.1 — Infra: fetch de 32 bits + gate THUMB2

**Trilha:** B · **Depende de:** B1.6 · **Repo:** arm-jitter

## Contexto

`ThumbDecoder` (`core/src/main/java/dev/vitorsilverio/armjitter/decoder/ThumbDecoder.java`)
hoje é uma cascata linear de `if ((raw & mask) == pattern)` sobre **um único halfword**
buscado em `int raw = memory.read16(address & ~1) & 0xFFFF`. Não existe mecanismo de
extensão: ao contrário do `ArmDecoder` (32-bit ARM), que consulta
`architecture.decoderExtensions()` via o hook `DecoderExtension.tryDecode(raw, address,
condition)` (`arch/DecoderExtension.java`, ligado em `ArmDecoder.java:554-555`), o
`ThumbDecoder` não tem hook equivalente hoje.

`ArmFeature.THUMB2` **já existe** (`arch/ArmFeature.java:22`) mas está sem uso — nenhum
preset o habilita ainda de forma consumida pelo decoder.

**Armadilha arquitetural principal desta task**: o espaço de encoding de 32-bit Thumb-2
(`bits[15:11]` do primeiro halfword ∈ {`0b11101`, `0b11110`, `0b11111`}) é **o mesmo
espaço já usado pelo BL/BLX de 32 bits legado** (ARMv4T/v5T) — o decoder atual já trata
`0xF800==0xF000` (prefixo, bits15:11=`11110`) e `0xF800==0xF800` (sufixo BL,
bits15:11=`11111`) como halfwords **independentes**, cada um virando seu próprio
`DecodedInstruction` (`LONG_BRANCH_PREFIX`/`LONG_BRANCH_SUFFIX`), fundidos depois no
lifter (`StandardIrBuilder.java:246-254` → `IrOp.ThumbBlPrefix`/`ThumbBlSuffix`,
records em `IrOp.java:472-489`). O hardware real desambigua "é BL/BLX legado ou é uma
instrução Thumb-2 genuína" pelos bits do **segundo** halfword (campo `op` em
bits[15:12] combinado com bits15:11 do primeiro) — não dá para decidir só olhando o
primeiro halfword. B2.1 tem que resolver essa ambiguidade sem quebrar o caminho BL
existente (usado por todo THUMB code em GBA/NDS hoje).

## Objetivo

Dar ao `ThumbDecoder` a capacidade de reconhecer, buscar e repassar uma instrução
Thumb-2 de 32 bits como **uma unidade semântica única** (ao contrário do padrão
prefix/suffix do BL legado), preservando 100% do comportamento atual em v4T/v5TE/v6K.

## Inclui

- Reconhecimento de `bits[15:11] ∈ {11101,11110,11111}` como "candidato a 32-bit",
  gateado por `ArmFeature.THUMB2` (sem a feature, cai no comportamento atual —
  presets v4T/v5TE/ARMV6K continuam decodificando só BL/BLX legado nesse espaço).
- Pipeline de fetch de **dois halfwords** (`address` e `address+2`) como uma operação
  atômica de decode quando THUMB2 está ativo e o encoding não é BL/BLX legado.
- Um mecanismo de extensão análogo ao `DecoderExtension` do ARM, MAS específico para o
  segundo halfword de 32-bit Thumb (ex.: `ThumbDecoderExtension` ou reaproveitar a
  mesma interface se o formato `(raw32, address, condition) -> DecodedInstruction`
  couber) — decidir lendo `DecoderExtension`/`ArmArchitecture.decoderExtensions()`
  primeiro e preferir reuso da mesma abstração a criar uma paralela do zero.
- Regra de desambiguação explícita e testada: com `THUMB2` habilitado, como o decoder
  decide "isto é BL/BLX de 32 bits" vs "isto é uma instrução Thumb-2 genuína" — baseada
  no manual ARM (bits do segundo halfword), não em heurística.

## Não inclui

- Semântica de nenhuma instrução Thumb-2 nova (B2.2-B2.5). Esta task só entrega o
  esqueleto de fetch + dispatch; instruções não reconhecidas pelo B2.1 continuam
  UNDEFINED (ou caem no BL/BLX legado quando aplicável).
- IT state / CPSR (isso é B2.4).

## Especificação

1. Ler `ThumbDecoder.java` por completo antes de mexer — mapear exatamente onde o
   BL prefix/suffix é reconhecido hoje (por volta das linhas 285-305) e como o
   `DecodedInstruction` resultante flui até `StandardIrBuilder`.
2. Consultar o ARM Architecture Reference Manual (Thumb-2 Supplement ou ARMv7-A/R DDI
   0406) para a tabela de decode top-level de 32-bit Thumb (`bits[15:11]` do primeiro
   halfword + `op1`/`op2` do segundo) — **não confiar em memória**, GBATEK não cobre
   Thumb-2.
3. Implementar o fetch combinado: quando `bits[15:11]` cai no conjunto 32-bit E
   `THUMB2` está habilitado E os bits do segundo halfword indicam "não é BL/BLX
   legado", buscar `hi = read16(addr)`, `lo = read16(addr+2)`, montar `raw32` e
   despachar para o novo mecanismo de extensão.
4. Preservar o caminho BL/BLX legado exatamente como está para presets sem `THUMB2`
   E, quando `THUMB2` estiver ativo, para o subconjunto de bits que o manual reserva
   a BL/BLX (ou seja: BL/BLX continuam funcionando IGUAL em ARMv7, não são
   substituídos — apenas o restante do espaço 32-bit passa a ser reconhecido).
5. Sem extensão registrada (nenhum consumidor de B2.2-B2.5 ainda), o resultado para
   encodings genuinamente Thumb-2 deve ser UNDEFINED consistente — não uma exceção
   de "extensão ausente".

## Testes mínimos

- Preset sem `THUMB2` (ARMV4T, ARMV5TE, ARMV6K): encodings de 32-bit Thumb-2 puro
  (fora do espaço BL/BLX) continuam UNDEFINED — nenhuma regressão (G2).
- Preset com `THUMB2`: BL/BLX de 32 bits legado continua decodificando IDÊNTICO
  (mesmo `DecodedInstruction`/`IrOp` de antes) — teste de regressão byte-a-byte.
- Preset com `THUMB2`: um encoding sintético de 32-bit Thumb-2 (fora do espaço
  BL/BLX) é reconhecido como candidato de 32 bits e busca os dois halfwords
  corretos (`address`/`address+2`), mesmo sem extensão registrada (undefined
  controlado, não crash).
- Todas as suítes existentes (arm-jitter/gbaemu/ndsemu) continuam verdes — nenhum
  jogo GBA/NDS real usa Thumb-2 hoje, então isto é puramente uma checagem de
  não-regressão.

- Documentar no javadoc `///` do novo hook a regra de desambiguação BL/BLX vs

## Armadilhas

- **A ambiguidade de encoding descrita no Contexto é a armadilha #1** — resolvê-la
  errado quebra silenciosamente todo THUMB code de GBA/NDS que usa `bl`/`blx`
  (onipresente). Testar exaustivamente contra o comportamento atual antes de mexer.
- `THUMB2` habilitado não significa "todo código agora é Thumb-2" — BL/BLX legado
  de 32 bits SEMPRE existiu nesse espaço de encoding mesmo em v4T/v5T; a feature só
  adiciona reconhecimento do restante.
- Cuidado com o fetch cruzando página/bloco de memória de forma diferente do padrão
  atual — o segundo halfword pode estar fora do bloco JIT sendo liftado; conferir
  como o BL prefix/suffix lida com isso hoje (eles são liftados como duas
  instruções separadas exatamente para evitar esse problema — um fetch atômico de
  32 bits é uma mudança de padrão, avaliar impacto no liftador de blocos).

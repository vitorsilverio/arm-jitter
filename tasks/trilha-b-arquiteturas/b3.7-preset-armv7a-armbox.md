# B3.7 — Preset `ARMV7A` + validação armbox com binário gcc hard-float

**Trilha:** B (épico B3, fechamento) · **Depende de:** B3.1–B3.6 + **B2.7, B1.7,
B2.8** (paridade Thumb-2, acesso desalinhado v6+, PLD — sem elas o binário gcc
falha; dependências ampliadas 2026-07-15) · **Repos:** arm-jitter + armbox

## Contexto

Todas as peças do ARMv7-A user-level existem; falta o preset público e a prova
objetiva com binário real (nível 2 e 3 da matriz `docs/VALIDACAO-ARQUITETURAS.md`).
Padrão já estabelecido por B4.0.1 (ARMv6K) e B4.0.2 (Thumb-2): torture test `.s`
auto-verificável + gêmeo `-broken` + binário de compilador real, nos 3 backends.

## Inclui — arm-jitter

Preset novo em `ArmArchitecture`:

```java
public static final ArmArchitecture ARMV7A = extending(ARMV6K_THUMB2, "ARMv7-A",
        ArmFeature.MOVW_MOVT, ArmFeature.MLS_MULTIPLY, ArmFeature.BIT_FIELD,
        ArmFeature.BIT_REVERSE, ArmFeature.DIVIDE, ArmFeature.MEMORY_BARRIERS,
        ArmFeature.VFPV2)
        .withDecoderExtensions(List.of(new VfpDecoder(), new CoprocessorDecoder(),
                new ArmV7MediaDecoder()))
        .withThumb32DecoderExtensions(List.of(/* TODAS as de ARMV6K_THUMB2
                (as 4 de B2.6 + as de B2.7: RegisterDataProcessing/Multiply/
                CoprocessorDecoder-Thumb) + */ new VfpDecoder()));
```

Atenção: `extending` HERDA as listas da base, mas `withDecoderExtensions` SUBSTITUI —
monte a lista completa explicitamente (VfpDecoder ANTES de CoprocessorDecoder, regra
da B3.5). Javadoc: user-level only (sem MMU/CP15-VMSA — B4.1), NEON fora, SDIV/UDIV
habilitados (nota v7VE da decisão nº 5 do épico).

## Armadilhas

- Se o gcc da toolchain emitir NEON mesmo com `-mfpu=vfp` (memcpy vetorizado de
  libc pré-compilada), o binário cai em UNDEFINED — use `-static` com a MESMA libc
  dos testdata atuais e, se aparecer NEON, troque o workload para evitar a rotina
  (registrar no PR qual símbolo) — NÃO implemente NEON de improviso.
- printf de float via libc completa puxa MUITO código — preferir formatação manual
  (multiplicar por 10^k e imprimir inteiro) se a libc dos testdata for a nosys.
- O `--check` (divergence) com FP só é confiável depois de B3.6 (CpuSnapshot já
  compara o banco — B3.3); se divergir, o bug é REAL, não "ruído de NaN": bits são
  determinísticos nos dois backends por construção.

## Resultado

✅ 2026-07-23 — `ArmArchitecture.ARMV7A` novo (`extending(ARMV6K_THUMB2, ...)`): `MOVW_MOVT`/`MEMORY_BARRIERS` já herdados de `ARMV6K_THUMB2_FEATURES`, mas `MLS_MULTIPLY`/`BIT_FIELD`/`BIT_REVERSE`/`DIVIDE` (demais features do "inteiro v7" de B3.1) NÃO são herdados de nenhum preset anterior — precisaram ser declarados aqui explicitamente, junto com `VFPV2` novo. **Desvio real do plano original, mesmo padrão de honestidade de B3.1**: a spec previa `.withDecoderExtensions(List.of(new VfpDecoder(), new CoprocessorDecoder(), new ArmV7MediaDecoder()))` — mas `ArmV7MediaDecoder` nunca existiu (B3.1 já desviou disso, ver a entrada dela); o preset só precisa de `VfpDecoder`/`CoprocessorDecoder` (nesta ordem — regra de B3.5) mais as features certas, já que as 13 instruções "media" v7 são carve-outs diretos em `ArmDecoder`. `withThumb32DecoderExtensions` lista de novo as 7 extensões de `ARMV6K_THUMB2` (substituição, não soma) mais `Thumb2VfpDecoder` posicionado ANTES de `Thumb2CoprocessorDecoder`. **Quebra-cabeça do ovo e da galinha resolvido com `ARMV7A_FEATURES` privado** (mesmo padrão de `ARMV6K_THUMB2_FEATURES`): `VfpDecoder`/`Thumb2VfpDecoder` recebem `ArmArchitecture` no construtor para gatear `VFPV2`, e `ARMV7A` ainda não existe nesse ponto. Lado armbox: `--arch=armv7a` no `Main` (mesmo padrão de `--arch=thumb2`); `testdata/armv7a-torture.s` (28 checagens auto-verificáveis: MOVW/MOVT, UBFX/SBFX/BFC/BFI, RBIT, MLS, SDIV/UDIV incl. x/0 e MIN_VALUE/-1, DMB, e a seção VFP — VMOV imediato single/double + transferência core↔S/D, VADD/VMUL/VDIV/VSQRT [`sqrtf(2)=0x3FB504F3`, mesmo vetor exato de `IrVfpExecutorTest`/B3.4], VCMP+VMRS APSR_nzcv, VCVT int↔float, VLDR/VSTR, VPUSH/VPOP) + gêmeo `-broken`; `testdata/hello-float.c` (série de Leibniz de 6 termos em `double`, formatação manual sem printf de float). **Armadilha do enunciado resolvida diferente do previsto**: a spec temia NEON via memcpy vetorizado de libc pré-compilada mesmo sob `-mfpu=vfp` — a mitigação adotada foi mais forte que "trocar o workload": `hello-float.c` segue o MESMO padrão bare-metal de todo o resto do testdata (`-nostdlib`, `_start` próprio via `naked`, syscalls cruas via `svc #0`, sem CRT/libc/libgcc nenhuma — divisão por constante 10 inline pelo próprio gcc) — zero libc linkada, então o risco de NEON não existe estruturalmente, confirmado via `objdump`/`nm` (só 2 símbolos, `_start`/`c_main`, nenhum registrador `q`). Toolchain real exigiu 2 ajustes não previstos na spec: `SDIV`/`UDIV` não existem em `-march=armv7-a` base (é a extensão opcional "integer divide", nota v7VE) — usado `-march=armv7ve`; `VMOV` imediato é VFPv3, não VFPv2 real — usado `.fpu vfpv3-d16` no assembler (nome real da variante de 16 registradores `D` que corresponde ao que `VfpDecoder` já valida como "`D:Vd>15` é UNDEFINED"). **Bug REAL encontrado e corrigido pela validação N3** (exatamente o cenário que a Armadilha 3 da spec previa: "se divergir, o bug é real"): `hello-float.elf` divergia nos 3 backends (JIT e interpretado davam respostas DIFERENTES e ambas erradas) — causa raiz: `IrOp.VfpLoad`/`VfpStore`/`VfpMultipleTransfer` não tinham o campo `baseValueOverride` que `IrOp.Load`/`Store` já tinham para o idioma `Rd,[pc,#imm]` (literal pool do `gcc`) — sem ele, `base`=PC era lido AO VIVO em `core.register(15)`, que só reflete o viés `+8` do PC arquitetural DEPOIS que o bloco termina, então duas `VLDR Dx,[pc,#imm]` consecutivas liam os literais TROCADOS entre si. Fix: campo novo em `IrOp.java` (3 records) + `StandardIrBuilder` passando `baseValueOverride(instruction)` (helper já existente, reusado) + `IrVfpExecutor` usando `support.registerValue(...)` em vez de `core.register(op.base())` direto + `AsmBlockCompiler`/`AsmRuntimeHelpers` (emissão nativa) com o mesmo tratamento de `Load`/`Store`. 3 novos testes de regressão (`VfpDecoderTest` ida-e-volta decode+execução com `Rn=PC`, `VfpNativeEquivalenceTest` provando que o override — não o PC ao vivo — dirige o endereço). Depois do fix, os 3 backends (JIT/interp/check) concordam bit-a-bit: `0.744012` (Leibniz de 6 termos), confirmado contra cálculo de referência Java (`Double.doubleToRawLongBits`). Suíte arm-jitter (core+truffle) + armbox (incl. `Armv7TortureTest` novo: torture 28/28 + `-broken` exit 77 + hello-float 3 backends idênticos) + `mvn -o install` + gbaemu + ndsemu todos verdes (JBR 25) — zero regressão.

# B6.9 — AArch64: `AND`/`ORR`/`EOR`/`ANDS`/`BIC`/`ORN`/`EON`/`BICS` (logical, shifted register) + alias `MOV`/`MVN`

**Trilha:** B · **Depende de:** B6.3.1 (reaproveita o dispatch `decodeDataProcessingRegister` e o
executor `logicalWithFlags`) · **Repo:** arm-jitter

## Contexto

Aberta pela sessão 3 da F11 (`virtual-arm-box`, 2026-08-20 — ver `tasks/FILA-EXECUCAO.md`, linha
P17c): com `CCMP`/`CCMN` (B6.8) disponíveis, o boot do `kernel8.img` real avança até
`0x13ba9e8` (`0xaa0003f5` = `ORR X21, XZR, X0`, o alias `MOV` de registrador) e bate num SEGUNDO
gap de decode, documentado desde B6.3.1 como "fora do escopo fechado do épico" — `Logical
(shifted register)` nunca foi implementado. Diferente de `CCMP`/`CCMN` (família inteira
esquecida por acidente), este é um "não fazer" EXPLÍCITO das specs anteriores (B6.3.1 Armadilhas,
B6.8 D3) — esta task revoga essa decisão de escopo porque a F11 provou que o gap bloqueia boot
real (`MOV` de registrador é onipresente em qualquer binário AArch64 real).

## Fatos de referência (CONFERIDOS nesta rodada de spec contra a fonte real do QEMU — `master`,
lido via `curl` de `raw.githubusercontent.com` em 2026-08-20, não recordado de memória; mesma
disciplina de B6.3.1/B6.6.7, ao contrário do aviso explícito de B6.8)

1. **Encoding** (`target/arm/tcg/a64.decode`):
   ```
   &logic_shift    rd rn rm sf sa st n
   @logic_shift    sf:1 .. ..... st:2 n:1 rm:5 sa:6 rn:5 rd:5  &logic_shift

   AND_r           . 00 01010 .. . ..... ...... ..... .....    @logic_shift
   ORR_r           . 01 01010 .. . ..... ...... ..... .....    @logic_shift
   EOR_r           . 10 01010 .. . ..... ...... ..... .....    @logic_shift
   ANDS_r          . 11 01010 .. . ..... ...... ..... .....    @logic_shift
   ```
   Bits (MSB→LSB): `sf`(31) `opc`(30:29) `01010`(28:24) `st`(23:22) `n`(21) `rm`(20:16)
   `sa`(15:10) `rn`(9:5) `rd`(4:0). **Confirmado que isto reaproveita EXATAMENTE os mesmos
   deslocamentos de bit já usados por `decodeAddSubShiftedRegister`** (B6.3.1):
   `ADDSUB_REGISTER_GROUP_SHIFT`=24 (mas padrão `0b01010`, não `0b01011` — só esse bit distingue
   as duas famílias dentro da classe "Data Processing — Register"), `ADDSUB_SHIFTED_TYPE_SHIFT`=22
   (campo `st`, 2 bits), `ADDSUB_REGISTER_EXTENDED_BIT_SHIFT`=21 (aqui é o bit `n`, não
   "extendedForm" — mesma posição, semântica diferente por famíla), `ADDSUB_REGISTER_RM_SHIFT`=16,
   `ADDSUB_SHIFTED_AMOUNT_SHIFT`=10, `RN_SHIFT`=5, `REGISTER_FIELD_MASK` para `rd`. **Reaproveitar
   essas constantes já existentes** em vez de duplicar (G6) — só uma constante nova é necessária
   para o padrão de grupo (`0b01010`).
   `opc` (bits 30:29) usa o MESMO mapeamento já usado por `decodeLogicalImmediate` (B6.3.1):
   `00`=`AND`, `01`=`ORR`, `10`=`EOR`, `11`=`ANDS` — **reaproveitar `LOGICAL_IMM_OPC_*` (shift 29,
   mesmos valores)**, não duplicar constantes.

2. **Semântica real, transcrita de `do_logic_reg`/`trans_{AND,ANDS,EOR}_r`
   (`target/arm/tcg/translate-a64.c`)**:
   ```c
   static bool do_logic_reg(DisasContext *s, arg_logic_shift *a,
                            ArithTwoOp *fn, ArithTwoOp *inv_fn, bool setflags)
   {
       if (!a->sf && (a->sa & (1 << 5))) return false;   // UNDEFINED, igual ADD/SUB shifted
       tcg_rm = read_cpu_reg(s, a->rm, a->sf);
       if (a->sa) shift_reg_imm(tcg_rm, tcg_rm, a->sf, a->st, a->sa);
       (a->n ? inv_fn : fn)(tcg_rd, tcg_rn, tcg_rm);
       if (!a->sf) tcg_gen_ext32u_i64(tcg_rd, tcg_rd);
       if (setflags) gen_logic_CC(a->sf, tcg_rd);         // Z/N do resultado, C=0,V=0 SEMPRE
   }
   TRANS(AND_r, do_logic_reg, a, tcg_gen_and_i64, tcg_gen_andc_i64, false)
   TRANS(ANDS_r, do_logic_reg, a, tcg_gen_and_i64, tcg_gen_andc_i64, true)
   TRANS(EOR_r, do_logic_reg, a, tcg_gen_xor_i64, tcg_gen_eqv_i64, false)
   // ORR_r: caminho geral idêntico (tcg_gen_or_i64, tcg_gen_orc_i64, false) — ver item 4 (MOV).
   ```
   Ou seja: **`Rm` é deslocado primeiro (`st`/`sa`, os 4 tipos LSL/LSR/ASR/ROR — `st==11` aqui NÃO
   é reservado, ao contrário de `AluShiftedRegister`), depois OPCIONALMENTE invertido bit a bit
   (`n`=1), depois combinado com `Rn` pela operação lógica** (`AND`/`ORR`/`EOR`). O bit `n` é o
   que produz `BIC`(=`AND`+invert)/`ORN`(=`ORR`+invert)/`EON`(=`EOR`+invert)/`BICS`(=`ANDS`+
   invert) — **não são opcodes adicionais no encoding, são o MESMO `opc` de 2 bits com `n=1`**.
   `gen_logic_CC` confirma `C=0,V=0` sempre quando `setflags` (`ANDS`/`BICS`) — **idêntico ao
   comportamento de `logicalWithFlags` já existente** (`Ir64BlockExecutor`, usado por
   `executeAlu`/B6.3.1 imediato) — reaproveitar sem alteração (mesmo padrão de D2 em B6.3.1).
   `!sf`: resultado zero-estendido para os 64 bits do destino (`tcg_gen_ext32u_i64`) — mesma regra
   já aplicada por `core.setXForWidth`.
   `shift_reg_imm`/`shift_reg` confirmados suportando os 4 tipos, `enum a64_shift_type {LSL=0,
   LSR=1, ASR=2, ROR=3}` — mapeamento de bits idêntico ao campo `st` do encoding.

3. **`Rd`/`Rn`/`Rm` nunca são `SP`** — `do_logic_reg` usa `cpu_reg`/`read_cpu_reg` em todo lugar
   (nunca `cpu_reg_sp`/`read_cpu_reg_sp`), diferente de `AluExtendedRegister`. Mesma regra que
   `AluShiftedRegister` já implementa (B6.3.1) — índice `31` é sempre `XZR`, sem campo
   `dstIsStackPointer`/`src1IsStackPointer`.

4. **`MOV`/`MVN` (registrador) são um alias de DISASSEMBLY puro, sem semântica própria** —
   achado real desta rodada de spec, **muda o Objetivo desta task**: `trans_ORR_r`
   (`translate-a64.c:9127-9153`) tem um `if (a->sa == 0 && a->st == 0 && a->rn == 31)` que
   special-casa `ORR`/`ORN` com `Rn=XZR`/sem shift para gerar TCG mais simples (`MOV`/`MVN`), mas
   isso é **uma otimização de codegen do QEMU, não uma exigência arquitetural**: o caminho geral
   (`do_logic_reg` com `fn=or_i64`/`inv_fn=orc_i64`, `Rn=XZR`) já produz `XZR | shift(Rm) = Rm`
   (ou `~Rm` com `n=1`) SEM precisar de nenhum caso especial — `shift_reg_imm` com `sa=0` já é
   `mov` puro, e `XZR OR qualquer_coisa` já é `qualquer_coisa`. **Conclusão: o interpretador
   (oráculo) NÃO precisa de nenhum decode/executor dedicado para `MOV`/`MVN` — o caminho geral de
   `ORR`(`n=0`)/`ORN`(`n=1`) com `Rn=XZR`,`sa=0`,`st=LSL` já é correto por construção.** Só
   precisa de um teste de regressão confirmando isso (Testes mínimos #5) — não uma decisão de
   design nova.

## Decisões de desenho FECHADAS nesta rodada

### D1 — `Ir64Op.LogicalShiftedRegister`, um record novo (não reaproveitar `AluShiftedRegister`)

`AluShiftedRegister` (B6.3.1) já existe para `ADD`/`SUB` com `Ir64ShiftType` (só `LSL`/`LSR`/
`ASR` — `ROR` é RESERVADO nessa forma, ver o javadoc do próprio enum). Esta instrução PRECISA de
`ROR` — reaproveitar `AluShiftedRegister`/`Ir64ShiftType` obrigaria adicionar `ROR` a um enum cujo
contrato documentado diz explicitamente que as 3 combinações são as únicas válidas para
`ADD`/`SUB`, e forçaria todo `switch` exaustivo sobre `Ir64ShiftType` (ex.
`Ir64BlockExecutor#applyShift`) a ganhar um `case ROR` que nunca é alcançável por
`AluShiftedRegister` — confunde os dois contratos. **Decisão: enum novo `Ir64LogicalShiftType`
(`LSL`/`LSR`/`ASR`/`ROR`)**, dedicado a esta instrução, e um record novo `LogicalShiftedRegister`
(campos: `opcode` (`Ir64AluOp.AND`/`ORR`/`EOR` — reaproveita o enum já existente, sem variante
`ANDS` própria, mesma decisão de D2 abaixo), `dst`, `src1` (`Rn`), `src2` (`Rm`),
`shiftType` (`Ir64LogicalShiftType`), `shiftAmount`, `invert` (bit `n` — produz
`BIC`/`ORN`/`EON`/`BICS` quando `true`), `wide`, `setFlags`).

### D2 — `setFlags`/flags reaproveitam exatamente o padrão de `Alu64`/B6.3.1 (D2 daquela task)

`ANDS`/`BICS` não ganham um `Ir64AluOp` próprio — é o mesmo `opcode=AND` com `setFlags=true`
(igual à decisão já tomada para a forma imediata). O executor reaproveita `logicalWithFlags`
(`Ir64BlockExecutor`, já existente, já usado por `executeAlu`) sem nenhuma duplicação de cálculo —
`C=0,V=0` sempre, confirmado pela fonte real (Fatos de referência #2).

### D3 — Sem decode/executor dedicado para `MOV`/`MVN`

Confirmado pelos Fatos de referência #4: **não implementar nenhum caminho especial**. O único
efeito prático é um teste de regressão que decodifica `mov x21, x0` (equivalente a
`orr x21, xzr, x0`) e confirma que produz o mesmo `Ir64Op.LogicalShiftedRegister` que `orr` com
`Rn=31` produziria, executando corretamente.

### D4 — `st==0b11` (`ROR`) sem restrição UNDEFINED nesta forma

Ao contrário de `AluShiftedRegister` (onde `st==0b11` é RESERVADO, ver B6.3.1 Fatos de referência
#4), aqui os 4 valores de `st` são válidos sempre — não portar a checagem de reserved de
`decodeAddSubShiftedRegister` para este decoder. A única checagem UNDEFINED que sobrevive é a
mesma de `AluShiftedRegister`: `!wide && (shiftAmount & 32) != 0`.

## Objetivo

- `AND`/`ORR`/`EOR`/`ANDS` (registrador deslocado, `n=0`) e `BIC`/`ORN`/`EON`/`BICS` (`n=1`)
  decodificados em `decodeDataProcessingRegister`, novo `case` para o padrão de grupo `0b01010`.
- `Ir64Op.LogicalShiftedRegister` (D1) + `Ir64LogicalShiftType` (D1) novos.
- Executor novo em `Ir64BlockExecutor` reaproveitando `logicalWithFlags` (D2) e um `applyShift`
  próprio com suporte a `ROR` (não estender o `applyShift` existente de `AluShiftedRegister` — ver
  Armadilhas).
- `MOV`/`MVN` (registrador) funcionam por construção, sem código dedicado (D3) — só teste.
- `Raspi364BootTest` (virtual-arm-box) deixa de bater nesse gap especificamente — critério
  prático, não aceite formal desta task (outro repo, sessão própria).

## Não inclui

- Qualquer outro gap de decode que a continuação do boot da F11 revelar depois deste ponto — não
  presumir que fechar isto conclui o boot.
- `EXTR` (fora de escopo desde B6.3.2, sem relação com esta task).
- Alterar `AluShiftedRegister`/`Ir64ShiftType` (D1) — permanecem exatamente como estão, só
  `ADD`/`SUB`.

## Testes mínimos

1. `AND`/`ORR`/`EOR`/`ANDS`, `n=0`: vetor real por opcode, `LSL`/`LSR`/`ASR`/`ROR` com quantidade
   não-zero, `wide`/`!wide`.
2. `BIC`/`ORN`/`EON`/`BICS`, `n=1`: mesmos 4 opcodes×shifts, confirmando que o operando é invertido
   ANTES da combinação (ex. `bic rd, rn, rm` com `rm=rn` deve dar `rd=0`, não `rd=rn`).
3. `ANDS`/`BICS`: `C=0,V=0` sempre, mesmo em casos que "pareceriam" gerar carry informalmente
   (mesmo teste de D2 de B6.3.1, adaptado).
4. `!wide` (`sf=0`) com quantidade de shift `>=32`: `UnsupportedOperationException`.
5. **`MOV`/`MVN` (D3)**: `mov x21, x0` (`0xaa0003f5`, o vetor literal da F11) decodifica para
   `LogicalShiftedRegister(ORR, dst=21, src1=31, src2=0, LSL, 0, wide=true, setFlags=false,
   invert=false)` e executa `X21 = X0`; `mvn` equivalente com `invert=true` executa
   `X21 = ~X0`. Confirma o achado do item 4 dos Fatos de referência sem precisar de nenhum código
   novo além do decode genérico.
6. Corpus real (`aarch64-none-elf-as`/`objdump`, `C:\devkitPro\devkitA64\bin`): pelo menos um vetor
   por combinação de (`AND`/`ORR`/`EOR`/`ANDS`) × (`n=0`/`n=1`) × (`LSL`/`LSR`/`ASR`/`ROR`),
   incluindo o vetor literal `0xaa0003f5` da F11.
7. Regressão: suíte completa B6.1-B6.8 sem mudança de comportamento; `AluShiftedRegister`/
   `Ir64ShiftType` inalterados (nenhum `ROR` neles).

## Armadilhas

- **Não confundir com `AluShiftedRegister`** — mesmo "formato" superficial (opcode + dst + src1 +
  src2 + shiftType + shiftAmount + wide + setFlags), mas semânticas de shift (`ROR` válido aqui,
  reservado lá) e de opcode (lógico vs aritmético, com o bit `n` de inversão que `AluShiftedRegister`
  não tem) genuinamente diferentes — não tentar unificar os dois records nem os dois enums de shift
  (D1).
- **`n=1` inverte o operando ANTES da combinação, não depois** — `bic rd,rn,rm` = `rn AND (NOT
  rm)`, não `NOT(rn AND rm)`. Fácil de inverter a ordem por engano copiando a estrutura de
  `AluExtendedRegister` (que não tem esse bit).
- **`st==0b11` (`ROR`) é VÁLIDO aqui**, ao contrário do vizinho `AluShiftedRegister` — não copiar a
  checagem `ADDSUB_SHIFTED_TYPE_RESERVED_ROR`/`throw unsupported` de `decodeAddSubShiftedRegister`
  para este decoder (armadilha simétrica à de D4).
- **`MOV`/`MVN` não precisam de nenhum código dedicado** (D3/D4 dos Fatos de referência) — a
  tentação, copiando o padrão de outras tasks desta trilha, é criar um `case` especial para
  `Rn=31,sa=0,st=LSL`; isso seria trabalho e código extra sem propósito (o caminho geral já está
  correto) — só o teste de regressão é necessário.
- **Reaproveitar os shifts de bit já existentes** (`ADDSUB_REGISTER_GROUP_SHIFT`,
  `ADDSUB_SHIFTED_TYPE_SHIFT`, `ADDSUB_REGISTER_EXTENDED_BIT_SHIFT` para o bit `n`,
  `ADDSUB_REGISTER_RM_SHIFT`, `ADDSUB_SHIFTED_AMOUNT_SHIFT`, `RN_SHIFT`, `REGISTER_FIELD_MASK`,
  `LOGICAL_IMM_OPC_*`) em vez de declarar constantes duplicadas com nomes novos (G6) — só o padrão
  de grupo (`0b01010`) é genuinamente novo.

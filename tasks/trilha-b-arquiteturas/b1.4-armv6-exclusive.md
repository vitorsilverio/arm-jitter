# B1.4 — LDREX/STREX e monitor de exclusividade

**Trilha:** B · **Depende de:** B1.1 · **Repo:** arm-jitter

## Contexto

Base dos atomics de qualquer SO (Linux usa para futex/spinlock; 3DS idem). O core
precisa de um **monitor de exclusividade local**: estado (endereço marcado, tamanho,
flag aberto/fechado) consultado pelo STREX.

## Objetivo

- ARMv6 (`EXCLUSIVE_WORD`): `LDREX`, `STREX` (word).
- ARMv6K (`EXCLUSIVE_SIZED`): `LDREXB`, `LDREXH`, `LDREXD`, `STREXB`, `STREXH`,
  `STREXD`, `CLREX`.

## Especificação

1. **Monitor no `ArmCore`** (estado novo, com constantes nomeadas):
   - `LDREX{,B,H,D} Rd, [Rn]` → lê a memória normalmente E marca
     (endereço=Rn, tamanho) no monitor.
   - `STREX{,B,H,D} Rd, Rm, [Rn]` → se o monitor está marcado para esse
     endereço/tamanho: escreve na memória, `Rd = 0`, limpa o monitor. Senão:
     NÃO escreve, `Rd = 1`.
   - `CLREX` e **qualquer entrada de exceção** (SWI/IRQ/undefined — ver onde
     `ArmCore` faz a entrada de exceção) limpam o monitor.
   - Emulador single-core por enquanto: granularidade exata do endereço marcado pode
     ser a word alinhada; documentar a simplificação no javadoc.
2. **LDREXD/STREXD**: par de registradores (Rd, Rd+1... na verdade Rt/Rt2 conforme
   encoding) — 64 bits em duas words; conferir restrições de registrador par no manual
   e decodificar como UNPREDICTABLE→undefined se violadas.
3. **IR:** espelhar `IrOp.Load`/`IrOp.Store` — provavelmente `IrOp.LoadExclusive` /
   `IrOp.StoreExclusive` com campo de tamanho. Executor em `IrMemoryExecutor`.
4. **Snapshot/equivalência:** o estado do monitor deve entrar em `CpuSnapshot`
   (codegen/equivalence) para o harness detectar divergência futura do backend nativo.
5. **Gancho futuro (só javadoc, sem código):** documentar que para multi-core (3DS)
   o monitor precisará de visão global por `AddressSpace` — deixar a nota onde o
   monitor for implementado.

## Testes mínimos

- LDREX→STREX no mesmo endereço = sucesso (Rd=0, memória escrita).
- STREX sem LDREX prévio = falha (Rd=1, memória INTACTA — verificar!).
- LDREX→exceção (SWI)→retorno→STREX = falha.
- LDREX→CLREX→STREX = falha.
- LDREX word → STREXB no mesmo endereço = falha (tamanho diferente).
- Loop LDREX/STREX de incremento atômico converge (teste funcional).
- Gating: tudo undefined no ARMV4T/ARMV5TE; variantes B/H/D undefined num preset só
  com `EXCLUSIVE_WORD`.

## Aceite

- `mvn test` + gbaemu/ndsemu verdes; sem emissão ASM nativa (B1.6).

## Armadilhas

- STREX que falha NÃO PODE ter efeito colateral de memória — cuidado com a ordem
  (checar monitor ANTES de chamar `write32`).
- O Rd do STREX não pode ser o mesmo Rm/Rn (UNPREDICTABLE no hardware) — decodificar
  e testar como undefined em vez de silenciosamente aceitar.

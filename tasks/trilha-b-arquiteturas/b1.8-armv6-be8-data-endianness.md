# B1.8 — Suporte real a BE8 (`CPSR.E=1`, acesso de dados big-endian)

**Trilha:** B · **Depende de:** B1.5, B1.6, B1.7 · **Repo:** arm-jitter

## Contexto

A task B1.5 decidiu, como escopo MVP, que `SETEND` decodifica e alterna o bit E do CPSR mas
que qualquer acesso de dados com `E=1` (big-endian) lança
`UnsupportedOperationException` — decisão documentada em
`IrExecutionSupport.checkLittleEndianData` ("Linux/3DS rodam little-endian e nunca ligam E").

Essa premissa se provou **errada** ao rodar um kernel Linux ARMv6K real
(`virtual-arm-box`, task F3, `Raspi1BootTest`): o kernel `vmlinuz` para Raspberry Pi 1 usa
`SETEND BE` bem cedo no boot (antes de `early_trap_init()`), como parte do suporte BE8 do
próprio kernel (compilação padrão do Raspbian/Debian armel-ish para ARM11). O boot trava no
limite documentado. Esta task implementa o suporte real, fechando a lacuna.

**Terminologia importante (confirmar contra ARM DDI 0406C A2.9 "Endian support" antes de
mexer)**: o modo relevante aqui é **BE8** ("byte-invariant big-endian"), o único modo BE que
`SETEND`/`CPSR.E` controlam:
- **Busca de instrução (fetch) é SEMPRE little-endian**, independente de `CPSR.E`. `SETEND`
  nunca afeta como uma instrução é buscada — só como acessos de DADO (`LDR`/`STR`/`LDRH`/
  `STRH`/`LDRD`/`STRD`/`LDM`/`STM`/`LDREX`/`STREX`/`SWP`) leem/escrevem memória.
- Um acesso de **byte único** (`LDRB`/`STRB`) é, por definição, invariante a endianness — o
  mesmo byte no mesmo endereço, sempre. BE8 só afeta a ORDEM em que os bytes de um acesso
  multi-byte (halfword/word/doubleword) são combinados no registrador de destino (load) ou
  decompostos na memória (store): em LE, o byte no endereço mais baixo é o menos
  significativo; em BE8, o byte no endereço mais baixo é o MAIS significativo. Isso é
  EXATAMENTE `Integer.reverseBytes` (word) / troca dos 2 bytes (halfword) aplicado sobre o
  valor já composto em LE — não é preciso reimplementar a composição byte a byte.

## Objetivo

Substituir a exceção da B1.5 por suporte real: acessos de dados com `CPSR.E=1` produzem o
valor com bytes trocados (word/halfword), tanto no interpretador quanto no backend ASM
nativo, sem afetar fetch de instrução nem qualquer preset/comportamento existente com `E=0`
(default, G3).

## Inclui

1. Interpretador (`IrExecutionSupport`, pacote `codegen.executor`): os pontos primitivos de
   acesso de dados —
   `read32Arm7`/`read16Arm7`/`write32Arm7`/`write16Arm7` (ponto único usado, direta ou
   indiretamente via `readWordForLoad`/`readHalfwordForLoad`/`writeWordForStore`/
   `writeHalfwordForStore`, por TODO acesso de dados do core: `LDR`/`STR`/`LDRH`/`STRH`
   simples e desalinhado, `LDRD`/`STRD`, `LDM`/`STM`/`PUSH`/`POP`/`SRS`/`RFE`, `LDREX`/
   `STREX`, `SWP`, transferências VFP de 32 bits) — e os 4 helpers "Crossed"
   (`readCrossedWord`/`readCrossedHalfword`/`writeCrossedWord`/`writeCrossedHalfword`, usados
   por `LDR`/`STR`/`LDRH`/`STRH` sob `ArmFeature.UNALIGNED_ACCESS` com destino ≠ PC) — ganham
   a troca de bytes condicionada a `core.cpsr().isBigEndian()`, aplicada:
   - em leituras: DEPOIS de o valor já estar composto/rotacionado do jeito LE de sempre;
   - em escritas: ANTES do valor ser decomposto/escrito, do jeito LE de sempre.
   `read8Arm7`/`write8Arm7`/`loadByte`/`storeByte` (byte único) **não mudam** — invariantes a
   endianness por definição (ver Contexto). O ramo de `read16Arm7` que vira leitura de byte
   (quirk ARMv4T de `LDRSH` desalinhado em endereço ímpar) também não muda — é um acesso de
   byte disfarçado.
2. `checkLittleEndianData` é removido (junto com as chamadas a ele) — não lança mais.
3. Backend ASM nativo (`AsmRuntimeHelpers`, pacote `codegen.jvm`): os helpers espelho
   — `loadWord`/`loadHalf`/`loadHalfSigned`/`storeWord`/`storeHalf` e as variantes
   `*Crossed` — ganham a MESMA troca de bytes, no mesmo ponto relativo (depois de compor/
   antes de decompor). `loadByte`/`storeByte` não mudam. Como `AsmBlockCompiler` já emite
   `Load`/`Store`/`LoadLiteral`/`MultipleTransfer`/`LDREX`/`STREX` nativamente (nenhuma
   dessas ops está na lista de rejeição de `AsmNativePolicy`) e todas chamam estes mesmos
   helpers, nenhuma mudança é necessária em `AsmBlockCompiler` nem em `AsmNativePolicy` —
   BE8 passa a funcionar nativamente "de graça" para tudo que já é nativo, sem precisar
   forçar blocos para o interpretador depois de um `SETEND`.
4. Gate: nenhum — a troca é condicionada a `core.cpsr().isBigEndian()` em tempo de EXECUÇÃO
   (estado do CPSR), não em tempo de compilação/preset. Isso já é suficiente para G2/G3: só
   presets com `ArmFeature.SETEND_BIG_ENDIAN_DATA` (`ARMV6K`, `ARMV6K_THUMB2`, `ARMV7A`,
   `ARM11_MPCORE`) conseguem decodificar `SETEND` para setar `E=1` — `ARMV4T`/`ARMV5TE`
   (GBA/NDS) nunca setam o bit, então `isBigEndian()` é sempre `false` lá e o código novo é
   sempre um no-op nesses presets (confirmar com um teste de regressão dedicado, não só
   assumir).
5. Javadoc: atualizar `CpsrRegister.ENDIAN_FLAG` (hoje diz "não implementados"), o comentário
   de classe de `AsmRuntimeHelpers` na seção `UNALIGNED_ACCESS`, e o Javadoc de
   `IrExecutionSupport` que cita a B1.5/MVP.

## Não inclui (decisão de escopo explícita, documentar no índice ao fechar)

- **Modo BE32** ("word-invariant big-endian", `SCTLR.B=1`, removido desde ARMv6 e nunca usado
  por Linux/3DS) — fora de escopo, não confundir com BE8.
- Nenhuma mudança na busca de instrução (fetch) — permanece sempre little-endian, em
  qualquer `CPSR.E`. Se a spec descobrir durante a implementação algum ponto do código que
  aplica endianness ao fetch, é um bug a corrigir, não um recurso novo.
- `TranslatingAddressSpace`/MMU (B4.1) não são tocados — BE8 opera inteiramente no valor já
  lido/a escrever, não no endereço nem na tradução.

## Testes mínimos

- `SETEND BE`/`SETEND LE`: decodifica e alterna `CPSR.E` (já coberto por B1.5, não duplicar —
  só referenciar).
- `LDR`/`STR` word com `E=1`: valor lido/escrito com os 4 bytes trocados vs. `E=0`, endereço
  alinhado e desalinhado (sob `UNALIGNED_ACCESS`, ARMv6K).
- `LDRH`/`STRH` halfword com `E=1`: 2 bytes trocados vs. `E=0`.
- `LDRB`/`STRB` com `E=1`: **idêntico** a `E=0` (byte é invariante — teste negativo
  explícito, não só omissão).
- Fetch de instrução permanece little-endian mesmo com `E=1` ligado antes de buscar a
  instrução seguinte (ex.: `SETEND BE` seguido de uma instrução cujo encoding, se fosse lido
  big-endian, decodificaria como outra coisa — provar que decodifica igual).
- `LDM`/`STM` com `E=1`: pelo menos um teste de regressão/cobertura, já que o primitivo
  compartilhado (`read32Arm7`/`write32Arm7`/`loadWord`/`storeWord`) cobre isso "de graça" —
  provar que cobre mesmo, não assumir.
- Equivalência interpretado×ASM (`BlockEquivalenceHarness`, G1): `LDR`/`STR`/`LDRH`/`STRH`
  com `E=1`, 14 condições × 16 combinações de NZCV, mesmo padrão de
  `ArmV6UnalignedAccessNativeEquivalenceTest`; incluir o caso desalinhado (`UNALIGNED_ACCESS`
  + `E=1` juntos) e o caso alinhado.
- Regressão G3: preset `ARMV4T`/`ARMV5TE` — impossível chegar a `E=1` (não decodifica
  `SETEND`), então nenhum comportamento muda; regressão G2 padrão (`SETEND` continua
  `UNDEFINED` nesses presets, já coberto por B1.5, só confirmar que segue verde).
- Regressão G3: qualquer teste pré-existente com `E=0` (o caminho por default de todos os
  presets, incl. `ARMV6K`) não muda de resultado — a suíte completa já cobre isso, mas vale
  um teste dedicado e explícito comparando `E=0` antes/depois desta task para um `LDR`
  desalinhado (o caso mais "tocado" pela mudança).

## Armadilhas

- Não confundir BE8 com BE32 (ver "Não inclui").
- Não aplicar a troca de bytes a `LDRB`/`STRB` — é o erro mais fácil de cometer (agrupar
  "todo acesso de dados" sem separar byte de halfword/word).
- O quirk ARMv4T de `LDRSH` desalinhado em endereço ímpar (`read16Arm7`, vira leitura de
  byte) não deve ganhar troca de bytes — é um acesso de byte disfarçado, e de qualquer forma
  é inatingível sob `E=1` real (ARMv6K sempre tem `UNALIGNED_ACCESS`, que desvia esse
  caminho para os helpers "Crossed" quando o destino não é PC).
- `LDR pc,...`/`LDRH pc,...` continuam alinhando (task B1.7, item 4) — isso é ortogonal a
  BE8 e não deve ser tocado; a troca de bytes ainda se aplica ao VALOR lido (que pode virar
  o novo PC/estado THUMB), só o alinhamento do ENDEREÇO de busca é que segue a regra
  legada.
- `AsmNativePolicy` não precisa de nenhuma mudança — resistir à tentação de "gatear" BE8 lá;
  a troca já acontece dentro dos helpers que todo path nativo chama.

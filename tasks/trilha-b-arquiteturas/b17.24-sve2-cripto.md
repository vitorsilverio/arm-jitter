# B17.24 — SVE2 cripto: `AESE`/`AESD`/`AESMC`/`AESIMC`/`SM4E`/`SM4EKEY`/`RAX1` vetoriais — 7 encodings

**Trilha:** B · **Repo:** arm-jitter (+ revalidação G5) · **Depende de:** B17.5 (⬜)
**Épico:** `b17-plano-sve.md` · **Status:** ⬜ (spec escrita 2026-09-14, ainda não executada)

## Contexto

A menor task de conteúdo do épico e a de menor risco: **a semântica já existe inteira** no projeto,
vinda da B8.11b (SHA-1/SHA-256 A64), da B11.12 (`FEAT_SHA3`) e do AdvSIMD cripto

### Recorte normativo

`### SVE2 Crypto Extensions` inteiro (`sve.decode` linhas 1939-1952), **7 encodings** — bate com o
"7" da escada do épico.

### Os encodings reais (todos os 7)

```
@rdn_rm_e0      ........ .. ...... ...... rm:5 rd:5 &rrr_esz rn=%reg_movprfx esz=0
@rd_rn_rm_e0    ........ ... rm:5 ... ... rn:5 rd:5 &rrr_esz esz=0

# SVE2 crypto unary operations
AESMC           01000101 00 10000011100 0 00000 rd:5
AESIMC          01000101 00 10000011100 1 00000 rd:5

# SVE2 crypto destructive binary operations
AESE            01000101 00 10001 0 11100 0 ..... .....  @rdn_rm_e0
AESD            01000101 00 10001 0 11100 1 ..... .....  @rdn_rm_e0
SM4E            01000101 00 10001 1 11100 0 ..... .....  @rdn_rm_e0

# SVE2 crypto constructive binary operations
SM4EKEY         01000101 00 1 ..... 11110 0 ..... .....  @rd_rn_rm_e0
RAX1            01000101 00 1 ..... 11110 1 ..... .....  @rd_rn_rm_e0
```

### O que já existe (medido nesta rodada)

- `core/src/main/java/dev/vitorsilverio/armjitter/advsimd/AdvSimdCrypto.java` — `aes(...)` e
  `shaTwoRegister(...)`, já escritos contra a interface `AdvSimdRegisterWords` (não contra
  `Aarch64FpRegisters` direto), com o Javadoc dizendo: *"sempre um registrador `Q` completo (128
  bits/16 bytes)"*. **É exatamente a forma certa para reuso aqui** — ver Achado 1.
- `Aarch64Feature.SM4`, `Aarch64Feature.SHA3` (para `RAX1`) — já existem, declaradas em
  `ARMV8_2_A`. A feature de AES do A64 também (verificar o nome exato por `grep`).

### Achados desta rodada de spec

1. **SVE cripto opera POR SEGMENTO de 128 bits.** `AESE Zdn.B, Zdn.B, Zm.B` aplica uma rodada de
   AES a CADA segmento de 128 bits do vetor — em `VL=512`, quatro blocos AES independentes numa
   instrução. `AdvSimdCrypto.aes` já trabalha em "um registrador Q completo" indexado por
   `baseWord`, então o reuso é um LAÇO sobre segmentos, não uma reimplementação. Em `VL=128` é
   indistinguível da forma AdvSIMD — mais um caso do argumento da RFC B17.2.
2. **As features são SEPARADAS de `FEAT_SVE2`**: `FEAT_SVE_AES` (AESE/AESD/AESMC/AESIMC),
   `FEAT_SVE_SM4` (SM4E/SM4EKEY), `FEAT_SVE_SHA3` (RAX1) — anunciadas em campos distintos de
   `ID_AA64ZFR0_EL1` (`AES`, `SM4`, `SHA3`). **Não** são as mesmas constantes do A64
   (`Aarch64Feature.SM4`/`SHA3` cobrem `FEAT_SM4`/`FEAT_SHA3` escalares/AdvSIMD). Decidir na sessão:
   reusar as constantes existentes (mais simples, mas menos fiel — um núcleo pode ter `FEAT_SM4` e
   não `FEAT_SVE_SM4`) ou criar 3 constantes novas (fiel, aditivo, G3-safe). **A regra máxima do
   projeto favorece a versão fiel** — documentar a escolha.
3. **`AESMC`/`AESIMC` não têm operando de origem**: `00000` fixo no lugar de `rn`, e o destino é
   também a origem (destrutivo puro). São as únicas 2 linhas do arquivo com esse formato.
4. **`RAX1` é `esz=0` no formato mas opera em doublewords** (`Zd = Zn EOR rol(Zm, 1)` sobre
   elementos de 64 bits) — mesma armadilha de "esz do formato ≠ tamanho de operação" que a B17.11
   registrou para `REVD`.
5. **`SM4E` é destrutivo (`@rdn_rm_e0`) e `SM4EKEY` é construtivo (`@rd_rn_rm_e0`)** — mesmo par
   `EXT`/`EXT_sve2` que a B17.10 encontrou.
6. **`VL` tem que ser múltiplo de 128** para essas instruções fazerem sentido — o que é garantido
   pela arquitetura (`VL` sempre é múltiplo de 128). Nenhuma restrição extra.

## Objetivo

As 7 células decodificam sob as features de cripto SVE corretas e executam aplicando a operação
criptográfica **a cada segmento de 128 bits**, reusando `AdvSimdCrypto` sem duplicar nenhuma tabela
(S-box de AES, constantes de SM4).

## Inclui

1. **`AESMC`/`AESIMC`** (2) — unárias destrutivas.
2. **`AESE`/`AESD`/`SM4E`** (3) — binárias destrutivas.
3. **`SM4EKEY`/`RAX1`** (2) — binárias construtivas.
4. **Gate de feature** — 3 constantes novas em `Aarch64Feature` (`SVE_AES`, `SVE_SM4`, `SVE_SHA3`)
   ou o reuso das existentes, conforme a decisão do Achado 2.
5. Testes (ver Aceite).

## Não inclui

- **Qualquer implementação nova de AES/SM4/SHA3** — a semântica vem de `AdvSimdCrypto` e dos
  executores de B8.11b/B11.12. Se alguma primitiva faltar, é achado a documentar, não a
  reimplementar do zero sem conferir.
- **`PMULLB`/`PMULLT`** (multiplicação polinomial, que também é cripto-adjacente) — B17.21.
- **SHA-1/SHA-256/SHA-512 vetoriais** — **não existem em SVE**; o `.decode` não tem essas linhas.
- **Emissão nativa/Truffle** — padrão da trilha B.

## Aceite

- As 7 linhas decodificam sob as features de cripto SVE e são recusadas sob `SVE2` sem elas.
- **Teste cruzado com o A64**: `AESE Z0.B, Z0.B, Z1.B` em `VL=128` produz **exatamente** o mesmo
  resultado que `AESE V0.16B, V1.16B` do A64, para o mesmo estado inicial. Idem `AESD`, `AESMC`,
  `AESIMC`, `SM4E`, `SM4EKEY`, `RAX1`. É o teste que prova o reuso (e que não há S-box duplicada).
- **Com `VL >= 256`, cada segmento de 128 bits é processado independentemente** — teste com dois
  blocos distintos no mesmo vetor, comparando cada um com o resultado A64 correspondente.
- `AESMC`/`AESIMC` não leem operando de origem separado (o campo é `00000`).
- `RAX1` opera em doublewords (Achado 4).
- Nenhuma tabela criptográfica nova aparece no diff (conferir: `grep` por S-box/constantes no
  código novo deve não encontrar nada).
- Testado em pelo menos dois `VL`.
- `mvn -o test` verde + G5 verde nos 5 consumidores.

## Armadilhas

1. **Laço por segmento, não "o vetor inteiro é um bloco"** (Achado 1). Um AES sobre `VL=512` bits
   não é "AES de 512 bits" — são 4 AES de 128.
2. **Features separadas** (Achado 2) — e a decisão tem consequência para a **B17.3**, que anuncia os
   campos de `ID_AA64ZFR0_EL1`: só acender `AES`/`SM4`/`SHA3` lá depois que esta task fechar.
3. **`esz=0` de `RAX1` não é "opera em bytes"** (Achado 4).
4. **Não duplicar a S-box.** Se a implementação nova tiver uma tabela, o reuso falhou.
5. **`AESMC`/`AESIMC` têm formato único** (Achado 3) — um decoder genérico do grupo lê `rn` de um
   campo que é constante `00000`, o que "funciona" (sempre lê `Z0`) e está errado.
6. **`SM4E` destrutivo × `SM4EKEY` construtivo** (Achado 5).

## Não fazer

- Não reimplementar AES/SM4/SHA3.
- Não decodificar as 7 sob `SVE2` genérico sem resolver a questão das features.
- Não anunciar `ID_AA64ZFR0_EL1.AES`/`SM4`/`SHA3` antes desta task fechar (é a B17.3 quem escreve
  esse registrador, mas a decisão de acender cada campo é da task que implementa a família).

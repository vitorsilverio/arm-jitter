# B6.4 — AArch64: backend ASM 64-bit (3 PRs)

**Trilha:** B · **Depende de:** B6.3 ✅ (100% fechada, 2026-07-26) · **Repo:** arm-jitter

## Contexto

`b6-aarch64.md` fecha o escopo de B6.4 como "Backend ASM 64-bit: `GuestToHostMapper` com
locals `long` (2 slots), cache/tiers/chaining reusados" com aceite "harness de equivalência
A64 (novo `BlockEquivalenceHarness64`), busybox ≥3× interpretador". Esta é a rodada de spec
que a nota do próprio épico previu ("B6.4-B6.6 ganham spec própria quando B6.2 concluir").

Hoje (pós B6.3.4) o mundo A64 tem **decoder → `Ir64Op` direto** (sem estágio intermediário
`DecodedInstruction`+`IrBuilder` como o 32-bit) e um **interpretador de UMA instrução por vez**
(`Ir64BlockExecutor.step`, decodifica+executa, sem `IrBlock`/cache/JIT — isso é literalmente o
gap que B6.4 fecha). Não existe hoje: nenhum "bloco" A64 (lista de `Ir64Op` cobrindo várias
instruções), nenhum lifter, nenhum cache de blocos, nenhum runtime orquestrador, nenhum emissor
de bytecode.

### Por que "cache/tiers/chaining reusados" do épico NÃO se sustenta ao ler o código real

A frase original do épico presumia que `JitRuntime`/`BlockCache`/`BlockKey` (32-bit) fossem
genéricos o bastante para parametrizar por largura. Não são — investigado nesta rodada:

- `BlockKey` (`jit/BlockKey.java`) carrega `InstructionSet` (ARM/THUMB, não existe em A64),
  `itState` (Thumb-2 IT block, não existe em A64) e `translationGeneration` (MMU 32-bit, A64
  ainda não tem MMU — isso é B6.6). Nenhum desses 3 campos faz sentido para A64 hoje.
- `BlockCache` indexa por página de 1 KiB para invalidação de código automodificável
  (`invalidate(address, sizeBytes)`), amarrado a endereços `int`. A64 usa endereços `long`.
- `JitRuntime.execute(int pc, ArmCore core)` está pervasivamente amarrado a `ArmCore`/`int pc`/
  `InstructionSet` — inline cache (32K slots, tags de 41 bits compostas de `pc:instructionSet:
  itState`), encadeamento de blocos (`chainCycleBudget`), promoção tiered em background
  (`ExecutorService`/`ConcurrentLinkedQueue`), loop-superblocos — tudo lê `core.cpsr()`,
  `core.memory().translationGeneration()` (`AddressSpace`, não `AddressSpace64`), etc. Não há
  um ponto de extensão limpo para "trocar `ArmCore` por `Aarch64Core`" sem reescrever a classe
  inteira ou introduzir genéricos em 800 linhas de código quente já delicado (regressão real em
  gbaemu/ndsemu não vale o risco, G5).
- `CompiledBlock` é `@FunctionalInterface int execute(ArmCore core)` — amarrado a `ArmCore`.

**Decisão (D0, mesmo padrão "sibling, não generalização" já usado em `ir64`/`core64`/
`decoder64`/`executor64`, e nomeadamente em `Aarch64ExclusiveMonitor` vs `core.ExclusiveMonitor`
na B6.3.4): criar um pacote-irmão `jit64/` com `CompiledBlock64`/`BlockKey64`/`BlockCache64`/
`JitRuntime64` estruturalmente paralelos aos de 32 bits, MAS DELIBERADAMENTE MAIS SIMPLES —
sem inline cache, sem encadeamento, sem tiering em background, sem invalidação por página.**
Justificativa da simplificação (não é só "copiar e enxugar por preguiça"): nenhuma dessas
features tem hoje um consumidor A64 que precise delas — não existe host A64 com hot loop medido
(armbox roda `hello-aarch64.elf`, um programa curto, síncrono, sem SMC), e replicar as
otimizações de 15 tasks de trilha C (`chainCycleBudget`, IC de 32K slots, superblocos) sem um
caso de uso real para validar contra seria puro cargo-cult, arriscando bugs sutis sem teste de
regressão real para pegá-los. Cada uma dessas features fica como pendência EXPLÍCITA (ver
Armadilhas) para quando um host A64 real precisar — mesma disciplina que B6.1-B6.3.4 já
seguiram ("fora do escopo desta task", não "peça de campo minado escondida").

`ExecutionThreshold` (`jit/ExecutionThreshold.java`) **é** genérico o bastante (só `int
hotCount`, nenhuma referência a `ArmCore`/`int pc`) — **decisão: REUSAR diretamente**, sem
sibling. Único componente do pacote `jit` reaproveitado por este PR.

## Decisões de desenho fechadas nesta rodada

### D1 — `Ir64Block`/`Ir64BlockLifter` (novos, faltam desde B6.1)

Espelho estrutural de `ir/IrBlock.java`/`ir/IrBlockLifter.java`, com `long startPc/endPc` (A64
usa endereços de 64 bits — a analogia direta do `int` de 32 bits quebraria em qualquer VA acima
de 4 GiB). `StandardIr64BlockLifter` é MAIS SIMPLES que `StandardIrBlockLifter` (32-bit) porque
`Aarch64Decoder.decode` já devolve `Ir64Op` diretamente — não há estágio `DecodedInstruction`+
`IrBuilder` para atravessar. O laço do lifter:

```
para cada instrução (até maxInstructions):
    emite Fetch(endereço, 4)
    emite Cycle(1)
    op = decoder.decode(memory, pc)
    emite op
    se op é terminal (Branch64, CompareBranch64, Svc) -> para
    pc += 4
```

Terminal = `Branch64`/`CompareBranch64` (podem trocar o PC) e `Svc` (pode ter efeito colateral
arbitrário via `Aarch64SvcHandler` — mesmo precedente de `IrOp.Swi`/`IrOp.Coprocessor` no lifter
32-bit terminarem o bloco). Nenhum outro `Ir64Op.Kind` troca o PC (A64 não tem "MOV PC,..."
genérico — só as formas de desvio dedicadas), então nada mais é terminal.

### D2 — Reaproveitar a lógica de execução do `Ir64BlockExecutor`, não duplicá-la (G1 por construção)

Dois métodos públicos novos e pequenos em `Ir64BlockExecutor` (aditivos, corpo delega às
private já existentes — zero duplicação de lógica):

```java
/// Executa uma única operação já decodificada (sem repetir fetch/cycle) — usado pelo backend
/// ASM (B6.4) para despachar através do MESMO caminho do interpretador, garantindo G1 por
/// CONSTRUÇÃO (chama a mesma implementação, não uma reescrita). `Cycle`/`Fetch` não são
/// aceitos aqui — ver {@link #executeBlock}.
public boolean executeOp(Aarch64Core core, Ir64Op op) { return execute(core, op); }

/// Executa um {@link Ir64Block} inteiro (Fetch/Cycle tratados inline, demais ops via
/// {@link #executeOp}) — oráculo de bloco usado pelo backend interpretado do B6.4 e pelo
/// harness de equivalência.
public int executeBlock(Aarch64Core core, Ir64Block block) { ... }
```

`executeBlock` sabe, EM TEMPO DE COMPILAÇÃO DO PRÓPRIO MÉTODO (não em tempo de execução), que
o PC de fallthrough de cada instrução não-terminal é `fetch.address() + 4` (a mesma informação
que o `Ir64BlockCompiler`, D3 abaixo, usa para fixar o próximo PC como CONSTANTE no bytecode
gerado — os dois pontos derivam da mesma garantia estrutural do lifter: ops aparecem em grupos
`[Fetch, Cycle, op]` na ordem do PC linear).

### D-ASM — Bytecode do PR1 delega ao `Ir64BlockExecutor` compartilhado, não reimplementa aritmética

Decisão explícita (evita reimplementar `addWithFlags`/`subWithFlags`/`logicalWithFlags`/
avaliação de condição em bytecode bruto, que duplicaria lógica já auditada e teria que ser
re-testada do zero — G1 por reimplementação é mais fraco que G1 por reuso direto): o bytecode
gerado por `Ir64BlockCompiler` (PR1), para cada `Ir64Op` real do bloco, **reconstrói o record
exato** (`NEW`+`DUP`+campos como constantes de compilação+`INVOKESPECIAL <init>`) e chama
`Ir64AsmRuntimeHelpers.executeOp(Aarch64Core, Ir64Op)` (que delega a
`Ir64BlockExecutor#executeOp`, D2) — depois, se o retorno for `false` (PC não mudou), emite
`core.setProgramCounter(nextPcConstante)` (o "próximo PC" já é conhecido em tempo de
compilação, D1/D2).

**Consequência honesta, registrada aqui para não ser lida como alegação de performance**: este
bytecode NÃO inlina aritmética em locais de registrador (ao contrário do `AsmBlockCompiler`
32-bit maduro, que usa um cache de registrador com locais JVM dedicados por `Rn` — 2493 linhas
de engenharia acumulada ao longo de ~15 tasks). Para o conjunto de ops do PR1, o caminho
"ASM" e o caminho "interpretado64" (`InterpretedIr64CodeEmitter`, que só chama
`executeBlock`) fazem chamadas equivalentes por op — a única economia real do PR1 é pular o
`switch` externo de despacho por `Ir64Op.Kind` do laço do interpretador substituindo-o por uma
sequência linear de `INVOKESTATIC`s already-resolved at compile time (bytecode JIT-friendly do
HotSpot/JBR pode inlinear essa sequência melhor que um `switch` sobre `kind()` a cada iteração,
mas isso não foi medido nesta task). **O ganho de performance de verdade (registrador em
`long` local, aritmética direta sem reconstrução de record por chamada, sem despacho por
`Kind`) é trabalho explícito de uma PR futura** (dentro do próprio B6.4 se o usuário priorizar
retomar, ou registrado como pendência do épico) — replicar a arquitetura de cache de
registrador de 2493 linhas do 32-bit dentro desta sessão não é um escopo realista (ver
Contexto/D0). O Aceite do PR1 (abaixo) reflete isto: equivalência + pipeline funcionando,
SEM meta de performance.

### D3 — `Ir64NativePolicy`/`Ir64CodeEmitter`: espelho de `AsmNativePolicy`/`AsmCodeEmitter` (política `WHOLE_BLOCK` apenas)

`Ir64CodeEmitter` (interface, `codegen64/`): `CompiledBlock64 emit(Ir64Block block)`.
`InterpretedIr64CodeEmitter` (`emit` = fecha uma closure sobre um `Ir64BlockExecutor`
compartilhado + `executeBlock`). `Asm64CodeEmitter` decide, via `Ir64NativePolicy.supports
(block)`, entre delegar ao interpretado (`WHOLE_BLOCK`, única política do PR1 — `PER_OP`/
`FAIL_FAST` do 32-bit ficam fora, sem caso de uso ainda) ou compilar nativamente
(`Ir64BlockCompiler`). PR1: `Ir64NativePolicy.supports(Ir64Op)` é `true` só para
`ALU64`/`MOVE_WIDE`/`PC_RELATIVE`/`BRANCH64`/`COMPARE_BRANCH64`/`CYCLE`/`FETCH`; `false` para
todo o resto (`SVC`, loads/stores, B6.3.x) — PR2/PR3 ligam os `case`s restantes.

### D4 — `Aarch64GuestToHostMapper`

Sibling pequeno de `codegen/jvm/GuestToHostMapper` (reusa o `record HostMethodBinding` já
genérico daquele pacote — não é ARM-32-específico, é só `(owner, name, descriptor)`, decisão
por componente conforme D0: aqui um sibling seria puro boilerplate). PR1 só precisa de 3
bindings: `Aarch64Core#memory()`, `Aarch64Core#addCycles(long)`,
`Aarch64Core#setProgramCounter(long)` (mais `AddressSpace64#accessCycles` para o `Fetch`,
tipado como método de interface — `INVOKEINTERFACE`). Loads/stores de PR2 adicionam o resto.

### D5 — `BlockKey64`/`BlockCache64`/`JitRuntime64` minimalistas (ver D0)

`record BlockKey64(long pc)` — sem `instructionSet` (A64 não tem Thumb), sem `itState` (não
existe), sem `translationGeneration` (sem MMU A64 ainda, B6.6 futuro). `BlockCache64`: mapa
simples `pc -> CompiledBlock64` + contagem de hits para `ExecutionThreshold`, **sem
invalidação por escrita/página** (pendência explícita — ver Armadilhas: nenhum host A64 atual
sofre código automodificável). `JitRuntime64.execute(long pc, Aarch64Core core)`: caminho
"clássico" do 32-bit (pré-tiering) — sem cache, interpreta via `Ir64BlockExecutor.step` (uma
instrução, cold); ao atingir o threshold, faz lift do bloco (D1) e compila via `emitter.emit`
(D3), cacheia e executa. **Sem inline cache, sem encadeamento, sem compilação em background**
(D0) — cada chamada de `execute` faz UM lookup de `HashMap` (aceitável para o volume atual sem
medição que justifique otimizar às cegas).

## Testes mínimos

- `Ir64BlockExecutorTest` (novo método/classe): `executeBlock` sobre um bloco de 3-4
  instruções retas (`MOVZ`/`MOVK`/`ADD` imediato) produz o mesmo estado final que chamar
  `step()` a mesma quantidade de vezes.
- `StandardIr64BlockLifterTest`: bloco termina em `Branch64`/`CompareBranch64`/`Svc`; bloco
  reto (`MOVZ`×`maxInstructions`) para no limite; ops aparecem na ordem `[Fetch,Cycle,op]` por
  instrução.
- `BlockEquivalenceHarness64Test` (ou reaproveitando um teste de equivalência dedicado):
  para cada `Ir64Op` do conjunto do PR1 (`Alu64` ADD/SUB/AND/ORR/EOR com/sem `setFlags`,
  `MoveWide` MOVZ/MOVN/MOVK, `PcRelative` ADR/ADRP, `Branch64` incondicional/`B.cond`
  tomado/não-tomado/`BLR`/`RET`, `CompareBranch64` CBZ/CBNZ/TBZ/TBNZ tomado/não-tomado),
  `InterpretedIr64CodeEmitter` e `Asm64CodeEmitter` produzem o MESMO `Aarch64CpuSnapshot` e os
  MESMOS ciclos internos — usando vetores reais do corpus já existente (`corpus.s`/`.bin`/
  `.objdump.txt` de B6.1-B6.3.4) sempre que o vetor já cobrir o caso; senão, bloco montado à
  mão sobre os records `Ir64Op` (não precisa reassemblar — o alvo é a equivalência do
  BACKEND, não o decode, já coberto pelos corpus tests anteriores).
- `Ir64NativePolicyTest`: `supports` `true` para os 7 kinds do PR1, `false` para o resto
  (incl. `Svc` — ainda fora, PR2).
- `JitRuntime64Test`: um `pc` executado `threshold.hotCount()` vezes fica frio (interpretado,
  via `Ir64BlockExecutor.step`) até o limite, e QUENTE (bloco compilado, cache hit) depois —
  espiar `BlockCache64.size()`/contagem de hits; comportamento idêntico entre threshold=1
  (compila na primeira) e um threshold maior.

## Aceite (PR1)

- `mvn -o test` verde (JBR 25). G5 não se aplica — nenhum arquivo 32-bit tocado (só pacotes
  novos `jit64/`, `codegen64/`, mais os 2 métodos aditivos em `Ir64BlockExecutor` e o novo
  arquivo em `ir64/`; `Jvm64BlockLoader` em `codegen/jvm/` é aditivo, não modifica nenhum
  arquivo existente daquele pacote).
- `BlockEquivalenceHarness64` prova que `InterpretedIr64CodeEmitter` e `Asm64CodeEmitter`
  concordam byte-a-byte em `Aarch64CpuSnapshot` + ciclos para o conjunto de ops do PR1.
- **Sem meta de performance** (D-ASM) — "busybox ≥3× interpretador" do épico só é cobrado ao
  fechar PR3, com o registrador-cache que entrega o ganho real.
- Corpus/toolchain: nenhum vetor NOVO precisa ser assemblado nesta PR (reusa o corpus
  existente de B6.1-B6.3.4 para os vetores de equivalência sempre que cobrir o caso).

## Armadilhas

- **Não confundir "backend ASM funcionando" com "backend ASM rápido"** (D-ASM) — o PR1 entrega
  pipeline+equivalência, não performance; qualquer decisão de priorização futura deveria medir
  antes de otimizar (mesma lição que várias tasks da trilha C já registraram).
- **`jit64/` NÃO tem inline cache, encadeamento, tiering em background nem invalidação por
  escrita** (D0/D5) — pendências explícitas, não esquecimentos. Um host A64 futuro com código
  automodificável (SMC) ou um hot loop medido precisa de uma task própria para cada uma —
  não adicionar "de graça" sem um consumidor real e teste de regressão para validar (mesmo
  raciocínio do próprio D0).
- **`Jvm64BlockLoader` mora em `codegen/jvm/`, não `codegen64/jvm64/`** (Especificação #6) —
  única exceção à convenção de pacote desta task, por reaproveitar `JvmBlockClassLoader`
  package-private; documentado para não gerar confusão numa sessão futura.
- **G4 continua valendo mesmo sem predicação geral em A64**: `Cycle`/`Fetch` nunca ganham guard
  condicional no bytecode gerado — trivialmente satisfeito aqui porque nenhum op do conjunto
  do PR1 pula o `Cycle`/`Fetch` da própria instrução (branches não-tomados ainda consumem o
  ciclo/fetch da instrução de desvio em si, só não tomam o desvio) — mas registrar a invariante
  explicitamente para PR2/PR3 (loads/stores condicionais não existem em A64 fora de `CSEL`, que
  não é load/store, então o risco é baixo, mas a disciplina é a mesma do 32-bit).
- **`Ir64AsmRuntimeHelpers` reconstrói o record `Ir64Op` a cada chamada** (D-ASM) — um `record`
  Java é barato (alocação simples, sem overhead de reflexão), mas isto SOMA para um loop
  quente; é o preço documentado da decisão de reuso direto sobre reimplementação — aceitável
  para o PR1, candidato natural de otimização quando a PR de registrador-cache chegar.
- **B6.2 aceite #2 / B6.3 aceite agregado (busybox aarch64) seguem bloqueados no usuário**
  (toolchain `aarch64-linux-*`/musl real ausente, ver `tasks/FILA-EXECUCAO.md` seção 🧑) — não
  afeta o PR1 (trabalho 100% testável sem binário real), mas o aceite final do PR3 ("busybox
  ≥3× interpretador") herda o MESMO bloqueio: sem um busybox aarch64 real para medir, o número
  de performance do épico fica também pendente até esse ambiente existir.

### Sub-família 1 — os quatro blocos `{}` sobrepostos (linhas 223-279, 30 linhas)

O comentário do arquivo explica por que `VSHLL` T2 mora aqui e não com os deslocamentos por imediato
(B16.10):

```
# The VSHLL T2 encoding is not a @2op pattern, but is here because it
# overlaps what would be size=0b11 VMULH/VRMULH
{
  VCVTB_SH       111 0 1110 0 . 11 1111 ... 0 1110 0 0 . 0 ... 1 @1op_nosz
  VMAXNMA        111 0 1110 0 . 11 1111 ... 0 1110 1 0 . 0 ... 1 @vmaxnma size=2
  VSHLL_BS       111 0 1110 0 . 11 .. 01 ... 0 1110 0 0 . 0 ... 1 @2_shll_esize_b
  VSHLL_BS       111 0 1110 0 . 11 .. 01 ... 0 1110 0 0 . 0 ... 1 @2_shll_esize_h
  VQMOVUNB       111 0 1110 0 . 11 .. 01 ... 0 1110 1 0 . 0 ... 1 @1op
  VQMOVN_BS      111 0 1110 0 . 11 .. 11 ... 0 1110 0 0 . 0 ... 1 @1op
  VMAXA          111 0 1110 0 . 11 .. 11 ... 0 1110 1 0 . 0 ... 1 @1op
  VMULH_S        111 0 1110 0 . .. ...1 ... 0 1110 . 0 . 0 ... 1 @2op
}
```
e os três blocos gêmeos (`VCVTB_HS`/`VSHLL_BU`/`VMOVNB`/`VQMOVN_BU`/`VMULH_U`;
`VCVTT_SH`/`VMINNMA`/`VSHLL_TS`/`VQMOVUNT`/`VQMOVN_TS`/`VMINA`/`VRMULH_S`;
`VCVTT_HS`/`VMINNMA`/`VSHLL_TU`/`VMOVNT`/`VQMOVN_TU`/`VRMULH_U`).

Formatos envolvidos (linhas 75-78, 101-105, 143-146):

```
@1op      .... .... .... size:2 .. .... .... .... .... &1op qd=%qd qm=%qm
@1op_nosz .... .... .... .... .... .... .... .... &1op qd=%qd qm=%qm size=0
# VSHLL encoding T2 where shift == esize
@2_shll_esize_b .... .... .... 00 .. .... .... .... .... &2shift qd=%qd qm=%qm size=0 shift=8
@2_shll_esize_h .... .... .... 01 .. .... .... .... .... &2shift qd=%qd qm=%qm size=1 shift=16
# 2-operand, but Qd and Qn share a field. Size is in bit 28, but we don't decode it in this format
@vmaxnma  .... .... .... .... .... .... .... .... &2op qd=%qd qn=%qd qm=%qm
```

### Sub-família 2 — complexos FP e dual-accumulate inteiros (linhas 325-350, 14 linhas)

```
{ VCMUL0    111 . 1110 0 . 11 ... 0 ... 0 1110 . 0 . 0 ... 0 @2op_sz28
  VQDMLADH  1110  1110 0 . .. ... 0 ... 0 1110 . 0 . 0 ... 0 @2op
  VQDMLSDH  1111  1110 0 . .. ... 0 ... 0 1110 . 0 . 0 ... 0 @2op }
{ VCMUL180 / VQDMLADHX / VQDMLSDHX }
{ VCMUL90  / VQRDMLADH / VQRDMLSDH }
{ VCMUL270 / VQRDMLADHX / VQRDMLSDHX }
VQDMULLB  111 . 1110 0 . 11 ... 0 ... 0 1111 . 0 . 0 ... 1 @2op_sz28
VQDMULLT  111 . 1110 0 . 11 ... 0 ... 1 1111 . 0 . 0 ... 1 @2op_sz28
```

com `%size_28 28:1 !function=plus_1` (`@2op_sz28`: tamanho 1 ou 2 vindo do bit 28) — note que nesses
blocos o bit 28 deixa de ser o `U` de signed/unsigned e passa a ser tamanho, o que é justamente por
que as formas convivem num `{}`.

### Sub-família 3 — a seção `# 2-operand FP` (linhas 771-789, 14 linhas)

```
# 2 operand fp insns have size in bit 20: 1 for 16 bit, 0 for 32 bit, like Neon FP insns.

%2op_fp_size_rev 20:1 !function=plus_1
```

Total: 30 + 14 + 14 = **58**.

### Gate de feature: `MVE_FLOAT`, não `MVE_INTEGER`

As formas FP desta task (`VADD_fp`…`VCMLA270`, `VCMUL*`, `VMAXNMA`/`VMINNMA`, `VCVTB_SH`/`VCVTT_SH`/
`VCVTB_HS`/`VCVTT_HS`) exigem `FEAT_MVE_FP`. A **B16.1** criou `ArmFeature.MVE_FLOAT` exatamente
para isso. As formas inteiras da sub-família 1/2 (`VSHLL_*` T2, `VQMOVN*`/`VMOVN*`, `VMAXA`/`VMINA`,
`VMULH`/`VRMULH`, `VQDML*DH*`, `VQDMULL*`) ficam em `MVE_INTEGER`. **Isso é gate por linha, não por
task** — e é a armadilha nº 1.

## Objetivo

As 58 linhas decodificam sob o gate correto (`MVE_INTEGER` ou `MVE_FLOAT`, por linha) e executam com
predicação por elemento, reusando o núcleo `AdvSimdLanes` (que já tem `fpThreeSame`,
`fpComplexAdd`, `fpComplexMultiplyAccumulate`, `maxNum`/`minNum`, `halfBits`/`halfToFloat`,
`shiftWidenImmediate`, `narrow`). 58 células `·`/`❌` → `✅`.

   primeiro: `VCVTB_SH` tem `bits[19:16]=1111` fixo, `VSHLL_*` tem `bits[17:16]=01`, `VMULH_*` tem

## Armadilhas

1. **Gate por LINHA, não por task.** Misturar `MVE_INTEGER`/`MVE_FLOAT` num gate único faria um
   Cortex-M com Helium inteiro-apenas executar FP vetorial — falso positivo de arquitetura, o mesmo
   tipo de erro que a B12.4 recusou cometer com `Cortex-M3`/`ARMV7M`.
2. **`bit28` muda de significado entre formas do MESMO bloco `{}`**: é `U` (signed/unsigned) em
   `VMULH_S`/`VMULH_U`, e é TAMANHO em `@2op_sz28` (`%size_28 28:1 !function=plus_1`) em
   `VCMUL*`/`VQDMULL*`. Extrair `U` cru e usá-lo para os dois é misdecode silencioso.
3. **`VSHLL` T1 (B16.10) e T2 (esta task) são encodings diferentes com o mesmo mnemônico.** O
   comentário do arquivo é explícito em dois lugares ("the T2 VSHLL encoding is elsewhere in this
   file" / "The VSHLL T2 encoding is not a @2op pattern, but is here because it overlaps what would
   be size=0b11 VMULH/VRMULH"). Se o decoder desta task reivindicar o espaço T1, as 8 células da
   B16.10 saltam para `✅` erradas — medir o delta.
4. **`Thumb2NocpDecoder` e `Thumb2VfpDecoder`**: `VCADD90_fp`/`VCADD270_fp`/`VCMLA*` são
   `1111 110x` — o espaço "extension register load/store" do VFP, que o `VfpDecoder` reivindica
   **sem checar `bits[31:28]`** (bug G8 achado pela B14). Esta é a sub-família MVE com maior risco
   real de ser roubada pelo VFP. Verificar a lista de decoders do preset e, se a colisão for real,
   **reportar** (é candidata a correção na B14), não contornar.
5. **`VQDMLADH`/`VQDMLSDH` e variantes `X`/`R` são "dual accumulate" com troca de metades** —
   semântica cheia de detalhe (halving, rounding, exchange). Transcrever `DO_VQDMLADH` do
   `mve_helper.c`; não derivar de `SQDMULH`.
6. **`fp16`**: o `FPSCR` deste projeto foi modelado para VFP escalar (B3.3/B3.8). Se
   `RMODE`/`FZ`/`DN` não se aplicarem igual em MVE FP, isso é pendência a documentar, não a
   aproximar (G8 aplicado a semântica numérica).
7. **G4** e a regra de `QC` só para lanes ativas.

## Não fazer

- Não implementar `VSHLL` T1 (B16.10) nem `VCVT`/`VRINT` das linhas 798-832 (B16.12).
- Não usar um gate único de feature para inteiro e FP.
- Não derivar semântica de `VQDML*DH*`/`VCMUL*` por analogia; transcrever.
- Não tocar `VfpDecoder` (Armadilha 4).
- Não duplicar operação já presente em `AdvSimdLanes`.

**2 achados reais que corrigem a leitura ingênua do `.decode`** (medidos bit a bit contra o arquivo
real, não por suposição — a mesma disciplina de B16.6): (1) no slot `bits[17:16]=01,bit7=1`, `U=0`
produz `VQMOVUNB`/`T` (`SQXTUN`, saturante) mas `U=1` produz **`VMOVNB`/`T`** (`XTN`, PURO, sem
saturação) — não existe "VQMOVUN unsigned" nem "VMOVN signed"; os dois mnemônicos diferentes
compartilham o mesmo espaço de bits, discriminados só pelo bit que em toda a seção parece significar
"signed/unsigned". (2) `VMAXA`/`VMINA` **só existem para `U=0`** — `DO_VMAXMINA` não tem variante
"fonte unsigned" (`Qm` já é sempre assinado por construção, seu valor absoluto é tomado antes da
comparação), então `bits[17:16]=11,bit7=1,U=1` fica genuinamente não-alocado, não vira uma
"VMAXA unsigned" inventada — a primeira versão do decoder cometeu exatamente esse erro (testado e
corrigido antes de comitar).

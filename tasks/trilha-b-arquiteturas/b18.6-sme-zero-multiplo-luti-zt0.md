# B18.6 — SME multiple zero (`ZERO_za`) + lookup table read (`LUTI2`/`LUTI4`) + move into/from `ZT0` (`MOVT`) — 37 encodings

**Trilha:** B · **Repo:** arm-jitter (+ revalidação G5) · **Depende de:** B18.3
**Épico:** `b18-plano-sme.md` · **Status:** ⬜ (spec escrita 2026-09-14, ainda não executada)

## Contexto

Degrau 6 da escada B18 — e o que **fecha o registrador `ZT0`**, o segundo banco de estado que a
SME2 introduziu (512 bits, uma tabela de consulta em hardware). `LUTI2`/`LUTI4` são a operação que
justifica o `ZT0` existir: descompactar valores de 2 ou 4 bits em vetores completos, que é como
inferência quantizada vira código.

**Recorte normativo** (partição da B18.1, medida contra `target/isa-decode/sme.decode`):

| Bloco | Linhas | Enc |
|---|---|---:|
| `### SME Multiple Zero` (`ZERO_za`) | 1019-1041 | 8 |
| `### SME Lookup Table Read`, só a parte `LUTI` | 1042-1089 | 26 |
| `### SME Move into/from ZT0` (`MOVT`) | 139-145 | 3 |
| **Total** | | **37** |

> **Achados desta rodada de spec** (ver a B18.1 para o quadro completo): (a) as linhas 1090-1161 da
> seção `### SME Lookup Table Read` **não são lookup table** — são `MOP4` e `TMOP`, outer product,
> e vão para a **B18.5**; (b) as 3 linhas de `MOVT` vêm da seção `### SME Move into/from ZT0`, lá
> na frente do arquivo, e foram trazidas para cá porque é aqui que `ZT0` ganha sentido. O épico
> estimava "~40" para este degrau, e o número real é 37 — a diferença é exatamente o realinhamento
> acima.

### Os encodings reais

**`ZERO_za`** (8) — a forma multi-vetor de `ZERO`, com combinações de `ngrp`(1/2/4) × `nvec`(1/2/4):

```
&zero_za        rv off ngrp nvec

ZERO_za         11000000 000011 000 .. 0000000000 off:3 \
                &zero_za ngrp=2 nvec=1 rv=%mova_rv
ZERO_za         11000000 000011 100 .. 0000000000 off:3 \
                &zero_za ngrp=4 nvec=1 rv=%mova_rv
ZERO_za         11000000 000011 001 .. 0000000000 ...   \
                &zero_za ngrp=1 nvec=2 rv=%mova_rv off=%off3_x2
ZERO_za         11000000 000011 010 .. 0000000000 0..   \
                &zero_za ngrp=2 nvec=2 rv=%mova_rv off=%off2_x2
ZERO_za         11000000 000011 011 .. 0000000000 0..   \
                &zero_za ngrp=4 nvec=2 rv=%mova_rv off=%off2_x2
ZERO_za         11000000 000011 101 .. 0000000000 0..   \
                &zero_za ngrp=1 nvec=4 rv=%mova_rv off=%off2_x4
ZERO_za         11000000 000011 110 .. 0000000000 00.   \
                &zero_za ngrp=2 nvec=4 rv=%mova_rv off=%off1_x4
ZERO_za         11000000 000011 111 .. 0000000000 00.   \
                &zero_za ngrp=4 nvec=4 rv=%mova_rv off=%off1_x4
```

**Um mnemônico, 8 encodings**: os 3 bits `bits[18:16]` codificam o par (`ngrp`,`nvec`), e o `off`
muda de largura e de **escala** (`%off3_x2`, `%off2_x2`, `%off2_x4`, `%off1_x4`) conforme o par.

**`MOVT` de/para `ZT0`** (3):

```
MOVT_rzt        1100 0000 0100 1100 0 off:3 00 11111 rt:5
MOVT_ztr        1100 0000 0100 1110 0 off:3 00 11111 rt:5
MOVT_ztz        1100 0000 0100 1111 00 off:2 00 11111 rt:5
```

`MOVT_rzt` = `ZT0[off] → X<rt>`; `MOVT_ztr` = `X<rt> → ZT0[off]`; `MOVT_ztz` = forma vetorial.
Note o `11111` fixo no meio — um campo de registrador forçado a `ZR`, que é como o encoding
distingue estas formas.

**`LUTI2`/`LUTI4`** (26) — consulta em `ZT0` com índice de 2 ou 4 bits, em variantes
**consecutivas** (`_c_`, destino são registradores consecutivos) e **strided** (`_s_`, destino
espaçado), com 1, 2 ou 4 vetores de destino e elemento `b`/`h`/`s`:

```
&lut            zd zn idx

# LUTI2, consecutive
LUTI2_c_1b      1100 0000 1100 11 idx:4    00 00 zn:5 zd:5      &lut
LUTI2_c_2b      1100 0000 1000 11 idx:3  1 00 00 zn:5 .... 0    &lut zd=%zd_ax2
LUTI2_c_4b      1100 0000 1000 11 idx:2 10 00 00 zn:5 ... 00    &lut zd=%zd_ax4

# LUTI2, strided (must check zd alignment)
LUTI2_s_2b      1100 0000 1001 11 idx:3  1 00 00 zn:5 zd:5      &lut
LUTI2_s_4b      1100 0000 1001 11 idx:2 10 00 00 zn:5 zd:5      &lut

# LUTI4, consecutive
LUTI4_c_1b      1100 0000 1100 101 idx:3    00 00 zn:5 zd:5     &lut
LUTI4_c_4b      1100 0000 1000 101     1 00 00 00 ....0 ...00   \
                &lut zd=%zd_ax4 zn=%zn_ax2 idx=0
LUTI4_s_4b      1100 0000 1001 101     1 00 00 00 ....0 zd:5    \
                &lut zn=%zn_ax2 idx=0
```

Os 26 mnemônicos: `LUTI2_c_{1,2,4}{b,h,s}` (9), `LUTI2_s_{2,4}{b,h}` (4), `LUTI4_c_{1}{b,h,s}` +
`LUTI4_c_{2}{b,h,s}` + `LUTI4_c_4{h,s}` + `LUTI4_c_4b` (9), `LUTI4_s_{2}{b,h}` + `LUTI4_s_4h` +
`LUTI4_s_4b` (4). **Repare nas assimetrias reais**: existe `LUTI2_c_4s` mas **não** existe
`LUTI2_s_4s`; existe `LUTI4_c_4h`/`_4s` com `idx:1`, mas `LUTI4_c_4b` tem `idx=0` **fixo** e `zn`
vindo de `%zn_ax2` (um par de vetores). A tabela não é um produto cartesiano.

O comentário do próprio `.decode` é um requisito de implementação:
`# LUTI2, strided (must check zd alignment)`.

### `ZT0`, e o gate

`ZT0` é `FEAT_SME2`; as formas com `zd=%zd_ax4`/tabela estendida podem exigir `FEAT_SME_LUTv2`
(`dc_isar_feature(aa64_sme_lutv2, s)` no QEMU — um dos 8 predicados medidos na B18.1). O acesso a
`ZT0` tem **checagem própria** no QEMU, distinta da de `ZA`:

```c
bool sme2_zt0_enabled_check(DisasContext *s)
{
    if (!sme_za_enabled_check(s)) return false;
    if (s->zt0_excp_el) {
        gen_exception_insn_el(s, 0, EXCP_UDEF,
                              syn_smetrap(SME_ET_InaccessibleZT0, false),
                              s->zt0_excp_el);
        return false;
    }
    return true;
}
```

— ou seja `ZT0` acessível **implica** `ZA` acessível, mas não o contrário, e a síndrome é
`SME_ET_InaccessibleZT0`, própria.

## Objetivo

`ZERO_za`, `MOVT` (3 formas) e as 26 formas de `LUTI2`/`LUTI4` decodificam sob `FEAT_SME2`
(`FEAT_SME_LUTv2` onde aplicável) e executam contra `ZA`/`ZT0`. `docs/COBERTURA-ISA.md`: 37 células
saem de `❌`.

## Inclui

1. **Decode das 37 linhas**, com os extratores de `off` escalado (`%off3_x2`, `%off2_x2`,
   `%off2_x4`, `%off1_x4`) e os de registrador múltiplo (`%zd_ax2`, `%zd_ax4`, `%zn_ax2`)
   **transcritos**, não deduzidos.
2. **`ZERO_za`**: zera `ngrp × nvec` vetores do array `ZA` a partir do índice
   `(W<rv> + off) MOD (SVL/8)`, com `rv = bits[14:13] + 8` (`W8`-`W11`).
3. **`MOVT`**: transferência entre `ZT0` e um GPR/vetor, com `off` indexando dentro dos 512 bits.
4. **`LUTI2`/`LUTI4`**: para cada elemento do destino, índice tirado de `Zn` (2 ou 4 bits, com o
   deslocamento vindo de `idx`), valor lido de `ZT0`, replicado no elemento de destino de largura
   `b`/`h`/`s`. Variantes consecutive (destino `Zd`, `Zd+1`, …) e strided (destino espaçado — o
   espaçamento **tem** que ser medido contra o manual, não suposto), com verificação de alinhamento
   de `zd` nas formas strided.
5. **Checagem de acesso a `ZT0`** (a da B18.1), com a síndrome própria; `ZERO_za` usa a de `ZA`.
6. **Gates**: `FEAT_SME2` para tudo; `FEAT_SME_LUTv2` onde o QEMU o exigir (medir instrução a
   instrução, não por família).
7. Testes (ver Aceite).

## Não inclui

- **`MOP4`/`TMOP`** (linhas 1090-1161) — **B18.5**, apesar de estarem na mesma seção `###` do
  arquivo. Este é o principal risco de sobreposição entre as duas tasks: quem executar esta task
  primeiro deve **parar** ao chegar na linha 1090 (`# SME MOP4 Quarter-tile outer products`).
- **`ZERO`/`ZERO_zt0`** das linhas 24-25 — B18.3.
- **`MOVA`/`MOVAZ`** (B18.3), memória (B18.4), outer product (B18.5), SME2 multi-vector (B18.7+).
- **Emissão nativa/Truffle.**

## Aceite

- As **37** células saem de `❌`, e nenhuma outra muda — em particular, **as 31 células de
  `MOP4`/`TMOP` continuam `❌`** (o teste de que a task parou na linha certa; precedente do achado
  da B15.2, em que uma máscara larga demais acendeu células de tasks futuras).
- **Round-trip de `ZT0`**: `MOVT_ztr` escreve, `MOVT_rzt` lê de volta o mesmo valor, para todos os
  valores de `off`.
- **`LUTI` de verdade**: com `ZT0` preenchido com um padrão conhecido e `Zn` com índices
  conhecidos, o destino contém exatamente a tabela consultada — teste para `LUTI2` e `LUTI4`, para
  `b`/`h`/`s`, e para 1/2/4 vetores de destino.
- **Strided ≠ consecutive**: o mesmo teste nas duas variantes produz destinos em registradores
  DIFERENTES — sem essa asserção, "strided implementado como consecutive" passa.
- **Alinhamento de `zd` nas formas strided** é verificado (o comentário do `.decode` é explícito);
  um `zd` desalinhado é recusado, não silenciosamente aceito (G8).
- **`ZERO_za` zera `ngrp × nvec` vetores**, e só eles — teste que preenche `ZA` inteiro, zera um
  grupo e confere que o resto sobreviveu, para os 8 pares (`ngrp`,`nvec`).
- **`off` escalado**: `%off2_x2` com `off=1` acessa o vetor 2, não o 1 (teste que distingue as 4
  escalas).
- Acesso a `ZT0` sem permissão gera a síndrome própria de `ZT0`, não a de `ZA`.
- Sem `FEAT_SME2`, as 37 continuam `UNIMPLEMENTED`.
- Testado em pelo menos dois `SVL` (256 e 512).
- `mvn -o test` verde + G5 verde nos 5 consumidores.

## Armadilhas

1. **A fronteira com a B18.5 está no meio de uma seção `###`.** A linha 1090
   (`# SME MOP4 Quarter-tile outer products`) é o limite desta task. Um decoder que reivindique "a
   seção Lookup Table Read inteira" invade 31 encodings da B18.5.
2. **`ZT0` tem checagem de acesso PRÓPRIA** (`sme2_zt0_enabled_check` ⊃ `sme_za_enabled_check`,
   com `SME_ET_InaccessibleZT0`). Reusar a checagem de `ZA` produz a síndrome errada num caminho
   que software real inspeciona.
3. **A tabela `LUTI` não é um produto cartesiano.** Não existe `LUTI2_s_4s`; `LUTI4_c_4b` tem
   `idx=0` fixo e `zn=%zn_ax2`; `LUTI4_c_4h`/`_4s` usam `idx:1`. Gerar as 26 por laço sobre
   {2,4}×{c,s}×{1,2,4}×{b,h,s} produz encodings que não existem **e** deixa de fora os casos
   especiais. Transcrever linha a linha.
4. **`idx` muda de largura conforme a forma** (`idx:4` em `LUTI2_c_1*`, `idx:3` em `LUTI2_c_2*`,
   `idx:2` em `LUTI2_c_4*`, e `idx=0` fixo em `LUTI4_c_4b`/`LUTI4_s_4b`). A largura codifica quantos
   segmentos de `ZT0` existem para aquele tamanho de destino — não é arbitrária.
5. **`ZERO_za` é um mnemônico com 8 encodings.** A tentação é implementar "um `ZERO` parametrizado";
   o problema é que `off` muda de **largura e escala** a cada linha, então o campo tem que ser
   extraído por encoding, não uma vez só.
6. **`rv` aqui é `W8`-`W11`** (`%mova_rv = bits[14:13] + 8`), ao contrário do `rs` de `MOVA`
   (`W12`-`W15`) — mesma Armadilha 2 da B18.3, e em `ZERO_za` ela é o único registrador envolvido.
7. **`SVL`, nunca `VL`** — inclusive no `MOD` do índice de vetor de `ZERO_za`.

## Não fazer

- Não implementar `MOP4`/`TMOP` (B18.5) — parar na linha 1089.
- Não reusar a checagem de acesso de `ZA` para `ZT0`.
- Não gerar a família `LUTI` por loop (Armadilha 3).
- Não usar `VL` no lugar de `SVL`.
- Não adicionar caso nativo em `Ir64NativePolicy`.

# B11.9 — quinto gate real de feature A64: `FEAT_FlagM2` (`XAFLAG`/`AXFLAG`) + `CFINV` (`FEAT_FlagM`, gap deixado por B11.7)

**Trilha:** B · **Repo:** arm-jitter (+ revalidação G5 nos consumidores) · **Status:** ✅ fechada 2026-08-28
**Depende de:** B11.2 ✅ (fiação `Aarch64Architecture` no decoder), B11.3 ✅ (auditoria — catalogou
`XAFLAG`/`AXFLAG` como `ARMv8.5-A`/`FEAT_FlagM2`, já implementadas sem gate desde B8.2), B11.5 ✅
(`Aarch64Feature.FLAG_MANIPULATION_2` já existe e já está mapeada em `Aarch64Architecture.ARMV8_5_A`)

## Contexto

Quinta da escada de gate real iniciada por B11.4 (`FEAT_RDM`), B11.6 (`FEAT_WFxT`), B11.7
(`FEAT_FlagM`), B11.8 (`FEAT_NMI`). Como em B11.6/B11.7, o decoder DEFAULT (`ARMv8.0-A`) hoje aceita
`XAFLAG`/`AXFLAG` incondicionalmente — um Cortex-A53 real (`ARMv8.0-A`) não tem `FEAT_FlagM2`
(introduzida em `ARMv8.5-A`), então o gate é o comportamento correto, não uma restrição nova.

`XAFLAG`/`AXFLAG` vivem em `Aarch64Decoder#decodeFlagOrPstateImmediate`
(`Aarch64Decoder.java:2267`), dentro do bloco `op1 == SYSTEM_INSTRUCTION_FLAG_MANIP_OP1` — o MESMO
`switch` que também decodifica `CFINV` e cai no `PSTATE_FIELD_NOP` para `UAO`/`PAN`/`SPSel`. Isso é
diferente de B11.7 (que vivia num método privado dedicado, sem `switch` compartilhado).

## Achado real desta sessão: `CFINV` nunca foi gateado

`CFINV` é `FEAT_FlagM` (mesma feature de `RMIF`/`SETF8`/`SETF16`, ARM DDI 0487, `ARMv8.4-A`) — mas
B11.7 só tocou `decodeAddSubtractCarryOrFlags` (onde vivem `RMIF`/`SETF8`/`SETF16`). `CFINV` vive num
método DIFERENTE (`decodeFlagOrPstateImmediate`), nunca examinado por B11.7, e continua aceito
incondicionalmente pelo decoder default hoje — confirmado por leitura de código e por
`IsaCoverageReport#AARCH64_VERSION_REQUIREMENTS`, que mapeia `RMIF`/`SETF8`/`SETF16` para
`FLAG_MANIPULATION` mas NÃO tem entrada para `CFINV` (conta como baseline não classificado). É uma
violação de G8 (instrução deveria ser recusada em `ARMv8.0-A` e não é) na MESMA linha de código que
esta task já precisa tocar para gatear `XAFLAG`/`AXFLAG` — corrigido aqui em vez de virar uma task
`B11.x` separada só para 1 instrução no mesmo `switch`.

## Inclui

1. `Aarch64Decoder#decodeFlagOrPstateImmediate`, dentro do bloco `op1 ==
   SYSTEM_INSTRUCTION_FLAG_MANIP_OP1`:
   - `case SYSTEM_INSTRUCTION_FLAG_MANIP_OP2_CFINV` só decodifica quando
     `architecture.has(Aarch64Feature.FLAG_MANIPULATION)`.
   - `case SYSTEM_INSTRUCTION_FLAG_MANIP_OP2_XAFLAG`/`_AXFLAG` só decodificam quando
     `architecture.has(Aarch64Feature.FLAG_MANIPULATION_2)`.
   - Sem a feature correspondente, cai no `default -> throw unsupported(word, address)` já existente
     no `switch` (mesmo padrão G8 de B11.4/B11.6/B11.7/B11.8).
   - `UAO`/`PAN`/`SPSel` (`PSTATE_FIELD_NOP`) permanecem INCONDICIONAIS — cada um é a sua própria
     task futura (`PAN`/`UAO` na lista de 6 restantes; `SPSel` é baseline `ARMv8.0-A`, sem feature
     associada).
2. `Aarch64DecoderCorpusTest#cfinv`/`#xaflag`/`#axflag`: atualizar para esperar
   `UnsupportedOperationException` no `DECODER` default (`ARMv8.0-A`).
3. Teste novo `Aarch64FlagManipulation2DecoderTest` (mesmo padrão de
   `Aarch64FlagManipulationDecoderTest`, B11.7): decoder default rejeita as 3 palavras do corpus real
   (`0xd500401f`=`cfinv` offset `0x5a8`, `0xd500403f`=`xaflag` offset `0x5ac`, `0xd500405f`=`axflag`
   offset `0x5b0`); decoder `Aarch64Architecture.ARMV8_4_A` decodifica `cfinv` mas rejeita
   `xaflag`/`axflag` (prova que `FLAG_MANIPULATION`≠`FLAG_MANIPULATION_2`, `ARMv8.4-A` não implica
   `ARMv8.5-A`); decoder `ARMV8_5_A` decodifica os 3 (`ARMV8_5_A` estende `ARMV8_4_A`, ver
   `Aarch64Architecture.java:68-71`), com as mesmas asserções de campo que `Aarch64DecoderCorpusTest`
   já validava.
4. `mvn -o test` verde + `mvn -o install`; G5 nos 5 consumidores (nenhum usa `ARMV8_4_A`+ — zero-diff
   esperado, já que `CFINV`/`XAFLAG`/`AXFLAG` não são emitidas por toolchains alvo de `ARMv8.0-A`/
   raspi3).

  `FLAG_MANIPULATION_2` já mapeadas em `ARMV8_4_A`/`ARMV8_5_A`).
- `docs/COBERTURA-ISA.md` (o medidor por versão já reflete `XAFLAG`/`AXFLAG` corretamente desde
  B11.5; `CFINV` não tinha entrada nenhuma em `AARCH64_VERSION_REQUIREMENTS` antes desta task — ver
  Armadilhas — mas adicionar essa entrada é parte do Inclui #2/#3 acima só na medida em que os testes
  do decoder exigem, não uma regeneração do relatório).

## Armadilhas

- **`op1` já é checado ANTES deste `switch`** (achado da B8.3/B11.7, ver comentário de
  `SYSTEM_INSTRUCTION_FLAG_MANIP_OP1` em `Aarch64Decoder.java:561-570`) — não reintroduzir a
  colisão antiga com `SBSS`/`DIT`/`ALLINT` (que têm `op1` diferente).
  `IsaCoverageReport#AARCH64_VERSION_REQUIREMENTS` não tinha entrada para `CFINV` — se o mnemônico
  usado pelo relatório de cobertura for `"CFINV"`, considerar adicionar
  `AARCH64_VERSION_REQUIREMENTS.put("CFINV", Aarch64Feature.FLAG_MANIPULATION)` ao lado das entradas
  de `RMIF`/`SETF8`/`SETF16` (mesma feature) — checar se isso muda alguma contagem de
  `docs/COBERTURA-ISA.md` antes de decidir regenerar o relatório (fora do Inclui se não mudar nada
  observável).
- `ARMV8_4_A` tem `FLAG_MANIPULATION` mas NÃO `FLAG_MANIPULATION_2` — o teste novo precisa provar as
  duas direções (`cfinv` aceito, `xaflag`/`axflag` rejeitados) nesse arquiteture intermediária, não só
  no extremo `ARMV8_0_A`/`ARMV8_5_A`.

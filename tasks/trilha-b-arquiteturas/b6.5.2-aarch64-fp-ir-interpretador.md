# B6.5.2 — AArch64: `Ir64Op`s de FP escalar + executor interpretado

**Trilha:** B · **Depende de:** B6.5.1 (banco `Aarch64FpRegisters`) · **Repo:** arm-jitter

## Contexto

Segunda das 4 sub-tasks de B6.5 (ver decomposição em B6.5.1). Com o banco
pronto (B6.5.1), esta task cria a semântica: os `Ir64Op`s novos e o executor
interpretado (oráculo, G1) — mesma ordem que `b3.4-vfp-ir-interpretador.md`
seguiu para o VFP32 (IR+interpretador ANTES do decoder; os testes constroem IR
à mão). Decode fica em B6.5.3.

**Escopo literal do épico**: "FMOV/FADD/FMUL/FDIV/FCMP/FCVT". Ver Armadilhas
sobre a leitura ESTRITA de `FCVT` (só conversão float↔float de precisão —
`SCVTF`/`UCVTF`/`FCVTZS`/`FCVTZU`, conversão inteiro↔float, são mnemônicos
DIFERENTES e NÃO estão cobertos por esta leitura literal, mesmo sendo
prováveis candidatos a aparecer em `printf` de float de verdade).

## Fatos de referência (fontes: `ARM DDI 0487` C6.2 + QEMU
`target/arm/tcg/a64.decode` — para os `Ir64Op`s desta task, a REFERÊNCIA
NORMATIVA de encoding só chega em B6.5.3 — aqui os fatos relevantes são de
SEMÂNTICA, citados de onde já foram usados corretamente para o precedente
VFP32; CONFERIR contra o manual/QEMU na hora de implementar B6.5.3, não travar
esta task nisso)

1. **`FCMP`/`FCMPE` escrevem `PSTATE.NZCV` diretamente** (achado de B6.5.1,
   Fatos de referência #4) — ao contrário de `IrOp.VfpCompare` (32-bit), que
   escreve um `FpscrRegister.NZCV` separado do `CpsrRegister`, exigindo um
   segundo passo (`VfpSystemTransfer(read,15)`/`VMRS APSR_nzcv`) para chegar
   ao registrador de flags que os branches condicionais realmente leem. Em
   A64, o executor de `Fp64Compare` (D2 abaixo) chama
   `core.pstate().setNzcv(...)` diretamente — não existe um segundo record
   equivalente a `VfpSystemTransfer` para mover flags (não seria FPCR/FPSR
   fora de escopo por D2 de B6.5.1, seria algo que nem existe na ISA — a
   distinção FP-flags-vs-CPSR do AArch32 não tem paralelo em A64).
2. **Tabela NZCV do compare** (mesma tabela de `b3.4-vfp-ir-interpretador.md`
   linha 29, reaproveitável tal e qual — a semântica de comparação IEEE é a
   mesma família de resultado nos dois mundos): `eq→(N,Z,C,V)=(0,1,1,0)`,
   `lt→(1,0,0,0)`, `gt→(0,0,1,0)`, `unordered(NaN envolvido)→(0,0,1,1)`.
3. **Round-to-nearest-even fixo, sem flush-to-zero** (B6.5.1 D2) — aritmética
   via `float`/`double` puro do Java, mesma decisão nº 3 de
   `b3-armv7a-vfp.md`. `SQRT` fora do escopo literal do épico (não citado em
   "FMOV/FADD/FMUL/FDIV/FCMP/FCVT") — **não incluir `FSQRT`** nesta rodada
   (ver Armadilhas; diferente do VFP32, que tinha `SQRT` no enum
   `VfpOperation` desde o início por já estar no escopo fechado daquele
   épico).
4. **`FMOV` tem DUAS formas bem diferentes**: registrador↔registrador (`FMOV
   Sd, Sn`/`FMOV Dd, Dn` — cópia de bits, sem arredondamento) e
   imediato (`FMOV Sd, #imm`/`FMOV Dd, #imm` — mesmo `VFPExpandImm` de 8 bits
   já citado em `b3.5-vfp-decoder.md` linha 33, reaproveitável como
   ALGORITMO — mas a codificação do imediato em A64 tem seu próprio encoding
   de 8 bits, não necessariamente idêntico ao ARM32; CONFERIR na hora de
   B6.5.3). **Não existe** `FMOV Rt, Sn` (core↔FP) no escopo desta task —
   isso seria um record de transferência core↔FP (`VfpCoreTransfer`
   equivalente), que a leitura literal do épico NÃO cita; musl `printf` de
   float pode precisar dele para inspecionar bits de um double (`frexp`,
   etc.) — mesmo tipo de gap que a nota sobre `SCVTF`/`UCVTF` registra, ver
   Armadilhas.

## Decisões de desenho FECHADAS nesta rodada

### D1 — Sem campo `Condition` em nenhum record novo

Ao contrário de `IrOp.VfpAlu`/`VfpCompare` (32-bit, que carregam
`Condition condition` porque TODA instrução ARM/Thumb é condicional), os
`Ir64Op`s novos desta task **não têm campo de condição** — mesma disciplina já
documentada no javadoc de `Ir64Op` (`ir64/Ir64Op.java:9-13`): A64 não tem
predicação geral, só `Branch64` carrega uma condição de verdade. Isto é
consistente com TODOS os `Ir64Op`s existentes desde B6.1 (nenhum tem
`Condition`) — não introduzir uma exceção aqui.

### D2 — Records novos, `Kind` contíguo a partir de 20

`ir64/Ir64Op.java` tem hoje 19 subtipos selados, `Kind` de `0` a `19`
(`ir64/Ir64Op.java:24-61`). Novos records (nomes `Fp64*` para não colidir
com o namespace `Vfp*` de 32 bits, mesma disciplina de prefixo `Ir64`/`64`
já usada em todo o pacote):

```java
enum Fp64Operation { ADD, SUB, MUL, DIV, NEG, ABS, MOV /* registrador↔registrador, sem aritmética */ }
// SQRT/MLA/MLS/NMUL FORA (não citados na leitura literal do épico — ver Fatos de referência #3
// e Armadilhas; se aparecerem como bloqueio real do aceite "musl printf de float", tratar como
// achado que abre uma sub-task nova, não expandir aqui)

record Fp64Alu(Fp64Operation op, boolean doublePrecision, int vd, int vn, int vm) implements Ir64Op
// unárias (NEG/ABS/MOV) usam só vm; kind() = FP64_ALU = 20

record Fp64MoveImmediate(boolean doublePrecision, int vd, long immediateBits) implements Ir64Op
// kind() = FP64_MOVE_IMMEDIATE = 21 — mesmo VFPExpandImm citado nos Fatos de referência #4

record Fp64Compare(boolean doublePrecision, boolean compareWithZero,
                    boolean signalOnQuietNaN, int vn, int vm) implements Ir64Op
// kind() = FP64_COMPARE = 22 — escreve PSTATE.NZCV DIRETO (Fatos de referência #1),
// nomes vn/vm (não vd/vm) porque não escreve registrador FP nenhum

enum Fp64Conversion { F32_TO_F64, F64_TO_F32 }
// SÓ estas duas — leitura literal de "FCVT" (Fatos de referência #3/Armadilhas). NÃO incluir
// S32_TO_F32/S32_TO_F64/U32_TO_F32/U32_TO_F64/F32_TO_S32/F64_TO_S32/F32_TO_U32/F64_TO_U32
// (esses são SCVTF/UCVTF/FCVTZS/FCVTZU, mnemónicos DIFERENTES, fora da leitura literal do épico)

record Fp64Convert(Fp64Conversion conversion, int vd, int vm) implements Ir64Op
// kind() = FP64_CONVERT = 23
```

`kind()` de cada record: constante int, contígua a partir de `20`
(`FP64_ALU=20`, `FP64_MOVE_IMMEDIATE=21`, `FP64_COMPARE=22`,
`FP64_CONVERT=23`) — adicionar ao `final class Kind` existente
(`ir64/Ir64Op.java:37-61`), mesma técnica de `tableswitch` já documentada lá.
`Ir64Op` sealed `permits` (linha 24-29) ganha os 4 novos tipos.

### D3 — Sem `Fp64Load`/`Fp64Store`/`Fp64MultipleTransfer` nesta rodada

A leitura literal do épico não cita `VLDR`/`VSTR`/`VLDM`/`VSTM` equivalentes
(`LDR`/`STR` (SIMD&FP), `LDP`/`STP` (SIMD&FP)) — sem eles, um valor FP só pode
chegar/sair de registrador via `FMOV` imediato ou registrador↔registrador
(D2), nunca de/para memória. **Isto é uma limitação séria para o aceite
"binários musl com printf de float" real** (`printf` de double quase sempre
passa o argumento por pilha/memória em ABIs reais) — registrada explicitamente
como Armadilha, não resolvida aqui (fora da leitura literal do "Inclui").

## Objetivo

- `Fp64Alu` (`FADD`/`FSUB`/`FMUL`/`FDIV`/`FNEG`/`FABS`/`FMOV` reg↔reg).
- `Fp64MoveImmediate` (`FMOV` imediato, VFPExpandImm).
- `Fp64Compare` (`FCMP`/`FCMPE`, com/sem comparação-com-zero) — escreve
  `PSTATE.NZCV` direto.
- `Fp64Convert` (`FCVT` só F32↔F64).
- Executor interpretado (`executor64/Ir64FpExecutor.java` novo, sibling de
  `Ir64BlockExecutor`, ou métodos adicionados diretamente em
  `Ir64BlockExecutor` — decidir na hora conforme o tamanho real, mesma
  liberdade que `codegen/executor/IrVfpExecutor.java` teve como classe
  própria).

## Especificação

1. Os 4 records novos em `ir64/Ir64Op.java` (D2), com javadoc `///` em
   português citando `ARM DDI 0487` (seção a confirmar contra o manual antes
   de implementar) — mesmo padrão dos records existentes no arquivo.
2. `executor64/Ir64FpExecutor.java` (ou métodos em `Ir64BlockExecutor`):
   - `Fp64Alu`: aritmética via `core.fp().sFloat/dDouble` (Java `float`/
     `double` puro — D... ver Fatos de referência #3). `NEG`/`ABS` via
     manipulação do BIT DE SINAL (nunca `-x`/`Math.abs`, mesma armadilha
     crítica de `IrVfpExecutor` linha 56-59 — subtração/abs ingênuo quebra
     `-0.0` e payload de NaN). `MOV` (registrador↔registrador) é cópia de
     BITS crus (`setS(vd, s(vm))`/`setD(vd, d(vm))`), nunca via view
     float/double (evita qualquer canonicalização acidental).
   - `Fp64MoveImmediate`: `VFPExpandImm`-equivalente já decodificado pelo
     decoder (B6.5.3) — o executor só grava `immediateBits` cru.
   - `Fp64Compare`: tabela NZCV (Fatos de referência #2), sinaliza (lança
     `UnsupportedOperationException` central, mesmo padrão de "exceção de
     ponto flutuante não implementada" que B1.5/B3 já usam para o bit E de
     `VCMPE`/`signalOnQuietNaN`? **CONFERIR**: verificar se o precedente VFP32
     realmente trata `signalOnQuietNaN` como sinalização real ou só como um
     bit carregado sem efeito — `codegen/executor/IrVfpExecutor.java` é a
     fonte; espelhar o que ele faz, não inventar).
   - `Fp64Convert`: `(double) floatValue` / `(float) doubleValue` — cast
     direto do Java já é round-to-nearest correto para F32→F64 (sem perda,
     widening exato) e para F64→F32 (arredonda corretamente, IEEE 754 —
     mesma garantia que `IrVfpExecutor` já usa para `SQRT`).
3. Registrar os 4 `Kind`s novos como opacos/efeito-colateral nos passes de
   otimização A64 (se B6 já tiver algum pass próprio — **auditar**: RFC
   §5 item 7 diz "fold A64 em passes próprios"; se nenhum pass A64 existe
   ainda, esta task não precisa criar um só para isto, só documentar que os
   4 kinds novos NÃO devem ser tocados por um futuro pass sem tratamento
   explícito).

## Testes mínimos (`Ir64FpExecutorTest`, construir `Ir64Op` à mão)

1. `FADD`/`FSUB`/`FMUL`/`FDIV` single e double: vetores concretos (ex.
   `0.1f+0.2f` → bits exatos, mesmo vetor de `b3.4-vfp-ir-interpretador.md`
   item 1).
2. `FNEG`/`FABS` preservam payload de NaN e distinguem `+0.0`/`-0.0`
   corretamente (via bit de sinal, não `0-x`) — mesmo teste 3 do precedente.
3. `FMOV` registrador↔registrador: bits crus idênticos, incl. NaN payload,
   single e double, cross-size REJEITADO (S↔S e D↔D só — `doublePrecision`
   dos dois lados do record precisa bater; se o encoding real permitir mix,
   isso é achado de B6.5.3, não desta task).
4. `FMOV` imediato: os mesmos 4 vetores canônicos citados em
   `b3.5-vfp-decoder.md` linha 74-75 (1.0, -1.0, 0.5, 31.0), reaproveitando o
   algoritmo `VFPExpandImm` já testado para VFP32 como referência de
   comportamento (a codificação de bits pode diferir — isso é escopo de
   B6.5.3, aqui só testa o executor recebendo `immediateBits` já resolvido).
5. `FCMP`: os 4 quadrantes da tabela NZCV (eq/lt/gt/unordered com NaN),
   escrevendo `PSTATE.NZCV` — testar que `core.pstate()` reflete o resultado
   IMEDIATAMENTE, sem nenhum passo intermediário (ao contrário do VFP32).
6. `FCVT`: F32→F64 (widening exato) e F64→F32 (arredondamento correto,
   incl. vetor de perda de precisão) — incl. NaN preservando "quietness"
   (não a payload exata, já que widening/narrowing de NaN não preserva bits
   crus da mesma forma que `FMOV` — CONFERIR o comportamento exato do cast
   Java contra o esperado do IEEE 754 antes de fechar o teste).
7. Regressão: suíte completa de B6.1-B6.4 sem mudança.

## Armadilhas

- **Leitura literal de "FCVT" exclui conversão inteiro↔float** — `SCVTF`/
  `UCVTF`/`FCVTZS`/`FCVTZU` são mnemônicos diferentes e quase certamente
  necessários para `printf` de float/double funcionar de ponta a ponta em
  musl real (formatar um `int`/`long` como componente do algoritmo de
  impressão, ou converter o double de entrada para inteiro em alguma parte
  do path). **Não expandir esta task para cobri-los** — registrar aqui,
  bem alto, que o aceite agregado do épico B6.5 ("binários musl com printf
  de float") pode ficar bloqueado por este gap real até uma sub-task nova
  ser priorizada (mesmo padrão de honestidade que B6.3.1 usou para
  "Logical shifted register" e B6.3.4 usou para `LDXP`/`CAS`).
- **Falta de load/store FP (D3) é igualmente séria** — sem eles, um valor FP
  só circula entre registradores/imediato, nunca memória; ABIs reais (soft e
  hard-float) costumam passar `double` por pilha em várias situações
  (varargs de `printf`, por exemplo, SEMPRE passam por pilha na AAPCS64 —
  `printf(..., double)` é varargs). Registrar como o MESMO tipo de gap que a
  nota de `SCVTF`/`UCVTF` acima — ambos são candidatos fortes a bloquear o
  aceite "musl printf de float" mesmo com B6.5.1-B6.5.4 100% implementadas
  como especificado aqui.
- **`SQRT` fora do escopo** — diferente do VFP32 (que tinha desde o início),
  não incluir por conta própria; se o binário de aceite precisar, é achado
  que abre task nova, mesmo raciocínio dos dois itens acima.
- **`signalOnQuietNaN` (bit E de `FCMPE`)**: auditar o comportamento real do
  `IrVfpExecutor` (32-bit) antes de decidir se o executor A64 sinaliza de
  verdade ou só carrega o bit sem efeito — não assumir sem checar.
- **Citações de seção do manual marcadas "CONFERIR"** nesta task — mesma
  disciplina de B6.5.1: comportamento bem estabelecido, números de seção não
  verificados nesta rodada de spec.

# B4.0.3 — Validar Thumb-2 COMPLETO no armbox (pós-B2.6, com binário de compilador)

**Trilha:** B · **Depende de:** B2.6 · **Repo:** armbox · **Fecha:** armbox#1

## Contexto

B4.0.2 validou Thumb-2 no armbox só com o subconjunto data-processing (o preset da
época). Com B2.6 fechando o preset (4 extensões + BL/BLX de 32 bits), falta a
validação de nível 3 da matriz (`docs/VALIDACAO-ARQUITETURAS.md` do arm-jitter):
**código Thumb-2 gerado por compilador**, que usa load/store de 32 bits, IT blocks
e tabelas TBB à vontade — coisas que nenhum teste sintético cobre com a mesma
malícia.

Nota: a parte handwritten (torture estendido) já entra na PRÓPRIA B2.6 (passo 6).
Esta task é o degrau seguinte: compilador real.

## Inclui

1. `testdata/hello-thumb2.c` + rotinas com switch denso (força TBB/TBH), structs
   com bitfields e um qsort pequeno (força IT + cmp/branches), compilado
   `arm-none-eabi-gcc -mthumb -march=armv6t2 -Os -static` (mesma libc/receita dos
   testdata atuais; `-Os` gera mais IT blocks). Conferir via `objdump -d` que o
   binário contém: `ldr.w`, `strd`, `ldmia.w`, `tbb`, `it`/`itt`, `bl` — anexar o
   trecho no PR como prova.
2. Se a toolchain não tiver multilib armv6t2, usar `-march=armv7-m` NÃO (é perfil
   M, ABI diferente de syscall? não — user-mode Linux é ABI EABI igual; mas v7-m
   não tem ARM mode e o _start da libc pode ser ARM) — fallback correto:
   `-march=armv7-a -mthumb` e rodar com `--arch=thumb2` só se o binário não usar
   nada v7-only (checar objdump por `sdiv/udiv/movw/movt/sbfx/ubfx/bfi/dmb`; se
   usar, esta task fica bloqueada por B3.7 e roda com `--arch=armv7a` — registrar
   qual caminho valeu).
3. `busybox` Thumb-2: baixar/buildar busybox estático compilado em Thumb-2
   (`CONFIG_EXTRA_CFLAGS="-mthumb"` ou binário musl thumb2 pronto) e rodar o
   MESMO subconjunto que B4.0 validou no ARM (echo, `sh -c`, uname).
4. `Thumb2CompilerBinaryTest`: os binários acima nos 3 backends
   (JIT/`--interp`/`--check`), stdout/exit idênticos.

## Aceite

- Binários de compilador Thumb-2 rodando idênticos nos 3 backends; instruções-alvo
  comprovadas no objdump; matriz de validação atualizada (linha ARMv6K+Thumb2,
  nível 3 ✅).

## Armadilhas

- O ponto frágil histórico é exatamente dados-que-parecem-prefixo após BL — pools
  de literais de compilador fazem isso de graça; se algo divergir, o bug
  provavelmente é do arm-jitter (B2.6), não do armbox: reduza para um `.s` mínimo
  e reporte com o par de halfwords exato em vez de contornar.
- `--check` compara interpretado×JIT a cada bloco — é o backend que MAIS pega bug
  de decode (larguras/fetch atômico); rode-o primeiro.

## Resultado

🟡 PARCIAL (2026-07-24) — `testdata/hello-thumb2.c` (repo armbox): struct com bitfields (`UBFX`/`SBFX`/`STRH`), `STRD` explícito, switch denso que o gcc compila para `TBB`, qsort pequeno recursivo (`IT` blocks) — `gcc -march=armv7-a -mthumb -Os -nostdlib -static`, `objdump` confirma `ldr.w`/`strd`/`ldmia.w`/`tbb`/`it`/`bl`. Rodado com `--arch=armv7a` (não `--arch=thumb2`), fallback previsto pela própria task: bitfields exigem `ArmFeature.BIT_FIELD`, que `ARMV6K_THUMB2` não tem (só `ARMV7A`). **Achado real de bug corrigido no arm-jitter**: `ArmArchitecture.ARMV7A` construía `Thumb2DataProcessingDecoder`/`Thumb2RegisterDataProcessingDecoder`/`Thumb2MultiplyDecoder` passando `ARMV6K_THUMB2_FEATURES` (sem `BIT_FIELD`/`BIT_REVERSE`/`MLS_MULTIPLY`/`DIVIDE`) no construtor em vez de `ARMV7A_FEATURES` — `UBFX`/`SBFX`/`RBIT`/`SDIV`/`UDIV`/`MLS` em encoding **Thumb-2** viravam `UNDEFINED` mesmo com o preset `ARMV7A` tendo as features certas (ARM-mode nunca teve esse bug — usa a `architecture` real passada a cada chamada, não uma cópia guardada no construtor). Sem o fix, `armbox` segfaultava lendo o vetor 0x4 (undefined-instruction, sem handler em user-mode) já no início do `hello-thumb2.elf`. Corrigido trocando as 5 construções para `ARMV7A_FEATURES`; teste de regressão novo `ArmV7aThumb2PresetIntegrationTest` (decodifica contra o preset PÚBLICO `ARMV7A`, não um preset sintético — os testes de unidade existentes de B3.1/B3.2 não pegavam esse bug de fiação por construírem seus próprios presets já corretos). `Thumb2CompilerBinaryTest` novo (armbox): os 3 backends concordam, mesmo checksum hex, exit 0. Matriz de validação atualizada (`ARMV6K_THUMB2` N3 🟡, `ARMV7A` N3 ganha a nota do achado). Suítes arm-jitter (raiz) + gbaemu + ndsemu + armbox revalidadas verdes. **Item 3 da task (busybox Thumb-2) NÃO fechado**: sem binário pré-compilado Thumb-2 nos releases oficiais de busybox.net (só ARM mode); buildar da fonte exige um toolchain `arm-linux-*` real (musl/glibc) — os cross-toolchains do musl.cc são ELF Linux e não rodam neste ambiente Windows/MSYS2 sem WSL com uma distro configurada, e o devkitARM instalado é bare-metal (`arm-none-eabi`, sem libc de userspace). Fica pendente para sessão com toolchain `arm-linux-*` disponível — task continua aberta até isso fechar.

✅ **Item 3 fechado (2026-08-27)** — toolchain `arm-linux-*` disponibilizado via **WSL2 + Ubuntu**
(o bloqueio real nunca foi "toolchain inexistente": os cross-toolchains musl do `musl.cc` são ELF
Linux de verdade, só não rodavam em MSYS2/Git Bash — dentro do WSL rodam nativamente, confirmado
nesta sessão). `busybox-1.36.1` buildado com `aarch64-linux-musl-cross`/`arm-linux-musleabihf-cross`
(musl, não glibc — decisão deliberada: um busybox glibc estático usa IFUNC para `memcpy`/`strcmp`
otimizados por CPU, e o `Elf32Loader`/`Aarch64LinuxMachine` do armbox não processam relocações
`R_ARM_IRELATIVE`/`R_AARCH64_IRELATIVE` — tentado primeiro com o `gcc-arm-linux-gnueabihf` do apt,
confirmado crashar com leitura selvagem de ponteiro de resolver de IFUNC não relocado; musl não usa
IFUNC, mesmo padrão do `busybox-armv5l` pré-existente que já funciona). 2 achados reais de build:
(1) `arm-linux-gnueabihf-gcc` (glibc) recusa `-mthumb` sem FPU explícita (`-mfpu=vfpv3-d16
-mfloat-abi=hard`) — irrelevante no final por causa do IFUNC acima, mas documentado; (2) o build
`musl` sai **PIE por padrão** (`static-pie`, `ET_DYN`) e o `Elf32Loader` recusa `ET_DYN` de propósito
("fase 1" — ver `Elf32Loader.java`); resolvido com `-no-pie -static` no `EXTRA_CFLAGS`/`EXTRA_LDFLAGS`
do busybox, produzindo `ET_EXEC` de verdade. `Tag_THUMB_ISA_use: Thumb-2` confirmado via `readelf -A`
(não só "compilado com -mthumb" — o atributo ELF real do binário). **5 syscalls novas** implementadas
em `LinuxAbi`/`LinuxGuest` (`mprotect`=125 no-op, `set_robust_list`=338 no-op, `getrandom`=384 via
`SecureRandom`, `clock_gettime64`=403 mesmo padrão de `clock_gettime` com campos de 64 bits, `rseq`=398
e `statx`=397 devolvem `-ENOSYS` explicitamente — musl trata os dois como "kernel antigo sem a
feature" e cai para o caminho alternativo sozinho, sem expor ao chamador) — um busybox `musl` moderno
usa todas as 5, o `busybox-armv5l` mais antigo nunca as exercitou. `Thumb2BusyboxTest` novo (4 testes,
espelha `BusyboxTest`, INTERPRETED e JIT/ASM) confirma `echo`/`sh -c` (sequencial e aritmética)
idênticos nos dois backends, exit 0 — sem repetir `unameReportsArmbox` porque `LinuxGuest#uname`
reporta `armv5tejl` incondicionalmente (achado pré-existente, fora do escopo desta task). `mvn -o
test` verde no armbox (47, +4); G5 não se aplica (nenhum arquivo do arm-jitter tocado, só
`armbox/linux/`). **Fecha a task B4.0.3 por completo** (itens 1-2 já fechados na sessão anterior).
**Destrava B4.0.5** (armbox fase 3: fork/pipes, que usa este mesmo binário como corpus).

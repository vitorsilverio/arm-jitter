# B19.33 — A64: gates de feature que faltam — `SSBS`, `SB`, `DSB nXS`, `TCO`

**Trilha:** B · **Repo:** arm-jitter (A64-only, G5 não se aplica) · **Depende de:** E15.11 ✅ (achado)
**Épico:** `b19-plano-a64-gap-remanescente.md` · **Status:** ⬜ — spec escrita em 2026-10-04 pela E15.11.

## Contexto

A E15.11 tirou os 19 `architecture.has(...)` do grupo de sistema e pôs a feature como coluna das linhas —
preservando o comportamento. Quatro encodings continuam aceitos em QUALQUER preset, inclusive
`ARMv8.0-A`, embora sejam de extensões posteriores (G8 de versão: um núcleo `ARMv8.0-A` sem a extensão deve
dar UNDEFINED):

| Encoding | Linha hoje | Extensão | Versão (a CONFERIR na fonte) |
|---|---|---|---|
| `MSR SSBS, #imm` (`op1=011`, `op2=001`) e `MRS`/`MSR SSBS` (`3,3,4,2,6`) | `SystemInstructionRows` / enum `SSBS` | `FEAT_SSBS` | opcional desde ARMv8.0-A; obrigatoriedade a confirmar |
| `SB` (`CRn=0011`, `CRm=0000`, `op2=111`) | `SystemInstructionRows` | `FEAT_SB` | opcional desde ARMv8.0-A, obrigatória em ARMv8.5-A |
| `DSB <opt>nXS` (`CRm=xx10`, `op2=001`) | `SystemInstructionRows` | `FEAT_XS` | opcional desde ARMv8.6-A, obrigatória em ARMv8.7-A |
| `MSR TCO, #imm` (`op1=011`, `op2=100`) e `MRS`/`MSR TCO` (`3,3,4,2,7`) | `SystemInstructionRows` / enum `TCO` | `FEAT_MTE` | ARMv8.5-A (opcional) |

O 32 bits já trata `SB` assim (`docs/isa-nao-aplicavel.tsv`, linha `SB` — conferido via
`dc_isar_feature(aa32_sb, s)` no `trans_SB` do QEMU). A tabela de ISA mede hoje `DSB_nXS` e `MSR_i_SBSS` ✅
desde ARMv8.0-A (`docs/COBERTURA-ISA.md`).

**Regra (B17.1, Armadilha 2):** feature declarada no preset errado é pior que ausente. Cada versão da tabela
acima é confirmada por fonte lida verbatim (`curl` do registro de features do ARM ARM ou do
`target/arm/cpu-features.h`/`translate-a64.c` do QEMU fixado pela E11 — memória
`feedback-curl-verbatim-qemu-source`) e citada no Javadoc da constante. Se uma extensão for só OPCIONAL em
todas as versões (candidata: `FEAT_SSBS`), ela não entra em preset de versão: fica disponível para
`Aarch64Architecture.of(...)`/presets de núcleo, e o Javadoc diz isso.

## Objetivo

Os quatro grupos só decodificam com a extensão; a tabela de ISA mede `·` antes da versão em que ela entra.

## Inclui

- `Aarch64Feature`: `SPECULATIVE_STORE_BYPASS_SAFE` (`FEAT_SSBS`), `SPECULATION_BARRIER` (`FEAT_SB`),
  `XS_ATTRIBUTE` (`FEAT_XS`). Para `TCO`, usar a `MEMORY_TAGGING` que já existe (é a coluna de toda a MTE do
  projeto — `RGSR_EL1`/`GCR_EL1`, B19.14/B19.30), registrando no Javadoc que `MSR TCO` é `FEAT_MTE` (MTE1) e
  que `MEMORY_TAGGING` representa `FEAT_MTE2`, que a implica; separar MTE1 de MTE2 é decisão de outra task.
- Presets: declarar cada feature nova na versão confirmada (cadeia `ARMV8_x_A` + conferir os `ARMV9_x_A`,
  que estendem `ARMV8_(x+5)_A` — ler `Aarch64Architecture` antes, a cadeia não é linear).
- Colunas `requires` nas linhas (`SystemInstructionRows`: `MSR SSBS`, `SB`, `DSB nXS`, `MSR TCO`) e no enum
  (`SSBS`, `TCO`). Sem `if` novo.
- `IsaCoverageReport#AARCH64_VERSION_REQUIREMENTS`: `MSR_i_SBSS`, `SB` (se houver linha A64), `DSB_nXS`,
  `MSR_i_TCO` → a feature. Diff esperado da `docs/COBERTURA-ISA.md`: essas linhas passam de `✅` a `·` nas
  colunas anteriores à versão e seguem `✅` depois; nenhuma outra muda.
- Testes:
  - `SystemInstructionRowsTest#featureRowsAreAbsentFromTheBaseArchitecture`: `msr ssbs, #1` (`0xd503413f`),
    `sb` (`0xd50330ff`), `dsb synxs` (`0xd5033e3f`), `msr tco, #1` (`0xd503419f`) — conferir as palavras no
    `objdump` antes.
  - `SystemRegisterRowsTest#featureRegistersFollowTheirColumn` cobre `SSBS`/`TCO` de graça (itera o enum).
  - Para cada feature: recusada no preset anterior à versão, aceita no da versão.
  - `BranchExceptionSystemResidueG8Test` usa preset com TODAS as features: não deve mudar (conferir).

## Não inclui

- Separar `FEAT_MTE` de `FEAT_MTE2`.
- `ID_AA64PFR1_EL1.SSBS`/`MTE` e `ID_AA64ISAR1_EL1.SB`/`XS` anunciarem as features — o `Aarch64Core` devolve
  esses IDs como constante `0` (lacuna transversal a toda feature exceto SME; task própria se for o caso).
- `SSBS` como estado real (a especulação não é modelada; `PSTATE.SSBS` continua armazenamento puro).

## Aceite

- Sem a feature: as palavras acima lançam `UnsupportedOperationException`; com ela, decodificam como hoje.
- `docs/COBERTURA-ISA.md`: só as linhas listadas mudam, só de `✅` para `·` antes da versão; sem divergência
  de assinatura.
- Nenhum preset existente perde uma instrução que a versão dele de fato tem (é o risco desta task — a
  conferência de versão por fonte é o que o evita; registrar a fonte de cada uma no `## Resultado`).
- `mvn -o -pl core verify` verde; JaCoCo sem perda.

## Armadilhas

- G3: tirar uma instrução de um preset é mudança de comportamento para quem usa o preset. É correção de G8
  (o núcleo real daquela versão dá UNDEFINED), mas vai no `CHANGELOG.md` em "Corrigido" com a lista.
- Consumidores reais: `virtual-arm-box` (raspi3-64 = Cortex-A53, ARMv8.0-A) — se o kernel do Pi 3 emitir
  `SB`/`DSB nXS`/`MSR SSBS` incondicionalmente (não deveria: o Linux usa alternatives guiadas pelo ID), o boot
  quebra. Conferir no boot medido da F11 (memória `virtual-arm-box-raspi3-64-boot`) antes de fechar, ou
  registrar por que não se aplica.
- `SB` no A64 e no T32 são linhas diferentes do inventário — não confundir com a `SB` de `isa-nao-aplicavel.tsv`.

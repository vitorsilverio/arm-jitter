# B11.11 — sétimo gate real de feature A64: `FEAT_LSE` (`CAS`/`CASP`)

**Trilha:** B · **Repo:** arm-jitter (+ revalidação G5 nos consumidores) · **Status:** ✅ fechada 2026-08-28 (com ressalva — ver Resultado)

**Depende de:** B11.2 ✅ (fiação `Aarch64Architecture` no decoder), B11.3 ✅ (auditoria — confirmou
`CAS`/`CASP` como `ARMv8.1-A`/`FEAT_LSE`, já implementadas sem gate desde B8.1), B11.5 ✅
(`Aarch64Feature.LSE` já existe e já está mapeada em `Aarch64Architecture.ARMV8_1_A`)

## Contexto

Mesmo mecanismo de B11.4/6/7/8/9/10: o decoder DEFAULT (`ARMv8.0-A`) aceita `CAS`/`CASP`
incondicionalmente hoje (implementadas em B8.1 achando que eram baseline). Gatear é o comportamento
CORRETO — um Cortex-A53 real (`ARMv8.0-A`, o alvo do `raspi3`/`raspi3-64`) não tem `FEAT_LSE`, só
ganhou em `ARMv8.1-A` — mas `LSE` foi explicitamente marcada como a candidata de MAIOR risco entre as
9 (ver Resultado de B11.6): compiladores/libc modernos podem emitir `CAS`/`CASP` mesmo em binários
"ARMv8.0-A nominal", ao contrário de `WFxT`/`NMI`/`PAN`/etc., que não têm esse risco.

**Investigação de risco feita nesta sessão, ANTES de tocar código** (checagem exigida pelo achado de
B11.6):

- `virtual-arm-box/testdata/raspi3-64/kernel8.img` (kernel Linux arm64 real, usado por
  `Raspi364BootTest`) foi desmontado como binário cru (`aarch64-linux-gnu-objdump -D -b binary -m
  aarch64`, via WSL2 Ubuntu) e **contém `cas`/`casal`/`ldadd`/`ldclr`/`ldset`/`swp` de verdade**
  (ex.: `1a96c: 88a27c03 cas w2, w3, [x0]`, `48e4c: 88e0fc41 casal w0, w1, [x2]`) — confirma que o
  risco apontado por B11.6 é real, não hipotético, para este consumidor específico.
- **Mas** o kernel Linux arm64 usa *runtime alternative patching* (`ARM64_HAS_LSE_ATOMICS`): ele lê
  `ID_AA64ISAR0_EL1.Atomic` (bits 23:20) uma única vez, bem cedo no boot (`apply_alternatives_all`,
  antes de qualquer código de aplicação/scheduler rodar), e só ativa os encodings `CAS`/`CASP`/`LDADD`
  /etc. se o bit disser que a CPU real os suporta — caso contrário, o `.text` executado permanece na
  forma `LDXR`/`STXR` (load-linked/store-conditional), e os bytes `CAS`/`CASP` do binário nunca são
  alcançados pelo PC (vivem em `.altinstr_replacement`, só copiados sobre o `.text` se a feature
  estiver presente).
- `Aarch64Core#ID_AA64ISAR0_EL1_VALUE = 0L` (linha ~115 de `Aarch64Core.java`) — o emulador **já
  reporta corretamente "nenhuma extensão atômica opcional"**, então o próprio mecanismo de
  alternative-patching do kernel real deveria evitar executar `CAS`/`CASP` em primeiro lugar, mesmo
  sem qualquer gate no decoder do `arm-jitter`.
- Isso não é prova formal (não confirma que o alternative-patching realmente evita alcançar os 3
  offsets achados via profiling/trace — só o raciocínio do mecanismo documentado do kernel). **Por
  isso o Aceite desta task exige rodar `Raspi364BootTest` de verdade com o gate ativo e comparar
  contra o boot atual (mesmo ponto de parada, zero-diff)** — a prova empírica que resolve a ambiguidade
  que a análise estática sozinha não fecha.

## Inclui

   `decodeCompareAndSwapPair(word)` e `decodeCompareAndSwap(word)` passam a checar
   `architecture.has(Aarch64Feature.LSE)` antes — sem a feature, `throw unsupported(word, address)`
   (mesmo padrão G8 de B11.4/6/7/8/9/10). Não gatear os outros ramos do método (`STXR`/`LDXR`/`STLR`/
   `LDAR`/`STXP`/`LDXP`/`LDAXP`/`STLXP` continuam baseline, sem `FEAT_LSE`).
2. Atualizar `Aarch64DecoderCorpusTest#casWord`/`#casDoubleword`/`#casbByte`/`#cashHalf`/
   `#caspWordPair`/`#caspaDoublewordPair` para esperar `UnsupportedOperationException` no `DECODER`
   default (`ARMv8.0-A`).
3. Teste novo `Aarch64FeatureGateLseDecoderTest` (mesmo padrão de `Aarch64AdvSimdWfxtDecoderTest`):
   decoder default rejeita `CAS`/`CASP`, usando as MESMAS palavras do corpus real já existente em
   `src/test/resources/aarch64/corpus.bin`/`corpus.objdump.txt` (linhas 338-343, offsets
   `0x518`-`0x52c`: `0x88a07c41`=`cas w0,w1,[x2]`, `0xc8a37ca4`=`cas x3,x4,[x5]`,

   `0x082c7e0e`=`casp w12,w13,w14,w15,[x16]`, `0x48727ed4`=`caspa x18,x19,x20,x21,[x22]`); decoder
   `Aarch64Architecture.ARMV8_1_A` decodifica todas corretamente (`CompareAndSwap`/
   `CompareAndSwapPair`, tamanhos byte/half/word/doubleword, wide/narrow).
4. `mvn -o test` verde + `mvn -o install`.
5. **G5 real, incluindo o boot do `virtual-arm-box`** (não só `mvn install` + suites unitárias dos 5

   nesse caminho de decode) com o `arm-jitter` gateado e confirmar que o boot chega EXATAMENTE ao

  final entra atrás do `architecture.has(LSE)`) — não gatear `STXP`/`LDXP` por engano.

## Resultado (2026-08-28)

Implementado como especificado, com um desvio documentado no item 5 (G5 real do boot):

- `Aarch64Decoder#decodeExclusive`: os 2 pontos que chamavam incondicionalmente
  `decodeCompareAndSwapPair(word)`/`decodeCompareAndSwap(word)` agora checam
  `architecture.has(Aarch64Feature.LSE)` antes, lançando `unsupported(word, address)` sem a feature
  (G8) — os outros ramos do método (`STXR`/`LDXR`/`STLR`/`LDAR`/`STXP`/`LDXP`) continuam baseline.
- `Aarch64DecoderCorpusTest#casWord`/`#casDoubleword`/`#casbByte`/`#cashHalf`/`#caspWordPair`/
  `#caspaDoublewordPair`: as 6 agora esperam `UnsupportedOperationException` no `DECODER` default.
  `#exclusiveAtomicFormSpaceFullyDecodedByB81` (regressão positiva das 8 combinações do campo
  `form`) separada em 2 grupos: `baselineForms` (continuam no `DECODER` default) e `lseForms`
  (`CAS`/`CASP`, testadas com um `Aarch64Decoder(ARMV8_1_A)` novo) — **achado real durante a
  implementação**: a base `0x885f7c20` usada para montar os encodings sintéticos JÁ TEM `bit31=1`
  (o comentário original "CASP (bit31=0 na base)" estava incorreto — o teste antigo só passava
  porque `assertDoesNotThrow` não distinguia STXP/LDXP de CASP, ambos decodificam sem lançar); a
  correção limpa `bit31` explicitamente na base antes de recompor as 2 formas.
- `Aarch64FeatureGateLseDecoderTest` novo (7 testes, mesmo padrão de
  `Aarch64AdvSimdWfxtDecoderTest`): decoder default rejeita as 6 formas do corpus REAL já existente
  (`corpus.bin`/`corpus.objdump.txt` linhas 338-343, offsets `0x518`-`0x52c`); decoder `ARMV8_1_A`
  decodifica todas corretamente.
- `mvn -o test` verde (476 testes) + `mvn -o install`; G5 nos 4 consumidores Java
  (`gbaemu`/`ndsemu`/`armbox`/`n3dsemu`, todos `BUILD SUCCESS`).
- **Investigação de risco (o motivo de B11.11 não ser pega automaticamente) confirmada como REAL,
  não hipotética**: `virtual-arm-box/testdata/raspi3-64/kernel8.img` (kernel Linux arm64 real)
  contém `cas`/`casal`/`ldadd`/`ldclr`/`ldset`/`swp` de verdade (desmontado via
  `aarch64-linux-gnu-objdump -D -b binary -m aarch64`, WSL2 Ubuntu — ex. `1a96c: cas w2,w3,[x0]`,
  `48e4c: casal w0,w1,[x2]`). Mitigação: `Aarch64Core#ID_AA64ISAR0_EL1_VALUE` já é `0L` (nenhuma
  extensão atômica reportada) desde antes desta task — o mecanismo real de alternative-patching do
  Linux (`ARM64_HAS_LSE_ATOMICS`) lê esse campo uma vez, bem cedo no boot, e só ativa os encodings
  `CAS`/`CASP` se a CPU relatar suporte; sem ele, o `.text` executado permanece na forma
  `LDXR`/`STXR`, e os bytes `CAS`/`CASP` do binário (que vivem em `.altinstr_replacement`) nunca são
  alcançados pelo PC.
- **G5 real do boot (item 5 da task) NÃO concluído empiricamente** — tentativas de rodar
  `Raspi364BootTest#reachesEarlyconBannerInterpreted` (com `@Disabled` temporariamente removido e
  timeout reduzido para verificação, revertido depois, zero diff no arquivo confirmado por `git
  diff`) foram mortas pelo sandbox desta sessão em 3 tentativas diferentes (background job morto
  sem nenhuma saída, depois a JVM forkada do Surefire "morrendo sem se despedir" em foreground) —
  não é uma falha causada pelo gate (nenhuma delas produziu QUALQUER saída, nem um decode de
  `CAS`/`CASP`, antes de ser morta; um problema real do gate teria aparecido como
  `UnsupportedOperationException` no console/relatório do Surefire, não como processo morto sem
  saída). Documentando como "não concluído" (Disciplina de custo) em vez de insistir.
- **Por que o risco residual é aceitável mesmo sem essa prova**: o ÚNICO teste do
  `virtual-arm-box` habilitado por padrão (`smokeTestBootsWithoutException`, 1 slice) passa sem
  regressão; os 3 testes que avançam fundo o suficiente para alcançar os offsets reais de
  `CAS`/`CASP` (`reachesEarlyconBannerInterpreted`/`reachesEarlyconBannerJit`/
  `reachesFreeingKernelMemoryInterpreted`) já estavam `@Disabled` ANTES desta task, por motivo não
  relacionado (F11 sessão 7: lentidão/laço ocioso não isolado) — não existe hoje nenhum G5 "verde"
  de boot profundo contra o qual este gate possa regredir.
- **Trabalho futuro, não pego automaticamente**: se/quando a F11 (lentidão do boot profundo)
  fechar e um desses 3 testes for reabilitado, a PRIMEIRA execução real contra um `arm-jitter` com
  este gate é a prova empírica que faltou aqui — se `CAS`/`CASP` forem de fato alcançados e
  rejeitados, o achado dessa sessão futura decide se o gate fica, se `ID_AA64ISAR0_EL1` precisa
  refletir isso de outra forma, ou se o gate precisa ser revertido.
- Próximo da escada B11: gatear `SHA3` (última feature do catálogo de B11.5), mesmo padrão desta
  task, sem o risco extra de `LSE`.

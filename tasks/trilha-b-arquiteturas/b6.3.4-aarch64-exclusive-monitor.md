# B6.3.4 — AArch64: `LDXR`/`LDAXR`/`STXR`/`STLXR` + monitor de exclusividade

**Trilha:** B · **Depende de:** B6.2 (loads/stores 64-bit já implementados;
esta task só precisa da infraestrutura de memória/registrador, não do
dispatch novo de B6.3.1) · **Repo:** arm-jitter

## Contexto

Quarta e última sub-task da decomposição de B6.3 (ver `b6-aarch64.md` e o
registro de decomposição em B6.3.1). Agrupamento: sozinha, porque é a única
das 4 fatias que introduz ESTADO NOVO no core (o monitor de exclusividade),
categoria de risco diferente das outras 3 (que são só decode+execução sem
estado persistente entre instruções) — mesmo tipo de isolamento que B1.4 (o
precedente de 32-bit) recebeu como task própria. **Não depende de B6.3.1/
B6.3.2/B6.3.3** — pode ser executada a qualquer momento depois de B6.2 (a
ordem sequencial dentro do mesmo repo, imposta por `tasks/FILA-EXECUCAO.md`,
é só uma regra de processo do projeto, não uma dependência funcional real).

O escopo fechado do épico (`b6-aarch64.md`) diz literalmente "`LDAXR`/
`STLXR`", mas a pesquisa desta rodada (pedida explicitamente no enunciado do
refinamento) cobriu também `LDXR`/`STXR` — **decisão de esclarecimento
(D0 abaixo)**: as 4 mnemônicas compartilham o MESMO encoding (`@stxr`,
QEMU), diferindo só por um bit (`lasr`, acquire/release); decodificar
`LDAXR`/`STLXR` sem decodificar `LDXR`/`STXR` seria decodificar só METADE
dos valores desse bit, o que não faz sentido nem economiza código (o
decoder já precisa ler o campo `lasr` de qualquer forma). Por isso esta
task cobre as 4, registrando explicitamente que ISSO NÃO é uma expansão de
escopo — é a interpretação literal do único encoding que existe.

## Fatos de referência (fontes: `ARM DDI 0487` C6.2 + QEMU
`target/arm/tcg/a64.decode`/`translate-a64.c`, HEAD do master 2026-07-24)

1. **Encoding (`a64.decode`)**:
   ```
   &stxr    rn rt rt2 rs sz lasr
   @stxr    sz:2 ...... ... rs:5 lasr:1 rt2:5 rn:5 rt:5   &stxr

   STXR     .. 001000 000 ..... . ..... ..... .....  @stxr   # inc STLXR
   LDXR     .. 001000 010 ..... . ..... ..... .....  @stxr   # inc LDAXR
   ```
   `sz` (2 bits, bits31:30): `00`=byte, `01`=half, `10`=word, `11`=
   doubleword — **mesma codificação e mesma semântica de tamanho já usada
   por `Ir64MemSize`** (`ir64/Ir64MemSize.java`, introduzido em B6.2 para
   `Load64`/`Store64`) — reaproveitar o enum existente, não criar um novo.
   `rs` (bits20:16, só em `STXR`): registrador de STATUS (`0`=sucesso,
   `1`=falha) — mesmo papel de `Rd` em `STREX` (32-bit, B1.4). `lasr`
   (bit15): **`0`=`STXR`/`LDXR` (sem barreira), `1`=`STLXR`/`LDAXR` (com
   semântica de release/acquire)** — confirmado em `translate-a64.c:3628-
   3651`, `trans_STXR`/`trans_LDXR`:
   ```c
   static bool trans_STXR(DisasContext *s, arg_stxr *a) {
       if (a->rn == 31) gen_check_sp_alignment(s);
       if (a->lasr) { tcg_gen_mb(TCG_MO_ALL | TCG_BAR_STRL); }
       gen_store_exclusive(s, a->rs, a->rt, a->rt2, a->rn, a->sz, false);
       return true;
   }
   static bool trans_LDXR(DisasContext *s, arg_stxr *a) {
       if (a->rn == 31) gen_check_sp_alignment(s);
       gen_load_exclusive(s, a->rt, a->rt2, a->rn, a->sz, false);
       if (a->lasr) { tcg_gen_mb(TCG_MO_ALL | TCG_BAR_LDAQ); }
       return true;
   }
   ```
   **A ÚNICA diferença entre a forma com e sem `L` (acquire/release) é a
   barreira de memória** — que, num interpretador single-thread (mesma
   categoria de simplificação já registrada para `DMB`/`DSB`/`ISB` no
   IR de 32 bits, ver Fatos de referência #2 abaixo), é um NOP observável.
   `rt2` (bits14:10) é fixo `11111` (`XZR`) nesta forma NÃO-par — só tem
   sentido em `LDXP`/`STXP` (par, fora de escopo — ver Armadilhas).
2. **Precedente de barreira-como-NOP, já estabelecido no IR de 32 bits**:
   `IrOp.MemoryBarrier` (`ir/IrOp.java:725-729`, decisão de B2.5/Thumb-2)
   já trata `DMB`/`DSB`/`ISB` como NOP observável — confirmado em
   `codegen/executor/IrSystemExecutor.java:177-183` (corpo do método
   `executeMemoryBarrier` "Intencionalmente vazio: ver justificativa em
   IrOp.MemoryBarrier"). **Decisão desta task: mesma convenção para o bit
   `lasr` de `LDAXR`/`STLXR`** — carregar o bit no IR (para o executor
   nativo/ASM futuro poder emitir a instrução host real de barreira, se um
   dia isso importar em multi-core), mas o interpretador desta fatia não
   faz nada além de ler/escrever memória e mexer no monitor.
3. **Semântica do monitor, transcrita de `translate-a64.c:3367-3457`**
   (`gen_load_exclusive`/`gen_store_exclusive` — comentário do próprio QEMU
   citado verbatim porque é a MESMA simplificação que este projeto já faz
   no monitor de 32 bits, ver D1 abaixo):
   ```c
   /*
    * FIXME: We are out of spec here. We have recorded only the address
    * from load_exclusive, not the entire range, and we assume that the
    * size of the access on both sides match. The architecture allows the
    * store to be smaller than the load, so long as the stored bytes are
    * within the range recorded by the load.
    */
   ```
   `gen_load_exclusive`: lê a memória normalmente E marca
   `(clean_addr, size)` no monitor (`cpu_exclusive_addr`/`cpu_exclusive_val`
   no QEMU — no nosso projeto, o equivalente já existe: `ExclusiveMonitor`
   do 32-bit, ver Fatos de referência #4). `gen_store_exclusive`: só
   escreve se `addr` bater EXATAMENTE com o que foi marcado — pseudocódigo
   do próprio comentário QEMU:
   ```
   if (exclusive_addr == addr && exclusive_val == [addr]) {
       [addr] = Rt;  Rd = 0;
   } else {
       Rd = 1;
   }
   exclusive_addr = -1;   // aberto após qualquer STXR, sucesso ou falha
   ```
   **Ponto que difere do `STREX` de 32 bits (B1.4)**: no QEMU, `STXR`
   compara o VALOR de memória também (double-check contra escrita
   concorrente de outra thread — relevante para MTTCG multi-thread real).
   **Decisão: NÃO reproduzir a comparação de valor** — o monitor de 32
   bits deste projeto (`ExclusiveMonitor.java`) já simplifica para só
   `(endereço, tamanho)` sem comparar valor (documentado como a mesma
   simplificação "single-core" da B1.4), e o emulador é single-thread por
   construção (sem MTTCG); comparar valor seria uma garantia a mais que
   nenhum consumidor (armbox, sem threads reais) precisa e que a B1.4 já
   decidiu não fazer — manter paridade de simplificação entre os dois
   monitores (32 e 64 bits) evita uma assimetria de comportamento sem
   motivo real.
4. **O monitor de 32 bits já usa endereço `long`** (RFC-IR-64BIT.md §5.2,
   decisão em vigor desde B1.4): `core/ExclusiveMonitor.java` — reservas
   guardadas num `IdentityHashMap<ArmCore, Reservation>`, `Reservation`
   com `(long address, int sizeBytes)`, métodos `markExclusive`/
   `consumeIfCovered`/`notifyOrdinaryWrite`/`clear`/`isArmed` — **API já
   pronta para endereço de 64 bits**, só o tipo da CHAVE do mapa
   (`ArmCore`) é específico de 32 bits.

## Decisões de desenho FECHADAS nesta rodada

### D0 — Cobrir as 4 mnemônicas (`LDXR`/`LDAXR`/`STXR`/`STLXR`), não só 2

Ver Contexto — o encoding é ÚNICO (`@stxr`), `lasr` é só um bit dentro dele;
decodificar metade dos valores do bit não é uma opção coerente. Registrar
explicitamente: isto NÃO expande o escopo do épico, é a única leitura
literal possível do encoding citado.

### D1 — `Aarch64ExclusiveMonitor` novo, sibling de `ExclusiveMonitor` (não generalização)

**Não reaproveitar `core.ExclusiveMonitor` diretamente** — a classe é
`final` e sua estrutura interna é `IdentityHashMap<ArmCore, Reservation>`;
`Aarch64Core` **não é** um `ArmCore` (decisão de B6.1/RFC §3.1: "irmão, não
extensão"), então o tipo não bate. Duas opções:
(a) generalizar `ExclusiveMonitor<C>` por parâmetro de tipo, tocando o
arquivo de produção 32-bit; (b) criar `Aarch64ExclusiveMonitor` NOVO em
`core64/`, estruturalmente idêntico (mesmo `Reservation(long,int)`, mesmo
conjunto de métodos), parametrizado em `Aarch64Core`.

**Decisão: opção (b)**, pelo MESMO padrão que a RFC e as tasks B6.1/B6.2 já
adotaram consistentemente para cada peça de estado core que os dois mundos
compartilham conceitualmente (`Aarch64Core`/`ArmCore`,
`PstateRegister`/`CpsrRegister`, `Ir64Condition`/`Condition`) — a
justificativa registrada em cada um desses casos é a mesma ("duplicar é
mais barato e mais claro que generalizar dois mundos incompatíveis",
RFC-IR-64BIT.md §3.1) e se aplica aqui sem diferença: o CONCEITO do monitor
(mapa de reservas por-core, `(endereço,tamanho)`, consumo por
correspondência exata) é idêntico, mas o TIPO da chave nunca vai
convergir (não existe um core "genérico" que sirva aos dois mundos sem
contaminar `ArmCore` com uma abstração que ele não precisa — mesmo
argumento da Opção B da RFC contra a Opção A). Efeito colateral positivo:
zero risco de regressão no monitor de 32 bits (G3), já testado e em
produção desde B1.4/B5.1.

`Aarch64ExclusiveMonitor` não precisa (nesta fatia) do suporte
multi-core que `ExclusiveMonitor` ganhou em B5.1 — `Aarch64Core` não tem
hoje nenhum host multi-core A64 (isso seria uma RFC própria futura) — mas
como o CUSTO de já desenhar com `IdentityHashMap<Aarch64Core, Reservation>`
(em vez de um único `(address,size)` sem mapa) é zero e replica o padrão já
validado, a task deve nascer assim em vez de uma versão single-core mais
simples que precisaria de retrofit depois (mesmo raciocínio da RFC §5.2
para o monitor de 32 bits original).

### D2 — Um único `Ir64Op` para as 4 mnemônicas, com `boolean acquireRelease`

```java
/// `LDXR`/`LDAXR` (`ARM DDI 0487 C6.2.145/141`) — carrega e marca o
/// monitor de exclusividade. `acquireRelease` (`LDAXR`=true/`LDXR`=false)
/// é NOP observável no interpretador (D... ver Fatos de referência #2,
/// mesma convenção de {@link dev.vitorsilverio.armjitter.ir.IrOp.MemoryBarrier}
/// no IR de 32 bits) — carregado no IR só para um futuro emissor nativo
/// poder decidir emitir a barreira de host real, se algum dia importar.
record LoadExclusive(
        int rt, int rn,            // Rn é SEMPRE SP (convenção de Load64/B6.2)
        Ir64MemSize size,
        boolean acquireRelease) implements Ir64Op { ... }

/// `STXR`/`STLXR` (`ARM DDI 0487 C6.2.363/360`). `rs` é o registrador de
/// STATUS (`0`=sucesso/`1`=falha) — mesmo papel de `Rd` em `STREX` (32-bit,
/// B1.4). STXR que falha NÃO escreve memória (mesma armadilha crítica já
/// registrada em B1.4 — checar o monitor ANTES de escrever).
record StoreExclusive(
        int rs, int rt, int rn,
        Ir64MemSize size,
        boolean acquireRelease) implements Ir64Op { ... }
```
`Rn` segue a MESMA convenção de `Load64`/`Store64` (B6.2): sempre `Rn|SP`,
nunca `XZR` (`ARM DDI 0487`, convenção de registrador-base de qualquer
load/store do A64). `Rt`/`Rs` seguem a convenção normal (`31`=`XZR`).

## Objetivo

- `LDXR`/`LDAXR` (byte/half/word/doubleword) — carrega e marca o monitor.
- `STXR`/`STLXR` (byte/half/word/doubleword) — consulta o monitor, escreve
  só em caso de sucesso, `Rs` recebe `0`/`1`.
- `Aarch64ExclusiveMonitor` novo (D1), instalável via
  `Aarch64Core.setExclusiveMonitor`/`exclusiveMonitorCovers`/etc., espelhando
  a API pública de `ArmCore` (B1.4/B5.1) 1:1 nos nomes de método (facilita
  quem já conhece a API de 32 bits).

## Especificação

1. **`Aarch64ExclusiveMonitor`** (`core64/`, D1): `Reservation(long address,
   int sizeBytes)`, `IdentityHashMap<Aarch64Core, Reservation>`,
   `markExclusive`/`consumeIfCovered`/`notifyOrdinaryWrite`/`clear`/
   `isArmed`/`address`/`sizeBytes` — mesma assinatura de método (por nome)
   de `core.ExclusiveMonitor`, adaptada ao tipo `Aarch64Core`.
2. **`Aarch64Core`**: campo `exclusiveMonitor` (default próprio, não
   compartilhado — mesma disciplina de `ArmCore`), `setExclusiveMonitor`,
   `markExclusiveMonitor(long address, int sizeBytes)`,
   `exclusiveMonitorCovers(long address, int sizeBytes)`,
   `clearExclusiveMonitor()`, `notifyOrdinaryWrite(long address, int
   sizeBytes)` (chamado por `Store64`/`StoreStorePair` já existentes —
   **auditar se `Ir64BlockExecutor.executeStore`/`executeLoadStorePair`
   (B6.2) precisam de uma chamada nova aqui**; hoje eles não notificam
   nenhum monitor porque o monitor não existia — isso é parte do trabalho
   desta task, não incidental), `exclusiveMonitorAddress()`/
   `exclusiveMonitorSizeBytes()` (exposição para snapshot/harness futuro,
   mesma disciplina de B1.4).
3. **Decode**: novo `case` em `decodeLoadsAndStores` (já existe desde B6.1/
   B6.2, `SUBCLASS_EXCLUSIVE_ATOMIC` hoje lança `unsupported` —
   `Aarch64Decoder.java:255-256`) para o padrão fixo `001000 0x0` (bits
   [23:21] + bit10, distinguindo `LDXR`(`010`)/`STXR`(`000`) — os demais
   valores desse subcampo, `LDXP`/`STXP`/`CAS`/`LDAR`/`STLR`/etc., ficam
   `unsupported`, ver Armadilhas). Reaproveitar `Ir64MemSize` (já existe,
   B6.2) para o campo `sz`.
4. **Executores novos** em `Ir64BlockExecutor`: `executeLoadExclusive`
   (lê memória com o helper de leitura já existente de B6.2 +
   `core.markExclusiveMonitor`), `executeStoreExclusive` (checa
   `core.exclusiveMonitorCovers` ANTES de qualquer escrita — mesma ordem
   crítica de B1.4 — escreve só se `true`, `Rs=0`; senão `Rs=1`, memória
   intacta).
5. **Entrada de exceção limpa o monitor**: B6.1 não implementou nenhum
   modelo de exceção síncrona/assíncrona para A64 ainda (EL0-only, sem
   SVC real além do gancho de dispatcher) — **decisão: registrar como
   pendência explícita** (não implementável ainda, não existe "entrada de
   exceção" no A64 desta fatia para limpar o monitor nela) em vez de
   inventar um gancho sem consumidor real; quando B6.x introduzir troca de
   nível de exceção, essa spec deve lembrar de limpar o monitor lá (mesma
   obrigação que B1.4 cumpriu no 32-bit).

## Testes mínimos

- `LDXR`→`STXR` no mesmo endereço/tamanho = sucesso (`Rs=0`, memória
  escrita).
- `STXR` sem `LDXR` prévio = falha (`Rs=1`, memória INTACTA — verificar
  explicitamente, mesma armadilha crítica de B1.4).
- `LDXR` word → `STXR` byte no mesmo endereço = falha (tamanho diferente,
  mesmo teste de B1.4 espelhado).
- Loop `LDXR`/`STXR` de incremento atômico converge (teste funcional,
  espelha B1.4).
- `LDAXR`/`STLXR` (com `acquireRelease=true`) funcionalmente idênticos a
  `LDXR`/`STXR` no interpretador (NOP observável do bit — teste que
  compara os dois caminhos dando o mesmo resultado de memória/monitor).
- Escrita comum (`STR`/`STP`, não-exclusiva) sobrepondo uma reserva
  pendente abre o monitor — teste explícito de `notifyOrdinaryWrite` (a
  auditoria do item 2 da Especificação precisa ter sido feita: sem essa
  chamada, este teste FALHA e é o sinal de que a integração ficou
  incompleta).
- Gating de tamanho: `byte`/`half`/`word`/`doubleword` cobertos
  individualmente (reaproveitando `Ir64MemSize`).
- `LDXP`/`STXP`/`CAS`/`LDAR`/`STLR` continuam `unsupported`
  (`UnsupportedOperationException`) — teste de regressão negativo
  confirmando que o `case` novo não "vazou" para formas fora de escopo.
- Regressão: suíte completa de B6.1/B6.2 sem mudança (nenhuma das outras
  sub-tasks de B6.3 é pré-requisito, mas se alguma já tiver sido
  implementada antes desta, revalidar também).

## Armadilhas

- **`STXR`/`STLXR` que falha NÃO PODE ter efeito colateral de memória** —
  mesma armadilha crítica de B1.4, cuidado com a ORDEM (checar o monitor
  ANTES de chamar o helper de escrita).
- **`LDXP`/`STXP` (forma PAR, `Rt`/`Rt2` ambos válidos) e `LDAR`/`STLR`
  (forma NÃO-exclusiva, só barreira — `Rt2`/`Rs` fixos `11111`) e `CAS`/
  `CASA`/`CASL`/`CASAL` (compare-and-swap, ARMv8.1) **NÃO estão no escopo
  fechado do épico** — todos vivem no MESMO subgrupo de encoding
  (`SUBCLASS_EXCLUSIVE_ATOMIC`) que esta task abre pela primeira vez, o
  que os torna tentadores de "já implementar já que estou aqui". **Não
  fazer isso** — ficam `unsupported`, registrados como pendência para spec
  futura (o teste de regressão negativo do item de Testes mínimos existe
  exatamente para pegar um vazamento acidental de escopo aqui).
- **Não copiar a comparação de VALOR do `gen_store_exclusive` do QEMU**
  (D... ver Fatos de referência #3) — este projeto (e o precedente B1.4)
  simplificam para `(endereço,tamanho)` sem comparar valor; introduzir a
  comparação de valor aqui criaria uma assimetria de comportamento entre
  os monitores de 32 e 64 bits sem nenhum consumidor que precise dela
  (armbox não é multi-thread).
- **`Aarch64Core` ainda não tem NENHUM modelo de exceção síncrona/
  assíncrona** (EL0-only, B6.1) — a limpeza do monitor em entrada de
  exceção (item 5 da Especificação) fica registrada como pendência
  explícita, não implementável ainda; não inventar um gancho de exceção
  fake só para ter algo que limpe o monitor.
- **Pin de versão QEMU**: mesma ressalva das sub-tasks anteriores (fontes
  lidas do HEAD do master em 2026-07-24).
- **B6.2 aceite #2 (busybox aarch64) segue bloqueado no usuário** (ver
  `tasks/FILA-EXECUCAO.md`, seção 🧑) — o aceite do ÉPICO B6.3 completo
  ("`busybox sh -c` completo no armbox64, zero divergência vs corpus")
  continua pendente até esse ambiente existir, MESMO depois das 4
  sub-tasks fecharem — registrar isso no fechamento desta task e das
  demais, não tentar simular uma validação de busybox impossível nesta
  máquina. `LDXR`/`STXR` são particularmente prováveis de aparecer em
  `busybox sh -c` de verdade (futex/spinlock de glibc/musl), então esta
  task é um pré-requisito funcional real do aceite do épico mesmo sem
  poder validá-lo agora.

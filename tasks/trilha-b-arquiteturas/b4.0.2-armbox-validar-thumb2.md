# B4.0.2 — Validar Thumb-2 de verdade no armbox (binário real, não só testes Java)

**Trilha:** B · **Depende de:** B4.0.1 (plumbing de seleção de arquitetura),
B2.1-B2.2 (cresce conforme B2.3-B2.5 fecharem) · **Repo:** armbox (+ arm-jitter)

## Contexto

Mesma lacuna de B4.0.1, agora para Thumb-2: B2.1 (infra) e B2.2 (data-processing)
foram validadas inteiramente por testes Java (`ThumbTwoDecoderTest`,
`Thumb2DataProcessingDecoderTest`), incluindo comparações contra o ARM clássico
equivalente — mas nunca por um binário ELF real executando código Thumb-2 de fato.
Diferença importante em relação a B4.0.1: **hoje não existe nenhum preset de
produção do arm-jitter com `ArmFeature.THUMB2` habilitado** — só arquiteturas
locais de teste (`ArmArchitecture.extending(ARMV6K, "...", ArmFeature.THUMB2)`
construídas dentro de cada classe de teste, com `Thumb2DataProcessingDecoder`
plugado manualmente via `withThumb32DecoderExtensions`). Esta task precisa criar
essa combinação como algo reutilizável ANTES de o armbox conseguir selecioná-la.

## Objetivo

1. arm-jitter ganha um preset reutilizável (não é o ARMv7-A completo da B3 — só o
   subconjunto Thumb-2 que já existe até aqui) que o armbox possa referenciar por
   nome.
2. `armbox --arch=thumb2` (novo valor do flag introduzido em B4.0.1) executa um
   binário real com código Thumb-2 de 32 bits genuíno e produz o resultado correto,
   nos três backends.

## Não inclui

- Não é o preset ARMv7-A final da task B3 (que inclui VFP, SDIV/UDIV, etc.) — é um
  preset intermediário, do tamanho do que B2.x já implementou. Nomear de forma que
  não sugira completude (ex. `ARMV6K_THUMB2` ou nome equivalente, decidir
  e documentar por quê).
- Não implementa nada de B2.3/B2.4/B2.5 aqui — só exercita o que já existe (B2.1 +
  B2.2). Se rodar esta task antes de B2.3-B2.5 estarem prontas, o escopo do binário
  de teste é só data-processing; se rodar depois, expandir a cobertura é natural
  (mas isso é uma repetição desta task, não uma dependência bloqueante).
- Não resolve B2.2.1/B2.2.2 (as duas simplificações conservadoras já documentadas)
  — se o binário real tropeçar nelas, isso é EVIDÊNCIA para priorizá-las, não algo
  a corrigir dentro desta task.

## Especificação

1. **Preset em arm-jitter:** novo `ArmArchitecture` público (ex. em
   `ArmArchitecture`, ao lado de `ARMV6K`) construído com
   `ArmArchitecture.extending(ARMV6K, "<nome>", ArmFeature.THUMB2)
   .withThumb32DecoderExtensions(List.of(new Thumb2DataProcessingDecoder()))` —
   mesma composição que os testes já fazem, só promovida a API pública. Adicionar
   a extensão à lista sempre que uma nova task B2.x fechar (documentar isso como
   convenção para B2.3-B2.5, para não esquecer de atualizar o preset).
2. **Seleção no armbox:** estender o enum/flag de B4.0.1 com o novo valor.
3. **Binário(s) de teste:** mesma limitação de toolchain de B4.0.1 (sem
   glibc/gcc no Windows). Duas fontes, pelo motivo já documentado em B4.0.1 (código
   handwritten cobre o que o compilador não emite espontaneamente):
   - Torture test `.s` (devkitARM, `-nostdlib`) escrito DIRETAMENTE em encoding
     Thumb-2 de 32 bits (`.thumb`, `.syntax unified`, mnemônicos que forcem a forma
     de 32 bits quando ambíguo — ex. `.w`) cobrindo pelo menos: modified immediate
     com carry-out (`ANDS`/`ADDS` com imediato rotacionado), `MOVW`+`MOVT`
     compondo uma constante de 32 bits, `ADD`/`ADR` com `SP`/`PC`, e a forma
     registrador com shift (incl. RRX).
   - Se devkitARM suportar `-mthumb -march=armv7-a` (ou equivalente) para C normal:
     recompilar `hello.elf` como sinal de cobertura de código gerado por
     compilador, mesmo padrão de B4.0.1.
4. Rodar em `--arch=thumb2` nos três backends e comparar com o valor esperado.

## Aceite

- `armbox --arch=thumb2 testdata/thumb2-torture.elf` sai com código 0 (sucesso) nos
  três backends; uma falha proposital confirma que o teste realmente detecta
  regressão.
- `--arch=armv5te` (default) e `--arch=armv6k` (B4.0.1) continuam inalterados.
- `mvn test` do armbox verde; `mvn test` do arm-jitter verde com o preset novo
  (mais gbaemu/ndsemu, G5, se algum bug for revelado e corrigido no caminho).
- README do armbox atualizado.

## Validação

`mvn test` no arm-jitter e no armbox (JBR 25) + execução manual dos binários reais.

## Armadilhas

- **`.syntax unified` e a escolha 16-bit-vs-32-bit é do assembler**, não 1:1 com o
  mnemônico — o mesmo `ADD` pode virar Thumb-1 (16 bits) ou Thumb-2 (32 bits)
  dependendo dos operandos/registradores. Usar o sufixo `.w` explicitamente onde a
  intenção é forçar a forma de 32 bits testada por B2.2, e CONFERIR o binário
  desmontado (`objdump -d`) antes de assumir que o assembler gerou o encoding
  esperado — é fácil escrever um "torture test Thumb-2" que na verdade compila
  para Thumb-1 e não testa nada novo.
- O preset novo herda de `ARMV6K` (não de `ARMV5TE`) — um binário Thumb-2 real
  pode acabar exercitando alguma instrução ARMv6K "de graça" mesmo sem essa ser a
  intenção do teste; não é um problema, mas ajuda a saber diagnosticar uma falha
  inesperada.
- Ver a mesma armadilha de toolchain de B4.0.1 (versão do binutils/GCC do
  devkitARM pode não suportar todos os mnemônicos Thumb-2 novos).

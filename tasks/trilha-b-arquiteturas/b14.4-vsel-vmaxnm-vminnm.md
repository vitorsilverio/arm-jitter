# B14.4 — `VSEL` + `VMAXNM`/`VMINNM` (`sp`/`dp`): abre o espaço VFP incondicional — 6 encodings

**Trilha:** B · **Repo:** arm-jitter (+ revalidação G5) · **Depende de:** B14.1
**Épico:** `b14-plano-vfp-armv8-32bit.md` · **Status:** ⬜ (spec escrita 2026-09-13, ainda não executada)

## Contexto

Primeira task do épico a mexer no espaço de encoding `1111 1110` (`cond=0b1111`, incondicional) —
o que o épico chama de "historicamente o ponto fraco do `ArmDecoder`".

### O encoding real (`target/isa-decode/vfp-uncond.decode`, linhas 37-61 — medido)

```
%vm_dp  5:1 0:4        %vm_sp  0:4 5:1
%vn_dp  7:1 16:4       %vn_sp  16:4 7:1
%vd_dp  22:1 12:4      %vd_sp  12:4 22:1

VSEL        1111 1110 0. cc:2 .... .... 1001 .0.0 ....   vm=%vm_sp vn=%vn_sp vd=%vd_sp sz=1
VSEL        1111 1110 0. cc:2 .... .... 1010 .0.0 ....   vm=%vm_sp vn=%vn_sp vd=%vd_sp sz=2
VSEL        1111 1110 0. cc:2 .... .... 1011 .0.0 ....   vm=%vm_dp vn=%vn_dp vd=%vd_dp sz=3

VMAXNM_hp   1111 1110 1.00 .... .... 1001 .0.0 ....      @vfp_dnm_s
VMINNM_hp   1111 1110 1.00 .... .... 1001 .1.0 ....      @vfp_dnm_s
VMAXNM_sp   1111 1110 1.00 .... .... 1010 .0.0 ....      @vfp_dnm_s
VMINNM_sp   1111 1110 1.00 .... .... 1010 .1.0 ....      @vfp_dnm_s
VMAXNM_dp   1111 1110 1.00 .... .... 1011 .0.0 ....      @vfp_dnm_d
VMINNM_dp   1111 1110 1.00 .... .... 1011 .1.0 ....      @vfp_dnm_d
```

Escopo desta task: **`VSEL` `sz=2`/`sz=3` + `VMAXNM_sp`/`VMINNM_sp`/`VMAXNM_dp`/`VMINNM_dp`** = 6.
As 3 formas `sz=1`/`_hp` (`bits[11:8]=1001`) ficam para **B14.6** (`FEAT_FP16`).

Os extratores de registrador (`%vm_sp`/`%vn_dp`/...) são **exatamente os mesmos** que
`VfpDecoder.registerNumber`/`vd`/`vm` já implementam desde B3.5 — nenhuma matemática de registrador
nova nesta task.

### 🔴 Achado central desta spec (medido lendo o código, não suposto): misdecode G8 pré-existente

`ArmDecoder#decodeUnconditional` (linha ~1015) termina consultando as extensões de decoder, com um
comentário que diz explicitamente que *"o espaço VFP incondicional já pluga aqui"*:

```java
for (DecoderExtension extension : architecture.decoderExtensions()) {
    DecodedInstruction decoded = extension.tryDecode(raw, address, condition);
    if (decoded != null) { return decoded; }
}
return DecodedInstruction.unimplemented(address, raw, InstructionSet.ARM, condition);
```

E `VfpDecoder#isVfpCoprocessorSpace` olha **só** `bits[27:24]` e `bits[11:8]` — nunca
`bits[31:28]`. Resultado, **hoje, em `ARMV7A` e `ARM11_MPCORE`** (e nas formas T32 via
`Thumb2VfpDecoder`, que delega para a mesma classe):

| Encoding real | Caminho tomado hoje | Decodifica como |
|---|---|---|
| `VSEL` `cc=00` | `decodeDataProcessing`, `op1 = bit23:bit21:bit20 = 000`, `bit6=0` | **`VMLA`** |
| `VSEL` `cc=01` | `op1=001`, `bit6=0` | **`VNMLS`** |
| `VSEL` `cc=10` | `op1=010`, `bit6=0` | **`VMUL`** |
| `VSEL` `cc=11` | `op1=011`, `bit6=0` | **`VADD`** |
| `VMAXNM_sp`/`_dp` | `op1=100`, `bit6=0` | **`VDIV`** |
| `VMINNM_sp`/`_dp` | `op1=100`, `bit6=1` → `null` | `UNIMPLEMENTED` (honesto por acidente) |

Ou seja: **8 dos 12 encodings de `VSEL`/`VMAXNM` (sp+dp) hoje produzem silenciosamente uma
instrução VFP DIFERENTE e errada** — exatamente a violação de G8 que o `tasks/README.md` descreve
("um decoder que devolve a instrução errada para um encoding desconhecido troca um diagnóstico por
corrupção silenciosa") e a mesma classe de bug da E5/E6 (`0xF2000000` virando `AND`). A tabela de
cobertura **não** mostra isso porque o grupo `vfp-uncond.decode` é `NOT_IN_ANY_PRESET` (as células
saem `·`, não `⚠️`).

**Consequência de desenho**: o fechamento G8 **não pode** viver num decoder novo anexado só ao
`ARMV8A_32` — isso deixaria `ARMV7A`/`ARM11_MPCORE` misdecodificando. A recusa tem que acontecer no
caminho que TODOS os presets com VFP percorrem. Ver "Especificação".

### O discriminador funciona nos DOIS encodings

O cabeçalho do próprio `vfp-uncond.decode` diz que estas instruções são, em A32,
`1111 1110 .... .... .... 101. ...0 ....` e, em T32, `1111 110. ...`/`1111 1110 ...`. Nos dois
casos o nibble `bits[31:28]` do `raw`/`raw32` é `1111` — enquanto o VFP **condicional** tem ali a
condição real (A32) ou o prefixo fixo `1110` do hw1 (T32, ver Javadoc de `Thumb2VfpDecoder`).
Portanto `(raw >>> 28) == 0xF` é um discriminador válido para os dois caminhos, e é a única
informação nova que `VfpDecoder` precisa passar a olhar. ⚠️ Confirmar o lado T32 byte a byte com um
montador real antes de fixar (Armadilha 5) — a mesma disciplina que B13.11/B13.14/B13.19 usaram.

### Semântica (confirmada no QEMU real, `target/arm/tcg/translate-vfp.c`, via `WebFetch`)

- **`VSEL`**: `cc:2` **não** é o nibble de condição de 4 bits. `trans_VSEL` mapeia
  `0`→`EQ` (Z), `1`→`VS` (V), `2`→`GE` (N == V), `3`→`GT` (!Z && N == V) — os flags lidos são os do
  **CPSR/APSR**, não os do `FPSCR`. `vd = cond ? vn : vm`. Gate `aa32_vsel`.
- **`VMAXNM`/`VMINNM`**: `trans_VMAXNM_sp/dp` chama `gen_helper_vfp_maxnums`/`maxnumd`, que
  implementa **IEEE 754-2008 `maxNum`/`minNum`** — prefere o operando numérico quando o outro é NaN.
  Gate `aa32_vminmaxnm` (`MVFR2.FPMISC >= 4`).

### A semântica de `maxNum`/`minNum` JÁ EXISTE neste projeto

`advsimd/AdvSimdLanes.maxNum`/`minNum` (usados por `FMAXNM`/`FMINNM` A64 desde B8.4, e por
`Ir64FpExecutor` linhas ~79-93). Esta task **não escreve o algoritmo** — reusa, no mesmo espírito
"D1" da RFC B13.2. É literalmente a armadilha que o épico anota ("implementar com `Math.max` produz
o resultado errado para NaN e para `+0.0`/`-0.0`"): o código correto já está escrito, basta chamá-lo.

## Objetivo

Os 6 encodings decodificam e executam sob `ARMV8A_32` (gate `ArmFeature.ARMV8_FP`), e **o espaço
incondicional inteiro `1111 1110`+CP10/CP11 passa a ser recusado explicitamente** (`UNIMPLEMENTED`)
em todo preset sem essa feature — fechando o misdecode G8 descrito acima.

## Inclui

1. **Gate do espaço incondicional em `VfpDecoder`**: reconhecer `(raw >>> 28) == 0xF` **antes** do
   dispatch atual (`decodeCdpOrMrcSpace`/`decodeLoadStore*`), roteando para um caminho novo
   (`decodeUnconditional...`, nesta classe ou numa classe irmã — ver Armadilha 1). Sem
   `ArmFeature.ARMV8_FP`, esse caminho devolve `UNIMPLEMENTED` explícito para TODO o espaço.
2. **`VSEL`** (`sz=2`/`sz=3`): `InstructionKind` novo (ver Armadilha 2 — **não** reusar o campo
   `Condition` da `DecodedInstruction`) + `IrOp` novo + executor, lendo os flags NZCV do **CPSR**.
3. **`VMAXNM`/`VMINNM`** (`sp`/`dp`): duas constantes novas em `IrOp.VfpOperation`
   (`MAXNM`/`MINNM`), reusando `InstructionKind.VFP_ALU` e delegando a
   `AdvSimdLanes.maxNum`/`minNum`.
4. **Fechamento G8 do que sobra**: dentro de `1111 1110`+CP10/CP11, tudo que não for um dos 6
   encodings desta task (incluindo os de B14.5/B14.6, ainda não implementados) devolve
   `UNIMPLEMENTED`, nunca `null` que caia num `CoprocessorDecoder` genérico nem no dispatch
   condicional.
5. Testes (ver Aceite), incluindo os de **não-misdecode** (o achado central).

## Não inclui

- **`VRINT{A,N,P,M}`/`VCVT{A,N,P,M}`** (`sz=2`/`sz=3`) — **B14.5** (depende desta: usa o mesmo
  caminho de decode do espaço incondicional que esta task instala).
- **As 3 formas `sz=1`/`_hp` de `VSEL`/`VMAXNM`/`VMINNM`** e `VMOVX`/`VINS` — **B14.6**
  (`FEAT_FP16`). Até lá, `bits[11:8]=1001` no espaço incondicional é `UNIMPLEMENTED` explícito.
- **Qualquer NEON** — o espaço `1111 001x` (NEON A32) é do épico B13; esta task só toca
  `1111 1110` com `bits[11:8] ∈ {1010,1011}` (e a recusa explícita de `1001`).
- **Coluna `v8-A/32` na tabela / `ArmProcessor`** — B14.7.
- **Emissão nativa/Truffle** — decode + interpretado apenas.

### Desenho proposto (a validar na execução)

```
VfpDecoder.tryDecode(raw, ...):
    if ((raw >>> 28) == 0xF)                      // espaço incondicional, A32 e T32
        return decodeUnconditionalSpace(raw, ...) // nunca cai no dispatch condicional
    ... (tudo como hoje)

decodeUnconditionalSpace:
    if (!architecture.has(ARMV8_FP)) return UNIMPLEMENTED     // fecha o misdecode em v7-A/MPCore
    if (bits[11:8] == 1001)          return UNIMPLEMENTED     // formas _hp → B14.6
    if (bits[11:8] not in {1010,1011}) return null            // não é CP10/CP11 (NEON etc.)
    if (bit23 == 0)  → VSEL   (cc = bits[21:20])
    if (bits[23:20] == 1000) → VMAXNM (bit6=0) / VMINNM (bit6=1)
    ... resto → UNIMPLEMENTED (B14.5/B14.6)
```

`claimsEncodingSpace` precisa acompanhar (é ele que impede o `CoprocessorDecoder` genérico de
capturar o espaço depois) — conferir a interação com `claimsThisDecoder`, que hoje só devolve
`true` com `VFPV2`.

### `VSEL`: tabela de condição

| `cc` | Condição | Teste nos flags do **CPSR** |
|---:|---|---|
| `00` | `EQ` | `Z == 1` |
| `01` | `VS` | `V == 1` |
| `10` | `GE` | `N == V` |
| `11` | `GT` | `Z == 0 && N == V` |

`vd = cond ? vn : vm` (cópia de bits, sem aritmética — não normaliza NaN, não toca `FPSCR`).

## Aceite

- `VSEL` (`sz=2`/`sz=3`, 4 valores de `cc`) e `VMAXNM`/`VMINNM` (`sp`/`dp`) decodificam sob
  `ARMV8A_32`, **nos dois encodings** (A32 e T32), e executam:
  - `VSEL` seleciona `vn`/`vm` pelos flags do CPSR (teste com os 4 `cc` × condição verdadeira e
    falsa);
  - `VMAXNM`/`VMINNM` devolvem o operando NUMÉRICO quando o outro é NaN (teste explícito com
    `NaN`, com `+0.0`/`-0.0` e com o par `(+0.0, -0.0)`), e a MESMA resposta que o `FMAXNM`/`FMINNM`
    A64 para as mesmas entradas (teste de equivalência entre os dois lados).
- **Não-misdecode (o achado central)**: sob `ARMV7A`/`ARM11_MPCORE`, os mesmos 12 encodings
  (`VSEL` sp/dp × 4 `cc` + `VMAXNM`/`VMINNM` sp/dp) devolvem `UNIMPLEMENTED` — nunca
  `VMLA`/`VNMLS`/`VMUL`/`VADD`/`VDIV`.
- **Zero-diff do VFP condicional**: todos os testes existentes de `VfpDecoder`/`Thumb2VfpDecoder`
  passam sem alteração (o gate novo só olha `bits[31:28]`).
- O que sobra do espaço `1111 1110` (formas de B14.5/B14.6, `bits[11:8]=1001`, valores reservados)
  é `UNIMPLEMENTED` explícito, não `null` engolido por `CoprocessorDecoder` (G8) — teste explícito.
- `docs/COBERTURA-ISA.md` sem regressão em nenhuma célula.
- `mvn -o test` verde + G5 verde nos 5 consumidores.

## Armadilhas

1. **Onde colocar o decode novo**: dentro de `VfpDecoder` (mais simples, reusa `registerNumber`/
   `vd`/`vm`/`validDoubleRegister` e serve A32 e T32 de graça via `Thumb2VfpDecoder`) ou numa classe
   irmã (`VfpUnconditionalDecoder`) anexada a todos os presets com VFP. **A restrição dura é**: o
   fechamento G8 tem que valer também em `ARMV7A`/`ARM11_MPCORE`, que NÃO terão a feature — ou seja,
   se for classe nova, ela precisa ser anexada a esses presets também (e ANTES de `VfpDecoder` na
   lista), o que mexe em 2 presets existentes. Decidir por medição e documentar.
2. **🔴 `VSEL` NÃO é uma instrução condicional.** Mapear `cc` para `Condition` e preencher o campo
   `condition` da `DecodedInstruction` faria o bloco PULAR a instrução quando a condição fosse
   falsa, em vez de escrever `vm` em `vd` — resultado silenciosamente errado, e ainda por cima
   colidindo com **G4** (`Cycle`/`Fetch` nunca recebem guard). A condição é **dado**, não controle:
   tem que viver no `IrOp` (um campo próprio) e ser avaliada pelo executor.
3. **`VMAXNM` ≠ `VMAX`** — a armadilha que o épico já anota, e que o A64 pagou em B8.4. Não escrever
   `Math.max`: chamar `AdvSimdLanes.maxNum`/`minNum`. Casos de teste obrigatórios: `(NaN, 1.0)`,
   `(1.0, NaN)`, `(NaN, NaN)`, `(+0.0, -0.0)`, `(-0.0, +0.0)`.
4. **O espaço `1111 1110` colide visualmente com `MCR2`/`CDP2`** (coprocessador "forma 2", ARMv5+,
   que `ArmDecoder`/`CoprocessorDecoder` já tratam) — `bits[27:24]=1110` com `cond=1111`. O que
   separa é `bits[11:8] ∈ {1010,1011}` (CP10/CP11, VFP) vs qualquer outro coprocessador. Se o gate
   novo reivindicar `bits[11:8]` genérico, rouba `MCR2`/`CDP2` de coprocessadores reais — e o
   `n3dsemu` usa coprocessador de verdade (CP15). Testar `MCR2`/`MRC2`/`CDP2` para cp15 e cp9 como
   não-regressão.
5. **Confirmar o encoding T32 com um montador real** antes de fixar (`arm-linux-gnueabihf-as
   -march=armv8-a` no WSL, mesma técnica de B13.11/B13.14/B13.19/B13.20): montar
   `vseleq.f32 s0, s1, s2` e `vmaxnm.f64 d0, d1, d2` em ARM e em Thumb e comparar os bytes com o que
   o decoder espera. O cabeçalho do `.decode` menciona **duas** faixas T32 (`1111 110.` e
   `1111 1110`) — conferir qual delas realmente carrega estas 6, em vez de deduzir.
6. **`claimsEncodingSpace` também precisa mudar** — é o método que impede o `CoprocessorDecoder`
   genérico de pegar o espaço. Alterar `tryDecode` e esquecer dele produz um `⚠️`/FALLBACK em vez de
   um `❌` honesto (o `IsaCoverageReport` distingue os dois — usar isso como teste, como o épico
   sugere).
7. **`bit4`**: no `.decode`, os 6 encodings desta task fixam `bit4=0` (`.0.0`/`.1.0`). O caminho
   novo não deve aceitar `bit4=1` (é outro espaço — transferência para registrador geral).
8. **G3/G5 com ressalva honesta**: esta task MUDA comportamento observável de `ARMV7A`/
   `ARM11_MPCORE` (de misdecode para `UNIMPLEMENTED`). Isso é uma correção de G8, não uma violação
   de G3 (nenhuma factory/assinatura/default muda, e o comportamento anterior era um bug), mas
   **tem que ser declarado** no `## Resultado` e validado nos 5 consumidores — nenhum binário
   ARMv7-A real contém essas palavras (são encodings ARMv8), então o risco medido é zero, mas a
   afirmação precisa de evidência (G5 verde), não de fé.

## Não fazer

- Não implementar `VRINT`/`VCVT` com `rm:2` (B14.5) nem as formas `_hp`/`VMOVX`/`VINS` (B14.6) —
  mas **deixar o `UNIMPLEMENTED` explícito** no lugar delas (G8), nunca `null`.
- Não mexer no espaço NEON `1111 001x` (B13).
- Não usar `Math.max`/`Math.min` (Armadilha 3).
- Não representar `cc` como `Condition` da instrução (Armadilha 2).
- Não acrescentar a coluna `v8-A/32` nem `ArmProcessor` (B14.7).
- Não "consertar" o misdecode só no preset novo, deixando `ARMV7A` misdecodificando (Armadilha 1).

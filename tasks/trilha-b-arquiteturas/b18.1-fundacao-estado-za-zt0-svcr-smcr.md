# B18.1 — Fundação de estado SME: `SVCR` real, `SMCR_EL1/2/3`, `ID_AA64SMFR0_EL1`, banco `ZA` e `ZT0` — 0 encodings

**Trilha:** B · **Repo:** arm-jitter (+ revalidação G5) · **Depende de:** B17.3 (⬜, que por sua vez depende da RFC B17.2)
**Épico:** `b18-plano-sme.md` · **Status:** ⬜ (spec escrita 2026-09-14, ainda não executada)

## Contexto

Degrau 1 da escada B18. O épico `b18-plano-sme.md` mede **623 encodings** em
`target/isa-decode/sme.decode`, hoje `NOT_IN_ANY_PRESET` — o **último** grupo nesse estado na
tabela (`docs/COBERTURA-ISA.md`); fechá-lo é o pré-requisito declarado do release `1.4.0`
(`tasks/README.md`).

Esta task é o espelho, do lado SME, do que a **B17.3** é do lado SVE: **estado, sem decode**.
Nenhum encoding de `sme.decode` é decodificado aqui; `docs/COBERTURA-ISA.md` sai byte a byte
idêntica.

O buraco que ela fecha está escrito no próprio código, em
`arch64/Aarch64Feature.java` (constante `SCALABLE_MATRIX_EXTENSION`, medida nesta rodada de spec):

```java
/// `FEAT_SME` — Scalable Matrix Extension (estado ZA/streaming-SVE, controlado por `SVCR` via
/// `MSR (immediate)`). ARMv9.2-A. Nenhum estado ZA/SVE é modelado ainda — esta feature só
/// existe para permitir que `MSR SVCR` continue recusado (`UNIMPLEMENTED`) de forma
/// explicitamente rastreável, não silenciosa, quando o decoder passar a consultá-la.
SCALABLE_MATRIX_EXTENSION,
```

A **B19.28** (✅ 2026-09-11) já ligou o decoder a essa constante: `MSR SVCR<mask>, #imm`
(`a64.decode:311`) decodifica `mask`/`imm` e **sempre recusa**, com mensagem nomeada quando o
preset declara `FEAT_SME`. Esta task cria o estado que falta atrás do gate; a **B18.2** é que
transforma a recusa em efeito real.

Três achados concretos, todos verificados no arquivo real:

1. **`### SME Memory` tem 9 encodings, não 28.** São `LDST1` ×5 (linhas 150-172, uma por `esz`),

### O modelo do QEMU (confirmado por `WebFetch` de `target/arm/tcg/translate-sme.c` nesta rodada)

- **`ZA` é um array de tiles do MESMO tipo do registrador vetorial**, indexado por tile:

  ```c
  static TCGv_ptr get_tile(DisasContext *s, int esz, int tile)
  {
      offset = tile * sizeof(ARMVectorReg) + offsetof(CPUARMState, za_state.za);
  }
  ```
  e o endereçamento de linha/coluna (slice horizontal/vertical) é `(Rs+imm) MOD (svl >> esz)`:
  ```c
  static TCGv_ptr get_tile_rowcol(DisasContext *s, int esz, int rs,
                                  int tile, int imm, int div_len,
                                  int vec_mod, bool vertical)
  {
      len = ctz32(streaming_vec_reg_size(s) / div_len) - esz;
      ...
  }
  ```
- **Tudo é dimensionado por `streaming_vec_reg_size(s)` (o `SVL`)**, nunca por uma constante.
- **A checagem de acesso é hierárquica, em TRÊS níveis** — é o que esta task tem que entregar:
  ```c
  bool sme_enabled_check(DisasContext *s)      /* PSTATE.SM habilitado */
  bool sme_za_enabled_check(DisasContext *s)   /* + PSTATE.ZA / armazenamento ZA */
  bool sme_smza_enabled_check(DisasContext *s) /* os dois juntos */
  bool sme2_zt0_enabled_check(DisasContext *s) /* + ZT0 acessível */
  ```
  com síndrome própria (`syn_smetrap(SME_ET_InaccessibleZT0, false)`) — ou seja, o trap de SME
  **não** é o mesmo trap de SVE (B17.3), tem `EC`/síndrome próprios.
- **O gate de feature é fatiado**, não monolítico (`dc_isar_feature`):
  `aa64_sme`, `aa64_sme2`, `aa64_sme2p1`, `aa64_sme_i16i64`, `aa64_sme_f64f64`, `aa64_sme_lutv2`,
  `aa64_sme_mop4`, `aa64_sme_tmop`. **Oito** predicados distintos — a Armadilha 1 do épico
  ("o gate tem que ser dividido antes de crescer") é mais profunda do que "`SME` vs `SME2`".
- **Layout de `ZA` (de `sme_helper.c`)**: *"Recall that ZAnH.D[m] is spread across ZA[n+8*m], so
  each row is discontiguous within ZA[]"* — as slices verticais são descontíguas por construção
  (`tile_vslice_offset()`/`tile_vslice_index()`), as horizontais são `memcpy`/`memset` diretos.

`Aarch64Core` ganha `ZA` (alocado preguiçosamente), `ZT0`, `SVCR` (`SM`/`ZA`), `SMCR_EL1/EL2/EL3` e

5. **Banco `ZA`, com alocação preguiçosa (REQUISITO, não otimização — ver Armadilha 2)** —

6. **`ZT0`** — 512 bits (`long[8]`), SME2, também preguiçoso, com a mesma disciplina.
7. **Checagem de acesso SME**, em três níveis, espelhando o QEMU: "SM habilitado", "ZA habilitado",

8. **`ID_AA64SMFR0_EL1`** em `Aarch64SystemRegisterId`, refletindo as features do preset — e **só**

### `ZA`: o dimensionamento

`ZA` é um quadrado de `SVL × SVL` **bits**: `SVL/8` bytes por linha, `SVL/8` linhas ⇒
`(SVL/8)²` bytes. Números reais:

| `SVL` | `ZA` |
|---:|---:|
| 128 bits | 256 B |
| 256 bits | 1 KiB |
| 512 bits | 4 KiB |
| 1024 bits | 16 KiB |
| 2048 bits | 64 KiB |

O épico diz "32 KiB com VL de 512" — a conta correta para `SVL=512` é **4 KiB**; 32 KiB
corresponde a `SVL≈1448` (na prática, `SVL=2048` ⇒ 64 KiB). Corrigir o número no `## Resultado`;
**a conclusão do épico não muda** — é grande o bastante para que alocação preguiçosa seja
requisito.

## Aceite

- **Alocação preguiçosa comprovada por teste**, não por inspeção: um core criado com um preset
  ARMv9.2-A **sem** nunca ligar `SVCR.ZA` não aloca o array de `ZA` (asserção direta sobre o campo
  interno, ou um contador/flag exposto para teste). É o item de Aceite central desta task.
- Ligar `SVCR.ZA` aloca `ZA` com `(SVL/8)²` bytes e **zerado**; desligar libera/zera. O ciclo
  liga→escreve→desliga→liga devolve `ZA` zerado (regra ARM real — confirmar contra o manual).
- `MRS x0, SMCR_EL1` / `MSR SMCR_EL1, x0` funcionam; `SMCR_EL1.LEN` limita o `SVL` efetivo; `SVL`
  efetivo nunca excede o implementado nem cai abaixo do mínimo arquitetural.
- `SVL` e `VL` são **independentes**: um teste com `VL=256` e `SVL=512` (e vice-versa) mostra os
  dois métodos devolvendo valores distintos.
- `ID_AA64PFR1_EL1.SME` é não-zero sob um preset com `FEAT_SME` e zero sob `ARMV8_0_A`;
  `ID_AA64SMFR0_EL1` anuncia `SMEver` e **zero** em todos os campos de capacidade.
- Acesso SME com `CPACR_EL1.SMEN = 0b00` é negado nos três níveis (chamar as checagens
  diretamente — nenhuma instrução SME decodifica ainda).
- Save/restore de um core com `ZA`/`ZT0`/`SVCR`/`SMCR_ELx` não nulos preserva o estado bit a bit;
  save/restore de um core que **nunca** alocou `ZA` não cria o array no restore.
- **`docs/COBERTURA-ISA.md` byte a byte idêntica.**
- `mvn -o test` verde + G5 verde nos 5 consumidores.

   `sme_i16i64`, `sme_f64f64`, `sme_lutv2`, `sme_mop4`, `sme_tmop`). Criar só `SME`/`SME2` e
   descobrir na B18.5/B18.6 que falta `FEAT_SME_MOP4`/`FEAT_SME_LUTv2` custa uma segunda passagem
   por `Aarch64Feature` e pelos presets. **E o risco imediato**: `ARMV9_2_A` já declara
   `SCALABLE_MATRIX_EXTENSION` hoje — se esta task puser estado real atrás dela sem fatiar, esse
   preset passa a **prometer SME inteiro** (incluindo SME2, que é ARMv9.4-A) para software real.
2. **`ZA` grande — alocação preguiçosa é REQUISITO.** `(SVL/8)²` bytes: 4 KiB em `SVL=512`, **64
   KiB** em `SVL=2048`. Alocar incondicionalmente no construtor do `Aarch64Core` penaliza **todo**
   consumidor que não usa SME — inclusive `virtual-arm-box` e `n3dsemu`, e qualquer um que
   instancie muitos cores. Requisitos concretos: (a) campo `null` até o primeiro uso; (b) nenhum
   caminho quente (`step`/`execute`) toca o campo quando `SVCR.ZA == 0`; (c) `Aarch64CpuSnapshot`/
   `saveState` representam "nunca alocado" sem materializar o array. Mesma disciplina que o
   `memoryTags` esparso da B19.14 já estabeleceu no projeto.
3. **Encodings de `SMCR_ELx` e layout de `ID_AA64SMFR0_EL1` têm que ser MEDIDOS.** `MSR` com o
   encoding errado grava em OUTRO registrador — é exatamente o misdecode silencioso que o **G8**
   proíbe, e é pior que recusar. Mesma Armadilha 3 da B17.3.
4. **`SVL ≠ VL`.** É o erro mais fácil do épico: reusar `vectorLengthBytes()` (B17.3) para
   dimensionar `ZA` "porque em modo streaming são iguais" está errado duas vezes — o hardware pode
   implementar `SVL` diferente de `VL`, e fora do modo streaming `VL` é o valor não-streaming.
   Métodos separados desde o primeiro dia.
5. **`ID_AA64SMFR0_EL1` não pode anunciar o que não existe.** Anunciar `I16I64`/`F64F64`/`SMEver=2`
   antes de B18.5/B18.7 faz software real (um kernel Linux com suporte SME — o caso da B4.1.5)
   escolher caminhos que batem em `UNIMPLEMENTED`. Cada campo é aceso pela task que fecha a família
   correspondente. Deixar isso escrito no `## Resultado`.
6. **O trap de SME não é o trap de SVE.** `CPACR_EL1.SMEN` (bits distintos de `ZEN`), `CPTR_EL2.SMEN`,
   `CPTR_EL3.ESM`, e uma síndrome `SME_ET_*` própria. Reusar o `sve_access_check` da B17.3 "porque
   é parecido" produz síndrome errada num caminho que o software real inspeciona.
7. **Ligar/desligar `SVCR.SM` ou `SVCR.ZA` tem efeito destrutivo no hardware real** (zera `Z`/`P`
   ao entrar/sair de streaming; zera `ZA` ao habilitar). Esta task **só armazena os bits** — o
   efeito é B18.2. Mas o Javadoc do campo tem que dizer isso explicitamente, senão a B18.2 vira
   uma caça a suposições.
8. **`Aarch64CpuSnapshot` é `record` público** — acrescentar componente é mudança de assinatura.
   Mesma avaliação da Armadilha 6 da B17.3; decidir por leitura e documentar.

- Não implementar efeito de modo streaming, `SMSTART`/`SMSTOP` nem mudar o comportamento de

- Não alocar `ZA`/`ZT0` no construtor do core (Armadilha 2).
- Não anunciar campos de `ID_AA64SMFR0_EL1` sem a implementação correspondente.

- Não começar antes de a RFC B17.2 ser decidida pelo usuário e a B17.3 estar ✅.

# B6.6.1 — AArch64: acesso a registrador de sistema (`MRS`/`MSR`) — pré-requisito da MMU

**Trilha:** B · **Depende de:** B6.1 ✅ (`decoder64`/`ir64`/`core64` precisam
existir) · **Repo:** arm-jitter

## Contexto

Primeira das 6 sub-tasks em que esta rodada de spec (2026-07-26) decompõe
**B6.6** (`b6-aarch64.md`, escopo fechado "MMU v8 (VMSA64, 4KiB granule,
EL0/EL1) + hospedeiro `virt64`", aceite "kernel arm64 mínimo até shell —
reusar aprendizado de B4.1"). Agrupamento em 6 (não 5, como o precedente
32-bit B4.1.1-B4.1.5) porque a pesquisa desta rodada confirmou um
**pré-requisito estrutural que não existe no mundo 32-bit**: AArch64 NÃO tem
instrução `MCR`/`MRC` — controle de sistema (`TTBR0_EL1`, `TCR_EL1`,
`SCTLR_EL1`, `MAIR_EL1`, `ESR_EL1`, `FAR_EL1`, etc.) é acessado via `MRS`/`MSR
(register)`, com um encoding próprio (`op0:op1:CRn:CRm:op2` empacotado) que
**não existe em NENHUM lugar do código A64 hoje** — confirmado por grep nesta
rodada: `decoder64/Aarch64Decoder.java` não tem nenhum caso de `MRS`/`MSR`
(só um COMENTÁRIO na linha 847 reconhecendo o gap: `// System instructions
(barreiras, hints, MSR/MRS...) e demais formas do grupo Branch/`);
`ir64/Ir64Op.java` não tem nenhum record `SystemRegister`/`Mrs`/`Msr`; grep
repo-wide por `CoprocessorBus`/`Cp15` não encontra NENHUM análogo A64.

**Por que isto é pré-requisito, não parte de B6.6.2+**: toda a cadeia B6.6.2
(page-walk) → B6.6.3 (ponte sistema↔MMU) → B6.6.4 (aborts) → B6.6.5
(gerações no BlockCache) precisa que CÓDIGO GUEST consiga programar
`TTBR0_EL1`/`TCR_EL1`/`SCTLR_EL1`/etc. — exatamente como o precedente 32-bit
(`Cp15VmsaCoprocessor`, B4.1.2) precisou que `MCR`/`MRC` já existissem desde
B1.x antes de existir algo para ligar. Sem este mecanismo, B6.6.3 não teria
"onde pendurar" os registradores de controle da MMU. Por isso esta task vem
PRIMEIRO na ordem de dependência, mesmo sendo, por si só, independente de
qualquer coisa relacionada a MMU (é só decode+IR+executor de um mecanismo de
acesso a registrador, reutilizável por QUALQUER registrador de sistema A64
futuro — FPCR/FPSR de B6.5, `CNTFRQ_EL0` de um timer futuro, etc. — não só
os da MMU).

## Fatos de referência (fonte: `ARM DDI 0487` C5.2 "System instructions" +
QEMU `target/arm/tcg/a64.decode` — CONFERIR literalmente contra o HEAD do
master antes de implementar, mesma disciplina de pin de versão de B6.3.x;
nada abaixo foi transcrito de uma leitura de código nesta rodada, é o
ESQUELETO esperado a partir do conhecimento arquitetural geral da ISA)

1. **Encoding geral**: `MRS`/`MSR (register)` vivem dentro da classe
   top-level "Branch, Exception Generating and System instructions"
   (`CLASS_BRANCH_EXCEPTION_SYSTEM = 0b101`, já tratada por
   `Aarch64Decoder.decodeBranchExceptionSystem` desde B6.1 — B/BL/B.cond/
   CBZ/CBNZ/TBZ/TBNZ/BR/BLR/RET/SVC já moram lá; `MRS`/`MSR` são um subgrupo
   adicional dentro do MESMO método top-level, não uma classe nova).
   Encoding fixo típico: bits `1101010100` + `L` (bit21, 1=MRS/leitura,
   0=MSR/escrita) + `op0`(2) + `op1`(3) + `CRn`(4) + `CRm`(4) + `op2`(3) +
   `Rt`(5) — CONFERIR a posição exata de cada campo contra `a64.decode`
   (`SYS`/`SYSL`/`MRS`/`MSR_reg` no QEMU) antes de implementar; os nomes
   `op0`/`op1`/`CRn`/`CRm`/`op2` seguem a nomenclatura do próprio manual
   (`ARM DDI 0487 C5.2.3`, "System register encodings").
2. **`op0:op1:CRn:CRm:op2` identifica UM registrador de sistema específico**
   — o manual publica uma tabela de ~200+ combinações válidas (a maioria
   fora do escopo desta task). Esta task cobre só o subconjunto necessário
   para B6.6.3 (MMU) mais o que B6.5 já deixou como pendência (`FPCR`/
   `FPSR`, opcionais nesta task — ver Decisão D3): `TTBR0_EL1`, `TCR_EL1`,
   `SCTLR_EL1`, `MAIR_EL1`, `ESR_EL1`, `FAR_EL1`, `VBAR_EL1`, `ELR_EL1`,
   `SPSR_EL1` (os 3 últimos citados aqui como pré-requisito ANTECIPADO de
   B6.6.4, que precisa deles para entrada/retorno de exceção EL0→EL1 — ver
   Armadilhas sobre não implementar a SEMÂNTICA de exceção nesta task, só o
   mecanismo de leitura/escrita do registrador).
3. **`MSR (immediate)`** (forma que escreve campos de `PSTATE` diretamente
   como `DAIFSet`/`DAIFClr`/`SPSel` via um imediato de 4 bits, sem passar por
   `Xt`) é um encoding DIFERENTE de `MSR (register)` — **fora do escopo desta
   task** (não citado como necessário por B6.6.2-B6.6.5; se aparecer como
   bloqueio real, é achado que abre task nova).

## Decisões de desenho FECHADAS nesta rodada

### D1 — `Ir64Op.SystemRegister` único para `MRS` e `MSR`, com `boolean read`

Mesma decisão estrutural que `IrOp.MProfileSystemRegister` (perfil M, B7.4)
já tomou para o `MRS`/`MSR` de 16 bits do Cortex-M — reaproveitar o PADRÃO
(não o tipo: perfil M é 32-bit/`int`, isto é A64/`long` — sibling, não
generalização, mesmo motivo de sempre) mas não o código:

```java
/// `MRS`/`MSR (register)` (`ARM DDI 0487 C5.2.3`, encoding a confirmar contra
/// `a64.decode` — ver Fatos de referência #1 da task B6.6.1). O registrador de
/// sistema é identificado pela 5-upla `op0:op1:crn:crm:op2` empacotada num
/// índice único pelo DECODER (nunca resolvida pelo executor a partir dos bits
/// crus — mesma disciplina de resolução única já usada em outros pontos do
/// projeto, ex. `Ir64Condition.decode`).
record SystemRegister(boolean read, Aarch64SystemRegisterId register, int rt) implements Ir64Op
// kind() = SYSTEM_REGISTER = 24 (próximo Kind livre depois de B6.5.2's FP64_CONVERT=23,
// SE B6.5 já tiver fechado quando esta task for implementada — CONFERIR o próximo
// Kind livre real no momento da implementação, não assumir 24 às cegas)
```

`Aarch64SystemRegisterId` — enum novo (`ir64/` ou `core64/`, decidir na hora)
com UMA constante por registrador coberto (Fatos de referência #2):
`TTBR0_EL1`, `TCR_EL1`, `SCTLR_EL1`, `MAIR_EL1`, `ESR_EL1`, `FAR_EL1`,
`VBAR_EL1`, `ELR_EL1`, `SPSR_EL1` (+ `FPCR`/`FPSR` se D3 decidir incluir).
Decoder mapeia `op0:op1:CRn:CRm:op2` → `Aarch64SystemRegisterId` via `switch`
exaustivo; combinação não coberta → `UnsupportedOperationException` (mesmo
padrão UNDEFINED-vs-não-implementado já usado em toda a trilha A64 — aqui é
literalmente "não implementado ainda", já que o espaço de encoding É válido
arquiteturalmente, só não coberto pelo subconjunto desta task; documentar
essa distinção explicitamente no javadoc, diferente de um UNDEFINED real).

### D2 — Barramento de registrador de sistema A64: `Aarch64SystemRegisterBus`

Sibling de `CoprocessorBus` (32-bit) — mesma composição/decorator, não
herança (`b4.1-mmu-softmmu.md`/RFC-SOFTMMU.md §4 cita
`Cp15VmsaCoprocessor implements CoprocessorBus` como o precedente de
"hospedeiro instala e pode encadear outro bus"). Interface nova
`core64/Aarch64SystemRegisterBus` (ou `decoder64/`/pacote a decidir):
```java
public interface Aarch64SystemRegisterBus {
    boolean handles(Aarch64SystemRegisterId register);
    long read(Aarch64SystemRegisterId register);
    void write(Aarch64SystemRegisterId register, long value);
}
```
`Aarch64Core` ganha um bus default (`Aarch64SystemRegisterBus.NONE` ou
similar — leitura/escrita de qualquer registrador não instalado lança
`UnsupportedOperationException`, mesmo padrão de "nenhum hospedeiro instalou
nada ainda" que `ArmCore`/`CoprocessorBus` já usam) + `setSystemRegisterBus`.
B6.6.3 instala `Aarch64VmsaSystemRegisters implements Aarch64SystemRegisterBus`
(nome análogo a `Cp15VmsaCoprocessor`) — não esta task, que só cria o
MECANISMO, sem nenhum registrador de MMU realmente ligado a nada ainda
(handles() sempre false até B6.6.3 instalar um bus real; comportamento de
"sem MMU" = mesma exceção central de sempre).

### D3 — `FPCR`/`FPSR` (pendência de B6.5.1) — incluir ou não?

**Decisão: NÃO incluir nesta task.** B6.5.1 registrou `FPCR`/`FPSR` como
pendência explícita dependente deste mecanismo (D2 daquela task). Embora o
mecanismo GERAL criado aqui sirva para eles, incluir `FPCR`/`FPSR` no
`Aarch64SystemRegisterId` desta task expandiria o escopo desta sub-task de
B6.6 (MMU) para cobrir uma pendência de B6.5 (FP) — **decisão: manter os dois
épicos com fronteiras limpas**; se o usuário priorizar fechar a pendência de
B6.5.1/B6.5.2 depois que este mecanismo existir, isso é uma task PRÓPRIA
pequena ("B6.5.5" ou similar, fora desta rodada de spec), não um item extra
aqui. Registrar isso explicitamente como o motivo de D3 não incluir FPCR/FPSR
apesar do mecanismo já estar pronto para eles.

## Objetivo

- `Ir64Op.SystemRegister` (D1) + `Aarch64SystemRegisterId` enum.
- Decoder: subgrupo `MRS`/`MSR (register)` dentro de
  `decodeBranchExceptionSystem` (já existe desde B6.1).
- `Aarch64SystemRegisterBus` (D2) + fiação em `Aarch64Core`.
- Executor: leitura escreve `Xt`/`Wt` (`Wt` zero-estende para os 64 bits
  altos — mesma regra geral de A64 já documentada nas Armadilhas do épico
  para operações `W`); escrita lê `Xt` (nunca `Wt` — `MSR` sempre lê o
  registrador de 64 bits inteiro, não há forma `W` de `MSR`, CONFERIR).

## Especificação

1. `Ir64Op.SystemRegister` (D1) em `ir64/Ir64Op.java`, `Kind` novo (próximo
   valor livre — auditar o estado real do arquivo no momento da
   implementação, ver nota em D1).
2. `Aarch64SystemRegisterId` enum novo, com os 9 registradores de Fatos de
   referência #2 (sem FPCR/FPSR, D3).
3. `Aarch64SystemRegisterBus` interface (D2) + `Aarch64Core.systemRegisters`
   (campo, default "nenhum bus instalado") + `setSystemRegisterBus`.
4. Decoder: novo `case`/sub-dispatch dentro de
   `decodeBranchExceptionSystem` (`Aarch64Decoder.java`, método já existe
   desde B6.1 — auditar a estrutura atual antes de adicionar) mapeando
   `op0:op1:CRn:CRm:op2` → `Aarch64SystemRegisterId` (D1), combinação não
   coberta → `UnsupportedOperationException` (documentado como "não coberto
   ainda", não UNDEFINED real).
5. Executor: `executeSystemRegister` em `Ir64BlockExecutor`, delega
   leitura/escrita ao bus instalado (D2); registrador não `handles()` por
   nenhum bus instalado → `UnsupportedOperationException` (mesmo padrão
   "sem hospedeiro" de `ArmCore`/`CoprocessorBus`).
6. Corpus: apêndice do mesmo `corpus.s`/`.bin`/`.objdump.txt`, cobrindo
   `MRS`/`MSR` para pelo menos 2-3 registradores da lista (ex. `SCTLR_EL1`,
   `TTBR0_EL1`, `VBAR_EL1`), montado com `aarch64-none-elf-as`/`objdump`
   reais do devkitA64 (o toolchain bare-metal JÁ monta instruções de
   sistema EL1 sem problema — não precisa de um kernel real para gerar o
   binário de teste, só o assembler).

## Não inclui

- Qualquer registrador fora da lista de Fatos de referência #2 (`FPCR`/
  `FPSR` incl. — D3).
- `MSR (immediate)` (Fatos de referência #3).
- Instalação real de um `Aarch64SystemRegisterBus` de MMU (isso é B6.6.3) —
  esta task só cria o mecanismo, testável com um bus FALSO/de teste
  (`InMemorySystemRegisterBus` ou similar, só para os testes desta task).
- Semântica de EL0/EL1 (privilégio, `AT PL0 MRS a um registrador EL1 deveria
  fazer X` — A64 real distingue acesso privilegiado, mas `Aarch64Core` ainda
  é EL0-only, B6.1; ver Armadilhas).

## Testes mínimos (`Aarch64SystemRegisterTest`)

1. `MRS`/`MSR` decodificados campo a campo contra o corpus real, para os
   registradores cobertos.
2. Combinação `op0:op1:CRn:CRm:op2` fora da lista →
   `UnsupportedOperationException`.
3. `MRS`/`MSR` sem bus instalado → `UnsupportedOperationException` (mesmo
   padrão "sem hospedeiro").
4. Com um bus de teste instalado: `MSR` seguido de `MRS` no mesmo
   registrador faz ida-e-volta.
5. `Wt` (forma 32-bit, se existir — CONFERIR se `MRS`/`MSR` realmente tem
   forma `W`, pode ser que só exista `X` para registrador de sistema; se
   confirmado que só existe `X`, remover esse teste e documentar por quê).
6. Regressão: suíte completa de B6.1-B6.5 sem mudança.

## Armadilhas

- **Não implementar semântica de privilégio EL0/EL1** — `Aarch64Core` ainda
  não distingue nível de exceção (B6.1, EL0-only); esta task só cria o
  mecanismo de leitura/escrita, sem checar se o "modo" atual teria permissão
  de acessar um registrador `_EL1` de verdade (isso pressupõe B6.6.4, que
  introduz o modelo mínimo de exceção EL0→EL1 — pendência explícita, não
  esquecimento).
- **Não expandir para `FPCR`/`FPSR`** mesmo sendo trivial com o mecanismo já
  pronto (D3) — fronteira de épico deliberada.
- **Não inventar `MSR (immediate)`** — encoding diferente, fora do escopo
  citado como necessário.
- **Citações de encoding marcadas "CONFERIR"** — nenhuma foi verificada
  contra código real nesta rodada de spec (diferente de B6.3.x, que cita
  QEMU literalmente); a implementação real precisa desse passo de
  verificação como primeiro item, não pular direto para código.
- **Pin de versão QEMU**: mesma ressalva de sempre.

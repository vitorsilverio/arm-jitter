# B9.8 — Hyp mode + Monitor mode 32-bit (ARMv7VE Security/Virtualization Extensions)

**Trilha:** B · **Repo:** arm-jitter (+ revalidação G5 nos consumidores) · **Status:** 📋 plano

Documento MESTRE do épico. Nasce do achado 6/"Não inclui" da `B9.7` (T32 Thumb-2, 2026-08-23):
`MRS_bank`/`MSR_bank`/`ERET`/`SMC`/`HVC` continuam `❌` na tabela de cobertura porque exigem Hyp mode
+ Monitor mode de 32 bits — registradores bancados (`SP_hyp`/`ELR_hyp`/`SPSR_hyp`, `SP_mon`/`LR_mon`/
`SPSR_mon`), 2 modos de CPU novos e vetores de exceção próprios. O usuário interveio em tempo real
naquela sessão para reverter uma tentativa de excluí-las como "Hyp mode não modelado" — mesma regra
de `feedback-nunca-excluir-instrucao-arm` que gerou a escada `B10` (EL2/EL3 do AArch64). Este épico
é o equivalente 32-bit de `B10` — mesmo motivo, mesma disciplina de fatiamento.

## Por que isso apareceu agora

`ArmCore`/`CpuMode` só modelam os 7 modos "clássicos" (`USER`/`FIQ`/`IRQ`/`SUPERVISOR`/`ABORT`/
`UNDEFINED`/`SYSTEM`) — nenhum bit de modo fora dessa lista é reconhecido; `CpuMode.fromBits`
lança `IllegalArgumentException` para qualquer valor não mapeado. Isso é, na prática, um bug
latente: um guest real que tentasse `CPS`/`MSR CPSR_c` para `0b11010` (Hyp) ou `0b10110` (Monitor)
travaria o emulador com uma exceção Java em vez de trocar de modo (mesmo que o emulador não tivesse
NENHUMA instrução de Hyp/Monitor implementada ainda — o simples bit de modo já quebra).

`HVC`/`SMC`/`MRS_bank`/`MSR_bank`/`ERET` nem chegam a ser decodificados hoje (T32 e A32 — conferido
nesta sessão, zero ocorrências fora dos comentários da B9.7 em `ArmDecoder`/`Thumb2MiscDecoder`).

## Meta

Modelar os 2 modos de CPU que faltam (`HYP`/`MONITOR`) com banking de registradores real, decodificar
e executar `HVC`/`SMC`/`MRS_bank`/`MSR_bank`/`ERET` corretamente — sem stub "Hyp/Monitor não
modelados" sobrando em lugar nenhum. **Escopo deliberadamente SIMPLIFICADO em relação ao hardware
real** (documentado em cada task, mesmo padrão da B10): nenhum consumidor deste projeto hoje precisa
de Secure/Non-secure world switching completo (`SCR.NS`, `NSACR`, dual view de memória) — essa
simplificação é sequenciamento, não exclusão (ver `tasks/README.md`, regra máxima): se um consumidor
real precisar de segurança completa no futuro, vira task nova na mesma escada.

## Fatos de referência (conferidos via QEMU real nesta sessão — `target/arm/tcg/{translate.c,a32.decode}`
do `qemu/qemu` em `master`, `curl` direto, não de memória)

- **`HVC`** (`ENABLE_ARCH_7`, ou seja ARMv7 base — não precisa de V7VE!): `.... 0001 0100 iiii iiii
  iiii 0111 iiii` (`imm16` = bits 19:8 + 3:0), `UNDEFINED` em modo USER. Entra em Hyp mode.
- **`SMC`** (`ENABLE_ARCH_6K`, ARMv6K — mais antigo que HVC): `---- 0001 0110 0000 0000 0000 0111
  iiii` (`imm4`, cond ≠ `1111` — tem `cond` normal, ao contrário do que a B9.7 presumia por
  analogia com o AArch64), `UNDEFINED` em modo USER. Entra em Monitor mode.
- **`ERET`** (exige `ARM_FEATURE_V7VE`): `---- 0001 0110 0000 0000 0000 0110 1110` — MESMO espaço de
  encoding que a B9.7 já mapeou como alias de `SUBS PC,LR,#0` (T32) — no A32 é um encoding PRÓPRIO,
  não um alias de `SUB`. `UNDEFINED` em modo USER. **Achado real**: em Hyp mode, `ERET` usa
  `ELR_hyp`, NÃO `LR` — diferente de todo resto do perfil A/R, onde a instrução de retorno sempre lê
  `LR` do modo ativo.
- **`MRS_bank`/`MSR_bank`** (tabela completa do `ARM DDI 0487` seção `F5.2.3`, replicada em
  `msr_banked_access_decode` do QEMU): campo `sysm` de 5 bits (`r:1` + `mode:4`, onde `r=1` seleciona
  SPSR do modo alvo, `r=0` seleciona registrador geral) mapeia para:
  - `sysm=0x0..0x6` (r=0): `r8_usr..r14_usr` (modo `USER`)
  - `sysm=0x8..0xe` (r=0): `r8_fiq..r14_fiq` (modo `FIQ`, já banked hoje)
  - `sysm=0x10/0x11` (r=0): `r14_irq`/`r13_irq`
  - `sysm=0x12/0x13` (r=0): `r14_svc`/`r13_svc`
  - `sysm=0x14/0x15` (r=0): `r14_abt`/`r13_abt`
  - `sysm=0x16/0x17` (r=0): `r14_und`/`r13_und`
  - `sysm=0x1c/0x1d` (r=0): `r14_mon`/`r13_mon` — **modo novo**
  - `sysm=0x1e/0x1f` (r=0): `ELR_hyp`/`r13_hyp` — **modo novo, `ELR_hyp` NÃO é `r14_hyp`** (Hyp mode
    não banca `LR` — usa o `LR_usr` compartilhado; `ELR_hyp` é um registrador à parte, sem índice
    0-15, "arbitrariamente" chamado de "regno 17" pelo próprio QEMU)
  - `sysm=0xe/0x10/0x12/0x14/0x16/0x1c/0x1e` (r=1): `SPSR_<fiq/irq/svc/abt/und/mon/hyp>`
- **Regras de acesso** (`msr_banked_access_decode`, simplificadas nesta escada — ver "Não inclui" de
  cada task): acesso a registradores de `MON` exige `current_el>=... EL3`/não-Secure; acesso a
  `r13_hyp`/`SPSR_hyp` só de Monitor mode; `ELR_hyp` também de Hyp mode. Este projeto não modela
  Secure/Non-secure — checagens completas ficam fora do escopo inicial (documentar, não excluir).

## Simplificações deliberadas desta escada (documentar em cada task que se aplicar, não excluir)

- **Sem Secure/Non-secure world completo** (`SCR.NS`, `NSACR`, dual view de memória) — nenhum
  consumidor real precisa hoje. Se aparecer, vira task nova nesta mesma escada (`B9.8.6`+).
- **Sem `HVBAR`/`MVBAR` reais** — vetores de exceção de Hyp/Monitor herdam o mesmo esquema de
  `highVectors`/vetor fixo que o resto do perfil A/R já usa, até que algum consumidor precise
  reprogramá-los.
- **Sem checagem de "current EL"/"secure state" nos acessos de `MRS_bank`/`MSR_bank`** (o QEMU real
  faz várias checagens de contexto antes de permitir acesso aos registradores Mon/Hyp) — este core
  não modela EL2/EL3 de 32 bits como conceito de privilégio separado do modo de CPU.

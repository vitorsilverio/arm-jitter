# B11.6 — segundo gate real de feature A64: `FEAT_WFxT` (`WFET`/`WFIT`)

**Trilha:** B · **Repo:** arm-jitter (+ revalidação G5 nos consumidores) · **Status:** ✅ fechada 2026-08-28
**Depende de:** B11.2 ✅ (fiação `Aarch64Architecture` no decoder), B11.3 ✅ (auditoria — confirmou
`WFET`/`WFIT` como `ARMv8.7-A`/`FEAT_WFxT`, já implementadas sem gate desde B8.3), B11.5 ✅ (`Aarch64Feature.WFXT`
já existe e já está mapeada em `Aarch64Architecture.ARMV8_7_A`)

## Contexto

`B11.4` provou o mecanismo de gate real (`FEAT_RDM`) para uma instrução que **nunca tinha sido
implementada antes** (zero risco de regressão: default continuava rejeitando). `B11.3`/`B11.5`
catalogaram 9 features cujas instruções **já decodificam incondicionalmente hoje** (implementadas
achando que eram baseline `ARMv8.0-A`, quando na verdade são extensões posteriores) — gateá-las é
diferente: o decoder DEFAULT (`ARMv8.0-A`) vai passar a REJEITAR algo que hoje aceita. Isso é o
comportamento CORRETO (um Cortex-A53 real, que é `ARMv8.0-A`, não tem `WFET`/`WFIT` — só ganhou
`FEAT_WFxT` em `ARMv8.7-A`), mas precisa de G5 real para confirmar que nenhum consumidor depende do
aceite incondicional de hoje.

Esta task ataca `FEAT_WFxT` (`WFET`/`WFIT`) por ser a mais isolada das 9: vive num subgrupo de
encoding próprio (`CRn=0b0001` dentro de `decodeSystemInstructionBarrier`,
`SYSTEM_INSTRUCTION_WAIT_TIMEOUT_CRN`), sem colisão com os demais subgrupos do mesmo método (hints
`CRn=0b0010`, barreiras `CRn=0b0011`, `MSR (immediate)`/flags `CRn=0b0100`) e sem reuso de
`Ir64Op`/`Kind` que outras instruções baseline também usem para fins diferentes — `WFIT` reaproveita
o MESMO `Ir64SystemInstructionOp.WFI` que `WFI` (baseline) já usa, mas por um CAMINHO de decode
inteiramente separado (CRn diferente), então gatear não risca `WFI` puro.

## Achados de investigação (nesta sessão)

- `decodeSystemInstructionBarrier` (`Aarch64Decoder.java:4205`) despacha por `crn`: o bloco
  `crn == SYSTEM_INSTRUCTION_WAIT_TIMEOUT_CRN` (linha 4230) é o único lugar que decodifica
  `WFET`→`NOP_HINT`/`WFIT`→`WFI`. Gatear esse bloco inteiro atrás de `architecture.has(WFXT)` é
  suficiente — sem tocar nos blocos de barreira/hint/flag vizinhos.
- Corpus real já existe em `src/test/resources/aarch64/corpus.bin` (devkitA64), confirmado em
  `corpus.objdump.txt` linhas 377-378: `0xd5031000` = `wfet x0` (offset `0x5b4`), `0xd5031021` =
  `wfit x1` (offset `0x5b8`) — não precisa gerar corpus novo.
- Testes existentes que quebram com o gate (checados nesta sessão):
  - `Aarch64DecoderCorpusTest#wfet`/`#wfit` (usam o `DECODER` default, esperam sucesso) — passam a
    esperar `UnsupportedOperationException`; a decodificação bem-sucedida migra para o teste novo
    dedicado.
  - `Aarch64DecoderCorpusTest#systemRegisterOp0ZeroIsWfet` (mesmo `DECODER` default, mesmo motivo)
    — mesma correção.
  - `Ir64BlockExecutorB83Test` (WFET/WFIT) **NÃO precisa mudar**: constrói
    `Ir64Op.SystemInstruction(NOP_HINT/WFI)` diretamente, sem passar pelo decoder — testa semântica
    de execução, não decode, e é ortogonal ao gate.

## Inclui

1. `Aarch64Decoder#decodeSystemInstructionBarrier`: o bloco `crn == SYSTEM_INSTRUCTION_WAIT_TIMEOUT_CRN`
   só decodifica `WFET`/`WFIT` quando `architecture.has(Aarch64Feature.WFXT)` — caso contrário,
   `throw unsupported(word, address)` (mesmo padrão de G8/B11.4: nunca silenciosamente confundir com
   outra instrução).
2. Atualizar `Aarch64DecoderCorpusTest#wfet`/`#wfit`/`#systemRegisterOp0ZeroIsWfet` para esperar
   `UnsupportedOperationException` no `DECODER` default (`ARMv8.0-A`).
3. Teste novo `Aarch64AdvSimdWfxtDecoderTest` (mesmo padrão de `Aarch64AdvSimdRdmDecoderTest`):
   decoder default rejeita `wfet x0`/`wfit x1`; decoder `Aarch64Architecture.ARMV8_7_A` decodifica
   os dois corretamente (`WFET`→`NOP_HINT`, `WFIT`→`WFI`), usando as MESMAS palavras do corpus real
   já existente (`0xd5031000`/`0xd5031021`).
4. `mvn -o test` verde + `mvn -o install`; G5 nos 5 consumidores (nenhum usa `ARMV8_7_A` — zero-diff
   esperado, prova só que nada quebra, já que `WFET`/`WFIT` não são emitidos por toolchains alvo de
   `ARMv8.0-A`/raspi3).

## Não inclui

- Qualquer outra das 8 features restantes (`LSE`/`PAN`/`SHA3`/`UAO`/`FLAG_MANIPULATION`/`DIT`/
  `FLAG_MANIPULATION_2`/`NMI`) — cada uma vira sua própria task `B11.x`, seguindo este mesmo padrão.
- Mudar `Aarch64Feature`/`Aarch64Architecture` (já existem desde B11.1/B11.5 — `WFXT` já mapeada em
  `ARMV8_7_A`).
- `docs/COBERTURA-ISA.md` (o medidor por versão já reflete `WFET`/`WFIT` corretamente desde B11.5 —
  gatear o decoder não muda o que o medidor já reportava para a coluna `ARMv8.7-A`+).

## Armadilhas

- Não tocar nos outros 3 blocos de `decodeSystemInstructionBarrier` (barreira `CRn=0b0011`, hint
  `CRn=0b0010`, flag/PSTATE `CRn=0b0100` via `decodeFlagOrPstateImmediate`) — só o bloco
  `SYSTEM_INSTRUCTION_WAIT_TIMEOUT_CRN`.
- `WFI` (baseline, `CRn=0b0010`/hint) e `WFIT` (`CRn=0b0001`/wait-timeout) são dois encodings
  DIFERENTES que produzem o MESMO `Ir64SystemInstructionOp.WFI` — gatear `WFIT` não pode, por
  engano, afetar o caminho de `WFI` puro (são `if`s separados, não compartilham código).

## Resultado (2026-08-28)

Implementado exatamente como especificado, sem desvio:

- `Aarch64Decoder#decodeSystemInstructionBarrier`: bloco `SYSTEM_INSTRUCTION_WAIT_TIMEOUT_CRN` agora
  começa com `if (!architecture.has(Aarch64Feature.WFXT)) throw unsupported(word, address);` antes do
  `switch` existente — os outros 3 blocos do método (barreira/hint/flag) intocados.
- `Aarch64DecoderCorpusTest#wfet`/`#wfit`/`#systemRegisterOp0ZeroIsWfet`: as 3 agora esperam
  `UnsupportedOperationException` no `DECODER` default, com comentário citando esta task.
- `Aarch64AdvSimdWfxtDecoderTest` novo (3 testes): default rejeita as 2 palavras do corpus real
  (`0xd5031000`/`0xd5031021`); `ARMV8_7_A` decodifica `wfet x0`→`NOP_HINT` e `wfit x1`→`WFI`
  corretamente.
- `mvn -o test` verde (core+truffle) + `mvn -o install`; G5 completo nos 5 consumidores
  (`gbaemu`/`ndsemu`/`virtual-arm-box`/`n3dsemu`/`armbox`, todos `BUILD SUCCESS`, zero-diff esperado
  e confirmado — nenhum usa `ARMV8_7_A`, e nenhum binário-alvo de `ARMv8.0-A` emite `WFET`/`WFIT`).
  Sem mudança em `docs/COBERTURA-ISA.md` (o medidor por versão, desde B11.5, já classificava
  `WFET`/`WFIT` como `ARMv8.7-A`; gatear o decoder não muda o que já era medido).
- **Próximo da escada B11, não pego automaticamente**: gatear qualquer uma das 8 features restantes
  (`LSE`/`PAN`/`SHA3`/`UAO`/`FLAG_MANIPULATION`/`DIT`/`FLAG_MANIPULATION_2`/`NMI`), mesmo padrão desta
  task. `LSE` (`CAS`/`CASP`) merece atenção extra antes de pegar: são instruções de atômico
  reais que ferramentas modernas (`musl`/`glibc` recentes) podem emitir mesmo em binários que alvejam
  `ARMv8.0-A` nominal (compilador com `-march` mais novo) — vale checar se algum consumidor real
  (`virtual-arm-box`) as exercita antes de gatear, ao contrário de `WFxT`, que não tem esse risco.

# B19.29 — A64: `FEAT_JSCVT` (`FJCVTZS`) — 1 linha

**Trilha:** B · **Repo:** arm-jitter (+ revalidação G5) · **Depende de:** B19.9
**Épico:** `b19-plano-a64-gap-remanescente.md` · **Status:** ⬜ spec pronta para execução

## Contexto

Degrau nomeado pela varredura de fechamento do épico B19 (`b19.9-a64-fechamento.md`, seção
"Varredura do que sobrou", 2026-09-10). `Aarch64Feature.JAVASCRIPT_CONVERT` **já existe** e **já
está declarada** em `Aarch64Architecture.ARMV8_3_A` — esta task decodifica a única linha medida.

A linha (`target/isa-decode/a64.decode`):

```
1473:FJCVTZS         0 0011110 01 111110 000000 ..... .....  @rr
```

Vizinha direta do grupo "Conversion between floating-point and integer (general register)" que
`Aarch64Decoder#decodeFpIntegerConvertOrGeneralRegisterMove` já trata (mesmo prefixo `0011110`, `rr`
de FP-para-inteiro) — confirmar o `opcode`/`type` exatos contra a linha 1473 e localizar o ponto
certo de inserção nesse método ou em `decodeFpDataProcessing`, o que a leitura do decoder mostrar
ser o correto.

### O que `FJCVTZS` faz, e por que não é um `FCVTZS` comum

`FJCVTZS Wd, Dn` converte um **double** para inteiro de 32 bits, truncando para zero
(round-toward-zero) — a MESMA direção de arredondamento de `FCVTZS`. A diferença real está em como
trata valores **fora do alcance de 32 bits**, `NaN` e `Inf`: em vez de SATURAR (comportamento padrão
de `FCVTZS`, que devolve `INT32_MAX`/`INT32_MIN` nesses casos), `FJCVTZS` implementa exatamente a
semântica `ToInt32` do ECMAScript — o resultado é definido bit a bit como os **32 bits baixos** da
conversão truncada de 64 bits (efetivamente `(int64) truncamento` seguido de descarte da metade
alta), com `NaN`/`Inf`/valores não representáveis produzindo `0`. **Conferir a fórmula exata**
(pseudocódigo `FJCvtZS` — o nome real no ARM DDI 0487 — ou o helper equivalente
`vfp_tosizd`/`do_fjcvtzs` do QEMU, se acessível) antes de implementar: não assumir que
`(int)(long) valor` do Java produz o mesmo resultado em todo caso de overflow sem checar
explicitamente contra a definição arquitetural (a semântica de `(int)(long)` cast de Java já trunca
para os 32 bits baixos de um `long`, o que pode coincidir — mas `NaN`/`Inf` em ponto flutuante para
`long` em Java tem sua própria regra de saturação que PRECISA ser conferida contra `ToInt32`
separadamente, não assumida igual).

**Achado a não esquecer**: `FJCVTZS` é a **única instrução de conversão FP→inteiro de todo o A64
que define a flag `Z` (zero) de NZCV** como efeito colateral — `Z = 1` se a conversão foi EXATA (o
double já representava um inteiro dentro do alcance de 32 bits, sem truncamento nem overflow), `Z =
0` em qualquer outro caso (fração descartada, overflow, `NaN`, `Inf`). As demais flags (`N`/`C`/`V`)
não são definidas por esta instrução — CONFIRMAR se ficam com valor indefinido/preservado ou são
zeradas, contra o manual.

**Leitura obrigatória**: `Ir64Op` de `Fp64IntegerConvert` (o record que `FCVTZS`/etc. já usam —
decidir se `FJCVTZS` reusa esse record com um novo modo, ou se precisa de um record próprio por
tocar flags), `PstateRegister` (como as flags NZCV são escritas por outras instruções — reusar a
mesma API, não inventar uma nova), `decodeFpIntegerConvertOrGeneralRegisterMove` (o vizinho de
decode).

## Objetivo

`FJCVTZS` decodifica e executa sob `ARMv8.3-A`+, gateada por `Aarch64Feature.JAVASCRIPT_CONVERT`,
produzindo o resultado `ToInt32`-compatível E escrevendo a flag `Z` corretamente, e é recusada
antes.

## Aceite

- `FJCVTZS` decodifica sob `ARMV8_3_A`+ e segue `unsupported` abaixo.
- **`Z=1`**: double que é um inteiro exato dentro do alcance de 32 bits (ex. `3.0`) — conversão
  exata, `Z` setada.
- **`Z=0`**: double com fração (ex. `3.5`) — trunca para `3`, mas `Z=0` porque a conversão não foi
  exata.
- **Overflow**: double fora do alcance de 32 bits (ex. `1e20`) — resultado = 32 bits baixos da
  conversão truncada de 64 bits (NÃO satura como `FCVTZS`), `Z=0`.
- **`NaN`/`Inf`**: resultado `0`, `Z=0`.
- **Comparação direta contra `FCVTZS`** com o MESMO operando de overflow — os dois produzem
  resultados DIFERENTES, prova de que a saturação não vazou para `FJCVTZS`.
- `docs/COBERTURA-ISA.md`: `FJCVTZS` vira `✅` de `ARMv8.3-A` em diante.
- `mvn -o test` verde + G5 verde nos 5 consumidores.

## Armadilhas

1. **Não é `FCVTZS` com um nome diferente.** O tratamento de overflow/`NaN`/`Inf` é
   FUNDAMENTALMENTE diferente (bits truncados vs. saturação) — copiar o padrão de `FCVTZS` sem
   checar essa diferença produz uma instrução plausível e errada.
2. **A flag `Z` é o detalhe mais fácil de esquecer.** Nenhuma outra conversão FP→int neste projeto
   toca flags; um executor que segue o padrão comum (nenhum efeito em NZCV) vai silenciosamente
   deixar `Z` errado, e nenhum teste que só confira o valor convertido vai pegar isso.
3. **`(int)(long)` de Java pode não bater com `ToInt32` para `NaN`/`Inf`** — Java satura
   double→long para esses casos (`Double.NaN → 0L` de fato, mas `Infinity → Long.MAX_VALUE`, que
   truncado para 32 bits baixos NÃO é `0`) — conferir cada caso especial contra a definição real, não
   assumir que o cast de Java já faz o trabalho certo.

## Não fazer

- Não implementar como alias de `FCVTZS`.
- Não deixar a flag `Z` sem efeito.
- Não adicionar caso nativo em `Ir64NativePolicy`.

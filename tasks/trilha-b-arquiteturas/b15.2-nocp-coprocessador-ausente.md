# B15.2 — Perfil M: `NOCP`/`NOCP_8_1` (exceção de coprocessador ausente) — 2 linhas

**Trilha:** B · **Repo:** arm-jitter (+ revalidação G5) · **Depende de:** B15.1 (✅ 2026-09-12)
**Épico:** `b15-plano-armv8m.md` · **Status:** ⬜ (spec escrita 2026-09-13, ainda não executada)

## Contexto

`b15-plano-armv8m.md` mede `m-nocp.decode` (11 encodings) como a única linha da tabela inteira a
**0%** num preset REAL (`v6-M`/`v7-M`), e descreve a escada B15.2-B15.5 para fechá-la. Esta task é
o primeiro degrau: só `NOCP`/`NOCP_8_1` (2 das 11 células) — as outras 9 (`VLDR_sysreg`/
`VSTR_sysreg`/`VMSR_VMRS`/`VLLDM_VLSTM`/`VSCCLRM`) ficam para **B15.3**/**B15.5**, que dependem
desta.

### O encoding real (`target/isa-decode/m-nocp.decode`, medido nesta rodada de spec)

```
&nocp cp

{
  # Special cases (VLLDM/VLSTM/VSCCLRM/VMSR_VMRS/VLDR_sysreg/VSTR_sysreg) — fora desta task,
  # ver B15.3/B15.5. Todas vivem no MESMO bloco `{...}` do QEMU, competindo pelo MESMO espaço de
  # bits que NOCP — o bloco decodifica primeiro as formas específicas, e só cai em NOCP quando
  # nenhuma bate.

  NOCP         111- 1110 ---- ---- ---- cp:4 ---- ---- &nocp
  NOCP         111- 110- ---- ---- ---- cp:4 ---- ---- &nocp
  # A partir de v8.1M, esta faixa também gera NOCP:
  NOCP_8_1     111- 1111 ---- ---- ---- ---- ---- ---- &nocp cp=10
}
```

Lidos como 8 nibbles de `raw` = halfword-alto:halfword-baixo combinados (mesma convenção de
{@link Thumb2MiscDecoder}, `hi = raw >>> 16`):

- **`NOCP` (forma 1)**: `bits[31:28] ∈ {1110,1111}`, `bits[27:24] = 1110` — ou seja
  `hi ∈ {0xEE00..0xEEFF, 0xFE00..0xFEFF}` com `cp` em `bits[11:8]`. Este É exatamente o espaço
  "coprocessor register transfer" (`MCR`/`MRC`, `hw1 = 1110 1110`) que
  `Thumb2CoprocessorDecoder`/`CoprocessorDecoder` **já reivindicam incondicionalmente** em
  `ARMV7M`/`ARMV7M_PURE`/`ARMV7EM` (ver Armadilha 1 — é a raiz de por que a célula mede 0% hoje).
- **`NOCP` (forma 2)**: `bits[31:28] ∈ {1110,1111}`, `bits[27:25] = 110` (`bits[24]` livre) — o
  espaço "extension register load/store"/coprocessor de 64 bits (`hi ∈ 0xEC.._0xEF..`,
  `0xFC.._0xFF..`), o mesmo espaço `bits[27:24] ∈ {1100,1101}` que `Thumb2VfpDecoder`/`VfpDecoder`
  reivindicariam — **mas nenhum preset de perfil M anexa `Thumb2VfpDecoder` hoje** (ver Javadoc de
  `ArmArchitecture.ARMV7M`: "**Sem VFP** ... fora do escopo"), então esta faixa cai inteiramente
  sem decoder — `null` → `UNIMPLEMENTED` (G8 já satisfeito por omissão, não por decisão).
- **`NOCP_8_1`**: `bits[31:28] ∈ {1110,1111}`, `bits[27:24] = 1111` fixo, sem campo `cp` (a spec
  original do QEMU fixa `cp=10` — a partir de ARMv8.1-M, TODO o espaço `1111` vira NOCP, não só
  coprocessador 10/11).

### Por que só 2 células e não as 11

As outras 9 linhas de `m-nocp.decode` (`VLLDM_VLSTM`/`VSCCLRM`/`VMSR_VMRS`/`VLDR_sysreg`/
`VSTR_sysreg`) são formas ESPECÍFICAS que, na árvore real do QEMU, são checadas **antes** de cair
no `NOCP` genérico (mesmo bloco `{...}`, prioridade de padrão mais específico primeiro). Elas
manipulam registradores de contexto FP (`FPCXT_NS`/`FPCCR`) que `MProfileExceptionModel` ainda não
tem — ficam para B15.3 (`VMSR_VMRS`+`VLDR_sysreg`/`VSTR_sysreg`) e B15.5 (`VLLDM_VLSTM`+`VSCCLRM`),
ambas dependentes desta (a ordem de prioridade de decode importa: o gate de "é uma das formas
específicas?" tem que vir antes do `NOCP` genérico que esta task instala).

## Objetivo

`NOCP`/`NOCP_8_1` decodificam sob qualquer preset com `ArmFeature#M_PROFILE` e, ao executar,
levantam `MProfileException#USAGE_FAULT` com o bit `NOCP` do `UFSR` (parte do `CFSR`, offset
`0xED28` do SCS) setado — o mecanismo real pelo qual firmware descobre "este Cortex-M não tem
FPU" tentando uma instrução VFP e inspecionando o fault status no handler. `docs/COBERTURA-ISA.md`:
as 2 células (`v6-M`/`v7-M`, coluna `m-nocp.decode`) saem de `❌`/0% para `✅`.

## Inclui

1. **Registrador `CPACR`** (Coprocessor Access Control Register, offset `0xED88` do SCS,
   `MProfileSystemControl`) — armazenamento simples (leitura/escrita de 32 bits, sem gate
   funcional nesta task: nenhum FPU existe para `CP10`/`CP11` habilitarem/desabilitarem de
   verdade). Existe para (a) software real que sonda `CPACR` antes de tentar VFP não travar por
   `CPACR` não existir (lê 0 hoje via `MProfileSystemControl.read32` default — **confirmar se already
   correto** antes de adicionar, ver Armadilha 4) e (b) ficar pronto para B15.5 (`VLLDM`/`VSCCLRM`
   preservam estado FP condicionalmente a `CPACR`, arquitetura real).
2. **`UFSR`/`CFSR`** (Configurable Fault Status Register, offset `0xED28`; `UFSR` é o byte alto,
   `bits[31:16]`; bit `NOCP` = `bit[19]`, ou seja `bit[3]` do `UFSR` — ARMv7-M ARM B3.2.15) —
   armazenamento simples com o bit `NOCP` setado por esta task quando `NOCP`/`NOCP_8_1` entra em
   `USAGE_FAULT`. Escrita de software limpa bits por `write-1-to-clear` (semântica real do
   `CFSR` — **confirmar contra o manual antes de implementar**, não assumir RW simples).
3. **Decode de `NOCP`/`NOCP_8_1`** — nova extensão de decoder Thumb-2 (ou método dentro de um
   decoder já anexado ao perfil M, ver Armadilha 1) que reconhece as 2 formas acima e produz um
   `InstructionKind` novo (ex. `InstructionKind.NOCP`), condicionado a `ArmFeature#M_PROFILE`.
4. **Executor**: `NOCP`/`NOCP_8_1` chamam `MProfileExceptionModel`, que seta o bit `UFSR.NOCP` e
   entra em `MProfileException.USAGE_FAULT` (reusa `enterException`, ver Armadilha 2 sobre como
   plugar isso no `ArmException` genérico ou por um caminho dedicado).
5. Testes (ver Aceite).

## Não inclui

- **`VLDR_sysreg`/`VSTR_sysreg`/`VMSR_VMRS`** — B15.3.
- **`VLLDM_VLSTM`/`VSCCLRM`** — B15.5.
- **`NSACR`** (Non-secure Access Control Register) — só existe com a Security Extension
  (ARMv8-M), que não existe ainda neste projeto (B15.4). O plano do épico (`b15-plano-armv8m.md`,
  linha da escada B15.2) cita "CPACR/NSACR" junto, mas **NSACR é prematuro aqui** — `ARMV7M`/
  `ARMV7M_PURE` (os únicos presets afetados por esta task) não têm estado seguro/não-seguro. Se
  esta leitura estiver errada, PARE e confirme com o usuário antes de implementar NSACR.
- **Qualquer FPU real** (VFP para perfil M) — fora de escopo do projeto inteiro por ora
  (ver Javadoc de `ArmArchitecture.ARMV7M`). `CPACR` armazena bits, não gateia nada de verdade.
- **Emissão nativa/Truffle** — decode + interpretado apenas, mesmo padrão do resto da trilha B.

  `WebSearch` se não houver cópia local, mesma disciplina de medição das specs B19.x.

### Registro de `UFSR.NOCP`

Bit 19 do `CFSR` (bit 3 do `UFSR`, que ocupa `bits[31:16]` do `CFSR`). Ao entrar em `USAGE_FAULT`
por `NOCP`/`NOCP_8_1`, setar esse bit ANTES de empilhar o frame de exceção (a arquitetura real seta
o fault status como parte da detecção, não do handler). Escrita de software no `CFSR` real é
write-1-to-clear — confirmar contra o manual antes de implementar (Armadilha 3).

## Armadilhas

1. **Achado central desta spec, a confirmar na execução**: `Thumb2CoprocessorDecoder` (MCR/MRC) é
   anexado INCONDICIONALMENTE a `ARMV7M`/`ARMV7M_PURE`/`ARMV7EM` hoje (`ArmArchitecture.java`
   ~linha 375/401), e seu espaço de bits (`hi = 1110 1110`) é o MESMO da forma 1 de `NOCP`. Se o
   perfil M real não suporta `MCR`/`MRC` de coprocessador genérico (só o espaço 10/11 reservado
   para FP, tudo o mais é sempre NOCP), esse decoder está **incorretamente anexado** desde que os
   presets M-profile existem — confirmar contra o ARMv7-M ARM antes de decidir se remove ou se
   torna condicional. Não assumir sem medir: pode ser que `Thumb2CoprocessorDecoder` nunca tenha
   sido exercitado por nenhum teste M-profile real (checar `grep` por testes que usam `MCR`/`MRC`
   sob `ARMV7M`).
2. **`ArmException` é compartilhado entre perfil A e M** (`ExceptionModel` interface,
   `AProfileExceptionModel`/`MProfileExceptionModel`). Adicionar `ArmException.NOCP` exige decidir
   o que `AProfileExceptionModel.enterException` faz com ele (nunca deveria ser chamado, mas o
   `switch`/`exceptionMode`/`exceptionVector` de lá são exaustivos sobre o enum — verificar se
   compila só com um `default`/`throw` ou se precisa de um `case` explícito). Alternativa: não usar
   `ArmException` para isto, chamar `MProfileExceptionModel` diretamente do executor (mesmo padrão
   de método dedicado que `IrSystemExecutor` já usa para outros casos M-profile-only, se algum
   existir — verificar).
3. **`CFSR`/`UFSR` é write-1-to-clear no hardware real**, não RW simples — implementar como
   `shcsr`/`systCsr` (RW cru) seria uma semântica errada silenciosa (G8 aplicado a registrador
   memory-mapped, não só a instrução). Confirmar contra o manual ANTES de escrever
   `MProfileSystemControl.write32` para este offset.
4. **Antes de adicionar `CPACR_OFFSET`**, confirmar que `MProfileSystemControl.read32` hoje
   devolve `0` para offsets desconhecidos (visto no código: `return 0;` no fim de `read32`) — ou
   seja, ler `CPACR` sem esta task JÁ devolve 0 (coerente com "nenhum coprocessor habilitado"), e a
   única razão real para adicionar o offset explícito é preparar o terreno para B15.5 gravar/ler
   um valor não-zero depois. Se a sessão de execução decidir que armazenamento explícito não é
   necessário ainda (0 sempre é suficiente até B15.5 precisar de verdade), documentar a decisão de
   NÃO adicionar `CPACR` nesta task em vez de forçar o escopo.
5. **Não confundir com `NSACR`** — ver "Não inclui".
6. **G3**: `ARMV6M`/`ARMV7M`/`ARMV7M_PURE` não podem regredir nenhum teste existente. Se a
   Armadilha 1 remover/alterar `Thumb2CoprocessorDecoder` desses presets, rodar a suíte completa
   (não só os testes novos) antes de commitar.

## Não fazer

- Não implementar `VLDR_sysreg`/`VSTR_sysreg`/`VMSR_VMRS` (B15.3) nem `VLLDM_VLSTM`/`VSCCLRM`
  (B15.5) — mesmo bloco de decode do QEMU, mas células diferentes desta task.
- Não implementar `NSACR`/Security Extension (B15.4).
- Não adicionar nenhuma FPU real.
- Não decidir sozinho, sem medir, se `Thumb2CoprocessorDecoder` deve sair dos presets M-profile —

  existente rodando MCR/MRC sob perfil M, ou ausência confirmada) antes de agir.

## Resultado

**FECHADA 2026-09-13.** Armadilha 1 confirmada por medição (não suposição): `grep` em
`core/src/test` mostrou que só `Thumb2CoprocessorDecoderTest` exercita `MCR`/`MRC` Thumb-2, e
apenas sob `ARMV6K_THUMB2` (A-profile) — nenhum teste pré-existente rodava `MCR`/`MRC` sob
`ARMV7M`/`ARMV7M_PURE`/`ARMV6M`. Confirmado também, lendo `CoprocessorRegisterDecoder`, que o
espaço que `Thumb2CoprocessorDecoder` reivindicava (`bits[27:24]=1110`, bit4=1) é um SUBCONJUNTO
estrito da forma 1 de `NOCP` (que cobre bit4 livre e os dois nibbles altos `0xEE`/`0xFE`, não só
`0xEE`) — decisão: `Thumb2NocpDecoder` **substitui** `Thumb2CoprocessorDecoder` nos 3 presets
M-profile (não coexiste), e é **acrescentado** a `ARMV6M` (que nunca teve `Thumb2CoprocessorDecoder`
mas `docs/COBERTURA-ISA.md`/`IsaCoverageReport` já medem `m-nocp.decode` como aplicável a v6-M via
`ArmFeature#M_PROFILE` cru, sem distinguir versão — mesma convenção que
`MProfileExceptionModel#enterException(ArmCore, ArmException)` já usa para UNDEFINED→USAGE_FAULT).

**Achado real, pego ANTES de commitar** (medindo o delta de `docs/COBERTURA-ISA.md`, mesma
disciplina da B19.16/B19.14): a primeira versão do decoder tratava a forma 2 (`bits[27:25]=110`)
genericamente, e isso fazia as células `VLLDM_VLSTM`/`VSCCLRM` (B15.5, ainda não implementadas)
saltarem de `❌` para `✅` por engano — o probe de `IsaCoverageReport` usa os bits FIXOS do encoding
real de cada instrução, e o padrão INTEIRO de `VLLDM_VLSTM`/`VSCCLRM` cabe dentro da máscara
genérica da forma 2 (top byte `0xEC` fixo). Corrigido com duas máscaras de exclusão específicas
(`VLLDM_VLSTM_MASK`/`VSCCLRM_MASK`, computadas bit a bit a partir do `m-nocp.decode` real) que
devolvem `null` (mantém `❌` honesto) para esses dois padrões — G8 aplicado ao contrário do usual:
não é a instrução nova que precisa recusar o que não reconhece, é o catch-all genérico que precisa
NÃO engolir instruções mais específicas que ainda não existem. `VMSR_VMRS`/`VLDR_sysreg`/
`VSTR_sysreg` (B15.3) não precisaram de exclusão — vivem no espaço da forma 1, mas seus 4 bits
altos livres (`----`) usam `0` no probe de cobertura (não `111-`), então não colidem com o gate
`TOP_THREE_BITS`; a colisão real (para software real usando esses encodings com o nibble alto
`1110`/`1111` de verdade) continua existindo e é o motivo já documentado de por que a B15.3 precisa
plugar seu decoder ANTES do `Thumb2NocpDecoder` na lista.

`CPACR` (Armadilha 4): decisão de **não adicionar armazenamento explícito** — `MProfileSystemControl
.read32` já devolve `0` para offsets desconhecidos (coerente com "nenhum coprocessador habilitado"),
documentado no Javadoc da classe; fica para B15.5 quando `VLLDM`/`VSCCLRM` precisarem de um valor
gravável de verdade. `CFSR`/`UFSR` ganhou armazenamento real em `MProfileExceptionModel` (mesmo
padrão de `basepri`/`faultmask`), com semântica write-1-to-clear confirmada contra o ARMv7-M ARM
B3.2.15 e testada explicitamente (`NocpTest#cfsrIsWriteOneToClearThroughSystemControl`).

Mecanismo de exceção: `IrSystemExecutor#executeNocp` chama `MProfileExceptionModel` DIRETO (seta
`UFSR.NOCP`, entra em `USAGE_FAULT`), sem passar por `ArmException` genérico — mesma alternativa que
a Armadilha 2 oferecia, evitando adicionar um `case` sem sentido em `AProfileExceptionModel` (perfil
A/R nunca produz `NOCP`). `IrOp.Nocp`/`InstructionKind.NOCP` novos (`Kind` 106); `StandardIrBlockLifter
.isTerminal` precisou do novo kind (mesma classe de cuidado que `Branch64`/`Hvc`/`Breakpoint` já
tratam — sem isso o lifter continuaria decodificando depois de um `NOCP` no MESMO bloco JIT). Sem
emissão nativa (`AsmNativePolicy` devolve `false`, mesmo padrão de NEON) nem nó Truffle (`Kind` 106
entra na lista "descoberta" de `TruffleCodeEmitterSupportsCoherenceTest`, 40→41) — "Não inclui"
explícito da task.

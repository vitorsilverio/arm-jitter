# B3.1 — Inteiro ARMv7, encodings ARM (MOVW/MOVT, MLS, bitfield, RBIT, SDIV/UDIV, barreiras)

**Trilha:** B (épico B3) · **Depende de:** B2.6 · **Repo:** arm-jitter

## Contexto

O lado ARM (32 bits clássico) ainda para no ARMv6K. Este grupo é o restante inteiro
que o ARMv7-A adiciona e que aparece em QUALQUER binário gcc moderno (`movw`/`movt`
para constantes de 32 bits, `ubfx`/`bfi` para structs/bitfields, `sdiv`/`udiv` em
`-O2`). Espelha o padrão de B1.2–B1.5: features novas + `DecoderExtension` + IR +
interpretador; **sem ASM nativo nesta task** (`AsmNativePolicy` rejeita as ops novas;
a emissão nativa entra junto com B3.6 ou numa sub própria se ficar grande — decisão:
entra na B3.6, já anotado lá).

## Inclui

Features novas em `ArmFeature` (com javadoc `///` em português, G7):

| Feature | Instruções gateadas |
|---------|--------------------|
| `MOVW_MOVT` | `MOVW`, `MOVT` (encoding ARM; o Thumb-2 de B2.2 passa a consultar a MESMA feature — hoje usa só `THUMB2`; ajustar `Thumb2DataProcessingDecoder` para exigir as duas é parte desta task) |
| `MLS_MULTIPLY` | `MLS` |
| `BIT_FIELD` | `SBFX`, `UBFX`, `BFI`, `BFC` |
| `BIT_REVERSE` | `RBIT` |
| `DIVIDE` | `SDIV`, `UDIV` |

`DMB`/`DSB`/`ISB` encoding ARM: reusam `ArmFeature.MEMORY_BARRIERS` e `IrOp.MemoryBarrier`
(B2.5) — só falta o decode ARM.

## Não inclui

- Encodings Thumb-2 dos mesmos grupos (B3.2).
- ASM nativo (B3.6). `AsmNativePolicy` deve rejeitar explicitamente os `IrOp` novos.
- Nenhum preset novo ainda (B3.7). Para testar, use `ArmArchitecture.extending(ARMV6K,
  "test", ...)` por teste, como B1.x fez.

## Especificação

### 1. Decoder: `ArmV7MediaDecoder implements DecoderExtension`

Novo arquivo em `core/src/main/java/dev/vitorsilverio/armjitter/decoder/`, espelhando
`CoprocessorDecoder` (mesmo pacote, mesma forma). Plugado via
`ArmArchitecture.withDecoderExtensions` **apenas nos testes** desta task (o preset
real chega em B3.7).

Encodings (ARM DDI 0406C; oráculo de referência: QEMU `target/arm/tcg/a32.decode` —
reconferir cada padrão lá antes de implementar, mesmo protocolo de B2.x):

| Instr | Padrão (bits 27:0, `x`=campo) | Campos |
|-------|-------------------------------|--------|
| `MOVW` | `0011 0000 imm4 Rd imm12` | imm16 = imm4:imm12 |
| `MOVT` | `0011 0100 imm4 Rd imm12` | idem |
| `MLS`  | `0000 0110 Rd Ra Rm 1001 Rn` | Rd = Ra − Rn×Rm |
| `SBFX` | `0111 101 widthm1 Rd lsb 101 Rn` | width = widthm1+1 |
| `UBFX` | `0111 111 widthm1 Rd lsb 101 Rn` | idem |
| `BFI`  | `0111 110 msb Rd lsb 001 Rn` | width = msb−lsb+1; `Rn=1111` → `BFC` |
| `RBIT` | `0110 1111 1111 Rd 1111 0011 Rm` | |
| `SDIV` | `0111 0001 Rd 1111 Rm 0001 Rn` | Rd = Rn/Rm |
| `UDIV` | `0111 0011 Rd 1111 Rm 0001 Rn` | idem |
| `DMB`/`DSB`/`ISB` | espaço incondicional `1111 0101 0111 1111 1111 0000 01xx option` | `option` ignorado (NOP observável) |

UNPREDICTABLE (Rd/Rn/Rm = PC nas formas acima, `lsb+width > 32`) → UNDEFINED, a
convenção do projeto.

**Passo 0 obrigatório (antes de escrever o decoder):** teste-sonda que decodifica
cada `raw` da tabela no preset `ARMV6K` puro e asserta `InstructionKind.UNIMPLEMENTED`
(ou UNDEFINED) — prova de que o `ArmDecoder` base NÃO reivindica esses espaços hoje e
de que a extensão será consultada. Se algum raw decodificar como outra coisa (ex.
espaço MSR imediato vizinho de MOVW), PARE e registre no PR qual — nesse caso o
carve-out no `ArmDecoder` base precisa ser gateado por feature e isso deve ser feito
espelhando como o decoder base já gateia `BLX`/`CLZ` por `ArmFeature`.

### 2. IR nova (`ir/IrOp.java` + `IrOpCode`/executores)

| Instr | IR |
|-------|----|
| `MOVW` | `IrOp.Alu` MOV com imediato (nada novo) |
| `MOVT` | `IrOp.MoveTop` (existe desde B2.2 — reusar) |
| `MLS` | `IrOp.Multiply` ganha componente novo `boolean subtractFromAccumulator` (default `false`; atualizar TODOS os call sites — mudança mecânica; o executor faz `Ra − Rn×Rm` quando true) |
| `SBFX`/`UBFX` | novo `record BitFieldExtract(int dst, int src, int lsb, int width, boolean signedExtract, Condition condition)` |
| `BFI`/`BFC` | novo `record BitFieldInsert(int dst, int src, int lsb, int width, Condition condition)` — `src == -1` significa BFC (insere zeros) |
| `RBIT` | novo `record BitReverse(int dst, int src, Condition condition)` — executor usa `Integer.reverse` |
| `SDIV`/`UDIV` | novo `record Divide(int dst, int dividend, int divisor, boolean signedDivide, Condition condition)` |
| `DMB`/`DSB`/`ISB` | `IrOp.MemoryBarrier` (existe) |

Siga a forma exata dos records vizinhos em `IrOp.java` (campos `Condition`, javadoc
`///`). Semântica de `Divide` (A8.8.165): divisão por zero → resultado **0** (sem
exceção); `Integer.MIN_VALUE / -1` → `Integer.MIN_VALUE` (o overflow trunca — em Java
esse caso já devolve MIN_VALUE sem trap para `int`, confirmar com teste). Nenhuma
dessas ops toca flags.

Executores: `BitFieldExtract`/`BitFieldInsert`/`BitReverse`/`Divide` entram em
`IrAluExecutor` (são ALU puras); o dispatch em `IrBlockExecutor#executeOp` ganha os
casos novos. `DeadCodeEliminationPass`/`ConstantFoldPass`/`FlagMergePass`: adicionar
os records novos como "define dst, não toca flags" seguindo o que B1.3 fez para
`Sel`/`Saturate` (procurar por `Sel` nesses 3 arquivos e espelhar).

### 3. `AsmNativePolicy`

Rejeitar `BitFieldExtract`, `BitFieldInsert`, `BitReverse`, `Divide` e `Multiply` com
`subtractFromAccumulator=true` (fallback PER_OP até B3.6) — espelhar como a política
rejeitava as ops B1.x antes de B1.6.

## Testes mínimos (todos em um `ArmV7MediaDecoderTest` novo)

1. Sonda do Passo 0 (um teste por linha da tabela).
2. Por instrução: vetor concreto de entrada→saída (ex. `UBFX r0, r1, #4, #8` com
   `r1=0xABCD1234` → `r0=0x23`; `SDIV` com −7/2 → −3 (trunca para zero);
   `SDIV x/0` → 0; `MIN_VALUE/−1` → MIN_VALUE; `RBIT 0x80000001` → `0x80000001`;
   `MLS 10−3×4` → −2; `BFC` limpa o campo; `BFI` insere sem tocar o resto;
   `MOVW+MOVT` compõem 32 bits, MOVT preserva os 16 baixos).
3. Gate: cada instrução em preset SEM a feature → UNDEFINED.
4. Equivalência PER_OP: bloco misto com as ops novas, interpretado × ASM
   (`BlockEquivalenceHarness`, `perOpFallbackOpCount() > 0`), mesmo harness de B1.2.
5. G2: nada disso decodifica em `ARMV4T`.

## Armadilhas

- O espaço `0111 1xxx ... 1xx1` ARM é "media" e vizinho de UNDEFINED permanente
  (`0x07F000F0` é o UDF canônico) — não reivindique além dos padrões exatos da tabela.
- `MOVW` NÃO seta flags e NÃO tem forma com S — se o bit S (20) estiver ligado o
  encoding é outra coisa (MSR/TST); o padrão da tabela já exige S=0.
- G4: condição falsa ainda consome `Cycle`/`Fetch` (as ops novas são condicionais no
  encoding ARM — carregue `Condition` nos records, como TODOS os vizinhos fazem).
- `Thumb2DataProcessingDecoder` (MOVW/MOVT Thumb) passar a exigir `MOVW_MOVT`: cuidado
  para não quebrar `ARMV6K_THUMB2` — o preset de B2.6 NÃO tem `MOVW_MOVT`; adicionar
  a feature ao preset `ARMV6K_THUMB2` faz parte desta task (MOVW/MOVT é ARMv6T2, o
  preset já prometia isso; registrar no javadoc).

## Resultado

✅ 2026-07-17 (`ArmFeature.MOVW_MOVT`/`MLS_MULTIPLY`/`BIT_FIELD`/`BIT_REVERSE`/`DIVIDE` novos; `IrOp.BitFieldExtract`/`BitFieldInsert`/`BitReverse`/`Divide` + `Multiply.subtractFromAccumulator` [MLS], executados em `IrAluExecutor`, DCE atualizado [`ConstantFoldPass`/`FlagMergePass` não precisaram — só tratam `IrOp.Alu`, e nenhuma destas 4 ops novas é uma]; `AsmNativePolicy` rejeita as 4 [interpretado até B3.6, mesmo padrão B1.x pré-B1.6]. **Desvio real do plano original da spec, descoberto pelo Passo 0 obrigatório**: a task previa uma `ArmV7MediaDecoder implements DecoderExtension` plugada só nos testes — mas TODAS as 8 instruções (`MOVW`/`MOVT`/`MLS`/`SBFX`/`UBFX`/`BFI`/`BFC`/`RBIT`/`SDIV`/`UDIV`/`DMB`/`DSB`/`ISB`) colidem com dispatches genéricos do `ArmDecoder` que retornam ANTES de alcançar o loop de extensões no fim de `decode()`: `MOVW`/`MOVT` caem no dispatch ALU genérico [opcode 0x8/0xA = TST/CMP com S=0]; `MLS` cai no bloco de halfword-transfer [`raw&0x0E000090==0x00000090`]; `SBFX`/`UBFX`/`BFI`/`BFC`/`RBIT`/`SDIV`/`UDIV` [todos com bits27:26=01] caem no bloco de LDR/STR imediato, cujo ramo interno `!immediateOffset && bit4` já devolve UNIMPLEMENTED para esse padrão [mesmo espaço "Media instructions" do ARM DDI 0406C A5.4, adjacente ao de LDR/STR]; `DMB`/`DSB`/`ISB` [espaço incondicional cond=1111] também caem nesse mesmo bloco de LDR/STR e decodificavam como um `LOAD` incorreto. A spec já prescrevia exatamente este contingente ["PARE e registre... o carve-out no ArmDecoder base precisa ser gateado por feature, espelhando BLX/CLZ"] — todas as 13 instruções da tabela viraram carve-outs diretos em `ArmDecoder` [mesmo padrão de `BLX`/`CLZ`/`UMAAL`/exclusivos], posicionados antes dos blocos que as engoliriam; nenhuma classe `ArmV7MediaDecoder`/`DecoderExtension` foi criada. `Thumb2DataProcessingDecoder#decodeMoveWide` (B2.2) passou a exigir `MOVW_MOVT` além de `THUMB2` (item da spec); `ARMV6K_THUMB2_FEATURES` ganhou `MOVW_MOVT` para não regredir (teste pré-existente `Thumb2DataProcessingDecoderTest` ajustado). 17 testes novos (`ArmV7MediaDecoderTest`): sonda do Passo 0 [as 13 formas UNIMPLEMENTED sob `ARMV6K` puro — provou o desvio acima], vetores concretos [MOVW+MOVT compõem 32 bits; MLS 10−3×4=−2; UBFX 0xABCD1234 lsb4/width8→0x23; SBFX com sinal vs UBFX sem sinal no mesmo campo; BFC limpa/BFI insere sem tocar o resto; RBIT 0x80000001→0x80000001 palíndromo; SDIV trunca para zero, /0→0, MIN_VALUE/−1→MIN_VALUE sem exceção; UDIV como não-assinado; MOVW/MOVT com Rd=PC→UNDEFINED; DMB/DSB/ISB NOP observável], gate ausente→UNIMPLEMENTED, G2 [nada decodifica em ARMV4T/ARMV5TE], e equivalência interpretado×ASM(PER_OP) com `perOpFallbackOpCount()>0` [sem emissão nativa ainda]. Suíte arm-jitter 698 core [682+16, +1 ajustado] + 13 truffle verdes (`mvn -o test`, JBR 25). **G5 validado**: `mvn -o install` seguido de `mvn -o test` nos dois consumidores — gbaemu verde (`JitInterpreterDivergenceTest` sem divergência em 20M blocos) + ndsemu verde — zero regressão)

# B8.16 — A64 `NZCV`/`DAIF` (via `MRS`/`MSR`) + `CNTVCT_EL0`/timer virtual

**Trilha:** B · **Depende de:** B6.6.7 ✅ (PSTATE.I/timer genérico) · **Repo:** arm-jitter

## Contexto

Continuação da varredura sistemática de registradores de sistema A64 (B8.14/B8.15). Dois grupos
fechados juntos por viverem no mesmo `CRn`/vizinhança de encoding:

1. **`NZCV`/`DAIF`** (`CRn=4,CRm=2`): uma SEGUNDA via de acesso aos mesmos 4 flags de condição
   (`PSTATE.{N,Z,C,V}`) e ao bit `I` de máscara de IRQ que já existem desde B6.1/B6.6.7 — código
   real usa isso para salvar/restaurar flags em volta de uma seção crítica (`MRS x0,NZCV` / ... /
   `MSR NZCV,x0`) sem depender de uma instrução aritmética "descartável".
2. **`CNTVCT_EL0`/`CNTV_TVAL_EL0`/`CNTV_CTL_EL0`/`CNTV_CVAL_EL0`** (`CRn=14,CRm=0/3`): o contador e
   comparador VIRTUAL do timer genérico, mesmo papel do físico (`CNTPCT_EL0`/`CNTP_*`, B6.6.7) —
   `clock_gettime`/timers de userspace geralmente preferem o contador virtual ao físico.

## Inclui

- **`Aarch64SystemRegisterId.NZCV`/`DAIF`** — resolvidos INTRINSECAMENTE pelo `Aarch64Core`
  (mesmo grupo de `TPIDR_EL0`/`FPCR`/`FPSR`), mas ao contrário deles NÃO são escaninhos novos:
  `PstateRegister` ganhou `toNzcvRegisterFormat`/`setFromNzcvRegisterFormat` e
  `toDaifRegisterFormat`/`setFromDaifRegisterFormat`, lendo/escrevendo o MESMO `nzcv`/`irqDisabled`
  que toda ALU/`B.cond`/`Aarch64Core#enterIrq` já usam — um `MSR NZCV,x0` seguido de `B.cond` no
  próximo bloco tem que ver o valor novo, não um valor paralelo desincronizado. `DAIF` só o bit
  `I` tem efeito real (mesma disciplina de B6.6.7); `D`/`A`/`F` são `WI` (aceitos, sem efeito).
- **`Aarch64SystemRegisterId.CNTVCT_EL0`/`CNTV_TVAL_EL0`/`CNTV_CTL_EL0`/`CNTV_CVAL_EL0`** —
  reaproveitam o mecanismo PLUGÁVEL já existente (`Aarch64SystemRegisterBus`, mesmo caminho de
  `CNTPCT_EL0`/`CNTP_*`): sem hospedeiro instalado, `MRS`/`MSR` lança "sem hospedeiro" (correto,
  mesma disciplina). Só decode + resolução de ID novos, sem storage no `Aarch64Core` (não são
  identidade da CPU, são dependentes do relógio do hospedeiro).
- **`Aarch64Decoder`**: `CRn=4` do grupo EL0 agora roteia por `CRm` (`decodeCrn4RegisterId`,
  refatorado de `decodeFpControlStatusRegisterId` da B8.15 — MESMO `CRn` hospeda `NZCV`/`DAIF`
  (`CRm=2`) e `FPCR`/`FPSR` (`CRm=4`), teria colisão se checássemos só `CRn`).

## Não inclui

- `D`/`A`/`F` de `DAIF` com efeito real (debug/SError/FIQ não são modelados — mesmo escopo já
  fechado de B6.6.7).
- `CNTVOFF_EL2` (offset entre contador físico e virtual) — `CNTVCT_EL0` delega 100% ao
  hospedeiro, que decide o que devolver (mesma simplificação de `CNTPCT_EL0`).
- `SPSel`/`UAO`/`PAN`/`DIT`/`SSBS`/`TCO`/`ALLINT` via `MRS`/`MSR (register)` — já existem como
  `MSR (immediate)` (B8.3), mas a via `MRS`/`MSR (register)` de leitura/escrita PSTATE genérica
  para esses bits fica para task futura (candidata registrada, não presumida desnecessária).

## Validação

- `Aarch64PstateSystemRegisterTest` (novo, 7 testes): decode via corpus real (devkitA64) + prova
  que `MRS`/`MSR NZCV`/`DAIF` mudam o MESMO estado que `evalCond`/`irqDisabled` consultam (não um
  escaninho paralelo) + decode dos 4 registradores de timer virtual.
- `mvn -o test` verde (core+truffle) + `mvn -o install` local.
- **G5**: gbaemu 240/240 ✅, ndsemu 183/183 ✅, armbox 47/47 ✅.

## Armadilhas

- `CRn=4` do grupo `op1=3` (EL0) hospeda 2 famílias sem relação semântica (`NZCV`/`DAIF` vs.
  `FPCR`/`FPSR`) — só `CRm` distingue. Checar só `CRn==4` sem also checar `CRm` teria misturado as
  duas (achado de design, corrigido antes de virar bug: `decodeCrn4RegisterId` sempre olha `CRm`
  primeiro).
- `NZCV`/`DAIF` NÃO seguem o padrão "escaninho novo" de `TPIDR_EL0`/`FPCR`/`FPSR` (B8.14/B8.15) —
  são uma segunda VIEW de estado que já existe. Adicionar um campo `long nzcvScratch` novo em vez
  de ligar em `PstateRegister` teria sido um bug real (leitura/escrita por `MRS`/`MSR` divergindo
  do estado que as instruções aritméticas/`B.cond` realmente usam).

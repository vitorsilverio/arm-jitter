# B9.5 — VFP: VCVT/VMOV restantes (MPCore/v7-A)

**Trilha:** B · **Depende de:** — · **Repo:** arm-jitter

## Contexto

Task da escada 32 bits (B9) do plano mestre `b7-plano-cobertura-isa.md`, que descrevia o escopo
como "`VCVT` (8 formas) + `VMOV` (7 formas) — VFPv2 genuínos". A regra de triagem do próprio plano
mestre manda regenerar `docs/COBERTURA-ISA.md` e conferir cada instrução contra a fonte real ANTES
de implementar, em vez de confiar na lista colada no plano (que "envelhece").

⚠️ **Sem spec formal escrita antes da implementação** — mesmo padrão ad-hoc de B6.9/B6.11/B8.1
(task pequena o bastante para não precisar de rodada de spec separada). Este arquivo documenta a
triagem e o resultado, não um plano prévio.

## Triagem real (achado principal desta sessão)

A caracterização do plano mestre ("VFPv2 genuínos") estava **errada** para a maior parte das 15
células `❌` que a tabela mostrava para `VMOV_to_gp`/`VMOV_from_gp`/`VMOV_64_sp`/`VCVT_*`. Conferido
campo a campo contra `target/arm/tcg/translate-vfp.c` real do QEMU (`WebFetch`+`curl`, não de
memória — precedente de aviso da B6.8):

- **`VMOV_to_gp`/`VMOV_from_gp`** (6 linhas — bytes/halfword/word × to/from): `trans_VMOV_to_gp`/
  `trans_VMOV_from_gp` calculam `insn_is_neon = (size != MO_32)` e exigem `ARM_FEATURE_NEON` nesse
  caso — **só a forma word (`size=2`) é VFPv2 genuína** (`aa32_fpsp_v2`); as formas byte/halfword
  são Advanced SIMD de verdade. Nenhum preset deste projeto declara NEON (0% de cobertura
  documentado) e o ARM11 MPCore real do 3DS também não tem.
- **`VMOV_64_sp`**: `aa32_fpsp_v2` — genuinamente VFPv2 (forma depreciada mas real).
- **`VCVT_fix_sp`/`VCVT_fix_dp`**: `aa32_fpsp_v3`/`aa32_fpdp_v3` — **VFPv3**, não VFPv2 (o projeto já
  mistura os dois sob a mesma feature `ArmFeature.VFPV2`, que seu próprio Javadoc documenta como
  "VFPv2 + VMOV imediato do v3-d16" — mesma simplificação, sem feature separada).
- **`VCVT_f32_f16`/`VCVT_f16_f32`**: `aa32_fp16_spconv` — extensão OPCIONAL de meia precisão do
  VFPv3, não VFPv2/v3 base.
- **`VCVT_f64_f16`/`VCVT_f16_f64`**: `aa32_fpdp_v2` + `aa32_fp16_dpconv` — idem, lado dupla precisão.
- **`VCVT_b16_f32`**: `aa32_bf16` — BFloat16, ARMv8.6-A.
- **`VCVT_hp_int`**: `aa32_fp16_arith` — ARMv8.2-A FP16 aritmética completa. ⚠️ Achado colateral:
  este mnemônico NÃO casa com o padrão `*_hp` já curado em `docs/isa-nao-aplicavel.tsv` (termina em
  `_int`, não em `_hp`) — por isso ainda aparecia `❌` mesmo sendo claramente pós-VFPv2/v3; seu par
  `VCVT_int_hp` já era corretamente `·` pelo mesmo padrão de sufixo.

## Escopo implementado (5 instruções reais)

- **`VMOV_to_gp`/`VMOV_from_gp`, forma word** (`decodeScalarGpTransfer`, novo em `VfpDecoder`):
  distingue as 3 formas via `bit22`(byte)/`bit5`(halfword)/`bit22=0,bit5=0,bit6=0`(word) — só a
  última é aceita. **Não ganhou `Kind` novo**: a semântica é idêntica a `VMOV_single`
  (`VFP_CORE_TRANSFER`), só o registrador `S` de origem/destino é calculado como `2*vn+index` a
  partir do `D` combinado em vez de vir direto de `%vn_sp` — reaproveita o `IrOp.VfpCoreTransfer`
  já existente sem duplicar execução.
- **`VMOV_64_sp`** (`Kind`/`IrOp` novos: `VFP_CORE_PAIR_TRANSFER_SINGLE`/`VfpCorePairTransferSingle`):
  transfere `Sm`/`Sm+1` (par consecutivo) de/para dois registradores ARM. **Não reaproveita**
  `VfpCorePairTransfer` (que assume um `D` inteiro via `d()`/`setD()`) porque `Sm`/`Sm+1` só
  coincidem com um `D` completo quando `m` é PAR — para `m` ímpar as duas metades pertencem a `D`
  diferentes (testado explicitamente: `corePairTransferSingleWithOddVmSpansTwoDifferentDRegisters`).
- **`VCVT_fix_sp`/`VCVT_fix_dp`** (`Kind`/`IrOp` novos: `VFP_CONVERT_FIXED`/`VfpConvertFixed`):
  conversão fixo↔float no MESMO registrador `vd`. `opc2` do encoding (`{0xA,0xB,0xE,0xF}`) embute 2
  dos 3 bits do campo real `opc=op:u:sx` (bit18/bit16), o terceiro (`sx`) é `bit7` — conferido
  contra `vfp_helper.c` (`VFP_CONV_FIX*`): fixo→float SEMPRE arredonda ao mais próximo (par);
  float→fixo SEMPRE trunca para zero e satura na largura/sinal do campo (16 ou 32 bits). A direção
  dp usa o registrador `D` de 64 bits inteiro como container do inteiro fixo (sign/zero-extend até
  64 bits ao gravar, não só os 32 bits baixos — achado ao ler `vfp_helper.c`: o helper devolve
  `uint64_t` a partir de um `int16_t`/`int32_t`, convertido implicitamente com extensão de sinal).

## Não inclui (documentado em `docs/isa-nao-aplicavel.tsv`)

- `VCVT_f32_f16`/`VCVT_f16_f32`/`VCVT_f64_f16`/`VCVT_f16_f64`/`VCVT_b16_f32`/`VCVT_hp_int` — todos
  extensões opcionais posteriores a VFPv2/v3 base, ver "Triagem real" acima. Linhas novas na TSV.
- `VMOV_to_gp`/`VMOV_from_gp`, formas byte/halfword — NEON-gated (ver acima). **NÃO adicionadas à
  TSV**: a curadoria casa por NOME, e o inventário usa o MESMO mnemônico para as 3 formas
  (byte/halfword/word) — excluir pelo nome apagaria também a forma word, já implementada. Ficam
  como falso-negativo conhecido (2 das 3 linhas de cada mnemônico continuam `❌` na tabela) —
  documentado aqui em vez de "corrigido incorretamente". Só uma curadoria por-encoding (não só por
  nome) no `IsaCoverageReport` resolveria isso de verdade; fora do escopo desta task.
- Suporte ASM nativo para os 2 `Kind`s novos (`AsmNativePolicy` devolve `false` para os dois) — caem
  no interpretado via `AsmFallbackPolicy.PER_OP`, mesmo padrão de várias tasks B8.x/B9.x.

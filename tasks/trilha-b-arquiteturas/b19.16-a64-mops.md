### O que a extensão faz, e o padrão "3 fases"

`FEAT_MOPS` acelera `memcpy`/`memset` com instruções que o compilador/libc emite em **trio**:
prólogo (alinha, decide tamanho/direção), principal (faz o grosso do trabalho, interruptível — pode
ser re-executada após uma exceção/interrupção), epílogo (termina o resto não alinhado). O SOFTWARE
sempre emite os 3 na ordem certa com os MESMOS 3 registradores (`Xd`=destino, `Xn`=origem/valor,
`Xs`/`Xzr`=tamanho) — o hardware real detecta emissão fora de ordem e falha (`UNDEFINED` ou
`SETGE`/opção específica); **esta task pode simplificar isso** (ver Inclui item 3).

- **`SETP`/`SETM`/`SETE`**: `memset(Xd, byte(Xn), Xzr)` acelerado — como o emulador não precisa
  "acelerar" nada (não há hardware real com micro-arquitetura para explorar), a implementação
  correta e mais simples é: `SETP` faz o trabalho (loop de escrita do byte `Xzr` vezes), `SETM`/
  `SETE` são efetivamente NOP funcionais (o trabalho já terminou), OU distribuir entre as 3 —
  **decisão de implementação, não de escopo**: qualquer divisão que produza o efeito observável
  correto ao final das 3 instruções está certa, desde que os registradores sejam atualizados
  conforme o pseudocódigo real (avançam para refletir progresso, mesmo que o "progresso" seja
  instantâneo neste emulador).
- **`CPYFP`/`CPYFM`/`CPYFE`**: `memcpy` **forward-only** (direção fixa, do menor para o maior
  endereço) — trio análogo ao de `SET*`.
- **`CPYP`/`CPYM`/`CPYE`** ⚠️: `memcpy` genérico, que PODE copiar de trás para frente se os
  intervalos de origem/destino se sobrepuserem de um jeito que exija isso (`memmove`-like) — a
  direção é decidida por bits de opção no encoding (`options` no formato `@cpy`), não fixa como
  `CPYF*`. Medem `⚠️`, não `❌`: outra instrução hoje reivindica parte deste encoding. **Confirmar
  se a causa raiz é compartilhada com `SETGP`/`SETGM`/`SETGE` (B19.14)** — os dois grupos vivem no
  mesmo bloco "Memory Copy and Memory Set" citado pelo comentário do decoder, e a B19.14 já
  referencia esta task para investigação conjunta.

**Leitura obrigatória**: `b19.14-a64-mte2.md` (a família `SETGP`/`SETGM`/`SETGE`, possível causa
raiz compartilhada). No código: `decoder64/Aarch64Decoder.java:677-678` e `:1749` (os dois
comentários que já apontam para este bloco não modelado — ler o contexto ao redor de cada um antes
de decidir onde plugar o decode novo).

## Aceite

- **O Javadoc de `MEMORY_COPY_SET` reflete a realidade** depois desta task (corrigido se estava
  errado, confirmado como estava se a investigação achar o "caminho genérico" real).
- As 9 linhas decodificam sob `ARMV8_8_A`+ e seguem `unsupported` abaixo.
- **`SETP`+`SETM`+`SETE` em sequência** produzem o efeito de `memset` completo e correto (região
  preenchida com o byte certo, tamanho certo).
- **`CPYFP`+`CPYFM`+`CPYFE`** produzem o efeito de `memcpy` forward correto, incluindo um caso onde
  origem e destino NÃO se sobrepõem.
- **`CPYP`+`CPYM`+`CPYE`** produzem o efeito de `memmove` correto num caso de sobreposição real
  (origem e destino se cruzam) — prova de que a direção é honrada corretamente.
- **Regressão negativa do `⚠️` original** de `CPYP`/`CPYM`/`CPYE` documentada.
- `docs/COBERTURA-ISA.md`: as 9 células saem de `❌`/`⚠️` para `✅` de `ARMv8.8-A` em diante.
- `mvn -o test` verde + G5 verde nos 5 consumidores.

## Armadilhas

1. **A discrepância do Javadoc pode enganar quem só ler a constante** — investigar antes de confiar
   nela.
2. **`CPYF*` é sempre forward; `CPY*` (sem `F`) pode ser reverso** — é a diferença central entre os
   dois trios, fácil de perder ao ler os nomes rápido.
3. **`⚠️` compartilhado possível com `SETGP`/`SETGM`/`SETGE`** — não investigar isoladamente sem
   checar a B19.14 primeiro.
4. **O protocolo real de 3 fases existe para interromper/retomar um `memcpy` gigante** — este
   emulador pode simplificar (fazer tudo na 1ª fase), mas os registradores de progresso ainda
   precisam terminar no estado que o pseudocódigo real prevê, para que software real que LEIA esse
   estado entre as fases não quebre.

## Não fazer

- Não implementar `STGP`/`SETGP`/`SETGM`/`SETGE` (B19.14) nem `LDCLRP`/`LDSETP`/`SWPP` (B19.25).
- Não assumir a afirmação do Javadoc sem investigar a discrepância.
- Não adicionar caso nativo em `Ir64NativePolicy`.

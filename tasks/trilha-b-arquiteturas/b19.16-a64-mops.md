### O que a extensão faz, e o padrão "3 fases"

`FEAT_MOPS` acelera `memcpy`/`memset` com instruções que o compilador/libc emite em **trio**:
prólogo (alinha, decide tamanho/direção), principal (faz o grosso do trabalho, interruptível — pode
ser re-executada após uma exceção/interrupção), epílogo (termina o resto não alinhado). O SOFTWARE
sempre emite os 3 na ordem certa com os MESMOS 3 registradores (`Xd`=destino, `Xn`=origem/valor,
`Xs`/`Xzr`=tamanho) — o hardware real detecta emissão fora de ordem e falha (`UNDEFINED` ou
`SETGE`/opção específica); **esta task pode simplificar isso** (ver Inclui item 3).

- **`SETP`/`SETM`/`SETE`**: `memset(Xd, byte(Xn), Xzr)` acelerado — como o emulador não precisa
  "acelerar" nada (não há hardware real com micro-arquitetura para explorar), a implementação
  correta e mais simples é: `SETP` faz o trabalho (loop de escrita do byte `Xzr` vezes), `SETM`/
  `SETE` são efetivamente NOP funcionais (o trabalho já terminou), OU distribuir entre as 3 —
  **decisão de implementação, não de escopo**: qualquer divisão que produza o efeito observável
  correto ao final das 3 instruções está certa, desde que os registradores sejam atualizados
  conforme o pseudocódigo real (avançam para refletir progresso, mesmo que o "progresso" seja
  instantâneo neste emulador).
- **`CPYFP`/`CPYFM`/`CPYFE`**: `memcpy` **forward-only** (direção fixa, do menor para o maior
  endereço) — trio análogo ao de `SET*`.
- **`CPYP`/`CPYM`/`CPYE`** ⚠️: `memcpy` genérico, que PODE copiar de trás para frente se os
  intervalos de origem/destino se sobrepuserem de um jeito que exija isso (`memmove`-like) — a
  direção é decidida por bits de opção no encoding (`options` no formato `@cpy`), não fixa como
  `CPYF*`. Medem `⚠️`, não `❌`: outra instrução hoje reivindica parte deste encoding. **Confirmar
  se a causa raiz é compartilhada com `SETGP`/`SETGM`/`SETGE` (B19.14)** — os dois grupos vivem no
  mesmo bloco "Memory Copy and Memory Set" citado pelo comentário do decoder, e a B19.14 já
  referencia esta task para investigação conjunta.

**Leitura obrigatória**: `b19.14-a64-mte2.md` (a família `SETGP`/`SETGM`/`SETGE`, possível causa
raiz compartilhada). No código: `decoder64/Aarch64Decoder.java:677-678` e `:1749` (os dois
comentários que já apontam para este bloco não modelado — ler o contexto ao redor de cada um antes
de decidir onde plugar o decode novo).

## Armadilhas

1. **A discrepância do Javadoc pode enganar quem só ler a constante** — investigar antes de confiar
   nela.
2. **`CPYF*` é sempre forward; `CPY*` (sem `F`) pode ser reverso** — é a diferença central entre os
   dois trios, fácil de perder ao ler os nomes rápido.
3. **`⚠️` compartilhado possível com `SETGP`/`SETGM`/`SETGE`** — não investigar isoladamente sem
   checar a B19.14 primeiro.
4. **O protocolo real de 3 fases existe para interromper/retomar um `memcpy` gigante** — este
   emulador pode simplificar (fazer tudo na 1ª fase), mas os registradores de progresso ainda
   precisam terminar no estado que o pseudocódigo real prevê, para que software real que LEIA esse
   estado entre as fases não quebre.

## Resultado

**FECHADA 2026-09-10.**

**Discrepância do Javadoc confirmada e corrigida** — nenhum dos 9 mnemônicos tinha decode de
verdade (`decodeLoadsAndStores` jogava todo o bucket bit24=1 em `unsupported`); o Javadoc de
`Aarch64Feature.MEMORY_COPY_SET` foi reescrito para não afirmar mais um "caminho genérico" para
`SET*`/`CPYF*` que nunca existiu.

**Causa raiz do `⚠️` de `CPYP`/`CPYM`/`CPYE`** (e, de carona, de `SETGP`/`SETGM`/`SETGE`, família da
B19.14): o bit `V` (bit26, `VECTOR_FORM_BIT_SHIFT`) nesta região do encoding **não é** o seletor
SIMD&FP de verdade — é parte do opcode MOPS/tag (`CPYFx`=0/`CPYx`=1, `SETx`=0/`SETGx`=1). Como
`decodeLoadsAndStores` checava `vectorForm` ANTES do bucket "reservado" (bit24=1 dentro de
`SUBCLASS_LITERAL`), essas 6 instruções com bit26=1 "por acidente" caíam em `decodeFpLoadLiteral` e
viravam `LDR (literal)` SIMD&FP — mesma classe de bug que a B11.3 já tinha corrigido para o lado
GPR. Fix: mover o check do bucket bit24=1 para ANTES do `if (vectorForm)`, independente de bit26.

**Segundo achado, encontrado só depois de medir `docs/COBERTURA-ISA.md` pós-implementação**:
`LDAPR_i`/`STLR_i` (`FEAT_LRCPC2`, forma imediata `@ldapr_stlr_i`, ainda não implementada —
B19.19) compartilham o MESMO prefixo de 6 bits `011001` (bits[29:24]) que `SETP`/`SETM`/`SETE`/
`CPYFP`/`CPYFM`/`CPYFE` (bit26=0 nos dois grupos) e o mesmo bit21=0 — o único discriminador real é
bits[11:10] (`01` fixo em MOPS, `00` fixo em `LDAPR_i`/`STLR_i`), campo que a primeira versão do
decoder novo não checava. Sem esse check, `LDAPUR`/`LDAPURB`/`STLUR` (`opc`∈{01,10,11}) eram
absorvidos como `CPYFM`/`CPYFE`/`SETP` — 7 linhas ganhariam `✅` falso (confirmado medindo
`docs/COBERTURA-ISA.md` ANTES/DEPOIS do fix: delta inicial de +80 células, não os +45 esperados;
isolado revertendo/reaplicando o check dedicado). Corrigido com um terceiro campo checado
(`MOPS_FIXED_BITS_11_10_VALUE`), confirmado byte a byte contra `aarch64-linux-gnu-as`/`objdump`
(WSL Ubuntu, `-march=armv8.4-a`, `ldapur x0,[x1,#8]`/`ldapurb w0,[x1,#8]`/`stlur x0,[x1,#8]`) e
coberto por teste de regressão dedicado.

**Implementação**: 2 `Ir64Op` novos (`MemorySet`, `MemoryCopy`) + enum `Ir64MopsPhase`
(`PROLOGUE`/`MAIN`/`EPILOGUE`), interpretados apenas (sem caso nativo, conforme "Não inclui").
Simplificação registrada explicitamente (G8, mesmo padrão de `Crc32`/`PointerAuthGeneric`): a fase
que encontra o contador (`Rn`) diferente de zero faz o trabalho INTEIRO num loop byte a byte e zera
o contador; a(s) fase(s) seguinte(s), com o contador já zerado, são NOP funcional — válido tanto
rodando as 3 fases em sequência (uso real de software) quanto uma fase isolada (nunca crasha,
apenas não avança nada se `Rn==0`). `CPYP`/`CPYM`/`CPYE` (`forwardOnly=false`) escolhem a direção
do loop pela mesma regra de `memmove` (`src < dst && src+count > dst` ⇒ copiar de trás para
frente), testado com um caso de sobreposição real. `PSTATE.NZCV` gravado como Option B da
arquitetura (`0b0010` sentido direto, `0b1010` reverso) — decisão registrada, irrelevante para a
simplificação de fases mas arquiteturalmente correto.

**Testes**: `Aarch64MemoryCopySetDecoderTest` (10 casos: gate por feature, as 9 formas com
registradores corretos, `SETGP`/`SETGM`/`SETGE` continuam recusados, `LDAPUR`/`LDAPURB`/`STLUR`
continuam recusados) + `Ir64MemoryCopySetExecutorTest` (7 casos: sequência `SETP`+`SETM`+`SETE`,
byte de preenchimento só usa os 8 bits baixos, NOP com contador zero, `CPYF*` sem sobreposição,
`CPY*` com sobreposição tipo `memmove`, `CPY*` sem sobreposição). Golden values dos 9 mnemônicos e
das 3 formas `LDAPUR`/`LDAPURB`/`STLUR` via `aarch64-linux-gnu-as`/`objdump` reais (WSL Ubuntu,
`-march=armv8.8-a`/`armv8.4-a` + `.arch_extension memtag` para `SETGP`/`SETGM`/`SETGE`).

**`docs/COBERTURA-ISA.md`**: as 9 células saem de `❌`/`⚠️` para `✅` de `ARMv8.8-A` em diante (5
colunas aplicáveis cada — `ARMv8.8-A`/`ARMv8.9-A`/`ARMv9.3-A`/`ARMv9.4-A`/`ARMv9.5-A`, já que

# B6.3.1 — AArch64: logical immediate (`DecodeBitMasks`) + ALU registrador (shifted/extended)

**Trilha:** B · **Depende de:** B6.2 🟡 (parcial — ver Armadilhas sobre o aceite #2 de
busybox bloqueado) · **Repo:** arm-jitter

## Contexto

Esta é a **primeira** das 4 sub-tasks em que
[b6-aarch64.md](b6-aarch64.md) decompõe B6.3 (rodada de refinamento de spec,
2026-07-24 — B6.3 original era grande demais para uma task só, ver o registro
de decomposição no próprio `b6-aarch64.md`). Agrupamento escolhido para esta
fatia: **o encoding mais traiçoeiro da ISA A64** (`logical immediate`,
citado nas Armadilhas do épico) **junto com as duas formas de ALU por
registrador** (`shifted register` e `extended register`) — motivo do
agrupamento: as duas formas de ALU por registrador vivem numa classe
top-level do encoding A64 (`Data Processing — Register`) que
{@code Aarch64Decoder} **ainda não tem nenhum dispatch para** (só
`Data Processing Immediate` e `Branch/Exception/System` existem hoje — ver
Fatos de referência #1); esta task cria esse dispatch novo, do qual **B6.3.2**
(CSEL) e **B6.3.3** (MUL/MADD/SDIV/UDIV) dependem funcionalmente (adicionam
mais `case`s ao mesmo método). Colocar o encoding mais arriscado (logical
imm) na mesma task que cria a infraestrutura de dispatch nova evita que o
risco fique espalhado por três tasks diferentes sem dono claro.

`logical (immediate)` fica fora da classe nova — é subgrupo de `Data
Processing Immediate` (mesma classe de `ADD`/`SUB` imediato e `MOVZ`/`MOVN`/
`MOVK`, já implementados em B6.1), então é o `case` que falta no switch que já
existe (`decodeDataProcessingImmediate`), não dispatch novo.

## Fatos de referência (fixados nesta rodada de spec — fontes: `ARM DDI 0487`
seções citadas + QEMU `target/arm/tcg/a64.decode`/`translate-a64.c`, lidos do
HEAD do master em 2026-07-24; ver Armadilhas sobre pin de versão)

1. **Onde a classe "Data Processing — Register" cabe no dispatch atual.**
   `Aarch64Decoder.decode` (`decoder64/Aarch64Decoder.java:222-237`) hoje só
   trata dois casos antes/depois de `isLoadsAndStoresClass`: se bit27=1 e
   bit25=0 → Loads/Stores (`isLoadsAndStoresClass`, linha 239-243); senão,
   `topLevelClass = bits[28:26]`, com `switch` só para `0b100`
   (`CLASS_DATA_PROCESSING_IMMEDIATE`) e `0b101`
   (`CLASS_BRANCH_EXCEPTION_SYSTEM`); qualquer outro valor lança
   `unsupported`. **Confirmado por leitura do próprio javadoc da classe**
   (linha 26-27): "`Data Processing Register/SIMD&FP`... também têm bit27=1
   mas bit25=1" — ou seja, a classe "Data Processing — Register" (`ARM DDI
   0487 C4.1`, padrão `x101` nos bits[28:25]: bit27=1 fixo, bit26 livre,
   bit25=1 fixo, bit28 livre) tem a MESMA ambiguidade de bits[28:26] que
   `Loads-and-Stores` já resolveu com uma checagem própria fora do switch de 3
   bits — **precisa do mesmo tratamento**: uma nova função
   `isDataProcessingRegisterClass(word)` (bit27=1 && bit25=1), verificada em
   `decode()` ANTES de cair no switch de 3 bits (ou logo depois de
   `isLoadsAndStoresClass`, já que as duas compartilham bit27=1 e só bit25 as
   distingue). Dentro dessa classe, os subgrupos (ALU shifted/extended,
   lógica por registrador, `CSEL`, `2-source`/`3-source`) são distinguidos
   pelos bits [30:21] — cada sub-task usa só o fatiamento que precisa, sem
   reproduzir a tabela inteira aqui.

2. **`Logical (immediate)`** (`a64.decode`, QEMU master 2026-07-24):
   ```
   &rri_log        rd rn sf dbm
   @logic_imm_64   1 .. ...... dbm:13 rn:5 rd:5            &rri_log sf=1
   @logic_imm_32   0 .. ...... 0 dbm:12 rn:5 rd:5          &rri_log sf=0

   AND_i           . 00 100100 . ...... ...... ..... ..... @logic_imm_64/@logic_imm_32
   ORR_i           . 01 100100 . ...... ...... ..... ..... @logic_imm_64/@logic_imm_32
   EOR_i           . 10 100100 . ...... ...... ..... ..... @logic_imm_64/@logic_imm_32
   ANDS_i          . 11 100100 . ...... ...... ..... ..... @logic_imm_64/@logic_imm_32
   ```
   Em `Aarch64Decoder.decodeDataProcessingImmediate` (linha 387-397), o
   subgrupo `00` de `SUBGROUP_24_23` (hoje só `SUBGROUP_MOVE_WIDE=0b01` é
   tratado) é este grupo. Campo `dbm` de 13 bits (64-bit) é `N:immr:imms`
   contíguo — `N` no bit mais alto (bit22 da instrução), `immr` nos 6
   seguintes (bits21:16), `imms` nos 6 mais baixos (bits15:10); na forma
   32-bit (`sf=0`), `N` é sempre `0` e não faz parte do campo de 12 bits
   (`dbm:12` = só `immr:imms`) — arquiteturalmente, `N=1` com `sf=0` é
   reservado/UNDEFINED (não existe elemento de 64 bits numa operação `W`).
   `opc` (2 bits, bits30:29) seleciona `AND`(00)/`ORR`(01)/`EOR`(10)/`ANDS`(11)
   — reaproveita exatamente `Ir64AluOp.AND/ORR/EOR` já declarados no formato
   desde B6.1 (`ir64/Ir64AluOp.java:15-19`, hoje inalcançáveis pelo decoder —
   esta task é o primeiro lugar que os produz) + um novo `Ir64AluOp.ANDS`
   dedicado (`ANDS` não é `AND` com `setFlags=true` reaproveitável 1:1 — ver
   Decisão D2 abaixo).

3. **`DecodeBitMasks` — algoritmo REAL, transcrito de
   `target/arm/tcg/translate-a64.c:5224-5286`, função
   `logic_imm_decode_wmask`** (QEMU master, comentário original: "Simplified
   variant of pseudocode `DecodeBitMasks()` for the case where we only
   require the `wmask`"):
   ```c
   bool logic_imm_decode_wmask(uint64_t *result, unsigned int immn,
                               unsigned int imms, unsigned int immr)
   {
       uint64_t mask;
       unsigned e, levels, s, r;
       int len;
       assert(immn < 2 && imms < 64 && immr < 64);

       /* First determine the element size */
       len = 31 - clz32((immn << 6) | (~imms & 0x3f));
       if (len < 1) {
           /* immn == 0, imms == 0x11111x: reservado */
           return false;
       }
       e = 1 << len;

       levels = e - 1;
       s = imms & levels;
       r = immr & levels;

       if (s == levels) {
           /* <length of run - 1> não pode ser todo-uns */
           return false;
       }

       /* um elemento: s+1 bits setados, rotacionado por r dentro de e bits */
       mask = MAKE_64BIT_MASK(0, s + 1);
       if (r) {
           mask = (mask >> r) | (mask << (e - r));
           mask &= MAKE_64BIT_MASK(0, e);
       }
       /* replica o elemento pelos 64 bits inteiros */
       mask = bitfield_replicate(mask, e);
       *result = mask;
       return true;
   }
   ```
   `bitfield_replicate(mask, e)` (mesma unit, função utilitária QEMU) só
   duplica o padrão de `e` bits sucessivamente até preencher 64 bits (`e` *=
   2` a cada passo, `mask |= mask << e`, começando de `mask` já do tamanho
   `e`) — trivial de reimplementar. `MAKE_64BIT_MASK(0, n)` é
   `n==64 ? -1L : (1L<<n)-1` (cuidado com `n==64`: shift de 64 bits em Java é
   UB por wraparound do operador `<<`, tratar como caso especial — mesma
   armadilha que qualquer shift de largura cheia neste projeto já trata em
   outros pontos do 32-bit, ex. buscar `-1 <<` ou `>>> 32` no `IrAluExecutor`
   para o precedente de estilo).
   **Chave de leitura do algoritmo** (glossário rápido pra quem só olhar o
   código): `len` é o log2 do tamanho do elemento replicado (`e = 2^len`,
   `e ∈ {2,4,8,16,32,64}`), achado contando quantos bits `1` líderes tem a
   concatenação `N:~imms` (é isso que `31 - clz32(...)` calcula: a posição do
   bit `1` mais alto identifica o tamanho do elemento, ver comentário do
   próprio QEMU linha 5233-5254 para a tabela `N:imms` → tamanho do elemento).
   `s` = quantos bits setados tem a "corrida" de uns dentro do elemento,
   MENOS 1; `r` = rotação à direita dentro do elemento. Combinações
   reservadas: (a) `len<1` (a concatenação é `000000`, só ocorre quando
   `N=0` e `imms=0b11111x`); (b) `s == levels` (a corrida de uns ocupa o
   elemento inteiro — não seria uma máscara útil, seria todo-1 ou todo-0
   dependendo do contexto, e o manual reserva esse caso).
   **Property test obrigatório contra o corpus** (ver Testes mínimos) — não
   é permitido "confiar" no algoritmo transcrito sem validar contra saída
   real do assembler para pelo menos os casos de canto (`N=1`/elemento de 64
   bits, elemento de 2 bits o menor possível, rotações não-triviais).

4. **`Add/subtract (shifted register)`** (`a64.decode`):
   ```
   &addsub_shift    rd rn rm sf sa st
   @addsub_shift    sf:1 .. ..... st:2 . rm:5 sa:6 rn:5 rd:5   &addsub_shift

   ADD_r   . 00 01011 .. 0 ..... ...... ..... .....    @addsub_shift
   SUB_r   . 10 01011 .. 0 ..... ...... ..... .....    @addsub_shift
   ADDS_r  . 01 01011 .. 0 ..... ...... ..... .....    @addsub_shift
   SUBS_r  . 11 01011 .. 0 ..... ...... ..... .....    @addsub_shift
   ```
   `st` (2 bits, `shift type`): `00`=LSL, `01`=LSR, `10`=ASR, **`11`=RESERVADO
   para ADD/SUB** (diferente do `Logical (shifted register)`, fora de escopo
   desta task, onde `11` é ROR — `ADD`/`SUB` não tem forma ROR). `sa` (6
   bits, quantidade, `0`-`63`).
   **Restrições UNDEFINED, confirmadas em `translate-a64.c`, função
   `do_addsub_reg` (chamada pelos 4 `TRANS(..._r, do_addsub_reg, ...)`)**:
   ```c
   if (a->st == 3 || (!a->sf && (a->sa & 32))) {
       return false; /* undef */
   }
   ```
   ou seja: `st==0b11` sempre reservado; e com `sf=0` (operação `W`), `sa`
   com o bit 5 setado (quantidade ≥32) também é reservado — a quantidade
   válida em `W` é só `0`-`31`.
   **`Rd`/`Rn` NUNCA são `SP` nesta forma** — `do_addsub_reg` sempre lê/escreve
   com `cpu_reg`, nunca `cpu_reg_sp`; confirma a distinção que a task pediu
   para verificar contra a forma `extended register` abaixo.

5. **`Add/subtract (extended register)`** (`a64.decode`):
   ```
   &addsub_ext     rd rn rm sf sa st
   @addsub_ext     sf:1 .. ........ rm:5 st:3 sa:3 rn:5 rd:5   &addsub_ext

   ADD_ext   . 00 01011001 ..... ... ... ..... .....     @addsub_ext
   SUB_ext   . 10 01011001 ..... ... ... ..... .....     @addsub_ext
   ADDS_ext  . 01 01011001 ..... ... ... ..... .....     @addsub_ext
   SUBS_ext  . 11 01011001 ..... ... ... ..... .....     @addsub_ext
   ```
   `st` aqui é o campo `option` de 3 bits (`ARM DDI 0487 C6.2.4`, "extend
   type"): `000`=UXTB, `001`=UXTH, `010`=UXTW, `011`=UXTX (também o
   encoding de "LSL" quando escrito com `Rd`/`Rn`=`SP` — mesmo padrão de
   {@link dev.vitorsilverio.armjitter.ir64.Ir64ExtendType#LSL} já
   documentado em B6.2 para a forma de load/store), `100`=SXTB, `101`=SXTH,
   `110`=SXTW, `111`=SXTX. `sa` (3 bits) é a quantidade de shift aplicada
   APÓS a extensão, **restrita a `0`-`4`** — confirmado em
   `do_addsub_ext`: `if (a->sa > 4) return false;` (embora o campo tenha 3
   bits e caiba até 7, valores 5-7 são UNDEFINED).
   **`Rn` é SEMPRE `Rn|SP`** (`read_cpu_reg_sp`), **`Rd` é `Rd|SP` só quando
   `!setflags`** (`ADD`/`SUB`, não `ADDS`/`SUBS`) — EXATAMENTE a mesma regra
   já usada por `Ir64Op.Alu64` na forma imediata (`dstIsStackPointer =
   !setFlags`, `src1IsStackPointer = true` sempre — ver
   `Aarch64Decoder.decodeAddSubImmediate`, linha 419-424). **`Rm` NUNCA é
   `SP`** nesta forma (sempre `cpu_reg`/`read_cpu_reg`, estendido pelo
   helper `ext_and_shift_reg`).
   O helper de extensão (`translate-a64.c:1689-1696`, `ext_and_shift_reg`):
   ```c
   static void ext_and_shift_reg(TCGv_i64 tcg_out, TCGv_i64 tcg_in,
                                 int option, unsigned int shift)
   {
       int extsize = extract32(option, 0, 2);
       bool is_signed = extract32(option, 2, 1);
       tcg_gen_ext_i64(tcg_out, tcg_in, extsize | (is_signed ? MO_SIGN : 0));
       tcg_gen_shli_i64(tcg_out, tcg_out, shift);
   }
   ```
   confirma a regra de leitura: os 2 bits baixos de `option` codificam o
   TAMANHO lido de `Rm` antes da extensão (`00`=8 bits/byte, `01`=16
   bits/half, `10`=32 bits/word, `11`=64 bits/doubleword — **não** "sempre
   W como no load/store"; aqui há 4 tamanhos, não 2), o bit alto (`bit 2`)
   seleciona sinal (`1`) vs zero (`0`) extensão. **Diferença arquitetural
   real confirmada com a forma `shifted register`**: as duas formas usam
   espaços de bits DIFERENTES (`01011..0` vs `01011001`, distinguidos pelos
   bits[23:21]) e têm semânticas de operando distintas (shift puro de `Rm`
   completo vs extend-then-shift de uma FATIA de `Rm`) — não são a "mesma
   operação com um parâmetro a mais", são dois modos de endereçamento de
   operando genuinamente diferentes, cada um com sua própria regra de
   `SP`/tamanho de shift.

## Decisões de desenho FECHADAS nesta rodada

### D1 — Novo dispatch de classe top-level ("Data Processing — Register")

**Decisão:** adicionar `isDataProcessingRegisterClass(int word)` (bit27=1 &&
bit25=1) em `Aarch64Decoder`, verificada em `decode()` logo após
`isLoadsAndStoresClass` (mesmo padrão, mesmo motivo: a ambiguidade dos bits
[28:26] exige resolver bit25 fora do switch de 3 bits). Um método novo
`decodeDataProcessingRegister(int word, long address)` concentra os
sub-dispatches desta classe; **esta task só preenche os `case`s de
`ADD_r`/`SUB_r`/`ADDS_r`/`SUBS_r`/`ADD_ext`/`SUB_ext`/`ADDS_ext`/`SUBS_ext`**
— os subgrupos de `CSEL` (B6.3.2) e `2-source`/`3-source` (B6.3.3) entram
como `case`s adicionais no MESMO método, adicionados por essas tasks
subsequentes (dependência funcional real, não arbitrária — ver Contexto).
Qualquer subgrupo não coberto (lógica por registrador `AND`/`ORR`/`EOR`
registrador, que a spec do épico NÃO lista — ver Armadilhas) continua
lançando `unsupported`.

### D2 — `ANDS` (imediato) não reaproveita `AND` com `setFlags=true`

**Investigado:** `Ir64Op.Alu64` já tem um campo `setFlags` genérico
reaproveitado por `ADD`/`SUB`/`ADDS`/`SUBS` (mesmo opcode, flag liga/desliga
o cálculo de NZCV). Para `AND`/`ANDS` a tentação seria fazer o mesmo
(`Ir64AluOp.AND` + `setFlags=true`), mas **os flags calculados são
diferentes por natureza da operação, não só "ligar/desligar" o mesmo
cálculo**: `ADD`/`SUB` calculam C/V a partir de aritmética real (carry/
overflow de complemento-de-dois); `AND`/`ORR`/`EOR` (imediato) **nunca têm
C/V calculado a partir de nada — são SEMPRE `C=0,V=0`** quando `setFlags`
(`ARM DDI 0487 C6.2.9`, `ANDS` imediato: "PSTATE.C = '0'; PSTATE.V = '0'").
Isso já está, na verdade, resolvido pelo executor existente
(`Ir64BlockExecutor.logicalWithFlags`, linha 346-350, já usado por
`AND`/`ORR`/`EOR` mesmo sem terem decode ainda) — **decisão: reaproveitar o
MESMO `Ir64Op.Alu64` e o MESMO `logicalWithFlags` já escritos em B6.1/B6.2
para a forma imediata**; não é preciso um `Ir64AluOp.ANDS` novo, nem um
record novo. `ANDS_i` produz `Ir64Op.Alu64(AND, ..., setFlags=true, ...)` —
igual a `ADDS`/`SUBS` produzirem `Alu64(ADD/SUB, setFlags=true, ...)`. A
menção a "`Ir64AluOp.ANDS` dedicado" no item 2 dos Fatos de referência acima
foi a hipótese inicial da pesquisa — **revogada aqui**: o campo `setFlags`
existente já é suficiente porque o EXECUTOR (`logicalWithFlags`) já
implementa a semântica certa de C/V=0 para operações lógicas,
independentemente de qual opcode lógico for. `AND`/`ORR`/`EOR` (imediato)
**nunca têm forma `SP` em `Rd`/`Rn`** (diferente de `ADD`/`SUB` imediato) —
`dstIsStackPointer`/`src1IsStackPointer` são sempre `false` para os 4
opcodes lógicos, e o decoder deve setá-los explicitamente assim (não deixar
implícito).

### D3 — Novo(s) record(s) de IR para ALU por registrador

`Ir64Op.Alu64` é estruturalmente imediato-apenas (campo `immediate` de
`long`, sem segundo registrador). As duas formas de registrador exigem um
segundo operando registrador + o modificador (shift OU extend) — **decisão:
dois records novos**, não uma extensão de `Alu64` (evita um record com
campos mutuamente exclusivos "immediate xor (rm+shiftOrExtend)", que já é o
tipo de design que este projeto evita — ver como `Ir64Op.Load64`/`Store64`
já preferem campos dedicados por modo em vez de um union implícito, mas
mantêm um record só porque os 4 modos de endereçamento realmente
compartilham a maioria dos campos; aqui os dois modos de ALU-registrador têm
regras de `SP` E de tamanho de shift diferentes o bastante para merecer
records distintos):
```java
/// `ADD`/`SUB` na forma "shifted register" (`ARM DDI 0487 C6.2.4` variante
/// registrador). `Rd`/`Rn` NUNCA são `SP` nesta forma (D... ver Fatos de
/// referência #4) — ao contrário de {@link Alu64} (forma imediata) e de
/// {@link AluExtendedRegister}, não há campos `dstIsStackPointer`/
/// `src1IsStackPointer` aqui, porque o valor seria sempre `false`.
record AluShiftedRegister(
        Ir64AluOp opcode,       // só ADD/SUB (setFlags cobre ADDS/SUBS)
        int dst, int src1, int src2,
        Ir64ShiftType shiftType,  // LSL/LSR/ASR (novo enum — ROR não existe aqui)
        int shiftAmount,          // 0-63 (wide) / 0-31 (!wide) já validado no decode
        boolean wide, boolean setFlags) implements Ir64Op { ... }

/// `ADD`/`SUB` na forma "extended register". `Rn` é SEMPRE `Rn|SP`; `Rd` é
/// `Rd|SP` só quando `!setFlags` (mesma regra da forma imediata, ver
/// Fatos de referência #5); `Rm` NUNCA é `SP`.
record AluExtendedRegister(
        Ir64AluOp opcode, int dst, int src1, int src2,
        Ir64ExtendType extendType,  // reaproveita o enum de B6.2 (load/store)
        int shiftAmount,             // 0-4, já validado no decode
        boolean wide, boolean setFlags, boolean dstIsStackPointer) implements Ir64Op { ... }
```
`Ir64ExtendType` já existe (B6.2, `ir64/Ir64ExtendType.java`) com só as 4
combinações válidas para load/store (`UXTW`/`LSL`/`SXTW`/`SXTX`) — **a forma
`extended register` de ALU tem 8 combinações válidas** (byte/half/word/
doubleword × zero/sinal). Decisão: **não reaproveitar o enum de 4 valores**
— criar `Ir64ExtendType8` (ou renomear/ampliar; a task decide o nome ao
implementar, registrando a escolha) com os 8 valores (`UXTB`/`UXTH`/`UXTW`/
`UXTX`/`SXTB`/`SXTH`/`SXTW`/`SXTX`), já que o enum de 4 valores de B6.2 é
usado por `Load64`/`Store64`/`LoadStorePair` com um contrato documentado
("só as 4 combinações válidas para load/store de registrador geral") que
não deve ganhar 4 valores que load/store nunca produz. `Ir64ShiftType`
(novo, `LSL`/`LSR`/`ASR`) é só para `AluShiftedRegister` — não confundir com
o eventual shift type do `Logical (shifted register)` (fora de escopo,
tem ROR também, mas essa instrução nem está na lista fechada do épico).

## Objetivo

- `AND`/`ORR`/`EOR`/`ANDS` (imediato) — decode do campo `dbm` (`N:immr:imms`)
  via `DecodeBitMasks`, reaproveitando `Ir64Op.Alu64`/`Ir64AluOp` já
  existentes (D2).
- `ADD`/`SUB`/`ADDS`/`SUBS` (shifted register) — novo
  `Ir64Op.AluShiftedRegister` (D3).
- `ADD`/`SUB`/`ADDS`/`SUBS` (extended register) — novo
  `Ir64Op.AluExtendedRegister` (D3).
- Novo dispatch de classe top-level "Data Processing — Register" (D1),
  base para B6.3.2/B6.3.3.

## Especificação

1. **`DecodeBitMasks`**: implementar como método utilitário (`private
   static` em `Aarch64Decoder`, ou uma classe utilitária dedicada se ficar
   grande — decidir ao implementar) transcrevendo o algoritmo do item 3 dos
   Fatos de referência, com as constantes nomeadas (G6: nada de `0x3f`/`31`
   soltos sem nome — `ELEMENT_SIZE_FIELD_MASK`, etc.). Retorna algo como
   `OptionalLong`/um resultado com flag de "reservado" — decodificar
   reservado como `UnsupportedOperationException` (mesmo padrão de encoding
   fora de escopo, já que é tecnicamente UNDEFINED arquitetural, não uma
   feature fora da fatia — mas documentar a distinção no javadoc do método:
   é UNDEFINED de verdade, não "não implementado ainda").
2. **Decode do subgrupo `Logical (immediate)`** em
   `decodeDataProcessingImmediate`: novo `case 0b00` (constante
   `SUBGROUP_LOGICAL_IMMEDIATE`), usando o `opc` (bits30:29) para escolher
   `Ir64AluOp`, `DecodeBitMasks` para o imediato, `setFlags = (opc==0b11)`,
   `dstIsStackPointer=false`, `src1IsStackPointer=false` (D2). `N=1` com
   `sf=0` é UNDEFINED (Fatos de referência #2) — testar explicitamente.
3. **`isDataProcessingRegisterClass` + `decodeDataProcessingRegister`** (D1):
   esqueleto do método novo, só com os `case`s desta task; outros subgrupos
   (`CSEL`, `2-source`, `3-source`, `Logical (shifted register)` — este
   último fora de escopo do épico) caem em `unsupported` por enquanto.
4. **`AluShiftedRegister`/`AluExtendedRegister`** (D3): decode completo com
   as validações UNDEFINED do item 4/5 dos Fatos de referência (`st==0b11`
   reservado para shifted; `sa>4` reservado para extended; `!sf && sa
   bit5` reservado para shifted). Executor novo em `Ir64BlockExecutor`
   (reaproveitar `addWithFlags`/`subWithFlags` já existentes — só o cálculo
   do segundo operando muda: shift puro vs extend-then-shift).
5. **Corpus**: apêndice de `corpus.s`/`.bin`/`.objdump.txt` (mesmo padrão de
   B6.2) com vetores para os 4 opcodes lógicos (incluindo pelo menos um caso
   de elemento de 64 bits `N=1`, um de elemento pequeno como 2 ou 4 bits, e
   uma rotação não-trivial `immr≠0`) e para as duas formas de ALU-registrador
   (incluindo `lsl`/`lsr`/`asr` com quantidade não-zero, e as 8 combinações
   de extensão pelo menos uma vez cada, usando `sp` como `Rd`/`Rn` na forma
   `extended register` para provar a regra de D3).

## Armadilhas

- **`DecodeBitMasks` é o encoding mais traiçoeiro da ISA A64** (aviso do
  próprio épico) — não confiar na transcrição acima sem o property test
  contra uma segunda implementação independente (não o mesmo algoritmo
  reescrito, uma DERIVAÇÃO diferente, ex. a definição literal do manual
  "replicar um padrão de e bits" feita por concatenação de strings/loop
  simples, mesmo que ineficiente — só para o teste).
- **Shift de 64 bits em Java é UB por wraparound** (`1L << 64` não dá `0`,
  dá `1L` de novo — o operador de shift em Java só usa os 6 bits baixos do
  deslocamento) — todo lugar que o algoritmo do manual diz "máscara de N
  bits" com N podendo ser 64 precisa tratar esse caso à parte, não confiar
  em `(1L << n) - 1` funcionar para `n=64`.
- **`ANDS` (imediato) não é "AND com setFlags"** no sentido de C/V herdarem
  alguma lógica aritmética — são SEMPRE zero, resolvido pelo D2 acima
  reaproveitando `logicalWithFlags` já escrito; não reintroduzir um cálculo
  de carry/overflow por engano só porque `ADD`/`SUB` fazem isso.
- **`shifted register` e `extended register` são dois modos de operando
  DIFERENTES**, não uma generalização um do outro — não tentar unificá-los
  num único record "pra economizar código" (D3); as regras de `SP` e de
  validação de quantidade de shift são diferentes o bastante para que a
  tentativa de unificar geraria bugs sutis de UNDEFINED mal detectado.
- **`Logical (shifted register)` (`AND`/`ORR`/`EOR`/`ANDS`/`BIC`/`ORN`/
  `EON`/`BICS` com um SEGUNDO registrador, não imediato) NÃO está no escopo
  fechado do épico** (`b6-aarch64.md` só lista "logical imm" e "shifts/
  extends de registrador" — este último se refere às formas de ALU
  aritmética desta task, não à forma lógica-por-registrador, que tem seu
  próprio espaço de bits `st==0b11`→ROR e não aparece na tabela do épico).
  **Não implementar por conta própria** — ficaria com o mesmo formato de
  `AluShiftedRegister` menos os flags de carry/overflow (usa
  `logicalWithFlags`), mas decidir isso é escopo de uma spec futura, não
  desta. Se o corpus de teste real acabar produzindo esse encoding por
  acidente (ex. um assembler emitindo `bic` em vez de `and`+shift manual),
  isso é bug de teste, não motivo para expandir o escopo aqui.

  citados foram lidos do HEAD do master em 2026-07-24 (baixados via

# B11.7 — terceiro gate real de feature A64: `FEAT_FlagM` (`RMIF`/`SETF8`/`SETF16`)

**Trilha:** B · **Repo:** arm-jitter (+ revalidação G5 nos consumidores) · **Status:** ✅ fechada 2026-08-28
**Depende de:** B11.2 ✅ (fiação `Aarch64Architecture` no decoder), B11.3 ✅ (auditoria — confirmou
`RMIF`/`SETF8`/`SETF16` como `ARMv8.4-A`/`FEAT_FlagM`, já implementadas sem gate desde B8.2), B11.5 ✅
(`Aarch64Feature.FLAG_MANIPULATION` já existe e já está mapeada em `Aarch64Architecture.ARMV8_4_A`)

## Contexto

Terceira da escada de gate real iniciada por B11.4 (`FEAT_RDM`) e B11.6 (`FEAT_WFxT`). Como em B11.6,
o decoder DEFAULT (`ARMv8.0-A`) hoje aceita `RMIF`/`SETF8`/`SETF16` incondicionalmente — um
Cortex-A53 real (`ARMv8.0-A`) não tem `FEAT_FlagM` (introduzida em `ARMv8.4-A`), então o gate é o
comportamento correto, não uma restrição nova.

Esta é a candidata mais isolada das 8 restantes: vive inteiramente dentro de
`decodeAddSubtractCarryOrFlags` (`Aarch64Decoder.java:2238`), um método privado dedicado que já
distingue os 3 subgrupos (`ADC`/`SBC` vs `RMIF` vs `SETF8`/`SETF16`) por padrões de bits fixos
adicionais — sem colisão de `Ir64Op`/opcode com nenhuma outra instrução, sem reuso de switch
compartilhado (diferente do bloco `MSR (immediate)` de `PAN`/`UAO`/`DIT`/`ALLINT`, que divide um
`switch` só entre várias features).

## Achados de investigação (nesta sessão)

- `decodeAddSubtractCarryOrFlags` (`Aarch64Decoder.java:2238-2269`): o bloco `ADC`/`SBC`
  (`opcode2 == ADD_SUB_CARRY_OPCODE2_ADC_SBC`, linha 2243) retorna cedo e é baseline — não deve ser
  tocado. Os dois blocos seguintes (`RMIF`, linha 2251; `SETF8`/`SETF16`, linha 2259) são os únicos
  a gatear.
- Corpus real já existe em `src/test/resources/aarch64/corpus.bin` (devkitA64): offsets `0x59c`
  (`rmif`), `0x5a0` (`setf8`), `0x5a4` (`setf16`) — usados hoje por
  `Aarch64DecoderCorpusTest#rmif`/`#setf8`/`#setf16` no `DECODER` default. Não precisa gerar corpus
  novo.
- Testes existentes que quebram com o gate:
  - `Aarch64DecoderCorpusTest#rmif`/`#setf8`/`#setf16` (usam o `DECODER` default, esperam sucesso)
    — passam a esperar `UnsupportedOperationException`; a decodificação bem-sucedida migra para o
    teste novo dedicado.
  - `Ir64BlockExecutorB82Test` (testes de `RotateIntoFlags`/`EvaluateIntoFlags`) **NÃO precisa
    mudar**: constrói os `Ir64Op` diretamente, sem passar pelo decoder — ortogonal ao gate.

## Inclui

1. `Aarch64Decoder#decodeAddSubtractCarryOrFlags`: os blocos `RMIF` (linha ~2251) e `SETF8`/`SETF16`
   (linha ~2259) só decodificam quando `architecture.has(Aarch64Feature.FLAG_MANIPULATION)` —
   caso contrário, cai no `throw unsupported(word, address)` final do método (mesmo padrão de
   G8/B11.4/B11.6: nunca silenciosamente confundir com outra instrução). O bloco `ADC`/`SBC`
   permanece incondicional.
2. Atualizar `Aarch64DecoderCorpusTest#rmif`/`#setf8`/`#setf16` para esperar
   `UnsupportedOperationException` no `DECODER` default (`ARMv8.0-A`).
3. Teste novo `Aarch64FlagManipulationDecoderTest` (mesmo padrão de `Aarch64AdvSimdWfxtDecoderTest`):
   decoder default rejeita as 3 palavras do corpus real (`0x59c`/`0x5a0`/`0x5a4`); decoder
   `Aarch64Architecture.ARMV8_4_A` decodifica os 3 corretamente (`RMIF`→`RotateIntoFlags`,
   `SETF8`/`SETF16`→`EvaluateIntoFlags`), com as mesmas asserções de campo que
   `Aarch64DecoderCorpusTest` já validava.
4. `mvn -o test` verde + `mvn -o install`; G5 nos 5 consumidores (nenhum usa `ARMV8_4_A`+ — zero-diff
   esperado, já que `RMIF`/`SETF8`/`SETF16` não são emitidas por toolchains alvo de `ARMv8.0-A`/
   raspi3).

## Não inclui

- Qualquer outra das 7 features restantes (`LSE`/`PAN`/`SHA3`/`UAO`/`DIT`/`FLAG_MANIPULATION_2`/
  `NMI`) — cada uma vira sua própria task `B11.x`. **Atenção**: `LSE` continua precisando de checagem
  extra de consumidor real antes de ser pega (ver Resultado de B11.6).
- Mudar `Aarch64Feature`/`Aarch64Architecture` (já existem desde B11.1/B11.5 —
  `FLAG_MANIPULATION` já mapeada em `ARMV8_4_A`).
- `docs/COBERTURA-ISA.md` (o medidor por versão já reflete `RMIF`/`SETF8`/`SETF16` corretamente desde
  B11.5 — gatear o decoder não muda o que o medidor já reportava para a coluna `ARMv8.4-A`+).

## Armadilhas

- Não tocar no bloco `ADC`/`SBC` (`opcode2 == ADD_SUB_CARRY_OPCODE2_ADC_SBC`) — é baseline
  `ARMv8.0-A`, sem feature associada.
- `RMIF` e `SETF8`/`SETF16` são discriminados por padrões de bits adicionais (`sf`/`opc`/campos
  fixos), não só por `opcode2` — a ordem de checagem existente (ADC/SBC cedo, depois RMIF, depois
  SETF) precisa ser preservada; o gate entra DENTRO de cada bloco já identificado, não antes da
  distinção.

## Resultado (2026-08-28)

Implementado exatamente como especificado, sem desvio:

- `Aarch64Decoder#decodeAddSubtractCarryOrFlags`: os dois blocos `RMIF` e `SETF8`/`SETF16` agora
  começam com `if (!architecture.has(Aarch64Feature.FLAG_MANIPULATION)) throw unsupported(word,
  address);` antes de montar o `Ir64Op` — o bloco `ADC`/`SBC` (baseline) intocado.
- `Aarch64DecoderCorpusTest#rmif`/`#setf8`/`#setf16`: as 3 agora esperam
  `UnsupportedOperationException` no `DECODER` default, com comentário citando esta task.
- `Aarch64FlagManipulationDecoderTest` novo (4 testes): default rejeita as 3 palavras do corpus real
  (`0xba020405`=`rmif x0,#4,#5` offset `0x59c`, `0x3a00082d`=`setf8 w1` offset `0x5a0`,
  `0x3a00484d`=`setf16 w2` offset `0x5a4`); `ARMV8_4_A` decodifica os 3 corretamente com os mesmos
  campos que `Aarch64DecoderCorpusTest` validava antes.
- `mvn -o test` verde (core+truffle, 473 testes no core) + `mvn -o install`; G5 completo nos 5
  consumidores (`gbaemu`/`ndsemu`/`armbox`/`virtual-arm-box`/`n3dsemu`, todos `BUILD SUCCESS`,
  zero-diff esperado e confirmado — nenhum usa `ARMV8_4_A`+, e nenhum binário-alvo de `ARMv8.0-A`
  emite `RMIF`/`SETF8`/`SETF16`). Sem mudança em `docs/COBERTURA-ISA.md` (o medidor por versão, desde
  B11.5, já classificava `RMIF`/`SETF8`/`SETF16` como `ARMv8.4-A`; gatear o decoder não muda o que já
  era medido).
- **Próximo da escada B11, não pego automaticamente**: gatear qualquer uma das 7 features restantes
  (`LSE`/`PAN`/`SHA3`/`UAO`/`DIT`/`FLAG_MANIPULATION_2`/`NMI`), mesmo padrão desta task. `LSE`
  continua precisando de checagem extra de consumidor real antes de ser pega (ver Resultado de

# B13.3 — NEON load/store (A32): `VLD1`-`VLD4` / `VST1`-`VST4`

**Trilha:** B · **Repo:** arm-jitter (+ revalidação G5 nos consumidores) · **Depende de:** B13.1, B13.2
**Épico:** `b13-plano-neon-a32.md` · **Status:** ⬜

## Contexto

Primeira família de encodings do épico B13 depois da fundação (B13.1, banco `D0`-`D31`/`Q0`-`Q15`) e
da RFC (B13.2). São os **5 encodings de `neon-ls.decode`** — o grupo inteiro de load/store de NEON,
que hoje aparece a 0% (`NOT_IN_ANY_PRESET`) em `docs/COBERTURA-ISA.md`:

| Linha do `.decode` | Instruções reais | Encodings |
|---|---|---:|
| `VLDST_multiple` | `VLD1`-`VLD4`/`VST1`-`VST4`, estruturas MÚLTIPLAS | 1 |
| `VLD_all_lanes` | `VLD1R`-`VLD4R` (um elemento replicado por todas as lanes) | 1 |
| `VLDST_single` | `VLD1`-`VLD4`/`VST1`-`VST4` de UMA lane (3 linhas: `size`=byte/halfword/word) | 3 |

**Leitura obrigatória antes de começar**: `docs/RFC-NEON-NUCLEO-VETORIAL.md` (B13.2) inteira. Ela
decide como cada família se implementa daqui em diante — em particular que o acesso a lane usa a
vista PLANA de palavras de 64 bits (`advsimd/AdvSimdLanes#element`/`setElement` com
`baseWord = índice de D`), e que o decoder vetorial entrega o `IrOp` PRONTO pelo escape hatch
`DecodedInstruction#liftedOp` (`InstructionKind.LIFTED_IR_OP`), nunca espremendo a forma do operando
nos campos neutros do record.

Espelho estrutural do que a **B8.6** fez do lado A64 (`Ir64Op.VectorLoadStoreMultiple`/
`VectorLoadStoreSingle`/`VectorLoadSingleReplicate` + os `executeVectorLoadStore*` de
`Ir64BlockExecutor`) — mas **não é um espelho literal**: ver "Diferenças reais entre o A64 e o NEON
de 32 bits" abaixo, que é onde esta task pode dar errado em silêncio.

## Objetivo

Decodificar e executar as 5 linhas de `neon-ls.decode` no encoding **A32**, gateadas por
`ArmFeature.ADVANCED_SIMD` — que nenhum preset declara, portanto **zero-diff de runtime** nos 5
consumidores e `docs/COBERTURA-ISA.md` byte a byte idêntica ao fim da task.

## Inclui

1. **`decoder/NeonLoadStoreDecoder`** (novo, `DecoderExtension`) — espaço
   `1111 0100 xxx0 xxxx ...`, irmão do `NeonDataProcessingDecoder` de B13.2.
2. **3 records novos em `ir/IrOp`** (+ `Kind` + `permits`): `NeonLoadStoreMultiple`,
   `NeonLoadStoreSingle`, `NeonLoadAllLanes`.
3. **`codegen/executor/IrNeonExecutor`** (novo) com a execução das três formas; o
   `executeNeonThreeSame` que a B13.2 deixou provisoriamente em `IrVfpExecutor` **passa a delegar**
   a ele (o método público continua existindo — G3).
4. **Acesso de elemento em memória sem o quirk ARM7** — ver "Especificação / memória".
5. Dispatch: os 3 `Kind` novos nos DOIS `switch` de `IrBlockExecutor` e em `AsmNativePolicy`
   (interpretado, `false`, como todo `Kind` vetorial desde B8.4).
6. Testes: encoding (vetores conferidos contra assembler real), decode, UNDEFINED de cada caso
   inválido, execução (incluindo entrelaçamento, `stride`, writeback e replicação) e prova de
   zero-diff sem a feature.

## Não inclui

- **T32** (encoding Thumb-2 `1111 1001 xxx0 ...`): é a B13.16, que transforma e delega para o mesmo
  decoder — não antecipar.
- Qualquer família de processamento de dados (B13.4+).
- Preset declarando `ADVANCED_SIMD` (é a B13.22 que faz o grupo sair de `NOT_IN_ANY_PRESET`).
- Emissão ASM/JIT nativa (achado 2 da RFC).
- Corrigir o backend Truffle (achado 1 da RFC) — ver "Não fazer".

## Especificação

### Encoding (oráculo: QEMU `target/arm/tcg/neon-ls.decode` + `translate-neon.c`; ARM DDI 0406C A7.7)

Espaço comum: `1111 0100 ...`. `bit21` (`.` depois do `0100 x`) é o `D` do registrador
(`vd = D:Vd`, mesma convenção de precisão dupla do `VfpDecoder`).

```
VLDST_multiple 1111 0100 0 D l 0 rn:4 vd:4 itype:4 size:2 align:2 rm:4
VLD_all_lanes  1111 0100 1 D 1 0 rn:4 vd:4 11 n:2 size:2 t a  rm:4
VLDST_single   1111 0100 1 D l 0 rn:4 vd:4 00 n:2 reg_idx:3 align   rm:4   (size=0, stride=1)
VLDST_single   1111 0100 1 D l 0 rn:4 vd:4 01 n:2 reg_idx:2 . align rm:4   (size=1, stride=bit5+1)
VLDST_single   1111 0100 1 D l 0 rn:4 vd:4 10 n:2 reg_idx:1 . align:2 rm:4 (size=2, stride=bit6+1)
```

`l` = load (`1`) / store (`0`). `n` = `selem - 1` (quantos registradores formam uma estrutura).

**Tabela de `itype` de `VLDST_multiple`** (`neon_ls_element_type` do QEMU, índice `0`-`10`;
qualquer `itype > 10` é **UNDEFINED**):

| `itype` | nregs (repetições) | interleave (`n` de `VLDn`) | spacing (stride) |
|---:|---:|---:|---:|
| 0 | 1 | 4 | 1 |
| 1 | 1 | 4 | 2 |
| 2 | 4 | 1 | 1 |
| 3 | 4 | 1 | 2 |
| 4 | 1 | 3 | 1 |
| 5 | 1 | 3 | 2 |
| 6 | 3 | 1 | 1 |
| 7 | 1 | 1 | 1 |
| 8 | 1 | 2 | 1 |
| 9 | 1 | 2 | 2 |
| 10 | 2 | 1 | 1 |

`size == 3` (doubleword) só é válido quando `interleave == 1 && spacing == 1`.

### Endereçamento e writeback (`rm`) — regra NEON, diferente de tudo que já existe no repo

| `rm` | Efeito |
|---|---|
| `0b1111` (15) | **sem** writeback |
| `0b1101` (13) | writeback IMEDIATO: `Rn += número de bytes transferidos` |
| qualquer outro | writeback por REGISTRADOR: `Rn += R[rm]` |

`Rn == 15` (PC) é UNPREDICTABLE no hardware → **UNDEFINED** aqui (mesma disciplina de
`exclusiveRegistersValid` em `ArmDecoder`). O writeback acontece **depois** de toda a transferência.

### Faixa de registradores

Todos os índices são de **`D`** (`0`-`31`), não de `Q` — é assim que o encoding NEON nomeia. O
último registrador tocado é `vd + (regsTocados - 1) * stride`; se passar de `31`, é **UNDEFINED**
(NEON de 32 bits NÃO faz wrap-around módulo 32, ao contrário do A64 — ver Armadilhas).

### IR

Três records em `ir/IrOp`, espelhando a forma dos de `Ir64Op` (mesmos nomes de componente onde a
semântica é a mesma), com os campos extras que o A32 exige:

- `NeonLoadStoreMultiple(boolean load, int vd, int rn, int rm, int esz, int nregs, int interleave,
  int stride)`
- `NeonLoadStoreSingle(boolean load, int vd, int rn, int rm, int esz, int selem, int stride,
  int index)`
- `NeonLoadAllLanes(int vd, int rn, int rm, int esz, int selem, int stride, boolean quad)`

`rm` carrega o campo CRU do encoding (`15` = sem writeback, `13` = imediato) — resolver essa
convenção no decoder duplicaria a informação; documentar no Javadoc do record. Condição: NEON é
sempre incondicional, todos com `Condition.AL` (o record herda o default de `IrOp`).

### Execução

Laço espelhando `Ir64BlockExecutor#executeVectorLoadStoreMultiple`, com a lane lida/escrita por
`AdvSimdLanes.element`/`setElement` usando `baseWord = índice do D` (RFC D1). Ordem dos acessos =
ordem crescente de endereço, um elemento por vez, avançando `1 << esz` bytes.

- **`VLDST_multiple`**: para `r` em `0..nregs`, `e` em `0..elementosPorD`, `xs` em `0..interleave`:
  registrador `vd + (r + xs) * stride`, elemento `e`. `elementosPorD = 8 >> esz` (a unidade aqui é
  o `D`, sempre 64 bits — não existe forma de 128 bits neste encoding; o que existe é transferir
  vários `D`).
- **`VLDST_single`**: um elemento no índice `index` de cada um dos `selem` registradores
  `vd + xs * stride`, sem tocar nenhum outro bit.
- **`VLD_all_lanes`**: lê um elemento por registrador e replica por todas as lanes de `D` (ou dos
  dois `D` do par, quando `quad`), usando `AdvSimdLanes.setElement` lane a lane.

Store: chamar `core.notifyOrdinaryWrite(address, bytes)` por elemento escrito, como o A64 faz —
sem isso, código automodificável não invalida bloco de JIT (o bug que já custou uma sessão em
`gbaemu`, ver memória `gba-game-compat`).

### Memória: **não** usar `read32Arm7`/`read16Arm7`

`IrExecutionSupport#read32Arm7`/`read16Arm7` aplicam a ROTAÇÃO de acesso desalinhado do ARM7
(quirk ARMv4T) — semântica errada para elemento NEON, que nunca rotaciona. Acrescentar em
`IrExecutionSupport` um par de helpers de elemento vetorial (`readVectorElement(core, address,
esz)` / `writeVectorElement(core, address, esz, value)`) que:

1. usam `read8`/`read16`/`read32` do `AddressSpace` diretamente quando o endereço está alinhado ao
   tamanho do elemento (doubleword = dois acessos de 32 bits consecutivos, baixo primeiro);
2. compõem/decompõem byte a byte, little-endian, quando genuinamente desalinhado;
3. contabilizam ciclos (`core.addMemoryCycles`) igual aos helpers existentes;
4. aplicam a mesma regra de endianness de dados (`applyDataEndianness*`) que o caminho VFP usa —
   byte é invariante por definição (BE8, ver Javadoc de `read8Arm7`).

O item 1 não é otimização: decompor um acesso alinhado em `read8` quebra periférico MMIO com
registrador esparso — é o achado real da F3 documentado no Javadoc de `readWordForLoad`, e vale
igual aqui.

### Gating e G8

Gate único `ArmFeature.ADVANCED_SIMD`. Sem a feature, `tryDecode` devolve `null` (o espaço volta a
cair no `UNIMPLEMENTED` de `ArmDecoder#decodeUnconditional`, comportamento idêntico ao de hoje).
**Com** a feature, todo sub-encoding do espaço `1111 0100 xxx0` que esta task não reconhece tem que
virar `DecodedInstruction.unimplemented` EXPLÍCITO — nunca `null`, nunca outra instrução (G8).

## Armadilhas

### Diferenças reais entre o A64 e o NEON de 32 bits (é aqui que espelhar cegamente quebra)

1. **`stride`/"double spacing" não existe no A64.** O A64 sempre usa registradores CONSECUTIVOS
   (`Vt`, `Vt+1`, ...); o NEON de 32 bits tem formas com espaçamento 2 (`D0`, `D2`, `D4`, ...). O
   laço de `Ir64BlockExecutor` não tem esse fator — copiá-lo sem o `stride` produz transferência
   para o registrador errado, sem erro nenhum.
2. **Sem wrap-around módulo 32.** O A64 faz `(rt + r + xs) % 32` (arquitetural lá); no A32,
   ultrapassar `D31` é UNDEFINED. Copiar o `%` esconde um encoding inválido em vez de recusá-lo (G8).
3. **Sem escrita destrutiva.** O A64 zera os bits altos do `V` quando o arranjo é de 64 bits; o
   VFP32 nunca escreve fora do registrador nomeado (documentado no Javadoc de `VfpRegisters`, e é a
   decisão D1 da RFC). Não portar o `finishDestructiveWrite`.
4. **A unidade é o `D`, não o `Q`.** O encoding conta registradores `D`; não existe bit `Q` aqui
   (o `quad` de `VLD_all_lanes` é o bit `t`, que significa "replica em DOIS `D`", e ainda assim são
   dois `D` nomeados por `stride`, não um `Q`).

### Outras

5. **`VLD_all_lanes` com `size == 3` tem tratamento ESPECIAL** e não é simétrico com
   `VLDST_multiple` — conferir `trans_VLD_all_lanes` no `translate-neon.c` real antes de assumir
   que é UNDEFINED. Não deduzir por simetria.
6. **`align` não é enfeite**: certos valores são UNDEFINED por encoding (a validação depende de
   `itype`/`size`/`n`). Conferir caso a caso no oráculo; o que esta task NÃO faz é FALHAR por
   desalinhamento em tempo de execução (`SCTLR.A` não é modelado) — decodificar o campo, recusar os
   valores inválidos, e tratar o resto como hint.
7. **`rm = 13` é `SP` como número, mas NÃO é o `SP` como registrador** — é o código de "writeback
   imediato". Ler `R13` aqui é bug silencioso que só aparece em código que usa `SP` de verdade.
8. **Os 3 `Kind` novos vão quebrar o backend Truffle** se algum dia um preset declarar
   `ADVANCED_SIMD` — é o achado 1 da RFC (`IrOpNodeFactory` não cobre nem os `Kind` de VFP e
   `TruffleCodeEmitter#supports` devolve `true` sempre). Esta task só ACRESCENTA os novos `Kind` à
   lista do achado na RFC; consertar é task própria.

## Não fazer

- Não "aproveitar" para implementar T32 (B13.16), nem nenhuma família de dados (B13.4+).
- Não mexer em `IrOpNodeFactory`/`TruffleCodeEmitter` (achado 1 da RFC, task própria).
- Não implementar abort no meio da transferência com restauração de base — o pipeline de 32 bits
  já trata abort de `LDM`/`STM` com semântica base-restored no `IrTransferExecutor`, e replicar
  isso para NEON exige decisão própria (o hardware NEON tem regras próprias sobre o que já foi
  escrito). Se aparecer necessidade, PARE e reporte em vez de improvisar.
- Não declarar `ADVANCED_SIMD` em nenhum preset.

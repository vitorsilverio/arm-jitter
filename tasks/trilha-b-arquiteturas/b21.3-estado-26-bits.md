## Contexto

O plano mestre resume o que muda: `R15` = `[31:28]` `N`/`Z`/`C`/`V`, `[27:26]` `I`/`F`, `[25:2]` PC
(26 bits de endereço, 64 MiB), `[1:0]` modo (`USR`/`FIQ`/`IRQ`/`SVC`). Não existe `CPSR` separado,
não existe `SPSR`. São **4 modos**, não 7 — sem `ABT`/`UND`/`SYS`, e sem banco de registradores para
eles (`ABT`/`UND` entram em `SVC` nas versões que não têm modo próprio — isso é B21.4).

Hoje, no código real, os pontos onde um `R15` de 26 bits seria observado estão **todos concentrados
em `IrExecutionSupport`** (medido nesta rodada, `core/src/main/java/dev/vitorsilverio/armjitter/
codegen/executor/IrExecutionSupport.java`):

| Ponto | Linha | Papel no modelo de 26 bits |
|---|---|---|
| `registerValue(core, register, valueOverride)` | 36-42 | **leitura** de `R15` como operando: hoje devolve o `valueOverride` (o `address+8` que o lifter já calculou). É aqui (ou onde o override é calculado) que os bits de PSR têm que entrar junto |
| `writeLoadedRegister` | 54-60 | `LDR`/`LDM` com `R15` no destino |
| `loadToPc` | 62-73 | idem, já com gate de `LOAD_PC_INTERWORKING` e o intercept de `ExceptionModel` (B7.2) |
| `writeAluDestination(core, register, value, restoreSpsr)` | 75-87 | **`Rd = R15`** em data-processing, com `restoreSpsr` = o bit `S`. **É literalmente o ponto do `MOVS PC, R14`** |
| `alignAndSetPc` | 89-92 | máscara de alinhamento (`~1`/`~3`) — o lugar natural da máscara de 26 bits (B21.5) |

Isso é uma boa notícia para o custo: a opção (c) precisa de gate em **5 métodos de um arquivo**, não
espalhado pelo projeto. `ArmCore.registers[]`/`cpsr` ficam intocados, o formato de save state fica
intocado, o cache de registradores da trilha C fica intocado.

## Objetivo

Um `ArmCore` configurado para 26 bits (preset `ARMV1`/`ARMV2`/`ARMV2A` da B21.2, ou um `ARMV3` com
`prog32` desligado) executa com a semântica real de `R15`:

- ler `R15` como operando traz PC+8 **com os bits de PSR juntos** (e o "bug clássico" de usá-lo como
  endereço sem mascarar é **reproduzido**, não consertado);
- escrever `R15` sem `S` altera **só os bits de PC**, preservando flags/máscaras/modo;
- escrever `R15` com `S` em modo privilegiado altera **tudo** (é o retorno de exceção — B21.4);
- escrever `R15` com `S` em modo **usuário** altera só PC e flags, **nunca** `I`/`F`/modo;
- existem 4 modos, e o banco de registradores é o reduzido (`USR`/`FIQ`/`IRQ`/`SVC`).

E o caminho de 32 bits continua **bit a bit e ciclo a ciclo idêntico** (G3).

## Inclui

1. **`CpuMode` ganha 4 constantes**: `USER26` (`0b00000`), `FIQ26` (`0b00001`), `IRQ26` (`0b00010`),
   `SUPERVISOR26` (`0b00011`) — **acrescentadas NO FIM do enum** (Armadilha 1, a mais perigosa do
   épico). Os 4 valores estão livres na tabela `BY_BITS` hoje (medido).
2. **`Arm26ProgramStatus`** (classe nova, `core/`, sem estado, só constantes nomeadas + estáticos —
   G6): `PC_MASK = 0x03FF_FFFC`, `FLAGS_MASK = 0xF000_0000`, `IRQ_DISABLE_BIT = 1 << 27`,
   `FIQ_DISABLE_BIT = 1 << 26`, `MODE_MASK = 0b11`, mais `compose(ArmCore)` → `int r15` e
   `applyToCore(ArmCore, int r15, boolean privileged)`.
3. **O estado "este core está em 26 bits"**, conforme a RFC decidir: campo do core ou do modelo
   instalado, **resolvido em lift-time** pelo `StandardIrBlockLifter`/codegen, nunca consultado por
   acesso a registrador (é a condição que torna a opção (c) gratuita — Armadilha 2).
4. **Os 5 pontos de `IrExecutionSupport`** gateados por esse estado, mais o ponto onde o lifter
   calcula o `valueOverride` de `R15` (leitura PC+8) — ver Especificação.
5. **Banco reduzido**: `switchMode`/`saveBank`/`restoreBank`/`spLrBank` passam a aceitar os 4 modos
   novos, mapeando `FIQ26`→banco FIQ (R8-R14), `IRQ26`/`SUPERVISOR26`→bancos SP/LR próprios,
   `USER26`→banco usr/sys. **Reuso dos bancos existentes**, não bancos novos (Armadilha 5).
6. Testes (ver Aceite), incluindo **`BlockEquivalenceHarness`** (G1) — o modelo de 26 bits é um
   backend como qualquer outro perante o oráculo interpretado.

## Não inclui

- **Entrada/retorno de exceção, vetores, `ABT`/`UND` caindo em `SVC`** — **B21.4** (depende desta).
  Esta task entrega a *representação*; a B21.4 entrega o *fluxo de exceção* que a usa. A única
  exceção deliberada: `writeAluDestination` com `S`+`Rd=R15` (o `MOVS PC,R14`) precisa **já** ter a
  semântica certa aqui, porque é uma instrução comum de data-processing, não um mecanismo de
  exceção — mas o *vetor* e a *entrada* ficam para B21.4.
- **A máscara/wrap de 26 bits do espaço de endereço e o Address Exception** — **B21.5**.
- **Presets/features** — B21.2 (dependência de fato: sem `ARMV1`… não há como testar; ver Passos).
- **`SCTLR.P`/`prog32` dinâmico via CP15** — task própria, conforme a RFC B21.1 decidir.
- Emissão nativa/Truffle: **decode + interpretado apenas**. ⚠️ Mas ver Armadilha 3 — "não incluir"
  não pode virar "o backend ASM executa 26 bits com semântica de 32 bits em silêncio".

### As regras de `R15` (a confirmar no DDI 0100 — esta é a parte mais incerta da spec)

O que as fontes secundárias sustentam:

- `R15` = PC (26 bits) + PSR nos bits altos e nos 2 baixos
  ([26-bit computing](https://en.wikipedia.org/wiki/26-bit_computing),
  [Assembler Ch.3](http://www.riscos.com/support/developers/asm/cpu.html)).
- `MOVS PC, R14` restaura os flags automaticamente no retorno, e **"o bit `S` só deve ser setado se
  a instrução for executar em modo privilegiado"** ([Assembler Ch.3], seção de retorno de exceção) —
  ou seja, em modo usuário o `S` com `Rd=PC` **não** restaura `I`/`F`/modo.

O que **precisa** ser confirmado no DDI 0100 antes de codar, porque muda o código:

1. Quando `R15` é lido como **operando** (`Rm`/`Rn`) de data-processing, os bits de PSR vêm junto?
   (a evidência aponta que sim — é a origem do "bug clássico"); e quando `R15` é a **base de
   endereço** de um `LDR`/`STR`, os bits de PSR são tratados como zero?
2. Uma escrita em `R15` **sem** `S` altera só `[25:2]`, preservando PSR? (evidência: sim.)
3. Uma escrita em `R15` **com** `S` em modo usuário altera flags mas não `I`/`F`/modo? (evidência:
   sim, pela citação acima — mas é exatamente o tipo de regra que merece a fonte normativa.)
4. `LDM` com `R15` na lista e o sufixo `^`: carrega também os bits de PSR?
5. `MUL`/`MLA` com `Rd=R15` — UNPREDICTABLE, ou definido?

**Registrar no `## Resultado` a resposta de cada um dos 5 pontos, com a referência.** Se algum ficar
sem fonte, implementar o comportamento mais conservador E documentar a incerteza no Javadoc, em vez
de escolher em silêncio (mesma disciplina das duas incertezas registradas na B20.3).

### Onde o gate entra (opção (c))

- **Lift-time**: o lifter/codegen já recebe a `ArmArchitecture`. O estado 26/32 vira um booleano
  resolvido uma vez por bloco. Nenhum `if` novo no caminho de 32 bits em runtime.
- **`registerValue`/override de `R15`**: sob 26 bits, o valor lido de `R15` é
  `Arm26ProgramStatus.compose(core)` com o PC já somado de 8 — **não** o PC cru.
- **`writeAluDestination`**: sob 26 bits, o parâmetro `restoreSpsr` (o bit `S`) deixa de significar
  "restaura do SPSR" e passa a significar "aplica os bits de PSR do próprio valor escrito",
  filtrado por privilégio. **Renomear ou documentar** — um parâmetro chamado `restoreSpsr` que não
  lê SPSR nenhum é a receita da armadilha do plano mestre ("`MOVS PC,R14` é retorno de exceção, não
  um `MOV` com flags").
- **`alignAndSetPc`**: sob 26 bits a máscara é `PC_MASK` (`0x03FF_FFFC`), não `~3` — mas o
  comportamento de endereços ACIMA de 64 MiB é **B21.5**, não aqui. Aqui só o mascaramento.

## Aceite

- Sob `ARMV2` em 26 bits: `MOV R0, PC` deixa em `R0` o PC+8 **com** os bits de PSR; `MOV PC, R0`
  (sem `S`) altera só os bits `[25:2]`; `MOVS PC, R14` em modo privilegiado restaura flags, `I`/`F`
  e modo; o mesmo `MOVS PC, R14` em `USER26` restaura só PC e flags.
- `CpuMode` tem as 4 constantes novas, **no fim**, e um teste trava os ordinais de todas as 9
  antigas (`USER.ordinal() == 0` … `MONITOR.ordinal() == 8`).
- Um save state gravado ANTES desta task carrega corretamente DEPOIS dela (teste de round-trip com
  bytes fixos, não regravados na hora).
- `switchMode(FIQ26)` banca R8-R14 como o `FIQ` de 32 bits; `IRQ26`/`SUPERVISOR26` bancam SP/LR.
- **Caminho de 32 bits inalterado**: suíte completa verde, `docs/COBERTURA-ISA.md` byte-idêntica,
  G5 verde nos 5 consumidores.
- `BlockEquivalenceHarness` verde para um bloco que lê e escreve `R15` sob 26 bits (G1) — **ou**, se
  o backend ASM não suportar 26 bits nesta task, uma recusa explícita (Armadilha 3), nunca execução
  silenciosa com semântica errada.
- As 5 perguntas do DDI 0100 estão respondidas e citadas no `## Resultado`.

## Armadilhas

1. **`CpuMode` é serializado por `ordinal()`** (`ArmCore.saveState` linha 170, `loadState` 209).
   Inserir as constantes de 26 bits no MEIO do enum — que é onde elas "deveriam" ficar pela ordem
   numérica dos bits — **corrompe silenciosamente todo save state existente** do gbaemu/ndsemu/
   n3dsemu: um `IRQ` viraria `SUPERVISOR`. **No fim do enum, sempre.** Compila, passa nos testes de
   unidade, e quebra o save state do usuário — a pior classe de bug G3 do projeto.
2. **O gate tem que ser lift-time.** Um `if (core.is26Bit())` dentro de `registerValue` ou
   `alignAndSetPc` é um branch novo no caminho quente de 5 consumidores. Se a execução descobrir que
   isso é inevitável (porque o estado pode mudar no meio de um bloco), **volte à RFC B21.1**: essa é
   exatamente a condição que a Armadilha 1 de lá manda reavaliar.
3. **"Não inclui emissão nativa" não pode virar corrupção silenciosa.** Os backends ASM/Truffle leem
   `registers[]` direto e não passam por `IrExecutionSupport`. Se um core de 26 bits for executado
   pelo backend ASM sem suporte, o resultado não é "mais lento", é **estado errado** (G1 violado).
   A task tem que fechar isso explicitamente: ou `AsmNativePolicy` recusa blocos sob 26 bits
   (padrão de NEON/`NOCP`, o caminho barato), ou o suporte entra junto. Escolher e **testar a
   recusa**, não presumi-la.
4. **`MOVS PC, R14` não é um `MOV` com flags** (plano mestre). O parâmetro se chama `restoreSpsr` e,
   em 26 bits, não existe SPSR nenhum — é o próprio valor escrito que carrega o PSR. Mesma classe
   da armadilha que a B9.11 achou no alias `SUBS PC,LR,#imm`.
5. **Não criar bancos de registrador novos.** Os 4 modos de 26 bits mapeiam nos bancos que já
   existem (`fiqR8ToR14`, `irqSpLr`, `supervisorSpLr`, `userSystemSpLr`). Criar `fiq26SpLr` etc.
   duplicaria estado e quebraria o save state (que grava os arrays por nome/ordem).
6. **`CpuMode.fromBits` lança para bits desconhecidos** e roda por instrução/bloco
   (`synchronizeModeFromCpsr`). Antes desta task, qualquer CPSR com modo `0b000xx` **explode** — o
   que é bom (G8), mas significa que nenhum teste de 26 bits é possível antes do passo 4.
7. **Reproduzir o bug, não consertá-lo** (plano mestre): "ler `R15` para usar como endereço sem
   mascarar é o bug clássico do código de 26 bits". Nenhuma normalização defensiva de `R15` na
   composição — o emulador tem que se comportar como o hardware.
8. **`CpuSnapshot` pode precisar do estado 26/32** para o harness de equivalência distinguir dois
   cores. Medir antes de decidir; se precisar, é mudança em `codegen/equivalence/` (G1), não opcional.
9. **Os `switch` exaustivos sobre `CpuMode`** (`ArmCore.spsr`, `setSpsr`, `spLrBank`;
   `AProfileExceptionModel`) quebram a compilação ao ganhar constantes novas. Isso é **desejável**
   (erro em tempo de compilação). Resolver cada um com o `case` CERTO, nunca com um `default`
   genérico que engole o modo novo — `default` aqui é a porta para corrupção silenciosa.
10. **`spsr(USER26)`/`setSpsr(USER26)` não existem** (não há SPSR em 26 bits). Lançar
    `IllegalArgumentException` como já se faz para `USER`/`SYSTEM`, para os 4 modos novos.

## Não fazer

- Não começar antes de a RFC B21.1 estar decidida pelo usuário.
- Não implementar vetores/entrada de exceção (B21.4) nem o wrap/Address Exception (B21.5).
- Não mexer no layout de `registers[]`/`cpsr` nem no formato de save state.
- Não inserir constantes no meio de `CpuMode`.
- Não "consertar" a leitura de `R15` mascarando os bits de PSR por conta própria.
- Não deixar o backend ASM executar 26 bits sem suporte e sem recusa (G1/G8).

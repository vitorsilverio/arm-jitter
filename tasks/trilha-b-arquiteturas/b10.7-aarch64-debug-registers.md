# B10.7 — AArch64: registradores de debug (`op0=2`)

**Trilha:** B · **Depende de:** — (independente) · **Repo:** arm-jitter

## Contexto

Sétima task da escada B10 (`b10-plano-el2-el3.md`), a única sem dependência de outra task desta
escada — pode entrar a qualquer momento (ordem sugerida do plano mestre). B8.3 deixou os
registradores de debug (`MRS`/`MSR` com `op0=2`) explicitamente de fora, "documentado" — o
precedente que criou o épico B10 inteiro (ver `b10-plano-el2-el3.md`, "Por que isso apareceu
agora") proíbe esse tipo de adiamento sem implementar.

Sem debugger de hardware conectado a este emulador, a meta aqui NÃO é implementar a semântica real
de breakpoint/watchpoint (parar a CPU) — é fazer o guest (ex.: o handshake de debug do kernel Linux
real em `head.S`/`kgdb`, ou bibliotecas que sondam a presença de debug arquitetural) conseguir ler
e escrever esses registradores sem o emulador rejeitar a instrução (`UnsupportedOperationException`
hoje, via `unsupported(word, address)` do decoder).

## Inclui

Decodificar e armazenar (leitura devolve exatamente o que foi escrito, ou uma constante fixa
plausível — sem side effect real, mesma disciplina de B10.2/B10.3) os seguintes registradores,
todos `op0=2,op1=0`:

| Registrador | CRn | CRm | op2 | Fonte |
|---|---|---|---|---|
| `MDSCR_EL1`  | 0 | 2 | 2 | controle de debug monitor |
| `OSLAR_EL1`  | 1 | 0 | 4 | OS Lock Access Register |
| `OSLSR_EL1`  | 1 | 1 | 4 | OS Lock Status Register |
| `DBGBVR0_EL1`| 0 | 0 | 4 | valor do breakpoint 0 |
| `DBGBCR0_EL1`| 0 | 0 | 5 | controle do breakpoint 0 |
| `DBGWVR0_EL1`| 0 | 0 | 6 | valor do watchpoint 0 |
| `DBGWCR0_EL1`| 0 | 0 | 7 | controle do watchpoint 0 |

**Decisão de escopo**: `DBGBVR<n>`/`DBGBCR<n>`/`DBGWVR<n>`/`DBGWCR<n>` existem arquiteturalmente
para `n=0..15`, mas o número de instâncias REALMENTE implementadas é anunciado por
`ID_AA64DFR0_EL1.BRPs`/`.WRPs` (`ARM DDI 0487 D19.2.60`) — este projeto já fixa
`ID_AA64DFR0_EL1_VALUE = 0x6` (`Aarch64Core`, B6.6.7/B6.10), que deixa `BRPs=0`/`WRPs=0` ⇒
**1 breakpoint + 1 watchpoint implementados** (`n = campo + 1`). Implementar só `n=0` mantém
consistência com o que o próprio registrador de identidade já anuncia — um guest bem-comportado
nunca acessa `n≥1` porque já leu `BRPs=0`/`WRPs=0` primeiro. Se um consumidor real precisar de
mais, é uma task nova que também revisita `ID_AA64DFR0_EL1_VALUE` (não expandir por conta própria
aqui).

Fatos de referência conferidos contra `target/arm/debug_helper.c` real do QEMU (`WebFetch`, sessão
atual) antes de codificar: os 4 registradores de breakpoint/watchpoint usam `crn=0`, `crm=i`
(índice), `opc2` fixo por família (`4`=`DBGBVR`, `5`=`DBGBCR`, `6`=`DBGWVR`, `7`=`DBGWCR`);
`MDSCR_EL1`/`OSLAR_EL1`/`OSLSR_EL1` batem com a tabela acima.

- `Aarch64SystemRegisterId`: 7 constantes novas (mesmo padrão de B10.2/B10.3).
- `Aarch64Decoder#decodeSystemRegisterId`: novo branch `op0 == SYSREG_OP0_DEBUG` (constante nova,
  `= 2`) ANTES do `if (op0 != SYSREG_OP0_EL1) return null`, delegando a
  `decodeDebugRegisterId(op1, crn, crm, op2)` — só aceita quando `op1 == 0` (único grupo coberto),
  espelhando `decodeEl2RegisterId`/`decodeEl3RegisterId`.
- `Aarch64VmsaSystemRegisters`: estende `handles`/`read`/`write` para os 7 registradores novos —
  armazenamento puro (nenhum campo delega a `Aarch64ExceptionState`, ao contrário de
  `SPSR_ELx`/`ELR_ELx`/`VBAR_ELx` — debug não tem análogo nesses bancos).
  - **`OSLAR_EL1` é `WO`/`OSLSR_EL1` é `RO` no hardware real**, mas a task explicitamente pede "não
    travar/rejeitar o guest" — mesma disciplina de armazenamento uniforme leitura/escrita dos
    demais (sem enforcement de direção, ao contrário do padrão `RO` já usado para identidades da
    CPU em `Aarch64Core#writeIntrinsicSystemRegister` — aqui a meta é tolerância, não fidelidade de
    hardware, por decisão explícita desta task).

## Não inclui

- Semântica real de breakpoint/watchpoint (parar a CPU, gerar exceção de debug) — sem debugger de
  hardware conectado, não há consumidor real hoje.
- `n=1..15` de `DBGBVR`/`DBGBCR`/`DBGWVR`/`DBGWCR` — ver "Decisão de escopo" acima.
- Qualquer registrador do grupo `op0=2` fora da tabela (ex.: `DBGCLAIMSET_EL1`,
  `DBGAUTHSTATUS_EL1`, `DBGPRCR_EL1`) — sem consumidor real conhecido; se aparecer, vira gap novo
  (mesmo padrão G8: cair em `UNIMPLEMENTED`, não confundir com outro registrador).

## Validação

- Teste novo cobrindo os 7 registradores: `MSR`/`MRS` round-trip via decoder (mesmo estilo de
  `Aarch64El2SystemRegisterDecoderTest`/`Aarch64El3SystemRegisterDecoderTest`), valor arbitrário
  não-trivial.
- Teste provando independência dos 7 registradores entre si (escrever um não muda os outros).
- `mvn -o test` verde no `core`. `mvn -o install` local.
- **G5**: gbaemu, ndsemu, virtual-arm-box (único consumidor A64), n3dsemu, armbox (40/41
  pré-existente).
- Sem mudança de comportamento observável em nenhum consumidor hoje — mudança puramente aditiva
  (G3).

## Armadilhas

- `op0=2` é um branch NOVO no dispatcher (`decodeSystemRegisterId` hoje começa com
  `if (op0 != SYSREG_OP0_EL1) return null` — `SYSREG_OP0_EL1=3`) — checar `op0==2` ANTES desse
  `if`, não depois (senão cai sempre em `null`).
- Toolchain devkitA64 indisponível nesta sessão (mesma situação de B10.2/B10.3): encodings
  DERIVADOS POR FÓRMULA (`0xD5000000 | L<<21 | op0<<19 | op1<<16 | CRn<<12 | CRm<<8 | op2<<5 | Rt`),
  conferida contra os opcodes já existentes no repo (grupo EL2/EL3) antes de gerar os valores
  novos — só o `op0` muda de `3` para `2`.
- Não confundir `op0=2` (debug) com o `MDCR_EL2`/`MDCR_EL3` já implementados em B10.2/B10.3 — esses
  dois ficam propositalmente em `op0=3` (mesma observação já registrada nas Armadilhas de B10.2/
  B10.3: "este projeto já trata `MDCR_EL2`/`MDCR_EL3` como `op0=3` por precedente, não reabrir essa
  decisão aqui").

# B13.1 — Fundação NEON: banco de registradores D0-D31 / Q0-Q15 no lado de 32 bits

**Trilha:** B · **Repo:** arm-jitter (+ revalidação G5 nos consumidores) · **Depende de:** —
**Épico:** `b13-plano-neon-a32.md` · **Status:** ⬜

## Contexto

O épico B13 (NEON/Advanced SIMD de 32 bits, 325 encodings hoje marcados "não se aplica a nenhum
preset atual") está bloqueado por uma lacuna de estado, não de decode: **o banco de registradores
de 32 bits não comporta NEON.**

`core/VfpRegisters.java` é literalmente `private final int[] s = new int[32]` (`SINGLE_COUNT = 32`),
e `d(index)`/`setD(index)` montam cada `D` a partir de DOIS `S` consecutivos — logo só **D0-D15**
são endereçáveis. NEON exige **D0-D31** (o mesmo banco do VFPv3-D32) com vista **Q0-Q15** de 128
bits. O `VfpDecoder` já documenta a lacuna no ponto onde ela dói:

```java
if (!validDoubleRegister(vn, true)) {
    return null; // D16-D31 não existem neste projeto (sem VFPv3-D32/NEON).
}
```

Esta task é o espelho exato da **B8.6** do lado A64, que "estendeu `Aarch64FpRegisters` para 128
bits reais (reabre B6.5.1 D4, decisão explícita do usuário: **pré-requisito de toda a escada
AdvSIMD**, não só desta task)". `core64/Aarch64FpRegisters.java` é o TEMPLATE a copiar: `long[] lo`
+ `long[] hi`, com acessores `element(index, lane, sizeLog2)`/`setElement`/`setQ`/`low64`/`high64`/
`replicateElement`.

## Objetivo

`VfpRegisters` passa a modelar **D0-D31** (64 bits reais cada) com vista **Q0-Q15**, e o projeto
ganha as duas `ArmFeature` que gateiam isso — **sem nenhum preset declará-las ainda**, portanto
zero-diff de runtime para os 5 consumidores. Nenhum encoding novo é decodificado nesta task.

## Inclui

1. **`core/VfpRegisters.java` reescrito sobre `long[] d = new long[32]`** (`DOUBLE_COUNT = 32`),
   espelhando `Aarch64FpRegisters`:
   - `SINGLE_COUNT = 32` **permanece** (S0-S31 são exatamente a vista de 32 bits de D0-D15 — a
     arquitetura não tem S32+); `s(i)`/`setS(i)` passam a ler/escrever a metade correta de
     `d[i / 2]`, mantendo o layout little-endian já documentado (`S<2i>` = metade BAIXA).
   - `d(i)`/`setD(i)` viram acesso direto ao array, agora válidos para `i` em `0..31`.
   - Novos: `QUAD_COUNT = 16`, `q(i)`/`setQ(i, lo, hi)`/`low64(i)`/`high64(i)` (`Q<i>` = `D<2i>`
     baixo + `D<2i+1>` alto), `element(i, lane, sizeLog2)`/`setElement(...)`/`replicateElement(...)`
     com a MESMA assinatura e semântica de `Aarch64FpRegisters` (é a interface que toda a escada
     B13.4+ vai consumir).
2. **`ArmFeature.VFPV3_D32`** — o banco estendido de 32 `D` (VFPv3-D32; VFPv3-D16 e VFPv2 têm 16).
3. **`ArmFeature.ADVANCED_SIMD`** — NEON propriamente dita. Javadoc citando: extensão OPCIONAL do
   ARMv7-A, **não existe** em ARMv4T/v5TE/v6K/ARM11 MPCore (G2), e implica `VFPV3_D32`.
4. **`VfpDecoder#validDoubleRegister` passa a consultar a arquitetura**: aceita D16-D31 **somente**
   quando `VFPV3_D32` está presente. Como nenhum preset a declara, o comportamento observável não
   muda (continua recusando) — mas o gate fica no lugar certo, mesmo padrão de B11.4/B11.6.
5. **Compatibilidade de save-state (G3, ver Armadilhas)**: `saveState`/`loadState`/`snapshot`
   mantêm EXATAMENTE o formato atual (32 `int` = S0-S31 = D0-D15). Métodos NOVOS
   `saveStateExtended`/`loadStateExtended`/`snapshotD` (`long[32]`) expõem o banco completo; os
   consumidores migram quando bumparem a própria versão de save-state, nunca por efeito colateral
   desta task.
6. Testes: `VfpRegistersTest` novo cobrindo o aliasing (escrever `Q0` altera `D0`/`D1` e `S0-S3`;
   escrever `S3` altera a metade alta de `D1` e a alta de `Q0`), `element`/`setElement` nas 4
   larguras, D16-D31 independentes de qualquer `S`, e round-trip de save-state nos DOIS formatos.

## Não inclui

- Qualquer decode de instrução NEON (é B13.3+); esta task não muda nenhuma célula de
  `docs/COBERTURA-ISA.md`.
- Preset novo declarando `ADVANCED_SIMD` — é a B13.22 (fechamento) que faz o grupo sair de
  `NOT_IN_ANY_PRESET`. Aqui as features nascem existindo e desligadas em todo preset.
- A RFC de reuso do núcleo vetorial A64 — é a **B13.2**, próxima task, e ela pode legitimamente
  pedir ajustes nesta interface.
- Emissão ASM nativa dos acessos novos (o backend `AsmBlockCompiler`/`GuestToHostMapper` continua
  vendo só o que já via).

## Armadilhas

- **Save-state é o risco real desta task.** `VfpRegisters#saveState` escreve 32 `int` e é
  serializado dentro dos save-states de `gbaemu` (`.ss` v2, "full-machine") e `ndsemu`. Trocar isso
  por 32 `long` invalida silenciosamente todo arquivo existente — e o sintoma aparece só quando um
  usuário carrega um estado antigo, não em teste. Por isso o formato legado é **preservado como
  default** e o estendido entra por método novo (G3).
- **`snapshot()` devolve `int[]` e é consumido pelo `BlockEquivalenceHarness`** (G1). Não mudar a
  assinatura: adicionar `snapshotD()`. Trocar o tipo de retorno quebraria o oráculo do projeto.
- **S32+ não existe.** É tentador escrever `SINGLE_COUNT = 64` "por simetria" — errado: a
  arquitetura ARM tem exatamente 32 registradores `S`, e apenas D0-D15 têm vista `S`. D16-D31 são
  endereçáveis só como `D`/`Q`.
- **G2**: nenhum preset de `ARMV4T`/`ARMV5TE`/`ARMV6K`/`ARM11_MPCORE` pode ganhar as features
  novas. O ARM11 MPCore do 3DS **não tem NEON** — se `n3dsemu` começar a decodificar NEON, é bug.
- **`Aarch64FpRegisters` e `VfpRegisters` continuam classes separadas** (disciplina do B6 de nunca
  misturar os dois mundos). Espelhar a interface, não extrair superclasse — a unificação, se
  acontecer, é decisão da RFC B13.2, com dados na mão.

## Resultado (2026-08-28)

### O que foi feito

1. **`core/VfpRegisters.java` reescrito sobre `long[] d = new long[32]`** (`DOUBLE_COUNT = 32`),
   espelhando `core64/Aarch64FpRegisters`:
   - `SINGLE_COUNT = 32` mantido; `s(i)`/`setS(i)` agora leem/escrevem a metade little-endian de
     `d[i >> 1]` (`S<2i>` = metade BAIXA). `setS`/`setD` **continuam não-destrutivos** (só tocam
     os próprios bits) — é a diferença semântica que PERMANECE entre os dois bancos (o lado A64
     faz "SIMD&FP destructive write"); documentada no Javadoc da classe.
   - `d(i)`/`setD(i)` viraram acesso direto ao array, válidos para `i` em `0..31`.
   - Novos: `QUAD_COUNT = 16`; `low64(i)`/`high64(i)`/`q(i)` (retorna `long[]{lo,hi}`)/`setQ(i,lo,hi)`
     (`Q<i>` = `D<2i>` baixo + `D<2i+1>` alto); `element(i,lane,sizeLog2)`/`setElement(...)`/
     `setScalar(...)`/`replicateElement(...)` com a MESMA assinatura/semântica de
     `Aarch64FpRegisters` — **Q-indexados (`0..15`), span de 128 bits** através de `d[2i]`/`d[2i+1]`
     (o mirror literal: a unidade de 128 bits do banco de 32 bits é o `Q`). A RFC B13.2 pode
     ajustar isso.
2. **`ArmFeature.VFPV3_D32`** e **`ArmFeature.ADVANCED_SIMD`** adicionadas (Javadoc `///` em
   português, G7). **Nenhum preset as declara** — nascem existindo e desligadas (zero-diff).
3. **`VfpDecoder#validDoubleRegister` passou de `static` para método de instância** e consulta
   `architecture.has(ArmFeature.VFPV3_D32)`: aceita `D16`-`D31` só com a feature. Como nenhum
   preset a liga, o comportamento observável é idêntico ao anterior (continua recusando).
4. **Save-state (G3)**: `saveState`/`loadState`/`snapshot` mantêm EXATAMENTE o formato legado
   (32 `int` = `S0`-`S31` = `D0`-`D15`) — save-states `.ss` de gbaemu/ndsemu já gravados carregam
   sem mudança. Novos `saveStateExtended`/`loadStateExtended`/`snapshotD` (`long[32]`) expõem o
   banco completo, sem serem chamados como efeito colateral.
5. **Testes**: `VfpRegistersTest` ampliado (aliasing `Q0`↔`D0`/`D1`↔`S0`-`S3`, `S3`↔metade alta de
   `D1`↔alta de `Q0`, `element`/`setElement` nas 4 larguras, `setScalar`/`replicateElement`,
   `D16`-`D31` independentes de qualquer `S`, round-trip dos dois formatos de save-state,
   `snapshot()` continua `int[32]`). `VfpDecoderTest` ganhou o gate: `VADD.F64 D16` é
   `UNIMPLEMENTED` sem `VFPV3_D32` (idêntico ao de antes) e decodifica com um arch de teste que
   liga a feature (`VFP_D32_TEST_ARCH`).

### Validação

- `mvn -o test` (JBR 25) no arm-jitter: **verde** (2710 no core + módulos truffle/asm).
- `mvn -o install` OK; **G5 verde e zero-diff** nos 5 consumidores: gbaemu (240), ndsemu (183),
  armbox (47), virtual-arm-box (87), n3dsemu (221).
- `./gerar-cobertura-isa.sh` regenerado: `docs/COBERTURA-ISA.md` **byte a byte idêntica** (o gate
  não vazou — nenhuma célula muda; a task não decodifica nenhum encoding NEON).

### Decisões / achados

- **`q(i)` retorna `long[2]`** (`[baixo, alto]`) — `Aarch64FpRegisters` não tem um `q()` análogo
  (só `low64`/`high64`/`setQ`), mas a spec da task pediu `q(i)` explicitamente; é conveniência
  pura, sem alocar no caminho quente de nada ainda (nenhum decode consome).
- **`element` & cia. são Q-indexados** (não D-indexados): "MESMA semântica de `Aarch64FpRegisters`"
  → span da largura total do registrador; a unidade de 128 bits aqui é `Q0`-`Q15`. Acesso a lane
  de um `D` individual (comum em NEON real) fica para a interface que a B13.2/B13.4 definir.
- Nenhuma mudança em `Thumb2VfpDecoder` — ele não fazia gating próprio de `D16` e a task não
  decodifica nada novo.

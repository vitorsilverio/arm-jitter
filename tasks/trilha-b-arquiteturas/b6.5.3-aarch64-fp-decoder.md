# B6.5.3 — AArch64: decoder FP escalar (classe "Data Processing — Scalar FP and Advanced SIMD")

**Trilha:** B · **Depende de:** B6.5.2 (`Ir64Op`s de FP + executor) · **Repo:** arm-jitter

## Contexto

Terceira das 4 sub-tasks de B6.5 (ver decomposição em B6.5.1). Com IR+executor
prontos (B6.5.2), esta task liga o decode — a categoria de MAIOR risco das 4,
mesmo padrão que motivou B3.5 (VFP32) a ser sua própria task e que motivou o
próprio épico B6 a citar "encoding traiçoeiro" nas Armadilhas gerais (lá para
`DecodeBitMasks`; aqui, o risco é outro: a classe top-level inteira ainda não
tem NENHUM dispatch).

**Achado desta rodada de pesquisa, que fixa o ponto de entrada exato**:
`Aarch64Decoder.isDataProcessingRegisterClass` (`decoder64/Aarch64Decoder.java:
370-374`) testa SÓ `bit27=1 && bit25=1` — não testa `bit26`. Pela tabela de
classes top-level do `ARM DDI 0487 C4.1`, o padrão `x1x1` nos bits[28:25] na
verdade cobre DUAS classes irmãs, distinguidas por `bit26`:
- `bit26=0` → "Data Processing — Register" (já coberta por
  `decodeDataProcessingRegister`, `B6.3.1-B6.3.4` — todos os padrões fixos
  usados lá, ex. `ADD_r` = `.  00 01011 ..`, `CSEL` = `011010100` em
  `[29:21]`, têm bit26=0 dentro do campo, confirmado por leitura de
  `Aarch64Decoder.java:753-800` e `685-704`).
- `bit26=1` → "Data Processing — Scalar Floating-Point and Advanced SIMD"
  (**NÃO decodificada hoje** — todo `word` com `bit27=1,bit26=1,bit25=1` cai
  em `decodeDataProcessingRegister`, não bate NENHUM padrão fixo dos `case`s
  existentes ali, porque todos eles exigem `bit26=0` dentro dos campos que
  testam — CONFERIR essa afirmação lendo `decodeDataProcessingRegister` linha
  a linha antes de implementar, mas a leitura desta rodada não achou nenhum
  padrão fixo que aceite `bit26=1`), e cai no `throw unsupported(word,
  address)` do final do método (`Aarch64Decoder.java:703`). **Comportamento
  hoje: `UnsupportedOperationException`, correto por acidente (nenhum
  encoding de FP é decodificado como se fosse outra coisa), mas sem
  dispatch nenhum.**

**Decisão de nomenclatura**: `isDataProcessingRegisterClass` continua com o
mesmo nome (não é um nome errado — bit27=1&&bit25=1 É de fato o gate correto
para "entra em `decodeDataProcessingRegister`", que passa a ter uma
ramificação nova por `bit26` logo no topo). Não renomear o método existente
só por causa desta task — risco de diff desnecessário em código já testado
(G3, mesmo espírito).

## Fatos de referência (fonte: `ARM DDI 0487` C4.1/C7 + QEMU
`target/arm/tcg/vfp.decode` — para A64, o layout de bits é DIFERENTE do
espaço CP10/11 do VFP32, mesmo a semântica sendo análoga; CONFERIR literalmente
contra `a64.decode`/`vfp.decode` do QEMU (HEAD do master, mesma disciplina de
pin de versão que B6.3.x já registrou) antes de transcrever qualquer padrão de
bits — os padrões abaixo são o ESQUELETO esperado, não uma transcrição
verificada nesta rodada de spec sem código)

1. **Ponto de entrada**: `decodeDataProcessingRegister(word, address)`
   (`Aarch64Decoder.java:677`), logo no início (antes do `addSubGroup` atual
   na linha 678): checar `bit26` primeiro — `if (bit26set) return
   decodeDataProcessingScalarFpSimd(word, address);` — só então continuar com
   a lógica existente de `Data Processing — Register` (que já assume
   implicitamente `bit26=0`, como provado pela leitura dos padrões fixos
   citados acima). Este é o ÚNICO ponto de entrada novo no dispatch —
   nenhuma mudança na assinatura de `isDataProcessingRegisterClass` nem no
   `decode()` principal.
2. **Sub-classe A64 "Scalar FP" vs "Advanced SIMD"**: dentro de `bit26=1`, o
   manual distingue ainda mais (SIMD vetorial vs FP escalar) por outros bits
   — esta task só implementa o subconjunto ESCALAR necessário para
   FADD/FSUB/FMUL/FDIV/FNEG/FABS/FMOV(reg)/FMOV(imm)/FCMP/FCMPE/FCVT(F32↔F64)
   (herdado de B6.5.2). Qualquer padrão de bits fora dessa lista — incl.
   TODA a Advanced SIMD (vetorial) — cai em `unsupported`, mesmo tratamento
   que `Aarch64Decoder.java` já dá a "Load/store de registrador SIMD&FP
   (V=1)" hoje (`decodeLoadsAndStores`, achado do agente de pesquisa desta
   rodada: bit `V` setado já lança `unsupported` explicitamente com esse
   comentário).
3. **Índice de registrador em A64 é direto, sem `D:Vd`/`Vd:D`**: diferente do
   VFP32 (`b3.5-vfp-decoder.md` Armadilhas linha 91 — "a ordem `D:Vd` vs
   `Vd:D` inverte entre single e double"), o campo de registrador em A64 é um
   único índice de 5 bits (`Rd`/`Rn`/`Rm`, 0-31) que se aplica IGUALMENTE a
   `Sn` e `Dn` (mesma célula, B6.5.1) — **não há bug clássico a herdar aqui**,
   confirmar isso é uma simplificação real em relação ao precedente, não um
   descuido da spec.
4. **`type` (2 bits) seleciona a precisão** na maioria dos encodings FP
   escalares A64 (`00`=single, `01`=double, `10`=reservado/half — fora de
   escopo, `11`=reservado) — CONFERIR contra `a64.decode` a posição exata do
   campo `type` em cada grupo (ALU, compare, convert, move) antes de
   implementar; não assumir que a posição é a mesma em todos os grupos sem
   checar.

## Decisões de desenho FECHADAS nesta rodada

### D1 — Ramo novo em `decodeDataProcessingRegister`, sem novo `isXxxClass`

Ver Fatos de referência #1. Não criar um `isDataProcessingScalarFpSimdClass`
separado verificado no `decode()` principal — o gate de entrada
(`isDataProcessingRegisterClass`, bit27&&bit25) já é o correto para as DUAS
classes irmãs; só falta ramificar por `bit26` DENTRO do método já existente.
Método novo `decodeDataProcessingScalarFpSimd(word, address)` concentra os
sub-dispatches desta task — mesmo padrão de "método novo por classe/subclasse"
já usado consistentemente desde B6.3.1.

### D2 — Feature gate: reaproveitar `ArmFeature` ou criar equivalente A64?

**Investigar antes de implementar**: o pipeline A64 (B6.1-B6.4) hoje NÃO tem
nenhum sistema de feature gating equivalente a `ArmFeature`/preset — todo
`Aarch64Decoder` decodifica o conjunto fechado do épico incondicionalmente
(não há `ArmArchitecture`-equivalente para A64 ainda, confirmado pela ausência
de qualquer menção a "preset"/"feature" nos pacotes `decoder64`/`core64`
lidos nesta rodada). **Decisão: não inventar um sistema de features A64 só
para esta task** — seguir o padrão já estabelecido por B6.1-B6.4 (decode
incondicional do conjunto coberto, `unsupported` para o resto) em vez de
introduzir um gate novo sem um segundo consumidor que precise dele (mesmo
raciocínio "sem consumidor real" que B6.4 D0 usou para não replicar IC/
chaining/tiering no `jit64/`).

## Objetivo

- Dispatch novo dentro de `decodeDataProcessingRegister` (D1) para a classe
  irmã `bit26=1`.
- Decode de `FADD`/`FSUB`/`FMUL`/`FDIV`/`FNEG`/`FABS`/`FMOV`(reg) →
  `Fp64Alu`.
- Decode de `FMOV`(imediato) → `Fp64MoveImmediate` (VFPExpandImm-equivalente
  de A64 — encoding próprio, CONFERIR contra `a64.decode`).
- Decode de `FCMP`/`FCMPE` (com/sem comparação-com-zero) → `Fp64Compare`.
- Decode de `FCVT` (só F32↔F64) → `Fp64Convert`.
- Corpus real (mesmo padrão `corpus.s`/`.bin`/`.objdump.txt` de B6.1-B6.3.4,
  apêndice com offsets novos, montado com `aarch64-none-elf-as`/`objdump`
  reais do devkitA64).

## Especificação

1. `decodeDataProcessingScalarFpSimd(word, address)` novo — sub-dispatch por
   padrão de bits fixo (a task decide os nomes de constante ao ler
   `a64.decode` real; G6 aplica, nomear tudo).
2. Cada grupo (ALU, move-imediato, compare, convert) com seu método de
   decode dedicado, mesmo padrão de `decodeConditionalSelect`/
   `decodeMultiplyAccumulate` etc. já usados desde B6.3.1-B6.3.4.
3. `type` (Fatos de referência #4): `00`→`doublePrecision=false`,
   `01`→`doublePrecision=true`, `10`/`11`→`UnsupportedOperationException`
   (reservado/half, fora de escopo — mesmo padrão de "UNDEFINED de verdade,
   não não-implementado" já usado em B6.3.1 para `N=1,sf=0`).
4. `VFPExpandImm`-equivalente de A64: algoritmo análogo ao de `vfp.decode`
   (`b3.5-vfp-decoder.md` linha 33), mas a POSIÇÃO/tamanho do campo imediato
   no encoding A64 precisa ser conferida contra `a64.decode` — não assumir
   que é bit-a-bit idêntico ao ARM32 só porque o algoritmo de expansão (sinal
   + expoente replicado + mantissa) é o mesmo conceito IEEE.
5. Corpus: apêndice do mesmo `corpus.s`/`.bin`/`.objdump.txt` (offsets a
   definir ao implementar — continuar a sequência dos apêndices anteriores),
   cobrindo cada grupo em single E double, os 4 vetores canônicos de
   `FMOV`-imediato, e pelo menos um vetor de cada mnemônico
   (`FADD`/`FSUB`/`FMUL`/`FDIV`/`FNEG`/`FABS`/`FMOV` reg/`FMOV` imm/`FCMP`/
   `FCMPE`/`FCVT` ambas direções).

## Não inclui

- Advanced SIMD vetorial (Fatos de referência #2).
- `type=10` (half-precision) — reservado nesta leitura, fora de escopo.
- Qualquer feature-gating novo (D2).
- `SCVTF`/`UCVTF`/`FCVTZS`/`FCVTZU`/loads-stores FP/`SQRT`/`FMOV`
  core↔FP — herdados como fora de escopo de B6.5.2, reafirmados aqui: se o
  decoder encontrar esses encodings dentro da classe `bit26=1`, devem cair em
  `unsupported`, NÃO ser decodificados por engano só porque "já que estou
  aqui" (mesma armadilha de escopo que B6.3.4 registrou para `LDXP`/`CAS`).

## Testes mínimos (`Aarch64DecoderScalarFpTest` ou extensão do teste de
corpus existente)

1. Cada grupo decodificado campo a campo contra o corpus real (vetores
   montados com `aarch64-none-elf-as` — nenhum encoding inventado à mão,
   mesma disciplina de todas as sub-tasks A64 anteriores).
2. `type=10`/`type=11` → `UnsupportedOperationException` (reservado).
3. `FMOV`-imediato: os 4 vetores canônicos, campo a campo.
4. Advanced SIMD (vetorial, um encoding qualquer com `bit26=1` fora do
   subconjunto escalar coberto) → `UnsupportedOperationException` — teste de
   regressão negativo confirmando que nada "vazou" (mesmo padrão de B6.3.4).
5. Execução ponta-a-ponta: bloco `FMOV`(imm)+`FADD`+`FCMP`+`B.cond` montado
   em memória, rodado no `Ir64BlockExecutor` — o "hello float" mínimo A64
   (mesmo espírito do teste 3 de `b3.5-vfp-decoder.md`, sem o passo `VMRS`
   intermediário que A64 não precisa — Fatos de referência #1 de B6.5.2).
6. Regressão: suíte completa de B6.1-B6.4/B6.5.2 sem mudança — em particular,
   NENHUM vetor de corpus existente de `decodeDataProcessingRegister`
   (B6.3.1-B6.3.4, `bit26=0`) muda de resultado.

## Armadilhas

- **Não transcrever padrões de bits sem checar `a64.decode`/`vfp.decode`
  reais** — os Fatos de referência desta task são um ESQUELETO esperado, não
  uma transcrição verificada (ao contrário de B6.3.1-B6.3.4, que já citam
  trechos literais do QEMU lidos naquela rodada). Esta é a maior diferença de
  rigor desta spec em relação às sub-tasks de B6.3 — reflete que esta rodada
  é SPEC-ONLY, sem acesso a implementar/testar contra o assembler real; a
  PRÓXIMA sessão que executar B6.5.3 precisa fazer esse trabalho de
  verificação como PRIMEIRO passo, não pular direto para transcrever daqui.
- **Bit26 é o discriminador entre "Data Processing — Register" (B6.3.x) e
  "Scalar FP/SIMD" (esta task)** — qualquer padrão fixo novo desta task que
  aceite `bit26=0` por engano arriscaria colidir com um encoding já
  decodificado por B6.3.1-B6.3.4 (teste de regressão 6 é o guarda).
- **Não decodificar Advanced SIMD vetorial "de graça"** — mesmo padrão de
  disciplina de escopo de B6.3.1 (Logical shifted register) e B6.3.4
  (LDXP/CAS): tentador porque o subgrupo de bits é vizinho, mas fora do
  "Inclui" fechado do épico.
- **`FMOV`-imediato A64 pode NÃO ter o mesmo layout de bits do `VFPExpandImm`
  de 32 bits** mesmo usando o mesmo algoritmo conceitual — não copiar
  posições de campo do VFP32 sem conferir contra `a64.decode`.
- **Pin de versão QEMU**: mesma ressalva de todas as sub-tasks A64
  anteriores — verificar contra o HEAD do master na hora de implementar, não
  confiar em memória de uma leitura antiga se muito tempo tiver passado.

# B15.6 — Preset `ARMV8_1M` + Low Overhead Branch (`WLS`/`DLS`/`LE`/`LCTP` + variantes `TP`)

**Trilha:** B · **Repo:** arm-jitter (+ revalidação G5) · **Depende de:** B15.4 (⬜)
**Épico:** `b15-plano-armv8m.md` · **Status:** ⬜ (spec escrita 2026-09-14, ainda não executada)

## Contexto

`b15-plano-armv8m.md` reserva esta task para (a) criar o preset `ARMV8_1M`
(`extending(ARMV8M_MAINLINE, ...)`, a versão que a **B16 (MVE/Helium)** exige como pré-requisito
DURO) e (b) decodificar/executar a família "Low Overhead Branch" (`FEAT_LOB`): `WLS`/`DLS`/`LE`/
`LCTP` (formas escalares) e suas variantes `WLSTP`/`DLSTP`/`LETP` (que também controlam o "tail
predication" do MVE — mas SEM MVE real, essas 3 formas ficam `❌` honesto ou recebem a mesma
simplificação, ver "Não inclui").

### Os encodings reais (`target/isa-decode/t32.decode`, linhas ~734-749, medidos nesta rodada de spec)

```
# LE and WLS immediate
{
  DLS          1111 0 0000 100     rn:4 1110 0000 0000 0001 size=4
  WLS          1111 0 0000 100     rn:4 1100 . .......... 1 imm=%lob_imm size=4
  {
    LE         1111 0 0000 0 f:1 tp:1 1111 1100 . .......... 1 imm=%lob_imm
    # This is WLSTP
    WLS        1111 0 0000 0 size:2 rn:4 1100 . .......... 1 imm=%lob_imm
  }
  {
    LCTP       1111 0 0000 000     1111 1110 0000 0000 0001
    # This is DLSTP
    DLS        1111 0 0000 0 size:2 rn:4 1110 0000 0000 0001
  }
  VCTP         1111 0 0000 0 size:2 rn:4 1110 1000 0000 0001
}
```

- **`DLS`/`WLS`** (formas "puras", `size=4`): iniciam um loop de baixo overhead — `DLS Rn` copia
  `Rn` para o `LR` interno usado como contador (`Rn` = número de iterações); `WLS Rn, label` faz o
  mesmo E salta para `label` se `Rn==0` (loop "while", pode nunca executar).
  - **`WLSTP`/`DLSTP`** (`size:2` ≠ `4`, formas de tail-predication MVE): MESMO opcode-base de
    `WLS`/`DLS`, discriminadas só pelo campo `size` NÃO ser o valor sentinela `4` — além do contador,
    calculam a máscara de predicação `VPR.P0` para a última iteração parcial de um loop vetorial MVE
    (`size` = tamanho do elemento). **Sem MVE real neste projeto (B16 ainda `⬜`), essas formas não
    têm onde produzir efeito** — ver "Não inclui".
- **`LE`** (`f`=forward/não-forward — na verdade `f=0` é branch condicional a `LR!=0`, `f=1` é
  incondicional "loop always taken, decrementa e nunca sai" — CONFIRMAR contra o manual, não deduzir
  do nome; `tp`=1 forma tail-predicated `LETP`): fecha o loop — decrementa o contador interno e salta
  para trás até `imm` se ainda não zerou (ou se `f=1`, sempre volta E ajusta o `VPR` na iteração
  final).
- **`LCTP`** (`LoopClearWithTailPredication`, zero campos livres além do prefixo): limpa o estado de
  tail-predication ao sair de um loop MVE cedo (`break` dentro do loop) — igualmente sem efeito real
  sem MVE.
- **`VCTP`** (Vector Compare for Tail Predication) **está no MESMO bloco de decode** mas é do MVE
  propriamente dito (calcula `VPR.P0` a partir de `Rn`, sem relação com contador de loop) — **listada
  aqui porque compete pelo MESMO espaço de bits**, mas pertence semanticamente à B16 (`mve.decode`
  também a lista) — decidir nesta task se ela decodifica (e recusa por falta de MVE) ou fica para a
  B16 abrir o espaço; ver Armadilha 3.

### Achado central (pesquisado via `WebSearch` nesta rodada — sem fonte QEMU local; a arquitetura
### real usa um mecanismo de HARDWARE de predição de branch que este projeto não precisa replicar)

- Hardware real: depois da primeira iteração, o processador "aprende" o padrão do loop e para de
  buscar/decodificar `LE` fisicamente a cada volta (zero overhead de verdade). **Para este emulador,
  isso é irrelevante** — `LE`/`WLS`/`DLS` são simplesmente um branch condicional com um contador
  dedicado; a simplificação correta é modelar o CONTADOR (um registrador interno, análogo ao `LR`
  usado como contador de loop — na prática, a arquitetura real reusa o próprio `LR` do banco de
  registradores visível, não um registrador oculto) e a lógica de decremento/salto, sem tentar
  simular a "predição" (que não tem efeito observável, só efeito de desempenho no hardware real).
- **O contador de `DLS`/`WLS`/`LE` é literalmente o `LR` (R14) do banco de registradores visível** —
  não há registrador oculto: `DLS Rn` grava `Rn` em `LR`, `LE` decrementa `LR` e testa. Isso é
  arquiteturalmente simples e não exige estado novo no `ArmCore` além do que já existe (mesma lição
  que `VLLDM_VLSTM`/B15.5 aprenderam ao evitar modelar `FPCCR.LSPACT`: preferir a leitura mais
  simples que ainda é честа quando a "otimização" de hardware não tem efeito observável).

## Objetivo

Preset `ARMV8_1M` existe (`extending(ARMV8M_MAINLINE, ...)`, zero regressão nos presets existentes,
G3). `DLS`/`WLS`/`LE`/`LCTP` (formas puras, sem tail-predication) decodificam e executam sob
`ArmFeature.LOW_OVERHEAD_BRANCH`, usando `LR` como contador. `WLSTP`/`DLSTP`/`LETP`/`VCTP` (formas
de tail-predication) decodificam (para não caírem em `UNIMPLEMENTED` genérico) mas recusam
EXPLICITAMENTE por ausência de MVE (mesmo padrão que a B19.28 já validou para `SME`: "trocar o
`default` genérico por um `case` próprio que decodifica de verdade e produz recusa NOMEADA",
suficiente para `docs/COBERTURA-ISA.md` medir `✅` sem semântica completa) — ou ficam `❌` honesto se
a sessão de execução decidir que decodificar sem poder executar de verdade seria enganoso; decidir e
documentar.

## Inclui

1. **Preset `ARMV8_1M`** — `extending(ARMV8M_MAINLINE, ...)`, sem remover/alterar nada dos presets
   existentes.
2. **`ArmFeature.LOW_OVERHEAD_BRANCH`** — feature nova.
3. **Decode de `DLS`/`WLS`/`LE`/`LCTP`** (formas puras) + **decode de `WLSTP`/`DLSTP`/`LETP`**
   (reconhecidas, mas gateadas separadamente — ver Objetivo) — no bloco de decode citado acima,
   gateado por `ArmFeature.LOW_OVERHEAD_BRANCH`.
4. **Executor**: `DLS Rn` → `LR = Rn`; `WLS Rn, label` → `LR = Rn`; se `LR==0`, salta para depois do
   loop (branch condicional); `LE label`/`LE always` (`f`) → decrementa `LR`, salta para `label` se
   `LR!=0` (ou sempre, se `f=1` — CONFIRMAR a semântica exata de `f` antes de implementar, ver
   Armadilha 1); `LCTP` → sem efeito de estado real (mesma disciplina de recusa nomeada se depender
   de MVE, ou NOP puro se a leitura confirmar que não depende).
5. Testes (ver Aceite).

## Não inclui

- **Semântica real de `WLSTP`/`DLSTP`/`LETP`/`VCTP`** (cálculo de `VPR.P0` de tail-predication) —
  depende do banco `VPR`/predicação MVE, que só existe a partir de **B16.1/B16.2** (ainda `⬜`). Se
  decodificadas nesta task, apenas recusam nomeadamente (G8) — nunca simular um `VPR` que não existe.
- **MVE/Helium propriamente dito** — B16 inteiro.
- **`Cortex-M55`/`M85`** (que TÊM Helium/MVE de verdade) no catálogo — fica para B15.7/B16.14.
- **Predição de branch/otimização de desempenho** — irrelevante para um interpretador (ver Achado
  central); implementar `LE` como um branch condicional comum é suficiente e correto.
- **Emissão nativa/Truffle** — decode + interpretado apenas.

## Armadilhas

1. **Semântica de `f` em `LE` não confirmada nesta spec** — decidir com evidência real (manual ou
   QEMU), não deduzir do nome do bit.
2. **`WLSTP`/`DLSTP`/`LETP`/`VCTP` competem pelo MESMO espaço de bits que `WLS`/`DLS`/`LE`/`LCTP`**
   (discriminados só por `size`/`tp`) — um decoder que trata TUDO como forma pura, ignorando `size`/
   `tp`, produziria execução errada silenciosa (G8) para binários MVE reais (mesmo que MVE em si não
   exista ainda) — checar os campos discriminantes SEMPRE, nunca assumir.
3. **`VCTP` pertence semanticamente à B16, não a esta task** — decidir explicitamente se esta task
   a decodifica (com recusa nomeada) ou deixa o espaço para a B16 abrir; documentar a escolha, para a
   B16 saber se precisa remover um decoder desta task ou só adicionar semântica.
4. **`LR` como contador de loop colide com o uso normal de `LR` como link register** — um `BL`/`BLX`
   dentro de um loop `DLS`/`LE` sobrescreve o contador (comportamento ARQUITETURAL real, não um bug
   deste projeto — mas TEM que ser testado para confirmar que o executor não "protege" `LR`
   artificialmente).
5. **G3**: presets existentes (incluindo `ARMV8M_MAINLINE`/`ARMV8M_BASELINE` da B15.4) não podem
   regredir.

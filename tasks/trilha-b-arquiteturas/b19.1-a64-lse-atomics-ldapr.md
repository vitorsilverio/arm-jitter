# B19.1 — A64: atômicos `FEAT_LSE` (`LDADD`…`SWP`) + `LDAPR` (`FEAT_LRCPC`)

**Trilha:** B · **Repo:** arm-jitter (+ revalidação G5 nos consumidores) · **Depende de:** —
**Épico:** `b19-plano-a64-gap-remanescente.md` (cluster "Atômicos LSE + RCPC") · **Status:** ⬜

## Contexto

Primeiro degrau da escada B19 (fechar as ~174 células `❌` que sobram no A64 dentro de um preset que
JÁ existe e é usado — `ARMV8_0_A` é o preset do `armbox`/`virtual-arm-box` aarch64). Este degrau
completa a extensão **LSE**, que a B8.1 implementou pela metade: `CAS`/`CASP` já existem
(`Ir64Op.CompareAndSwap`/`CompareAndSwapPair`, gate `Aarch64Feature.LSE` desde B11.11), mas as **9
operações de memória atômica** da mesma extensão ficaram de fora por decisão explícita do plano
mestre da época ("só `CAS`/`CASP` foram pedidos"). Mais o `LDAPR` (load-acquire com semântica RCpc),
que é `FEAT_LRCPC` — uma feature que **ainda não existe** em `Aarch64Feature`.

São as **10 linhas de encoding** do `target/isa-decode/a64.decode` (QEMU) hoje `❌` em todas as 16
colunas de versão:

|---|---|---|
| `LDADD` `.. 111 0 00 . . 1 ..... 0000 00 ..... .....` `@atomic` | `LDADD`/`LDADDA`/`LDADDL`/`LDADDAL` + aliases `STADD`/`STADDL` | `FEAT_LSE` (ARMv8.1-A) |

| `LDSMIN` `... 0101 00 ...` `@atomic` | `LDSMIN*` + `STSMIN*` | `FEAT_LSE` |

Espelho estrutural do que a **B8.1** fez com `CAS`/`CASP` (`Ir64Op.CompareAndSwap` +
`Ir64BlockExecutor#executeCompareAndSwap` + gate no `Aarch64Decoder#decodeExclusive`) — mas o espaço
de encoding é **outro**: os atômicos de memória não moram em `decodeExclusive` (esse é o subgrupo
"Load/store exclusive and atomic" de `CAS`/`LDXR`/…). Eles moram em `decodeLoadStoreSingle`, no ramo
`idx == IDX_UNSCALED && bit21`, que **hoje faz `throw unsupported` de propósito** (bug real que a
B8.1 consertou: sem checar `bit21`, um atomic memory op virava silenciosamente `LDUR`/`STUR` de um
`Rs` que na verdade é o opcode atômico — `Aarch64Decoder.java` ~linha 1818). Este degrau troca esse
`throw` por um decode de verdade.

## Objetivo

Decodificar e executar as 10 linhas acima, gateadas por `Aarch64Feature.LSE` (as 9) e
`Aarch64Feature.LRCPC` (a de `LDAPR`, feature **nova**). O decoder default (`ARMV8_0_A`, e portanto
os 5 consumidores hoje) **continua recusando** as 10 — G3, zero-diff de runtime. `docs/COBERTURA-ISA.md`
**muda** (é ganho real de cobertura: ~10 células × 16 colunas, todas as colunas ≥ ARMv8.1-A para as
9 e ≥ ARMv8.3-A para `LDAPR`).

## Especificação

### Encoding (oráculo: `target/isa-decode/a64.decode` linhas 548-561 + ARM DDI 0487 C6.2.{LDADD…SWP,LDAPR})

Layout de 32 bits (`V=0`, subgrupo "Atomic memory operations"):

```
 31 30 | 29 28 27 | 26 | 25 24 | 23 | 22 | 21 |20 .. 16| 15 |14 13 12| 11 10 | 9 .. 5 | 4 .. 0
 size  |  1  1  1 |  0 |  0  0  |  A |  R |  1 |  Rs    | o3 |  opc   |  0  0 |  Rn    |  Rt
```

- `size` (bits[31:30]) → `Ir64MemSize` `BYTE`/`HALF`/`WORD`/`DOUBLEWORD` (`00`/`01`/`10`/`11`).
- `A` (bit23) = acquire, `R` (bit22) = release. Combinações: `LD<op>` (A=0,R=0), `LD<op>A`
  (A=1,R=0), `LD<op>L` (A=0,R=1), `LD<op>AL` (A=1,R=1). Todas NOP observável — carregar em
  `acquire`/`release` do record só para um futuro emissor nativo.
- `bit21` fixo `1` (é ele que distingue este espaço de `LDUR`/`STUR`, `bit21=0`).
- `Rs` (bits[20:16]) = registrador com o operando; `31` = **`XZR`** (lê `0`), **não `SP`**.
- `Rn` (bits[9:5]) = base; `31` = **`SP`**.
- `Rt` (bits[4:0]) = destino do valor antigo; `31` = `XZR` → é o alias `ST<op>` (o resultado é
  descartado, mas o RMW acontece igual).
- `bits[11:10]` fixo `00` (o campo `idx` de `decodeLoadStoreSingle`; qualquer outro valor com
  `bit21=1` já é tratado — ou recusado — por outros ramos).

**Split `o3`:`opc` (bit15 : bits[14:12])** — conferir contra ARM DDI 0487 C6.2 antes de implementar:

| `o3` | `opc` | Instrução | Nesta task |
|---:|---:|---|---|
| 0 | 000 | `LDADD` | ✅ `Ir64AtomicOp.ADD` |
| 0 | 001 | `LDCLR` | ✅ `CLR` (bit-clear: `old & ~Rs`) |
| 0 | 010 | `LDEOR` | ✅ `EOR` |
| 0 | 011 | `LDSET` | ✅ `SET` (bit-set: `old \| Rs`) |
| 0 | 100 | `LDSMAX` | ✅ `SMAX` (com sinal, estendido de `size` bits) |
| 0 | 101 | `LDSMIN` | ✅ `SMIN` (com sinal) |
| 0 | 110 | `LDUMAX` | ✅ `UMAX` (sem sinal) |
| 0 | 111 | `LDUMIN` | ✅ `UMIN` (sem sinal) |
| 1 | 000 | `SWP` | ✅ `SWP` (valor novo = `Rs`, ignora `old` no store) |
| 1 | 001 / 010 / 011 | `LD64B`/`ST64B`/… (`FEAT_LS64`) | ❌ `UNIMPLEMENTED` (G8) |
| 1 | 100 | `LDAPR` (se `Rs==31 && A==1 && R==0`) | ✅ via `Ir64Op.Load64` + gate `FEAT_LRCPC` |
| 1 | 101 / 110 / 111 | reservado | ❌ `UNIMPLEMENTED` (G8) |

`LDAPR` (linha própria no `.decode`): `A=1`, `R=0`, `Rs=11111` **fixos**. Se `o3=1 && opc=100` mas
`Rs != 31` ou `A != 1` ou `R != 0` → `UNIMPLEMENTED` (não é `LDAPR`, não é nada — G8).

### IR

```java
/// `LDADD`/`LDCLR`/`LDEOR`/`LDSET`/`LDSMAX`/`LDSMIN`/`LDUMAX`/`LDUMIN`/`SWP` (…, extensão LSE
/// ARMv8.1). Semântica RMW atômica do ponto de vista do guest: lê `[Rn]` (size), calcula
/// `<operation>(old, Rs)`, escreve de volta, e grava `old` (zero-estendido) em `Rt`. `Rt==31`
/// (`XZR`) é o alias `ST<op>` — descarta o resultado, o RMW acontece igual. Interpretador
/// single-thread: não precisa de RMW real de host (mesma nota de {@link CompareAndSwap}).
/// `acquire`/`release` NOP observável.
record AtomicMemoryOp(int rs, int rt, int rn, Ir64MemSize size, Ir64AtomicOp operation,
                      boolean acquire, boolean release) implements Ir64Op {
    @Override public int kind() { return Kind.ATOMIC_MEMORY_OP; }
}
```

`Kind.ATOMIC_MEMORY_OP = 93` (o máximo atual é `CRYPTO_SHA3_TWO_SOURCE_ROTATE = 92`). Condição:
A64 não tem campo de condição — herda o default do `Ir64Op`.

### Execução (espelho de `executeCompareAndSwap`, `Ir64BlockExecutor.java` ~linha 1085)

```
address  = readBaseRegister(core, op.rn())          // 31 => SP
wide     = op.size() == DOUBLEWORD
old      = readMemory(core, address, op.size())     // já zero-truncado a size
rsVal    = zeroTruncateToSize(core.xForWidth(op.rs(), wide), op.size())   // 31 => XZR => 0
newVal   = switch (op.operation()) {
    ADD  -> old + rsVal
    CLR  -> old & ~rsVal
    EOR  -> old ^ rsVal
    SET  -> old | rsVal
    SMAX -> max(signExtend(old,size), signExtend(rsVal,size))   // resultado re-truncado por writeMemory
    SMIN -> min(signExtend(old,size), signExtend(rsVal,size))
    UMAX -> Long.compareUnsigned(old, rsVal) >= 0 ? old : rsVal
    UMIN -> Long.compareUnsigned(old, rsVal) <= 0 ? old : rsVal
    SWP  -> rsVal
}
writeMemory(core, address, op.size(), newVal)
core.notifyOrdinaryWrite(address, op.size().bytes())    // SEMPRE (store incondicional) — ver Armadilhas
core.setXForWidth(op.rt(), old, wide)                   // 31 => XZR, descarta
return false
```

- **`notifyOrdinaryWrite` é obrigatório e incondicional** — diferente de `CAS` (onde o store é
  condicional), o atomic memory op sempre escreve. Sem essa chamada, código automodificável deixa
  de invalidar bloco de JIT (o bug que já custou uma sessão em `gbaemu`, memória `gba-game-compat`)
  e uma reserva `LDXR`/`LDAXR` pendente não é derrubada (mesma auditoria da Especificação #2 da
  B6.3.4 / B8.1).
- O **monitor de exclusividade não é setado nem checado** aqui (LSE atômico não é exclusivo) — só
  `notifyOrdinaryWrite`.
- `SMAX`/`SMIN`: comparar com sinal a partir de `size` bits; deixar `writeMemory` re-truncar. Usar
  o helper de sign-extend já existente no executor (mesmo que `LDRSB`/`LDRSH` usam) — **não**
  reinventar.
- Verificar o nome exato de `zeroTruncateToSize`/`xForWidth`/`readBaseRegister`/`readMemory`/
  `writeMemory` no `Ir64BlockExecutor` atual antes de escrever (a B8.1 usa todos).

`LDAPR` não tem executor próprio — é um `Ir64Op.Load64` comum (o executor de `LOAD64` já faz
load + zero-extend + sem writeback quando `addressingMode == OFFSET` e `immediate == 0`).

## Armadilhas

1. **O espaço de encoding NÃO é `decodeExclusive`.** `CAS`/`CASP`/`LDXR`/`STXR`/`LDAR`/`STLR` moram
   no subgrupo "Load/store exclusive and atomic" (`SUBCLASS_EXCLUSIVE_ATOMIC`). Os atomic memory
   ops moram em `decodeLoadStoreSingle`, ramo `idx == IDX_UNSCALED && bit21` (`Aarch64Decoder.java`
   ~1818) — que hoje é um `throw unsupported` único. Trocar por `return decodeAtomicMemoryOp(...)`.
2. **O ramo gêmeo de SIMD&FP fica intocado.** `decodeFpLoadStoreSingle` (~1929) tem o mesmo
   `idx == IDX_UNSCALED && bit21 -> throw unsupported`. LSE é GPR-only, `V=1` não tem forma
   atômica. Não mexer.
3. **`Rs == 31` é `XZR`, `Rn == 31` é `SP`.** Trocar os dois é bug silencioso que só aparece em
   código que usa `SP` de verdade (mesma classe da armadilha de `rm=13` no NEON, B13.3).
4. **`Rt == 31` NÃO é "instrução inválida"** — é o alias arquitetural `ST<op>` (store sem retorno).
   RMW + `notifyOrdinaryWrite` acontecem; só o `setXForWidth(31, …)` vira no-op (já é, `XZR`).
5. **`notifyOrdinaryWrite` é incondicional aqui** (ao contrário de `CAS`, que só notifica no ramo
   "bateu"). O store do atomic memory op sempre acontece.
6. **Monitor de exclusividade**: não setar, não checar — só a notificação de escrita comum (que por
   efeito colateral derruba reserva pendente, igual `executeStore`).
7. **`FEAT_LRCPC` é feature nova.** Adicionar em `Aarch64Feature` E em `Aarch64Architecture.ARMV8_3_A`
   (aditivo, `extending(...)`, G3). Conferir se `Aarch64ArchitectureTest` tem asserção exaustiva de
   "features de ARMv8.3-A" para atualizar junto.
8. **`LDAPR` register-form ≠ `LDAPUR`.** `LDAPR_i`/`STLR_i` (`@ldapr_stlr_i`, offset imediato,
   `FEAT_LRCPC2`) são outro espaço, fora de escopo — não confundir e não tocar no que já
   decodifica lá.
9. **`LD64B`/`ST64B` (`FEAT_LS64`) partilham `o3=1`.** `opc ∈ {001,010,011}` com `o3=1` NÃO é SWP
   nem LDAPR — recusar explicitamente (G8), não deixar cair em nenhum ramo genérico.
10. **G4**: atomic memory op é incondicional (A64 não tem campo de condição) — `Cycle`/`Fetch`
    seguem o padrão, sem guard.
11. **`SMAX`/`SMIN` re-truncagem**: comparar com sinal em `size` bits, mas gravar o valor cru — o
    `writeMemory(size)` já mascara. Não pré-mascarar o resultado de forma que perca o sinal antes
    da comparação.

  `SMIN`/`UMAX`/`UMIN`/`SWP`.
- **`Ir64Op.AtomicMemoryOp`** novo (`Kind.ATOMIC_MEMORY_OP = 93`, + `permits`): `rs`, `rt`, `rn`,
  `size`, `operation`, `acquire`, `release`.
- **`Aarch64Decoder#decodeAtomicMemoryOp`** novo. **Desvio da spec (necessário):** o check
  `idx==UNSCALED && bit21` foi posto no **TOPO** de `decodeLoadStoreSingle`, ANTES do caso PRFM —
  não no ramo antigo da linha ~1818. Motivo: `LDADDA`/`SWPA`/... de largura `X` têm
  `size`=`11` + `A`=1 + `R`=0, que casa exatamente
  `sizeField==DOUBLEWORD && opcField==OPC_LOAD_SIGN_EXTEND_TO_X` — o caso PRFM (que roda primeiro e
  devolve `NOP_HINT` incondicionalmente) as engoliria em silêncio (G8). O ramo antigo virou
  defesa morta (`throw unsupported`, inalcançável hoje). O ramo gêmeo de `decodeFpLoadStoreSingle`
  ficou **intocado** (Armadilha 2).
- **`LDAPR`** reaproveita `Ir64Op.Load64` (`OFFSET`, imediato `0`, sem writeback), exatamente como
  `LDAR` em `decodeOrderedSingle` — sem `Kind` novo. `o3`=1+`opc`=100 com `Rs≠31`/`A≠1`/`R≠0` →
  `UNSUPPORTED` (G8). `o3`=1+`opc`∈{001,010,011} (`LD64B`/`ST64B`, `FEAT_LS64`) e {101,110,111}
  (reservado) → `UNSUPPORTED` (G8).
- **`Ir64BlockExecutor#executeAtomicMemoryOp`** novo + `case ATOMIC_MEMORY_OP` no dispatch.
  `SMAX`/`SMIN` comparam com sinal via `signExtendFromSize` (helper existente de `LDRSB`/`LDRSH`),
  gravam o valor cru (`writeMemory(size)` re-mascara). `notifyOrdinaryWrite` **incondicional**
  (store LSE sempre acontece, ao contrário de `CAS`). Monitor de exclusividade não é setado nem
  checado.
- **`Ir64NativePolicy`**: nada a editar — `default -> false` já manda `ATOMIC_MEMORY_OP` para o
  interpretado (mesma situação de `COMPARE_AND_SWAP`, também ausente da lista). `StandardIr64BlockLifter`
  idem (`isTerminal` tem `default -> false`; atomic op não troca PC).
- **`IsaCoverageReport.AARCH64_VERSION_REQUIREMENTS`**: `LDADD`/`LDCLR`/`LDEOR`/`LDSET`/`LDSMAX`/
  `LDSMIN`/`LDUMAX`/`LDUMIN`/`SWP` → `LSE`; `LDAPR` → `LRCPC`.

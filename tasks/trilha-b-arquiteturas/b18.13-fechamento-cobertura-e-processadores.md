### O que muda na medição

`IsaCoverageReport.GROUPS` tem hoje:

```java
new Group("sme.decode", "SME — extensão matricial", 32, Probe.A64, false, NOT_IN_ANY_PRESET,
        "Extensão opcional do ARMv9.2+; nenhum preset declara SME."),
```

(**medir a linha exata antes de editar** — o texto acima é o formato do vizinho `sve.decode`, não
necessariamente o literal deste grupo.)

E o mecanismo de coluna por versão, que hoje exclui explicitamente este grupo:

```java
// B11.5: só `a64.decode` (o único grupo A64 com `applicability() != NOT_IN_ANY_PRESET`,
// ver GROUPS) ganha colunas por versão — `sve.decode`/`sme.decode` continuam "não se
// aplica a nenhum preset" (nada decodifica hoje, versionar não traria informação nova).
boolean aarch64Versioned = aarch64 && group.applicability() != NOT_IN_ANY_PRESET;
```

⚠️ **O achado da B17.26 vale integralmente aqui, e é o ponto em que uma cópia mecânica de B13.22
quebra**: a `Applicability` do medidor é uma interface sobre `ArmArchitecture` (32 bits), **não**
sobre `Aarch64Architecture`:

```java
@FunctionalInterface
private interface Applicability {
    boolean appliesTo(ArmArchitecture architecture);
}
```

Para grupos A64 o medidor **não usa** `applicability().appliesTo(...)` — usa
`isApplicableToAarch64Version(instruction.name(), occurrence, aarch64Architecture)` quando
`aarch64Versioned`, e `group.applicability() != NOT_IN_ANY_PRESET` (um booleano!) quando não.
Ou seja: a mudança certa é **ligar o versionamento A64 para `sme.decode`**, deixando
`isApplicableToAarch64Version` e a curadoria de `AARCH64_VERSION_REQUIREMENTS` decidirem célula a
célula — exatamente como a B17.26 terá acabado de fazer para `sve.decode`. **Se a B17.26 já rodou,
o comentário do código acima já terá sido reescrito e o caminho já estará meio aberto**: ler o
estado real antes de editar, não este parágrafo.

`Aarch64Processor` tem hoje **39 núcleos** (medido: `CORTEX_A34` … `C1_NANO`), sem nenhum campo de
SME. Os candidatos a "tem SME de verdade" estão todos no bloco `ARMV9_2_A`+:

```java
CORTEX_A320("Cortex-A320", Aarch64Architecture.ARMV9_2_A),
```

**E é aqui que está o problema factual que o épico já antecipava** (Armadilha 1 de
`b18-plano-sme.md`): **`FEAT_SME` é OPCIONAL em ARMv9.2-A**, e vários desses núcleos **não a
implementam**. Como `ARMV9_2_A` já declara `SCALABLE_MATRIX_EXTENSION` hoje (desde a B8.3), no
momento em que esta task ligar a medição **todos os 8+4 núcleos acima passam a "prometer" SME**,
inclusive os que não têm. Não dá para resolver isso só no catálogo: ou o preset deixa de declarar a
feature e núcleos com SME ganham um preset próprio (aditivo, G3-safe — mesma solução de
`ARMV7A_NEON` na B13.22 e do que a B17.26 fizer para `NEOVERSE_V1`/`A64FX`), ou o catálogo ganha um
eixo de features por núcleo. **Decidir lendo o código e a fonte, com evidência citável por núcleo.**
Princípio B12.4/B12.6: **entrada factualmente errada é pior que ausência.**

# B17.7 — Reduções inteiras (`SADDV`/`UADDV`/`ANDV`/`SMAXV`/…) + `MOVPRFX` predicado — 19 encodings

**Trilha:** B · **Repo:** arm-jitter (+ revalidação G5) · **Depende de:** B17.6 (⬜)
**Épico:** `b17-plano-sve.md` · **Status:** ⬜ (spec escrita 2026-09-14, ainda não executada)

## Contexto

`### SVE Integer Reduction Group` inteiro (`sve.decode` linhas 330-362), 19 encodings — bate com o
"19" da escada do épico. É a família que **sai do domínio vetorial**: o destino é um escalar
`SIMD&FP` (`V<d>`), não um `Z<d>`.

### Os encodings reais (todas as 19, `@rd_pg_rn ........ esz:2 ... ... ... pg:3 rn:5 rd:5 &rpr_esz`)

```
# SVE bitwise logical reduction (predicated)
ORV             00000100 .. 011 000 001 ... ..... .....         @rd_pg_rn
EORV            00000100 .. 011 001 001 ... ..... .....         @rd_pg_rn
ANDV            00000100 .. 011 010 001 ... ..... .....         @rd_pg_rn

# SVE2.1 bitwise logical reduction (quadwords)
ORQV            00000100 .. 011 100 001 ... ..... .....         @rd_pg_rn
EORQV           00000100 .. 011 101 001 ... ..... .....         @rd_pg_rn
ANDQV           00000100 .. 011 110 001 ... ..... .....         @rd_pg_rn

# SVE constructive prefix (predicated)
MOVPRFX_z       00000100 .. 010 000 001 ... ..... .....         @rd_pg_rn
MOVPRFX_m       00000100 .. 010 001 001 ... ..... .....         @rd_pg_rn

# SVE integer add reduction (predicated)
# Note that saddv requires size != 3.
UADDV           00000100 .. 000 001 001 ... ..... .....         @rd_pg_rn
SADDV           00000100 .. 000 000 001 ... ..... .....         @rd_pg_rn

# SVE integer min/max reduction (predicated)
SMAXV           00000100 .. 001 000 001 ... ..... .....         @rd_pg_rn
UMAXV           00000100 .. 001 001 001 ... ..... .....         @rd_pg_rn
SMINV           00000100 .. 001 010 001 ... ..... .....         @rd_pg_rn
UMINV           00000100 .. 001 011 001 ... ..... .....         @rd_pg_rn

# SVE2.1 segment reduction
ADDQV           00000100 .. 000 101 001 ... ..... .....         @rd_pg_rn
SMAXQV          00000100 .. 001 100 001 ... ..... .....         @rd_pg_rn
SMINQV          00000100 .. 001 110 001 ... ..... .....         @rd_pg_rn
UMAXQV          00000100 .. 001 101 001 ... ..... .....         @rd_pg_rn
UMINQV          00000100 .. 001 111 001 ... ..... .....         @rd_pg_rn
```

### Achados desta rodada de spec

1. **`MOVPRFX_z`/`MOVPRFX_m` estão neste grupo**, não no grupo "misc" com o `MOVPRFX` não-predicado
   (que foi para a B17.5). Não são reduções — só compartilham o espaço de opcode. São as formas
   **predicadas** do prefixo construtivo, e a estratégia escolhida na B17.5 (Armadilha 1 de lá) tem
   que ser estendida a elas: `MOVPRFX_z` zera os elementos inativos, `MOVPRFX_m` os preserva.
2. **Duas famílias distintas de "redução"**:
   - `ORV`/`EORV`/`ANDV`/`SADDV`/`UADDV`/`SMAXV`/… reduzem o vetor INTEIRO a um escalar de 64 bits
     em `V<d>` (os bits altos de `V<d>` são zerados — regra de escrita destrutiva do A64);
   - `ORQV`/`EORQV`/`ANDQV`/`ADDQV`/`SMAXQV`/`SMINQV`/`UMAXQV`/`UMINQV` (**SVE2.1**, 9 linhas)
     reduzem **por segmento de 128 bits**, produzindo um `V<d>` de 128 bits com um resultado por
     segmento. Em `VL=128` há um segmento só e as duas famílias coincidem — o que é exatamente o
     argumento de "VL=128 esconde bugs" da RFC B17.2.
3. **`SADDV` exige `esz != 3`** (comentário literal do arquivo): a soma com sinal acumula em 64
   bits, então `esz=3` não teria para onde alargar. `UADDV` aceita os 4 tamanhos. Recusar `SADDV`
   com `esz=3` é G8.
4. **O resultado é sempre 64 bits**, independente do `esz`: `UADDV` de bytes soma em 64 bits
   (sem overflow), `SMAXV` de bytes devolve o byte estendido com sinal. Truncar para o `esz` é o
   bug natural.
5. **Vetor com predicado todo-zero**: a arquitetura define o valor neutro por operação (`ANDV` →
   todos-1, `ORV`/`EORV`/`UADDV`/`SADDV` → 0, `SMAXV` → o mínimo com sinal daquele `esz`, etc.).
   **Medir no QEMU** (`sve_helper.c`, os `DO_REDUCE`/`helper_sve_*v_*`), não deduzir.

## Objetivo

As 19 células decodificam e executam: 10 reduções escalares corretas em qualquer `VL`, as 8
reduções por segmento de 128 bits (SVE2.1) e as 2 formas predicadas de `MOVPRFX`.

## Inclui

1. **Reduções lógicas** (3): `ORV`, `EORV`, `ANDV`.
2. **Reduções aritméticas** (2): `SADDV` (`esz != 3`), `UADDV`.
3. **Reduções min/max** (4): `SMAXV`, `UMAXV`, `SMINV`, `UMINV`.
4. **Reduções por segmento SVE2.1** (8): `ORQV`, `EORQV`, `ANDQV`, `ADDQV`, `SMAXQV`, `SMINQV`,
   `UMAXQV`, `UMINQV` — gate por `SVE2` (**confirmar** se é `FEAT_SVE2p1`, ver Armadilha 3).
5. **`MOVPRFX_z`/`MOVPRFX_m`** (2).
6. Testes (ver Aceite).

## Não inclui

- **Reduções FP** (`FADDV`/`FMAXNMV`/`FADDA`/`FADDQV`) — B17.15.
- **`MOVPRFX` não-predicado** — B17.5.
- **`CNTP`/`FIRSTP`/`LASTP`** (contagem de predicado, que também produz escalar) — B17.4.
- **`LASTA_r`/`CLASTA_r`** (extração de elemento para GPR) — B17.11.
- **Emissão nativa/Truffle** — padrão da trilha B.

## Aceite

- As 19 linhas decodificam; `SADDV` com `esz == 3` é recusado.
- O destino é `V<d>` com os bits `[127:64]` (e, sob SVE, `[VL-1:64]`) **zerados** — mesma disciplina
  de escrita destrutiva que a B17.3 estabeleceu.
- Predicado todo-zero produz o valor neutro CORRETO por operação (teste tabelado para as 9 formas
  escalares — é o caso que o código real exercita em loop de borda).
- `UADDV` de 64 lanes de `0xFF` (`esz=0`, `VL=512`) soma em 64 bits sem truncar para 8.
- As 8 reduções por segmento produzem **um resultado por 128 bits** — teste obrigatoriamente com
  `VL >= 256` (em `VL=128` elas são indistinguíveis das escalares, ver Achado 2).
- `MOVPRFX_z` zera os elementos inativos e `MOVPRFX_m` os preserva; o par
  `MOVPRFX_z` + operação destrutiva equivale à forma construtiva com zeroing.
- Testado em pelo menos dois `VL`.
- `mvn -o test` verde + G5 verde nos 5 consumidores.

## Armadilhas

1. **Acumular no `esz`, não em 64 bits** — o bug mais provável. `UADDV` de 256 bytes `0xFF` dá
   `0xFF00` em 64 bits, não `0xFF`.
2. **As reduções por segmento (`*QV`) em `VL=128` são um falso verde.** Se a RFC B17.2 tiver
   escolhido `VL` fixo 128, estas 8 linhas ficam sem teste distintivo — documentar isso no
   `## Resultado` como limitação conhecida, nunca como "está coberto".
3. **Confirmar a feature das 8 `*QV` e das 3 `*QV` lógicas**: o arquivo diz "SVE2.1", que no manual
   é `FEAT_SVE2p1` — uma feature que a **B17.1** pode não ter criado. Se não existir,
   a saída honesta é criar a constante (aditiva, G3-safe) ou recusar as 8 linhas com `null` (`❌`
   honesto) e registrar a pendência nomeada. **Nunca** decodificá-las sob `SVE2` genérico se a
   arquitetura disser outra coisa.
4. **`MOVPRFX_z`/`MOVPRFX_m` não são reduções** e não escrevem `V<d>` — escrevem `Z<d>`. Estão
   neste grupo por acidente de encoding (Achado 1). Um executor genérico "grupo de redução" que
   trate as 19 linhas igual corrompe `Z<d>`.
5. **`ANDV` com predicado vazio devolve todos-1 no `esz`** (não em 64 bits): `ANDV b0, p0, z1.b`
   com `p0` vazio devolve `0xFF`, não `0xFFFFFFFFFFFFFFFF`. Medir no QEMU.
6. **Ordem de redução importa para FP, não para inteiro** — mas não presumir: `EORV`/`ORV`/`ANDV`
   são associativas e comutativas, `SMAXV` também; nenhuma armadilha aqui, **mas** a B17.15 (FP)
   terá, e o código compartilhado não deve assumir "reduzir em qualquer ordem" como propriedade
   geral.

## Não fazer

- Não implementar reduções FP (B17.15) nem `CNTP`/`LASTP` (B17.4).
- Não truncar o resultado para o `esz`.
- Não tratar `MOVPRFX_z|m` como redução.
- Não decodificar as 8 `*QV` sob uma feature que a arquitetura não define (Armadilha 3).

# B8.12 — A64 AdvSIMD copy (`DUP`/`INS`/`SMOV`/`UMOV`)

**Trilha:** B · **Depende de:** B8.10 ✅ (sub-dispatch `decodeAdvancedSimdExtractPermuteTable`, banco
`V` de 128 bits de B8.6)
**Repo:** arm-jitter

## Contexto

Achado documentado explicitamente pela B8.10 (`b8.10-a64-advsimd-permutacao-reducao-tabela.md`,
seção "Não inclui"): `DUP`/`INS`/`SMOV`/`UMOV` (AdvSIMD copy) vivem no MESMO prefixo vetorial
"01110", `bit21=0` que `EXT`/permute/`TBL`/`TBX` — B8.10 já tinha criado o sub-dispatch
(`decodeAdvancedSimdExtractPermuteTable`) e reconhecia o discriminador (`bit15=1` do campo
`opcode`), mas devolvia `null` de propósito (G8: recusa em vez de arriscar colisão), deixando como
"candidata a task própria". Priorizada pelo usuário em 2026-08-26 entre 3 opções (esta, `G6.2` e
`G6.3` do n3dsemu).

⚠️ **Sem spec formal escrita antes da implementação** — mesmo padrão ad-hoc de B8.4-B8.11 (task
pequena o bastante para não precisar de rodada de spec separada prévia). Este arquivo documenta o
resultado, não um plano prévio.

## Achado estrutural: o discriminador real é `bit10`, não `bit15`

A premissa herdada de B8.10 ("`bit15=1` dentro do sub-dispatch existente") estava **parcialmente
errada**: o gate `if (bit10) return null;` no TOPO de `decodeAdvancedSimdExtractPermuteTable`
(que existe desde B8.10 para excluir "qualquer coisa que não seja EXT/permute/TBL/TBX") já
descartava TODA a família "AdvSIMD copy" antes mesmo de chegar ao `if (bit15)` — porque as 5
instruções desta família têm **`bit10=1` fixo** no encoding real (o "1" antes de `Rn` no padrão
`ARM DDI 0487`), o oposto exato de `EXT`/permute/`TBL`/`TBX` (`bit10=0`). Confirmado bit a bit
contra corpus real (`aarch64-none-elf-as`/`objdump`, devkitA64): todas as 30+ palavras assembladas
para este teste têm bit10 setado.

Por isso a implementação criou um método NOVO (`decodeAdvancedSimdCopy`), despachado a partir do
`if (bit10)` (que antes só devolvia `null`), em vez de reaproveitar o `if (bit15)` já existente
dentro de `decodeAdvancedSimdExtractPermuteTable` (esse continua servindo só para reservado dentro
do espaço `bit10=0`).

## Escopo real (5 instruções, `ARM DDI 0487 C6.2.109/176/240/355`)

`U`(bit29) separa duas formas:

- **`U=0`** — `imm4` (bits[14:11]) seleciona: `DUP_element`(`0000`)/`DUP_general`(`0001`)/
  `INS_general`(`0011`)/`SMOV`(`0101`)/`UMOV`(`0111`). Valores fora desta lista são reservados.
- **`U=1`** — `INS_element` (único mnemônico desta forma).

Em todos os 5, `esz`/índice(s) vêm de `imm5` (bits[20:16], mesma posição de `Rm`/`di` alhures) pela
fórmula padrão do manual: `esz = LowestSetBit(imm5)`, `index = imm5 >>> (esz+1)` — `imm5==0` ou
`esz>3` é reservado. `INS_element` tem um segundo índice (`si`, bits[14:11]) derivado de
`srcIndex = si >>> esz` (SEM marcador de tamanho próprio — o `esz` já vem de `imm5`/`di`).

Restrições de validade adicionais, todas conferidas bit a bit contra corpus real e codificadas no
decoder (G8, nunca um encoding ERRADO):

- `DUP` (as duas formas): `esz==3` (doubleword) exige `Q=1` (não existe arranjo "1D").
- `INS_general`/`INS_element`: `Q` é **fixo em `1`** no encoding real (não uma escolha de arranjo
  — inserir sempre referencia o registrador `V` inteiro); `Q=0` é reservado.
- `SMOV`: `esz<3` sempre (não existe forma para doubleword — nada maior que `Xd` para
  sign-estender); `esz==2` exige `Q=1` (`SMOV Wd,Vn.S[i]` seria redundante com `UMOV`/`MOV`).
- `UMOV`: `Q == (esz==3)` **sempre** — não existe forma "estendida" redundante (`UMOV Wd` já zero-
  estende automaticamente para `Xd` na leitura seguinte, mesmo comportamento arquitetural de toda
  escrita `W`).

## Armadilhas (para quem mexer neste espaço de encoding depois)

- O discriminador entre "EXT/permute/TBL/TBX" (B8.10) e "AdvSIMD copy" (esta task) é **`bit10`**,
  não `bit15` — a nota "Não inclui" da B8.10 citava `bit15=1` porque essa era a leitura do
  `opcode` de 5 bits DENTRO do sub-dispatch que já filtrava `bit10=0`; o `bit15` real do word (LSB
  do campo de 5 bits que inclui `bit10`) não é o mesmo bit que separa as duas famílias no nível do
  chamador. Ver o comentário em `decodeAdvancedSimdExtractPermuteTable` e o novo
  `decodeAdvancedSimdCopy`.
- `INS_element` usa o MESMO bit `U`(29) que `EXT` (ambos `u=1`) — não colidem porque `EXT` exige
  `bit10=0` e `INS_element` exige `bit10=1` (o gate do topo já separa os dois antes de qualquer
  outro campo ser lido).
- `si` (índice fonte de `INS_element`) NÃO tem marcador de tamanho próprio — ao contrário de
  `imm5`/`di` (que usa `LowestSetBit`), `si` é lido cru e desloca `>>> esz`, com `esz` vindo
  inteiramente do lado DESTINO (`di`). Um `si` com bits baixos "sujos" (não múltiplos de
  `1<<esz`) não é validado pelo hardware nem por este decoder — mesma leniência do manual real.

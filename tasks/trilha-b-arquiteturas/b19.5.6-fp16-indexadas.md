# B19.5.6 — `FEAT_FP16`: formas INDEXADAS (8 linhas, `size = 00`)

**Trilha:** B · **Repo:** arm-jitter (+ revalidação G5) · **Depende de:** B19.5.4
**Plano:** `b19.5-plano-fp16.md` · **Épico:** `b19-plano-a64-gap-remanescente.md` · **Status:** ⬜

## Contexto

Último degrau de decode da escada B19.5, e **o mais barato dos quatro** — a medição desta spec mostra
que a infraestrutura inteira já existe e só falta destravar uma constante.

As 8 linhas são as formas "×  indexed element" de meia precisão:

| Bloco | Linhas | Mnemônicos |
|---|---:|---|
| Escalar `@rrx_h` | 4 | `FMUL_si` `FMLA_si` `FMLS_si` `FMULX_si` |
| Vetorial `@qrrx_h` | 4 | `FMUL_vi` `FMLA_vi` `FMLS_vi` `FMULX_vi` |

### O que já existe (medido)

Nesta classe, **`size` (bits[23:22]) escolhe o tamanho do elemento** — não é o `a`/`sz` das outras
famílias FP. E o `Aarch64Decoder` já diz, num comentário da B8.19 (`:1155-1161`), exatamente onde
está a porta:

```java
// ── `size`(23:22) ... `01`=halfword (só inteiro), `10`=word (inteiro E ponto flutuante,
// ── discriminados pelo opcode nibble+`U`), `11`=doubleword (só ponto flutuante, `bit21` fixo
// ── em `0`); `00` é meia-precisão (`FEAT_FP16`), fora de escopo.
```

E — o achado que barateia a task — **a montagem do índice e o estreitamento de `Rm` já estão
implementados**, porque `size = 01` (halfword INTEIRO) usa **o mesmo esquema**:

```java
// ── Índice do elemento de `Rm` é MONTADO a partir de bits espalhados (`H`=bit11 sempre;
// ── `L`=bit21 para word/doubleword; `L:M`=bits[21:20] para halfword, `M` também estreita `Rm`
// ── a `V0`-`V15`) — ver decodeAdvancedSimdIndexedElementIndex.
```

Conferido contra `a64.decode`: `@rrx_h` é `rm:4` + `idx=%hlm` (3 bits `H:L:M`), idêntico ao que
`size = 01` já usa. `@rrx_s` é `rm:5` + `idx=%hl`; `@rrx_d` é `rm:5` + `idx:1`.

⇒ **Esta task é: aceitar `size == 0b00` para os opcodes de FP, sob a feature.** Sem índice novo, sem
record novo, sem `Kind` novo, sem semântica nova (`AdvSimdLanes` já tem `esz = 1` desde a B19.5.1).

**Leitura obrigatória**: a **B8.19** (`## Resultado` INTEIRO — ela construiu esta classe e o
estreitamento de `Rm`), a **B19.5.4** (`## Resultado` — o gate de `FP16` e o padrão de reuso), e a
**B19.5.1** (a fundação `binary16`). No código: `decoder64/Aarch64Decoder#decodeAdvancedSimdIndexedElement`
INTEIRO, `#decodeAdvancedSimdIndexedElementIndex`, `#decodeAdvancedSimdIndexedFpOpcode`,
`ADVSIMD_INDEXED_SIZE_*`/`ADVSIMD_INDEXED_RM_H_MASK`/`ADVSIMD_INDEXED_LM_*` (`:1162-1172`);
`executor64/Ir64VectorArithmeticByElementExecutor` (ou o nome real do executor de B8.19);
`advsimd/AdvSimdLanes#fpThreeSame` (o ramo `esz=1`).

## Objetivo

As **8 linhas** decodificam e executam sob `ARMV8_2_A`+, gateadas por `Aarch64Feature.FP16`, e
continuam recusadas em `ARMV8_0_A`/`ARMV8_1_A`. **Zero record novo, zero `Kind` novo.**

## Inclui

1. **Aceitar `size == 0b00`** em `decodeAdvancedSimdIndexedElement`, **só** para os opcodes de ponto
   flutuante (`FMUL`/`FMLA`/`FMLS`/`FMULX`) e **só** com `Aarch64Feature.FP16`. Constante nomeada
   (G6): `ADVSIMD_INDEXED_SIZE_HALF_PRECISION = 0b00`, com Javadoc `///` PT.
2. **Índice**: para `size = 00` usar o MESMO caminho de `size = 01` — `L:M` em bits[21:20], `H` em
   bit11, `Rm` estreitado a `V0`-`V15` (`ADVSIMD_INDEXED_RM_H_MASK`). **Não escrever caminho novo**;
   se o método atual escolher o esquema por `size == ADVSIMD_INDEXED_SIZE_HALFWORD`, estender a
   condição para incluir `0b00`.
3. **Opcodes FP**: `FMUL` = `1001`, `FMLA` = `0001`, `FMLS` = `0101`, `FMULX` = `1001` com `U = 1`
   (bits[15:12] + `U`). São os MESMOS de `size = 10`/`11` — reusar `decodeAdvancedSimdIndexedFpOpcode`
   sem duplicar.
4. **`esz` do record** = `ADVSIMD_ESZ_HALFWORD`, derivado do `size`, como as outras larguras.
5. **G8**: com `size = 00`, todo opcode que NÃO for um dos 4 de FP tem que `throw unsupported` —
   inclusive os opcodes INTEIROS (`MUL`/`MLA`/`MLS`/`SQDMULH`/…), que em meia precisão não existem
   (o inteiro de halfword é `size = 01`). Ver Armadilha 2.
6. **Executor**: nenhuma mudança esperada — o executor de B8.19 já opera por `esz`, e
   `AdvSimdLanes.fpThreeSame` tem `esz = 1` desde a B19.5.1. **Confirmar e registrar.**
7. Testes (ver Aceite).

## Não inclui (com destino explícito)

- **`FMLAL_vi`/`FMLSL_vi`/`FMLAL2_vi`/`FMLSL2_vi`** (`FEAT_FHM`) e **`BFMLAL_vi`** (`FEAT_BF16`) e
  **`FDOT_hb_vi`** (FP8) — moram na MESMA classe indexada e **também** usam `size = 00`. Recusar
  explicitamente (G8) ⇒ **B19.7** (BF16/FP8) e task própria (FHM).
- **`FEAT_FP16` nas outras classes** — B19.5.3/.4/.5 já as cobriram.
- **`FPCR.RMode`/`FZ`/exceções**, **`FPSR.QC`**, **emissão nativa**.

## Especificação

### Encodings (oráculo: `target/isa-decode/a64.decode:1234-1292`)

```
FMUL_si    0101 1111 00 .. .... 1001 . 0 ..... .....   @rrx_h   (:1234)  size=00
FMUL_si    0101 1111 10 .  ..... 1001 . 0 ..... .....   @rrx_s   (:1235)  size=10  ← já ✅
FMUL_si    0101 1111 11 0  ..... 1001 . 0 ..... .....   @rrx_d   (:1236)  size=11  ← já ✅
FMLA_si    0101 1111 00 .. .... 0001 . 0 ..... .....   @rrx_h   (:1238)
FMLS_si    0101 1111 00 .. .... 0101 . 0 ..... .....   @rrx_h   (:1242)
FMULX_si   0111 1111 00 .. .... 1001 . 0 ..... .....   @rrx_h   (:1246)  U=1
FMUL_vi/FMLA_vi/FMLS_vi/FMULX_vi                        @qrrx_h  (:1273/1277/1281/1285)

@rrx_h   ........ .. .. rm:4 .... . . rn:5 rd:5   &rrx_e esz=1 idx=%hlm
@rrx_s   ........ .. .  rm:5 .... . . rn:5 rd:5   &rrx_e esz=2 idx=%hl
@rrx_d   ........ .. .  rm:5 .... idx:1 . rn:5 rd:5  &rrx_e esz=3
```

- **`size = 00` é meia precisão**, e nesta classe `size` é tamanho de verdade (não é `a`/`sz`).
- `@rrx_h` tem `rm:4`: o bit `M` (bit20) deixa de ser parte de `Rm` e vira o bit BAIXO do índice —
  exatamente como em `size = 01`, já implementado.
- Índice: `H`(bit11) : `L`(bit21) : `M`(bit20) ⇒ 3 bits, faixa `0..7` (8 lanes de `8h`).

### Por que a lane count fecha

`8h` tem 8 lanes ⇒ índice de 3 bits ⇒ `H:L:M`. `4s` tem 4 ⇒ 2 bits (`H:L`) ⇒ `Rm` pode usar os 5
bits. `2d` tem 2 ⇒ 1 bit (`H`). O estreitamento de `Rm` **é consequência** de precisar do terceiro
bit — e é a mesma conta que a B8.19 já fez para o inteiro de halfword.

## Aceite

## Armadilhas

1. **Nesta classe `size` É tamanho.** Depois de B19.5.3/.4/.5, o reflexo é ler bits[23:22] como
   `a`/`sz` — aqui não. `00`=half, `01`=halfword inteiro, `10`=word, `11`=doubleword.
2. **`size = 00` NÃO é "inteiro de byte".** Não existe forma indexada de elemento de 8 bits; o
   inteiro de halfword é `size = 01`. Aceitar opcodes inteiros com `size = 00` decodificaria lixo
   (G8) — recusar explicitamente e testar.
3. **`M` (bit20) muda de papel com o tamanho.** Em `size` `10`/`11` é bit de `Rm`; em `00`/`01` é o
   bit baixo do índice e `Rm` encolhe. Usar o caminho já existente, não recalcular.
4. **`FMULX` compartilha o opcode `1001` com `FMUL`** — só `U` (bit29) separa. Mesmo par que já
   existe em `size = 10`.
5. **`FMLA`/`FMLS` leem `Rd`.** Um executor que só escreva quebra as duas.
6. **Gate ausente** ⇒ `ARMV8_0_A` decodificando meia precisão.

## Não fazer

- Não escrever caminho novo de montagem de índice.
- Não aceitar opcodes inteiros com `size = 00`.
- Não deixar FHM/BF16/FP8 passarem.
- Não duplicar `decodeAdvancedSimdIndexedFpOpcode`.
- Não modelar `FPCR.RMode`/`FZ`/`FPSR.QC`.
- Não adicionar caso nativo em `Ir64NativePolicy`.

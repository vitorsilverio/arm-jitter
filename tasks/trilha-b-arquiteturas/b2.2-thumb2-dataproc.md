# B2.2 — Data-processing Thumb-2 de 32 bits

**Trilha:** B · **Depende de:** B2.1 · **Repo:** arm-jitter

## Contexto

Com o fetch de 32 bits e o mecanismo de extensão do B2.1 prontos, esta task preenche o
maior grupo de instruções Thumb-2: data-processing (equivalente ARM de 32 bits, mas com
encoding próprio Thumb-2 — não é "ARM decodificado como Thumb"). Precedente interno a
espelhar: como `ArmDecoder` decodifica data-processing ARM hoje (immediate rotation,
shifts, `S` bit, `Rd`/`Rn`/`Rm`) — a semântica de IR é a MESMA (`IrOp.Alu` +
`ShiftedRegister`), só o encoding de origem muda. **O IR não muda nesta task** (decisão
já registrada em `b2-thumb2.md`).

## Objetivo

Decodificar e liftar para IR (interpretador via fallback PER_OP existente; ASM nativo
fica para uma task futura de emissão, fora do escopo aqui — replicar o padrão de
B1.2-B1.5 que ficaram só no interpretador até B1.6):

- Data-processing com "modified immediate" (o encoding de imediato de 12 bits do
  Thumb-2, DIFERENTE do imediato rotate-8 do ARM clássico — tem seu próprio esquema de
  replicação de bytes/rotação, ler o manual com cuidado).
- `MOVW` (carrega imediato de 16 bits em Rd, zera o resto) e `MOVT` (carrega imediato
  de 16 bits na metade alta de Rd, preserva a baixa).
- Data-processing com registrador e shift imediato (forma "register" do Thumb-2,
  equivalente ao ARM shifted-register mas com encoding próprio).
- `ADD`/`SUB` com `Rd`/`Rn` = SP ou PC (formas especiais do Thumb-2 para cálculo de
  endereço, comuns em prólogo/epílogo de função compilada).

## Especificação

1. **Encodings:** ARM Architecture Reference Manual, Thumb-2 Supplement (ou ARMv7-A/R
   DDI 0406, seção A5.3 "32-bit Thumb instruction encoding" → A5.3.1-A5.3.4 data
   processing). Atenção especial ao algoritmo do "modified immediate" (campo `i:imm3:a`
   e os 4 casos de decodificação de `ThumbExpandImm` com carry-out para o bit C quando
   `S=1`) — é uma tabela própria, não reaproveita o rotate-imm do ARM.
2. **IR:** reusar `IrOp.Alu` + `ShiftedRegister` exatamente como o ARM 32-bit usa hoje
   (ler `StandardIrBuilder` para o caminho ARM data-processing e espelhar). `MOVW`/
   `MOVT` podem precisar de um caso novo em `IrAluExecutor` se não encaixarem em `Alu`
   existente (MOVT em particular: "escreve só a metade alta, preserva a baixa" não é um
   padrão ALU comum — decidir lendo o código do IR primeiro).
3. Registrar o handler no mecanismo de extensão do B2.1.
4. `S` bit (`ADDS`/`SUBS`/...) seta flags **igual ao ARM** — carry-out do
   ThumbExpandImm quando aplicável (ver B1.2/C2 como precedente de "carry-out do
   shifter" para a forma register).

## Testes mínimos

- Vetores concretos do ThumbExpandImm cobrindo os 4 casos de decodificação (incluindo
  o caso com carry-out para `S=1`).
- `MOVW Rd, #0x1234` seguido de `MOVT Rd, #0x5678` = `Rd == 0x56781234`.
- `ADD Rd, SP, #imm` (cálculo de endereço de stack) e `ADD Rd, PC, #imm` (equivalente a
  ADR) — casos usados por TODO código compilado com GCC/Clang thumb2.
- Forma "register" com shift imediato, comparando resultado E flags com o ARM
  equivalente (mesmo operando, mesmo shift) via harness de equivalência.
- Cada instrução também testada num preset sem `THUMB2` provando que a task B2.1
  ainda mantém undefined lá (G2).

## Aceite

- `mvn test` verde; gbaemu/ndsemu verdes (G5) — nenhuma emissão ASM nativa nesta task.
- Cobertura de equivalência: bloco Thumb-2 data-processing roda no fallback PER_OP sem
  divergência do interpretador (mesmo harness usado em B1.2-B1.5).

## Armadilhas

- **Não confundir o "modified immediate" do Thumb-2 com o rotate-imm do ARM clássico**
  — são algoritmos diferentes, mesmo que pareçam parecidos.
- `MOVT` afeta só bits[31:16] — um erro comum é reimplementar como MOV+shift, que
  destrói os bits[15:0] existentes.
- `ADD Rd, PC, #imm` usa PC **alinhado a 4 bytes** (mascara bits[1:0]), igual ao ADR do
  ARM — conferir se o `ArmCore`/lifter já tem esse alinhamento centralizado em algum
  lugar reutilizável antes de duplicar a lógica.

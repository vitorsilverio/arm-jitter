# B6.6.5 — AArch64: `translationGeneration` no `BlockKey64`/`JitRuntime64`

**Trilha:** B · **Depende de:** B6.6.4 (aborts + `TLBI`/`setTtbr0` reais) e
B6.4 ✅ (`jit64/BlockKey64`/`JitRuntime64` precisam existir) · **Repo:** arm-jitter

## Contexto

Quinta das 6 sub-tasks de B6.6 (ver decomposição em B6.6.1). Espelho direto
de **B4.1.4** (`translationGeneration` no `BlockKey`/`JitRuntime`, 32-bit) —
mas para `jit64/BlockKey64`/`JitRuntime64` (B6.4). RFC-IR-64BIT.md §5 item 3
já antecipa esta task explicitamente: *"Não introduzir novos empacotamentos
'PC cabe em 32 bits' (como a tag do IC atual) em código de infraestrutura
nova; se precisar de tag, isolar a estratégia de tag por runtime"* — ou seja,
o esquema de tag do inline-cache 32-bit (`long tag = pc | instructionSet.ordinal()
<< 32`) NÃO pode ser reaproveitado por empacotamento (A64 já usa o `pc`
inteiro de 64 bits, sem sobra de bits) — precisa de uma estratégia de tag
PRÓPRIA do runtime A64, que hoje (B6.4) nem tem inline cache implementado
ainda (ver Fatos de referência #1).

## Fatos de referência

1. **`jit64/BlockKey64.java` hoje**: `public record BlockKey64(long pc) {}`
   — 1 campo só (confirmado por leitura nesta rodada de pesquisa), com
   javadoc explícito: *"sem `translationGeneration` (A64 ainda não tem MMU —
   isso é a task futura B6.6)"* — ou seja, o precedente já deixou o
   comentário apontando para ESTA task.
2. **`jit64/JitRuntime64.java` (B6.4 D5)**: "caminho clássico (pré-tiering) —
   sem cache [de inline cache], interpreta via `Ir64BlockExecutor.step` até
   atingir o threshold, então compila e cacheia" — **B6.4 D0 registrou
   explicitamente que `jit64/` NÃO tem inline cache, encadeamento nem
   tiering em background** (pendências explícitas daquela task, sem
   consumidor real medido ainda). **Consequência para esta task**: só DOIS
   dos três pontos de uso que o precedente 32-bit tem (B4.1.4: chave de
   lift, flush de inline cache, guard de encadeamento) se aplicam
   HOJE ao `jit64/` — não há inline cache nem encadeamento para os outros
   dois pontos consumirem. **Decisão: implementar só o ponto que existe
   (chave do `BlockCache64`)**, registrando os outros dois como pendência
   que "cai de graça" quando/se IC e encadeamento forem adicionados a
   `jit64/` no futuro (mesma disciplina "sem consumidor real" de B6.4 D0).
3. **`AddressSpace64.translationGeneration()`** já tem o default `0`
   (B6.6.2 D4) — esta task só precisa que `TranslatingAddressSpace64`
   (B6.6.2) já incremente de verdade (D5 daquela task) e que `JitRuntime64`
   passe a LER o valor.

## Decisões de desenho FECHADAS nesta rodada

### D1 — `BlockKey64` ganha `int translationGeneration`, 2 campos totais

```java
public record BlockKey64(long pc, int translationGeneration) {
    public BlockKey64(long pc) { this(pc, 0); }  // construtor de compatibilidade preservado
}
```
Mesma técnica exata do precedente 32-bit (`BlockKey`, B4.1.4 — construtores
de compatibilidade preservados e testados). Todo chamador existente de
`new BlockKey64(pc)` continua compilando sem mudança (G3).

### D2 — `BlockCache64`/`JitRuntime64.execute` usam a chave de 2 campos

`JitRuntime64.execute(long pc, Aarch64Core core)` lê
`core.memory().translationGeneration()` uma vez por chamada (mesmo padrão do
precedente) e usa no `BlockKey64` do lookup/lift — uma troca de geração vira
MISS natural no `BlockCache64` (mesmo mecanismo "sem invalidação explícita"
que o precedente 32-bit documentou, e que já é a ÚNICA consequência real
possível hoje dado que `jit64/` não tem IC nem encadeamento, Fatos de
referência #2).

### D3 — Pendência explícita: IC/encadeamento de `jit64/` ainda não
existem, então os 2 outros pontos de uso do precedente 32-bit não se
aplicam ainda

Registrar no javadoc de `JitRuntime64`/`BlockKey64` que, se uma PR futura
adicionar inline cache ou encadeamento a `jit64/` (pendência já registrada
em B6.4 Armadilhas), essa PR precisa LEMBRAR de checar
`translationGeneration` nesses dois pontos novos também — mesmo achado
"a corrente de encadeamento é código mais novo que a RFC original" que
B4.1.4 (32-bit) documentou como achado próprio daquela task, para não se
perder de novo aqui.

## Objetivo

- `BlockKey64` com `translationGeneration` (D1).
- `JitRuntime64.execute` consultando a geração no lookup/lift (D2).

## Especificação

1. `jit64/BlockKey64.java`: 2º campo + construtor de compatibilidade (D1).
2. `jit64/JitRuntime64.java`: ler `core.memory().translationGeneration()`
   uma vez por `execute`, usar no `BlockKey64` (D2).
3. Javadoc de pendência (D3) em ambos os arquivos.

## Não inclui

- Inline cache/encadeamento para `jit64/` (não existem ainda — B6.4 D0).
- Per-ASID caching (mesma simplificação aceita do precedente 32-bit,
  RFC-SOFTMMU.md §5 — geração global monotônica, revisitar uma tabela já
  vista antes conta como geração NOVA e recompila em vez de reencontrar o
  bloco antigo).

## Testes mínimos (`JitRuntime64TranslationGenerationTest`, espelhando
`JitRuntimeTranslationGenerationTest` do precedente 32-bit)

1. Duas tabelas de página L0-L3 montadas à mão (B6.6.2) mapeando o MESMO VA
   para código físico DIFERENTE; duas "trocas de processo" via
   `TranslatingAddressSpace64.setTtbr0`+`invalidateTlbAll`; cada troca
   executa o código correto (nunca o bloco stale da geração anterior).
2. Construtor de compatibilidade `BlockKey64(long pc)` continua funcionando
   (`translationGeneration=0` default).
3. Regressão: suíte completa de B6.1-B6.6.4 sem mudança — em particular,
   nenhum teste de `JitRuntime64Test` (B6.4) que não envolva MMU muda de
   comportamento (todos usam `translationGeneration=0` implícito).

## Aceite

- `mvn -o test` verde; `mvn -o install` verde. G5 não se aplica (infra A64
  isolada, nenhum arquivo 32-bit tocado — diferente do precedente 32-bit,
  onde B4.1.4 TINHA que revalidar gbaemu/ndsemu porque `BlockKey`/
  `JitRuntime`/`AddressSpace` são compartilhados; aqui `BlockKey64`/
  `JitRuntime64`/`AddressSpace64` são exclusivos do mundo A64, sem consumidor
  32-bit — mesmo precedente de TODA sub-task A64 desde B6.1).

## Armadilhas

- **`jit64/` não tem IC/encadeamento hoje** — não inventar esses dois
  mecanismos só para ter "os 3 pontos de uso" do precedente; implementar só
  o que existe (D2), registrar o resto como pendência (D3).
- **Construtor de compatibilidade é obrigatório** — qualquer código
  existente que construa `BlockKey64(pc)` diretamente (testes de B6.4, por
  exemplo) não pode quebrar.
- **Mesma simplificação "sem per-ASID"** aceita explicitamente — não tentar
  otimizar isso nesta task.

## Resultado

✅ (2026-07-27) — espelho direto de B4.1.4 (32-bit), mas menor: `jit64/` não tem inline cache nem encadeamento (B6.4 D0), então só o ponto de lookup/lift de `JitRuntime64.execute` existe hoje (D2/D3). `BlockKey64` ganhou 2º campo `int translationGeneration` (D1) com construtor de compatibilidade `BlockKey64(long pc)` preservando `translationGeneration=0` (todo chamador existente de B6.4 continua compilando). `JitRuntime64.execute` passou a ler `core.memory().translationGeneration()` uma vez por chamada e usar no `BlockKey64` do lookup/lift — troca de `TTBR0_EL1` vira MISS natural no `BlockCache64`. Javadoc de pendência (D3) registrado em ambos os arquivos: se uma PR futura adicionar IC/encadeamento a `jit64/`, precisa lembrar de checar `translationGeneration` nesses pontos novos também. `JitRuntime64TranslationGenerationTest` novo (espelho de `JitRuntimeTranslationGenerationTest`): duas tabelas de página L0-L3 completas (4 níveis reais) mapeando o mesmo VA para código físico diferente, troca via `TranslatingAddressSpace64.setTtbr0`+`invalidateTlbAll`, cada troca executa o `MOVZ` certo, nunca o bloco stale da geração anterior; + teste do construtor de compatibilidade. `mvn -o test` verde (core 1254 + truffle 13); `mvn -o install` verde. G5 não se aplica — `BlockKey64`/`JitRuntime64`/`AddressSpace64` são exclusivos do mundo A64, confirmado por grep (nenhum arquivo 32-bit referencia essas classes). Épico B6.6 quase fechado: só falta B6.6.6 (bloqueada no usuário)

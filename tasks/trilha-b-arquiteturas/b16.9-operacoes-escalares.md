# B16.9 — MVE: operações escalares (vetor × registrador geral) — 35 encodings

**Trilha:** B · **Repo:** arm-jitter (+ revalidação G5) · **Depende de:** B16.6 (⬜)
**Épico:** `b16-plano-mve-helium.md` · **Status:** ⬜ (spec escrita 2026-09-13, ainda não executada)

## Contexto

Nono degrau da escada B16 (partição normativa na spec da **B16.1**). O épico conta 39 para a seção
`# Scalar operations` (linhas 496-573); a medição desta rodada de spec confirma as 39 linhas do
intervalo, mas **4 delas são comparações** (`VCMPEQ_fp_scalar`/`VCMPNE_fp_scalar`/
`VCMPLT_fp_scalar`/`VCMPGE_fp_scalar`, linhas 499/500/505/506) e foram para a **B16.8**, onde
pertencem semanticamente. Sobram **35** aqui.

O traço comum: o segundo operando é um **registrador geral** (`rm:4`), cujo valor é replicado por
todas as lanes (broadcast) — ou usado como contagem de deslocamento única (`*_scalar` de shift).

### O encoding real (`target/isa-decode/mve.decode`, linhas 92-93, 119 e 496-573 — medido)

Formatos:

```
@2scalar      .... .... .. size:2 .... .... .... .... rm:4 &2scalar qd=%qd qn=%qn
@2scalar_nosz .... .... .... .... .... .... .... rm:4 &2scalar qd=%qd qn=%qn
@shl_scalar   .... .... .... size:2 .. .... .... .... rm:4 &shl_scalar qda=%qd
@2op_fp_scalar .... .... .... .... .... .... .... rm:4 &2scalar qd=%qd qn=%qn size=%2op_fp_scalar_size

&2scalar qd qn rm size
&shl_scalar qda rm size
%2op_fp_scalar_size 28:1 !function=neon_3same_fp_size
%size_28 28:1 !function=plus_1
```

As 35 linhas, agrupadas pelos blocos `{}` reais:

```
{ VCMPEQ_fp_scalar (B16.8) / VCMPNE_fp_scalar (B16.8) / VADD_scalar  1110 1110 0 . .. ... 1 ... 0 1111 . 100 .... @2scalar }
{ VCMPLT_fp_scalar (B16.8) / VCMPGE_fp_scalar (B16.8) / VSUB_scalar  1110 1110 0 . .. ... 1 ... 1 1111 . 100 .... @2scalar }
{ VSHL_S_scalar / VRSHL_S_scalar / VQSHL_S_scalar / VQRSHL_S_scalar / VMUL_scalar }      # 5 linhas
{ VSHL_U_scalar / VRSHL_U_scalar / VQSHL_U_scalar / VQRSHL_U_scalar / VBRSR }            # 5 linhas
{ VADD_fp_scalar / VHADD_S_scalar / VHADD_U_scalar }                                     # 3
{ VSUB_fp_scalar / VHSUB_S_scalar / VHSUB_U_scalar }                                     # 3
{ VQADD_S_scalar / VQADD_U_scalar / VQDMULLB_scalar (@2scalar_nosz size=%size_28) }       # 3
{ VQSUB_S_scalar / VQSUB_U_scalar / VQDMULLT_scalar (@2scalar_nosz size=%size_28) }       # 3
{ VMUL_fp_scalar / VQDMULH_scalar / VQRDMULH_scalar }                                     # 3
{ VFMA_scalar  / VMLA   111 - 1110 0 . .. ... 1 ... 0 1110 . 100 .... @2scalar }          # 2
{ VFMAS_scalar / VMLAS  111 - 1110 0 . .. ... 1 ... 1 1110 . 100 .... @2scalar }          # 2
VQRDMLAH / VQRDMLASH / VQDMLAH / VQDMLASH                                                 # 4
```

2 + 5 + 5 + 3 + 3 + 3 + 3 + 3 + 2 + 2 + 4 = **35**.

### Dois achados de encoding que o arquivo documenta em comentário e que são fáceis de errar

1. **`VMLA`/`VMLAS` usam `111 -` (bit 28 don't-care), não `111 .`**:
   ```
   # The U bit (28) is don't-care because it does not affect the result
   VMLA   111 - 1110 0 . .. ... 1 ... 0 1110 . 100 .... @2scalar
   ```
   Ou seja: os DOIS valores de bit 28 dão a mesma instrução, e o par `VFMA_scalar`/`VMLA` no mesmo
   `{}` se distingue por `bits[21:20] == 11` (a forma FP) versus `size` livre (a inteira).
2. **`@shl_scalar` usa `qda`, não `qd`+`qn`**: o destino É o acumulador/fonte (`&shl_scalar qda rm
   size`), com `size` em `bits[19:18]` (`.... size:2 ..`), e o operando escalar `rm` é a CONTAGEM de
   deslocamento — não um valor replicado por lane. `VSHL_*_scalar` desloca `Qda` por um escalar; é
   diferente de `VSHL_S`/`VSHL_U` da B16.6 (deslocamento por vetor, `@2op_rev`) e de `VSHLI` da
   B16.10 (por imediato).

### Regras de registrador (QEMU `translate-mve.c`, via `WebFetch` nesta rodada)

```c
if (a->rm == 13 || a->rm == 15) {
    return false;  /* UNPREDICTABLE (scalar ops) */
}
```
mais `mve_check_qreg_bank` (`Qd`/`Qn` `< 8`) e, nas formas alargantes (`VQDMULLB_scalar`/
`VQDMULLT_scalar`), a restrição `Qd == Qn` UNDEF (confirmar).

## Objetivo

As 35 linhas decodificam sob o gate correto (`MVE_INTEGER`/`MVE_FLOAT` por linha) e executam
vetor × escalar-de-GPR com predicação por elemento e `FPSCR.QC` só para lanes ativas. 35 células
`·`/`❌` → `✅`.

## Inclui

1. **Decode das 35 linhas**, com `rm:4` (recusando `13`/`15`), `%qd`/`%qn`/`qda=%qd`, `size` de 2
   bits (ou `%2op_fp_scalar_size`, ou `%size_28`), e as recusas de `Q > 7`, `size == 3`,
   `Qd == Qn` onde aplicável. **Excluir explicitamente** as 4 `VCMP*_fp_scalar` (B16.8) que dividem
   os dois primeiros blocos `{}`.
2. **Broadcast do escalar**: `Rm` é lido UMA vez e replicado por lane conforme `size` (usar
   `AdvSimdLanes#replicateElement`/`VfpRegisters#replicateElement` da B13.1 se a forma bater, ou
   `AdvSimdLanes#threeSameByElement` — **auditar antes de escrever**, mesma disciplina da B16.6).
3. **Execução** com predicação + `QC` só para lanes ativas.
4. **`VBRSR`** (bit reverse and shift right) — operação sem análogo em NEON/A64: transcrever
   `DO_VBRSR` do `mve_helper.c`.
5. **`VFMA_scalar`/`VFMAS_scalar`** (fused multiply-add com escalar; `VFMAS` tem a ORDEM dos
   operandos diferente — `Qd = Qd*Qn + Rm` vs `Qd = Qd*Rm + Qn`; **confirmar qual é qual**).
6. Testes (ver Aceite).

## Não inclui

- As 4 `VCMP*_fp_scalar` das linhas 499/500/505/506 — **B16.8**.
- `VSHL_S`/`VSHL_U` por vetor (B16.6) e `VSHLI` por imediato (B16.10) — mnemônicos parecidos,

- Reduções para GPR (`VADDV`/`VMLADAV`/`VMAXV`) — **B16.13**; ali o GPR é DESTINO, aqui é fonte.

### Achado central de encoding (medido bit a bit, script descartável, mesma disciplina da B16.8)

`bits[27:24]` é `1110` FIXO em TODA a seção "Scalar operations" (diferente de
`Thumb2MveVector2opDecoder`, onde variava entre `1110`/`1111`) — a discriminação inteira das 35
linhas acontece via `bit28` (`U`, quando existe), `bit16`, `bits[11:8]`, `bit12`, `bits[6:4]` e
`bit7` (normalmente `Qn` alto, mas REPROPOSITADO como o bit "saturante" dentro de `@shl_scalar`,
onde não existe campo `Qn`). A colisão real dentro do slot `nib2=1110,b16=1,b12=1,nib3=110` (`@2op`
`VMUL_scalar`/`VBRSR` vs `@shl_scalar` inteiro) se resolve pela MESMA regra de especificidade já
usada em B16.6/B16.7/B16.8: `bits[21:20]==0b11` fixo (mais específico) seleciona `@shl_scalar`
(tamanho real em `bits[19:18]`); `bits[21:20]` livre (`0`-`2`) seleciona `VMUL_scalar`(`U=0`)/
`VBRSR`(`U=1`). O mesmo padrão resolve `VADD_fp_scalar`/`VSUB_fp_scalar`/`VMUL_fp_scalar`/
`VFMA_scalar`/`VFMAS_scalar`/`VQDMULLB_scalar`/`VQDMULLT_scalar` (todos com `bits[21:20]` fixo
`11`) contra os vizinhos de `size` livre no MESMO `{}`.

### Achados reais (medidos contra o QEMU real via `curl` + `Read`/`Grep`, não `WebFetch` — memória
`feedback-curl-verbatim-qemu-source`)

1. **`VMLA`/`VMLAS` são as ÚNICAS linhas com `111 -`** — confirmado: o decoder para essas duas NÃO
   lê `bit28` em nenhum momento da decisão; teste explícito (`vmlaDecodesTheSameRegardlessOfBit28`/
   `vmlasDecodesTheSameRegardlessOfBit28`) prova que os dois valores de `bit28` produzem instâncias
   `equals()` idênticas do record.
2. **`Rm ∈ {13,15}` é UNPREDICTABLE em TODAS as 35 formas** (`do_2op_scalar`/`do_2shift_scalar`
   reais recusam os dois) — **diferente** de `Thumb2MveComparisonDecoder` (B16.8), onde `Rm==15` é
   "constante zero" válida. Confirmado lendo `do_2op_scalar`/`do_2shift_scalar` verbatim.
3. **`VMLA`/`VMLAS` têm ordens de operando DIFERENTES, confirmadas no C real, não adivinhadas**:
   `DO_VMLA(D,N,M) = (N)*(M)+(D)` → `VMLA`: `Qd = Qn*Rm + Qd` (cabe direto no `case MLA` já
   existente de `computeThreeSame`, `d + a*b`). `DO_VMLAS(D,N,M) = (N)*(D)+(M)` → `VMLAS`: `Qd =
   Qn*Qd + Rm` — os papéis de `Qd`/`Rm` estão TROCADOS em relação a `VMLA` (o comentário real do
   arquivo é explícito: "the *MLASH insns are vector * vector + scalar"), por isso não cabe no
   `AdvSimdThreeSameOp` compartilhado sem alterar o `switch` exaustivo de A64/NEON — ganhou método
   dedicado (`multiplyAccumulateSwapScalarMasked`).
4. **`VFMA_scalar`/`VFMAS_scalar` seguem a MESMA troca de papéis, em ponto flutuante** — os dois
   comentários literais do `mve_helper.c` confirmam: "VFMA is vector * scalar + vector"
   (`Qd = fma(Qn, Rm, Qd)`) e "VFMAS is vector * vector + scalar, so swap op2 and op3"
   (`Qd = fma(Qn, Qd, Rm)`).
5. **`VQDMLAH`/`VQRDMLAH` vs `VQDMLASH`/`VQRDMLASH` trocam QUAL operando é multiplicado por `Qn`**
   (comentário real: "the *MLAH insns are vector * scalar + vector; the *MLASH insns are vector *
   vector + scalar") — `VQDMLAH`: `a=Qn,b=Rm,c=Qd` atual; `VQDMLASH`: `a=Qn,b=Qd` atual`,c=Rm`.
   A fórmula real (`do_vqdmlah_b`/`_h`/`_w`) é `sat16(2*a*b + (c<<esize) + round<<(esize-1)) >>
   esize` — um ÚNICO estágio de saturação de largura DUPLA, arquiteturalmente DIFERENTE do
   `SQRDMLAH` do A64/NEON (duas saturações independentes já implementadas em `computeThreeSame`) —
   por isso ganhou núcleo PRÓPRIO (`doublingMultiplyAccumulateScalarChecked`, via `BigInteger` para
   evitar o cuidado manual de overflow de 64 bits que o C real só precisa na forma `w`, mesma
   disciplina de `saturatingDoublingProductChecked`), em vez de reusar `SQRDMLAH`/`SQDMLAH`.
6. **`VQDMULLB_scalar`/`VQDMULLT_scalar`: `esz` = `%size_28` DIRETO** (`bit28+1`), e desta vez
   `%size_28` COINCIDE numericamente com o `esz` real da fonte (`bit28=0`→halfword, `bit28=1`→word)
   — confirmado via `fns[a->size]` indexando `[NULL, h-variant, w-variant, NULL]` em
   `trans_VQDMULLB_scalar` real. **Diferente** da Armadilha 2/7 da B16.6/B16.7 (`VMULLP_B`/`_T`),
   onde `%size_28` NÃO coincidia com o `esz` real — cada instrução precisou ser conferida
   individualmente, não presumida por analogia.
7. **`VQDMULLB_scalar`/`VQDMULLT_scalar`: `Qd == Qn` com `esz` word é UNPREDICTABLE** ("choose to
   undef" no QEMU real) — recusado no decoder; `Qd == Qn` com `esz` halfword é PERMITIDO (a
   restrição só existe para a largura word, mesma lógica de `Qd==Qn||Qm` da B16.7 para a forma
   vetor×vetor).
8. **`VBRSR` não tem análogo em NEON/A64** — transcrito `do_vbrsrb`/`_h`/`_w` verbatim
   (`bitReverseShiftRightMasked`): inverte os bits do elemento e desloca à direita por
   `esize - count`; `count == 0` produz `0`; `count >= esize` mantém totalmente invertido.

MESMA disciplina de predicação/saturação (`computeThreeSameChecked`, `mergeLaneBytes`) mas recebem
o escalar já lido como `long`, mais simples e mais barato.

`computeThreeSameChecked`/`saturatingDoublingProductChecked` continuam INTOCADOS, só reusados.

# B17.3 — Fundação de estado SVE: `Z0-Z31`, `P0-P15`, `FFR`, `ZCR_EL1/2/3` e `ID_AA64ZFR0_EL1` — 0 encodings

**Trilha:** B · **Repo:** arm-jitter (+ revalidação G5) · **Depende de:** B17.2 (RFC, ⬜ — decisão do usuário)
**Épico:** `b17-plano-sve.md` · **Status:** ⬜ (spec escrita 2026-09-14, ainda não executada)

## Contexto

Degrau 2 da escada B17. A **B17.1** criou as features e os presets; esta cria o **estado**. Nenhum
encoding de `sve.decode` é decodificado aqui — `docs/COBERTURA-ISA.md` continua byte a byte
idêntica. É o espelho, do lado SVE, do que a B13.1 foi para o banco `D0-D31` do NEON A32 e a B16.1
para `Q0-Q7`/`VPR` do MVE.

⚠️ **Esta task não pode começar antes de a RFC B17.2 fechar.** Ela é literalmente a implementação da
decisão da RFC; começar antes é escolher a opção sozinho, que é o que `tasks/README.md` (item 5b das
pendências de modelo forte) proíbe.

### O que já existe (medido nesta rodada de spec)

- `core64/Aarch64FpRegisters.java` — `long[] lo`/`long[] hi` de 32 posições, `WORDS_PER_REGISTER = 2`,
  23 métodos públicos, implementa `advsimd/AdvSimdRegisterWords` (vista plana por palavras de 64
  bits, criada pela RFC B13.2/D1).
- `ir64/Aarch64SystemRegisterId.java` — **já tem**:
  - `CPACR_EL1` (`op0=3,op1=0,CRn=1,CRm=0,op2=2`), com o Javadoc dizendo "controle de trap de
    FP/SIMD/**SVE** para EL1";
  - `ID_AA64ZFR0_EL1` (`CRn=0,CRm=4,op2=4`), Javadoc: *"features de SVE. Constante `0` (SVE não
    implementada — coerente com `ID_AA64PFR0_EL1`, que não anuncia SVE)"*;
  - `ID_AA64PFR0_EL1`, também constante.
  **Não existe** `ZCR_EL1`/`ZCR_EL2`/`ZCR_EL3`.
- `core64/Aarch64Core.java` — `handlesSystemRegisterIntrinsically`/`readIntrinsicSystemRegister`/
  `writeIntrinsicSystemRegister` (o padrão a espelhar), `Aarch64SystemRegisterBus` para o que é
  externo, `fp()` (90 chamadas no `main`).
- `codegen/equivalence/Aarch64CpuSnapshot.java` — `record` que captura `core.fp().snapshot()`; é o
  oráculo de equivalência (G1) e vai precisar do estado novo.

### O modelo do QEMU (confirmado por `WebFetch` nesta rodada)

- **`FFR` é um predicado como qualquer outro.** `translate-sve.c` tem `FFR_PRED_NUM` e implementa
  `RDFFR` reusando a operação de predicado com `rn = rm = FFR_PRED_NUM`:
  ```c
  arg_rprr_s alt_a = {.rd = a->rd, .pg = a->pg, .s = a->s,
                      .rn = FFR_PRED_NUM, .rm = FFR_PRED_NUM,};
  ```
  Consequência de desenho: modelar `FFR` como o 17º predicado (ou um campo do mesmo array) economiza
  a metade das operações da B17.4/B17.17.
- **Tamanhos vêm de funções, nunca de constantes**: `vec_full_reg_size(s)` e `pred_full_reg_size(s)`,
  com `vec_full_reg_offset(s, rd)`/`pred_full_reg_offset(s, pg)` calculando offsets no `tcg_env`.
  `ADDVL` é literalmente `tcg_gen_addi_i64(rd, rn, a->imm * vec_full_reg_size(s))`.
- **Gate duplo** em todo `trans_`: `dc_isar_feature(aa64_sve, s)` (decode) **e** `sve_access_check(s)`
  (runtime, trap por `CPACR_EL1.ZEN`/`CPTR_EL2`/`CPTR_EL3`). Esta task entrega o segundo.

## Objetivo

`Aarch64Core` tem `Z0-Z31`, `P0-P15` e `FFR` reais, dimensionados pelo `VL` escolhido na RFC;
`ZCR_EL1/EL2/EL3` são legíveis/escrevíveis por `MRS`/`MSR`; `ID_AA64PFR0_EL1`/`ID_AA64ZFR0_EL1`
anunciam SVE quando (e só quando) o preset a declara; `sve_access_check` existe; e o estado entra em
`saveState`/`loadState`/`Aarch64CpuSnapshot`. Zero encoding de `sve.decode` decodificado.

## Inclui

1. **Banco escalável** — a forma exata vem da RFC B17.2. Se for a Opção C (recomendada):
   `core64/Aarch64ScalableRegisters` com `long[] z` (32 × `wordsPerVector`), `long[] p`
   (16+1 × `wordsPerPredicate`, o `+1` sendo o `FFR`), e `Aarch64FpRegisters` convertida em **vista**
   das 2 palavras baixas de cada `Z<n>` — **sem mudar nenhuma das 23 assinaturas públicas** (G3).
2. **`VL` como propriedade do core**, derivada do preset e de `ZCR_ELx.LEN`, exposta por método
   (`vectorLengthBytes()`/`predicateLengthBytes()`), **nunca** constante espalhada (G6). Uma única
   constante nomeada para o mínimo arquitetural (`MIN_VECTOR_LENGTH_BITS = 128`) e para o máximo
   (`MAX_VECTOR_LENGTH_BITS = 2048`).
3. **`ZCR_EL1`, `ZCR_EL2`, `ZCR_EL3`** em `Aarch64SystemRegisterId` + `Aarch64Core`
   (`handlesSystemRegisterIntrinsically`), com os encodings reais (`ZCR_EL1`:
   `op0=3,op1=0,CRn=1,CRm=2,op2=0`; `ZCR_EL2`: `op1=4`; `ZCR_EL3`: `op1=6` — **conferir contra o
   manual/QEMU antes de implementar**, ver Armadilha 3). Campo `LEN` (`bits[3:0]`): `VL` efetivo =
   `min((LEN+1)*128, VL_implementado)`.
4. **`sve_access_check`** — o trap de acesso: `CPACR_EL1.ZEN` (`bits[17:16]`), `CPTR_EL2.ZEN`/`TZ`,
   `CPTR_EL3.EZ`. Uma instrução SVE executada com acesso negado gera exceção (`Aarch64Core`
   já tem o caminho de `enterUndefinedInstructionException`/`ArmException`; a classe exata de
   exceção — trap com `EC=0x19` "SVE access" — deve ser **medida** contra o manual, não chutada).
   Se o custo de fazer isso corretamente estourar o orçamento da sessão, entregar o método com o
   caminho de negação implementado e o *encoding* da síndrome documentado como pendência nomeada
   (nunca "não vamos implementar").
5. **`ID_AA64PFR0_EL1.SVE` (`bits[35:32] = 0b0001`) e `ID_AA64ZFR0_EL1`** passam a refletir as
   features do preset (`SVE`/`SVE2` da B17.1) em vez de constante `0` — e **só** quando o preset as
   declara (um `ARMV8_0_A` continua anunciando `0`). Os campos de `ID_AA64ZFR0_EL1` (`SVEver`,
   `AES`, `BitPerm`, `BF16`, `SHA3`, `SM4`, `I8MM`, `F32MM`, `F64MM`) só podem anunciar o que as
   tasks seguintes de fato implementarem — **esta task anuncia `SVEver` e nada mais**; cada campo
   restante é acendido pela task que fecha a família correspondente (B17.24 para `AES`/`SM4`,
   B17.23 para `BF16`/`F32MM`/`F64MM`, etc.). Deixar isso escrito no `## Resultado`.
6. **Persistência**: `saveState`/`loadState` do core e `Aarch64CpuSnapshot` passam a incluir
   `Z`/`P`/`FFR`/`ZCR_ELx`, com versionamento do formato.
7. Testes (ver Aceite).

## Não inclui

- **Qualquer decode** de `sve.decode` (B17.4+). Nem `MRS`/`MSR` de `ZCR_ELx` é decode novo — é uma
  entrada no mapa de `Aarch64SystemRegisterId` que o `Aarch64Decoder` já resolve genericamente
  (**confirmar** lendo `decodeSystemRegisterId`).
- **`SMCR_ELx`/`SVCR`/`ZA`/modo streaming** — épico **B18**, que depende desta.
- **`RDVL`/`ADDVL`/`ADDPL`/`CNTB`** — são encodings (B17.12/B17.4), mesmo lendo o `VL` que esta task
  cria.
- **Emissão nativa/Truffle** — decode+interpretado apenas, padrão da trilha B.

## Aceite

- `Z<n>[127:0]` e `V<n>` são **o mesmo armazenamento**: escrever por `fp().setQ(n, lo, hi)` e ler
  pelo banco escalável (e vice-versa) devolve o mesmo valor — teste explícito para os 32
  registradores, não só para `Z0` (o aliasing é o achado central do épico, ver "Armadilhas" do
  `b17-plano-sve.md`).
- **Nenhum teste AdvSIMD pré-existente muda de resultado** (G3): a suíte de B8.6-B8.12 roda verde
  sem edição.
- `P<n>` tem `VL/8` bits e `FFR` se comporta como um predicado (ler/escrever/reset).
- `MRS x0, ZCR_EL1` / `MSR ZCR_EL1, x0` funcionam; `ZCR_EL1.LEN` limita o `VL` efetivo; `VL`
  efetivo nunca excede o implementado nem cai abaixo de `MIN_VECTOR_LENGTH_BITS`.
- `ID_AA64PFR0_EL1.SVE` é `1` sob `ARMV9_0_A` e `0` sob `ARMV8_0_A`.
- Acesso SVE com `CPACR_EL1.ZEN = 0b00` em EL0/EL1 é negado (teste do caminho, mesmo que nenhuma
  instrução SVE decodifique ainda — chamar `sve_access_check` diretamente).
- Save/restore de um core com `Z`/`P`/`FFR` não nulos preserva o estado bit a bit.
- `docs/COBERTURA-ISA.md` byte a byte idêntica.
- `mvn -o test` verde + G5 verde nos 5 consumidores.

## Armadilhas

1. **`Z` alias `V` — o achado central do épico.** O banco da B8.6 tem que virar a **vista baixa** do
   banco `Z`, não um banco irmão sincronizado. Manter dois arrays e copiar entre eles é o erro
   clássico (o `MOVPRFX` e todo executor SVE escreveriam num e liriam do outro). Mesma classe de
   problema que o MVE terá com `Q0-Q7`.
2. **A escrita destrutiva do A64 muda de tamanho sob SVE.** Hoje escrever `V<n>` zera `[127:64]`;
   com SVE ativa, escrever `V<n>` (instrução AdvSIMD) zera `Z<n>[VL-1:64]` — **a regra ARM real**.
   Onde essa disciplina vive hoje é o chamador (Javadoc de `AdvSimdRegisterWords.setWord`). Se a
   task não tratar isso, um programa que mistura AdvSIMD e SVE (que é o caso normal) vê lixo nos
   bits altos. Se resolver corretamente estourar a sessão, **implementar o zeramento até `VL`** é o
   mínimo — nunca deixar "só 128" silenciosamente.
3. **Os encodings de `ZCR_ELx` têm que ser medidos**, não lembrados. `MSR`/`MRS` com o encoding
   errado é exatamente o misdecode silencioso que o **G8** proíbe: um `MSR` para o registrador
   errado corrompe outro estado em vez de recusar.
4. **`ID_AA64ZFR0_EL1` não pode anunciar o que não existe.** Anunciar `AES`/`BF16`/`F64MM` antes de
   B17.23/B17.24 faz software real escolher caminhos de código que vão bater em `UNIMPLEMENTED` —
   o inverso do G8, e o mesmo padrão do achado da B15.2 (o catch-all genérico engolindo instruções
   mais específicas que ainda não existem).
5. **`VL` não é constante de compilação.** Todo laço de lane tem que ser `for (lane = 0; lane <
   vectorLengthBytes() >> esz; lane++)`. Um `grep -n "128"` nos arquivos novos é item de Aceite
   informal — a VLA é disciplina, não feature.
6. **`Aarch64CpuSnapshot` é `record` público** — acrescentar componente é mudança de assinatura.
   Avaliar se cabe em G3 (é classe de teste/equivalência, `codegen/equivalence`) ou se precisa de
   construtor adicional; decidir por leitura, documentar no `## Resultado`.
7. **Memória**: `VL=2048` ⇒ 8 KiB de `Z` por core. Não é problema para 1-4 cores, mas o banco não
   deve ser alocado para presets **sem** SVE (um `ARMV8_0_A`/Cortex-A53 não paga por isso) —
   alocação preguiçosa ou dimensionada por preset.

## Não fazer

- Não decodificar nenhuma instrução SVE.
- Não implementar `ZA`/`SVCR`/`SMCR_ELx`/modo streaming (B18).
- Não manter `lo`/`hi` em paralelo a `Z` (Armadilha 1).
- Não anunciar campos de `ID_AA64ZFR0_EL1` sem a implementação correspondente.
- Não começar antes de a RFC B17.2 ser decidida pelo usuário.

# B3.3 — VFP: banco de registradores S/D + FPSCR no core

**Trilha:** B (épico B3) · **Depende de:** — (paralela a B3.1/B3.2) · **Repo:** arm-jitter

## Contexto

VFPv2 tem 32 registradores S (single, 32 bits) que se sobrepõem a 16 registradores D
(double, 64 bits): `D<i>` = par `S<2i>` (metade BAIXA) + `S<2i+1>` (metade ALTA) —
layout little-endian fixo do VFPv2/v3-d16 (ARM DDI 0406C A2.6.2). Mais o FPSCR
(flags NZCV próprios de FP + controles). Esta task cria só o ESTADO — nenhuma
instrução ainda (B3.4/B3.5).

## Inclui

### 1. `core/VfpRegisters.java` (novo, pacote `core`)

```java
public final class VfpRegisters {
    public static final int SINGLE_COUNT = 32;
    private final int[] s = new int[SINGLE_COUNT]; // bits crus IEEE 754
    public int s(int index);                 // bits crus
    public void setS(int index, int bits);
    public long d(int index);                // (s[2i+1] << 32) | (s[2i] & 0xFFFF_FFFFL)
    public void setD(int index, long bits);
    public float sFloat(int index);          // Float.intBitsToFloat(s(index))
    public void setSFloat(int index, float v);
    public double dDouble(int index);        // Double.longBitsToDouble(d(index))
    public void setDDouble(int index, double v);
}
```

Sempre trafegar BITS crus no estado (o float/double é view) — snapshot/save-state
ficam bit-exatos, NaN payloads inclusive.

### 2. `core/FpscrRegister.java` (novo, espelha `CpsrRegister` na forma)

Bits (A2.7.2, nomear TODAS as constantes, G6): `N`(31) `Z`(30) `C`(29) `V`(28)
`DN`(25) `FZ`(24) `RMODE`(23:22) `STRIDE`(21:20) `LEN`(18:16) e os cumulativos
IDC(7) IXC(4) UFC(3) OFC(2) DZC(1) IOC(0).

- `int value()` / `void setValue(int)` com a política da decisão nº 3 do épico
  (`b3-armv7a-vfp.md`): escrever `RMODE≠00`, `FZ=1`, `LEN≠0` ou `STRIDE≠0` lança
  `UnsupportedOperationException` com mensagem clara (`"FPSCR RMode/FZ/Len/Stride
  não suportados — modo IEEE round-to-nearest apenas"`) — mesmo padrão central do
  bit E de B1.5 em `IrExecutionSupport`. `DN` é aceito e armazenado (semântica de
  NaN é a do Java de qualquer forma — documentar no javadoc).
- Cumulativos: aceitos na escrita, lidos de volta como escritos (software faz
  read-modify-write), mas NUNCA setados por operação FP (limitação documentada).
- Helpers de flags: `boolean n()/z()/c()/v()` e `void setNzcv(int packed)` — B3.4
  (VCMP) e o `VMRS APSR_nzcv` vão usar.

### 3. `ArmCore` ganha o estado

- Campo `private final VfpRegisters vfp = new VfpRegisters();` + accessor
  `public VfpRegisters vfp()`; idem `private final FpscrRegister fpscr` +
  `public FpscrRegister fpscr()`. Sempre alocados (170 bytes; sem flag de
  presença — quem gateia é o decoder por `ArmFeature`, como sempre).
- `saveState`/`loadState` (`ArmCore.java:102/124`): acrescentar os 32 ints + fpscr
  ao FINAL do stream e **bump da versão** do formato — abrir os dois métodos e
  seguir o versionamento existente (compatibilidade de leitura com estados antigos:
  se a versão for anterior, zera o banco).
- `CpuSnapshot` (`codegen/equivalence/CpuSnapshot.java`): incluir banco S completo +
  FPSCR na captura e no `equals`/diff — é o que fará o harness de equivalência pegar
  divergência de FP em B3.6 (mesmo movimento que B1.4 fez com o monitor exclusivo).

### 4. Feature

`ArmFeature.VFPV2` nova (javadoc: VFPv2 + VMOV-imediato do v3-d16, decisão do épico).
Nenhum preset a usa ainda (B3.7).

## Não inclui

- Instruções, IR, decode (B3.4/B3.5). FPEXC/FPSID (registradores de sistema VFP):
  ficam para o hospedeiro via futuro hook se algum alvo precisar — userland Linux
  não os lê; NÃO criar agora.

## Testes mínimos (`VfpRegistersTest` + casos em testes existentes de save-state/snapshot)

1. Sobreposição S/D: `setS(2, 0xAAAAAAAA); setS(3, 0xBBBBBBBB)` →
   `d(1) == 0xBBBBBBBB_AAAAAAAAL`; `setD` reflete nos dois S.
2. Views float/double bit-exatas incl. NaN payload (`0x7FC00001` sobrevive
   ida-e-volta por bits — NUNCA passar por aritmética).
3. FPSCR: escrita/leitura de NZCV+DN+cumulativos; `RMODE=01`/`FZ=1`/`LEN=1`
   lançam `UnsupportedOperationException`.
4. save/load: estado com banco preenchido faz ida-e-volta; stream de versão antiga
   (gerado no teste com a versão anterior) carrega com banco zerado, sem exceção.
5. `CpuSnapshot`: dois cores idênticos exceto 1 registrador S → snapshot diferente.

## Armadilhas

- **Não** armazenar float/double como tipo primário — bits crus sempre; float é view.
- A ordem low/high do par S↔D é o erro clássico — o teste 1 é o guarda; não inverta.
- `CpuSnapshot` maior deixa o harness mais lento — capturar o banco só quando… NÃO:
  capturar sempre (correção > micro-perf de teste); se a suíte ficar lenta demais,
  registrar no PR, não otimizar por conta.

**Épico:** `b16-plano-mve-helium.md` · **Status:** ✅ B16.13a (2026-09-18, sub-famílias 1/2/4 —

## Contexto

Décimo-terceiro degrau da escada B16 (partição normativa na spec da **B16.1**). O épico estimou 22
para "Misc / `VADDV` / movimentos entre lanes e registradores gerais / imediato modificado"; a
medição desta rodada de spec confirma essas 22 (linhas 207-208, 371-395, 577-597) e acrescenta as
**28 linhas de acumulação/redução dual** (linhas 443-493) que o épico havia contado no grupo
rotulado "gather/scatter" por efeito do corte contíguo (ver o "Achado desta rodada de spec" na
B16.1). Total medido: **50**.

**É a maior task da escada junto com a B16.7**, e tem quatro sub-famílias independentes — é legítimo
quebrá-la em B16.13a/B16.13b na sessão de execução (sequenciamento, nunca exclusão; ver "Regra
máxima do projeto"). Corte sugerido em "Inclui".

### Sub-família 1 — movimentos entre 2 lanes de 32 bits e 2 GPRs (linhas 206-208, 2 linhas)

```
# Moves between 2 32-bit vector lanes and 2 general purpose registers
VMOV_to_2gp    1110 1100 0 . 00 rt2:4 ... 0 1111 000 idx:1 rt:4 qd=%qd
VMOV_from_2gp  1110 1100 0 . 01 rt2:4 ... 0 1111 000 idx:1 rt:4 qd=%qd
```

Regra confirmada no QEMU (`translate-mve.c`, via `WebFetch` nesta rodada):

```c
if (a->rt == 13 || a->rt == 15 || a->rt2 == 13 || a->rt2 == 15 || a->rt == a->rt2) {
    return false;
}
```

`idx` seleciona QUAL par de lanes de 32 bits (`{0,2}` ou `{1,3}`) — confirmar o mapeamento exato.

### Sub-família 2 — 1-op misc e `VDUP` (linhas 369-395, 15 linhas)

```
# Vector miscellaneous
VCLS     1111 1111 1 . 11 .. 00 ... 0 0100 01 . 0 ... 0 @1op
VCLZ     1111 1111 1 . 11 .. 00 ... 0 0100 11 . 0 ... 0 @1op
VREV16   1111 1111 1 . 11 .. 00 ... 0 0001 01 . 0 ... 0 @1op
VREV32   1111 1111 1 . 11 .. 00 ... 0 0000 11 . 0 ... 0 @1op
VREV64   1111 1111 1 . 11 .. 00 ... 0 0000 01 . 0 ... 0 @1op
VMVN     1111 1111 1 . 11 00 00 ... 0 0101 11 . 0 ... 0 @1op_nosz
VABS     1111 1111 1 . 11 .. 01 ... 0 0011 01 . 0 ... 0 @1op
VABS_fp  1111 1111 1 . 11 .. 01 ... 0 0111 01 . 0 ... 0 @1op
VNEG     1111 1111 1 . 11 .. 01 ... 0 0011 11 . 0 ... 0 @1op
VNEG_fp  1111 1111 1 . 11 .. 01 ... 0 0111 11 . 0 ... 0 @1op
VQABS    1111 1111 1 . 11 .. 00 ... 0 0111 01 . 0 ... 0 @1op
VQNEG    1111 1111 1 . 11 .. 00 ... 0 0111 11 . 0 ... 0 @1op

&vdup qd rt size
# Qd is in the fields usually named Qn
@vdup    .... .... . . .. ... . rt:4 .... . . . . .... qd=%qn &vdup

# B and E bits encode size, which we decode here to the usual size values
VDUP     1110 1110 1 1 10 ... 0 .... 1011 . 0 0 1 0000 @vdup size=0
VDUP     1110 1110 1 0 10 ... 0 .... 1011 . 0 1 1 0000 @vdup size=1
VDUP     1110 1110 1 0 10 ... 0 .... 1011 . 0 0 1 0000 @vdup size=2
```

### Sub-família 3 — acumulação/redução dual e reduções (linhas 422-493, 28 linhas)

```
# multiply-add long dual accumulate
# rdahi: bits [3:1] from insn, bit 0 is 1
# rdalo: bits [3:1] from insn, bit 0 is 0
%rdahi 20:3 !function=times_2_plus_1
%rdalo 13:3 !function=times_2
# size bit is 0 for 16 bit, 1 for 32 bit
%size_16 16:1 !function=plus_1

&vmlaldav rdahi rdalo size qn qm x a
&vmladav rda size qn qm x a
@vmlaldav / @vmlaldav_nosz / @vmladav / @vmladav_nosz   (linhas 433-440)
@vmaxv   .... .... .... size:2 .. rda:4 .... .... .... &vmaxv qm=%qm
@vmaxnmv .... .... .... .... rda:4 .... .... .... &vmaxv qm=%qm
```

As 28: `VMLADAV_S`/`VMLALDAV_S` (`{}`), `VMLADAV_U`/`VMLALDAV_U` (`{}`), `VMLSDAV`/`VMLSLDAV`
(`{}`), `VMLSDAV`/`VRMLSLDAVH` (`{}`), `VMLADAV_S`/`VMLADAV_U` (linhas 461-462, soltas), e os dois
grandes blocos `{ [...] [...] ... }` das linhas 464-494 com `VMAXNMAV`/`VMINNMAV`/`VMAXNMV`/
`VMINNMV` (×2, `size=2` e `size=1`), `VMAXV_S`/`VMINV_S`/`VMAXAV`/`VMINAV`, `VMAXV_U`/`VMINV_U`,
`VMLADAV_S`/`VRMLALDAVH_S`, `VMLADAV_U`/`VRMLALDAVH_U`.

**Achado de decodetree**: estes são os ÚNICOS lugares do arquivo com **grupos aninhados** (`[...]`
dentro de `{...}`). Isso muda a semântica de prioridade: os `[...]` são grupos não-sobrepostos
internos, avaliados como uma unidade dentro do `{...}` sobreposto. Um decoder Java tem que
reproduzir a ordem, não achatar (Armadilha 3).

### Sub-família 4 — redução de soma, `VABAV` e imediato modificado (linhas 575-597, 5 linhas)

```
# Vector add across vector
{
  VADDV   111 u:1 1110 1111 size:2 01 ... 0 1111 0 0 a:1 0 qm:3 0 rda=%rdalo
  VADDLV  111 u:1 1110 1 ... 1001 ... 0 1111 00 a:1 0 qm:3 0 rdahi=%rdahi rdalo=%rdalo
}
@vabav   .... .... .. size:2 .... rda:4 .... .... .... &vabav qn=%qn qm=%qm
VABAV_S  111 0 1110 10 .. ... 0 .... 1111 . 0 . 0 ... 1 @vabav
VABAV_U  111 1 1110 10 .. ... 0 .... 1111 . 0 . 0 ... 1 @vabav

# Logical immediate operations (1 reg and modified-immediate)
# The cmode/op bits here decode VORR/VBIC/VMOV/VMVN, but
# not in a way we can conveniently represent in decodetree without
# a lot of repetition:
# VORR: op=0, (cmode & 1) && cmode < 12
# VBIC: op=1, (cmode & 1) && cmode < 12
# VMOV: everything else
# So we have a single decode line and check the cmode/op in the trans function.
Vimm_1r 111 . 1111 1 . 00 0 ... ... 0 .... 0 1 . 1 .... @1imm
```

com `%imm_28_16_0 28:1 16:3 0:4` e
`@1imm .... .... .... .... .... cmode:4 .. op:1 . .... &1imm qd=%qd imm=%imm_28_16_0`.

2 + 15 + 28 + 5 = **50**.

## Objetivo

As 50 linhas decodificam sob o gate correto (`MVE_INTEGER`/`MVE_FLOAT` por linha) e executam:
movimento de 2 lanes ↔ 2 GPRs, operações de 1 operando (contagem de bits, reversão, valor absoluto,
negação, com/sem saturação), `VDUP` de GPR, acumulação dual longa em par de GPRs, reduções
horizontais para GPR (soma, max/min, com/sem valor absoluto, FP e inteiro), `VABAV` e o imediato
modificado (`VORR`/`VBIC`/`VMOV`/`VMVN` por `cmode`/`op`). 50 células `·`/`❌` → `✅`.

## Inclui

1. **Corte sugerido se a task for quebrada** (documentar se usado):
   **B16.13a** = sub-famílias 1, 2 e 4 (22 linhas — as 22 que o épico originalmente previa);
   **B16.13b** = sub-família 3 (28 linhas de acumulação/redução dual).
2. **Decode das 50 linhas**, com atenção a:
   - `qd=%qn` no `@vdup` (comentário literal: "Qd is in the fields usually named Qn");
   - `%rdahi`/`%rdalo` (pares ímpar/par — `rdahi` = bits[22:20]×2+1, `rdalo` = bits[15:13]×2), ou
     seja o destino é um PAR de GPRs consecutivos, ímpar acima;
   - `%size_16` (bit 16: 0 = 16 bits, 1 = 32 bits) — **diferente** de `%size_28` e de `size:2`;
   - `x:1` (exchange) e `a:1` (accumulate) nos `@vmladav`/`@vmlaldav`;
   - `u:1` como CAMPO em `VADDV`/`VADDLV` (o padrão escreve `111 u:1 1110`, não `111 . 1110`);
   - `@1imm` com `cmode:4`/`op:1` e o imediato de 8 bits montado de 3 pedaços
     (`%imm_28_16_0 28:1 16:3 0:4`);
   - as recusas: `Rt`/`Rt2`/`Rda`/`Rdahi`/`Rdalo` ∈ {13,15} ou `Rt == Rt2` → `null` (regras
     confirmadas no QEMU: "if (a->rda == 13 || a->rda == 15) return false; /* UNPREDICTABLE */"),
     `Q > 7` → `null`, `size == 3` → `null`, e as combinações `cmode`/`op` sem mnemônico → `null`.
3. **`Vimm_1r` não é expandido no decodetree** (comentário literal do arquivo): a linha única
   decodifica `cmode`/`op` e a escolha `VORR`/`VBIC`/`VMOV`/`VMVN` acontece no executor, pela regra
   transcrita no comentário. **Espelhar isso**: uma linha de decode, a decisão no lifter/executor —
   e reusar `AdvSimdModifiedImmediate`/`AdvSimdModifiedImmediateOp` do núcleo (RFC B13.2), que já
   existe e já implementa a expansão `cmode`→imediato de 64 bits.
4. **Auditoria de reuso**: `AdvSimdLanes#pairwise`/`narrow`/`AdvSimdUnaryOp`/`AdvSimdSwapPermuteOp`
   (para `VREV*`), `AdvSimdModifiedImmediate`, `VfpRegisters#replicateElement` (para `VDUP`),
   `maxNum`/`minNum` (para `VMAXNMV`/`VMINNMV`). As reduções horizontais MVE escrevem em **GPR**,
   o que é forma de saída nova (como a `VCMP` escrevendo `P0` na B16.8) — o núcleo produz o valor,
   quem escreve o GPR é o executor.
5. **Execução** predicada por elemento. **Atenção**: numa REDUÇÃO, a máscara determina quais lanes
   ENTRAM na redução; o resultado escalar é escrito no GPR independentemente (confirmar no QEMU o
   que acontece quando TODAS as lanes estão mascaradas — provavelmente o GPR mantém o valor
   acumulado/anterior quando `a=1`, e recebe o elemento neutro quando `a=0`; **não adivinhar**).
6. Testes (ver Aceite).

## Armadilhas

1. **Quatro convenções DIFERENTES de `size` convivem nesta task**: `size:2` (`@1op`, `@vmaxv`,
   `@vabav`), `%size_16` (bit 16, `@vmladav`/`@vmlaldav`), `size=N` fixo por linha (`VDUP`,
   `VMAXNMV`) e ausência de `size` (`@1op_nosz`, `@1imm`). Copiar a extração de uma para outra é o
   erro mais provável. Construir a tabela (linha → origem do `size`) a partir do arquivo real.
2. **`qd=%qn` no `@vdup`** (comentário literal do arquivo). Mesma classe de armadilha da
   "Qm is in the fields usually labeled Qn" da B16.5.
3. **Grupos aninhados `[...]` dentro de `{...}`** só aparecem aqui (linhas 464-494). O decodetree
   avalia o grupo interno como unidade; achatar a árvore num `if`/`else` linear muda a prioridade e
   faz uma redução roubar o encoding de outra. Reproduzir a ordem e testar cada mnemônico dos dois
   blocos.
4. **`u:1` é CAMPO em `VADDV`/`VADDLV`** (`111 u:1 1110`), não don't-care — diferente de `111 . 1110`
   das linhas vizinhas e de `111 - 1110` da B16.9.
5. **`Vimm_1r` é uma linha só de propósito** (comentário literal do arquivo). Expandi-la em 4
   `InstructionKind` no decoder contraria o desenho do arquivo, multiplica células que não existem e
   quebra a correspondência 1:1 com `docs/COBERTURA-ISA.md`.
6. **Reduções escrevem GPR** (forma de saída nova, como a `VCMP` escrevendo `P0` na B16.8). O núcleo
   compartilhado não tem essa saída — a redução produz um valor, o executor escreve o registrador.
   Não acrescentar "escrever GPR" ao núcleo vetorial (ele não conhece GPR, por desenho da RFC B13.2).
7. **`Thumb2NocpDecoder`** cobre `bits[27:24] ∈ {1100,1110,1111}` — todas as 50
   (`VMOV_*_2gp` são `1110 1100`). Ordem de registro.
8. **`VMOV_to_2gp`/`VMOV_from_2gp` são `1110 1100`** = o espaço de extension-register load/store do
   VFP, que `VfpDecoder` reivindica sem checar `bits[31:28]` (bug G8 da B14). Mesma Armadilha 3 da
   B16.3: verificar a lista de decoders do preset e **reportar** se houver colisão real.
9. **G4** e `QC` só para lanes ativas.

### Achados reais (medidos contra o QEMU real via `curl` + `WebFetch`, não presumidos)

1. **`VMOV_from_2gp` NÃO recusa `Rt==Rt2`** — só `VMOV_to_2gp` tem essa checagem no QEMU real
   (`trans_VMOV_to_2gp`/`trans_VMOV_from_2gp`, `translate-mve.c`). A task citava uma checagem
   genérica única para as duas; corrigido e testado (`fromGprAllowsRtEqualsRt2`).
2. **`VMOV_to_2gp`/`VMOV_from_2gp` NÃO são predicados por `VPR`** — só "beatwise" pelo `ECI`
   (nenhuma chamada a `mve_element_mask` nas duas funções reais). Emitem `IrOp.AdvanceEci`, não
   `AdvanceVpt` — mesma categoria de `MveInterleavedLoadStore` (B16.5).
3. **`VADDV`/`VADDLV` ficam no MESMO `{}` sobreposto e um raw pode satisfazer os dois
   literalmente** (`rdahi_raw=0b111`+`size=2` de `VADDLV`/`VADDV` colidem) — a ordem TEXTUAL do
   arquivo real decide (`VADDV` primeiro), replicada explicitamente no decoder (`tryDecodeAddV`
   antes de `tryDecodeAddLv`) e testada (`decodesVaddlvBeforeVaddvOnOverlap`/
   `rdahiRawSevenDecodesAsVaddvNotRejected`).
4. **`accumulate=false` sempre começa a soma do ZERO** (não do "beat corrente", que não existe
   neste emulador — cada instrução executa atomicamente, sempre no "primeiro beat" do QEMU real).
   Com todas as lanes mascaradas, `Rda` fica no valor inicial (zero ou o `Rda` atual conforme `a`) —
   verbatim de `DO_VADDV`/`DO_VADDLV`/`mve_helper.c` (o laço simplesmente não soma nada).
5. **`VABAV` não tem bit `a`: SEMPRE acumula sobre `Rda` atual** (`DO_VABAV` recebe `ra` já
   carregado do registrador, sem ramo de "começar do zero") — diferente de `VADDV`/`VADDLV`.
6. **`VMVN` (`@1op_nosz`) exige `bits[19:16]` LITERAIS `0000`**, não um `size` genérico herdado —
   um raw com o mesmo `nibble`/`sub2`/`group` e `size≠0` não tem mnemônico real (G8), testado
   (`decodesVmvnWithSizeZeroOnly`).
7. **`VDUP`: `Qd` vem de `%qn` (bit7+bits[19:17]), não de `%qd`** (comentário literal do arquivo) —
   `size` vem de `(B,E)=(bit22,bit5)`: `(1,0)`=byte, `(0,1)`=halfword, `(0,0)`=word, `(1,1)` sem
   mnemônico. Testado (`vdupUsesQnFieldForQd`/`rejectsVdupBEqualsEOne`).
8. **`bits[17:16]` (não `bits[19:18]`) é o discriminador primário dos 12 `@1op`** — `00`
   (`VCLS`/`VCLZ`/`VREV*`/`VMVN`/`VQABS`/`VQNEG`) vs `01` (`VABS`/`VABS_fp`/`VNEG`/`VNEG_fp`); `10`/
   `11` pertencem à B16.12 e nunca chegam a este decoder (checado, não assumido).
9. **`Vimm_1r` reusa `AdvSimdModifiedImmediate.expand` 1:1** (RFC B13.2 D1, mesmo núcleo do NEON
   A32) — decoder resolve `op`/`imm64`, executor só aplica com predicação por byte a granularidade
   de palavra de 64 bits (`DO_1OP_IMM`/`mergemask` real). `isReservedInAarch32(cmode=15,op=1)`
   reusado para a única combinação sem mnemônico.
10. **Achado de processo, documentado mas NÃO corrigido (fora do escopo desta task)**: os records
    `IrOp.MveVectorFpConvert`/`MveVectorFpConvertFixed` (B16.12) afirmam no Javadoc "Beatwise (mesmo

### Achados reais (medidos, não deduzidos)

1. **`VMLADAV_S`/`VMLADAV_U` têm DUAS codificações reais para a forma byte** (`bits[11:8]=1111`,
   `@vmladav_nosz`): uma "solta" fora de qualquer `{}` (linhas 461-462, `bit0=1`) e uma catch-all
   dentro dos dois blocos grandes de `VMAXV`/`VMAXNM*` (linhas 476/492, `bit0=0`). As duas produzem
   o MESMO `IrOp` — `bit0` não tem significado arquitetural conhecido aqui, só desambiguação de
   espaço de bits dentro do arquivo real (nenhuma outra linha usa esses bits de outro jeito).
2. **Corolário do achado 1, mesma classe do achado 3 da B16.13a (`VADDV`/`VADDLV`)**: um raw com
   `rdahiRaw=0b111` (`rdahi=15`) faz `VMLALDAV_S` colidir bit a bit com a forma solta de
   `VMLADAV_S` — como o primeiro `{VMLADAV_S/VMLALDAV_S}` do arquivo real lista `VMLADAV_S`
   PRIMEIRO, esse raw SEMPRE decodifica como `VMLADAV_S` (32 bits), nunca chega a ser "VMLALDAV_S
   com `rdahi=15` rejeitado". Testado explicitamente (`rdahiRawSevenDecodesAsVmladavSNotRejected`).
3. **Os grupos aninhados `[...]` dos dois blocos `VMAXV`/`VMAXNM*` colidem de verdade entre si**: um
   raw com `size=0b11` numa forma `VMAXV_S`/`VMAXAV` (bits[19:16] livres exceto o seletor) SEMPRE
   coincide bit a bit com o literal de `VMAXNMV_S`/`VMAXNMAV_S` (o grupo `[NMAV/NMV]`, checado
   PRIMEIRO) — não existe, na prática, um raw "VMAXV_S com size=3" sob um preset com `MVE_FLOAT`: a
   arquitetura reaproveita exatamente esse espaço de bits para as formas FP. Só num preset
   `MVE_INTEGER`-only (sem `MVE_FLOAT`) o raw chega a `tryIntMinMax` de verdade e é recusado por
   `size==3` (G8) — os dois cenários testados separadamente
   (`intMinMaxSizeThreeCoincidesWithFpFormUnderFullFeatureSet`/
   `intMinMaxSizeThreeIsRejectedWhenMveFloatAbsent`).
4. **`VMLSDAV`/`VRMLSLDAVH` usam o prefixo de topo `1111 1110`** (normalmente "forma unsigned" no
   resto da família) **mas continuam SEMPRE assinados** — não existe `vmlsdavu`/`vmlsldavu` no QEMU
   real (`DO_DAV_S(vmlsdav,...)`/nenhum `DO_DAV_U` equivalente). Testado
   (`decodesVmlsdavNoszAndVrmlsldavhAlwaysSigned`).
5. **`VMLADAV_U`/`VMLALDAV_U`/`VRMLALDAVH_U` não têm forma `exchange`** (`x=1` sem helper real —
   `fns[size][1]=NULL`/`fns[1]=NULL`) — recusado no decode (G8), testado
   (`vmladavUAndVmlaldavURejectExchange`).
6. **`VMAXNMV`/`VMINNMV`/`VMAXNMAV`/`VMINNMAV` usam o bit que normalmente escolhe sinal para
   escolher PRECISÃO**: bloco `S` (top byte `1110 1110`) = binary32 (`size=2`), bloco `U` (top byte
   `1111 1110`) = binary16 (`size=1`) — verbatim de `DO_VMAXV_FP`/`fns={NULL,h,s,NULL}`. Gate
   `MVE_FLOAT`, não `MVE_INTEGER`. Testado (`decodesFpMinMaxWithCorrectPrecisionPerBlock`).
7. **`VMAXV`/`VMINV`/`VMAXAV`/`VMINAV`/`VMAXNM*` não têm bit `a`**: sempre leem `Rda` ATUAL como
   semente (mesma categoria de `VABAV`, B16.13a), nunca "começam do zero" — verbatim de
   `do_vmaxv`/`mve_helper.c`.
8. **`VMAXAV`/`VMINAV` leem `Rda` como NÃO ASSINADO e o elemento como ASSINADO**, tomando
   `|elemento|` antes de comparar (`do_maxa`/`do_mina`) — sem forma `unsignedForm` própria.
9. **Precisão binary16 zera os 16 bits altos de `Rda`** (o helper real retorna `uint32_t` truncado
   do resultado `float16` de 16 bits) — testado (`halfPrecisionFormZeroesUpperHalfOfRda`).
10. **`VRMLALDAVH`/`VRMLSLDAVH` (rounding high)**: a negação de `VRMLSLDAVH` se aplica ao PRODUTO
    antes do arredondamento (só na lane ímpar), não ao acumulador — diferente de `VMLSLDAV`, onde a
    negação se aplica à ACUMULAÇÃO (`ODDACC -=`). Replicado verbatim de `DO_LDAVH` (arredondamento
    `(mul>>8)+((mul>>7)&1)` calculado ANTES de somar).

# B9.3 — T16 ARMv6 genuínos: `SETEND`, `CPS` A/R-profile, `REV`/`REV16`/`REVSH`, `SXTH`/`SXTB`/`UXTH`/`UXTB`

**Trilha:** B · **Depende de:** — · **Repo:** arm-jitter

## Contexto

Task da escada 32 bits (B9) do plano mestre `b7-plano-cobertura-isa.md`, que descrevia o escopo
como "T16 ARMv6 genuínos: `CPS`, `REV`, `REVSH`, `SXTAH`/`SXTAB`/`UXTAH`/`UXTAB`, `SETEND` + hints
(`YIELD`/`WFE`/`WFI`/`SEV`/`NOP`) | todos | ~14".

⚠️ **Sem spec formal escrita antes da implementação** — mesmo padrão ad-hoc de B6.9/B6.11/B8.1/
B9.1/B9.5 (task pequena o bastante para não precisar de rodada de spec separada). Este arquivo
documenta a triagem e o resultado, não um plano prévio.

## Triagem real

Regra do plano mestre: "instrução pertence à arquitetura-alvo → implementar; pertence a versão
POSTERIOR → linha em `docs/isa-nao-aplicavel.tsv` com a fonte; na dúvida, implementar."

### Achado 1 — `SXTAH`/`SXTAB`/`UXTAH`/`UXTAB` do plano mestre é o nome ERRADO

Confirmado contra `target/arm/tcg/t16.decode` real do QEMU (`curl`, não de memória — precedente de
aviso da B6.8): as 4 linhas de fato existem no `t16.decode` com esses nomes:

```
@extend         .... .... .. rm:3 rd:3          &rrr_rot rn=15 rot=0
SXTAH           1011 0010 00 ... ...            @extend
SXTAB           1011 0010 01 ... ...            @extend
UXTAH           1011 0010 10 ... ...            @extend
UXTAB           1011 0010 11 ... ...            @extend
```

Mas o formato `@extend` do T16 **fixa `rn=15`** — e `op_xta` (a função de tradução compartilhada
com a forma A32 real com acumulador, `translate.c`) só soma o acumulador quando `rn != 15`:

```c
static bool op_xta(DisasContext *s, arg_rrr_rot *a, ...) {
    ...
    if (a->rn != 15) {
        TCGv_i32 tmp2 = load_reg(s, a->rn);
        gen_add(tmp, tmp, tmp2);
    }
    ...
}
```

Ou seja, a instrução T16 real (mnemônico do ARM ARM, ARM DDI 0406C A8.8.232/233/236/237 T1) é a
forma **SEM acumulador**: `SXTH`/`SXTB`/`UXTH`/`UXTB Rd,Rm`. QEMU só reaproveita os nomes de função
`trans_SXTAH`/etc. internamente porque a mesma rotina de tradução serve às duas formas (T16 sem
acumulador de verdade e A32 com acumulador de verdade); isso NÃO significa que a instrução T16
"tenha" um acumulador. **`SXTAH`/`SXTAB`/`UXTAH`/`UXTAB` com um `Rn` de acumulador de verdade só
existem no espaço A32/T32 de 32 bits** (já cobertos por `ArmDecoder`, B1.2, `InstructionKind.EXTEND`
com `rn != 15`).

**Escopo corrigido**: implementadas `SXTH`/`SXTB`/`UXTH`/`UXTB` (sem acumulador), não `SXTAH`/
`SXTAB`/`UXTAH`/`UXTAB`. A tabela `docs/COBERTURA-ISA.md` mantém os nomes de linha do QEMU
(`SXTAH`/`SXTAB`/`UXTAH`/`UXTAB`, porque o inventário vem do `t16.decode`), mas o comportamento
implementado é o correto (sem acumulador) — não há exclusão em `isa-nao-aplicavel.tsv` porque a
instrução (com o nome real `SXTH`/etc.) pertence de fato à arquitetura-alvo.

### Achado 2 — hints (`YIELD`/`WFE`/`WFI`/`SEV`/`NOP`) já estavam implementados (B2.5)

O plano mestre lista hints no escopo, mas `ThumbDecoder` já decodifica `NOP`/`YIELD`/`WFE`/`WFI`/
`SEV` no espaço `0xBF00` desde a B2.5, gateado por `ArmFeature.THUMB2`. Investigado se esse gate
deveria ser relaxado para `ArmFeature.WAIT_HINTS` (que `ARMV6K`/`ARM11_MPCORE` já têm, mesmo sem
Thumb-2) — **decisão: manter como está**. O `t16.decode` do QEMU marca `IT` e os hints como
`thumb_insn_is_16bit` incondicional (decodificados independente de `ARM_FEATURE_THUMB2`) e
`trans_IT`/`trans_YIELD`/`trans_WFE`/`trans_SEV`/`trans_NOP` não têm gate de versão explícito no
`translate.c` — mas isso é uma simplificação de implementação do QEMU (nenhum modelo de CPU seu
implementa Thumb sem Thumb-2 na prática), não uma confirmação de que o hardware real ARMv6K
(pré-ARMv6T2, ex. ARM1176 puro) tinha esse encoding de 16 bits alocado. O ARM ARM (ARM DDI 0406C
Table A6-1) documenta esse espaço (`0b1011_1111`) como reservado até ARMv6T2 (mesma versão que
introduziu `IT`, com quem os hints compartilham o opcode). Existe também um teste de regressão
explícito (`Thumb2MiscDecoderTest#hint16SpaceIsUndefinedWithoutThumb2`) que já fixava esse
comportamento como intencional. Sem uma fonte mais forte que o "silêncio" do QEMU, mantida a
decisão anterior (gate por `THUMB2`) — nenhuma mudança nesta task. Isso está coerente com "todos"
do plano mestre: os presets que têm hints Thumb (`ARMV6K_THUMB2`, `ARMV7A`, `ARMV6M`, `ARMV7M`) já
os têm; `ARMV6K`/`ARM11_MPCORE` (sem Thumb-2) permanecem sem esse encoding de 16 bits específico,
que é a leitura mais defensável dos dois documentos-fonte que discordam entre si.

### Confirmação: as 4 famílias restantes (`SETEND`, `CPS`, `REV`/`REV16`/`REVSH`, `SXTH`/`SXTB`/`UXTH`/`UXTB`)

Confirmado contra `translate.c` (`trans_CPS`, `trans_SETEND`, `trans_REV`/`REV16`/`REVSH`,
`op_xta`) que as quatro famílias exigem só `ENABLE_ARCH_6` (ARMv6) e, no caso de `CPS`,
`!ARM_FEATURE_M` — **nenhuma delas depende de Thumb-2**, ao contrário dos hints/`IT`. Confirma que
o gate correto é reaproveitar as MESMAS features da forma A32 já implementada (B1.2/B1.5):
`ArmFeature.SETEND_BIG_ENDIAN_DATA`, `ArmFeature.MODE_CHANGE_INSTRUCTIONS`,
`ArmFeature.BYTE_REVERSE`, `ArmFeature.EXTEND_ROTATE` — todas já presentes em `ARMV6K` (herdadas
por `ARM11_MPCORE`/`ARMV7A`/`ARMV6K_THUMB2`), ausentes em `ARMV4T`/`ARMV5TE` (G2).

Também confirmado (achado colateral): `CPS` reaproveita EXATAMENTE o mesmo prefixo de 11 bits
(`0xB660`-`0xB67F`) que o `CPS` de 16 bits do perfil M já implementado na B7.4
(`ThumbDecoder#CPS16_MASK`/`CPS16_VALUE`) — os dois perfis (M vs A/R) dividem o espaço de encoding
com um campo a mais no A/R-profile (bit 2 = `A`, reservado/SBZ no M-profile). Um teste PRÉ-EXISTENTE
(`ArmArchitectureMProfilePresetsTest#cps16OnlyUnderMProfileAndCpsFNeedsFaultMasking`) fixava a
asserção OPOSTA (`assertNotEquals(CPS, ...)` sob A-profile) — corrigido para `assertEquals`, com
comentário explicando que a asserção antiga capturava exatamente o gap que esta task fecha, não um
invariante.

Todos os 13 encodings de 16 bits (2×`SETEND`, 4×`CPS`, 3×`REV`/`REV16`/`REVSH`, 4×`SXTH`/`SXTB`/
`UXTH`/`UXTB`) conferidos com corpus real (`arm-none-eabi-as -mcpu=arm1176jzf-s` + `objdump`,
devkitARM) — bateram campo a campo com o derivado do `t16.decode`/ARM ARM.

## Escopo implementado

- **`SETEND`** de 16 bits (`ThumbDecoder`, `0xB650`/`0xB658`): reaproveita `InstructionKind.SETEND`
  e o `IrOp.SetEndianness` já existentes (mesmo `Kind`/executor da forma A32, B1.5). Gate
  `ArmFeature.SETEND_BIG_ENDIAN_DATA`.
- **`CPS` A/R-profile** de 16 bits (`0xB660`-`0xB67F`, sem campo de modo — T16 não carrega 5 bits de
  modo): reaproveita `InstructionKind.CPS`/`IrOp.ChangeProcessorState` (mesmo `Kind`/executor da
  forma A32, B1.5), empacotando `immediate` na MESMA convenção (bit1=`changeFlags` sempre 1 aqui,
  bit0=`imod` baixo, bit3=`changeA`, bit4=`changeI`, bit5=`changeF`, `changeMode`/`mode`=0). Gate
  `ArmFeature.MODE_CHANGE_INSTRUCTIONS` e `!M_PROFILE` (precedência: o bloco M-profile da B7.4,
  que reivindica o MESMO prefixo de 11 bits com um campo a menos, é checado primeiro e continua
  zero-diff).
- **`REV`/`REV16`/`REVSH`** de 16 bits (`0xBA00`/`0xBA40`/`0xBAC0`): reaproveita
  `InstructionKind.BYTE_REVERSE` (mesmo `Kind`/executor da forma A32, B1.2). Gate
  `ArmFeature.BYTE_REVERSE`.
- **`SXTH`/`SXTB`/`UXTH`/`UXTB`** de 16 bits, SEM acumulador (`0xB200`/`0xB240`/`0xB280`/`0xB2C0`,
  achado de triagem acima): reaproveita `InstructionKind.EXTEND` (mesmo `Kind`/executor da forma
  A32, B1.2) com `sourceRegister=-1` (sem acumulador) e rotação sempre 0. Gate
  `ArmFeature.EXTEND_ROTATE`.
- Nenhum `IrOp`/`InstructionKind` novo — as 4 famílias são decode-only, reaproveitando 100% da
  semântica/executor já existente da forma A32 (zero código de execução novo, só reconhecimento de
  encoding + empacotamento de campos).

## Não inclui

- `SXTAH`/`SXTAB`/`UXTAH`/`UXTAB` (COM acumulador de verdade) em T16 — não existem nesse espaço de
  encoding (achado de triagem acima); a forma real com acumulador já está coberta em A32/T32.
- Hints (`YIELD`/`WFE`/`WFI`/`SEV`/`NOP`) para `ARMV6K`/`ARM11_MPCORE` (sem Thumb-2) — já
  implementados desde B2.5 para os presets com `THUMB2`; decisão de manter o gate como está (achado
  2 acima), evidência insuficiente para relaxar com segurança.
- Paridade M-profile de `REV`/`SXTB`/etc. — `docs/COBERTURA-ISA.md` mostra que `ARMV6M` continua
  sem `ArmFeature.BYTE_REVERSE`/`EXTEND_ROTATE` (o ARM ARM real documenta essas instruções como
  parte do baseline ARMv6-M) — gap real, mas de COMPLETUDE do preset M-profile, não desta task
  (que é sobre A/R-profile). Fica registrado aqui para uma task futura de paridade M-profile, não
  criada agora (fora do "Inclui" desta task, precedente da regra 4 do `tasks/README.md`).
- `T32` (Thumb-2 de 32 bits): os mesmos mnemônicos já existem lá desde B2.7/B3.x; fora do escopo.

## Resultado

✅ (2026-08-22) — Ver seções acima. Achado principal: o plano mestre citava `SXTAH`/`SXTAB`/
`UXTAH`/`UXTAB` (com acumulador) para T16, mas a forma real de 16 bits é `SXTH`/`SXTB`/`UXTH`/
`UXTB` (sem acumulador) — confirmado contra `op_xta`/`translate.c` do QEMU, que só soma o
acumulador quando `Rn != 15`, e o formato `@extend` do T16 fixa `Rn=15`. Achado secundário: `CPS`
A/R-profile de 16 bits reaproveita o MESMO prefixo de encoding que o `CPS` M-profile da B7.4,
corrigindo um teste pré-existente que asserzia o gap como comportamento esperado.

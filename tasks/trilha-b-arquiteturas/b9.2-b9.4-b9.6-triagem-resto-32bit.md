# B9.2/B9.4/B9.6 — triagem do resto do 32 bits (Q11)

**Trilha:** B · **Depende de:** — · **Repo:** arm-jitter

## Contexto

Task "Q11" da fila (`tasks/FILA-EXECUCAO.md`, Onda 5 — cobertura de ISA restante), os 3 degraus não
escritos/não implementados que sobravam da escada 32 bits do plano mestre
(`trilha-b-arquiteturas/b7-plano-cobertura-isa.md`):

- **B9.2** — A32, resto: `MOVW`/`MOVT`/`MLS`/`SBFX`/`UBFX`/`BFC`/`BFI`/`RBIT`/`SDIV`/`UDIV`,
  marcado no plano como "⚠️ ARMv6T2/v7 — provável exclusão para ARMv6K puro; conferir".
- **B9.4** — T16 restante: `IT`, `CBZ`/`CBNZ`, `HLT`, `UDF`, `B` (T2/T4), `BLX` (registrador),
  marcado "v7-A".
- **B9.6** — VFP fundidas: `VFMA`/`VFMS`/`VFNMA`/`VFNMS`, marcado "⚠️ VFPv4 — provável exclusão
  para MPCore; conferir".

⚠️ **Sem spec formal escrita antes da implementação** — mesmo padrão ad-hoc de B6.9/B6.11/B8.1/B9.1/
B9.5 (task pequena o bastante para não precisar de rodada de spec separada, escrito na mesma sessão
que implementa). Este arquivo documenta a triagem real e o resultado.

## Diretiva do usuário (prioridade máxima)

"Não há nenhuma exclusão justificável, se o hardware faz então emula." As marcações "⚠️ provável
exclusão... conferir" do plano mestre não são conclusão — são convite a investigar a fundo contra
fonte primária real antes de decidir. Só é aceitável excluir com citação de fonte primária real
provando que a versão de arquitetura introduzida é POSTERIOR a TODOS os presets-alvo relevantes.

## Triagem real (fonte: QEMU `target/arm/tcg/{translate.c,translate-vfp.c,a32.decode,vfp.decode}`
## real do GitHub, `arm11mpcore_initfn`, mais o que já estava documentado em `ArmArchitecture.java`)

### B9.2 — A32 resto: EXCLUÍDO para `v6K`/`MPCore`, JÁ IMPLEMENTADO para `v7-A`

Achado antes de mexer em qualquer linha: `MOVW`/`MOVT`/`MLS`/`SBFX`/`UBFX`/`BFC`/`BFI`/`RBIT`/
`SDIV`/`UDIV` **já estavam implementados** no preset `ARMV7A` desde a task **B3.1** (2026-07-17) —
`ArmFeature.MOVW_MOVT`/`MLS_MULTIPLY`/`BIT_FIELD`/`BIT_REVERSE`/`DIVIDE`, carve-outs diretos em
`ArmDecoder`. O que faltava era só a decisão sobre `ARMV6K`/`ARM11_MPCORE`, que NUNCA herdaram essas
features (`ARM11_MPCORE_FEATURES = extending(ARMV6K, "ARM11-MPCore", VFPV2)` — sem nenhuma delas).

Confirmado contra `target/arm/tcg/translate.c` real do QEMU (`curl` direto, não `WebFetch`
resumindo, para citação exata):

- `trans_MOVW`/`trans_MOVT`/`trans_MLS`/`op_bfx` (`SBFX`/`UBFX`)/`trans_BFCI` (`BFC`/`BFI`)/
  `trans_RBIT`: todas `if (!ENABLE_ARCH_6T2) return false;`, e
  `#define ENABLE_ARCH_6T2 arm_dc_feature(s, ARM_FEATURE_THUMB2)` — **ARMv6T2, não ARMv6K**.
- `trans_SDIV`/`trans_UDIV` (via `op_div`): `dc_isar_feature(aa32_arm_div, s)` — a extensão
  OPCIONAL de divisão inteira do **ARMv7-A/R** (o próprio bit ISAR nem existe antes da v7),
  arquiteturalmente ainda mais nova que ARMv6T2.
- `arm11mpcore_initfn` (`target/arm/tcg/cpu32.c`) do QEMU: só `ARM_FEATURE_V6K` +
  `ARM_FEATURE_VAPA`/`MPIDR`/`DUMMY_C15_REGS` — **nunca** `ARM_FEATURE_THUMB2`.

O ARM11 MPCore real do 3DS (e o ARM1176JZF-S do raspi1/`virtual-arm-box`, mesma geração) é ARMv6K
puro, sem Thumb-2 — decisão já registrada em `b5.2-...md` ("Sem Thumb-2: o MPCore é ARMv6K, não
v6T2"), agora reforçada com a fonte QEMU exata. As 9 instruções são POSTERIORES aos dois presets-alvo
(`ARMV6K`/`ARM11_MPCORE`) por construção, com citação de fonte real — critério do usuário satisfeito
para exclusão. **Excluídas em `docs/isa-nao-aplicavel.tsv`** (9 linhas, `v6K,MPCore`, cada uma
citando a função/macro do QEMU). Nenhuma mudança de código — já implementadas onde pertencem.

### B9.4 — T16 restante: quase tudo já implementado; 3 achados reais

Medido contra `docs/COBERTURA-ISA.md` regenerado (não a lista do plano mestre, que envelheceu):

| Instrução | Situação antes desta task |
|---|---|
| `IT`, `CBZ` | ✅ já implementadas (B2.4/B9.3), corretamente gateadas por `THUMB2` (ARMv6T2+) |
| `B` (T2, incondicional) | ✅ já implementada desde sempre (ARMv4T Thumb base) |
| `BLX_r` (registrador) | ✅ já implementada (ARMv5T+, `ArmFeature.BLX`) |
| `B_cond_thumb` (condicional) | **❌ FALSO NEGATIVO** — já decodificada (`ThumbDecoder`, mapeia para `InstructionKind.BRANCH`), mas a ferramenta de medição sondava com `cond=AL(0b1110)`, que é justamente o valor RESERVADO desse campo (idêntico ao encoding de `UDF`) |
| `UDF` (16 bits, `0xDE00`-`0xDEFF`) | **gap real** — reconhecida pelo decoder, mas como `UNIMPLEMENTED` genérico, não como `InstructionKind.UDF` explícito (mesmo padrão que B9.1 já resolveu para o A32) |
| `HLT` (16 bits) | fora do escopo real desta task — ver "Não inclui" |

**Achado 1 (ferramenta de medição, não `ArmDecoder`/`ThumbDecoder`)**: `B_cond_thumb`
(`t16.decode`: `1101 cond:4 imm8`) tem um campo chamado `cond`, mas ali os únicos valores válidos são
`0b0000`-`0b1101` (14 condições reais) — `0b1110` é **reservado e permanentemente indefinido** (ARM
DDI 0406C A8.8.4: "cond != '1110' and cond != '1111'"; `0b1110` é, byte a byte, o mesmo encoding de
`UDF #0`, por isso `ThumbDecoder` intercepta `0xDE00`-`0xDEFF` antes de chegar no dispatch de
`B_cond_thumb`) e `0b1111` é `SVC`. `IsaCoverageReport.encode()` forçava `cond=0b1110` sempre que via
um campo chamado `cond` (regra correta para o resto da ISA, onde `cond` É o AL de 4 bits) — para
`B_cond_thumb` isso sonda acidentalmente o encoding reservado de `UDF`, não "branch sempre". Corrigido
em `IsaCoverageReport.encode()`: caso especial para `instruction.name().equalsIgnoreCase("B_cond_thumb")`
usa `cond=0b0000` (`EQ`, sempre válido) em vez de `0b1110`. `ThumbDecoder` não mudou — já decodificava
`B<cond>` corretamente para as 14 condições válidas (teste de regressão não precisou mudar nada além
de reconhecer o `Kind` certo em `ArmExceptionHandlingTest`, que já esperava `CpuMode.UNDEFINED` ao
executar `0xDE00`, comportamento preservado).

**Achado 2 (gap real, mesmo padrão de B9.1)**: `UDF` de 16 bits (`ARM DDI 0406C A8.8.247`,
`t16.decode`: `1101 1110 imm8`) — instrução permanentemente indefinida, sem gate de versão.
`ThumbDecoder` já a reconhecia (`(raw & 0xFF00) == 0xDE00`), mas devolvia `UNIMPLEMENTED` genérico em
vez do `InstructionKind.UDF` explícito que a B9.1 introduziu para o A32 (e a B9.7 para o T32
`UDF.W`) — só para a tabela de cobertura distinguir "sempre indefinida por definição" de "gap de
decode real"; comportamento observável idêntico nos dois casos (`StandardIrBlockLifter` já cortava a
fronteira de bloco para os dois `Kind`s desde a B9.1, então nenhuma mudança adicional foi necessária
ali). Corrigido em `ThumbDecoder` (o mesmo bloco `if ((raw & 0xFF00) == 0xDE00)`, trocando o retorno).

Encodings reais conferidos com `arm-none-eabi-as -mfpu=vfpv4 -mfloat-abi=hard` (devkitARM) +
`arm-none-eabi-objdump`: `udf #0` → `0xDE00`, `udf #42` → `0xDE2A`, `beq.n` → `0xD0FF` (cond=EQ).

### B9.6 — VFP fundidas: EXCLUÍDAS para `MPCore`, IMPLEMENTADAS para `v7-A`

Confirmado contra `target/arm/tcg/translate-vfp.c` real do QEMU (`do_vfm_sp`/`do_vfm_dp`, macro
`MAKE_ONE_VFM_TRANS_FN`/`MAKE_VFM_TRANS_FNS`): gate `dc_isar_feature(aa32_simdfmac, s) &&
dc_isar_feature(aa32_fpsp_v2/aa32_fpdp_v2, s)`, com o comentário literal no código-fonte:

> "Present in VFPv4 only. Note that we can't rely on the SIMDFMAC check alone, because in a
> Neon-no-VFP core that ID register field will be non-zero."

**VFPv4, não VFPv2.** O ARM11 MPCore (3DS) é cronologicamente ANTERIOR à especificação VFPv4: a
geração ARM11/ARM1136/ARM1176/MPCore é de ~2002-2005, VFPv4 chega com a geração Cortex-A15/A7
(~2010, junto de NEONv2/half-precision). Não é "improvável" — é impossível por construção, mesmo
critério que a exclusão do A32 acima. **Excluída em `docs/isa-nao-aplicavel.tsv`** (8 linhas: as
formas `_sp`/`_dp` de `VFMA`/`VFMS`/`VFNMA`/`VFNMS`, `MPCore`; as formas `_hp` de meia-precisão nem
chegam a ser célula aplicável, mesmo motivo já registrado na TSV para `VCVT_f32_f16` etc.).

**Implementada para `v7-A`** (ARMV7A_FEATURES ganha `ArmFeature.VFP_FUSED_MULTIPLY_ACCUMULATE`),
mesma nota já feita para `SDIV`/`UDIV` no preset: "este preset emula um core que a possui, como o
Cortex-A15/A7".

Mapeamento de sinal confirmado bit a bit contra a macro `MAKE_ONE_VFM_TRANS_FN(INSN, PREC, NEGN,
NEGD)` do QEMU (`VFMA(false,false)`/`VFMS(true,false)`/`VFNMS(false,true)`/`VFNMA(true,true)`) e
contra o encoding real (`vfp.decode`): `op1` (bits `23,21,20`) `0b110` = família `VFMA`/`VFMS`
(`bit6=0`/`1`), `op1=0b101` = família `VFNMS`/`VFNMA` (`bit6=0`/`1`) — **MESMO** bit6 que já
seleciona `MLA`/`MLS`/`NMLA`/`NMLS` na família não-fundida vizinha (nenhum campo de bits novo,
reaproveita 100% da extração já existente em `VfpDecoder#decodeDataProcessing`). Resultado: convenção
de sinal idêntica às formas não-fundidas correspondentes (`FMA`≡`MLA`, `FMS`≡`MLS`, `FNMA`≡`NMLA`,
`FNMS`≡`NMLS`), só muda o arredondamento (um passo fundido via `Math.fma`, em vez de dois passos
arredondados separadamente).

Encodings reais conferidos com `arm-none-eabi-as -mfpu=vfpv4 -mfloat-abi=hard` (devkitARM):
`vfma.f32 s0,s1,s2` → `0xEEA00A81`, `vfms.f32 s0,s1,s2` → `0xEEA00AC1`, `vfnma.f32 s0,s1,s2` →
`0xEE900AC1`, `vfnms.f32 s0,s1,s2` → `0xEE900A81`, `vfma.f64 d0,d1,d2` → `0xEEA10B02`,
`vfnma.f64 d3,d4,d5` (Thumb-2, 32 bits) → `0xEE943B45` — todos batem campo a campo com a fórmula de
encoding derivada acima (conferido programaticamente no teste, não só "parece certo").

## Escopo implementado

- **`ArmFeature.VFP_FUSED_MULTIPLY_ACCUMULATE`** novo, em `ARMV7A_FEATURES` (não em `ARM11_MPCORE`/
  `ARMV6K`).
- **`IrOp.VfpOperation`** ganha `FMA`/`FMS`/`FNMA`/`FNMS` — únicos membros do enum que usam
  `Math.fma` de verdade (o resto da família `VfpOperation`, VFPv2, nunca funde).
- **`DirectedFpRounding.exactFma(a,b,c)`** novo: valor exato de `a*b+c` como `BigDecimal` num único
  passo (produto e soma na mesma expressão, sem o arredondamento intermediário que
  `exactMul`+`exactAdd` em dois passos teria) — é esse único-passo que distingue a família fundida.
- **`IrVfpExecutor`**: `computeSingleArithmetic`/`computeDoubleArithmetic` ganham os 4 casos novos,
  usando `Math.fma` para o candidato "nearest" e `exactFma` para o arredondamento dirigido (RMode/FZ
  já suportados, mesma infraestrutura da B3.8).
- **`VfpDecoder`**: dois `case` novos em `decodeDataProcessing` (`op1==0b110`/`0b101`), reaproveitando
  100% da extração de bits já existente (`vn`/`vd`/`vm`/`bit6`); gate adicional
  `VFP_FUSED_MULTIPLY_ACCUMULATE` além do `VFPV2` já checado pelo chamador — sem a feature, cai em
  `null` → `UNDEFINED` explícito (G8; este encoding nunca foi reivindicado por nenhum outro dispatch
  antes desta task, sem risco de misdecode). `Thumb2VfpDecoder` herda de graça (casca fina).
- **`AsmBlockCompiler`/`AsmRuntimeHelpers`**: os 4 `Kind`s novos entram no caminho "cold" já usado por
  `MLA`/`MLS`/`NMLA`/`NMLS`/`NMUL`/`SQRT` (chamada a `AsmRuntimeHelpers.vfpAluCold`), usando
  `Math.fma` diretamente — sob FPSCR default (RMode=nearest, FZ=0) equivale byte a byte ao
  interpretado; RMode≠nearest é uma limitação PRÉ-EXISTENTE deste helper para os vizinhos não-fundidos
  também, não introduzida por esta task.
- **`ThumbDecoder`**: `UDF` de 16 bits (`0xDE00`-`0xDEFF`) passa a usar `InstructionKind.UDF`
  explícito em vez de `UNIMPLEMENTED` genérico (mesmo padrão de B9.1/B9.7).
- **`IsaCoverageReport.encode()`** (ferramenta de medição, `core/src/test`): caso especial para
  `B_cond_thumb` — usa `cond=EQ(0b0000)` em vez do `AL(0b1110)` padrão, que para esse mnemônico
  específico é o encoding reservado de `UDF`, não "sempre". Falso negativo corrigido, sem mudança de
  comportamento em `ThumbDecoder`.
- **`docs/isa-nao-aplicavel.tsv`**: 17 linhas novas — 9 para `MOVW`/`MOVT`/`MLS`/`SBFX`/`UBFX`/
  `BFCI`/`RBIT`/`SDIV`/`UDIV` (`v6K,MPCore`) + 8 para `VFMA_sp`/`VFMA_dp`/`VFMS_sp`/`VFMS_dp`/
  `VFNMA_sp`/`VFNMA_dp`/`VFNMS_sp`/`VFNMS_dp` (`MPCore`), cada uma citando a função/macro/comentário
  real do QEMU.

## Não inclui

- **`HLT` de 16 bits** (T16, `1011 1010 10 imm:6`) — investigado, mas **não é** um simples gap de
  decode como `UDF`: `trans_HLT`/`gen_hlt` do QEMU não têm gate de arquitetura, e o comportamento
  real (sem hardware de debug externo conectado) é "trata como `UNDEFINED`, EXCETO quando semihosting
  está habilitado e o imediato bate um valor mágico (`0xF000` A32 / `0x3C` T16), aí dispara uma
  syscall de semihosting". O arm-jitter não implementa semihosting hoje (só `BKPT`, via
  `BkptDispatcher`/`BkptHandler`) — decidir HLT corretamente exigiria decidir semihosting primeiro,
  que é escopo maior que "triagem do resto do 32 bits". Fica como trabalho pendente aberto (candidata
  a task própria, "semihosting + HLT"), não excluída (não há fonte que prove versão POSTERIOR — pelo
  contrário, é sempre-UNDEFINED por definição em qualquer versão sem debug externo — só não é este o
  escopo desta task). A32 `HLT` já aparecia ✅ na tabela ANTES desta task (mecanismo não investigado,
  fora do escopo das 3 IDs desta task — nenhuma delas cita `HLT` A32).
- Nenhuma mudança em `n3dsemu`/`virtual-arm-box`/`gbaemu`/`ndsemu`/`armbox` além da reinstalação local
  do `arm-jitter` para G5.

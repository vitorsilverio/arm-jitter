# A10.8 — [REFINAR/RFC] Truffle para **AArch64**: o backend que não existe — 96 `Kind`

**Trilha:** A · **Repo:** arm-jitter · **Depende de:** A10.7, C12.9
**Épico:** `a10-plano-truffle-completo.md` · **Status:** ⬜ **RFC antes de implementar**

## Contexto

Medição da **C12.1** (`docs/COBERTURA-JIT.md`): **Truffle 64 bits = 0 de 96**. Não é cobertura baixa
— **o backend não existe**. O módulo `truffle/` não tem um único nó de `Ir64Op`; a coluna existe na
tabela só para tornar a ausência visível.

É o maior item isolado que separa o projeto do "100%" nas 4 dimensões do
[`ROADMAP-100-ARM.md`](../ROADMAP-100-ARM.md), e é um **épico dentro do épico**: espelhar
`IrOpNode`/`IrOpNodeFactory`/`TruffleCodeEmitter`/`TruffleBlockRootNode` para o pipeline de 64 bits,
mais os 96 `Kind`.

## Esta task é uma RFC, não uma implementação

O plano A10 já a marca `[REFINAR]` com a pergunta certa:

> *Precisa de RFC própria: vale a pena, ou o backend ASM 64 (C12) já cobre o caso de uso?*

A pergunta é séria e tem argumentos dos dois lados:

**Contra:**
- O backend **ASM 64** existe e, depois do épico C12, cobre a maior parte dos `Kind`. Os dois
  backends competem pelo mesmo caso de uso.
- O Truffle só rende de verdade com **GraalVM** e com especialização real (assumptions, profiles) —
  e a escada A10.3-A10.7 deliberadamente **não especializa**, só delega. Um backend Truffle de 96
  `Kind` que delega é, na prática, o interpretador com overhead de árvore.
- **Nenhum consumidor pede.** `armbox` é o único que usa o backend Truffle, e o workload dele é
  ARMv5TE. `virtual-arm-box` (o consumidor A64) usa ASM/interpretado.
- Os números da **A5**/**A7**/**A8** (`docs/TRUFFLE-BACKEND.md`) mostram que o ganho do Truffle no
  lado de 32 bits foi real em GraalVM mas **negativo** em HotSpot padrão.

**A favor:**
- A dimensão 3 do roadmap nunca fecha sem isso.
- A regra máxima do projeto (`tasks/README.md`) é sobre **cobertura de ARM**, e o Truffle é um
  backend, não uma arquitetura — mas o `ROADMAP-100-ARM.md` o listou como dimensão, então a decisão
  precisa ser explícita.
- Se o Truffle for a rota para native-image/AOT (A5/A9), o lado A64 fica de fora dela.

**Leitura obrigatória**: `a10-plano-truffle-completo.md`, `docs/TRUFFLE-BACKEND.md` (os números
medidos de A5/A7/A8 — **inclusive o caso em que GraalVM standalone foi 5,24× PIOR**), o
`ROADMAP-100-ARM.md`, a **A10.1** (a arquitetura atual: `category`/`supports`/fallback), a **A4**
(`TruffleJitRuntimeFactory` — API pública, G3) e a **C12.9** (`## Resultado` — a cobertura ASM 64
final, que é a linha de base da comparação). No código: `truffle/` INTEIRO,
`codegen64/`, `jit64/JitRuntime64`.

## Objetivo

Uma decisão registrada em `docs/`, com **medição**, sobre se o backend Truffle de 64 bits deve
existir — e, se sim, a escada para construí-lo.

## As três rotas

| Rota | O que é | Quando faz sentido |
|---|---|---|
| **(a) Espelho completo** | `Ir64OpNode`/`Ir64OpNodeFactory`/`Truffle64CodeEmitter` + 96 `Kind` | se houver caso de uso medido (GraalVM/native-image no lado A64) |
| **(b) Mínimo viável** | só a infra + os `Kind` do caminho quente, com fallback honesto (o desenho da A10.1) para o resto | fecha a dimensão parcialmente, com custo baixo |
| **(c) Não construir** | registrar a decisão, com o número, e a condição de reabertura | se a medição disser que o ASM 64 cobre o caso de uso |

**A rota (c) é legítima** — mas, como sempre neste projeto, **só se for medida e registrada com a
condição que a reabriria**, nunca como "fora de escopo".

## Inclui

1. **Medição comparativa** do que já existe: backend ASM 64 (pós-C12.9) × interpretado, no workload
   A64 real disponível (`armbox` aarch64, `virtual-arm-box`), em **HotSpot e em GraalVM**.
2. **Protótipo mínimo** (rota (b)) de um punhado de `Kind` de 64 bits, só para medir o custo de
   construção e o ganho — não precisa ser completo.
3. **Documento `docs/RFC-TRUFFLE-AARCH64.md`** com as três rotas, os números, a decisão e a escada
   (se houver).
4. **Se a decisão for (a) ou (b)**: escada A10.8.1-A10.8.N, com os 96 `Kind` distribuídos por
   categoria (espelhando as 7 da A6 + as que a A10.3-A10.7 acrescentaram).

## Não inclui

- **Construir o backend** antes da decisão.
- **Especialização** — se a RFC concluir que só especialização justifica o backend, isso é parte da
  decisão, não desta task.
- **Mexer no backend Truffle de 32 bits** (A10.3-A10.7) nem em `TruffleJitRuntimeFactory` (API
  pública desde a A4 — G3).

## Aceite

- **`docs/RFC-TRUFFLE-AARCH64.md`** com as três rotas, a medição, a decisão e o porquê.
- **Números, não impressão**: ASM 64 × interpretado × protótipo Truffle, em HotSpot **e** GraalVM,
  com a metodologia descrita (execuções, máquina, JDK/JVM). **`docs/TRUFFLE-BACKEND.md` já tem o
  precedente de tabela honesta** — inclusive registrando um caso em que o Truffle foi pior.
- **Se (a)/(b)**: escada definida, com tamanho por degrau.
- **Se (c)**: registrada como **medida**, com a condição de reabertura, e `docs/COBERTURA-JIT.md`
  ganha nota explicando por que a coluna Truffle 64 segue inteira `❌` deliberadamente. O
  `ROADMAP-100-ARM.md` reflete isso na dimensão 3.
- **G3**: `TruffleJitRuntimeFactory` inalterada.
- Zero mudança de runtime fora do protótipo.

## Armadilhas

1. **Medir em HotSpot E em GraalVM.** O `docs/TRUFFLE-BACKEND.md` registra que o resultado inverte
   entre os dois — uma medição só num deles decide errado.
2. **A linha de base é o ASM 64 pós-C12.9**, não o interpretado. Comparar contra o interpretado
   infla o ganho.
3. **"Delegar" não é backend Truffle de verdade.** Se a única forma de o backend render for
   especializar, a RFC tem que dizer isso — e aí o custo real não são 96 `Kind`, é 96 `Kind`
   especializados.
4. **(c) não é exclusão** — regra máxima.
5. **Workload real**, não microbenchmark.
6. **Nenhum consumidor pede hoje** — isso é dado de entrada, não argumento de autoridade; a
   biblioteca está no Maven Central e "nenhum projeto deste workspace usa" nunca foi argumento para
   reduzir escopo (`tasks/README.md`). Mas **é** argumento para priorizar depois.

## Não fazer

- Não construir o backend antes da decisão.
- Não medir só em HotSpot.
- Não comparar contra o interpretado.
- Não registrar (c) como "fora de escopo".
- Não mexer em `TruffleJitRuntimeFactory`.

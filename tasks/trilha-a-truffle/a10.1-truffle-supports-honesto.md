# A10.1 — Truffle: `supports` passa a dizer a verdade (troca crash por fallback)

**Trilha:** A · **Repo:** arm-jitter (+ revalidação G5 nos consumidores) · **Depende de:** —
**Épico:** `a10-plano-truffle-completo.md` · **Status:** ✅ (2026-09-02) — ver `## Resultado`

## Contexto

**Esta é uma correção de bug, não uma feature.** É a única task urgente do épico A10, não depende de
nada, e é pequena.

Hoje o backend Truffle tem dois fatos que, isolados, são inofensivos, e juntos são fatais:

1. `TruffleCodeEmitter#supports(IrBlock)` é literalmente `return true;` (`TruffleCodeEmitter.java:80-82`),
   com Javadoc afirmando *"`IrOpNodeFactory` cobre exaustivamente todo `IrOp.Kind`"*.
2. `IrOpNodeFactory#create` cobre **40 dos 73** `IrOp.Kind` e termina em
   `default -> throw new IllegalStateException("IrOp kind desconhecido: " + op.kind())`
   (`IrOpNodeFactory.java:40`).

A afirmação do Javadoc **era verdade na A3/A6** e deixou de ser conforme B3 (VFP), B9 (`HVC`/`SMC`/
`ERET`/`MRS_bank`/`MSR_bank`), B1/B3 (bitfield/`RBIT`/`SDIV`/`UDIV`), B7 (perfil M) e B13 (NEON)
acrescentaram Kinds. Ninguém percebeu porque **a superfície quebrada nunca foi exercitada**: os 13
testes do módulo `truffle/` cobrem o inteiro ARM/Thumb, `gbaemu` roda `ARMV4T` e `ndsemu` `ARMV5TE`
(nenhum tem VFP), e `armbox`/`virtual-arm-box` não usam o backend Truffle por padrão.

**Resultado medido (2026-09-02): qualquer binário ARM com uma instrução de ponto flutuante mata o
backend Truffle com `IllegalStateException`.** Não degrada, não cai para o interpretador — quebra.
São **33 Kinds**: `BIT_FIELD_EXTRACT`, `BIT_FIELD_INSERT`, `BIT_REVERSE`, `DIVIDE`, os 14 de VFP/
coprocessador (`VFP_ALU`, `VFP_MOVE_IMMEDIATE`, `VFP_COMPARE`, `VFP_CONVERT`, `VFP_LOAD`,
`VFP_STORE`, `VFP_MULTIPLE_TRANSFER`, `VFP_CORE_TRANSFER`, `VFP_CORE_PAIR_TRANSFER`,
`VFP_SYSTEM_TRANSFER`, `VFP_CORE_PAIR_TRANSFER_SINGLE`, `VFP_CONVERT_FIXED`, `COPROCESSOR_DOUBLE`,
`M_PROFILE_SYSTEM_REGISTER`), `BREAKPOINT`, `DSP_DUAL_MULTIPLY`, `DSP_TOP_WORD_MULTIPLY`, `HVC`,
`SMC`, `ERET`, `MRS_BANK`, `MSR_BANK`, e os 7 de NEON (`NEON_THREE_SAME`,
`NEON_LOAD_STORE_MULTIPLE`, `NEON_LOAD_STORE_SINGLE`, `NEON_LOAD_ALL_LANES`, `NEON_PAIRWISE`,
`NEON_FP_THREE_SAME`, `NEON_FP_PAIRWISE`).

**A infraestrutura do conserto já existe e já está fiada**: `TruffleCodeEmitter` tem o campo
`fallback` (um `InterpretedCodeEmitter`), o contador `fallbackBlockCount`, e o
`if (!supports(block)) { fallbackBlockCount.incrementAndGet(); return fallback.emit(block); }`
(`:49-52`). Só nunca é `false`. Esta task faz esse caminho existir.

Achado registrado antes: RFC **B13.2** ("Achados abertos") anotou que *"o backend Truffle quebra com
QUALQUER op de VFP — `IrOpNodeFactory` não tem casos VFP e `TruffleCodeEmitter#supports` devolve
`true` sempre"*, pré-existente e verificado; a **B13.6** o herdou como pendência 3. Esta task fecha o
achado.

**Leitura obrigatória**: `a10-plano-truffle-completo.md`, e no código —
`truffle/.../TruffleCodeEmitter` (INTEIRO, 83 linhas), `truffle/.../IrOpNodeFactory` (INTEIRO, 43),
`truffle/.../IrOpNode`, `truffle/.../TruffleBlockRootNode`,
`codegen/jvm/AsmNativePolicy#supports(IrBlock)` (**o padrão a espelhar**: varre as ops e pergunta por
cada uma), `codegen/InterpretedCodeEmitter`, `ir/IrOp.Kind`.

## Objetivo

O backend Truffle **nunca lança** por Kind não coberto: blocos que contenham um Kind fora da factory
são emitidos pelo `fallback` interpretado, contabilizados em `fallbackBlockCount`, e produzem estado
de CPU **idêntico** ao interpretador (G1). Nenhum Kind novo é implementado nesta task.

## Inclui

1. **`IrOpNodeFactory.supports(IrOp op)`** — método novo, `static boolean`, package-private (mesma
   visibilidade de `create`). Devolve `true` exatamente para os Kinds que `create` sabe construir.
   **A implementação tem de ser estruturalmente à prova de divergência** — ver "Especificação".
2. **`TruffleCodeEmitter#supports(IrBlock)`** deixa de ser `return true` e passa a varrer:
   ```java
   private static boolean supports(IrBlock block) {
       for (IrOp op : block.operations()) {
           if (!IrOpNodeFactory.supports(op)) {
               return false;
           }
       }
       return true;
   }
   ```
   Espelhar `AsmNativePolicy#supports(IrBlock)` (mesma forma, mesmo estilo).
3. **Javadoc corrigido nos dois arquivos** (G7, `///` PT). Hoje os dois afirmam cobertura exaustiva:
   - `TruffleCodeEmitter` (Javadoc de classe, `:28-31`, e o de `supports`, `:78-79`): dizer que a
     factory cobre um SUBCONJUNTO, que o fallback é o caminho real para o resto, e **por que** (a
     cobertura Truffle ficou para trás de B3/B7/B9/B13 — com a lista de categorias que faltam
     apontando para A10.3-A10.7).
   - `IrOpNodeFactory` (Javadoc de classe): idem; o texto "o `switch` de 40 casos" continua correto
     em número, mas passa a dizer explicitamente que **não é exaustivo** e que o `default` só é
     alcançável por bug (já que `supports` filtra antes).
4. **Testes** (ver Aceite): um bloco com Kind não coberto executa CERTO pelo fallback e incrementa o
   contador; e um teste que trava a coerência factory↔supports.

## Não inclui (com destino explícito)

## Especificação

### `IrOpNodeFactory.supports` — a armadilha de projeto

O jeito ingênuo é copiar a lista de Kinds de `create` para um segundo `switch`. **Isso cria duas
listas que vão divergir** — e a divergência é silenciosa nos dois sentidos:

- `supports` mais permissivo que `create` ⇒ volta o `IllegalStateException` (o bug de hoje);
- `supports` mais restrito ⇒ blocos perfeitamente suportados caem no fallback (perda de performance
  invisível, exatamente o tipo de coisa que apodrece sem ninguém notar — como esta cobertura
  apodreceu de A6 até aqui).

**Escolher UMA das duas formas abaixo** (a segunda é preferível; decidir no código e registrar no
`## Resultado`):

**(a) Uma fonte, dois usos** — extrair a lista para um único ponto (`private static final Set<Integer>
SUPPORTED_KINDS`, ou um método `category(IrOp)` que devolve um enum de categoria e é usado pelos
dois). `create` e `supports` passam a consultar a MESMA estrutura.

**(b) `supports` implementado sobre `create`** — mais simples e à prova por construção:
```java
static boolean supports(IrOp op) {
    return switch (op.kind()) { /* mesma lista */ -> true; default -> false; };
}
```
…**não** é (b). A forma (b) de verdade é fazer `create` devolver `null` em vez de lançar, e
`supports` ser `create(op, executor) != null` — mas isso constrói um nó só para descartá-lo.

⇒ **Preferir (a)**, com um **teste que prova a coerência** (ver Aceite): para os 73 Kinds, se
`supports` diz `true`, então `create` não lança; se diz `false`, `create` lança. Esse teste é o que
impede a regressão futura, e é mais importante que a escolha entre (a) e (b).

## Armadilhas

1. **Duas listas divergem.** É o risco central da task — ver "Especificação". O teste de coerência é
   obrigatório, não decorativo: sem ele, esta correção reintroduz em 6 meses exatamente o bug que
   está consertando.
2. **`supports` é por BLOCO, a factory é por OP.** `TruffleCodeEmitter#supports(IrBlock)` tem de
   varrer; `IrOpNodeFactory.supports(IrOp)` responde por op. Confundir os dois níveis dá erro de
   compilação no melhor caso e política errada no pior.
3. **Não "consertar" o `default -> throw` removendo-o.** Ele continua sendo a rede de segurança
   correta (G8, espírito): depois desta task ele só é alcançável por bug — `supports` filtra antes.
   Trocá-lo por `null` silencioso troca um crash diagnosticável por um NPE distante.
4. **O `switch` da factory roda na EMISSÃO, não em runtime** — crescê-lo (ou acrescentar `supports`
   ao lado) **não** degrada o partial evaluation do Graal; o Javadoc de `IrOpNodeFactory` explica
   isso. Não tentar "otimizar" com reflexão, tabela dinâmica ou lookup por índice.
5. **`InterpretedCodeEmitter` já está construído no campo `fallback`** — não instanciar outro, não
   torná-lo lazy. Ele é criado no construtor e é o oráculo (G1).
6. **Não é otimização.** Não justificar/medir a task por performance: hoje o caminho alternativo é
   uma exceção. A medição de performance do fallback é A10.2+.

## Resultado

**2026-09-02 — feito.** Troca crash por fallback; nenhum `Kind` novo implementado.

### O que mudou

- **`IrOpNodeFactory`** — forma **(a)** ("uma fonte, dois usos"). Extraído o `switch` de
  `op.kind()` para um `private static Category category(IrOp op)` (enum `Category` de 7 valores:
  `ALU`/`MULTIPLY`/`MEMORY`/`TRANSFER`/`BRANCH`/`SYSTEM`/`CYCLE_FETCH`), com `default -> null`.
  `create` agora faz `category(op)` → se `null`, `throw new IllegalStateException(...)` (a rede de
  segurança G8 continua, só alcançável por bug); senão mapeia a categoria ao nó. `supports(IrOp)`
  novo = `category(op) != null`. As duas listas não podem mais divergir porque **não há duas
  listas** — há um `switch` só.
  - **Por que (a) e não (b)**: a forma (b) honesta (fazer `create` devolver `null` e `supports`
    ser `create(op, executor) != null`) constrói um nó só para descartá-lo a cada chamada de
    `supports` — e `supports` roda por op em CADA bloco emitido. (a) não aloca nada.
- **`TruffleCodeEmitter#supports(IrBlock)`** — deixou de ser `return true`; varre
  `block.operations()` e devolve `false` no primeiro `!IrOpNodeFactory.supports(op)`. Forma
  idêntica a `AsmNativePolicy#supports(IrBlock)`. O `if (!supports(block)) { fallbackBlockCount++;
  return fallback.emit(block); }` que já existia em `emit` (:49-52) passa a ser alcançável.
- **Javadoc** (G7, `///` PT) de `TruffleCodeEmitter` (classe + `supports`) e `IrOpNodeFactory`
  (classe) reescrito: não afirmam mais cobertura exaustiva, dizem que a factory cobre um
  SUBCONJUNTO (40/73), que o fallback é o caminho real para o resto e **por quê** (B1/B3/B7/B9/B13
  acrescentaram Kinds depois da A6), apontando A10.3-A10.7 por categoria.

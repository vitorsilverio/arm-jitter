# G6.2 — `fs:USER`: `OpenArchive`/`OpenFileDirectly`/`FSFILE:` mínimos (RomFS self-mount de `.3dsx`)

**Fecha:** nenhuma issue própria ainda — nasce da causa 1 achada pela G6.1.

## Contexto

A `G6.1` mediu os 6 exemplos `graphics/gpu` que ainda não desenhavam e achou 2 causas reais,
cada uma bloqueando 3 exemplos. Esta task ataca a **causa 1**: `composite_scene`/`cubemap`/
`gpusprites` chamam `svcBreak(PANIC)` porque `fs:USER` não implementa `OpenArchive` (0x080C) nem
`OpenFileDirectly` (0x0803) — qualquer chamada cai no `respondUnknown` genérico de
`AbstractService`, e o guest reage a um resultado de erro fechando o processo.

**Achado real desta sessão, confirmado no `romfs.h` real instalado
(`C:\devkitPro\libctru\include\3ds\romfs.h`) e no fonte de `cubemap`/`gpusprites`
(`C:\devkitPro\examples\3ds\graphics\gpu\{cubemap,gpusprites}\source\main.c`, que chamam
`romfsInit()`/`C2D_SpriteSheetLoad("romfs:/...")`)**: para um `.3dsx` (RFC-N3DSEMU — este
projeto nunca carrega CIA/NCCH), `romfsInit()` é `romfsMountSelf("romfs")`, documentado no
próprio header: *"If the application is running as 3DSX, it mounts the embedded RomFS section
inside the 3DSX"*. O mecanismo real (confirmado contra `libctru/source/romfs_dev.c` via
`WebFetch` no GitHub): o guest chama `FSUSER_OpenFileDirectly(&fd, ARCHIVE_SDMC, path_vazio,
path_do_proprio_.3dsx, FS_OPEN_READ, 0)` para abrir **o próprio arquivo `.3dsx`** a partir do
cartão SD, lê o cabeçalho 3DSX estendido desse `fd` (`FSFILE_Read`) para achar o offset do RomFS
dentro do arquivo, e a partir daí só faz leituras brutas (`FSFILE_Read`) nesse MESMO `fd` em
offsets absolutos — a análise da estrutura RomFS (hash tables/diretórios/arquivos) é feita
**inteiramente pelo guest**, nunca pelo host.

**Consequência que simplifica MUITO esta task**: não precisamos implementar um parser de RomFS
em Java. Basta que `OpenFileDirectly` devolva uma sessão de arquivo que sirva os **bytes brutos
do próprio `.3dsx` já carregado** (o mesmo `byte[]` que `Loader3dsx` já leu do disco) através de
`FSFILE_Read`/`FSFILE_GetSize`/`FSFILE_Close` — o guest faz o resto sozinho.

`composite_scene` não usa RomFS no fonte (`grep` não acha `romfs`/`.t3x`/`fopen` em
`main.c`/`lenny.c`), mas o binário linkado (`composite_scene.lst`) referencia
`FSUSER_OpenArchive`/`FSUSER_CloseArchive`/o devoptab `archive_*` de newlib — é o registro
padrão do device `sdmc:` feito pelo runtime do libctru (`archiveMountDevice`), independente de
uso explícito de arquivo pelo `main()`. Devolver sucesso genérico para `OpenArchive` (sem
semântica real de arquivo — nenhum comando desta task opera "sobre" uma archive-handle) é
suficiente para esse caso.

## Objetivo

`composite_scene`/`cubemap`/`gpusprites` deixam de chamar `svcBreak(PANIC)` por causa de
`fs:USER`; `cubemap`/`gpusprites` conseguem ler os `.t3x` do RomFS embutido de verdade.

## Inclui

1. `FsUserService`: `OpenArchive` (0x080C) e `CloseArchive` (0x080E) — sucesso genérico, sem
   modelar arquivos de verdade (nenhum comando aceita uma archive-handle como entrada nesta
   task). Handle de archive é um valor `long` **placeholder fixo** (nomeado, não mágico),
   nunca usado depois — não há como um `.3dsx` real distinguir arquivos por handle real, dado
   que esta HLE só serve UM arquivo em qualquer cenário (ver item 2).
2. `FsUserService`: `OpenFileDirectly` (0x0803) — **ignora** `archiveId`/`archivePath`/
   `filePath` de propósito (simplificação documentada: esta emulação não tem cartão SD, e o
   único uso real de `OpenFileDirectly` neste corpus é o self-mount do RomFS, que sempre quer
   os bytes do `.3dsx` em execução) e devolve uma handle nova para uma sessão de arquivo que
   serve os bytes brutos do `.3dsx` carregado.
3. Sessão de arquivo nova (`FsFileService` ou nome equivalente): `FSFILE::Read` (0x0802),
   `FSFILE::GetSize` (0x0804), `FSFILE::Close` (0x0808) — leem/reportam o tamanho do `byte[]`
   bruto do `.3dsx`; `Close` remove a sessão do `ServiceRegistry` (adicionar
   `ServiceRegistry#unregister`).
4. `Image3dsx` ganha um componente novo com o `byte[]` bruto do arquivo (o `Loader3dsx` já tem
   essa referência em `parse()` — só precisa propagar); `N3dsMachine` passa esse `byte[]` ao
   construir `FsUserService`.
5. Testes automatizados novos para os 3 comandos de `fs:USER` e os 3 de `FSFILE:` (padrão dos
   testes existentes de serviço, ex. `AptServiceTest`/`GspGpuServiceTest`).
6. Rebuild + `--report`/execução real de `composite_scene`/`cubemap`/`gpusprites` (binários já
   existem de sessões anteriores em `C:\devkitPro\examples\3ds\graphics\gpu\<exemplo>`, ver
   Armadilha do `testdata/README.md`) confirmando que não panicam mais.

## Não inclui

- Parser de RomFS em Java (ver "Consequência" no Contexto — desnecessário, o guest já faz isso).
- `sdmc:` real (escrita, diretórios, múltiplos arquivos) — só o self-mount do próprio `.3dsx`.
- `ARCHIVE_ROMFS`/`romfsMountFromCurrentProcess` (caminho de título CIA/NCCH) — fora do escopo
  deste projeto (`.3dsx` homebrew apenas).
- Validação visual em janela (RFC D4) — fica para quando o usuário rodar.
- Os 3 exemplos da causa 2 (`fragment_light`/`lenny`/`textured_cube`, `VertexShaderInterpreter`
  `CMP`/`MAD`) — candidata `G6.3`, sessão separada.

## Especificação

### Comandos de `fs:USER` (3dbrew IPC — cabeçalhos conferidos contra
`libctru/source/services/fs.c` real via `WebFetch`, não recordados de memória)

- **`OpenArchive`** — `header=IPC_MakeHeader(0x80C,3,2)`. Request: `normal[0]`=archive id,
  `normal[1]`=path.type, `normal[2]`=path.size, grupo traduzido 0 = buffer estático do path
  (ignorado). Resposta: `header(cmd,3,0)`, `result`, `normal64(1)` = handle de archive
  placeholder.
- **`CloseArchive`** — `header=IPC_MakeHeader(0x80E,2,0)`. Request: `normal[0..1]` = archive
  handle (64 bits, ignorado). Resposta: `header(cmd,1,0)`, `result`.
- **`OpenFileDirectly`** — `header=IPC_MakeHeader(0x803,8,4)`. Request: `normal[0]`=padding
  (sempre 0), `normal[1]`=archiveId, `normal[2]`=archivePath.type, `normal[3]`=archivePath.size,
  `normal[4]`=filePath.type, `normal[5]`=filePath.size, `normal[6]`=openFlags,
  `normal[7]`=attributes; grupo traduzido 0 = buffer do archivePath, grupo traduzido 1 = buffer
  do filePath (ambos ignorados, ver Inclui item 2). Resposta: `header(cmd,1,2)`, `result`,
  `translateHandles(fileHandle)` — o `out = cmdbuf[3]` do `FSUSER_OpenFileDirectly` real bate
  com essa forma (a handle é a palavra logo após o descritor de movimentação).

### Comandos de `FSFILE:` (mesma fonte)

- **`Read`** — `header=IPC_MakeHeader(0x802,3,2)`. Request: `normal[0..1]`=offset (64 bits),
  `normal[2]`=size, grupo traduzido 0 = descritor de buffer mapeado (tipo diferente de "static
  buffer", mas o layout físico — descritor então ponteiro — é o mesmo; `IpcRequest
  .staticBufferPointer` já lê genericamente por posição, reaproveitar sem mudança). Resposta:
  `header(cmd,2,0)`, `result`, `normal(1)`=bytesRead. Ler além do fim do `byte[]` trunca
  (`bytesRead` menor que o pedido, nunca lança) — o guest real também lida com leitura parcial.
- **`GetSize`** — `header=IPC_MakeHeader(0x804,0,0)`. Resposta: `header(cmd,3,0)`, `result`,
  `normal64(1)`=tamanho do `byte[]` bruto.
- **`Close`** — `header=IPC_MakeHeader(0x808,0,0)`. Resposta: `header(cmd,1,0)`, `result`; a
  sessão correspondente é removida do `ServiceRegistry` (ver Inclui item 3).

### Modelo de sessão (mesmo mecanismo de `srv:GetServiceHandle`, sem SVC nova)

`OpenFileDirectly` não pode devolver uma sessão para um serviço **nomeado** fixo (cada arquivo
aberto precisa da sua própria instância/estado, ao contrário de `hid:USER`/`gsp::Gpu`) — usar o
mesmo truque que liga toda sessão a um nome resolvido por `ServiceRegistry`
(`SvcTable#handleSendSyncRequest` → `SessionObject#portName()` → `ServiceRegistry#resolve`):
gerar um nome sintético único por abertura (ex. `"fs:file#" + contador`), registrar uma
`FsFileService` nova sob esse nome, e devolver `handles.create(new SessionObject(nomeSintetico))`
como a handle traduzida. `FsUserService` precisa então de `HandleTable`+`ServiceRegistry`
injetados (mesmo padrão de `GspGpuService`, que já recebe `HandleTable`).

## Armadilhas

- **Não presumir que `OpenFileDirectly` precisa decodificar o path.** A simplificação (servir
  sempre o `.3dsx` em execução, ignorando o path pedido) é deliberada e documentada — não há
  cartão SD nesta emulação, e todo uso real do corpus atual é self-mount.
- **`staticBufferPointer` funciona para o descritor de `Read` mesmo sendo "buffer mapeado", não
  "buffer estático"** — o nome do método é do primeiro uso, mas a posição física (descritor,
  depois ponteiro) é idêntica; não escrever um método novo para isso.
- **A resposta de `OpenFileDirectly` devolve a handle numa posição que parece um `normalParam`
  (`cmdbuf[3]`) mas é na verdade a palavra de VALOR do grupo de handle traduzido** — usar
  `response.translateHandles(...)`, não `response.normalParam(2, handle)` (a posição de byte
  bate por coincidência de contagem, mas o campo é semanticamente uma handle movida, e o real
  3DS trata isso como capability transfer entre processos).
- `FSFILE::Read`/`GetSize` de 64 bits: usar `normalParam64`/`normal64` já existentes, não montar
  o par de palavras manualmente.

# G6.3 — `VertexShaderInterpreter`: `CMP` (formato 1c) e `MAD`/`MADI` (formato 5/5i)

**Fecha:** nenhuma issue própria ainda — candidata nascida da G6.1 (causa 2 dos 6 exemplos
`graphics/gpu` que não desenhavam).

## Contexto

A G6.1 mediu a causa real de 3 dos 6 exemplos-alvo (`fragment_light`/`lenny`/`textured_cube`):
`VertexShaderInterpreter` não implementa `CMP` (opcodes `0x2E`-`0x2F`, formato 1c) nem `MAD`/`MADI`
(opcodes `0x38`-`0x3F`/`0x30`-`0x37`, formato 5/5i) — confirmado contra
`3dbrew.org/wiki/Shader_Instruction_Set`. `MAD` é multiply-add de 3 operandos, uma das instruções
mais comuns do PICA200 — o Javadoc da classe já documentava esses dois formatos como "não
implementados" desde a G5/PR2, junto com o formato 1i e todo o controle de fluxo, por falta de
cross-validação de layout de bits contra um `.shbin` real (só transcrição de boa-fé do wiki, que
não documenta offsets de bit).

Esta task é a candidata explícita que a G6.1 e a `FILA-EXECUCAO.md` deixaram em aberto: "`G6.3`
(`VertexShaderInterpreter`: `CMP`+`MAD`)".

## Objetivo

Implementar `CMP`/`MAD`/`MADI` no `VertexShaderInterpreter`, com layout de bits validado por uma
fonte que documenta offsets reais (não o wiki), e confirmar o efeito observável real nos 3
exemplos-alvo via `--report`.

## Inclui

1. Layout de bits de `CMP` (formato 1c) e `MAD`/`MADI` (formato 5/5i), validado contra uma fonte
   que documenta os offsets — nesta sessão, o código-fonte real do
   [nihstro](https://github.com/neobrain/nihstro) (`include/nihstro/shader_bytecode.h`, o
   assembler/desassemblador de shader PICA200 usado pela comunidade de emuladores de 3DS), obtido
   via `curl` direto do arquivo raw do GitHub (o `WebFetch` da sessão não conseguiu extrair os
   `BitField<offset,width>` de forma confiável — resumia em vez de citar; `curl`+leitura direta do
   texto foi necessário).
2. `CMP`: grava o resultado nas condition codes internas do interpretador (`cmp.x`/`cmp.y`), não
   num registrador de destino normal (o formato não tem campo de destino — os bits que seriam
   `dest` no formato 1 são os dois campos de 3 bits do operador de comparação).
3. `MAD` (não invertido) e `MADI` (invertido): 3 operandos, descritor de operando de 5 bits (mesma
   tabela `operandDescriptors` do formato 1, MAD convencionalmente usa índices `<32`).
4. Teste automatizado para os três (`CMP`, `MAD`, `MADI`) — como nenhum `.shbin` real disponível
   nesta sessão usa essas instruções, os testes montam `ShaderBinary`s sintéticos com os words
   codificados bit a bit conforme o layout validado no passo 1 (não um `.shbin` compilado).
5. Rodar `--report` nos 3 exemplos-alvo (`fragment_light`/`lenny`/`textured_cube`) e atualizar a
   tabela de `g5-pr4-levantamento-exemplos.md` com o resultado real.

## Não inclui

- Formato 1i (`DPHI`/`DSTI`/`SGEI`/`SLTI`) — mesmo motivo de exclusão original (não cross-validado
  ainda).
- Controle de fluxo (`CALL`/`IFU`/`IFC`/`LOOP`/`JMPC`/`JMPU`/`BREAK`/`BREAKC`) — `CMP` grava
  condition codes, mas nada as lê ainda; isso é esperado (ver Armadilhas) e vira candidata própria
  se `fragment_light`/`lenny` esbarrarem nele (ver Resultado).
- Validação visual (janela) — `--report` headless já separa "desenha"/"não desenha"; validação
  visual fica para quando o usuário rodar (RFC D4, mesmo padrão de sempre).
- `DST`/`LITP` (formato 1, semântica especial, fora do escopo original desde a G5/PR2).

## Especificação (layout de bits, nihstro `shader_bytecode.h`)

Todos os offsets usam a convenção `bits(word, lowestBit, width)` já usada pelo resto do arquivo
(`(word >>> lowestBit) & ((1<<width)-1)`) — idêntica à convenção `BitField<offset, width>` do
nihstro (offset = bit menos significativo).

**`CMP`** (`union Instruction::Common`, especializado por `CompareOpType`):

| Campo | Bits | Notas |
|---|---|---|
| `operand_desc_id` | 0-6 (7) | mesma tabela do formato 1 |
| `src2` | 7-11 (5) | |
| `src1` | 12-18 (7) | |
| `address_register_index` | 19-20 (2) | relativo a `src1` (mesma regra do formato 1) |
| `cmp.y` (operador) | 21-23 (3) | |
| `cmp.x` (operador) | 24-26 (3) | |
| identificação do opcode | 27-31 (5) | `0b10111`; bit 26 é dado real (`cmp.x` bit 2), não
  identificação — "LSB opcode bit ignored" do nihstro |

Operadores (`CompareOpType::Op`): `0`=Equal, `1`=NotEqual, `2`=LessThan, `3`=LessEqual,
`4`=GreaterThan, `5`=GreaterEqual; `6`/`7` reservados (o nihstro chama de `Unk6`/`Unk7` — sem
consumidor real conhecido, o interpretador lança `UnsupportedOperationException` se aparecerem,
mesma disciplina de instrução não reconhecida).

**`MAD`/`MADI`** (`union Instruction::mad`):

| Campo | Bits (não invertido, `MAD`) | Bits (invertido, `MADI`) |
|---|---|---|
| `operand_desc_id` | 0-4 (5) | 0-4 (5) |
| `src3` | 5-9 (5) | — |
| `src3i` | — | 5-11 (7) — campo "largo", pode referenciar uniform |
| `src2` | 10-16 (7) — campo "largo" | — |
| `src2i` | — | 12-16 (5) |
| `src1` | 17-21 (5) | 17-21 (5) — mesma posição nos dois casos |
| `address_register_index` | 22-23 (2) | 22-23 (2) — aplica-se ao operando LARGO (src2 se não
  invertido, src3 se invertido) |
| `dest` | 24-28 (5) | 24-28 (5) |
| identificação do opcode | 29-31 (3) | `0b111` (`MAD`, `0x38`-`0x3F`) / `0b110` (`MADI`,
  `0x30`-`0x37`); bits 26-28 são dado real (parte de `dest`), não identificação — "lower 3 opcode
  bits ignored" do nihstro |

`src1` nunca é o operando "largo" (só 5 bits, não alcança o espaço de constantes `≥32`) — só um dos
outros dois pode ser uniform, e o endereçamento relativo (`idx`) só se aplica a esse operando largo,
mesma regra geral do formato 1 (`src1`/`src2` invertidos).

**Descritor de operando** (`union SwizzlePattern`, mesma tabela `operandDescriptors[]` de sempre —
`MAD` usa 3 slots em vez de 2):

| Campo | Bits |
|---|---|
| `dest_mask` | 0-3 |
| `negate_src1` | 4 |
| `src1_selector` | 5-12 |
| `negate_src2` | 13 |
| `src2_selector` | 14-21 |
| `negate_src3` | 22 |
| `src3_selector` | 23-30 |

   inteiros antes de mexer.
2. Generalizar `readSource` para um terceiro slot de operando (`OPERAND_SRC3`, usado só por

   ainda, então sem isso `CMP` não teria efeito observável testável).

## Armadilhas

- **Bits "ignorados" na identificação do opcode são dados reais** — não usar o valor de opcode já
  mascarado (`bits(word,26,6)`) dentro de `compare`/`multiplyAdd`; reler os campos direto do `word`
  bruto.
- **`WebFetch` sobre o wiki do 3dbrew retorna 403** nesta sessão — e mesmo fontes secundárias
  (nihstro `instruction_set.md`, documentação de alto nível) não têm offset de bit. Só o
  código-fonte (`shader_bytecode.h`) tem os `BitField`s reais; buscar via `curl` direto (raw
  GitHub), não `WebFetch` (que resumiu a estrutura em vez de citar os números).
- **Não presumir que `CMP` desbloqueia sozinho `fragment_light`/`lenny`** — eles usam `CMP` seguido
  de um salto condicional (`JMPC`), que continua fora do escopo desta task; o resultado esperado é
  um bloqueio NOVO e mais adiante, não o exemplo desenhando.

## Resultado (2026-08-27)

Implementado exatamente como especificado. **Achado de ambiente**: o `WebFetch` sobre
`3dbrew.org/wiki/GPU/Shader_Instruction_Set` retornou 403 (bloqueio do servidor); uma tentativa via
`WebFetch` sobre o `shader_bytecode.h` do nihstro (raw GitHub) devolveu um RESUMO da estrutura em
vez dos `BitField`s literais (o modelo do `WebFetch` reformula em vez de citar) — teve confiabilidade
duvidosa o bastante para não ser usado direto; a fonte final foi `curl` (Bash) do arquivo raw do
GitHub, lido com `grep`/`sed`, e os offsets/enums transcritos verbatim deste código-fonte real (não
do wiki, que não documenta bits, nem do resumo do `WebFetch`).

**Achado de decode** (documentado, "não presumir sem checar" — mesma disciplina de sempre): os bits
"ignorados" na identificação de `CMP`/`MAD`/`MADI` (LSB do opcode de `CMP`, 3 bits baixos do opcode
de `MAD`/`MADI`) são DADOS reais que também compõem outro campo (`cmp.x`/parte de `dest`) — resolvido
despachando por faixa de opcode (`opcode>=0x38`→`MAD`, `opcode>=0x30`→`MADI`,
`opcode∈{0x2E,0x2F}`→`CMP`) ANTES do `switch` do formato 1, e relendo os campos direto do `word` bruto
dentro de cada handler (nunca do valor de opcode já mascarado pelo dispatch).

`readSource` generalizado de um `boolean isSrc1` binário para um `int operandSlot` de 3 valores
(`OPERAND_SRC1`/`SRC2`/`SRC3`, com tabelas `OPERAND_NEGATE_BIT`/`OPERAND_SELECTOR_SHIFT`) — mudança
aditiva/interna à classe (`private`), sem efeito nos formatos 1/1u/mova já existentes (só passaram a
nomear os slots 0/1 em vez de `true`/`false`).

`run()` público manteve a assinatura (retorna só `float[][]`); `runDetailed()` novo (+ `record
Result(float[][] output, boolean[] conditionCode)`) expõe `cmp.x`/`cmp.y` só para permitir teste
automatizado do efeito observável de `CMP` — nenhum consumidor real lê essas condition codes ainda
(sem `JMPC`/`IFC`/`BREAKC`), então hoje elas só existem para essa finalidade de teste.

3 testes sintéticos novos em `VertexShaderInterpreterTest` (`ShaderBinary`s montados à mão, words
calculados via shift em Java, não hex decorado): `CMP` com `LessThan`/`GreaterEqual` provando que os
dois operadores de 3 bits são independentes por componente; `MAD` (registrador) calculando
`src1*src2+src3` com `src2` no campo largo; `MADI` (invertido) provando que o campo largo migra para
`src3` — usado para referenciar uma constante float (`c0`, índice 32, só alcançável com 7 bits, prova
que a inversão realmente troca qual operando pode ser uniform). `mvn -o test` verde no n3dsemu (209,
+3 novos). G5-invariante não se aplica (nenhum arquivo do arm-jitter tocado).

**Efeito real medido nos 3 exemplos-alvo** (`--report --slices=3000`, binários já existentes de
sessões anteriores):

- `textured_cube`: **destravado por completo** — `desenhos=605 vertices=21780` (antes: 0, morria no
  opcode `MAD` não implementado). Não validado visualmente ainda (RFC D4, fica para o usuário).
- `fragment_light`/`lenny`: **não morrem mais no `CMP`**, mas revelam um bloqueio NOVO e mais adiante
  — opcode `0x2C` (`JMPC`, salto condicional) não implementado, exatamente a Armadilha antecipada na
  spec (usam `CMP` seguido de salto condicional). `desenhos=0` continua, mas por um motivo
  DIFERENTE e mais profundo — candidata a task própria (família de controle de fluxo `JMPC`/`JMPU`/
  `IFC`/`IFU`/`CALL*`/`BREAK*`, mesmo padrão de "achado vira candidata" da trilha G).

Tabela de `g5-pr4-levantamento-exemplos.md` atualizada com os 3 resultados reais (não mais
"causa achada, sem correção").

**Candidata nova, não pega automaticamente**: controle de fluxo do vertex shader (`JMPC`/`JMPU`/
`IFC`/`IFU`/`CALL`/`CALLC`/`CALLU`/`LOOP`/`BREAK`/`BREAKC`) — desbloquearia `fragment_light`/`lenny`
e é pré-requisito para qualquer shader com condicional/laço real (`3dbrew` já cita `LOOP` como usado
por outros exemplos do corpus, ex. `textured_cube` original, que já funciona sem laços neste caso).

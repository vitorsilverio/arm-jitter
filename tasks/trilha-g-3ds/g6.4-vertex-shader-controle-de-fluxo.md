# G6.4 — `VertexShaderInterpreter`: controle de fluxo (`JMPC`/`JMPU`/`IFC`/`IFU`/`CALL*`/`LOOP`/`BREAK*`)

**Fecha:** nenhuma issue própria ainda — candidata nascida da G6.3 (bloqueio novo achado em
`fragment_light`/`lenny`, opcode `0x2C`/`JMPC`).

## Contexto

A G6.3 implementou `CMP`/`MAD`/`MADI` no `VertexShaderInterpreter` e mediu o efeito real nos 3
exemplos-alvo (`--report`): `textured_cube` destravou por completo, mas `fragment_light`/`lenny`
revelaram um bloqueio NOVO e mais adiante — `CMP` grava `cmp.x`/`cmp.y`, mas nada os lê ainda, e os
dois exemplos usam `CMP` seguido de um salto condicional (`JMPC`, opcode `0x2C`), que continua fora
do escopo até esta task. `VertexShaderInterpreter` documenta desde a G5/PR2 que TODO o controle de
fluxo (`CALL`/`IFU`/`IFC`/`LOOP`/`JMPC`/`JMPU`/`BREAK`/`BREAKC`) está fora — sem ele nenhum shader com
condicional ou laço real funciona.

## Objetivo

Implementar o controle de fluxo completo do PICA200 no `VertexShaderInterpreter` (formatos 2/3/4/6 do
3dbrew), com semântica validada contra uma implementação de referência real (não só o layout de
bits), e confirmar o efeito observável em `fragment_light`/`lenny` via `--report`.

## Inclui

1. Layout de bits (`union Instruction::FlowControlType`, nihstro `shader_bytecode.h`, mesma fonte
   já usada pela G6.3, obtida via `curl` do raw do GitHub — não `WebFetch`, que resumiu em vez de
   citar na G6.3).
2. **Semântica completa** (o layout de bits sozinho não basta — o nihstro documenta só os campos,
   não o algoritmo de pilhas), validada contra o interpretador de referência real do **Citra**
   (`src/video_core/shader/shader_interpreter.cpp`, obtido nesta sessão via `curl` do fork
   `lime3ds/lime3ds` — o `citra-emu/citra` original está fora do ar/renomeado, ver Armadilhas):
   pilha de `IF` (`if_stack`), pilha de `CALL` (`call_stack`), pilha de `LOOP` (`loop_stack`), a
   ordem de verificação por instrução (`CALL`→`IF`→`LOOP`) e o truque de paridade do `JMPU`.
3. `JMPC`/`JMPU`: salto condicional, sem pilha.
4. `IFC`/`IFU`: bloco condicional com "senão" opcional (pilha de `IF`).
5. `CALL`/`CALLC`/`CALLU`: chamada de sub-rotina com retorno (pilha de `CALL`).
6. `LOOP`: laço com contador/incremento vindos de uma constante inteira (`aL`, pilha de `LOOP`).
7. `BREAK`/`BREAKC`: sai do laço mais interno.
8. Avaliação de condição (`cmp.x`/`cmp.y` combinados por `AND`/`OR`/`JustX`/`JustY`, com inversão
   por `refx`/`refy`) — mesmo `Op` do 3dbrew, compartilhado por `JMPC`/`IFC`/`CALLC`/`BREAKC`.
9. Teste automatizado para cada instrução nova (programas sintéticos, mesmo padrão da G6.3 — sem
   `.shbin` real disponível que use laços/condicionais ainda).
10. Rodar `--report` em `fragment_light`/`lenny` e atualizar a tabela de
    `g5-pr4-levantamento-exemplos.md`.

## Não inclui

- Formato 1i (`DPHI`/`DSTI`/`SGEI`/`SLTI`) — mesma exclusão de sempre, não cross-validado.
- `EMIT`/`SETEMIT` (formato 4, geometry shader only) — `VertexShaderInterpreter` só roda vertex
  shader (RFC D1), sem consumidor real.
- Fidelidade de overflow das pilhas: o Citra usa `boost::circular_buffer` (8 níveis de `IF`, 4 de
  `CALL`, 4 de `LOOP` — descarta o mais antigo ao estourar). Esta task usa uma pilha comum
  (`ArrayDeque`) sem limite de profundidade — shaders reais do corpus atual não chegam perto desses
  limites; documentar como simplificação conhecida, não presumir sem checar se algum consumidor
  real algum dia estourar.
- Validação visual (janela) — RFC D4, fica para o usuário.

## Especificação (nihstro `shader_bytecode.h`, `union Instruction::FlowControlType`)

Mesma convenção `bits(word, lowestBit, width)` do resto do arquivo.

| Campo | Bits | Usado por |
|---|---|---|
| `num_instructions` | 0-7 (8) | `CALL`/`CALLC`/`CALLU` (tamanho da sub-rotina); `IFC`/`IFU` (tamanho do bloco "então"); `JMPU` (bit 0 = inversão de condição, resto ignorado) |
| `dest_offset` | 10-21 (12) | endereço-alvo (semântica varia por instrução, ver Especificação de semântica) |
| `op` (`Or`=0/`And`=1/`JustX`=2/`JustY`=3) | 22-23 (2) | `JMPC`/`IFC`/`CALLC`/`BREAKC` |
| `bool_uniform_id` | 22-25 (4) | `JMPU`/`IFU`/`CALLU` (mesmos bits físicos de `op`+`refy`+parte de `refx`, mas mutuamente exclusivo por opcode) |
| `int_uniform_id` | 22-23 (2) | `LOOP` (mesmos bits físicos de `op`) |
| `refy` | 24 (1) | `JMPC`/`IFC`/`CALLC`/`BREAKC` |
| `refx` | 25 (1) | `JMPC`/`IFC`/`CALLC`/`BREAKC` |

Opcodes (`OpCode::Id`, já conferidos contra `3dbrew`): `BREAK=0x20` (trivial, sem operando —
formato 0), `BREAKC=0x23`, `CALL=0x24`, `CALLC=0x25`, `CALLU=0x26`, `IFU=0x27`, `IFC=0x28`,
`LOOP=0x29`, `JMPC=0x2C`, `JMPU=0x2D`. Todos identificados pelo `opcode` de 6 bits normal
(bits 26-31) — sem bits "ignorados" como `CMP`/`MAD`/`MADI` da G6.3.

**Avaliação de condição** (`JMPC`/`IFC`/`CALLC`/`BREAKC`, `evaluate_condition` do Citra):

```
resultX = (refx == conditionCode[0])
resultY = (refy == conditionCode[1])
op == Or    -> resultX || resultY
op == And   -> resultX && resultY
op == JustX -> resultX
op == JustY -> resultY
```

**Semântica de pilha por instrução** (transcrita fielmente de `RunInterpreter`, Citra
`shader_interpreter.cpp` — variáveis: `pc` = program counter da instrução ATUAL antes de qualquer
salto, `fallthrough = pc + 1`):

- `JMPC`: se condição verdadeira, próximo pc = `dest_offset`; senão `fallthrough`. Sem pilha.
- `JMPU`: se `boolConstants[bool_uniform_id] == !(num_instructions & 1)`, próximo pc =
  `dest_offset`; senão `fallthrough`. (O bit 0 de `num_instructions` funciona como flag de
  inversão da condição — achado real do hardware, não documentado no nihstro além do campo bruto.)
  Sem pilha.
- `CALL`: empilha `{endAddress: dest_offset + num_instructions, returnAddress: fallthrough}`;
  próximo pc = `dest_offset`.
- `CALLC`/`CALLU`: como `CALL`, mas só se a condição for verdadeira; senão só `fallthrough`, sem
  empilhar.
- `IFC`/`IFU`: se condição verdadeira, empilha `{elseAddress: dest_offset, endAddress: dest_offset +
  num_instructions}`; próximo pc = `fallthrough` (entra no bloco "então"). Se falsa, próximo pc =
  `dest_offset` (pula direto para o "senão"/fim); NÃO empilha.
- `LOOP`: seja `loopParam = intConstants[int_uniform_id]` (`x`=contador, `y`=valor inicial de `aL`,
  `z`=incremento, `w` não usado); empilha `{entryAddress: fallthrough, endAddress: dest_offset + 1,
  loopDownCounter: loopParam.x, addressIncrement: loopParam.z, previousAL: aL atual}`; grava
  `aL = loopParam.y`; próximo pc = `fallthrough`.
- `BREAK`: marca "quebra de laço" para esta instrução (não altera pc diretamente — o
  processamento de pilha abaixo decide o destino real).
- `BREAKC`: como `BREAK`, mas só marca "quebra" se a condição for verdadeira.

**Processamento de pilha, executado APÓS toda instrução** (independente do opcode, na ordem
CALL→IF→LOOP — mesma ordem do Citra, comentário original: "Stacks are checked in the order CALL ->
IF -> LOOP"):

```
fallthrough = pc + 1               // pc = valor ANTES de qualquer salto desta instrução
probe = fallthrough
repita até 4 vezes:
    se pilha-CALL vazia OU topo.endAddress != probe: pare
    se não é a 4ª repetição: próximoPc = topo.returnAddress; probe = próximoPc
    desempilha CALL
    // "bug de hardware": ao estourar 4 escopos CALL de uma vez, o último não atualiza o pc

se pilha-IF não vazia E topo.elseAddress == fallthrough:
    próximoPc = topo.endAddress
    desempilha IF

se pilha-LOOP não vazia E (topo.endAddress == fallthrough OU marcado "quebra"):
    aL += topo.addressIncrement
    contadorAntigo = topo.loopDownCounter; topo.loopDownCounter -= 1  (decremento não-saturante,
        o valor ANTIGO é o que importa para a decisão abaixo)
    se NÃO "quebra" E contadorAntigo != 0:
        próximoPc = topo.entryAddress   // repete o corpo do laço
    senão:
        próximoPc = topo.endAddress     // sai do laço
        se pilha-LOOP tinha mais de 1 elemento: aL = topo.previousAL
        desempilha LOOP
```

O `próximoPc` calculado pela instrução em si (`JMPC`/`CALL`/etc.) é a base; o processamento de
pilha acima pode SOBRESCREVER esse valor de novo (ex.: uma `CALL` cujo alvo é o `fallthrough` de
outra `CALL` que termina exatamente ali fecha os dois escopos no mesmo passo). Isto é
intencional — replica o comportamento real do PICA200, não um detalhe de implementação do Citra
a ignorar.

## Armadilhas

- **O layout de bits sozinho não chega perto de bastar aqui** — ao contrário de `CMP`/`MAD`
  (G6.3, puramente combinacional), controle de fluxo tem estado (3 pilhas) e uma ordem de
  verificação não-óbvia. Ler o `shader_interpreter.cpp` de referência inteiro antes de escrever
  qualquer coisa — não inventar a máquina de pilha a partir só dos nomes dos campos.
- **`citra-emu/citra` não existe mais nesse caminho** (repo original arquivado/renomeado, `curl`
  devolve 404) — usar o fork `lime3ds/lime3ds` (raw GitHub), que manteve o arquivo
  `src/video_core/shader/shader_interpreter.cpp` com a mesma lógica.
- **`WebFetch` não é confiável para citar código-fonte literal** (achado da G6.3, reconfirmado
  aqui) — usar `curl` direto no raw do GitHub e ler o texto puro.
- **A checagem de fim de pilha usa `pc + 1` do INÍCIO da instrução, não o valor já sobrescrito por
  um salto que a própria instrução acabou de fazer.** É fácil "simplificar" isso incorretamente
  (usar o valor final direto) — o efeito só aparece quando um `JMPC`/`CALL` termina bem na
  fronteira de um escopo (`IF`/`LOOP`/`CALL`) mais externo; não presumir que não importa.
- **`loop_downcounter--` é decremento pós-condição**: a decisão de continuar o laço usa o valor
  ANTES do decremento; o decremento acontece de qualquer forma (mesmo quando o laço termina).
- **Não presumir que isto desbloqueia `fragment_light`/`lenny` até rodar `--report`** — mesmo
  padrão de cautela da G6.3 (`CMP` não desbloqueou sozinho, revelou `JMPC`); pode haver mais um
  degrau adiante (ex.: uma instrução de formato não coberto ainda).

## Resultado (2026-08-27)

Implementado exatamente como especificado. `citra-emu/citra` de fato não existe mais nesse caminho
(`curl` devolveu 404); o fork `lime3ds/lime3ds` (raw GitHub) tinha o `shader_interpreter.cpp` com a
mesma lógica (`RunInterpreter`), usado como fonte da semântica de pilha — o layout de bits veio do
`shader_bytecode.h` do nihstro (mesma fonte da G6.3, `curl` direto, não `WebFetch`).

`VertexShaderInterpreter.Run` ganhou 3 pilhas (`ArrayDeque<CallStackElement>`/`IfStackElement`/
`LoopStackElement`, sem limite de profundidade — simplificação documentada no Javadoc/"Não inclui"),
uma flag `isBreak` por passo, e um terceiro registrador de endereço (`addressRegisterAl`, antes um
campo `loopCounter` final sempre `0`, "LOOP não implementado"). `execute()` passou a chamar
`resolveNextPc(oldPc, nextPc)` depois de cada instrução — método novo que replica fielmente o bloco
de pós-processamento do Citra (ordem `CALL`→`IF`→`LOOP`, uso de `fallthrough = oldPc+1` em vez do
`nextPc` já calculado pela própria instrução para decidir fim de escopo, e o "bug de hardware" real
de só não atualizar o pc ao fechar a 4ª chamada empilhada de uma vez).

Cada instrução nova (`JMPC`/`JMPU`/`CALL`/`CALLC`/`CALLU`/`IFC`/`IFU`/`LOOP`/`BREAK`/`BREAKC`) foi
implementada como um `case` novo no `switch` de `step()`, despachando para `doCall`/`doIf`/`doLoop`
(ou inline para os casos sem estado — `JMPC`/`JMPU`/`BREAK`/`BREAKC`) e uma `evaluateCondition(word)`
compartilhada (`Or`/`And`/`JustX`/`JustY` combinando `cmp.x`/`cmp.y` com `refx`/`refy`).

**Achado real, não previsto na especificação inicial**: os testes sintéticos originalmente
tentavam usar um registrador de SAÍDA (`o0`) como acumulador dentro do laço (`o0 += v0` a cada
iteração) — mas registradores de saída não são legíveis como fonte no PICA200 real (`readRegister`
só mapeia índices `0-15` para `input[]`, nunca para `output[]`); corrigido usando um registrador
TEMPORÁRIO (`r0`, índice 16) como acumulador dentro do laço, com um `MOV r0,o0` fora dele para tornar
o resultado observável — mesmo padrão que qualquer shader PICA200 real usaria.

6 testes sintéticos novos em `VertexShaderInterpreterTest` (programas montados à mão, words
calculados via shift em Java): `JMPC` tomado/não-tomado, `IFC` com bloco "então" executado/pulado,
`CALL` com retorno correto para depois do ponto de chamada, `LOOP` repetindo o corpo o número certo
de vezes (contador `N` → `N+1` iterações, convenção confirmada contra o Citra), `BREAKC` saindo do
laço antes do contador natural terminar. `mvn -o test` verde no n3dsemu (215, +6). G5-invariante não
se aplica (nenhum arquivo do arm-jitter tocado).

**Efeito real medido** (`--report --slices=3000`, binários já existentes de sessões anteriores):

- `lenny`: **destravado por completo** — `desenhos=568 vertices=1899960` (antes: 0, mesmo bloqueio).
  Não validado visualmente ainda.

antes 8/20).

# G3.3 — investigar por que a thread principal de `read-controls.3dsx` nunca é reescalonada

**Trilha:** G · **Depende de:** G3.2 (PARCIAL, commit pendente desta sessão) · **Repo:** n3dsemu
**Leia a RFC-N3DSEMU.md antes.** Task de INVESTIGAÇÃO — o objetivo é isolar a causa raiz e decidir
o fix, não implementar G4 (Vulkan) nem nenhum serviço novo.

## Contexto

A G3.2 (2026-08-18) corrigiu o bug real do `GSP_MODULE_THREAD_INDEX` (a thread de relay do
`gsp::Gpu` agora drena a fila de interrupções de verdade a cada VBlank) mas revelou um bloqueio
NOVO e mais profundo: mesmo com o relay funcionando, a thread PRINCIPAL de `read-controls.3dsx`
nunca volta a ser escalonada — confirmado rodando até 29.377 ciclos de VBlank sem nenhuma `svc` da
main thread aparecer no trace.

## Achado desta sessão (investigação já executada, ver resumo abaixo)

**Não é um bug do `Scheduler`.** Instrumentação temporária (não commitada — trace de
`switchTo`/`blockOnArbiter`/`signalArbiter` atrás de `-Dn3dsemu.trace.sched=1`, revertida ao final
desta sessão) confirmou que o escalonador cooperativo funciona exatamente como projetado: seleção
por prioridade, FIFO de esperadores, pulso periódico e fast-forward do relógio virtual — tudo
correto.

**Causa raiz real, isolada com evidência**: a thread principal (`T1`, prioridade `48`) chama
`svcArbitrateAddress` (`WAIT_IF_LESS_THAN`/`_TIMEOUT`, `r0`=handle do arbiter=`3`, `r1`=endereço
`0x0011D26C`, sem timeout — `hasTimeout=false`) em `pc=0x00105DA0` **imediatamente após**
`svcCreateThread` (que cria a thread de relay `T2`, prioridade `26`, entry `0x00107314`) — e
**bloqueia para sempre**: nenhum código observado em toda a execução (nem a própria `T2`, nem
nenhum serviço IPC implementado) jamais sinaliza o endereço `0x0011D26C`. `T2`, por sua vez,
sinaliza repetidamente apenas dois endereços diferentes: `0x0011D25C` (uma única vez, no
cold-start) e `0x0011D294` (a cada VBlank, via `GspGpuService#onVBlank` → fila de interrupção →
`svcArbitrateAddress(SIGNAL)`).

Os três endereços (`0x11D25C`/`0x11D26C`/`0x11D294`) estão próximos o bastante (mesma região de
~0x11D2xx) para serem campos/elementos de UMA estrutura só — hipótese mais forte, apoiada por
fonte real do libctru (via `WebFetch` em
`github.com/devkitPro/libctru/.../services/gspgpu.c`/`include/3ds/synchronization.h` nesta sessão,
não por analogia): é o array `LightEvent gspEvents[GSPGPU_EVENT_MAX]` (`LightEvent` = 8 bytes,
`s32 state` + `LightLock lock`) que `gspEventThreadMain()` (a própria `T2`) sinaliza via
`LightEvent_Signal(&gspEvents[curEvt])` para cada entrada que desenfileira da fila de interrupção
compartilhada — `curEvt` é o BYTE de tipo de interrupção lido da fila, e este HLE só empurra UM
tipo (`GspGpuService.INTERRUPT_TYPE_PDC0_VBLANK_TOP = 2`, decisão de escopo já registrada — RFC
D6, "só a tela de cima é composta"). **A aritmética exata de offset não fechou nesta sessão**
(assumindo passo de 8 bytes, `0x11D294` bateria com um índice fora do array de 7 elementos
partindo de `0x11D25C` — os números não se encaixam limpos o bastante para eu afirmar QUAL índice
`0x0011D26C` representa sem símbolos de depuração reais), mas a hipótese qualitativa é forte e
consistente com a decisão de escopo já tomada: **T1 está esperando um `GSPGPU_Event` específico
(candidato mais provável: `GSPGPU_EVENT_VBlank1`, tela de baixo, ou algum outro tipo — `PSC0`/
`PSC1`/`PPF`/`P3D`/`DMA` — que este HLE nunca gera porque só implementa o marco mínimo do M3)**.

## Objetivo

Confirmar (ou refutar) com evidência qual `GSPGPU_Event` específico o endereço `0x0011D26C`
representa, e decidir o fix: ou (a) este HLE precisa passar a gerar esse tipo de interrupção
também (ex.: `VBlank1`/tela de baixo, ampliando `GspGpuService#onVBlank`), ou (b) é outra
descoberta (ex.: `T1` na verdade não deveria estar chamando isso neste ponto — um bug de
sequenciamento em outro serviço que faz o guest tomar um caminho de código que não deveria).

## Como reproduzir o trace desta sessão

Instrumentação usada (não commitada, recriar conforme necessário) — 3 blocos `System.err.println`
atrás de `System.getProperty("n3dsemu.trace.sched") != null`:

1. Em `Scheduler#switchTo`, antes do primeiro `if`: log de `tick`/thread atual→próxima/prioridades/
   estado de todas as threads (`ThreadObject#state()`/`#priority()`, ambos já acessíveis dentro do
   pacote `kernel`).
2. Em `Scheduler#blockOnArbiter`, antes de `current.blockWaitingArbiter(...)`: log de
   `tick`/thread/`arbiter` (`System.identityHashCode`)/`address`/`hasTimeout`/`timeoutNanos`/
   `core.register(15)` (PC).
3. Em `Scheduler#signalArbiter`, no topo do método: log de `tick`/thread atual/`arbiter`/`address`/
   `maxCount`/quantos esperadores há AGORA naquele endereço.

Build + execução (JBR 25, ver `arm-jitter/tasks/FILA-EXECUCAO.md` para o caminho):

```
mvn -o -q dependency:build-classpath -Dmdep.outputFile=cp.txt
java -Dn3dsemu.trace.sched=1 -cp "target/classes;$(cat cp.txt)" \
    dev.vitorsilverio.n3dsemu.Main --slices=18 testdata/read-controls.3dsx
```

`--slices=18` é o menor orçamento que já alcança o bloqueio de `T1` (confirmado nesta sessão por
busca binária: 15 fatias não bastam, 18 já mostram `T1 BLOQUEIA`). Passar `--trace-svc` também
imprime as últimas 32 `svc`s no fim — com `--slices=18` a sequência completa desde o boot até o
bloqueio ainda cabe no anel de 32, é isso que gerou o relato desta task.

## Armadilhas

- **`application.3dsx` não serve de repro** — use `read-controls.3dsx` (sem precisar de
  `--script`/tecla nenhuma: o bloqueio acontece durante a INICIALIZAÇÃO, antes de qualquer loop de
  input).
- Sem `libctru` fonte nesta máquina (mesma lacuna documentada em G2.2/G3.2) — `WebFetch` direto em
  `raw.githubusercontent.com/devkitPro/libctru/master/libctru/{source,include}/...` funcionou bem
  nesta sessão (achado real: retorna C real, não precisa de git clone) — prefira isso a
  desmontagem pura quando a pergunta for "o que este primitivo FAZ", e desmontagem quando a
  pergunta for "que ENDEREÇO/valor real o guest usa".
- `r0`/`r1` de `svcArbitrateAddress` no log de `SvcCall`/`--trace-svc` são **handle do arbiter** e
  **endereço**, NÃO o `type` (`r2`, não logado por `SvcCall` — só tem `r0`/`r1`/`pc`, ver
  `kernel/SvcCall.java`). Não confundir `r0=3` (handle) com `ArbitrationType.WAIT_IF_LESS_THAN_
  TIMEOUT` (também `3`) — coincidência de valor que já confundiu esta sessão brevemente.
- Se a investigação não isolar a causa dentro do orçamento normal de sessão (~60-80 tool calls,
  disciplina do `arm-jitter/tasks/FILA-EXECUCAO.md`), pare e documente o que foi descartado — não é
  obrigatório fechar tudo numa sessão só.
